# Durable Auth/Access capability implementation split

This is a local implementation handoff, not a replacement for discussion doc20 or ADR0035. No topic is moved between repositories. Scope is missing production capability bindings only; no product implementation, replacement policy engine, account model, or full Auth host in kernel registration is delivered here.

## Evidence and reusable authority

Read the branch's `services/kernel/src/access/{auth-bindings,operator,lifecycle}.ts`, `services/auth/src/{workflows,index}.ts`, the staged `discussion/docs/engineering/20-accounts-and-auth.md` and `discussion/docs/adr/0035-thin-access-native-and-standard-controls.md`. The AuthBindingCapabilities callbacks validate returned shapes and account facts; they do not establish provenance. `workflow-handle-fixture.ts` resolves `authorizeOperation` through an approvals Map containing bearer tokens. That fixture is not a deployment binding.

Reuse these native authorities before adding storage:

- `createLifecycleInternals.createPending` commits `access.actor-pending` through `lifecycleExecutor`, returning account, registration reservation and expiry. The core receipt exact key is `(partition_no, actor_account_id, command_kind, idempotency_key)`; lifecycle keys include route. The command digest includes route, target, kind, actor/client/principal basis and input. Its committed response and transaction identity are the provisioning authority, not `auth_registration_stage` existence or reservation-shaped strings.
- `readFenceReceipt(accountId, receiptId)` already seeks `(route, account_id, receipt_id)`. `readFenceState` supplies the current persistent fence and exact bigint floor. `raiseFence` commits the floor and receipt together. `clearFence` requires exact receipt/floor plus trusted new establishment evidence; preserve this separate command.
- `createOperatorCommands.authorizeOpening/consumeOpening` and `operator_opening_{insert,consume}.sql` already bind operator, subject, human, client, scopes, principal, relation version/reservation, floors, action and purpose. A native opening expires after 60 seconds. Consumption is a conditional exact-key UPDATE on `(route, operator_account_id, receipt_id)` and refuses replayed issuance, even on lost acknowledgement. Keep that authority; broad `credential-management` does not authorize another exact Auth purpose.
- `accessCommandAuthorization` rechecks before core receipt lookup on every command attempt at authoritative T. Its explicit `self-account-read` policy yields receipt-only access; it cannot execute a body. Recovery's fenced active human reader is separate from ordinary active-account reads. Preserve both exceptions without generalizing them to workflow approval.

## Minimal implementation tasks, in dependency order

1. **Access receipt readers and native capability contracts.** Add a trusted `readPendingRegistrationReceipt({ accountId, commandKey, digest })` that derives route/partition and fixed internal actor/kind, seeks the existing committed core receipt once, verifies digest/transaction and complete pending value, then checks current private registration ID/expiry and account eligibility. Do not accept caller-selected SQL key components or search responses by account/history. Expose a nonsecret reference encoding only the bounded locator and integrity binding. Retain the original command locator durably in Auth registration staging as part of the existing workflow; do not reconstruct it by enumeration. Existing `provisioningReference` and `verifyProvisioningReceipt` use this API. A rolled-back/uncommitted, unrelated-kind, expired or mismatched receipt fails closed. Independently reuse committed Auth provisioning evidence for activation; no Auth reads from kernel evidence resolvers.
2. **Authenticated workflow approval contract and persistence.** Add `approveAccountOperation(context, { operationKey, operation }) -> { reference, expiresAt }`, and `resolveAccountOperation(reference, operation) -> LifecycleRequest`. Approval runs through current authenticated request context and the mounted action catalogue. Bind canonical complete operation and stable workflow key, actor, authenticated epoch, client, original consented scopes, verified principal assignment reference, target, purpose and digest. Resolution reconstructs bounded native request evidence from committed nonsecret facts, never from a stored bearer, supplied actor object or callback Map. Current account/floor, consent, assignment and actor/principal grants are re-read through existing Access prepare/authorize. Original scopes are an upper bound; later consent cannot broaden this approval. Unknown/unavailable evidence denies.
3. **Exact workflow integration.** Implement the real `AccountWorkflowPorts.authorizeOperation` binding with task 2 and call it inside every protected step, including reservation/coordination mutations, fanout pages and Auth-effect steps. A cached DBOS authorization step is insufficient. Thread operation identity into these steps without serializing contexts. Use native command authorization for final resource checks at T on each retry. Before returning an already completed DBOS operation, reauthorize its exact request; otherwise the DBOS result shortcut could disclose a denied stored result. Reuse original command keys/digests/receipts for permitted replay: same receipt, one effect, no renewed approval. Internal service continuations must have explicitly bounded purpose/operation authority, never a generic service allow.
4. **Exact Auth effect binding.** Add `approveAuthEffect(context, { subjectAccountId, purpose, effectDigest, operationKey })` and `consumeAuthEffect(reference, SessionProof, exactEffect)`. Bind the precise Auth purpose and digest in addition to native operator opening identity. For automation use existing operator commands and consume exactly once with current relationship/epochs/management grant; own-credential sign-in remains Auth's independent native path. Serialize no credential plaintext into Access or DBOS; digest sensitive input with a trusted keyed commitment in Auth, and stage credentials only using existing encrypted Auth staging. Consumption/issuance must use one native Auth effect receipt keyed by the consumed opening and exact effect. A second consumer never issues; an acknowledged durable workflow replay may return its existing receipt after current authorization, without consuming a new opening. Lost acknowledgement must fail closed unless a committed exact issuance receipt proves completion; never reopen the native opening.
5. **Consent/recovery barrier capabilities.** Add a trusted `commitAuthInvalidation({ accountId, previousFloor, reason, operationKey, proofReference })`. Compare expected floor and commit its increase/fence/receipt atomically on the account anchor using lifecycle authority; expose exact previous/new floor, account and receipt. `invalidateAccount` is called only from Auth's authenticated consent-reduction path, and `authorizeRecovery` only after Auth verifies/consumes the actual current recovery proof. Bare account/epoch JSON cannot invoke these capabilities. Re-read the exact committed fence receipt and current account floor before any credential/session mutation. Bind the proof's account and epoch to the barrier; failed Auth work retains the fence. Trusted new establishment evidence is needed later to clear that exact fence; never clear from an old barrier/proof. Missing capabilities fail before protected Auth effects. Auth owns recovery/provisioning receipt persistence; Access owns account state/floor.
6. **Composition and verification.** Provide a pure Access-only kernel membership registrar exposing only Access commands/readers. The Auth host composes capability adapters, native credential workflows and schedules. Kernel registration must not import `createAuthHost`, open an Auth database, initialize an Auth executor, or call kernel-to-Auth maintenance RPC. Implement the test-only driver using real APIs/SQL/DBOS with process restarts, checkpoints and independent read observations; no model or test-local policy evaluator. Run the frozen outcomes against that binding, native receipt/opening tests, focused formatting/types, and the growth checks below. Existing suites remain untouched.

## Storage, cost and cleanup

Reuse native command and opening receipts first. A generic operation approval lacks a native durable authority today, so its minimal Access row, if needed, lives on the approving actor/subject anchor: primary key `(route, approving_account_id, reference_id)`, route derived from that account. Store immutable bounded identity/evidence locators, exact canonical digest/key/target/purpose, epochs and explicit expiry. No tokens, refresh tokens, plaintext credentials or serialized permission contexts. Do not duplicate grant truth. For operator openings retain their existing operator-resource anchor and exact native seek; an exact Auth-purpose adapter refers to that existing opening rather than copying its authority.

One reference resolution performs one route-leading exact row/receipt seek O(log R), bounded target/account/evidence point reads and the existing actor-side formula O((1+K)log G), K<=1000 per actor/principal. R=N+U*t+M. No lookup scans approvals for an account or enumerates command history. Consumption changes O(1) rows, using compare-and-set plus the native command/effect receipt. Route movement and locator decoding fail closed on invalid identities.

Add an expiry index `(partition_no, expires_at, route, approving_account_id, reference_id)` (or the existing partition-local equivalent), and the equivalent expiry index for native opening rows if absent. The owning host schedules a bounded durable tick, selecting at most B<=1000 expired keys in index order with a stable cursor, then exact-key deletes/terminalizes. Dispatch partitions through bounded host scheduling; never discover work by scanning accounts/receipts/references. Each batch commits its cursor/progress and can resume independently. Expiry is enforced during resolution/consumption at T and observed deadline, irrespective of GC lag. Audit/core receipt retention is a separate existing contract; GC cannot delete proof still required by a live operation.

The driver contract declares growth seeds for 1x/8x/64x independent series varying unrelated subjects, unrelated history and history on the very same approving anchor. Use real shared `openGrowthDatabase`, `seed`, `checkGrowth` from `services/kernel/test/support/growth.ts`; ANALYZE outside capture, include nested receipt/account/formula statements and retries. Keep measured request/target/evidence/K fixed; assert constant examined rows/statements and logarithmic buffers for reference resolution, then separately vary K within its cap for formula work. Measure valid, revoked, expired, replay, concurrent consumption and bounded expiry GC; include old consumed receipts as decoys. Preserve raw auto_explain output. The red-suite verifier makes no product cost claim.

If deployment has legacy records missing exact receipt/proof locators, introduce an explicit bounded migration barrier: closed admission until coverage is ready, keyset backfill with persistent progress and B<=1000 per tick, restart-safe completion markers. Never fall back to request-time history enumeration or permit an unbound reference during migration.

## Manager policy decisions before implementation

The native 60-second operator opening and 30-minute pending registration deadlines remain unchanged. No rule yet fixes a generic account-operation approval's maximum lifetime or whether long-running work may resume after it expires. The manager must choose a finite maximum and whether a new authenticated, exact-operation approval may resume unfinished work; until then expiry denies with no automatic extension. Separately decide how service continuations after deliberate fencing retain only the narrowly required cleanup authority without reusing stale user approval. No unlimited bearer-style continuation or broader reapproval is implied. These are implementation admission questions, not permission to change frozen assertions or native exceptions.

The `nativeException('self-read')` driver case exercises the native receipt-only policy using an authorized self-account read, not a newly invented public self-read endpoint. Negative `other-account-read` means attempting to substitute another account's read evidence/receipt basis. Do not prohibit an otherwise legitimately granted account read. Recovery negatives use actual native human/organization/automation eligibility and stale proof rules.
