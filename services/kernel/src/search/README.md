# Search

Search owns the subject search projection, indexing consumers, disclosure checks, query API, freshness and index generations.

## Cost

These are derivations from `src/search/`, `src/events/`, the called Access SQL, `db/search/` and the core/semantic schema, not measurements or guaranteed PostgreSQL plans.
The criterion is a bounded anchor neighbourhood per query, hit or change, with about changes × index depth work; OpenSearch's internal query execution is an engine constant, but kernel enumeration and source reads are not.
`N` is total subjects, `P` rows in an anchor partition (including history and other consumers where relevant), `H` outbox rows in one partition, `b` event changes in a batch, `h` candidates examined on a page, `s` requested results, `d` page depth, `C` checkpoints for one consumer (at most 4,096), and `k` rows/documents changed by an operation.
Write `L(x) = O(log(2+x))`: a unique B-tree probe examines constant rows and logarithmic shared blocks; a range returning k rows costs `O(L(x)+k)` rows/index work and blocks on an indexed path.
The partition map has 4,096 entries, routes map by `route >>> 4`, and checkpoint/outbox keys are `(partition_no,consumer)` and `(partition_no,position,event_seq)` respectively.
Search uses the default 64-envelope limit; commands cap events per envelope at 1,000, hence `b <= 64,000` for command-produced logs (the outbox DDL itself has no upper event-count check), and distinct changed subjects are at most b.
Search validates `1 <= s <= 100` (default 20); a page makes at most three rounds of `min(200, 2 * remaining + 1)` hits, hence `h <= 600`; suggest returns at most 10 results from at most 20 candidates.
Unless stated otherwise, an operation writes nothing, and rows/blocks mean kernel SQL examinations/shared blocks, not merely returned rows; constant request counts exclude no hidden per-hit source SQL guarantee.
Growth checks below separate existing call-count assertions from proposed SQL row/block checks; grow the total by adding unrelated subjects, then grow the anchor partition independently while fixing its selected neighbourhood, payload sizes, consumer/generation count and other named inputs.

The source port has no production implementation here, so semantic locality cannot be claimed: `semantic.subject` has a `(route,subject_id)` B-tree, `semantic.fact` a `(route,subject_id,slot_id,log_seq)` B-tree with only log_seq capped at 32, and `semantic.revision` a `(route,subject_id,revision)` B-tree plus `(route,subject_id,recorded_transaction_id)` index; none caps facts, slots or revisions per subject.
The existing semantic `read-subject.sql` materializes every fact for one subject and resolves its revisions, so substituting it for the missing search source would introduce uncapped history work rather than prove a bounded current-state snapshot.
Document building, filter rechecks and result projection consume uncapped subject payloads, including sorting labels, so fixing the number of subjects alone does not establish a fixed per-subject cost. Nested facts add one Lucene document per facet-capable statement: a subject costs 1 + F documents and its bulk line grows linearly in F with Q qualifiers each. F and Q are bounded by the statement limits of the subject read contract. Queries on facts touch only the nested documents of matching subjects. A changed mapping reaches a running deployment through the existing rebuild (new generation, reconcile, alias switch).
HTTP search and suggest inherit uncapped Global grant/denial and organization-membership neighbourhoods from Access, even though disclosure itself groups reads rather than issuing a statement per hit.
The consumer-leading checkpoint index lets Retire examine the retired consumer's k checkpoints in `O(k + L(C))` rows and blocks; Freshness reads one consumer's at most 4,096 checkpoints through it.
Relay discovery, freshness, reconciliation and retirement use cross-partition SQL joins/deletion on a shared pool: their fixed 4,096-partition cardinality does not make them independently executable on separately placed partition databases.
A prefix holds at most three generations: the previous one during its retirement grace, the active one and the one being built. Rebuild exclusion uses a PostgreSQL session advisory lock keyed by alias; alias switching is delegated to OpenSearch.
Full replay and reconcile are explicitly invoked whole-index maintenance, while discovery/retirement are periodic and freshness is cached/polled; no reconcile runs per indexed change.
