## Outcome

Main's web unit tests fail in the gate's order, and every complete gate of a web task fails with them. Reproduce on main:

`task goal:unit-files -- apps/web/tests/showcase-zone-editor.test.tsx apps/web/features/work-page/hub-access.test.ts` gives 41 pass, 6 fail (`WorkTabs` reads a null pathname). Each file alone passes.

The cause is the cleanup the guard `apps/web/tests/module-mocks.guard.test.ts` requires: `afterAll(() => mock.module(specifier, () => snapshot))`. Under this Bun (1.4.3), once a file has replaced a module again inside a cleanup hook, a later file's `mock.module` for the same specifier no longer reaches a module that is first loaded after that hook; the later module is bound to the real exports for the rest of the process. Program measured it with two files and a one-line consumer of `next/navigation`:

| First file's cleanup | Later file replaces, then first loads a consumer |
| --- | --- |
| `mock.module(specifier, () => snapshot)` in `afterAll` (same with a fresh copy) | consumer sees the real export: fails |
| none, or two replacements at top level | consumer sees the later replacement: passes |
| one replacement whose functions delegate to a table; cleanup resets the table and never calls `mock.module` | passes, also with `require` or a bare later replacement |
| the same, a second file with the old cleanup, then a third file | the third fails: the old cleanup in the middle file is enough |

Ten modules are cleaned up in one test file and replaced in another (`next/navigation` in 8 files, `next/headers` in 7, `features/work-page/read.ts` in 4), so the order of files decides which tests fail.

What must be true afterwards:

- One helper under `apps/web/tests/support/` replaces a module once, at the file's top level: the replacement keeps every real export, the replaced functions delegate to the current table, and the returned cleanup sets the table back to the real exports. Cleanup never calls `mock.module`. A file that swaps a reader inside a test (as the showcase test does with `work-page/read.ts`) changes the table, not the module. An export that is not a function and must change is handled inside the helper in one stated way, or refused by it.
- The guard requires the helper's form and refuses a `mock.module` call inside `afterAll`, `afterEach` or a function they call. It keeps requiring that the real exports are preserved.
- Every file in this task's paths uses the helper. Two files are another task's claim and keep the old form until that task converts them: `apps/web/features/work-page/hub-access.test.ts` and `apps/web/features/realm-appeal/read.test.ts`. The guard names exactly these two in one list that may only shrink, with one comment saying why.
- An order test proves the property with fixture files under `apps/web/tests/support/module-replacement/`: a first file replaces a module through the helper and cleans up; a second file replaces the same module and first loads a consumer there; the consumer sees the second file's replacement. It runs them in one `bun test` process in that order. Write it failing first by giving the first fixture the old cleanup, and say so in the handoff.
- The reproduction above gives 47 pass, 0 fail.

Do not build: a change to production code, to the two files named above, or to any assertion; a second helper; a retry or a file-order change in the gate.
