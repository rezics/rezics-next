## Outcome

G-1130 made references go through disclosure checks. Since then the same
defect has appeared three times: a reference the target reader discloses
(Structure positions, releases, classification Concepts) went to the semantic
reader alone, which knows only semantic Resources, public Works and relation
definitions, and was therefore treated as hidden.
- G-1139 fixed relation applicability (`relationReferences` and
  `undisclosedReferences` in `relation/change.ts`).
- G-1153 fixed semantic-change role members (`semanticWriteReferences` in
  `semantic/admitted.ts`).
- Still open, from G-1153's report: readers drop public Concept members.
  `lexicon/render.ts` (the member filter near line 257, and
  `readExactDefinition(..., canRead)`) and `semantic/read.ts` (member
  availability) filter `role.members` through the semantic reader, so every
  reader sees an empty `kind` member list on `variant-of`.
- `relationReferences` still sends `definition.roles[].members` straight to
  the semantic reader.

Fix the class with one shared rule, for example
`services/main/src/modules/target/disclosed-references.ts`. Given references
and the caller's authority, it resolves them in one `targetSummaries` batch,
and anything the target reader does not disclose goes to the semantic reader.
Hidden and missing references still look the same. Use it in all four places
(relation writer, semantic writer, lexicon render, semantic read) and remove
the per-site variants. Keep each site's query count bounded: one batch per
call, never per reference.

Integration test (`semantic-member-disclosure.test.ts`): on `variant-of`, a
public Concept member is visible to an anonymous reader through the lexicon and
the semantic read, and a member hidden from that reader is absent. A
`variant-of` relation write that names public Concepts is admitted.
