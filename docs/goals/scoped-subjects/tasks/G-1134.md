## Outcome

G-1130 (commit eff62689a) closed review finding 17: never leave a relation
occurrence position-gated by an edit that was then refused. It did this by
publishing the revelation row only after the graph write succeeds. In between,
every `ReadingBoundary` read runs an extra SPARQL query
(`services/main/src/modules/reading-position/boundary.ts`, the
`rv:revelationWork` receipt check). That puts one more Fuseki round trip on
the hottest read path, including resource summaries, for a window that only
relation writes open. The unit test
`tests/qa/unit/g-971-regressions.test.ts` (VIEW08) now fails with 503 because
its mocked graph does not expect the query.

Keep G-1130's guarantees and remove the read-path query:

- Before the graph write, record the revelation in SQL as pending. The existing
  `required` lookup already reads that table, so the reader treats pending as
  required and fails closed.
- When the graph accepts, mark the row published.
- When the graph refuses, delete the pending row in the same failure path.
- A crash between the two steps leaves the row pending, which fails closed. A
  retry with the same idempotency key completes or clears it. Describe the
  recovery path in a comment and test it.
- The revelation position checks G-1130 added (`preparePublication`, the Work
  and generation join) stay.

`ReadingBoundary` returns to its previous query count; restore
`REVELATION_COST` accordingly. VIEW08 passes unchanged, with no new mock.
