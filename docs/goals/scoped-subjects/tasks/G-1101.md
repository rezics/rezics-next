## Outcome

On 2026-10-04/05 the shared dev stack broke three times after merges because a
manager ran only part of the refresh: Main refused to start on a Fuseki image
without a new profile; the relay kept running pre-merge code and blocked on an
event the new code accepts; an Access migration was never applied
(`stack:up` does not migrate); and the dataset's model generation lagged the
build, so commands hung until their admissions expired. Add one task,
`task dev:refresh`, run from the main checkout, that brings the shared stack to
the committed `main`:

1. build the Fuseki image pinned in `infra/dev/compose.yaml` if it is missing;
2. recreate storage on it with data volumes kept, and apply migrations (what
   `dev:prepare` does), refusing to continue if the generated stack env would
   change without telling the caller to restart the AppHost;
3. align the dataset model generation (`dataset:bootstrap-model`);
4. restart the Main, relay and Account resources through Aspire and wait for
   their readiness endpoints;
5. print what changed (image, migrations applied, model generation, restarts).

It must be idempotent (a second run changes nothing) and refuse to run from a
worktree or while another manager holds the heavy QA lock on the shared stack.
Document it in one line where the program describes the shared host
(`docs/goals/README.md`) and in `docs/development/README.md`, and record the
task in the toolchain inventory if the inventory lists tasks.

## Checks

`task dev:typecheck`; unit tests for the step planner (what runs given which
inputs changed); a dry-run mode that prints the plan without acting, run
against the shared stack. Do not run the full refresh yourself; the manager runs
it. `task docs:check`.
