## Outcome

On the shared dev stack (main checkout, Main :3001, Fuseki :3030, Access DB URL
in `/home/edge/projects/rezics/rezics-next/.temp/stack/rezics-dev/dev.env`),
`task dev:seed -- --scoped-subjects-only` (run by the manager) still ends with
"Main /v1/rating-question-presentations: pending after retries". Every
`rating.question-presentation.review` admission there is claimed and never
sealed (latest registered 2026-10-04 23:44:06Z), while Main posts the guarded
Fuseki command about once a second, each answered `200 OK` in 150–340 ms, until
the admission expires. The relay is healthy (restarted at 23:4xZ; it had been
blocked on an unrelated event). Every QA project passes, including the seed's
own acceptance test, so the guard holds on a fresh graph and fails on this one.
G-1095 added fail-fast refusals for guards that cannot match, yet this case
still retries, so the failing clause is one those refusals do not cover.

Method: reproduce the exact command Main builds for one stuck review (same
Context, language, expected head and admission inputs, read from Access and the
graph), run its WHERE clause as ASK/SELECT against the shared Fuseki read-only,
and bisect the clauses until one is false. You may read the shared stack in any
way; do not write to it, restart it or stop it. Then:

- fix the cause in the command (or in the seed, if the seed sends an inconsistent
  expected state), with a QA test that builds the same state and fails before
  the fix;
- make every guard clause that can be false for a reason other than a
  concurrent winner end in a typed refusal instead of retrying to expiry;
- say in the handoff exactly which clause was false and why.
