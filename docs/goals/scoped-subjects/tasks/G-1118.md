## Outcome

`POST /v1/projections` requires the OAuth scope `rating:submit`
(`PROJECTION_WRITE_SCOPE` in `services/main/src/modules/projection/schema.ts`),
so a client that only writes reviews or discussion must ask people for rating
permission to anchor "X in F". A projection is a derived anchor that any
judgment on "X in F" needs. Accept a bearer that holds any one of the scopes
that write a judgment on a target (rating, review, discussion/reply; find their
exact names where those routes verify their scopes) and refuse one that holds
none, with the same typed refusal as today. Do not add a new scope or change
consent screens. Keep the Access admission scope (`projection:create:root`) as
it is.

## Checks

`task main:typecheck` through the slot; unit tests; an integration test alone:
a token with only the review or discussion scope creates a projection, one with
only an unrelated scope is refused; existing projection files pass.
`task ast-grep -- scan`.
