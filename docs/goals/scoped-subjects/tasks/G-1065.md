## Outcome

Implement the Projection of [decision 51](../../../contracts/semantic-model.md#identities-variants-and-projections):
one Resource that names "subject X within frame F", so ratings, reviews,
discussion and pages can target "Misaka in *Railgun* S1 episode 3" or
"a player on one map of one match" without a second target kind.

1. **Profile and type.** `model/definitions/projection-v1.ts` with canonical
   type `rv:Projection`: exactly one `rv:projectionOf` (any native Resource),
   one to eight `rv:frame` IRIs, and the owner revision pattern the other owner
   profiles use. A projection is immutable after creation. Register
   `rv:Projection` in `types-v1.ts` with a new structural base `projection`
   (labels in the eight UI locales) so the target resolver reports it.
2. **Frame dimensions as data.** Every frame coordinate belongs to exactly one
   dimension. Structural bases map in code: `work` → work,
   `realization` → realization, `release` → release, `occurrence` (Structure
   position) → position. Descriptive types declare theirs in the type registry
   with a new optional `frameDimension` field validated by `model/compiler/type.ts`:
   `schema:Event` → event, and three new descriptive types (base `resource`,
   eight-locale labels): `rv:NarrativeContinuity` → continuity (a story
   continuity such as Canon, Legends or Earth-616, distinct from the Work
   continuity that scopes progress), `rv:GameUnit` (no dimension) and
   `rv:Title` (no dimension). A type without a dimension cannot be a frame;
   Realms, Spaces, Contexts and Agents therefore never can.
3. **Get-or-create.** `POST /v1/projections` with `{ subject, frames }` returns
   the one projection for that subject and sorted frame set, creating it on
   first use. Concurrent requests for the same key yield one identity: back the
   key with a unique Access SQL row (your migrations) written in the same
   admission as the graph command. Validation: the subject is readable and not
   a Projection; each frame resolves through the shared target resolver to a
   type with a dimension; at most one frame per dimension; one to eight frames.
   Any signed-in principal who can read the subject and every frame may create
   one; it is a derived anchor, not authored content. Disclosure is the most
   restrictive of the subject and frames. `GET /v1/projections?subject=…&frame=…`
   looks one up without creating it; `GET /v1/projections?subject=…` lists a
   subject's projections with a bounded page and continuation.
4. **Targets.** Add base `projection` to `target/contract.ts` with the report,
   review, rating, discussion, collection-member and suitability capabilities,
   resolve it in `target/resolve.ts` (exact revision, no Work ownership), and
   give it a summary in `media/summary.ts` that carries the subject's summary
   and each frame's summary as structured parts: clients format them, the
   server concatenates no labels.
5. **Typed applicability.** In `modules/projection/`, export
   `dimensionOf(resolvedTarget)` and `covers(applicability, frames)`: values in
   one dimension combine with OR, dimensions combine with AND, and a position
   frame is covered by applicability naming its Work. Statements and relation
   occurrences keep their stored sets; this task only adds the shared reading
   rule and its unit tests.

Do not build: projection edits or retirement, projections of projections,
facts stored on projections, frame containment beyond position-in-Work, a
general context engine, caches or a new resource-create route outside
`/v1/projections`. Ratings, reviews and discussion admitting the new base, and
the projection page view, are later tasks.
