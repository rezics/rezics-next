### F2 — Medium: a verification JWT can authenticate a replacement account after email reuse

**Evidence.** Verification JWTs bind email and recovery generation, without immutable user ID (`services/account/src/auth.ts:379-381`). Admission resolves the current user by that email and compares only its recovery generation (`auth.ts:238-245`), defaulting to `0` without a policy (`services/account/src/recovery-claim.ts:407-410`). Email change releases the old address (`services/account/src/email-change.ts:132-135`). Auto-sign-in is enabled and link lifetime is 1800 seconds (`auth.ts:371`). The pinned provider selects the user by token email and verifies/logs in a currently unverified user (`node_modules/better-auth/dist/api/routes/email-verification.mjs:188,295-302`); the JWT is stateless.

**Exploit.** Retain A's verification URL, verify A, and change A's email. If B registers the released address before link expiry, replaying A's old link verifies and authenticates B when both recovery generations are `0`. The former mailbox owner/link holder gains B's session without B's password or newly delivered proof. The timing and mailbox reuse preconditions justify Medium. This uses email change, not the excluded, fixed account-deletion defect.

**Smallest fix and acceptance.** Add an immutable user ID claim and compare it with the selected user before provider verification/auto-login; reject legacy links lacking the binding. Regression: original link → original verification/email change → new unverified account at old address → original-link replay must neither verify nor authenticate the new account. Cover operator-generated verification links too (`services/account/src/admin-actions.ts:114-119`), using the same binding owner.
