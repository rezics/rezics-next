## Outcome

Kernel ruled that a Realm's policy revision has one representation. The Realm
node carries `rv:realmPolicyHead <receipt IRI>` (maxCount 1; it is written in
`space/policy.ts` around line 96 and validated by the space-realm shape). There
is no separate policy-head node and no `urn:rezics:realm-policy:<UUID>`
revision.

Access still expects `urn:rezics:realm-policy:<UUID>` plus a separate
`rv:receipt` link, from G-1253 and G-1254. So `initializeCreated` answers 403
"Realm creation proof is unavailable" for launch's G-1238: the graph revision
is `urn:rezics:receipt:<uuid>` and the permit revision is null (QA run
20261007t010034-6cf176).

1. **The permit revision equals the graph's `rv:realmPolicyHead`.**
   `realmPermit` (`realm-management-policy.ts`) returns the receipt IRI that
   the graph holds as `rv:realmPolicyHead`. For an initial policy, that is the
   creation command's own receipt IRI.
   - First check what an ordinary policy publication writes as
     `rv:realmPolicyHead`.
   - Make initial and ordinary revisions use the same IRI form, so submission
     admission compares like with like.
   - If ordinary publications use another form today, align both on the
     receipt IRI, and say exactly what changed.
2. **`initialRealmPolicyFacts` emits only the Realm's policy facts**, with
   `rv:realmPolicyHead` set to the creation receipt IRI and no separate node.
   Return `{ revision, current }`, where `revision` is that IRI.
3. **The initialization proof in `initializeCreated` accepts that revision.**
   Replay, conflict and immutable-binding behaviour stay as they are.
   Migration 1296's stored value may need to hold the receipt IRI or UUID; if
   its meaning changes, explain it in a code comment, with no new migration
   unless one is unavoidable.
