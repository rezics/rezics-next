## Outcome

1. **These six unit test files fail on `main` and failed before today's
   Access changes** (reproduced on the original sources):
   - `g-1005-fixture-consent`
   - `g-512-native-language`
   - `g-596-localized-rules`
   - `g-963-memberships`
   - `g-964-joining-policy`
   - `g-964-private-leave`

   They are all in `services/main/tests/`, about 21 failing tests together.
   For each failing test:
   - Find whether the product or the test is wrong.
   - When the test asserts behaviour that a later, deliberate change replaced,
     update the assertion. Say which commit made the change and why.
   - When the product regressed, fix the product. If that needs a file outside
     this claim, run `task goal -- owner <path>`; if the file is unclaimed,
     make the smallest change and list it.
   - Never delete a failing assertion or loosen it, except for a deliberate
     product change.

   Context for recent Access changes:
   - a decision now rests on one selected authority path;
   - management follows the current controller, not the provisioning
     principal;
   - leases end at the earliest authority expiry.
2. **Continuity refusals get their own HTTP problem.** A change refused because
   it would leave a resource without a controller currently surfaces through
   the generic `PolicyConflict`, which reads as an idempotency conflict, in
   `routes/access-policy.ts`. Give it a distinct 409 problem type,
   `controller_continuity`, with a clear message, and test it.

## Do not build

- No change to Access semantics beyond what a failing test proves is a
  regression.
- No new error framework; add one problem type beside the existing ones.

## Checks

- `task goal -- test` on the six files plus any file you changed. Every test
  in the six files passes.
- `task main:typecheck`.
- The handoff gives, per failing test, the cause (product or test) and the
  fix.
