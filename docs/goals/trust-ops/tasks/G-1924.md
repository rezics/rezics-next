## Outcome

The repository's nested-checkout guard (the runtime `main.database.nested-checkout` / NestedPoolCheckoutError instrumentation) fires inside Access on the path that Launch's browser proof (reloading a Zone resource page, zone-realm-attachment.e2e.ts:291) takes, and renders "Something went wrong". A request that holds one `access` pool client and then checks out a second one from the same pool can deadlock when the pool is exhausted; Access must never do it. Evidence (staged in `.temp/ref/`): `e2e-main.log` lines 82-84 from QA run 20261011t222330-2d406a and Launch's diagnosis `g1808-nested-diag.md`. The fired pairs (outer -> inner, pool `access`):
1. `admission.ts:331 readAdmission` -> `topology-control.ts:88 controlTransaction`;
2. `topology-control.ts:88 controlTransaction` -> `controlTransaction` again, and the reverse (`controlTransaction` -> `readAdmission`);
3. `admission.ts:1048 withOwnerAuthority` -> `address/registry.ts:176 currents`;
4. `admission.ts:1048 withOwnerAuthority` -> `topology-control.ts:88 controlTransaction`.
The trigger path: routes/zones.ts:534-542 and zone/route.ts:80-85 (`resolveZoneRoute`, `zoneRouteViewer`) -> `canReadSemanticResource` -> `readAdmission` (admission.ts:598-606).

Method: (1) read each pair and name the call chain that holds the outer client while reaching the inner checkout (a callee that takes the pool instead of the held client, or a helper that defaults `client` to undefined); (2) fix by passing the HELD client through (the existing Access helpers already accept an optional `client`: `readAdmission(pool, client, ...)`, `controlTransaction(pool, work, read, client)`, `controlRead(pool, work, client)`), never by enlarging a pool, adding a second pool, or catching and ignoring the error; (3) keep behaviour identical: same fences (recovery fence, lock timeout 2 s, statement timeout 5 s), same transaction boundaries (a caller's open transaction is left to the caller), same error normalisation; (4) the test `services/main/tests/access-nested-checkout.test.ts` drives each of the four pairs' entry points on a real Postgres with the repository's nested-checkout instrumentation active (find how `main.database.nested-checkout` is raised and reuse it, do not invent a detector) and asserts no NestedPoolCheckoutError and unchanged results (allow/deny decisions identical to the no-client path), including a pool of size 1 that would deadlock on a nested checkout (the strongest proof: it must complete). Look for the same pattern in the sibling helpers on the same read path and fix those the guard would also flag; list anything else you find in the handoff without fixing it.

Constraints: Access decisions must not change (all existing access/baseline/admission tests stay green; run the owner tests that cover readAdmission, controlTransaction and withOwnerAuthority in your single goalctl call). No repository-guard debt entries. If a pair cannot be fixed without a design change (e.g. the registry `currents` needs its own consistency snapshot), STOP and report the exact reason.

## Manager decision (2026-10-12), after attempt 1: fix inside Access and the seek index, no cross-owner edit

Attempt 1 confirmed the chain `withOwnerAuthority -> Zone commit -> Fuseki template-index callback -> TemplateSeekIndex.apply -> controlTransaction` drops the held client, reproduced the sibling `readAdmission -> controlTransaction` report, and showed `AliasRegistry.currents` ignores its held `withRead` client. It stopped because carrying the client through the Fuseki callback needs edits in zone/configuration.ts (G-1804) and infrastructure/fuseki.ts (G-1655). Do NOT edit those files. Use the pattern that already exists in this module: an AsyncLocalStorage-held client. `withOwnerAuthority` (and `readAdmission`'s own checkout) publishes its held client in an Access-owned AsyncLocalStorage store for the duration of its callback; `controlTransaction`/`controlRead` (when no `client` argument is passed and the pool is the Access pool) and `TemplateSeekIndex.apply` (services/main/src/modules/query/seek-index.ts, now in the claim) use `client ?? store ?? pool`, exactly like `AliasRegistry.currents` can reuse `client ?? this.reading.getStore() ?? this.pool`. Scope rules (these keep behaviour identical): the store is set only around the callback, cleared after (also on error), never leaks across requests (test with two concurrent requests), and an explicit `client` argument always wins. If a caller intentionally needs a SEPARATE Access connection while holding the owner client, make that explicit (and say so in the handoff); there should be none on this path. The four-pair regression stays as specified (real Postgres, nested-checkout instrumentation, pool of size 1 completes, decisions identical). List the other nested Zone/Realm callbacks and baseline reply-root client propagation you saw WITHOUT fixing them.
