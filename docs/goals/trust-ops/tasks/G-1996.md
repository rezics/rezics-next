### F1 — Medium: public Work readership authorizes unpublished exact Content bytes

**Evidence.** `/v1/content-revisions/:revision` resolves the revision's resource, then requires only `work:read` and `canReadContentTarget` for non-Zone content (`services/main/src/routes/content.ts:417-435`). That helper delegates Work content to `canReadWork` (`services/main/src/modules/content-publication/draft.ts:159-164`). With no explicit scope policy, an email-verified Person passes the public Work baseline (`services/main/src/modules/access/admission.ts:374-400`; `services/main/src/modules/access/baseline.ts:245`). Work visibility includes catalogue visibility or Contribution/Structure publication, independently of the requested Content revision (`services/main/src/modules/work/public-patterns.ts:198-204`).

The route then authorizes every requested exact revision and returns serialized bytes/body (`services/main/src/routes/content.ts:441-460`). The owner obeys that callback without a publication predicate (`services/content/src/core.ts:977-994`). Composed disclosure checks enforcement/audience, not exact publication (`services/main/src/modules/disclosure/assembly.ts:11-30,79-85`; `services/main/src/modules/disclosure/read.ts:163-177,203-211`). The adjacent comment-authoring baseline explicitly requires an exact currently published, publicly eligible revision because public Work visibility does not expose private drafts (`services/main/src/modules/access/baseline.ts:247-257`).

**Exploit.** An unrelated verified Person with a `work:read` token and a known unpublished revision UUID requests that revision with their own Person as actingSubject. On a public Work without an explicit policy or moderation hold, the Work baseline permits private draft body/provenance disclosure. No race is required. UUID knowledge is a prerequisite: the variant inventory has separate private authority and a delivery recheck, so no arbitrary UUID enumeration is claimed (`services/main/src/routes/studio.ts:140-173`; `services/main/src/modules/studio/access.ts:208-225`).

The no-policy prerequisite is reachable: ordinary creation activates the Work and records its outcome (`services/main/src/modules/work/create-admitted.ts:83-93,121-129`), whose initial bootstrap writes maintainership rather than a read policy (`services/main/src/modules/access/admission.ts:2114`; `services/main/src/modules/work/maintainer-proof.ts:28-51`). Read policy insertion belongs to explicit policy publication (`services/main/src/modules/access/policy-changes.ts:181-204`).

**Smallest fix and acceptance.** Authorize the exact Content revision. Permit public-reader authority only for the exact public publication/eligibility proof; otherwise require private owner/editor or explicit private read authority. Preserve public Work metadata readership and existing disclosure checks. Writer publishes A, then saves private B on the same public Work: unrelated Person's known-ID read of B returns 404 with no bytes/provenance, while authorized private readers can read B and eligible A remains available. Cover unselected language variants and withdrawn/superseded revisions according to public-history policy. Audit comment reads for the same Work-versus-revision distinction (`services/main/src/routes/content.ts:155-164,223-241`). Existing writer exact-read coverage does not test this unrelated reader (`tests/qa/integration/content-publication-native.test.ts:307-325`).


Rule as a table (the finding is of the kind 'which callers'): write in your handoff the table of EVERY route/caller that reads exact Content revision bytes or provenance (content-revisions, comment reads, Work content, Zone content, studio, export, search hydration) with the authority each requires today and after your change (public exact publication proof | private owner/editor | explicit private read grant | refused); the first review judges the class against it.
