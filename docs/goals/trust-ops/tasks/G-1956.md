## Manager decision (2026-10-12 03:30), binding: borrowed limit handling reads the ACTUAL parent settings

Review #2 (P2): a cached timeout metadata copy in the held-client context goes stale when the parent later issues SET LOCAL statement_timeout directly; the child then raises the parent's bound and restores a wrong value. A second copy of a setting that callers can change in SQL cannot be made correct, so the context carries NO limit metadata. A borrowed wrapper that applies a child bound does it in ONE statement that reads the actual current settings and applies the minimum in SQL (set_config(..., true) with LEAST over the non-zero values; 0 means unlimited), returning the previous values, and restores exactly those previous values in ONE statement afterwards (also on error). The borrowed path therefore costs two additional statements of one row each (apply, restore), bounded and constant; the unborrowed wrapper's statements and row counts are unchanged and stay pinned. Where the child's bound cannot tighten anything it still reads (that is the price of correctness); it never writes a value larger than the parent's. The pinned expectations for the BORROWED paths are updated to this bounded cost (the earlier seven-row cost and the repeated recovery predicate stay forbidden). Tests: a parent that issues SET LOCAL statement_timeout = '1s' (also 0 and 10s, and lock_timeout likewise) AFTER the context was published: the child runs under min(parent actual, child), the parent's actual value is restored exactly; a counting wrapper pins the statements and rows of the borrowed path.
