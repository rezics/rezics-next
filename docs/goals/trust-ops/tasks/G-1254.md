## Outcome

G-1253's `initialRealmPolicyFacts(input, space)` returns `{ revision, current,
receipt }`. Its `receipt` is a second receipt node in the graph creation
command. The Jena command module rejects that, because a command may write only
its own receipt (`CommandPolicy.java`, around lines 105–106). That invariant
stays. Launch's G-1238 is blocked on this.

Bind the initial policy delivery to the creation command's own receipt:

1. `policyReceipt` is the creation receipt's UUID, which launch already derives
   deterministically from the creation key. Rename the field if that makes
   the meaning clearer, for example `creationReceipt`, and state the rename in
   the handoff.
2. `initialRealmPolicyFacts` emits no receipt node. Its `current` facts
   reference the creation receipt IRI that the command itself writes, and the
   policy revision is `urn:rezics:realm-policy:<creation receipt UUID>`. Keep
   the revision shape `realmPermit` reads, or adjust `realmPermit` minimally
   so permit and graph agree.
3. `initializeCreated` records the delivery against that receipt. Replay and
   conflict behaviour stay as they are.

Migration 1296 already binds the receipt immutably, and its semantics are
unchanged. If its column name now misleads, explain that in a comment rather
than adding a migration.
