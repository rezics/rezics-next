## Outcome

Program decision (2026-10-10): the recovery evidence the Goal's outcome names comes first: **a backup taken from one stack restores on a separate, empty stack that has no access to the source, and the restored stack passes the readiness and erased-closure checks.** Today's restore tests copy databases/volumes between stacks that still share the harness, host paths or the source's keys. Prove the real thing with the production backup and restore procedures (`docs/operations/recovery.md`, `scripts/ops/restore.ts`, the owner-restore fixtures under `tests/qa/fault-recovery/owner-restore-erasure-*`):

1. Build a small populated source stack (use the small fixture profile; keep preparation inside its existing budget). Perform, BEFORE the backup, an erasure of a revision and of a media object and a suppression; perform, AFTER the backup, one more erasure (this one exists only in the erasure journal/relay, not in the backup).
2. Take the consistent backup with the production procedure; collect ONLY the backup artifact plus the documented key material (the minimum an operator carries). Then destroy the source stack completely (stop, remove volumes and networks, remove its env/config directory) so nothing of it remains reachable; the test must assert the source's volumes and containers are gone before restoring.
3. Restore onto a NEW empty stack using only that artifact and key material (no shared volume, no source path, no source credentials, no harness reuse of the source's secrets). The restore replays the erasure journal first.
4. Assert on the restored stack: readiness and Access open (`/health/ready`), the restore fence/hold released through the production release path, erased-closure holds (every erasure before AND after the backup is erased/suppressed in every owner: Content revisions, graph tombstones, media objects, search; nothing erased is readable), authorised data intact (exact samples), `rv:ErasedRevision` receipts unchanged, and the timed restore stays inside its documented budget (`docs/storage/workload-budgets.md`). Record the timings.
5. Negative cases: a backup missing its key material refuses (typed reason, no partial open); a restore pointed at a stack that still holds the source's volume name refuses; a restore that skips the journal replay leaves Access closed.

If the production procedure cannot be run this way (missing documented step, hard-coded host path), FIX THE PROCEDURE/script (scripts/ops/restore.ts and the recovery doc) minimally and say so; do not weaken the isolation assertions.

## Mechanisms

none — this is evidence over the existing backup, restore, journal-replay and release paths.

## Checks

The new fault/recovery test(s) pass on the real stack (QA id, run alone, no `--heavy` by workers; the manager runs any heavy tier). Mutation proof: skipping the journal replay, or leaving a source volume reachable, makes the test fail (state the QA ids). Lint, AST, types. Hand off the measured restore time and the exact operator inputs (what the artifact + keys contain).
