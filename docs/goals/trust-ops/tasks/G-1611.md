## Outcome

G-1605 built the registry and helper (\`tests/qa/support/hidden-id-equality.ts\`, \`scripts/static/hidden-id-reads.json\`) and its diagnostic found nine id-accepting reads that tell a HIDDEN id (exists, caller may not see it) from an ABSENT id by status, body or cost. Make each answer both identically, then register it (move from debt to registered; the debt list may only shrink):

1. \`GET /v1/claims/{claim}\` and \`GET /v1/statements/{id}\`: 200 vs 404 — a status leak (hidden exists). Hidden must answer exactly the absent answer.
2. \`GET /v1/content-revisions/{revision}/comments\`: 14 vs 1 SQL statements.
3. \`GET /v1/addresses/resolve\`: extra graph and SQL calls.
4. \`GET /v1/public-previews/{resource}\`: 3 vs 4 graph calls. \`GET /v1/resources/{resource}\`: 5 vs 6 graph calls.
5. \`POST /v1/resources/summaries\`: address-generation hash and accessChecks 1 vs 0.
6. \`GET /v1/works/{id}/history\`: 2 vs 4 graph calls. \`GET /v1/works/{id}/maintainers\`: 1 vs 0 SQL statements.
Concept pages (\`GET /v1/concepts/{id}\`) need a genuinely hidden concept in the fixture first: add one and register it.

Pattern (one mechanism, not nine): decide visibility FIRST with the one batched disclosure/Access check, and on "hidden" take the SAME code path as "absent" from that point (same queries issued or the same early return for both, never "skip the work only for absent"). Equalise cost by doing the absent path's work for hidden, or by short-circuiting both before any resource-specific read; choose the cheaper and keep every existing authority decision unchanged. Do not add padding queries or sleeps. Many files are in kernel's/launch's areas (this brief carries --allow-area): keep each edit minimal and local.

## Mechanisms

access-authority: consume — visibility is decided by the existing Access disclosure; this only makes hidden and absent share a code path.
