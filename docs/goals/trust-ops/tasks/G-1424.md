## Outcome

Test-only. Prove, on the isolated QA integration tier with the real stack (Fuseki,
Account/Access, Content, Main relay, real HTTP), that the landed
`POST /v1/owners/reconciliations {kind:'erasure', erasureId}` clears stored comment
and claim-evidence source text of an already-erased revision, and refuses cleanly
otherwise. No production code change: a production defect you find is reported with
a failing test, never patched or worked around.

Setup per case: publish a Work revision with a comment quote and a claim-evidence
quote; erase it through the normal erasure API; then replant the source text with
SQL to model data erased before the clearing code existed (the existing fault test
`tests/qa/fault-recovery/owner-restore-erasure-source-closure.test.ts` and
`services/main/tests/erasure-live-remediation.test.ts` show the replant shapes).
Cases, each reading the comment and the evidence through the real routes before
and after:

1. Operator with `owner:operate`, stable Idempotency-Key: sources gone, authored
   annotation and coordinates kept, the `rv:ErasedRevision` receipt unchanged, `GET`
   of the recorded row `kind: erasure`, the same key replays the same id (200).
2. The same operation refuses and leaves every source untouched when: a governance
   preservation hold is active on the resource; the graph proof is deleted (native
   refusal); the tombstone belongs to another journal entry or epoch; the operator's
   Access principal is deactivated; the caller lacks `owner:operate` (403).
3. A refusal records nothing, so the same key succeeds after the cause is removed.
