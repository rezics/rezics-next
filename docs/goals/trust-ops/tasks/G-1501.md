## Outcome

Run-5 integration `access-revocation-api` IAM29 is red because `readGrant` in
`services/main/src/modules/access/policy-decisions.ts` (~line 235) keeps a single direct grant
(`ORDER BY valid_until LIMIT 1`). IAM29 (tests/qa/integration/access-revocation-api.test.ts:117) states the
contract: two independent live grants of the same action on one scope are BOTH recorded as the
decision's proof sources (sorted by id), revoking one leaves the other as the only source (generation
and provenance rows intact), and revoking the representation guard still denies. Make the decision
record every live direct grant that supports it:

1. `readGrant` returns/records all live direct grants for (principal, action, scope) ordered by `id`,
   bounded by a small named constant (use 8; if more exist the first 8 by id are recorded and the
   decision still allows; never an unbounded scan or an unbounded snapshot-input write). One indexed
   query; no per-grant round trips. Respect the existing validity rules (active, valid_until, membership
   generation) exactly as today.
2. The same set feeds the snapshot inputs (`decision_snapshot_input`, role 'proof') so provenance
   lists them, and revocation/expiry of ANY recorded source later invalidates the decision exactly as
   one source does today (earliest-expiry rule for leases, C1: a lease ends no later than the
   earliest expiry of the authority it rests on, so a decision with several sources ends at the
   earliest of the recorded sources' expiries, or recompute: choose whichever the current code does
   for multiple sources elsewhere and keep consistent).
3. Align `represented-work-proof.ts` grant selection with the same order (`ORDER BY id`) so the two
   proofs cannot disagree on which grant is the source; keep its LIMIT semantics if it needs one
   grant, but choose it deterministically as the lowest id.

Do not change the policy language, the rule evaluator, the guards or the fence/lock behaviour.

## Checks

`--heavy`. Lint, AST, types.
