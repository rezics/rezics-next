## Outcome

Program decision (2026-10-10): **erasure reaches the live private copies.** For erased content: private Contribution / command payloads (the immutable private Contribution payload and the private historical command payloads recorded in state.md as "unqualified") and the media objects (originals, renditions, thumbnails) are GONE from the live database and the live object store, and a test reads them back as ABSENT. Do not build physical WAL/backup destruction: it is decided that backups and WAL expire by retention and that this is the guarantee for them; a restore re-applies the erasure journal (already landed).

1. Inventory first (write it in the handoff): every live place a private payload or media object of an erased revision/resource can live (Content tables incl. private contribution payload columns, relay command payload tables, `access`/`relay` journals' payload copies, object store keys for originals/renditions/screening artifacts, search/outbox copies). Use the existing erasure journal targets (`relay.erasure_target` kinds incl. `object`, `content_variant`, text_contribution_draft) and the existing owners' `eraseContent`-style appliers; extend those appliers, do NOT add a second erasure path, table or registry.
2. Make the one erasure operation (`POST /v1/erasures`, `content-revision-erasure-v1`) clear each place idempotently inside its owner's transaction (SQL: overwrite-then-null or delete as the schema allows with the immutability triggers' explicit one-way terminal transition, never a blanket mutation allowance), and delete the object-store objects (originals and every derived rendition) with a verified delete (read back absent). The journal records per-target completion; a replay completes what is left and never reports done while a payload or object remains (fail closed, retryable, operator-visible reason).
3. Tests with real PostgreSQL and the real object store (RustFS in the QA stack): create private Contribution content and an uploaded image with renditions; erase; assert via direct reads of the live DB rows and the object store that payload bytes/objects are absent, the authored annotation/receipt/tombstone identity remain, and a second request replays. Include a held-erasure/restore case: the restore journal replay removes them again.
4. Graph closures of 65..256 targets: NOT built. Requirement: an erasure whose graph closure exceeds the supported size FAILS CLOSED with an operator-visible reason, never completing partially. If a test already proves this say which (file, case) in the handoff; if not, add it.
5. Docs: in the erasure/recovery operations doc state, with the retention length, that backups and WAL expire by retention and that this is the erasure guarantee for them; and the restore re-applies the journal first. Keep it to one short section.

Stop and report (do not improvise) if a live copy cannot be reached by the existing owner's applier without a new mechanism.
