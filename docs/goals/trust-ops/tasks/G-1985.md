### F4 — Medium: holding platform:access does not fence administrator resource authority

**Evidence.** Exposure and platform-grant mutation refuse a closed platform gate (`services/main/src/modules/access/exposure.ts:113-121`, `services/main/src/modules/access/platform-grants.ts:236-244`). Shared administrator proof instead locks only the gate ID and never checks its flags (`services/main/src/modules/access/platform-administrator.ts:110-117`); platform grant reads also omit gate state (`services/main/migrations/access/1291_platform_grant_proof.sql:43-48,55-58`). Public media label/conceal routes (`services/main/src/routes/media.ts:92,95`) admit platform protection under `media:protect:<target>` (`services/main/src/modules/media/commands.ts:317-328`). Registration checks that resource gate and selects the deficient administrator proof (`services/main/src/modules/access/admission.ts:1102-1105,1347-1360`). Claim checks the resource gate and repeats the same deficient proof (`admission.ts:1677-1680,1759-1769`; `platform-administrator.ts:172`). Media presentation then applies the platform-authority revision (`services/main/src/modules/media/presentation.ts:269-282`).

**Exploit.** A previously granted administrator with the matching resource permission and live controller mandate keeps making protection changes after platform:access is held, provided the resource gate remains open. This is deterministic containment failure; it does not give an ordinary user administrator authority.

**Smallest fix and acceptance.** Require an existing `open AND dispatch_open` platform gate under the shared proof's lock. Apply the same gate predicate to other platform authority consumers as appropriate. Test both a fresh public media protection request and a previously registered request claiming after platform closure; preserve committed idempotent results.
