## Outcome

Class A security fix (Program confirmed 05:42; found by the read-only security review G-1975, full report at `.temp/ref/report-g1975.md` in your worktree: read the threat-model section too). The finding(s) with evidence, exploit and the smallest fix/acceptance, verbatim:

### F1 — High: form password sign-in bypasses recovery serialization

**Evidence.** The mounted authentication pipeline uses `withRecoveryAuthentication` (`services/account/src/app.ts:476-478`). Email sign-in selects its recovery-lock owner exclusively through `request.clone().json()` (`services/account/src/recovery-auth.ts:39-52`); parse failure leaves no user ID and calls the handler without the lock at line 145. The normal policy lock spans verification at lines 151-187. The pinned provider expressly accepts form sign-in (`node_modules/better-auth/dist/api/routes/sign-in.mjs:265`), reads the old credential at lines 315-323, asynchronously verifies it at lines 329-332, and creates a session at line 350. Account recovery changes the password and removes sessions (`services/account/src/recovery-claim.ts:327-348`); session insertion checks availability and stamps the current session generation, without binding the proof's generation (`services/account/migrations/1750_session_revocation_fence.sql:26-32`).

**Exploit, inferred interleaving.** A caller knowing a password-only user's old password submits form sign-in with the issuer Origin. Its credential read obtains the old hash; recovery commits during password verification; the old hash still verifies, then session creation stamps the current generation. The attacker gets a usable session after recovery without the new password or recovery proofs. This is a specific recovery ordering failure, not a claim that every recovery attempt is bypassed.

**Smallest fix and acceptance.** Reject non-JSON authentication media types before either wrapper, or use one strict parser for every accepted type and hold the existing recovery lock across the provider. Match provider normalization and reject ambiguous duplicate fields. Pause verification after the old-hash read, complete recovery, then resume form sign-in: it must not produce a usable current session. Existing fixtures always JSON-encode (`services/account/tests/account-fixture.ts:50-56`). The same parser mismatch also sends form sign-ins into one shared anonymous target bucket (`services/account/src/app.ts:158-163`); fix both consumers together.


### F3 — Medium: raw signed-in TOTP verification bypasses the per-user step-up attempt budget

**Evidence.** Raw TOTP verification requires step-up only for an unverified factor (`services/account/src/app.ts:146-153`). Its limiter accepts arbitrary `body.email` before the actual factor identity (`app.ts:158-163`). The provider schema strips undeclared email (`node_modules/better-auth/dist/plugins/two-factor/totp/index.mjs:14-22`); an existing session makes `isSignIn=false`, so its intrinsic challenge/account attempt limits do not apply (`totp/index.mjs:172-185,199-204`). Dedicated reauthentication instead limits by immutable user ID to five attempts per five minutes (`services/account/src/methods.ts:95-104`).

**Exploit.** An attacker with an older stolen session and the password guesses TOTP through `/api/auth/two-factor/verify-totp`, changing ignored email on every request. A successful code can then be used once at `/api/account/reauthenticate`. The provider still enforces three requests per ten seconds per IP in production (`node_modules/better-auth/dist/plugins/two-factor/index.mjs:338-343`), so distributed sources/adequate throughput are required. Guessing success was not measured. Pending sign-in TOTP remains protected by intrinsic limits; this finding is the signed-in oracle.

**Smallest fix and acceptance.** Derive throttle identity by endpoint and current authenticated user. Share the step-up budget for signed-in TOTP, or deny raw verification of already verified signed-in factors so bounded reauthentication owns that proof. With one fixed session, changing ignored email values must not admit guesses beyond the user budget.

## Manager decision after land review 3 (rule tables, binding; supersedes instance-by-instance fixing)

Three rounds fixed instances. The rules, once:

| Request kind | Subject of a FAILURE record (security-activity) | Budget charged |
| --- | --- | --- |
| TOTP verification (signed in), reauthentication, backup-code use | The session user (these providers authenticate that session's own user) | The immutable-user signed-in budget |
| Email/password sign-in, magic link, passkey assertion, SSO callback | The target the PROVIDER resolves (email or credential id), NEVER the request's session cookie: a wrong password for B sent with A's cookie records sign_in_failed for B, nothing for A | The target user's/sign-in budget as before |
| Unauthenticated request by email | The email's user (existing behaviour) | Existing |
| Body fields (email, userId) on a session-bound provider | Ignored for attribution | None |

One function maps (provider/route) to its subject rule; security-activity.ts and the wrappers consume it; there is no other derivation of the subject. Tests cover every row, including the two reviewer cases (wrong password for B with A's cookie; failed passkey proof for B's credential with A's cookie) and the original (TOTP for A with B's email in the body).

Pool rule: a request that holds a connection of a pool (mutateMethod, the recovery guard, the signed-in budget) never checks out a second connection from the SAME pool; it reuses the held connection (passes it down) or releases before calling the provider; a checkout timeout or 503 never consumes an attempt. Test: pool max:1 and eight simultaneous requests with a pool of four complete with correct outcomes and no lost attempts, for reauthentication, TOTP verification and backup-code use. Search the whole Account service for any other path that checks out twice (write the table of paths).

THIS IS THE CHECKLIST THE LANDING IS JUDGED BY. Implement exactly its specification starting from this branch: keep G-1983's strict JSON admission and transactional proof charging; replace the request resolution (`authentication-subject.ts` and its wrappers) with ONE provider-backed input adapter (`authentication-input.ts` + `authentication-subject.ts`, `prepareAuthentication`/`resolveAuthenticationSubject`) used by the three HTTP wrappers and the hooks; cookie names from the provider's own context (`auth.$context.createAuthCookie`, the passkey challenge option), never from raw options (the issuer URL is normalized by the provider: `HTTPS://issuer.test` selects `__Secure-better-auth.two_factor`); sessions by the provider's own resolution; no unsigned JWT lock selection for verify-email. Ancillary OAuth rows (P25-P28) are NOT in this task.

Landing review 5 found two P1 that the specification's race section already names; each needs a red-first test with a real provider and a pause:
1. cookie name from RAW auth.options ignores the provider's issuer normalization (ACCOUNT_BASE_URL=HTTPS://issuer.test): a pending TOTP request takes no recovery lock for its owner; consume the challenge, pause before session creation, complete recovery, resume: a usable session with the current generation after recovery. Test with initialized HTTP, HTTPS and uppercase-scheme issuers (not hardcoded names).
2. the provider can change subjects AFTER Account locked and charged the selected session user: A's valid session cookie together with B's valid two-factor challenge; pause after Account's admission checks; revoke A's session from another session; on resumption Better Auth finds no session and verifies B's challenge while Account holds only A's locks. RULE: lock, then RE-RESOLVE under the lock with the provider's resolver and compare the subject; if it changed (or the session is gone) release and either re-lock the new subject or refuse with a typed retry/denied outcome; never proceed on locks of a subject other than the one the provider will verify. Test: B's recovery cannot complete unguarded between the pause and the resume.
