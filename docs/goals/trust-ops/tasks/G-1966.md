## Outcome

A read-only code investigation (staged at `.temp/ref/account-deletion-facts.md`, file:line evidence) concluded that Account deletion is REFUSED for any user whose Access principal is the only live controller of an Agent, and that every onboarded user's Person Agent has exactly that shape (services/main/src/modules/agent/provision.ts:141-160 inserts one `agent.control` mandate for the user's principal; services/main/src/modules/access/admission.ts:1925-1932 `deactivatePrincipal` calls `principalControllerSubjects` + `assertControllerContinuity` (access/controller-continuity.ts:37-57, `access.agent_controller_count` in migration 054) which throws ControlConflict because the live-controller count drops below `min_controllers` (default 1); Account's `beforeDelete` (services/account/src/auth.ts:427-432) turns the failure into a 503 'Account deletion awaits the Access fence...' and the web client shows 'a safety check could not finish. Try again in a moment', with no pointer to anything). If true, NO user with a Person Agent can delete their Account: a right-to-erasure blocker. The conclusion was reached by reading only. YOUR JOB: settle it with a test, change no product code.

Write `services/main/tests/account-deletion-person-agent.test.ts` on a real Postgres (follow how services/main/tests/access-controller.integration.test.ts:281-318 sets up controller continuity and how existing tests drive `strongDeactivateAccountSubject` / the account-deletion fence; use the Access fixture helpers and the real Agent provisioning path (AgentProvisioning / the onboarding that creates the Person Agent), not hand-inserted rows, for the Person Agent). Cases, each its own named test: (1) a user whose principal is the ONLY controller of their own Person Agent (the normal onboarded user) runs the real account-deletion deactivation: record exactly what happens (success, or the exact error class and message); (2) the same user ALSO the sole controller of a second Agent that owns a Realm (set up via the real flows if one exists, otherwise a second provisioned Agent): record what happens and what a caller could learn from the error; (3) a user with a second live controller on the Agent (control invitation accepted) deletes successfully (control experiment). Write the assertions for the behaviour the PRODUCT SHOULD HAVE (case 1 and 3 succeed; case 2 is refused with an explicit, typed, actionable reason naming that an owned Agent needs a transfer or retirement) and mark the failing ones with the repository's expected-failure mechanism named 'known gap: ...', so the file is green and documents the facts. The handoff states, per case, the OBSERVED behaviour with the QA id. Run the file ONCE via goalctl (then rerun a failing file after a fix of YOUR test only). If case 1 unexpectedly succeeds, say so and why (find the code path that exempts the Person Agent), and then the facts report was wrong: record that precisely. Commit before the call.
