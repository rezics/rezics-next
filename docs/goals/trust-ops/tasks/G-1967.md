## Outcome

CONFIRMED defect (test services/main/tests/account-deletion-person-agent.test.ts on main, QA 20261012t041937-82407e): no user who is the only controller of an Agent can delete their Account. Every onboarded user's Person Agent has the user's own principal as its only controller (agent/provision.ts activate: one `agent.control` mandate), and `deactivatePrincipal` (access/admission.ts ~1925-1950) runs `principalControllerSubjects` + `assertControllerContinuity` (access/controller-continuity.ts; `access.agent_controller_count`, migration 054), which throws ControlConflict; Account's `beforeDelete` (services/account/src/auth.ts ~427-432) turns that into a generic 503 and the web says "a safety check could not finish". A right-to-erasure blocker. Read the test first (it documents the three observed cases with 'known gap' expected-failures: flip those marks as you fix each case).

## The rule (decided by the manager; Program confirms before landing; implement exactly this)

1. A PERSON Agent solely controlled by the deleting principal ENDS with the Account: inside the same deactivation transaction its authority subject becomes inactive (access.authority_subject.active = false), its mandates stop counting, and `assertControllerContinuity` ignores the subjects ended this way. "Person" is decided by the Agent's provisioned kind (access.agent_provision.agent_kind = 'person' for that agent id), never by a name or a request field. Profile/graph/media data of the ended Person is NOT erased here (a separate task does that); only the authority ends.
2. Any other Agent (Realm owner, Organization, ...) for which the deleting principal is the last live controller: the deletion request is REFUSED with a typed error carrying up to 16 such Agents (id, kind, display name if one exists) and a `hasMore` flag. Over 16: refused with the typed code `too_many_owned_agents` (no list). Main answers it as HTTP 409 problem `account_has_owned_agents` through routes/problems.ts like `controller_continuity`; Account's beforeDelete passes it through as a 409 with the same structured body (it must NOT become 503; true unavailability, recovery hold and unknown errors stay 503 / unchanged).
3. The retry with an explicit consent input `leaveOwnedAgentsStanding: true` (a validated boolean on the Account deletion request that reaches Access; find how the deletion request is carried from Account to Main and extend that contract minimally, with an optional field and a default of false) completes the deletion and leaves those Agents STANDING WITHOUT A CONTROLLER (maintainer's decision 56: a Realm is not closed by its owner leaving; it stays under the platform's care and only the platform's takedown applies). Record each in a new table `access.account_deletion_orphan_agent (agent_id text primary key, deleted_principal_id uuid, deleted_at timestamptz, operation_id text)` (migration access:986; write it like its sibling access migrations: schema-qualified, no destructive ops, indexes for the lookups used), and make `assertControllerContinuity` treat a subject present in that table as intentionally ownerless (floor waived) so later controller changes, recovery-authority reattachment (the existing 'agent-recovery' activation path) and ordinary operations on that Agent keep working; a NEW controller added later removes it from the orphan state only through the existing control-change path (state clearly in the handoff whether the table row is kept as history or removed; either is fine if tested).
4. Atomic and idempotent: all of this happens in the one existing deactivation transaction under the recovery fence; the same-key retry of an already completed deletion answers as today; bounded cost (the existing 17-row inventory limits; no population walk); no change to the controller-continuity guarantee for any OTHER operation (removing a controller from a live Agent still refuses).
5. Web copy is NOT in this task (a small Luna task follows once the API contract exists): but Account's 409 body must be stable and documented in the handoff (field names and codes).
