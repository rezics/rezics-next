## Outcome

First half of contract C1 (common admission). Kernel K5, K6, K8 and launch
L8 wait on it, so keep it to the smallest change that holds.

Today the published Access policy, deny rules included, is not part of resource
admission. The decision API previews a judgement that register and claim never
make. An admission is valid for a fixed 30 seconds, whatever the authority it
rests on.

Make admission (`access/admission.ts`) judge, at **register, retry and claim**:

- the published policy: mandatory restrictions and ordered rules, deny included;
- representation, the chosen grant and capability eligibility;
- in one place, through the existing evaluator (`policy-evaluator.ts`).

The decision API stays a preview of exactly this judgement. Then:

1. A deny published, or a grant or representation revoked, between register and
   claim makes the claim fail with `AdmissionDenied`. Nothing is written.
2. The lease ends no later than the earliest `valid_until` of the authority it
   rests on: the grant, the representation and each element of the one authority
   path the witness checks. 30 s stays the upper bound.
   - At claim, expiry is checked again even when no generation changed.
     `authority-witness.ts` already checks the chosen grant's `valid_until`;
     extend that witness, do not replace it.
3. If the policy store or witness cannot be read, admission fails closed with
   `AdmissionUnavailable`. It never falls back to allow.
4. Evaluation is bounded (record §9):
   - It reads by index only: the principal, `actingSubject`, the target, and the
     exact generations of one authority path.
   - Its cost does not grow with the number of grants, group members or
     resources. Policy stays in its bounded format (16 mandatory, 64 ordered,
     depth 8).
   - Cache by generation, if at all.

Re-verify each inherited finding against current code before you fix it, and
say in the handoff which ones no longer hold:

- IAM-01 and verify/06 #1 in `.temp/arch-review/README.md` (lines 150–170 and
  240–250).
- Design: `/home/edge/projects/rezics/rezics-next/.temp/arch-review-2/target-architecture.md`
  §9, first list.

## Do not build

- No second policy evaluator, no new witness or proof family, no
  per-resource permission fan-out, no change to the policy format, no
  feature-flag or registry machinery.
- Keep `admission.ts`'s exported signatures. About 30 modules call it, most of
  them in other Goals' areas. If a caller truly must change, stop and propose
  the change in the handoff instead of editing it.
- Controller continuity (T2) and platform exposure (T5) are later tasks. Leave
  hooks for them only where the code already needs one.

## Checks

- Unit tests of the access module and of the files you change; `task main:typecheck`.
- One integration test, `services/main/tests/access-admission-policy.integration.test.ts`
  or extend an existing access integration file. Run it through
  `task goal -- test <file>`. It drives the smallest API counterexamples:
  - a deny published between register and claim;
  - a grant expiring between register and claim with no generation change;
  - revocation before claim;
  - retry after deny;
  - an unavailable policy read;
  - a lease shorter than 30 s when the grant expires sooner.
- In the handoff, give C1's acceptance evidence for the program's board: the
  test names and the commit.
