## Outcome

Launch's "revoked editors" completion criterion exposed a product gap: `POST /v1/work-maintainer-changes` (profile `work-maintainer-change-v1`, actions `add` and `transfer`) can only drop the ACTING maintainer on a transfer. An owner cannot say "remove this co-maintainer". Add that operation by extending the same route and profile (new action `remove`, `target` = the maintainer to remove; no new route unless the existing profile cannot carry it):

- Authority: the same admission/claim path the `add` action uses for the Work; only a current maintainer acting for the Work AND holding the Work's owner/controller authority may remove another (find the rule in `modules/work/maintainers.ts` and the Access owner-proof helpers; do not invent a second evaluator). A removed maintainer cannot remove or re-add anyone.
- Continuity (C1): never remove the last maintainer; removing yourself is the existing `transfer` semantics, so `remove` with `target` = the acting subject is refused with the typed error the route already uses for invalid maintainer changes. The effective controller invariant holds after the change.
- `expectedGeneration` compare-and-set exactly like `add`; the Idempotency-Key replays the same receipt (200, `replayed` true); a different body under the same key is the existing conflict; removing someone who is not a maintainer is a typed no-op conflict (409) that changes nothing.
- Effect: the removed maintainer's very next write on that Work is refused (author-work / work.edit proofs are judged on the live maintainer set; revocation is judged where it is judged today, in one place; no cache of the old set) and nothing they could see before leaks: reads stay public-or-granted as before. Leases or admissions resting on that maintainer's authority end no later than the removal (C1 earliest-expiry rule): show the existing lease/admission invalidation path does it, or fix it.
- Bounded: the maintainer list stays <= 32; one extra indexed read at most.

## Mechanisms

access-authority: extend — owner removal is an authority change judged and recorded by Access; `work/maintainers.ts` stays the Work-side store until it moves onto Access (kernel's frozen-list move), and this change must not make that move harder (no new crossing into Access beyond registered entry points).

## Checks

Real PostgreSQL + real HTTP integration: owner removes a co-maintainer (201, then replay 200), the removed maintainer's next work write is refused, the last-maintainer and self-removal refusals, stale generation 409, non-maintainer target 409, a non-owner maintainer cannot remove, removed maintainer cannot re-add. Show the authority guard, the last-maintainer guard and the immediate-refusal test each fail with the guard removed (mutation + QA id). `task gen`; update `platform-exposure.test.ts` only if an operation count changes. Lint, AST, types. No `--heavy`.
