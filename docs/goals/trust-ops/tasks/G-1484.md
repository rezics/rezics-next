## Outcome

Pool rule: no caller borrows a second client from the pool it holds. G-1472's fault fields
now name the real holders. Launch's recipe-authoring journey (QA 20261008t165710-8e4ed0,
list `.temp/goal-launch/nested-holders-165710.txt`) still shows nine request-path nested
checkouts of the `access` pool, with the outer hold first and the inner caller second:

- `access/topology-control.ts:54 controlTransaction` <-> `access/admission.ts:429
  canReadAsBaselineMember` (nested both ways) and itself (`controlTransaction` inside
  `controlTransaction`);
- `outbox/receipt-custody.ts:87 withReceipt` inside `controlTransaction`;
- `address/registry.ts:92 AliasRegistry.withRead` outer, with inner callers
  `access/admission.ts:792 canReadScopedResource`, `disclosure/read.ts:138 readDecisions` and
  `address/registry.ts:175 currents`.

Fix each at its root with the borrowed-client seam this repository already uses (a function
takes the caller's `PoolClient`/`Pick<PoolClient,'query'>` and never begins, ends or releases
it; the caller that checked it out owns BEGIN/COMMIT/ROLLBACK and release). Where a function is
called both with and without a held client, give it an optional client parameter; the standalone
path keeps its own checkout. Keep every isolation level, `SET LOCAL` bound, lock order, fence
check and authority decision exactly as they are: this is a connection-reuse change, not a
policy change. Do NOT raise the pool size, release-and-reacquire, add an AsyncResource around
a request-path hold, or turn the guard off. A second pool (e.g. Account) is not a nested
checkout of this pool and stays as is. If a site cannot be fixed without changing what it
reads under which transaction, stop and report it instead of guessing.
