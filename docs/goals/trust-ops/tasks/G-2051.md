## Outcome

Four defects the verify landing review found in the merged Account deletion classification (the feature is on main; these are the owed fixes):

1. **Orphan cursor skips lower IDs.** The persisted orphan cursor skips newly affected Agents whose IDs sort before it. Scenario: delete A with consent and 257 sole-controlled Organizations, interrupt after the first orphan batch commits, then remove B's controller from another Organization co-controlled by A whose ID precedes the cursor. The wake frontier discovers it, orphan recording skips it, final continuity fails and every retry repeats the failure. Fix at the source: newly discovered affected Agents are recorded whatever their ID (a separate frontier pass for IDs below the cursor, or a cursor that is a position in discovery order, not in ID order), and the retry completes.
2. **Legacy keep fences are never released.** The classification-frontier migration fences legacy `keep` entries, but completion releases only `end` and `orphan` fences. A deletion paused before the migration containing a co-controlled Agent with effect `keep` finishes with `fenced=true` still set; the fence predicate ignores operation completion and permanently rejects later controller changes and deletion by the surviving controller. Completion releases every fence the operation set, whatever the effect; the migration fixes already-stranded rows (a new migration, claim in frontmatter) by releasing fences whose operation is complete.
3. **The principal-change budget is a different one from the owner's.** The new budget in the classification-frontier migration counts MANDATES, while the mapped `access-authority` owner's principalControllerSubjects counts DISTINCT AGENTS. A with two active controller mandates on each of 129 Agents (B retaining control) used to fit the 256-subject budget and keep continuity through ordinary strongDeactivatePrincipal; it now fails with 54000 at 258 mandates. Ordinary principal fencing must not change beyond the deletion feature: use the owner's budget semantics (distinct Agents) in the trigger, or reuse the owner's function, and prove 129 Agents x 2 mandates succeeds.
4. **The no-rescan test does not enforce the rule.** Scanning every previously classified inventory row at each step would still pass at 8/64/512 (each scan stays below 1024 rows). Make the measure sensitive: assert total rows read grows linearly (rows read at size 512 <= 2x of size 256 x 2 + constant, or count per-step reads and assert each step reads only its new rows), so a fixed-point rescan fails the test; verify by temporarily making the production code rescan and watching the test go red (say so in the handoff).
