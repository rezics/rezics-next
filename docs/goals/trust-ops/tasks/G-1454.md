## Outcome

Two linked findings from program's routing (G-1428).

A. PRODUCT DEFECT (priority). In launch's QA run `20261008t092836-2d8d73` the main log
has 98 `main.database.nested-checkout` worker faults in about two minutes
(`NestedPoolCheckoutError`: a caller holding a pooled client borrowed a second client
from the same pool), and the published recipe page's wiki failed to load. Find the log
(`.artifacts/qa/20261008t092836-2d8d73/**` under the launch worktree, or the main
checkout), identify the exact call stack(s) and the path (route, module, query) that
checks out the nested connection, and fix that path so it uses the connection it already
holds (the pool rule: no caller borrows a second client from the pool it holds; do not
raise the pool size, wrap in release/reacquire, or turn the guard off). Add a real
regression test through the actual path (real PostgreSQL, the guard in 'throw' mode, as
`services/main/tests/nested-pool-checkout.test.ts` does for restore), which fails
before your fix. If the path is outside your claim, stop and report the file and stack.

B. TEST DECISION. `nested-pool-checkout.test.ts` case "restore reconciliation reuses the
held access and relay connections" now sees disposition `unavailable` where the test
expects `conflict` (G-1351, c53d3effc: erasure refusals settle completion as held with
disposition conflict|unavailable|corrupt). Manager decision: a held restore with NO
retained reconciliation is an authoritative conflict (the retained capture is absent;
waiting does not help), so `conflict` with a hold reason mentioning the retained current
capture is right and `unavailable` is reserved for transient native/graph failures. Find
why this path now yields `unavailable` and make production return `conflict` here
without changing the other settlement outcomes; the test assertion stays as it is.
