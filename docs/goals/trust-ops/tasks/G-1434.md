## Outcome

Evidence (read it): the 100k medium campaign `QA 20261008t094618-c92c46`
(`.temp/erasure-campaign-qualification/20261008t094618-c92c46-f1-72544b7bda/qualification.json`,
log `.artifacts/qa/20261008t094618-c92c46/logs/fault-recovery-f1.log`) now passes
sources, samples, copy 0 (compact+index 155 s, activation, rollback) and copy 1
compact+index (120 s), then the 360 s active operation clock ends it before copy 1's
activation and retirement. The old COUNT/sample timeout is gone. The two copies run
serially in one fault file, so the file clock is the sum of two independent copy
operations; each operation alone is about 200 s. The 600 s preparation and 360 s
operation clocks are the program's decision and do NOT change.

Make each copy its own fault-file run: with `ERASURE_CAMPAIGN_COPY=0|1` and exactly
one `ERASURE_CAMPAIGN_SOURCES=<id>` the file runs only that copy (index 0 = rollback
path, index 1 = irreversible retirement path) inside its own 360 s clock, with the
same assertions, pins, evidence, destruction scope and samples for that copy; its
`qualification.json` is labelled with the copy and says it is one of two. Without the
env the current two-source behaviour and all its unit cases stay unchanged. Update
`docs/operations/recovery.md` and the file's header comment with the two-invocation
procedure (two sources restored from one fixture; run copy 0, then copy 1; the
qualification needs both green and both labelled evidence files).

Do not: raise or reshape any clock, drop a phase, weaken or skip an assertion, share
a copy between invocations, or touch production code. If an invariant can only be
checked across both copies, keep it in a small aggregate check over the two evidence
files rather than removing it.
