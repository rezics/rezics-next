## Outcome

The independent-restore drills (G-1776: OPS16 and OPS12, the first physical runs on the small fixture) stop BEFORE the child restore on one native Access capture refusal: `erasure-recovery.ts:491` throws `base Access row changed: access.realm_directory_position` (cause chain RestoreLineageConflict). The later-admission two-cut contract (base = the documented backup, current = the retained capture) compares every Access table row by row and refuses any change to a base row: right for AUTHORITY tables, wrong for tables that background workers legitimately mutate between the backup and the retained capture. `access.realm_directory_position` is the Realm directory index's projection cursor (data_epoch, sequence, phase; written by modules/realm-directory/index.ts, a derived projection of the graph, rebuilt from it). Any other such table will stop the drill the same way one run later, so fix the CLASS once:

1. Enumerate EVERY table of the Access native catalog (`ownerCatalog`) and classify it in code, in ONE table: AUTHORITY (compared exactly as today), DERIVED PROJECTION (a cursor/position/cache rebuilt from another owner: excluded from the base-row comparison and, on restore, reset to its not-yet-built state so its owner rebuilds it, never carried from the old cut), OPERATIONAL (counters, last-used stamps, lease/lock and heartbeat rows: excluded and reset or re-seeded per the existing rule for that table). For each non-authority table state the writer(s) (file) and why it may change after the backup, and what the restore does with it. Look at migrations access/*.sql and the writers (grep INSERT/UPDATE/DELETE by table); `rezics_account_grant.last_used_at` in Account is the precedent for an excluded column in an `authority-v1` profile (docs/storage or the restore-lineage code names it).
2. A unit test enumerates the catalog from the migrated schema and FAILS when an access.* table is in none of the three classes (so a future table cannot silently break restore), plus one test per non-authority table class decision: a changed base row of a DERIVED/OPERATIONAL table does not refuse; a changed base row of an AUTHORITY table still refuses (the existing refusal cases in tests/qa/fault-recovery/access-erasure-recovery.test.ts lines ~322 stay); the digest/footer commits to the classification so a changed classification changes the catalog digest.
3. The restore side: after import, derived projections are in their reset state (realm_directory_position with data_epoch NULL means rebuild, as RealmDirectoryIndex already does at index.ts:36), so the first directory read reports the typed unavailable-until-rebuilt rather than a stale cursor; prove it for realm_directory_position.
Do NOT weaken any refusal for an authority table; do not add a bypass flag.
