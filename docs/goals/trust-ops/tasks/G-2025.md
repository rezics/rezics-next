## Outcome

The independent-restore drills (G-1776: OPS16 and OPS12, the first physical runs on the small fixture) stop BEFORE the child restore on one native Access capture refusal: `erasure-recovery.ts:491` throws `base Access row changed: access.realm_directory_position` (cause chain RestoreLineageConflict). The later-admission two-cut contract (base = the documented backup, current = the retained capture) compares every Access table row by row and refuses any change to a base row: right for AUTHORITY tables, wrong for tables that background workers legitimately mutate between the backup and the retained capture. `access.realm_directory_position` is the Realm directory index's projection cursor (data_epoch, sequence, phase; written by modules/realm-directory/index.ts, a derived projection of the graph, rebuilt from it). Any other such table will stop the drill the same way one run later, so fix the CLASS once:

1. Enumerate EVERY table of the Access native catalog (`ownerCatalog`) and classify it in code, in ONE table: AUTHORITY (compared exactly as today), DERIVED PROJECTION (a cursor/position/cache rebuilt from another owner: excluded from the base-row comparison and, on restore, reset to its not-yet-built state so its owner rebuilds it, never carried from the old cut), OPERATIONAL (counters, last-used stamps, lease/lock and heartbeat rows: excluded and reset or re-seeded per the existing rule for that table). For each non-authority table state the writer(s) (file) and why it may change after the backup, and what the restore does with it. Look at migrations access/*.sql and the writers (grep INSERT/UPDATE/DELETE by table); `rezics_account_grant.last_used_at` in Account is the precedent for an excluded column in an `authority-v1` profile (docs/storage or the restore-lineage code names it).
2. A unit test enumerates the catalog from the migrated schema and FAILS when an access.* table is in none of the three classes (so a future table cannot silently break restore), plus one test per non-authority table class decision: a changed base row of a DERIVED/OPERATIONAL table does not refuse; a changed base row of an AUTHORITY table still refuses (the existing refusal cases in tests/qa/fault-recovery/access-erasure-recovery.test.ts lines ~322 stay); the digest/footer commits to the classification so a changed classification changes the catalog digest.
3. The restore side: after import, derived projections are in their reset state (realm_directory_position with data_epoch NULL means rebuild, as RealmDirectoryIndex already does at index.ts:36), so the first directory read reports the typed unavailable-until-rebuilt rather than a stale cursor; prove it for realm_directory_position.
Do NOT weaken any refusal for an authority table; do not add a bypass flag.

## Manager decision after land review 1 (rule tables, binding)

The first landing review returned one P1 and nine P2 (full text: `.temp/ref/g2025-review1.md`). The root cause of most is how tables were classified: by hand-picking a few. Rule: **a table's class is decided by its WRITERS.**

Method (do it first, write the table into the handoff): for EVERY access.* table (and every column class of a mixed table) grep its writers (INSERT / UPDATE / DELETE / ON CONFLICT outside migrations and test fixtures) and record: table | writer module | writer kind | class | restore rule.

| Writer kind | Class | Restore rule |
| --- | --- | --- |
| Only authority commands (admission, grant, representation, scope gate, receipts, outbox, erasure commands) | AUTHORITY | exact comparison (default for anything not proven otherwise: unclassified = refuse) |
| An owner worker that REBUILDS rows from another owner's data (feed checkpoints/items/targets, serial projections, zone_browse_entry, statement seek coverage, template seek checkpoints, event_temporal_checkpoint, read-ranking projections, realm_thread_checkpoint, judgment_badge_projection (updates updated_at even when the generation is unchanged), realm_directory, realm_directory_position, and every table found the same way) | DERIVED PROJECTION | excluded from the base-row comparison (changed OR removed rows do not refuse); on restore DELETE/reset so the owner rebuilds; the owner reports its typed unavailable-until-rebuilt state meanwhile |
| Schedulers, leases, progress cursors and counters (discovery_refresh_catalog.due_at, discovery_refresh lease_epoch/attempts/due_at, public_name_backfill_checkpoint progress/updated_at, rate_limit_v1, derived_generation lease/state columns, derived_generation_input progress columns snapshot_cursor/snapshot_complete/checkpoint_sequence/checkpoint_event, ranking payload rows, discovery/also-enjoyed generation progress) | OPERATIONAL | excluded; reset to the not-started/not-leased state on restore |
| Immutable identities and closed evidence inside mixed tables (derived_generation: id, family, scope_key, input_digest, input_manifest, validation/closed evidence; derived_generation_input identity columns) | AUTHORITY columns | compared exactly even while the generation is building (the identity-column protection test lists the expected identity columns LITERALLY in the test, never derived from the production rule) |

Other binding rules:
1. FENCING TOKENS ARE MONOTONE: the restored lease/epoch counter after reset is strictly greater than BOTH the backup's and the retained capture's value (max(backup, capture) + 1); a holder with an older epoch can never close the generation, and claimLease increments cannot collide with retained tokens; `markFailed`-style closers check expiry as well as epoch. Test: backup epoch 1, capture epoch 3 -> restored epoch >= 4; delayed epoch-3 holder is refused.
2. PROFILE VERSIONING: the coverage profile identifier is a discriminator: `access-state-v5` rows/captures signed earlier still verify (legacy verifier path kept) and `access-authority-v6` is used for new captures; native attachments carry a catalog version; version-1 attachments are accepted by their own digest rule: write the compatibility transition and test one old signed coverage and one old attachment still verify.
3. OWNER-LEVEL PROOFS: the lease reacquisition proof goes through the OWNER (RankingGenerations.claim with the open recovery fence and a matching input data epoch; RankingBuildWorker inclusion) on a generation that has derived_generation_input and ranking_generation rows, with the graph-restore allocated epoch; not through a raw claimLease.
4. EXISTING TESTS follow the contract: access-erasure-import-faults.test.ts builds its catalogDigest with the new classification-bound digest (parser-cause coverage kept); owner-restore-erasure-release.test.ts SingleConnectionOwner implements/mocks resetAccessRecoveryState (the successful release and interruption assertions are reached again); search the whole tree for every other construction of the old digest or the old ownerCatalog.
