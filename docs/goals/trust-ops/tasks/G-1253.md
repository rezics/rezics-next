## Outcome

`AccessRealmManagement.initializeCreated` (G-1250) saves open-review
settings, but records no initial policy delivery. `realmPermit`
(`access/realm-management-policy.ts`) reads its revision from
`access.realm_policy_delivery` as `urn:rezics:realm-policy:<receipt_id>`.
Submission admission needs a non-null graph revision that matches that permit.
So a Realm created open still answers `pending` instead of `accepted` (launch's
G-1238 integration test reproduces this).

1. **Bind the initial policy to the creation.** The graph Space is written
   first, by launch's `space/create.ts`, then Access is initialized. Both must
   name the same initial policy revision.
   - Choose the smallest contract. The preferred one: launch derives a
     `policyReceipt` deterministically from the creation key, writes the
     initial policy facts to the graph under
     `urn:rezics:realm-policy:<policyReceipt>`, and passes `policyReceipt`
     to `initializeCreated`.
   - `initializeCreated` then records the delivery as delivered, with that
     receipt, in the same Access transaction.
   - Read how an ordinary policy publication writes graph facts and the
     delivery row, and reuse that shape. If launch needs a helper that
     produces the graph policy facts for the creation write, export it from
     Access. Launch calls it; it does not reimplement it.
2. **Replay stays idempotent.**
   - The same key, digest and receipt replay with no writes.
   - A different receipt for the same key is a conflict.
3. **Proof by the counterexample.** A Realm created open with self-join
   admits an eligible member's submission as `accepted`, and a Realm created
   with review answers `pending`. Run this at the Access level, with the graph
   revision supplied as launch will supply it.

## Do not build

- No change to how later policy publications work.
- No graph writes from Access.
- No route.
