Subject: `services/main/src/modules/outbox/receipt-custody.ts` (ReceiptCustody, Access owner) gains a terminal erasure operation (`clearPayloadForErasure`) on branch goal/g-1783 (read it with `git show goal/g-1783` and `git diff main...goal/g-1783`; migration access/1786). The module serialises receipt operations with a per-receipt advisory lock around a callback. Callers pass either an owned connection, or a BORROWED client: (a) borrowed and IDLE (no open transaction; the existing nested-checkout test and the new erasure test use this), or (b) borrowed INSIDE the caller's open transaction (the erasure request path composes it inside its own transaction and must be able to roll back with the caller).
Review findings so far (Sol land reviews):
 - R1 (attempt 1): the clear used durable() = BEGIN/COMMIT on a borrowed client with an open transaction: PostgreSQL has no nested BEGIN, so it committed the caller's unrelated writes and released its locks.
 - R2 (attempt 2): after a SQL failure inside a borrowed transaction the `finally` pg_advisory_unlock failed (aborted transaction) and the catch retained the borrowed connection WITHOUT releasing the SESSION-level lock, which survives the caller's ROLLBACK and blocks other connections indefinitely.
 - R3 (attempt 3, current): the fix used pg_advisory_xact_lock for every borrowed client; for an IDLE borrowed client the xact lock is released when the SELECT finishes (autocommit), BEFORE the callback runs, so two connections can enter callbacks for the same receipt simultaneously and the required custody serialisation is lost. Also (P2) migration 1786's guard trigger breaks tests/qa/integration/title-candidate-original-custody.test.ts at :169 and :234 (it corrupts payload bytes to test the issuer's security assertions); the commit already adapted work-title-control.test.ts with a controlled test-only guard bypass and the same must be done there while preserving every assertion.

Specify: (1) how the module can know, soundly, whether a borrowed client is idle or inside a transaction (e.g. a server-side check such as `txid_current_if_assigned()`/`pg_current_xact_id_if_assigned()` does NOT show a started-but-unassigned transaction; consider `SELECT now() = statement_timestamp()`-style tests, `pg_backend_xid`, or requiring the caller to declare it through the existing borrowed-client contract of this module and the other owners in this repo; look at how other modules (outbox, erasure/request.ts, owner/operations.ts) pass borrowed clients and what the established convention is); (2) the lock discipline for each of the three cases (owned, borrowed idle, borrowed in a transaction) that gives: mutual exclusion for the whole callback, release on commit/rollback of the caller's transaction in case (b), no lock leak on failure, no retained borrowed connection; (3) the proofs: serialisation of two connections on an idle borrowed client, the failing-clear-then-rollback case, caller rollback undoing both writes; (4) the exact fixture adaptation for title-candidate-original-custody.test.ts. Keep the design inside the existing ReceiptCustody owner; no second lock mechanism. State confidence and what you did not verify.
