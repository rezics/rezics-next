## Outcome

Manager decision (product, 2026-10-09; launch asked): an appeal that is decided `reversed` must
lift the ban in the same operation, with a receipt. "Reversed" while the member stays banned
contradicts itself. G-1438 deliberately left `membership_ban` untouched on every decision; change
only the reversed outcome. Other outcomes (upheld, dismissed...) keep leaving the ban as is.

Build on what exists: the decision path (`decideRealmSanctionAppeal`), the realm-admin member
change that unbans (`AccessRealmManagement.changeMember` with action unban, which writes an
`access.realm_admin_receipt` and updates `membership_ban`, membership state and history). On a
`reversed` decision, in the SAME transaction: perform the existing unban transition with a
receipt that references the appeal case, record the resulting receipt id on the appeal resolution,
and keep every existing fence (generation / expected membership generation, authority epoch,
lock order, idempotency). The deciding moderator must hold the authority the existing unban
requires; if the decision path's authority is weaker than unban's, require the stronger one and
refuse with the existing typed error. If the ban already expired or was lifted by someone else
meanwhile, the reversal still records and returns the existing receipt without a second unban.
A replay of the same decision key returns the same result with no second unban. Moderator
identity stays hidden from the member; the member's reading (GET appeal, GET member-ban once
G-1488 has landed) shows the outcome `reversed`, that the ban was lifted and when (`liftedAt`),
and the lifting receipt id, never the moderator. Realm queue/audit reads keep presenting the
appeal and the new receipt without counting either as a report.

If an additive migration is needed, put it in the next free access number and say so in the
handoff; otherwise none. Run `task gen`.

## Checks

Real PostgreSQL + real HTTP: reversed => unbanned atomically (member can post/join per the Realm's
rules again, membership generation advanced), receipt present; upheld => ban unchanged; two
concurrent decisions on one appeal => one effect; replay => no second unban; failure inside the
unban rolls the decision back (no half state); moderator without unban authority refused; member
reading never contains decider. Show the atomicity test and the authority test fail with their
guard removed (mutation + QA id). Re-run the existing appeal, queue and exposure files. No `--heavy`.
