## Outcome

A copyright notice (DMCA-style) runs through intake, takedown, counter-notice
and either restoration after the waiting period or a court-filing stay. Both
parties can see the record of their own case. A scout of the code on
2026-10-07 found:

- **What exists.**
  - Account-free notice intake validates declarations
    (`public-report/contract.ts:31`).
  - Authenticated complaints and restrictions run through governance
    (`routes/rights.ts:206`).
  - Counter-notices need the affected party's credentials and create the
    10–14 business-day windows (`public-report/store.ts:244`).
  - Restoration decisions refuse early restoration or claimant action
    (`governance/store.ts:564`).
  - Staff see due steps (`safety-queue/store.ts:315`).
  - The intended process is in `docs/operations/trust-and-safety.md`, around
    line 148.
- **What is missing.**
  - A counter-notice is recorded but never forwarded to the claimant.
  - Party status reads (`public-report/store.ts:192`) leave out declarations
    and staff steps without a `report_id`.
  - Deadlines do not drive restoration; staff must issue another decision.
    The latest deadline does not prevent indefinite delay.
  - Authenticated `recordStep` counter-notices do not create the same windows
    as public correspondence.

What to build:

1. **One counter-notice operation** for both the public and the authenticated
   path, creating the same windows.
2. **Delivery to the claimant.** It is enqueued with an idempotent receipt,
   and its delivery time is the timing basis for the windows.
3. **Shared records.** Each party reads its own case: notice,
   counter-notice, steps and outcome. Contact details and declarations the
   other party may not see stay hidden.
4. **Deadline-driven restoration.** An indexed, resumable due-case pass
   invokes the existing restoration decision and effects when the window
   ends. It stops if the claimant reports a court filing, or another active
   restriction on the same target exists. Each invocation handles a bounded
   page.

## Do not build

- No new decision engine.
- No calendar service. Business days follow the documented rule; state it in
  code with a test for weekends.
- No change to the takedown policy.

## Checks

- Unit tests for the windows (including weekends), the court-filing stay, and
  a parallel restriction blocking restoration.
- One integration test through `task goal -- test`, covering:
  - notice, takedown, counter-notice, then the claimant receives it;
  - the window elapses (with an injectable clock), then the content is
    restored;
  - a second case with a filing stays down;
  - both parties read their records, and neither sees the other's private
    fields.
- `task main:typecheck`; `task docs:check` if the trust-and-safety paragraph
  changes.
