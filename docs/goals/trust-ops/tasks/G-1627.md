## Outcome

Program decision (2026-10-10): **a thin page in the existing Accounts admin** over the EXISTING grant API: list platform grants, grant a `platform:*` permission to a principal or group, revoke one, each with the audit entry the API already writes. **No new backend operation.** If one is missing (for example a list that the page cannot page, or a revoke that needs a field), STOP and mail the manager before adding it.

- Read the existing Accounts admin (`apps/accounts`, the admin panel structure, its route and layout conventions, i18n/locale handling and Storybook stories) and the grant API (`GET /v1/access/grants`, the `platform:grant` grant/revoke operations in the generated OpenAPI/SDK, exposure group). Build the page the way sibling admin pages are built: same layout, components from `packages/ui`, same locale files (all supported locales get real strings, not English placeholders; ask no translation tool: write them directly), same auth (the page only renders for a principal that may call the API, and the API enforces; hiding is a courtesy).
- Behaviour: list current grants (principal/group, permission, who granted, when, expiry) with keyset paging bounded by the API's page size; grant form (principal or group id, permission picker limited to `platform:*` names the API lists, optional expiry); revoke with a confirm step; each action shows the audit entry (receipt/id and time) it produced; refusals show the API's typed reason (assignment ceiling, last holder cannot be removed, closed operation) in plain words. Never show other people's account details beyond what the API returns.
- Quality bar: this is a back-office page but it must be excellent to use: keyboard-operable, readable empty/loading/error states, no layout shift, works at phone width, light and dark. Judge by looking: run the page in Storybook and the dev stack and take screenshots; iterate on what you see. Add stories for list/empty/error/refusal states and one e2e or component test per action against a mocked-by-contract API client (the generated SDK types), plus one real-stack check if the Accounts e2e tier supports it.
- Launch reviews the UI; keep the page small and conventional.
