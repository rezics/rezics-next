## Outcome

Class A (Program, 05:34). Launch's G-1968 profile (QA 20261012t051748-30046d; text at `.temp/ref/g1968-profile.md` if staged, otherwise the numbers here): one page read that shows a media image whose ASSET has many attachments (Uses on many targets) costs 16 attachments -> 53 Fuseki calls, 186 KB; 64 -> 53 calls, 657 KB; 256 -> 116 calls, 2.55 MB; about 400 attachments exceed the 4 MiB byte ceiling and the page is refused. Cause: media disclosure enumerates the asset's WHOLE attachment inventory: the facts query in `services/main/src/modules/media/store.ts` (~540-556, the `attachments` jsonb_agg over `media.use u WHERE u.asset_id = a.id`) and `services/main/src/modules/media/visibility.ts` (~95-125: `readResourceSummaries` for every distinct (context, target) in `fact.attachments`, and `fact.attachments.every(readable)`). Fix: DISCLOSE THE PAGE'S EXACT ATTACHMENT, never the asset's inventory.

Rule (decided by the manager): (1) when the requested media reference is a USE (the `requested_use` join in the facts query), the facts carry ONLY that Use's own attachment {target, context}: the verdict depends on that one target's readability plus the asset-level checks (lifecycle, moderation, pending/failed job, disclosure/owner rule) which stay exactly as they are; other Uses of the same asset are irrelevant to this page (a hidden or private other target neither blocks nor is probed). (2) When the requested reference is the ASSET itself (no Use: asset-level targets such as governance on the asset, downloads by asset id), keep the conservative whole-inventory rule BUT bounded: read at most 64 attachments (one page of the existing 64-batch), and if the asset has more, the verdict is 'hidden/unavailable' (fail closed, never certify readable from a truncated read), stated in a comment. (3) The selection-slot condition on avatar/showcase roles stays as is (only the selected head counts). (4) Hidden == absent unchanged: a Use whose own target is unreadable answers exactly as before.

Tests (new services/main/tests/media-disclosure-attachments.test.ts, real Postgres + the existing fixtures of media-visibility/disclosure tests): a Use-level disclosure with 1, 16, 64 and 256 attachments on the asset costs the SAME number of summary probes and bytes (assert the call count/probe count via the existing counting harness, not wall time); another Use's target being private/hidden does NOT hide this Use; this Use's own target being unreadable DOES (hidden == absent); an asset-level reference with 65+ attachments fails closed, with <= 64 behaves as before (all readable -> readable, one unreadable -> hidden); moderation/blocked/pending asset still hides the Use. Launch's `services/main/tests/zone-resource-page-budget.integration.test.ts` (G-1968, landing now) has two `test.failing` regressions; the second is this one: DO NOT edit that file (Launch's); after G-1968 lands the manager flips the mark in a follow-up resume of this task. Run the new test plus the owner tests that cover media visibility/disclosure and the cost-pinned media tests (find with --affected --list) in ONE goalctl call; rerun a failing file after a fix; commit before the call; no guard-debt entries; fixtures through Access fixture helpers.
