## Outcome

`GET /v1/me/platform-access` tells a caller which platform groups and operations it may use; the web hides what the summary does not name. The exposure gate admits a group a deployment opens (`REZICS_PLATFORM_OPEN_GROUPS`, as if every caller held the grant), but the summary reports only the grants a principal holds. So where a group is opened, the API admits a command the web never offers: in the QA stack a banned member's appeal answers 201 while their summary is `groups: []`, the appeal page shows no form, and the record of that page cannot hold the command.

The contract is already on main as expected failures in `tests/qa/integration/platform-access-open-groups.test.ts` (subset and wildcard deployments, every persona, a granted member on the cache path). Afterwards those tests pass as ordinary tests.

- The summary names every group the gate would admit for this caller: the groups the caller is granted and the groups the deployment opens, sorted, each once. A wildcard names every group the generated exposure declares. Operation grants are unchanged.
- A caller without a principal gets the opened groups as well, exactly as the test requires.
- `generation` differs between two deployments that open different groups, so a summary kept by a client does not outlive the configuration.
- Remove `test.failing` from those tests and change no assertion in them. Add the owner's unit cases beside the existing ones.
- An outcome proof that asserted an empty summary under the opened QA stack asserted the defect. Do not edit it: name it in the handoff with file and line.

Do not build: a new environment variable, a grant written for anyone, a change to what the gate admits, a change under `apps/web/`, a second place that reads the opened groups.

## Design note

Read by program: 2026-10-14

1. One value. `AccessExposure` already holds the opened groups for `groupOpened`; `summary` uses the same field. The route builds no summary of its own: the anonymous answer comes from `AccessExposure` too, so gate and summary cannot disagree.
2. No query is added. Opened groups are constants of the process; the cached summary stores the union, and the cache key and its expiry stay as they are.
3. Bounds. The response allows 128 groups. A union above that is a configuration fault found at start-up, not a 503 per request.
4. `generation` includes the opened set in its hash. With nothing opened it is byte-for-byte what it is today, so existing clients and records see no change.
5. Production preflight still refuses the variable. This task changes no production answer.
