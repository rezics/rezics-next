## Outcome

Main's declared problem answers match the answers its routes send, so an integrating
program can validate and retain a stale-write refusal without losing the conflict
details that the surface consumes. This is compatibility and contract-guard debt,
not a new capability or a promotion of any persona cell.

Program mail `3c83aba0-e341-4204-bc69-2f1d67d0b781` reports that G-2303's
`zone/a-zone-without-a-realm` six-persona recording passed but could not be
published: `POST /v1/content-drafts` returned its superseded-`expectedHead` 409
as `application/json` while declaring `application/problem+json`.

1. Inventory the entire hand-built problem-response class under
   `services/main/src/routes`, starting with the fifteen reported sites:
   stale_head in ratings, rating-global, contributions, semantic, media,
   resources (two) and content; stale_agent_profile; stale_session;
   stale_realm_profile; structure_refresh_conflict; interpretation_unresolved;
   unavailable_reference; and editorial-proposals. Each uses the existing
   `problem()` owner with its original status, code, title and detail members.
   If the inventory exposes a sibling outside the named paths, report the path
   for a scope decision; do not silently omit it or broaden the claim.
2. Every affected operation's declared answer admits each member actually sent,
   with its real type and nullability. Preserve `currentHead` (including null),
   `current`, `submitted`, `replayed`, `conflicts`, semantic reference diagnostics
   and any editorial details. Extend the existing typed problem details and
   response schemas only as needed. Do not erase details, rename them, allow
   arbitrary additional properties, or downgrade the declaration to JSON.
   Main currently already declares optional nullable `currentHead` in
   `problemResult`; verify the emitted operation rather than assuming it lacks it.
3. Focused tests exercise each affected answer through the actual Main HTTP
   route and validate status, `application/problem+json`, no-store and the whole
   body against that operation's emitted declaration. For Content include the
   superseded expected head and exact current head, plus null-head coverage
   wherever it is a valid conflict. Preserve validation of retained samples:
   fix the producer/declaration, never the recorder or its guard.
4. A route-wide executable guard rejects hand-built problem answers, including
   the reported `Response.json` form, and admits normal successful JSON and the
   canonical implementation inside `problem()`. Include negative controls that
   restore a representative inline problem and positive controls for successful
   JSON; the guard must not be merely a list of today's fifteen line numbers.

and the Content admission path (`saveAdmittedContentDraft` and its callers):
identify the exact denial/expiry/authority state, available grant/claim timing,
and whether it differs from the successful run. No new population run or retry

A genuinely unfinished admission must keep its existing retryable semantics;
a durable refusal must remain a refusal. Neither is inferred solely from a
403, load, or the neighbouring 201. No admission/Account repair, changed 403
expectation, weakened proof, new generic retry wrapper or assertion edits in
this task. A confirmed transient-as-refusal defect needs a separate outcome
brief before implementation; hand off its evidence and affected callers.

Do not build a new response framework, schema generator or dependency; no UI,
record format, lifecycle, storage, policy or authority changes. Keep this cut
small enough for one worker session.
