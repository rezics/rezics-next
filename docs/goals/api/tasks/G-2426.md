## Outcome

The area tasks that cover current-authority replay each claim one `*.entries.ts` file and may not change the shared driver. Three of them stopped at the same boundary (`.temp/ref/` holds their packets): the driver knows two authority classes, `controller` and `domain-grant`, and the ratchet knows two lists, covered and uncovered. Commands outside those have no honest place.

Afterwards an area task can register, without changing a shared file:

- a command whose only authority is the acting principal (`PUT /v1/me/interaction-mutes`, `PUT /v1/me/notification-preferences`);
- a command whose caller holds a capability or a case credential instead of an Account (public intake, private correspondence);
- a command whose owner binds its saved result to the resource, not to the request key (Realm initialization stores `realm-init:<Realm>`);
- a command that keeps no result, as a non-replay entry the ratchet runs.

Existing entries compile and pass unchanged. The ratchet places every discovered command in exactly one of covered, non-replay and uncovered, and the uncovered count may only fall.

Each new class is proved in `driver.test.ts` against a small stand-in owner written in the test: the driver passes when the owner refuses after the loss and fails when the owner returns its saved result. No real entry is added here; the entries files belong to the area tasks.

Do not build: a change under `services/main/src/`, an edit to any `*.entries.ts`, a new exemption list, a classification that is only a comment.

## Design note

Read by program: 2026-10-14

Decisions, each with its reason.

1. One rule for every class: after the caller loses the authority the command needs, the same key and body get the refusal a fresh call gets, never the saved answer, and the stored state is unchanged. The classes differ only in what the authority is and how it is lost.
2. `principal`: the authority is being that active principal with a valid credential. Losses: the credential is revoked or expired, and the principal stops being active through the product's own command or the fixture that stands for it. Removing a grant or a controller proves nothing here, which is why the two existing reductions could not cover these commands.
3. `capability`: the authority is holding the capability or case credential. Losses: revoked, expired, and consumed where the capability is single-use. The caller has no Account; the driver takes the credential from the entry instead of a session.
4. `resource-identity`: the owner deduplicates by the resource. The entry names that identity. Proof: the same key gives the first answer again; another key on the same resource gives it too; a changed body gets the answer the owner declares (the entry states it); after the loss both keys are refused. Reason: binding the request key inside every such owner is product work that adds no safety a retry does not already have, but a key the route declares must not be dead, so the entry proves which of the two identities holds. A command that today is neither (a repeat gives another answer) is a product defect for its owner, failing test first; it is not classified here.
5. `non-replay`: an entry with a reason and a check the ratchet runs: the contract declares no idempotency key for the operation, and a repeat executes again and gets the answer the entry states. A command that stores a result for its key is never non-replay.
6. The ratchet reads the three lists from the area modules as it reads two today. Its baseline holds the uncovered count; a change that raises it fails.

Rejected: one loan of the shared files to each area task (ten tasks would serialize on one file), and marking principal commands non-replay (they store a result, so that would hide a real replay).

## Mechanisms

access-authority: consume — the driver reuses the owners' current authority decisions and the accepted fenced fixture setup; it adds no product mechanism.

## Checks

`task goal -- test services/main/tests/command-replay-authorization/driver.test.ts` and the ratchet test, then `task goal -- check`. The handoff lists, for each of the three packets, which class its commands now register under, so the area tasks continue from one list.
