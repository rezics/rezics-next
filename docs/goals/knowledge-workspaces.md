# Subject-connected knowledge workspaces

## Outcome

A writer or learner organizes private documents around shared public Subjects, deliberately publishes selected
revisions, and reuses exact references to public knowledge. A Subject stays useful across independent authors and
notebooks. The same viewer-aware page/API may combine public content with that viewer's authorized private work.

The [product contract](../knowledge-workspaces.md) owns the model and release sequence;
[delivery and acceptance](../knowledge-workspaces-acceptance.md) owns the scenarios, baseline and native growth proof.
Both are adopted requirements; none of this Goal is claimed implemented by documentation alone.

## Done when

- The first-public writer journey works from an ordinary public Character through private Inspiration/Arc/Scene
  documents, nesting/reordering, conflict-safe editing and precise references to a selectively published analysis.
- Another reader discovers that publication from the Subject, follows an exact citation and creates independent
  private notes. Private siblings, ancestry, future drafts and other users' attachments are absent from public
  responses, source indexes, metadata, exports, media and cache representations.
- The structural mathematical journey works with problem, solution, theorem and definition documents: source-step
  references retain exact assumptions and versions, and learning navigation expands on demand. Mathematical source
  text is preserved; advanced formula rendering and formal checking are not presented as complete.
- Publication uses exact selected revisions and generation-specific historical eligibility. Withdrawal, trash,
  restoration, moderation, revoked identity and account erasure obey current authority with indexing paused and
  delayed jobs/replays. Restore does not republish old selections.
- Structure changes remain acyclic under concurrent moves; semantic merge/unmerge never merges documents or
  placement identities; lists, reference resolution, ordering maintenance and cleanup meet adopted cost bounds.
- Both user journeys pass native API acceptance before their ordinary generated-client/browser checks, with
  keyboard/narrow-screen review and native growth evidence on the integrated candidate. Promoted revision is recorded.

## Scope

The first-public scope is the complete first row of the product contract's release-priority table: private owned
notebooks, primary outline, subject attachments, same-page audience composition, exact/live navigation references,
revision publication and useful public Subject discovery, single-document copy/export and full lifecycle.

Local databases, rich math, team sharing, reference placements, synced content, realtime/offline editing, formulas,
bulk import and formal proof integrations are subsequent versions with their own acceptance gates. Existing
Articles/hosted works, general Search and Zone source exposure remain governed by [scope](../scope.md); the new
capability does not open every old grant-closed surface.

## Ownership

Content is the coordinating owner under the existing Content manager. This Goal introduces no new manager process
or control-plane configuration. Existing owners retain their paths and mechanisms:

| Owner       | Responsibility                                                                                                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Content     | Notebook/document/placement/reference and publication lifecycle, native sources, revision/media composition, erasure locators and direct document outcomes in the existing content module |
| Semantic    | Subject identity, definition-owned vocabulary, attachment identity resolution and ordinary catalogue contribution; no private document catalogue                                          |
| Accounts    | New native resource/action declarations, grants, current eligibility and account/Realm lifecycle through existing Access                                                                  |
| Search      | Admitted public association discovery/preparation and later query sources; no private facts in global indexes                                                                             |
| Web         | Document package extensions, editor/outline/subject composition, exact-reference navigation, publication preview, recovery, accessibility and generated-client consumers                  |
| Performance | Native plan/physical-work measurement, bound composition, large fixtures and contention/latency evidence                                                                                  |

Library and Zones consume admitted sources where their existing contracts support them; they do not own document
storage or sharing. Kernel command, History, events and Work remain shared infrastructure. Implementation modules
must register their ordinary public surfaces and dependency direction.

## Acceptance

Run the scenario suites and growth checks defined by the acceptance owner after their implementation paths exist.
The supermanager freezes actual commands and fixture paths in coherent briefs; this design does not invent tests
that currently pass. Record the exact integrated/promoted revision, persona, public exposure and native/browser
outcomes. A successful save, enqueue, build or screenshot alone does not complete this Goal.

## External conditions

No new hosted service or commercial integration is required for the launch design. Source content must have rights
for its selected publication; use original licensed fixtures. Later renderer, synchronization or proof dependencies
require version/licence review and their release-specific evidence before adoption.
