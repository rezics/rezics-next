## Outcome

Nothing in the tree still treats a chapter as a Work, and the last two Post
surfaces are finished, per
[Posts, texts and Works](../../../contracts/work-and-release.md#posts-texts-and-works).

1. (The reader's "also a Work" link is placed by G-1081, which holds the reader
   files; do not touch them.)
2. **Manage wording.** A queue subject that is a chapter Post with no readable
   label says "A chapter of <Book>" (all eight locales), never the Work
   fallback; thread it through the queue detail, view, log and context.
3. **Dead paths.** After the migration a Post never passes the Work header
   read: remove `partOf` from `work/read-header.ts`, its read contract and the
   web consumers (`queue-subject.ts`, `chapterPlaceHref` if unused), using
   Main's moderation `facts[].partOf` or `post-read-v2` placements where a place
   is still needed. Remove anything else only chapter Works used.
4. **Names and comments.** Rename `structure/chapter-work.ts` and its
   functions by what they do now (a Post's Book placements), and fix comments
   that still say "chapter Work" (`zone-modules/read.ts`,
   `address/redirect.ts`, `studio/content-api.ts`, and any you find).
5. **Legacy fixtures.** Fixtures that still write chapter Works directly
   (g-542 endpoints, found by G-1112) create chapter Posts the way Studio does;
   then remove the legacy chapter-Work branch G-1112 kept in
   `content-publication/search.ts`. Assertions stay unchanged.
6. **Docs.** Make `services/main/src/modules/structure/README.md`,
   `docs/contracts/creation.md` and `composition.md` state chapters as Posts
   placed by occurrences; delete what code now states; keep decisions and
   reasons only. The chapter Post migration (startup backfill and the narrow
   Jena policy) stays: older dataset snapshots may still hold chapter Works.

Smallest change. Do not build new features or rename served profile values.
