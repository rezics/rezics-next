## Outcome

G-1163 made votes and empty refreshes leave feed pages valid. Feed and Realm
thread cursors still restart with 409 after **any** graph write between two
pages.
- `decodeReadCursor` pins every cursor to the exact graph read position.
- The web client's `sameSource` (`apps/web/features/feed/projection.ts`)
  treats a changed `sourcePosition` as "moved".

On a live platform, where graph writes arrive continuously, readers keep
restarting. Better write concurrency makes this worse.

The G-336 decision (`services/main/src/modules/read-basis/retention.ts`) rejects
silently relaxing the sequence check. It endorses retained membership owned by
each owner, with disclosure checked live.

Register the Home feed, and Realm thread reads (`realm-reply/thread-read.ts`),
as retained-read-basis families under that protocol:
- **Membership:** the Access population revision, plus the target, follow and
  personal revisions where they apply. It does not include the graph sequence.
- **Expiry:** `READ_BASIS_RETENTION_MS`, fixed by the first page.
- **Disclosure:** stays live on every page, so a revoked or hidden item
  disappears instead of leaking.

Change the web projection so a moved graph position alone does not count as
"moved" for these families.

Record the rule where `retention.ts` keeps the G-336 decision, and in
`feed/timeline.md`. Do not add a graph snapshot, a copy or a cache.

## Checks

- **New cases in `tests/qa/integration/read-stability.test.ts`**, or in a feed
  test file, between two pages:
  - an unrelated graph write keeps the cursor valid;
  - a disclosure change on a served item hides it on the next page;
  - expiry ends the cursor;
  - a population change still gives the documented restart.
- `apps/web/features/feed/projection.test.ts` covers the web rule.

- The feed and Realm-thread integration files your change affects, run through
