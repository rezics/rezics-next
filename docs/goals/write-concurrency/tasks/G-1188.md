## Outcome

This Goal removed platform-wide write serialization: Content's owner
position, the feed checkpoint, the notification head, source fences, ordered
heads and scope gates. Add a check so a new one cannot land unnoticed.

The check fails when any of these appears without an allowlist entry:
- **A singleton table in a migration.** A boolean primary key with
  `CHECK (id)` or `CHECK (singleton)`, or another one-row design, under
  `services/*/migrations/**`.
- **A constant advisory lock key in source.** A `pg_advisory_xact_lock` or
  `pg_advisory_lock` whose key does not include a per-object value, under
  `services/*/src/**` and the migrations.
- **A write to a singleton in source.** An `UPDATE` of a singleton, or a
  `FOR UPDATE` / `FOR NO KEY UPDATE` lock on one.

Each allowlist entry is code, not a document. It gives the relation or key,
its class (`post-commit sequencer`, `builder fold`, `operator/startup`,
`recovery fence`, `rate gate`, `projection checkpoint (background)`), and a
one-line reason.

Seed the list from the current tree. Every remaining singleton must fit a
class whose writers are not user request paths. If one does not fit, report it
in the handoff instead of allowlisting it.

Follow the existing SQL relation guard's style (`scripts/qa/sql-relations.ts`,
`tests/qa/unit/g-1046-sql-relations.test.ts`): a parser in `scripts/qa/` and a
unit test. Run it from the static checks in
`scripts/research/storage_architecture/check.ts` if that is where such guards
run.

Do not change product code.

## Checks

- The new unit test passes on main.
- It fails on deliberate examples, in test fixtures: a new singleton table, a
  constant advisory key, and an `UPDATE` of a singleton in a route module.
- `task check:backend`
