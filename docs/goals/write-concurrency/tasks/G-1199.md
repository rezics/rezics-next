## Outcome

Review findings P2-1, P2-2, P2-3 (G-1195), all from G-1168's change signals (Access 1172, Content 810):
- P2-1: equality fences compare `h.snapshot::text`, so while any older writer is open in the cluster every check reports a change and reads churn. Replace with the count of visible change rows at or above the horizon (or another value that only moves when a covered change commits).
- P2-2: `access.site_moderation_change`, `realm_count_change`, `realm_growth_change` and `reading_position.change` gain a row per transaction and are never pruned. Add a bounded prune of rows below the largest stable key, run from an existing periodic worker.
- P2-3: `reading_position.change` keys on Content's `data_epoch` plus xid, but that epoch never changes on restore, so after a logical restore the fence never settles. Key on an epoch that a restore does advance (follow what G-1164/G-1162 did), or document why the Content restore path bumps it.

G-1198 runs concurrently on `realm-directory/**`; if your change needs `realm-directory/index.ts` beyond the fence read, coordinate by keeping your edit to the fence query only.

Smallest change; no new services or options. Read the finding in full in .temp/research/write-concurrency-review.md (main checkout) first.
