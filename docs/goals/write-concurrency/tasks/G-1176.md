## Outcome

Two Studio reads fence on the platform-wide Content position:
- the chapter list (`services/main/src/modules/studio/chapters.ts:94-97`);
- the variant page (`services/main/src/routes/studio.ts:155-157`).

Each one lists variant heads (`ContentCore.listVariantHeads`, which joins
`content.owner_control`), then queries the graph, then answers 409 "Content
variants changed" if `ownerPosition()` moved in between.

Since G-1162, every reading-progress save, session update, comment and media
command is a Content write. So any write by anyone between those two reads
fails an author's Studio page.

Fence each read on the state it actually returned: the listed variants'
`draft_head` values and the Work's variant set. For example, re-read the same
heads and compare them, or use a per-Work head if one already exists. A write
to another Work must never fail the read. A change to this Work's variants
still returns the existing 409.

`listVariantHeads` should stop joining `owner_control` unless something else
needs its position. Keep `sourcePosition` in the response only if a client
uses it; check `apps/web` before removing it, and report rather than change a
served shape.

Smallest change: no new tables, caches or options.

## Checks

- **New integration case:** a Studio chapter list and a variant page succeed
  while concurrent progress saves and comments on another Work commit between
  their reads, and still answer 409 when one of this Work's variants changes.
  Use a hook or a held transaction for determinism, not timing.
- `task content:test`, `task main:typecheck`
- The Studio and content-variant integration files your change affects, run
  through `task goal -- test`.
