## Outcome

`access.append_notification_producer_event`
(`services/main/migrations/access/495_notification_producer_log.sql:58`) gives
each event a gap-free position by updating the single row
`access.notification_producer_head`. Every transaction that appends holds that
row lock until it commits: every post vote, chapter publication, review,
invitation, submission decision, moderation outcome and Realm role change on
the platform.

Change only the internals so appends are plain inserts, following the
[GOAL.md pattern](../GOAL.md#pattern):
- each event row carries `xid8` from `pg_current_xact_id()` and an identity id;
- the consumers read in one statement, ordered by `(epoch, xid, id)` and gated
  by `pg_snapshot_xmin(pg_current_snapshot())`. These are
  `runOtherAccessOnce` and `runSafetyCorrespondenceOnce` in
  `notification-producers/producer.ts`.

Keep these unchanged:
- the function's name and arguments, which its triggers (migrations 495, 622,
  701) and `feed/store.ts` call;
- the event kinds;
- per-tick bounds (`PRODUCER_COST`);
- the cursor table's role: the consumer is still the only one that updates it.

Migrate existing cursors so no already-consumed event is delivered again and
no pending one is lost, then drop the head row.

Choose the epoch from what Access already has for restore, such as the recovery
fence or the relay data epoch, and explain the choice in the handoff. A logical
restore (pg_dump) does not carry the transaction counter
(`tests/qa/fault-recovery/erasure-restore.test.ts`), so new events after a
restore must order after the old ones. Update the Drizzle declarations and the
module README's cost and rules lines.

Keep it small. Change no other producer, no editorial clock, no
feed code, no delivery or digest code. Add no shared library, no new
worker and no configuration option. If a reusable helper would save code here
and in later fence tasks, keep it to one exported SQL fragment or function in
this module, and do not generalize further.

## Checks

- **New `tests/qa/integration/notification-producer-log.test.ts`** against a
  real Access database:
  - Two concurrent appending transactions do not block each other. Hold one
    open; the other commits within one second.
  - A held transaction with the lower xid is not skipped: the consumer stops
    before it and delivers it after it commits.
  - After an epoch change, events order after the old ones.
  - Each event is delivered once per consumer.
