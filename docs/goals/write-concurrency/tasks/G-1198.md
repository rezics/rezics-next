## Outcome

Review finding P1-2 (G-1195): since G-1165, every refresh cycle — including incremental ones after any graph write — clears the whole spare generation and recopies every published row (64 rows per tick, a `realm-count:` advisory lock per Realm) before hydrating the Realms that changed. Cost per publish grows with the number of Realms, and the worker runs whenever the graph sequence moves.

At the start of an incremental cycle, bring the spare generation up to date by copying only the Realms that changed since it was last published (the previous cycle's changed set plus this cycle's); keep the full clean-and-copy for rebuilds. Drop the `sourcePosition` fence on first pages if the review shows it only forces restarts. Keep the published generation readable throughout and keep count deltas exact.

Smallest change; no new services or options. Read the finding in full in .temp/research/write-concurrency-review.md (main checkout) first.

## Checks

- Unit or integration: with N Realms published and one Realm changed, an incremental publish touches O(changed) rows, not O(N) (assert a row or statement count independent of N).
