## Outcome

Main-wide regression (QA `20261005t223603-b21ab3`, fails alone):
`tests/qa/integration/library-status.test.ts:201` sends two identical library
visibility changes with the same `expectedVersion` at once. It expects one 200
and one 409; the loser now answers 503.

Before this Goal, both requests queued on the singleton
`access.also_enjoyed_source_fence` row, which an `agent_library_visibility`
trigger bumped. The second one then saw the version move and answered 409.
G-1167 and G-1179 replaced that bump with change-row appends, so the two
transactions now race directly. The loser hits some other error that maps to
503: a unique violation on a change row, a deadlock, a serialization failure,
or a lock timeout.

Find the error from the stack log, then fix the product so the loser is
refused as stale (409):
- Lock the visibility row itself (`FOR UPDATE` on the Agent's row) before the
  version check.
- Or make the conditional update and its change-row append conflict-free.
- Or map the specific error to the existing stale conflict where that is
  semantically exact.

Search the other writers whose triggers G-1167, G-1179 and G-1183 changed
(rating seals, onboarding, shelf status) for the same race, and fix them the
same way.
