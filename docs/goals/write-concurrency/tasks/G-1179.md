## Outcome

G-1167 removed writer locks from the discovery and also-enjoyed source fences.
Writers append one change row, and builders fold those rows into the fence
revision (Access migration 1160, Content migration 800). Two liveness problems
remain:

1. **Builds may never finish under load.** Change rows are platform-wide. Any
   judgment vote, rating seal or shelf change makes every discovery generation
   stale. Any change during a multi-batch build restarts the build. With
   continuous writes, a discovery or co-reader generation can restart forever
   and never activate. This was already true before G-1167; write concurrency
   makes it more likely.
2. **Co-reader change logs grow without bound.** Access and Content
   `also_enjoyed_source_change` rows are folded only when a co-reader build is
   registered, which today happens only on a manual build.

Make builds converge:
- Key change rows by what they affect, for example the Work or scope behind a
  statement, rating or shelf entry, so a build or refresh treats only changes
  to its own inputs as invalidating.
- A build in progress absorbs later changes to its inputs incrementally, or
  completes against its basis and lets the next refresh cover them. It must
  not restart from zero on every change.
- Fold co-reader change logs on a schedule, reusing an existing periodic worker
  where one fits, so they stay bounded.

Keep the no-skip guarantee: a change committed after a build's basis is
never treated as covered by that build. Keep the discovery-refresh-retirement
behaviour.

Also fix `tests/qa/integration/g-834-session.test.ts`. Since G-1167 its "no
invalidation" check compares only `reader.also_enjoyed_source_fence.revision`,
so it is now always true. It should also count unfolded change rows.

Smallest change that converges. No new services, no caches, no options.

  scope still makes the result report stale afterwards.
- **Co-reader logs:** the change log is folded without a manual build.
