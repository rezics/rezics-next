## Outcome

Two transactions wait on Fuseki over HTTP while holding rows that the whole
platform shares.

1. **Realm directory reads.** `RealmDirectoryIndex.refresh`
   (`services/main/src/modules/realm-directory/index.ts`) runs on user GETs:
   `/v1/realms`, `/v1/query` (`query/resources.ts:628`) and the discovery
   sections. While it runs, it holds two rows:
   - the singleton `access.realm_directory_position` FOR UPDATE (`:53`), so
     concurrent directory readers serialize whenever the projection is stale;
   - `access.realm_count_position` FOR SHARE, so every Realm join and leave
     waits (2 s `lock_timeout`).

   It holds both across up to 163 Fuseki calls (10 s deadline).
2. **Joins.** `recordRealmHistoryAdmission` (`realm-admin/history.ts:14-28`)
   queries Fuseki inside the membership transaction. Its callers have already
   taken `access.scope_gate 'work:create:root'` FOR UPDATE: `memberships.ts:452`,
   `private-memberships.ts:430`, `realm-management-members.ts:63` and
   `join-requests.ts:307`. So one slow graph read stalls every Access mutation
   that takes the gate.

Make GETs take no write lock and run no rebuild inline. They serve the last
built directory with its position, and refresh happens in a bounded background
step (the Main process already runs periodic workers; reuse that shape).

For joins, read the graph position before the transaction, then inside it
check only what is local: Access state, the read position's epoch, and a
compare-and-set that fails as stale rather than waiting. History admission must
still record the graph position it is for.

Keep these as they are:
- the response shapes;
- the directory's ordering and count semantics;
- the scope gate's mode, which is a later task in this Goal.

Smallest change only: no new services, no caching layer, no configuration
options.
