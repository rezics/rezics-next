## Outcome

A viewer of a 1,000-episode series sees exactly how far they have watched and
can resume or jump by episode number with bounded work, on any device. G-1337's
episode panel works for short series. At scale (its handoff) two launch-owned
reads fall short:
1. `/v1/reading-positions/{work}` (numeric seek and the reader's furthest
   finished occurrence, `position=mine`) fails for Episode parts:
   `reading-position/traversal.ts` (`child()`, `readMetadata()`) assumes every
   part is a Work. Make it work for any admitted occurrence type the Structure
   holds (Episode included), by seek, not by walking pages.
2. There is no read of "my completed occurrences in Structure S". Add one,
   cursor-paged, on the progress owner's existing keys and indexes, so the
   panel can show exact furthest-finished and per-episode ticks.

Every new or changed operation keeps `exposure` and a `read` rate-limit family;
list any new public operation in the handoff.

Not this: no anime, manga or game progress store, no whole-series reads, no
Composition read changes (kernel's: the composition page budget and ordinal
seek are a separate kernel request).

## Checks

```sh
task goal -- test services/main/tests/long-series-progress.test.ts
task goal -- test tests/qa/integration/long-series-progress.test.ts
bun node_modules/typescript/bin/tsc --project services/main/tsconfig.json
```

Counterexamples:
- in a 1,000-episode series, episode 1000's position resolves by number with
  bounded rows examined;
- the reader's furthest finished is right after out-of-order ticks;
- a second device sees the same;
- specials don't count toward the main sequence.
