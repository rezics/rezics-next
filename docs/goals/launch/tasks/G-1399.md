## Outcome

A Zone's published route lookup (`zone/route.ts`, `mountAt` at about :288)
pages through `readVisibleCompositionPage` until it finds the segment, so cost
grows with the navigation tree. A missing segment scans everything. G-1284's
review left this open pending kernel's keyed read. That read is now on main:
`readCompositionOccurrenceByQualifierKey(env, { structure, revision, key: {
type: 'zone-mount', zone, routeSegment }, header?, signal? })` in
`structure/read.ts` returns occurrence | null with sourcePosition and TreeCost.
Missing coverage answers UNAVAILABLE, not empty.

Resolve a published route through it:
- one key descent, plus the existing disclosure and final authority checks on
  the hit;
- a miss answers as today's not-found, with the same status and body;
- UNAVAILABLE coverage fails closed as an unavailable read, never as not-found.

Keep alias and id keys working, and keep the published-bundle rule (the
route reads the published revision, never current heads). Remove the scan
path; no fallback to it.

Counterexamples:
- a navigation of 1,000 mounts: the first, the last and a missing segment cost
  the same, bounded number of graph calls;
- a mount added in a draft isn't routable until published;
- a removed mount stops routing after republish;
- unavailable coverage is never reported as not-found.
