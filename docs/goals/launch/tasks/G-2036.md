## Outcome

Read-only sweep, part of audit pass 2 (program, 2026-10-12 12:01 UTC, from
the maintainer's question why notifications still failed after their
research). `docs/contracts/notifications.md` settles who is notified and at
which level, but says nothing about the inbox as a LIST. The web paged it with
its own arithmetic on the sequence, untested until today
(`window.test.ts`). Pass 1 found the same shape elsewhere: the library's
Continue stops at six, the shelf at 101.

Sweep EVERY list surface in the web (`apps/web`): feed, library, shelves,
reading status, notifications, search results and typeahead, Realm threads,
replies and members, directories (Realm, Zone), catalogue browse in every
Zone, episode and chapter inventories, Collection pages, Zone navigation,
recipe lists, imports and exports. One line per surface:
(a) does it page with the continuation the API returns and nothing else;
(b) does a filter or sort keep the API's continuation, or compute its own
window, offset or sequence arithmetic;
(c) is there a count beside it, and is that count read as one snapshot with
the page (not a separate racing read);
(d) which test covers a second page (file and test name), or "none".

Give each surface's file and line. Then list separately every surface that
computes its own window or has no second-page test. Finally, say whether a
mechanical guard is possible ("no arithmetic on a sequence, cursor or offset
outside the API client"): an ast-grep rule or a repository guard. Name the
pattern it would match and what it would flag today, so the program can class
the fixes. Change no code. Write the table to `.temp/list-sweep.md` in your
worktree and summarise it in the handoff.
