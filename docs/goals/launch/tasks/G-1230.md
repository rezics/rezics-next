## Outcome

A broadcast to a resource's followers and watchers does bounded work per batch
whatever the audience size, and finishes for every eligible recipient across
restarts. Today `follows/recipients.ts:30–53` unions all candidates, joins
preferences, sorts the remaining population and then takes `LIMIT 257`: one
page inspects O(N) candidates. Producers also stop when the first page is empty
(`notification-producers/resources.ts:158–159`, `producer.ts:91–92`), so a
first batch of only ineligible candidates ends a broadcast that has eligible
recipients later.

Evidence: `/home/edge/projects/rezics/rezics-next/.temp/goal-launch/scale-showcase-evidence.md`, "Task C" item 1. Binding criterion: every operation touches a
bounded neighbourhood (`/home/edge/projects/rezics/rezics-next/.temp/arch-review-2/target-architecture.md` §1 and §10).

## Smallest change

Seek raw source candidates in a stable order before eligibility, a fixed batch
per source; persist the examined frontier in the existing recipient progress
(`notification/store.ts:315–323,441–443`, Access migration 1017), widening it
with migration 1330 only if one UUID slot cannot hold the frontier; commit each
batch on its own; continue through batches that yield no eligible recipient;
advance the event checkpoint only when every source is exhausted. Remove the
first-page emptiness prechecks.

Do not build a broker, a fan-out service, a new queue table, a scheduler or
options nobody asked for. Reuse notification intake and its idempotency.

## Also: no nested pool checkout

Trust-ops' T6 (f0616aaa3) detects a request that holds a pool client while
borrowing another from the same pool, which deadlocks under load:
`notification-producers/producer.ts:420` holds the Access client taken at
`:396` and calls `editorialNotification`, which queries that pool at
`editorial.ts:49`. Pass the held client instead. Run this task's tests with
`REZICS_NESTED_POOL_CHECKOUT=throw` so any other nested checkout in the
files you touch fails, and fix those in your claim too.
