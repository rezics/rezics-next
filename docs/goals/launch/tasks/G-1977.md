## Land review 2 (2026-10-12 08:12 UTC): one canonical, conservative guard rule, no data-flow modelling

Each round adds cases because the guard tries to PROVE gating through data
flow. Stop. The guard accepts exactly one canonical shape and rejects
everything else. State the rule in the guard's doc comment:

| Accepted (the only forms) | Rejected (all others, intentionally) |
|---|---|
| The request expression lies lexically inside the consequent of `if (operationOpen('<op>', …)) { … }` or `operationOpen('<op>', …) ? <request> : …`, in the SAME function body (no crossing a function boundary), with the same operation literal. | A gate result held in a variable (`let allowed = …`) or conditionally assigned. |
| Inside a component, the request runs in an effect or handler whose function body starts with the same canonical `if (!operationOpen('<op>', …)) return;` (or the hook's equivalent boolean, used directly in that `if`). | A request as a JSX child of `<OperationGate>` (it evaluates first), a callback returned from a gated function, or an unresolved alias. |
| | Every reference to a closed client chain counts as a request site: aliases, `const { get } = …`, shorthand properties, returned clients. Each needs the canonical guard at its call. |

False positives are intended: production code that trips the guard is
rewritten into the canonical form. Hold each row with a fixture: the
reviewer's three examples rejected, the canonical forms accepted. Then
re-check that production code passes, and rewrite any site into the
canonical form.
