## Outcome

One of launch's completion criteria is a pair of journeys, one API and one
browser, for a revoked editor. None exists. A Work's owner can add a
co-maintainer (`/v1/works/{id}/maintainers`, `/v1/work-maintainer-changes`).
Prove what happens when the owner removes that co-maintainer while they're
editing:

- **API journey** `tests/qa/integration/revoked-maintainer.test.ts`:
  1. The owner creates a Work (a recipe is fine) and adds a co-maintainer.
  2. The co-maintainer saves one change (200).
  3. The owner removes them.
  4. Their next change answers a refusal (the existing problem shape, 403
     or the route's documented code), and the Work is unchanged by it.
  5. A read as the removed co-maintainer shows only what any reader sees.
  6. Re-adding them restores the right to edit.
- **Browser journey** `apps/web/tests/revoked-maintainer.e2e.ts`, two contexts
  at 390 px:
  1. The co-maintainer has the editor open, with unsaved text typed.
  2. The owner removes them in the other context.
  3. The co-maintainer's save is refused with a clear message that their
     editing access was removed, not a generic failure.
  4. Their typed text stays on screen (copyable), and the editor no longer
     offers save.
  5. Take a screenshot of that state.

Seed through the API (a `.prepare.ts` and seed file, like other journeys). If
the editor's refusal handling shows a generic error or drops the typed text,
fix it in the editor feature: recipe-editor or document-editor, whichever the
journey uses. If a server answer is wrong (a removed maintainer can still
write, or the refusal leaks more than a missing resource would), report it
under BLOCKERS with request, status and body. Don't work around it.
