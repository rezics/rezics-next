## Outcome

Trust-ops and the program decided (2026-10-10): the governance Realm settings
are the single source of a Realm's rules. There's one meaning and one writer,
`saveRealmSettings` through the Realm settings command.

Today:
- Space creation writes an empty managed rules document.
- `publishRealmProfile` (realm-profile/commands.ts) writes rules into the
  profile payload without touching governance.
- So profile-published rules never reach the header (`realmHeaderRules`) or
  the join page (`publishedRealmRules`).

Change:
1. `publishRealmProfile` stops accepting `rules`. Remove it from the profile
   contract. Refuse a request that still carries it with the existing typed
   invalid-request error; never drop it silently.
2. The header and join readers read only the governance snapshot. An empty
   managed document is a real "no rules". Don't read `rules` from profile
   payloads anywhere. Ignore the field on read for existing pre-launch data, with
   no migration. Remove it from generated types and OpenAPI via `task gen`.
3. The web's Realm profile editor, if it edits rules, moves that control to
   the settings screen, or links there.
4. g-1034-realm-ranking and any test or seed that publishes rules through the
   profile sets them through the settings command instead.
5. Add `services/main/tests/realm-rules-single-source.test.ts`:
   - a profile publish with `rules` is refused;
   - settings-written rules appear in the header and on the join page;
   - clearing them shows none.

No governance change is expected. If one is needed, report the hunk; trust-ops
reviews it before landing.
