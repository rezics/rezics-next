## Outcome

Trust-ops' G-1599 is on main (0495f0521). `POST /v1/work-maintainer-changes`
(`work-maintainer-change-v1`) accepts `action: 'remove'` with `target`:
- each Work has exactly one owner, shown as `owner` in
  `GET /v1/works/{id}/maintainers`;
- only the owner's controller may remove, and the owner can't be removed
  except by its own `transfer`;
- any maintainer may `add`, and the last maintainer can never be removed;
- writes use `expectedGeneration` CAS and an idempotent receipt (201, replay
  200); removing a non-maintainer is a 409 no-op.

The web has no maintainer management at all. Build it, and use it in the
revoked-editor journeys:
1. A compact "Maintainers" panel where a Work's editors manage it (find the
   Work's studio or settings surface the recipe editor and Work editing
   already use; mount it there, not on the public Work page):
   - list the maintainers with names and an "Owner" badge;
   - **Add** a maintainer (existing `add` action) for any maintainer;
   - **Remove** shown only to the owner, never on the owner's own row or the
     last maintainer, with a confirm step;
   - handle 409 and CAS conflicts with the existing conflict pattern;
   - strings in all eight locales, with non-English marked for native review.
2. Switch the revoked-editor journeys from the transfer workaround to real
   removal:
   - API: `tests/qa/integration/revoked-maintainer.test.ts` uses
     `action: 'remove'`, and adds a non-owner trying to remove (refused);
   - browser: `apps/web/tests/revoked-maintainer.e2e.ts`, where the owner
     removes the co-maintainer through the new panel in the other context.
3. Unit test the panel's visibility rules (owner sees Remove; others don't;
   none on owner or last row).

Screenshot the panel at 390 px; the manager reviews it before landing.

## Mechanisms

access-authority: consume — maintainer add, remove and transfer are Access decisions the panel only calls
