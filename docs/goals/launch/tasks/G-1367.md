## Outcome

Urgent. A Realm policy change no longer stalls Main's ordered relay stream.
Since trust-ops' G-1334 and G-1261, new Realm policy publications (and a
Realm's initial policy) use the canonical receipt head
`urn:rezics:receipt:<sha256>` (`space/policy.ts`, `policyHead()`). The
`RealmPolicyChangedEvent` handler (`space/outbox-event.ts:13`) still accepts
only the legacy `urn:rezics:realm-policy:<UUID>` form and refuses, which
blocks the stream (kernel found it in G-1341: two policy changes queued before
the relay; logs in `.temp/worktrees/g-1341/.temp/realm-phase-expanded-qa.json`).

Fix the handler's identity proof for both forms:
- accept the legacy form for existing deliveries (legacy replay unchanged)
  and the canonical receipt form for new ones;
- derive `systemProof.receiptId` correctly for each form (today
  `receipt.slice(-36)` assumes a UUID suffix);
- read visibility, review mode and policy generation from wherever each form
  actually records them. Check the real write path: for an initial policy the
  facts sit on the Realm node with `rv:realmPolicyHead` pointing at the
  creation receipt.

Keep every existing epoch, sequence, event-id and outcome check. Use the
existing committed Access intent and receipt; no guessed head, no fallback, no
swallowed event.

```sh
task goal -- test services/main/tests/realm-policy-event-identity.test.ts <existing space/outbox tests>
```

Counterexamples:
- a legacy-head event replays unchanged;
- a canonical-head event (initial and later publication) is delivered with
  the right fields;
- two policy changes queued before the relay both deliver in order;
- a mismatched epoch, sequence or receipt still throws.
