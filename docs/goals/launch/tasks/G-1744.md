## Outcome

Inventory item L10, slice 3. The specification is staged at
`.temp/ref/g-1740-spec.md` ("Contract" items 1, 4 and 5; "Ordered implementation
slices", row 3).

A Zone page's discussion is its attached Realm's one thread about the page's
resource. The canonical key is `(realm, about)`:
- two Zones attached to the same Realm and showing the same resource share it;
- a page edit keeps it.

Build the storage invariant only:
1. New `realm-reply/about-store.ts`, with `content-store.ts` and `schema.ts` and
   one Content SQL migration (any number above main's; goalctl renumbers):
   - canonical keys `(realm, about)`;
   - per-intent operation progress;
   - server-allocated identities, with the root or child selection recorded
     before the identity is inserted.
2. Two independent intent keys posting first at the same time select exactly
   one opener; the other becomes a child.
3. The same intent key with different input is a conflict.
4. Different Realm or resource keys are independent.
5. A pending reservation is visible to the second poster.
6. Lock waits are bounded.
7. A hidden opener keeps its key: no second opener appears.

Prove all of these in `services/main/tests/realm-about-thread-owner.test.ts` on
real SQL.

Do not add the posting command, the lookup route or any web change; those are
later slices. Use the existing realm-reply storage conventions. No discussion
tag and no Zone forum.

## Decisions since this brief (manager, 2026-10-11)

- Every Realm reply's identity step now makes one more indexed lookup with a
  row lock (`realm_about_post_operation` by reply id). A reserved canonical
  reply cannot take its identity outside its recorded root or child selection,
  even on replay.
- That is a bounded constant (+1 Content statement per reply, 781 to 782), not
  growth. The reply cost guard is updated openly in the same change, so this
  brief claims `realm-reply-write-cost.test.ts`.
