## Outcome

Launch's existing journeys pass with their original assertions intact. G-1264
restored them (a previous engine had loosened them). They now fail for reasons
the assertions don't own:
1. `g-530-m4.e2e.ts`, desktop and phone: `GET /auth/start?next=/en/w/<id>`
   lands on the signed-in canonical Work page, so the wait for `/sign-in` times
   out. Find out why: either the step's browser context is already signed in
   (fixture or seed state leaking into a signed-out step), or the sign-in
   contract changed. Fix the fixture, or follow the current contract while
   keeping the step's purpose (a signed-out reader is sent to sign in, then
   back).
2. `g-530-m4.e2e.ts`, Studio chapter: `toHaveValue('')` fails because the
   chapter editor is now contenteditable. Assert the same emptiness on the
   editor's text.
3. `g-853-records.ts`: its editor and reviewer need the executable-theme
   platform grant (use `platform-grant.ts`, as G-1264 did for the others).
4. `library-import.e2e.ts` needs `REZICS_LIBRARY_IMPORT_DEMO=1` and a seeded
   demo stack, so its closed-importer POST assertion is unverified. Make the
   journey seed what it needs through the API, or show that the QA stack
   provides it.

Assertion integrity is the point: never add reloads, retries, re-navigation
or looser expectations to make a step pass. If the product is wrong, name the
page, the request and the observed behavior under BLOCKERS.
