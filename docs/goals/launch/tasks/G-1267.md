## Outcome

`services/main/tests/g-630-zone-restore.test.ts` ("Validate complete Zone
navigation restore candidates", added in ae1f75e5b) hangs on `main`: 400 s with
no output under a plain unit run (`bun test ./services/main/tests/g-630-zone-restore.test.ts`).
The program's and kernel's merge gates hit it. Make it finish in a few
seconds as a unit test, or, if it genuinely needs a database, Fuseki or a
running stack, move it to the integration tier as
`tests/qa/integration/zone-restore-candidates.test.ts` (named by capability,
not task ID) and delete the unit file.

## Work order

1. Find what it waits on (an open handle, a pool or connection never closed,
   a real service it expects, a timer). Use `bun test --timeout` and logging,
   not guesses.
2. If it only leaks a handle, close it and keep it a unit test.
3. If it needs services, move it to the integration tier and register it the
   way neighbouring integration files are registered; run it with
   `task goal -- test tests/qa/integration/zone-restore-candidates.test.ts`.

Keep every assertion. Do not change Zone product code unless the hang is a
product defect (for example a restore path that never resolves); then fix it
minimally and say so under OWNER CHANGES.

## Checks

Report the cause, the fix, and the passing run (unit time or QA run ID).
