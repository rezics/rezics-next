## Outcome

A reader can record that they own a copy of an exact release (format,
acquired, owned since and until) and that a copy is lent to someone or
borrowed from someone or a library, with a due time. They can see what is due
and what is overdue, return it, and extend it; everything comes back in their
library export. The product promises this (`docs/product/capabilities.md:25`,
"ownership and loans"), launch's Completion requires expired loans, and today
nothing exists: no model, API or UI (launch audit,
`/home/edge/projects/rezics/rezics-next/.temp/goal-launch/launch-audit.md`,
section 1, B6).

## Decisions already made

Kernel and launch agreed on 2026-10-07 that copies and loans are **private
library records in the library owner's PostgreSQL** (Content migrations, beside
`370_reader_library.sql`), not a graph profile (record §2: private,
high-frequency personal state). Consequences:

- A copy references the exact release IRI from the graph; a loan references a
  copy, a direction (lent out or borrowed in), a counterparty (a person
  reference or a free-text name such as a library), a start and a due time
  (`endTime`), and its return.
- Private by default. A later public "owns this edition" is a
  disclosure-controlled read of the record, not a graph fact; do not build it
  now.
- The library export maps them to JSON-LD with schema.org terms:
  `OwnershipInfo` (`typeOfGood`, `acquiredFrom`, `ownedFrom`, `ownedThrough`)
  and `LendAction` or `BorrowAction` (`endTime`).
- Correct `docs/contracts/work-and-release.md` decision 6 in the same change:
  copies and loans keep their distinct identity, but as private library
  records, not versioned model profiles.

## Smallest change

Owner operations under the existing library owner: create, change and remove a
copy; open, extend and return a loan; one bounded, cursor-paged read of the
person's loans ordered by due time with an `overdue` state computed against
the database clock, and the copies of one Work for its page. Writes are
idempotent with CAS on the record revision, as library status writes are.
Every new route gets a rate-limit class (trust-ops' `rate-limit/routes.ts`: ask
the manager, do not edit it) and an `openApiOperations` declaration in its
route module with `exposure: 'public'` (since trust-ops' T5, an undeclared
operation is closed and a static check fails; the records stay private by
owner authority, not by a platform gate). Erasure: a person's copies and loans go with their library when
it is erased; say in the handoff where that hook is.

Do not build lending infrastructure, reminders by email, commerce, DRM, a
patron system, a graph profile, or a public ownership read. Do not edit
`library/status.ts`, `public.ts`, `shelf-page.ts` or `routes/library.ts`
(another live task holds them); register the new route module in
`services/main/src/app.ts` with one import and one `.use()` line.

## Checks

```sh
task goal -- test services/main/tests/library-copies-loans.test.ts
task goal -- test tests/qa/integration/library-copies-loans.test.ts
bun node_modules/typescript/bin/tsc --project services/main/tsconfig.json
```

Counterexamples: a loan due yesterday reads as overdue and returns cleanly; a
duplicate return with the same key is one return, a stale revision is refused;
two devices extending and returning at once end in one consistent state; a
borrower named in free text never resolves to a person; another person cannot
read or change the records; 500 loans page completely by due time; the export
round-trips copies and loans. Run `task gen` and `task web:typecheck` for the
new contract and restore generated paths. The UI is a separate task: list the
contract it needs in the handoff.
