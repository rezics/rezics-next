## Outcome

G-1425 restored a wiki chapter page's previous and next links. Since G-1414,
the reader's own progress read lists only their current chapter, so G-1425's
`readReadingOrder` (`apps/web/features/wiki/read.ts`) pages the reading order
from the start of the Work, at most 4 pages of 50. A chapter past that
position silently has no neighbours. `firstSeen` (`reveal.ts`) and
`revealedAt`'s chapter-before rely on the same list. A long serial (a
1000-episode anime, a web novel) is in launch scope, and each chapter page
makes up to 4 serial reads.

Main's reading-position read has what a bounded answer needs:
`ReadingPositionTraversal.location` (`traversal.ts`) and the order store's
keyset `range(…, reverse, probe)` in both directions, with the chooser's scan
window and disclosure. Give the reading-positions API a read of an
occurrence's previous and next chapters, in reading order, crossing volume
and group boundaries as the chooser does. Before adding one, check whether the
existing positions read can carry it as a parameter: keep one representation
of a position. Its rules:
- Cost doesn't depend on the Work's length or the chapter's place. Seeks per
  direction are bounded by the chooser's scan window. A neighbour beyond the
  window is reported as not found within the bound, never guessed.
- Same disclosure as the chooser: a neighbour the reader may not see is
  skipped, not revealed, and no ordinal is returned. Asking about an
  occurrence the reader can't see answers exactly as one that doesn't exist.
- The served cost metadata states the new read's bound.

The wiki uses it for the chapter page's neighbours and `revealedAt`'s chapter
before, and the 4-page scan goes.

A record's first appearance: if Main can answer "the first chapter where this
record is visible to this reader" with a bounded read from data it already
has, add it, and `firstSeen` uses it. If that needs a new index, don't add a
migration: keep `firstSeen` on G-1425's bounded list and propose the read, the
index it needs and its write cost under NEXT.

Tests in `services/main/tests/reading-position-neighbours.test.ts`, with data
written through the API:
- a Work with more than 250 chapters, the reader at chapter 240: both
  neighbours present;
- a hidden chapter between two visible ones is skipped;
- an invisible occurrence reads exactly like a missing one;
- the read's order-store calls for chapter 240 equal those for chapter 3.

Keep `apps/web/features/wiki/chapter-neighbours.test.ts` passing; change its
mocks only where the read it mocks changes.

## Do not

Don't edit the journeys or loosen a test. Don't change what the progress read
returns: the position control still gets the single resume item.
