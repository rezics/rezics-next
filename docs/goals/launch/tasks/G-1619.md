## Outcome

G-1597 made a Realm reply's cost flat with Realm size, which is the asymptotic
rule. But the absolute cost is high. One reply through its four product
commands (draft, identity, review, placement) costs about **783 Postgres
statements and 105 Fuseki requests**, 1.2–1.7 s on a QA stack, and the guard
`REALM_REPLY_WRITE_COST` allows 840 and 130. Content is 14/13/12/24
statements per command and account verification 54/54/18/72. The rest, about
520, are access and other reads. Writes go through the API, and a corpus of
10,000 replies takes hours at this rate, so this is a product defect.

1. Produce a per-command breakdown: which module issues each statement, and how
   many times the same read (admission, account assertion, membership, Realm
   basis, policy, thread root) repeats within one command and across the four.
   Put it under CASES.
2. Remove the repetition without changing any decision:
   - read once per command what is read several times;
   - pass the verified principal and admission through, instead of re-verifying
     the account per step, where the existing session object allows it;
   - batch the lookups that run one per row.
   Every authority, disclosure and fence check stays. If a repeat is a
   deliberate re-check (for example a closing fence), keep it and name it.
3. Lower `REALM_REPLY_WRITE_COST` to the new measured count, with an
   itemised comment. Keep the 100- versus 1,000-thread equality test.

Report the before-and-after counts and wall time.

## Mechanisms

access-authority: consume — admission and membership reads are shared within a command, never skipped
