## Outcome

G-1238 made Realm creation one operation: `POST /v1/spaces` with an
`Idempotency-Key` replays the same receipt, and
`tests/qa/integration/realm-create-intent.test.ts` proves a restricted Realm
is never visible while it's being set up. The browser keeps that key only in a
`useRef` (`apps/web/features/communities/create-form.tsx`). If the response is
lost and the founder reloads or reopens `/r/new` and submits again, a new key
can create a second Realm.

A founder ends with exactly one Realm and is led to it, whatever happens to
the response:
- A retry in the same page reuses the key, as now.
- After a reload, the founder sees the Realm their earlier submission
  created, from what the API already answers (for example the address
  conflict for their own Realm, or their own Realms list), and opens it
  instead of creating another. Use the API's answer, not a browser record of
  what was sent.
- If no existing read tells the founder that the Realm is theirs, stop and
  report the missing read under PROPOSED TASKS, with its method, path and
  privacy rule. Don't change the API: a Realm someone else owns or can't see
  must stay indistinguishable from a missing one.

Add the browser journey `apps/web/tests/realm-create.e2e.ts`, at 390 px and
1280 px, in English and one other locale:
- the founder creates a restricted Realm with its rules;
- an anonymous reader never sees it, during setup or after;
- the create response is lost (abort the route after the request reaches
  Main), the founder reloads `/r/new`, submits the same details and ends on
  the one Realm;
- the API afterwards lists exactly one Realm for the founder.

## Do not

No browser-side persistence orchestration, retry queue or compensation; the
API's receipt is the authority. No change to services/.
