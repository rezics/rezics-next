## Outcome

The tracking sheet (`apps/web/features/tracking/`) has one typed progress
control: the anime episode panel (`episode-progress.tsx`), proved by
`apps/web/tests/episode-progress.e2e.ts`. Its episode-1000 step runs against
a mocked Main. A manga reader or a player gets only the generic
attempt fields. Launch's scope includes a Bangumi-like catalogue (anime and
manga) and games.

Give the sheet a medium-appropriate action for each, on the existing
Composition occurrence progress API that the episode panel uses (the same
expected-version writes, conflict panel and resume read):
- **manga:** mark the chapter read, with the volume shown where the Work has
  volumes. A chapter inside a volume and an omnibus resolve to the right
  occurrence, as `long-series-progress` already proves on the API;
- **game:** mark it played and completed, and optionally a named part or
  route when the Work's structure has parts. Don't add hours or a game-only
  store;
- the right control comes from the Work's own kind and structure, read from
  the API. Don't keep a type table in the web.

Add `apps/web/tests/tracking-media.e2e.ts` against the real stack, with data
written through the API in `tracking-media-seed.ts`:
- a manga with volumes: phone marks volume 2 chapter 3; the desktop context
  resumes at the next chapter;
- both contexts write the same chapter at once: one wins, and the other shows
  the existing conflict panel without losing its intent;
- a game: mark it completed on one device; the other shows it completed;
- an episode past 1,000 on the real stack (not mocked): it resumes at the
  next one.

Run at 390 px and 1280 px. Strings come in all eight locales, with
non-English marked for native review. If an action needs an API the
progress routes don't have, report it under PROPOSED TASKS and don't change
services/.
