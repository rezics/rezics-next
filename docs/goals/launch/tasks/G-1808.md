## Step 2 (2026-10-11): the posting command

Kernel's draft bridge is on main (86a32bca5): `verifyMemberReplyDraftPrincipal`,
then `saveVerifiedMemberReplyDraft`, plus `resolveCanonicalReplyParent` in
`realm-reply/root.ts`. Trust-ops' Person-only author and root binding

`POST /v1/realms/{realm}/about-posts` (spec slice 4; trust-ops' requirements in
`.temp/ref/l10-trust-ops-operation-requirements.md`):
- A new `realm-reply/about-command.ts` composes the verified draft, the
  identity, placement and settle steps with G-1744's canonical storage.
  - The first post opens the thread; a later post becomes a child of the
    opener's retained root.
  - A pending opener answers 202 with only the durable operation identity.
- It validates the current Zone attachment and route basis server-side.
- The Idempotency-Key is required (400 without), scoped to (principal, key).
  The same key with different input is 409, and a replay returns the same status
  class and body.
- The rate-limit family is the existing Realm reply write family, per verified
  Person. The command debits what the separate draft, create and place calls
  would, never less.
- Authorship belongs to the verified Person only; no Org or PenName
  substitution.
- A hidden target, Realm or parent gets the same 404 as absent.
- Hidden opener: propose the outcome for a poster who cannot see an existing
  opener, and stop before implementing that branch. Trust-ops decides; it must
  not reveal "hidden thread" against "no thread".
- Tests in a new `tests/qa/integration/zone-realm-discussion.test.ts`:
  - the first post opens;
  - concurrent first posts by two Persons give one opener and one child;
  - both keep their Person and content;
  - replay;
  - attachment replaced or withdrawn;
  - a stale basis;
  - a policy refusal leaves no visible contribution.
- Declare its exposure and rate-limit family beside its neighbours, and
  regenerate the public API output.
