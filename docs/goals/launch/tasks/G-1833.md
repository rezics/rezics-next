## Outcome

Product defect, class A (launch's browser journey, 2026-10-11).
- After a moderator lifts a member's ban, the member's next reply never
  completes. Draft and reply identity succeed, then
  `GET /v1/member-replies/{reply}` answers 404 `reply_unavailable` before
  placement.
- The composer's pre-placement digest lookup
  (`apps/web/features/post-composer/api.ts:155`) reads the reply through the
  public member-reply endpoint, but `services/main/src/modules/realm-reply/store.ts:446`
  exposes a Realm reply only once a visible placement exists. A reply that is
  not yet placed is therefore unreadable to the composer that is placing it.
- Evidence: `.temp/ref/g1717-handoff.md` (QA 20261011t143950-5b2a45). The
  journey is staged as `.temp/ref/realm-moderation-journey.patch`.

1. Analysis first, into RESULT:
   - Does this break every reply, or only replies with no visible placement
     yet (after an unban, under review, a first reply)?
   - Which existing browser journeys post a reply, and why do they pass?
2. Fix it in the composer, keeping all authority:
   - get the digest the placement needs from what the composer already holds,
     the draft or identity response, or from an existing author-scoped read;
   - never ask the public endpoint to disclose an unplaced reply;
   - change no Main code. If Main has no author-scoped read for this, report the
     exact read needed under BLOCKERS.
3. Apply the staged journey to `apps/web/tests/realm-moderation.e2e.ts` and make
   it pass:
   - a moderator bans a member through Manage with a reason;
   - the member sees it and cannot post;
   - after the unban, the member posts successfully.

   Show a specific message to a banned member instead of a generic retry alert.
