## Outcome

At launch only first-party blocks run in Zones (standing direction 11; the
approved launch matrix keeps `third-party-blocks` closed). A Zone editor
without the `platform:use:third-party-blocks` grant cannot save a
configuration or a mount that names a non-first-party block, through any path,
including advanced configuration payloads. With the grant, it works as today.
A refusal is a 403 problem of type `platform_closed`.

Trust-ops' T5 (G-1235, which this task depends on) supplies the binding
function `requireSelectedPlatformCapability(..., { exposure: 'platform:third-party-blocks', ... })`
and the refusal contract, and names the two call sites in launch's area
(`/home/edge/projects/rezics/rezics-next/.temp/trust-ops/t5-call-sites.md`,
"Launch Zone"):

- `services/main/src/modules/zone/configuration.ts` `changeZoneConfiguration`,
  after checked block resolution;
- `services/main/src/routes/zones.ts`, mount target and block resolution.

## Smallest change

Call the gate once per request after the server has resolved which blocks the
configuration or mount uses (never from a client-declared flag), only when one
of them is not first-party. Reuse the existing first-party block catalogue to
decide; do not add a second list.

Do not build a block marketplace, a review queue, per-block grants or a web
change (the web hides closed surfaces through G-1236).

## Checks

```sh
task goal -- test services/main/tests/zone-third-party-gate.test.ts
bun node_modules/typescript/bin/tsc --project services/main/tsconfig.json
```

Counterexamples through the real routes: a first-party-only configuration
saves without the grant; one third-party block in a nested or advanced payload
is refused with `platform_closed` and changes nothing; a mount of a
third-party block is refused the same way; the same requests succeed with the
grant; a grant revoked between two saves refuses the second. No dev server or
browser.
