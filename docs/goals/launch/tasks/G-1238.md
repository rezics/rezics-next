## Outcome

A founder who creates a restricted Realm never exposes a public community, not
even for a moment, not after a failed step, a lost response or a closed tab.
Today the browser runs the setup (`apps/web/features/communities/create-form.tsx:80–100`):
it creates the Space and Realm with `disclosure: 'public'`
(`services/main/src/modules/space/create.ts:182`), then enrolls management
(`POST /v1/realms/{realm}/management`), then puts visibility, review mode,
who may submit, self-join and rules (`PUT /v1/realms/{realm}/settings`). A
failure after the first write leaves a public, open shell with no rules.

After this task the create operation carries the founder's intended
disclosure, admission (self-join, who may submit, review mode) and initial
rules, and commits them with the Space and Realm in the one receipted owner
command it already runs. Management enrollment of the founder happens in the
same operation or is made unnecessary by it. A replay with the same
idempotency key returns the same result. The form submits once, and after a
lost response it reads back by the same key instead of re-running steps.

Source: the launch product audit,
`/home/edge/projects/rezics/rezics-next/.temp/goal-launch/launch-audit.md`
section 5 (M1) and backlog item 1. The record's rule: APIs own business
operations; no browser-side persistence orchestration or compensation (launch
GOAL.md cut lines).

## Access contract (trust-ops G-1250)

Attempt 1 stopped correctly: founder grants, self-join, submission policy and
rules live in Access. Trust-ops' G-1250 provides, on `main` after it merges:

`AccessRealmManagement.initializeCreated(principal: VerifiedPrincipal, { realm, actingSubject /* founder */, creationKey, creationDigest, settings, rules? }, env: WorkActivationEnvironment) → { realm, accessRevision, replayed }`

- One Access transaction: founder enrollment and grants, the scope gate,
  settings (existing `saveRealmSettings`/`saveRealmAccessSettings`
  validation) and rules.
- Same key and digest replays with `replayed: true` and no writes; a founder
  grant revoked since then stays revoked; same key with another digest is a
  conflict.
- Call it server-side from `space/create.ts` after the graph Space exists. The
  graph Space is created with its intended disclosure, so a restricted Realm
  is never public even if this call fails; a failed call is resumed by
  replaying the creation key (the create operation's existing idempotency).
- The old `initialize` and settings routes keep working; the web stops calling
  them for creation in this task.

## Smallest change

Extend the existing create input with optional initial settings (validated by
the same rules `realm-admin/contract.ts` already applies to settings) and write
them into the Realm manifest in the existing `validatedCommand`. Defaults stay
as today for a public Realm, so existing callers keep working. Remove the
browser's management and settings calls from `create-form.tsx`.

Do not build a setup wizard service, a saga, a second Realm owner, a draft
Realm state or browser compensation. `space/create-authority.ts` belongs to
trust-ops' task G-1220 (controller continuity): do not edit it. If founder
enrollment needs a change in `services/main/src/modules/access/**`
(trust-ops' area), stop and hand off the exact request instead.
