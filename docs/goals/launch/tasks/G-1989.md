## Outcome

L29 audit pass 1, class A6 (program, 2026-10-12 05:42 UTC). Principle: the
furthest completed episode and every episode completed are different facts.
The full class is staged at `.temp/ref/product-audit-pass-1.md`, section 6.

Today `episodes.ts:112` treats a completed page endpoint as proof that every
earlier episode is completed. The binary search at `:120` assumes monotonic
completion, though the API keeps sparse marks (`routes/progress.ts:192`).
`episode-progress.tsx:133` turns that inferred prefix into a percentage, and
`:142` shows all watched. Derive the prefix from authoritative
completed-occurrence coverage (the existing paged composition progress API),
or prove each occurrence before the first gap. Keep the furthest-completed
resume separate. If a budget prevents a complete proof, show an unknown bound,
never a false one.

## Acceptance (as tests)

- `{1,12}`, `{1,6}`, and a formerly contiguous run with episode 2 unmarked,
  each report "through 1", with no false 100% and no "all watched".
- A case that crosses a page boundary.

## Land review 1 (2026-10-12 06:30 UTC): one class, so one rule replaces the client-side proof

Five P1s and a P2 share one cause: the web PROVES coverage itself, with
sequential reads that have no shared fence. That fails on budget exhaustion,
concurrent marks from another device, revision-specific completions, an
unmark before a refresh, and a resume beyond the page budget. Fix the class,
not the five sites.

| Rule | Detail |
|---|---|
| The web never infers coverage | No client-side prefix scan, binary search or cached completion set decides "watched through", a percentage, "all watched" or "all chapters read". |
| Only facts Main returns in ONE consistent read are shown | Main's progress summary (`GET /v1/me/progress-summaries/{resource}`; series summary `counts {completed, required, completedRequired}`, `next`, `partial`, `revisions`; `modules/session/series-contract.ts:13–20`) or the composition progress read, whichever carries the counts for episodes and chapters. "All watched" or "all read" only when `completedRequired == required` and not `partial` in that same read; the percentage comes from the same read. Main's completion semantics (a revision-specific completion counts) come with it. |
| Unknown stays unknown | If Main gives no count for this Work, show only "Last watched: X" and "Continue from Y" when Main's `next` resolves it. Show no percentage and no "through" claim. A failed resume read shows unavailable, never "No episode watched yet" or "Continue from episode 1". |
| A successful mark or unmark invalidates the summary at once | Until the refreshed summary arrives, show pending or unknown, never the disproved claim. |

Tests: the review's six scenarios, each failing on the current branch:
- 201 completed episodes with the resume read failing;
- unmarking 2 from a completed series;
- another device's unmark 1 and mark 2 during a read;
- the same for chapters across volumes;
- episode 2 completed only for a selected revision;
- 2,020 episodes with resume at 2019.

Remove the client-side proof code this replaces.
