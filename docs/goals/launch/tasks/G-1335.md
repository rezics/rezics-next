## Outcome

A library import request does bounded work before anyone is trusted: an
oversized body is refused before it is parsed, and the bearer, actor and
import reservation (budget) are checked before the file is parsed. Today
`POST` on the import route (`routes/library-imports.ts`, around lines 86–96)
declares `file: t.String({ maxLength: FILE_IMPORT_COST.bytes })`. Elysia
parses the whole JSON body first, then validates that bound, and
`parseLibraryFile` runs before authority and reservation work. Trust-ops'
M1 follow-up (security review) found this class; the media stream path is
already fixed and is the pattern to follow.

1. Refuse a body larger than `FILE_IMPORT_COST.bytes` plus a small envelope
   from `Content-Length`, and cap the streamed read when the length is absent
   or wrong. Do this before JSON parse, with `413` and the existing problem
   format.
2. Verify the bearer, `actingSubject` and the import reservation before
   `parseLibraryFile`.
3. Bound `parseLibraryFile` by rows and per-row size, so a small but
   pathological file cannot do unbounded work.

Not this: no new transport framework, no upload service, no change to import
semantics or formats.

## Checks

```sh
task goal -- test services/main/tests/library-import-intake-bounds.test.ts <existing library-import unit tests>
bun node_modules/typescript/bin/tsc --project services/main/tsconfig.json
```

Counterexamples:
- a body over the limit is refused with 413 and never reaches the JSON parser
  (prove with a spy or timing-independent counter);
- a bad bearer with a large valid body is refused before parsing;
- an exhausted reservation is refused before parsing;
- a file at the row limit parses, and one row over it is refused.
