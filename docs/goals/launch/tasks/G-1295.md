## Outcome

A moderation decision with many affected people is mailed page by page, and
ordinary notifications (follows, releases, replies) keep flowing meanwhile.

Trust-ops' G-1270 made `SafetyDecisionMail.enqueueDecision`
(`services/main/src/modules/governance/notices-mail.ts:75`) commit one
discovery or delivery page per call. It throws `SafetyNoticeContinuation`
("saved progress is retryable; the existing producer must retain its event
cursor") when more pages remain. Launch's
`runSafetyCorrespondenceOnce` (`notification-producers/producer.ts`, around
lines 347–375) lets that propagate like any failure, so one large decision
ends the tick as an error and is treated as an intake outage.

Change the producer so that:
1. A `SafetyNoticeContinuation` on an event counts as progress. Stop this
   tick's safety loop at that event, without advancing the
   `safety-correspondence-v1` cursor past it, and return normally. The next
   tick calls `enqueueDecision` for the same event and continues its pages.
2. Other errors still fail as today.
3. The safety correspondence run never blocks the ordinary producers in the
   same worker tick: a pending continuation, or a failure, on the safety cursor
   does not stop follows, releases or replies from running.

## Do not

Do not change `governance/**` (trust-ops'), page sizes, the cursor table or
intake identities, and do not catch errors broadly.

## Checks

```sh
REZICS_NESTED_POOL_CHECKOUT=throw task goal -- test services/main/tests/safety-notice-continuation.test.ts <existing producer unit tests>
bun node_modules/typescript/bin/tsc --project services/main/tsconfig.json
```

Counterexamples:
- a decision needing three pages completes over three ticks, with the cursor
  advancing past it only after the last;
- an ordinary follow notification enqueued during those ticks is delivered
  in the first tick;
- a real intake failure still fails the safety run, without stopping the
  ordinary producers.
