## Outcome

Class A (program, 2026-10-12 12:26 UTC), from audit pass 2. The class, with its
instances and traces, is in `.temp/ref/audit2-class1.md`. Content-report
Remove and rights restrictions return 202 with deferred effects; the backend
already resumes them on a replay with the same key
(`governance/store.ts:947`, `:653`, digest check at `:961`). The web treats
any non-error body as done and drops the pending entry. Role and rules saves
mint a new key on every attempt.

| Rule | Sites | Test that must fail without the fix |
|---|---|---|
| Before dispatch, the web retains the exact payload, key, actor and Realm, reusing the pattern in `manage/safety-pending.ts:17` and `:43` (no second backend operation owner). | `manage/commands.ts:185`, `:88`, `:202` | A lost response followed by a retry sends the SAME key and body; the backend completes the first operation and does not refuse it. |
| Three states: recorded, pending, completed, read from TYPED decision receipts (`operation.status`), never from "any non-error body". A 202 with deferred effects shows pending, never "removed". | `commands.ts:43`, `queue-view.tsx:72`, `queue-state.ts:140` | A 202 with deferred effects shows pending and keeps the item. After a reload it offers Resume with the same key, then shows completed. |
| A command is rebuilt from a fresh basis ONLY after an authoritative refusal establishes that the intent did not commit. | `queue-view.tsx:221`, `commands.ts:185` | A changed live basis between attempts still resumes the original payload. |
| Role assignment, role definitions and rules or settings saves reuse their key on a retry. | `admin-api.ts:105`, `:114`; `settings-view.tsx:180` | A lost response on role assignment and on rule publication recovers the original receipt. |

Cover content Remove, the rights interim and final restriction, role
assignment and rule publication. Use isolated fixtures, never the shared stack.
Add stories for the pending and resume states, and look at the screenshots.
