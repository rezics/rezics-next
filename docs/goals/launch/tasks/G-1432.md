## Outcome

Main can already publish a Zone site: a Realm-less Zone (G-1284), its home
page as a Content document, and `POST /v1/zones/{id}/site-publications`,
which binds exact Content revisions. `tests/qa/integration/zone-document-home.test.ts`
proves the flow: "Realm-less site binds exact revisions; drafts stay outside
and republishing moves public membership". The only browser editor is the
Showcase one (`apps/web/features/showcase-zone-editor`), so no author can do
this outside the API.

First slice: in the browser, an author who holds a Zone:
- opens the Zone's editor (under `manage/z/[space]`, beside `manage/r/[realm]`) and writes the home page with the existing document
  body editor (`apps/web/features/document-editor`);
- saves a draft and previews it as it will read, which only people who may
  edit can see;
- publishes it, after which anonymous readers see exactly that revision;
- edits again: readers keep the published revision until the author
  republishes.

A lost publish response is retried with the same key and ends published once.
A save against a stale head says so, and the author keeps their text. Every
write goes through the existing APIs, with command keys from
`apps/web/features/api/command.ts`. Strings come in all eight locales, with
non-English marked for native review. Navigation and theme editing are later
slices. Design the editor's layout and entry point to leave room for them,
and don't build them.

Find the operations in `services/main/src/routes/zones.ts` and the Content
routes the integration test uses. If one this slice needs is missing, report
it under PROPOSED TASKS; don't change the API.

Add the journey `apps/web/tests/zone-site-authoring.e2e.ts`, at 390 px and
1280 px. It walks the steps above, checks the anonymous view after each
publish, and includes a stale-head save from a second tab.

## Do not

No renderer specification stored in Content, no third-party blocks and no
change to services/. Don't modify the Showcase editor; reuse its parts only
where they already fit.
