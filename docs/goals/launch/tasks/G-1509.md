## Outcome

The Eden `treaty` clients (`apps/web/features/api/main.ts` for the server,
`browser.ts` for the browser) turn date-like strings in JSON responses into
`Date` objects. A Statement literal `1980-04-01` (xsd:date) reaches the page
as a `Date`. React can't render a Date, the value loses its datatype's
precision, and a string that merely looks like a date is changed. G-1459
worked around it in `entity-page/views.tsx` (`recordedLexical`). That fixes
one view only; every other reader of a literal still gets a Date.

One meaning, one representation: a literal's lexical form is the string the API
returned. Fix the class at the clients:
- turn off Eden's response date parsing in both clients, through Eden's option
  if it has one, or a fetcher or onResponse that parses JSON without revival;
- then remove the `recordedLexical` workaround from `views.tsx`, so it
  renders `value.lexical` as given.

Where code relies on getting a Date (timestamps such as `createdAt`), parse
them at the point of use. Find them through tsc errors once the generated types
say string, or by grep. Don't add a second revival layer. Report each changed
call site.

Add `literal-fidelity.test.ts`:
- a response with `"1980-04-01"`, `"2026-10-09T00:00:00Z"` and `"1980"`
  comes back from each client's response handling as identical strings.
