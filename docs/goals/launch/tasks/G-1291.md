## Outcome

A reader can reach every reply in a long Realm thread. Today a thread read
returns at most 191 replies below its focus, 32 levels deep and 32 ancestors
above (`REALM_THREAD_COST`, `realm-reply/thread-contract.ts:10–15`), and says
`complete: false` with no way to continue (launch product audit item 11). The
bound is right; the missing continuation turns it into a product limit.

Add continuations that keep the bounded work:
- **siblings:** a cursor for "more replies under this reply", seeking in the
  thread's existing reply order from the last returned sibling;
- **depth:** "continue this branch" from a reply at the depth limit, which
  reads that reply as the new focus;
- **ancestors:** the same, upwards.

Each continuation is a bounded read of the same shape, never a re-read of the
whole thread. The web thread view shows "more replies" and "continue this
thread" controls where the response says there is more.

## Do not

Do not raise the bounds, load the whole thread, add a second thread store or
change ordering. Every new or changed operation keeps its `exposure`
declaration and a `read` rate-limit family (launch has consent; send the
manager the method and path of any new public operation before merge).

Counterexamples:
- reply 192 under one focus is reachable through the sibling cursor;
- a branch 33 deep is reachable through "continue this branch";
- a reply posted mid-walk is neither duplicated nor skipped;
- a removed reply leaves no gap in the cursor;
- each page examines a bounded number of rows (assert rows examined, not wall
  time).

The contract changes: run `task gen` and `task web:typecheck`, then restore
generated paths.
