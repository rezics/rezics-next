## Outcome

Analysis only. Do not change code. Your RESULT is a specification of slices,
each fitting one implementation session.

Inventory item L10 (class A). From `docs/goals/launch/GOAL.md`:
- a Zone page's discussion is the attached Realm's thread `about=<resource>`,
  created on the first post;
- there is no discussion tag and no forum inside a Zone;
- the author stays the Person.

What exists:
- an editor attaches a Realm they steward to a Zone, sees it on the steward
  list, and a withdrawal removes it (`apps/web/tests/zone-realm-attachment.e2e.ts`,
  Main's attachment routes and Zone configuration);
- a Realm thread card already names the Work it is about
  (`services/main/src/modules/realm-reply/thread-contract.ts`).

What is missing:
- looking up a Realm's thread about a resource;
- the discussion entry on a Zone page;
- the first post creating exactly one thread when two people post at once;
- returning from the Realm to the page.

Specify:
1. The contract:
   - how a page finds its attached Realm's thread `about=<resource>` (a bounded
     read; hidden equals absent);
   - how the first post creates it exactly once (the owner command, its
     idempotency and race handling);
   - who may post, under the Realm's admission.
2. The slices in order, each with files, the change and the tests that prove it.
   Use existing owners (realm-reply commands, Zone configuration, cross-Space
   authority C1). No Zone forum, no discussion tag, no browser-side compensation.
3. Which slices are launch's and which need another Goal (kernel or
   trust-ops), with the exact ask.
4. The paired API and browser proof for the coverage registry row "zone /
   Attached Realm discussion".
