## Outcome

`growRealmThreads` in `services/main/tests/g-1034-fixture.ts` fakes a large
reply population:
- it writes content receipts, the outbox and `owner_control` with SQL;
- it writes the Realm reply slots and placements into the graph with raw
  SPARQL (`env.fuseki.update`, ~line 159).

Current stacks build Main through the product assembler, which doesn't serve
`/rezics/update` ("No Fuseki dispatch /rezics/update", 404). So
`tests/qa/integration/g-1034-realm-ranking.test.ts` can't reach its ranking
assertions. It also hides a design rule: writes go through the API, fixtures
included.

Seed the replies the way readers make them:
1. Post replies through the API (the Realm reply command, with parent replies
   where the chain needs them) and let the projector write the rows, as
   G-1563 aligned the parent chain.
2. If the volume the capped-chain assertions need doesn't fit the preparation
   budget through the API, build the dataset once through the API, keep a
   consistent QA backup, and restore an isolated copy for each run, as the
   harness already does for other large datasets. Routine preparation must
   stay under 10 minutes; see
   `docs/storage/workload-budgets.md#data-preparation-and-import`.
3. If one reply write is slow enough that this is impractical, report the
   per-write time and the count needed under BLOCKERS. A slow write path is a
   product defect to fix, not a reason for a back door.

Delete the raw SQL and SPARQL writes. Keep every assertion's meaning, and
lower the scale only if the brief of the original test allows it; say so if
you do. Other users of the fixture must keep passing:
tests/qa/integration/g-1042-ranking-followups.test.ts services/main/tests/g-1034-profile-child.ts 

Also, from G-1597 (2026-10-11): on the restored corpus, assert that one Realm
reply costs the same Postgres statements **and Fuseki requests** at the 100- and
1,000-thread scales, now with the graph populated. G-1597's own test grows only
Postgres owner rows.

## Decisions since this brief (program, 2026-10-11)

- Attempt 5 stopped under the three-attempt rule. One reply costs about 4.88 s through the product, so a 10,000-thread corpus would take about 13.6 h to build.
- Later the same day the program changed this. The G-1619 analysis found the local saving is only about 13% (732 to 640 SQL; most is Access and Account re-verification, which goes to a cross-Goal analysis). At 100/400/1,600 threads, the one-time build of about 1,600 replies takes 0.5–2.2 h, which is practical. So this task resumes now, fresh, with its attempt count reset, and does not wait for G-1619.
- Do not build 10,000 threads. Change G1034's cuts to three geometric scales, **100, 400 and 1,600 threads** (`REALM_RANKING_SCALES`, with the manifest version bumped). Assert with `assertWorkCostAtScales` (`tests/qa/support/work-profile.ts`), declaring a growth class per counter:
  - the ranking read: `constant` or `logarithmic` in threads;
  - the reply write: `constant`.

  Keep today's absolute caps. The check fails when a counter grows faster between scales than declared (20% margin).
- Why this is not a weaker assertion: it states the growth class at three scales, which catches a wrong complexity estimate. That is a stricter statement about growth than one large cut. The original "work at 100/1000/10000" becomes "the declared growth class holds across 100/400/1,600, under the same caps". The step 4 cost test (reply Postgres and Fuseki at two cuts) folds into the same three-scale check.
