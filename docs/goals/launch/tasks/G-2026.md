## Outcome

Class A (program, 2026-10-12 10:24 UTC), the first defect the seeded growth
check found that nothing else had. The evidence is staged at
`.temp/ref/g1909-census.md`, with the full stage trace.

`GET /v1/zones/{id}` (`routes/zones.ts` `zonePage`, about line 304) calls
`readVisibleCompositionPage` with a per-item `canReadTarget` callback. Each
mounted navigation entry is admitted separately: 17 SQL, 3 Fuseki and about
6 KB per entry, even when every entry points to the SAME Collection. At 64
mounts that is 578 SQL and 102 Fuseki in about 4.4 s, and the route deadline
aborts it (503, DOMException 23).

Rule: a page's mounted targets are admitted in ONE batched read over the
DISTINCT targets:
- `readVisibleCompositionPage` (`collection/visible-page.ts`, kernel's area,
  claimed with the area allowance; kernel is told) collects the page's
  candidate targets (page plus lookahead), deduplicates them, and admits them
  in one batched call: a `canReadTargets(targets[])` batch form, with the
  per-item callback kept as the fallback for other callers.
- `zonePage` passes the batch form, built on `canReadStructureTarget`'s batch
  path or a single Access statement set for the distinct targets.
- Any other caller keeps working unchanged.

The growth test `services/main/tests/zone-page-admission-growth.test.ts`
asserts a constant SQL and Fuseki count at 4, 16 and 64 mount entries over one
Collection, and over 64 distinct Collections a count bounded by the batch (not
per entry). It fails on today's code.

`routes/zones.ts` is also changed by unlanded G-1923: edit only the
`canReadTarget` argument there (whichever lands second rebases), and land
with the scope allowance.
