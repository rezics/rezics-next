## Outcome

Any client, the web or an agent, can tell which of two rating states is newer
without guessing from request timing. The web reader store (merged in G-1225,
b65cf6ea8) applies a response for a field only when it is newer than what it
holds. For shelf status it has a version, but Main gives a rating only an
unordered revision head (`services/main/src/routes/ratings.ts:166–182`), so
the store guesses order from when requests started. Its final review found
three remaining races that come from that guess:

1. A delayed successful rating write (rating 3) returns after another device
   set 5 and a refresh showed 5, and restores 3 (`reader-store.ts:328`).
2. Two overlapping reads: R1 starts, R2 starts and sees 2, R1 returns 5,
   R2 returns 2 later and replaces 5 (`reader-store.ts:213–217`).
3. A read started before a reconnect delivers a 403 afterwards and withdraws
   the new connection's controls (`reader-store.ts:251–254`); reads do not
   capture their lifetime.

Review text: `/home/edge/projects/rezics/rezics-next/.temp/goal-launch/review-g1225c.out`
(last section).

## Smallest change

Every rating read and write response carries an ordered value for the
person's standing rating on that subject: the owner already orders a person's
revisions, so expose that order (a per-subject sequence or the committed
revision position), not a new clock. The 409 `stale_head` problem carries it
too. Then the store compares that value instead of request start times, and
every read captures its store lifetime like writes do (item 3).

Do not add a version column the owner can derive already, a client clock, or
a new rating store; do not change rating semantics or CAS. `library/ratings.ts`
and `routes/ratings.ts` are launch's to change; anything in another Goal's area
goes to the manager as a request.
