The decided behaviour (launch and program, decision 7), staged at
`.temp/ref/recipe-publish-decision.md`:
- **API:** two explicit steps, publishing the Structure and publishing the
  notes, each with its own exact revision and idempotency. There is no
  transaction across them.
- **GUI:** one Publish button. It runs the Structure step, then the notes step
  only when there are notes. Results read part by part:
  - "Recipe published";
  - "Notes published";
  - pending, with the durable operation shown and resumed;
  - refused, with the reason and a retry for that part only.
  The editor never says "published" for a part that is refused or pending. A
  recipe without notes publishes in one step and shows no notes line. Withdraw
  is per part. "Changes not published" appears when the draft is newer than
  the published revision.

## Land review 1 (2026-10-12 04:26 UTC): two P2s

1. **`publication.ts:44–47`, a source refusal is not revoked access.** Work
   source refusals, such as rights unavailable, reach the editor as 404
   through `checkedWorkStructurePublicationReceipt` and `commandError`. The
   editor treats every 404 as revoked access and closes all writes. Classify
   by the problem's type or code:
   - a source refusal is a per-part publication refusal, with its reason and a
     retry when one applies;
   - only a real loss of Work authority closes writes.
   Test both.
2. **`saves.ts:308–312`, a confirmed supersession must release the attempt.**
   If another tab publishes or selects newer notes before confirmation,
   `readPublication` returns a mismatch after `attempt.selected` was persisted
   as true. The retained attempt then skips publication and selection for
   ever, and Publish stays disabled, even after a reload. On a confirmed
   supersession, release or rebuild the completed attempt so the notes can be
   republished. Test it with two tabs: a reload, then republish.

## Land review 2 (2026-10-12 04:49 UTC): classify by problem code, never by HTTP status

This is the second blocking review; a third ends the fix rounds. Both findings
come from mapping HTTP statuses to editor outcomes:
1. **`publication.ts:76–77` clears the retained request on every 409.** Main
   also returns `409 admission_busy`, which requires the same request to be
   retried (`services/main/src/routes/problems.ts:408–409`). After a pending
   or lost response, clearing it discards the operation's recovery identity.
   The notes publication and selection paths do the same.
2. **`publication.ts:46–48` sets revoked on every 403.** Main's governance
   publication fence also answers `403 authority_denied`
   (`denyWorkStructurePublicationAdmission`) while `work.edit` remains valid,
   so a publication restriction must not close the cook's draft editing.

Fix the class, not the two lines:
- Map each editor outcome from the problem's `type`/`code`, as main's
  `problems.ts` defines them, for every path in `publication.ts` and
  `saves.ts`.
- Retry-with-the-same-request codes (`admission_busy` and the like) keep the
  retained command, key and pending operation.
- Publication refusals (governance fence, rights, source) are per-part
  refusals; editing stays open.
- Only a code that means the Work's edit authority is gone closes writes. Any
  unknown code is a retryable failure that keeps the request, never
  revocation.
- Add a table-driven unit test covering every code main can return on these
  routes, with its expected outcome.
