## Outcome

Read-only, class A (program, 2026-10-12 04:40 UTC). In launch's Zone discussion
browser journey, a Zone resource page request intermittently exhausts the
160-call per-request Fuseki budget. Main logs the chain
`[DisclosureUnavailable, FusekiReadBudgetExceeded]` (run `20261012t041847-1f31b8`,
staged at `.temp/ref/qa/`, `e2e-main.log`, trace `599aee76d2c351ea20b560071cb8620c`),
and the discussion shows as unavailable. An earlier run of the same journey
passed. A duplicate projection read was already removed (`aca423a0d`); a normal
about-thread lookup costs about 10 calls.

Using the request profile (the native visit counters are in it since kernel's
G-1655), answer with numbers:
1. **Which reads one Zone resource page request makes,** and the Fuseki calls
   each spends: the page or Work read, disclosure, the about-thread lookup, the
   Realm view, and anything else. Name the files and lines.
2. **Do the calls grow** with the Realm's size, with the page's content, or only
   with retries under concurrent writes (a moved snapshot being re-read)? If
   the count depends on load, say whether retries are counted against the
   budget, and where (`fuseki.ts:127` budget, `read-session.ts`).
3. **If they grow with size:** end with a failing growth check at three sizes,
   through the existing verdict (`assertWorkCostAtScales`, the work-profile
   corpus axes), and name the owner of the read that grows and the fix.
4. **If it is retries:** name the exact retry loop and the fix: do not count a
   retry's reads against the request budget, or bound the retries, or read a
   consistent cut once.

Change no code, except an optional new test file that demonstrates the growth
(not product code).

## Two questions the profile must answer (program, 2026-10-12 05:06 UTC)

1. **What moves the fence.** For every retry, record which write caused
   `WorkReadMoved` or `SearchSnapshotMoved`:
   - a write to the Work being read, or to something the page shows (its
     neighbourhood);
   - an unrelated write elsewhere in the dataset.

   Include an unrelated-write arm in the concurrent run: writes to other Works
   and other Realms only. If unrelated writes cause retries, it is the
   gated-reads class (class A, kernel's one-consistent-cut). If only
   neighbourhood writes do, kernel's bounded replay is the first-scope fix.
2. **Is one asset's attachment count bounded in first scope?** From source:
   do same-bytes imports share one asset, for example a source's placeholder
   cover on thousands of Works (content-addressed media)? If assets are shared
   and the count is unbounded, add the failing three-size check over the
   attachment count (class A; trust-ops Media fixes it by reading the page's
   own attachment, not the asset's inventory). If it's one attachment per asset
   in practice, say so with file and line (class B).
