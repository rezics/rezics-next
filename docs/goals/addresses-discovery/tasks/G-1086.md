## Outcome

`tests/qa/integration/g-630-zone-routes.test.ts:212–216` sends two identical
`POST {root}/mounts` commands with the same `expectedHead` at once and asserts
the statuses are exactly `[200, 409]`. On a loaded host it now fails alone with
`[200, 202]`. Read-only evidence:
`/home/edge/projects/rezics/rezics-next/.temp/verify/.artifacts/qa/20261004t202915-172ccf/logs/integration-r1.log`.

The manager bisected the failure. It does not follow a code change: the last
candidate commits are documentation only, and the same commit both passed and
failed. A `202` is the route's documented `pendingOperation` answer
(`services/main/src/api-contract.ts:81`): `status: 'reconciling'`, retry
allowed after `retry.afterMs`, given while the winning command's admission is
still in flight.

Make the test assert the contract, not a timing. Exactly one racer succeeds
(200). The other answers 409, or 202 reconciling. A 202 is retried as the
contract says (same request and idempotency key, after `afterMs`) and settles
to the 409 conflict with the current head, never a second success or a
changed head. Keep every other assertion in the file. If the retried 202 does
not settle to 409, or the route returns any other status, stop and report:
that is a product defect, not a test fix.

Do not change product code. Do not add new `G-NNN` mentions or `g-NNN` files.

## Checks

Run the file alone five times and after ten other integration files through
`bun scripts/goal/goalctl.ts test --heavy …`. The host is memory-constrained:
run one at a time. Scan the changed file with `task ast-grep -- scan`.
