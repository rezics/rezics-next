## Outcome

`tests/qa/fault-recovery/g-727-recovery-set.test.ts` and
`g-727-launch-drill.test.ts` fail alone on main. Manager's run, read-only:
`/home/edge/projects/rezics/rezics-next/.temp/verify/.artifacts/qa/20261004t161457-13156b`,
logs `fault-recovery-f2.log` and `f3.log`:

> Recovery phase coverage failed: Account table set differs from pinned
> recovery profile: missing []; unexpected ["rezics_local_migration"]; serving
> remains held

`services/account/src/recovery-coverage.ts` compares every `public` base
table of the Account database with a pinned list. The release migration
runner (`scripts/ops/migrate.ts`, `task ops:migrate`) records applied owner
migrations in `public.rezics_local_migration` in each owner database. Since
`04e3232e3` (shared owner migrations between development and release), the QA
fixture's Account database has that ledger as production does. So a production
Account recovery drill would also fail here; QA now shows it. Main and Content
keep their tables in their own schemas, so only Account's `public`-wide check
collides.

Make Account recovery treat the migration ledger as what it is. A restored
Account database must still know which migrations ran, so check whether the
ledger belongs in the recovery set (covered, digested and restored) or must be
excluded from the table check, decide with evidence from the recovery
procedure and `migrate.ts`, and state the rule where the profile is defined.
Keep the check strict for every other table: an unknown table still holds
serving. Do not change `migrate.ts` or other owners.

Prove it: the two `g-727` fault files pass alone, and a unit or integration
test shows an Account database migrated by the release runner passes coverage
while an unrelated extra table still fails it. Run `--heavy`. Do not add new
`G-NNN` mentions or `g-NNN` files.
