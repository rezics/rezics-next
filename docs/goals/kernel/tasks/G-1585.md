## Outcome

Launch (journey `apps/web/tests/recipe-authoring.e2e.ts`, QA `20261010t010732-df3aaf`, branch goal/g-1471): on a just-published recipe Work, `GET /v1/resources/{work}/page` answers 200 and advertises a statements section at `/v1/resources/{work}/statements`; that read answers 503 `work_read_unavailable`, so the page's "Explore the wiki" section shows "could not be loaded". `readSubjectStatements` (`statement/subject-read.ts`) with the seek in `statement/seek.ts` throws `WorkReadUnavailable` for a healthy, just-published Work. Main now logs the cause: `workReadError` logs `main.route.work_read_unavailable` with `error.code`, a 32-character token of the fixed reason message (e.g. `statement_seek_coverage_is_unav`, `publication_local_coverage_moved`). A page that advertises a section whose read then 503s is one meaning with two answers.

1. REPRODUCE API-only: `tests/qa/integration/statements-after-publish.test.ts`. Publish a Work the way the journey does (create a Recipe Work and publish it; copy the setup from `tests/qa/integration/recipe-work-page.test.ts` / `recipe-change-sequence.test.ts`), then immediately `GET /v1/resources/{work}/statements` (read the exact routes and query the web app sends: `grep -rn "statements" apps/web/features/work-page apps/web/features/entity-page | head`). It must fail red on current main with 503; report the run id and the logged `error.code`.
2. FIND THE CAUSE with that code and the throw site. Likely families: the statement seek coverage for a subject not yet covered (`Statement seek coverage is unavailable`, seek.ts:253; coverage is advanced by a projector tick, so a Work published a moment ago has none yet), or a publication-source basis check that treats "not yet projected" as "unavailable". For a Work that has no statements the right answer is an empty COMPLETE list; for a Work whose seek coverage has not caught up, the read must answer from what the graph holds for that subject (a bounded neighbourhood read, the way G-1554/G-1535 did for other reads) or say explicitly `stale: true`/pending in the page the way the other seek-backed reads do, not 503. A real fault (store unreachable, basis genuinely inconsistent) stays 503 and logged.
3. FIX at the cause in the statement read path. Do not make unavailable-for-everything into an empty list: keep every genuine unavailable (corrupt coverage, moved basis that a retry cannot settle) a 503. Tests: the new file passes; add the cases the cause implies to `services/main/tests` (owner tier) for the read function with a fake coverage state: no coverage + no statements -> empty complete; no coverage + statements in graph -> statements (or explicit pending) per your chosen contract; corrupt coverage -> unavailable.
4. Neighbours (report run ids): `grep -rl "subject-read\|readSubjectStatements\|statements" tests/qa/integration services/main/tests | head -30`, run the ones touching the subject statement read; plus `recipe-work-page.test.ts`, `year-fact-public-statement.test.ts` if present on main.
Commit after each step. `task gen` if OpenAPI changes (state the contract change in RESULT if any field is added).
