## Outcome

Launch's request (Discover renders): `GET /v1/discovery/concepts` answers 200 with an EMPTY, complete page while no discovery generation has ever been produced; a store or dependency that fails while a generation should be readable stays 503 so real outages still show. Today `DiscoveryStore.active` (`services/main/src/modules/discovery/store.ts:830-844`) throws `RecommendationUnavailable('Discovery has no active generation')` when `access.derived_generation_head` has no row, and the concepts route answers it through `workReadError` as 503 `main.route.dependency_unavailable`. On a fresh stack (the e2e QA stack among them) every Discover render logs one such fault.

1. Make "no active generation yet" a distinct, typed state: a subclass `DiscoveryNotProduced extends RecommendationUnavailable` thrown ONLY where the head row is absent (so every existing `instanceof RecommendationUnavailable` handler keeps working unchanged). All other throw sites in `active` (recovery fence held, generation row missing or corrupt, Access owner unavailable) keep their current class and answers. State in the class comment that the state is "never produced", not "failed".
2. The concepts read (`readConceptSearch` and what it calls) treats `DiscoveryNotProduced` as an empty complete page of the response profile `concept-search-v1` (items `[]`, no next cursor, `stale` false, a source position the page schema accepts; read how a legitimately empty search returns today and reuse that exact shape, do not invent a field). Followed topics that need no generation (existing follows remain navigation, line ~119) still appear if the code path produces them without the generation; if the page cannot be built without one, the empty page has no items and that is fine.
3. Every other discovery route keeps its answer. `/v1/discovery/sections` and the Work-card also-enjoyed paths already treat the unavailable class as absent or 503 on purpose; do not change them. If another route reads concepts through the same store call on a render path Launch's Discover page uses (check `apps/web` Discover loader calls: `grep -rn "discovery/" apps/web/features/discover apps/web/app | head`), list it in RESULT but change only what concepts needs.
4. Tests: owner/unit `services/main/tests/discovery-concepts-empty.test.ts` with a real or fake store: no head row -> `DiscoveryNotProduced`, an existing head with a missing generation row stays a plain `RecommendationUnavailable`/503 path, a held recovery fence stays 503. Integration `tests/qa/integration/discovery-concepts-empty.test.ts` (fresh stack, no generation): `GET /v1/discovery/concepts` 200 with `items: []`; and the logged-fault check is not needed. Run the existing discovery concept files (`grep -rl "discovery/concepts" tests/qa/integration services/main/tests`) and report run ids. Do not change the 503 for the outage cases.

Commit after each step; `task gen` if the OpenAPI changes (it should not).
