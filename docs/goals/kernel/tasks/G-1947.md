## Outcome

Relay migration 024 (on main, with `outbox/repair-graph-cut.ts` and the `--repair-graph-cut` entry in `services/main/src/relay.ts`) added `relay.delivered_batch.graph_sequence` and made `feed/source.ts` `graphPositionAtRelay` read it, refusing a NULL cut explicitly. It backfilled only headers whose retained envelopes are COMPLETE and carry `data.relayPosition`. MEASURED on the shared development dataset after the refresh (read-only, data epoch `8c483e38-59e7-4d95-b27b-de9cd6742a3e`): 11,085 retained batches, 10,589 with NULL cut, of which 8,900 are EVENT-BEARING legacy batches (their envelopes predate `relayPosition`, so the migration's predicate `data.relayPosition.sequence = batch.sequence` is false) and 1,689 are ZERO-EVENT headers (no envelope can prove them). The feed's own checkpoint (`access.feed_checkpoint.sequence` = 10823) sits on a legacy zero-event batch, so `main.feed.refresh` refuses "Main feed graph reference cut is unavailable" about once a second and the feed never advances. Fix the class for ALL legacy headers, one representation, no compatibility layer:

1. A new additive migration `025_legacy_batch_graph_sequence.sql`: backfill `graph_sequence` for event-bearing headers that migration 024 left NULL because their envelopes LACK `data.relayPosition`. Read how `outbox/relay.ts` `deliver()` and `retainedEnvelopePosition` treat an envelope without `relayPosition` (the legacy rule: the delivered row's own `(stream_scope, data_epoch, sequence)` IS its position) and apply exactly that rule: a header is proven only when ALL its retained members are present (`count = event_count`), their ordinals are complete and distinct, they agree on ONE `data.sourcePosition.sequence` matching `^[1-9][0-9]{0,99}$` with `datasetId = 'product'` and `dataEpoch = batch.data_epoch`, and the members that DO carry `relayPosition` match the header. Anything else stays NULL (never guess). The 024 file is already applied: do not edit it.
2. A BULK form of the existing source-verified repair for the headers no envelope can prove (zero-event, damaged, or unmatched): `task main:relay -- --repair-graph-cuts --data-epoch <epoch> [--after <sequence>] [--limit <n, default 200, max 1000>]`, in the same entry file: it pages NULL headers in ascending sequence after the cursor, repairs each through the SAME `repairRetainedBatchGraphCut` (unchanged semantics: exact source reader, header identity equality, atomic fill under the row lock), never aborts a page on one refusal (records the sequence and the reason), and prints one JSON object `{ repaired, refused: [{ sequence, reason }], next }` where `next` is the cursor for the following page or null when none remain. A header whose source evidence is genuinely unavailable stays NULL and is listed, not skipped silently. Bounded per call (statement, read and time budgets stated in the code), resumable, safe to run twice.
3. The explicit refusal in `graphPositionAtRelay` already names the repair: make its text name the bulk command and the cursor-free single form, one sentence. Do not widen what the reader accepts.
4. Prove (Main tests on the real Postgres relay schema, plus the Fuseki-free stub the existing repair test uses for the source reader): a legacy event-bearing header without `relayPosition` is backfilled by 025 and a partially retained one is not; a header whose members disagree is not; the bulk command repairs a set of zero-event headers across two pages, lists a header with absent source evidence, and a second run repairs nothing; after the migration and the bulk repair on a synthetic mix no header is NULL except the listed ones; `graphPositionAtRelay` on each resolves.
5. Docs: one paragraph in `docs/operations/search-index.md` (or the nearest operating document for the relay) stating when to run the bulk repair (after the 024/025 migrations on a retained dataset, until `next` is null; the check query is `SELECT count(*) FROM relay.delivered_batch WHERE graph_sequence IS NULL`), and one sentence in `docs/contracts/events-and-jobs.md` that every retained header carries its graph cut.
