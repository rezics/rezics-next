Cause (verify first, say if wrong): `startTelemetry` (packages/observability/src/runtime.ts ~473-481) builds the peer map and the trace-propagation origin set ONCE from the process env at start (FUSEKI_URL, ACCOUNT_*, MAIN_ORIGIN). A restored copy (`openCopy` in tests/qa/integration/work-profile-seed-checkpoints.test.ts, `startMediaStack` in tests/qa/integration/media-support.ts) starts a stack on NEW ports, so its Fuseki/Account/Main origins are not in the map: `instrumentFetch` classifies those fetches `rezics.peer.service = 'other'` and does not add the trace headers (`origins.has(url.origin)`), so Fuseki's own spans and engine bytes never join the request's trace.

Fix by rule, one place: the telemetry owner exposes `registerTelemetryPeers(env)` (and its undo, returned function) that ADDS the origins of a started stack to the live peer map and the propagation set, idempotently, and the harness calls it where it starts any stack whose origins differ from the process env's (startMediaStack, and every harness that builds a stack's `apps` env: grep `ownerUrls` / `FUSEKI_URL` assignments in tests/qa/integration/media-support.ts and tests/qa/support). The growth files need no call of their own. A fetch to an unregistered origin keeps classifying as `other` (never guessed).
Tests: unit (packages/observability/tests): registered origin classified fuseki/account/main and receives propagation headers; unregistered stays other; the undo removes it; double registration idempotent.
