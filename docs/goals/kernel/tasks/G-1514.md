## Outcome

G-1512's profile found that `tests/qa/integration/g-1051-query-scale.test.ts` dies in 88 s during query population with `invalid source author batch`: `fenceAuthorNames(session)` in `services/main/src/modules/source/author-name-read.ts` (called from `services/main/src/modules/work/read-session.ts` around line 385 for every read) calls `authorReferences` with EVERY recorded Work, but `SOURCE_ADOPTION_READ_COST.authorWorks` is 64 (`services/main/src/modules/source/native-work-adoption.ts`, the check near line 206 throws when more are passed). With more than 64 recorded Works in a session the fence fails every read. Fix it so the fence batches its work list in chunks of at most `authorWorks` and merges the results, or (if the fence only needs "has any author name changed since the basis") restructures to one bounded probe; choose with evidence. Keep the cap, keep the fence's semantics (a read that depends on an author name sees a consistent basis and refuses when it moved), keep the per-read cost bound: state the maximum number of extra Fuseki calls a read can add (it must stay bounded: if the number of recorded Works is itself unbounded, bound the fence by the page, not the corpus; show the numbers). Do NOT raise `authorWorks`.

Tests: unit test with 65, 128 and 1,000 recorded Works proving no throw, chunk sizes <= 64, merged result equals the single-call result for a small set, and the call count bound; then run `USER=edge LANG=C.UTF-8 LC_ALL=C.UTF-8 task goal -- test tests/qa/integration/g-1051-query-scale.test.ts` once and report what remains (the 10,000-Work import may still hit the shared 430 s deadline: that is the throughput task; say whether the population now passes).
