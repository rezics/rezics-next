## Outcome

Addendum to `docs/goals/kernel/reports/G-1641-specification.md` (read its 'Deferred-forever class' section and items 7 to 12, 15, 16 first). Program's question, and Trust-ops' alternative: why not the smaller rule, CLOSED BY DEFAULT WITHOUT A RECORD? An event whose publication has no Public eligibility decision does not hold the Content projection cursor (it is evaluated and simply not projected; the completed position follows the owner position); a later Public approval is itself an event that (re)delivers that publication into projection. That would need no default decision per publication, no reconciliation of legacy publications, no new API field, no Content migration and perhaps no native build.

Answer, with file and line evidence: (1) what the relay can tell apart today: no eligibility head, a head whose decision is not Public, a head that is corrupt or unproven (the conditions both designs keep: nothing grants read visibility or asserts a copyright assessment, a corrupt or unproven head stays unresolved and keeps blocking completed coverage, no second policy registry). (2) What the smaller rule BREAKS, concretely: ordering per target, ordering against a concurrent newer publication of the same variant, a Public approval that arrives after the excluded evaluation (is it delivered durably today? the existing `ContentSearchEligibilityEvent` and which consumers act on it), crash between evaluation and acknowledgement, rebuild replay at a fixed owner cut (does a rebuild project exactly the same set as live projection did), the erasure supersession path, and the meaning of 'completed' for readiness gates that read it (Content phrase search readiness, health, generation, rebuild activation, checkpoint adoption, backpressure). (3) If it breaks nothing: the exact change in sessions, which items of the earlier specification it replaces or removes (justify each of the eight sessions, the image build and the API shape that remain against it), the tests that prove it (reuse item 12's fault test), and whether it needs a native build. (4) If it breaks something: the smallest addition that repairs that, and whether the default decision is then still smaller or not. End with a recommendation; Trust-ops reviews whichever wins.
