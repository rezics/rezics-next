## Outcome

Class A (Program, 09:40 UTC: "it removes the rebuild, the freeze question and every later rebuild, and it is what a restored deployment does anyway"). TEST/FIXTURE TOOLING ONLY; no product code, no Java, no migration.

Facts (read from the code, verify them first and say if any is wrong): `restoreFixture` (scripts/fixture/restore.ts) already applies NEWER SQL migration files at restore (`migrateFixtureOwners`, `pendingMigrations` in `restoreCompatibility`, scripts/fixture/manifest.ts), so migrations do not invalidate a `fixture:build` backup. What does: an owner `generator` or `compatibilityInputs` change; an applied migration's bytes changed; a migration inserted before applied ones; Postgres/RustFS image change. The graph owner (scripts/fixture/owners/graph.ts `compatibilityInputs`) lists the Jena version, `infra/jena/fuseki-text.ttl`, profile `work-metadata-v1` and the WHOLE `generated/model/manifest.json`: any model definition added anywhere (content-withdrawal-v1, zone-capability-v1, agent-erasure-v1, ...) makes a fixture stale although its stored records are unchanged.

Requirements:
1. Compatibility inputs: replace the whole-manifest digest by the digests of exactly the model profiles/shapes/vocabulary terms the fixture's records are written against (derive them from the corpus loaders' own declared profile use; do not hand-list; `work-metadata-v1` is already separate). A model change to a profile the records use still makes the fixture stale (that is correct and tested); an ADDITIVE definition elsewhere does not.
2. Restore aligns the model: after the restored stack starts, run the same model alignment step the shared-stack refresh uses (the dev stack's align-model / model bootstrap; find it in scripts/dev and reuse the function, do not copy it), so the restored graph carries the current model generation; the manifest keeps recording the generation the backup was built at, and the restore evidence records both generations and what alignment installed.
3. Tests (unit with injected inputs, plus one restore-compatibility test over real manifests): (a) a manifest from before an additive model definition is compatible, with the alignment listed as pending; (b) a change to a used profile is stale with the named reason; (c) an applied-migration byte change and an inserted-before-applied migration stay stale; (d) the existing fx-medium manifest in `.temp/fixture` classifies as before for the unchanged inputs.
4. Document the practice in docs/storage/workload-budgets.md (the fixture paragraph) in five lines: what does and does not invalidate a retained fixture.
