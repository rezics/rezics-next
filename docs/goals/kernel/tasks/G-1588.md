## Outcome

`tests/qa/integration/g-630-zone-routes.test.ts` fails on current main (QA `20261010t020430-1591dc`, alone, ordinary class, 27 s) and on the G-1567 branch with the same line: `Expected 201, got 503: {"code":"backpressure_unavailable","title":"The broker budget cannot be observed"}`. It is not a Zone assertion. The 503 is `OperationsBackpressure.admitDurable('broker')` (`services/main/src/operations/backpressure.ts`, `services/main/src/routes/operations.ts` global `beforeHandle` for `BROKER_INTENTS`): the broker lane's probe `relayHandoffPositions(fuseki, dataEpoch, () => work.relayPosition.read())` threw (Fuseki control lookup not exactly one row or held, relay checkpoint missing or on another data epoch) or the delivered checkpoint is ahead of the Fuseki head ("a gap, never negative backlog"). A test that creates a Zone/mount after ~26-40 s of earlier writes sees it, so the probe is observable at first and not later.

1. REPRODUCE: run the file alone twice on current main and record which of the three throws it is: instrument locally (do not commit the instrumentation): which condition in `relayHandoffPositions` or `durable()` returned `unavailable`, with the values (control rows count, hold, checkpoint epoch/sequence vs head). Report them.
2. CAUSE: decide by evidence whether the product or the test is wrong. Candidates: the in-process relay's checkpoint is on another data epoch than the Main's lineage in this fixture (a stack where the relay is created before the dataset epoch is rotated); `relayPosition.read()` is stale or `null` while the relay has not yet handed off (a fresh stack with no checkpoint row yet should read as `delivered = head`/empty, not as unavailable: "no handoff yet" is a normal state, not a gap); the checkpoint advances past a head read earlier in the same Promise.all (a race between the two reads; `delivered > head` for a moment is read order, not a gap, since the head can only grow: read the checkpoint FIRST and the head second, or treat delivered > head read in that order as unavailable only after one re-read); a held/ambiguous control row in that fixture.
3. FIX at the cause in product code: a missing checkpoint on the current epoch is "no handoff yet" (open, backlog = head - 0 or head, whichever the lane contract says: read the OPS06 contract in the file header and `docs/` references), read order removes the race, and a REAL unavailable (foreign epoch, held, ambiguous control, probe throws) stays `unavailable` and is logged with a fixed reason through the module's existing logging so it names which. Do not raise a budget, do not make the lane skip admission.
4. TESTS: `tests/qa/unit/operational-bounds.test.ts` (existing) stays green and gains cases for: no checkpoint yet = open; delivered ahead of head read in the safe order = open after one re-read; foreign epoch = unavailable; plus `tests/qa/integration/backpressure-broker-lane.test.ts` if the integration fixture shape makes the lane state visible (`GET /v1/operations/backpressure`): after writes on a fresh stack the broker lane is `open`, never `unavailable`. Run `g-630-zone-routes` alone (green), `operational-bounds`, and the other files that import the backpressure module (`grep -rl "backpressure\|operations/backpressure" tests services/main/tests | head`); report run ids.
Commit after each step.
