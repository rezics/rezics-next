## Outcome

Launch's L10 (Zone page discussion) stays class A and needs one kernel slice (slice 2 of Launch's specification, staged by the manager at `.temp/ref/g-1740-spec.md` in your worktree, together with the contract `.temp/ref/l10-contract.md`; read both, especially sections 3 and 5 of the contract). Launch's new server command `POST /v1/realms/{realm}/about-posts` composes draft, identity, placement and settle in ONE durable command; it needs from the content-publication owner:

1. A VERIFIED-PRINCIPAL ENTRYPOINT in `services/main/src/modules/content-publication/reply-draft.ts`: an internal function that drafts a Realm reply for a principal that the caller has ALREADY verified, so the command does not have to forge a `Request`. Keep the existing Request adapter, built on top of it; the public draft API stays equivalent (same admissions, provenance, origin Realm, receipts, bounds, response bytes and statuses; its existing tests pass unchanged).
2. VALIDATED CANONICAL-PARENT CONTEXT for retained-root child drafts: a reply to the canonical thread after the page's resource has been edited uses the opener's RETAINED root revision, while proving the current resource disclosure and the exact visible parent. Coordinate the small Launch-owned interface in `services/main/src/modules/realm-reply/root.ts` (read it, keep the change minimal and typed; Launch owns the file, so mail Launch the diff before you rely on it).

Rules: no new admission service and no new action (compose the existing `content.draft`); never accept a caller-supplied parent, opener, approval or retained-root bypass: the context is derived and validated inside the owner (exact parent identity, exact retained root revision, target and origin Realm unchanged, revision not erased, parent visible to this principal now); every refusal answers as hidden or absent where the existing reply drafts do (404 on a hidden parent); a lost draft response replays the exact bytes once.

Proof (`services/main/tests/reply-draft-bridge.test.ts` plus the existing reply draft tests unchanged): the existing draft API is equivalent; a child draft succeeds after the resource is edited; a forged parent, a changed target, a changed origin, an erased revision and a hidden parent each fail with no draft created; a lost draft response replays the exact bytes once. This task touches reply admissions: mail Trust-ops the diff before landing (they review it).


TRUST-OPS REVIEW CONDITIONS (2026-10-11, recorded here with their reason; the review approved the diff from the admission side): (1) SCOPE CEILING. `VerifiedPrincipal` is a plain interface, so the `comment:create` ceiling is enforced only where the principal was produced (`account.verify(request, ['comment:create'])`, and its `currentAssertion` refreshing with the same scopes); `saveVerifiedMemberReplyDraft` cannot check it. Export ONE helper used by BOTH the request adapter and Launch's command (verify with `['comment:create']` and return the principal); state in the bridge doc comment that callers must obtain the principal that way; a token without `comment:create` must be refused before any effect (Launch adds that test at its new route; add the equivalent unit case for the helper here). (2) AUTHOR. The bridge takes `actingSubject` from the caller and has no author logic (Access refuses Org, PenName and non-controlled subjects at register once Trust-ops' baseline change lands). Keep one test where the canonical branch is called with an Org `actingSubject` that a steward controls and assert refusal with NO Content save; mark it pending until that Access change is on main.
