## Outcome

Program's decision (run 6, G-1531 finding): two TS tests are killed at their tier's 180 s file budget because each wraps a SECOND native build inside a TS test, which duplicates the image build's own Maven gate and costs 12 to 22 minutes in the wrong tier:
- `infra/jena/tests/semantic-source-readiness-union.test.ts` (206 lines) reruns the whole native Maven suite in a container and compares per-class test counts (225 -> 251 etc.) and evidence.
- `services/main/tests/read-snapshot-native.test.ts` (77 lines) builds its own image (`mvn package`, `dependency:build-classpath`) to run a Java program against a snapshot.

Neither a native tier nor a per-file budget. Instead: **move each file's native assertion into the Maven module as a Java test** (under `infra/jena/command-module/src/test/java/com/rezics/jena/`), so it runs in the image build (which already runs the Maven suite, 403 tests at pin `0bee21b02aeb`) and blocks the pin; then **delete the TS wrapper**. Where a check really needs the TS side (a TS reader against a native snapshot), run it against the pinned image the integration stack already starts, never a rebuild; if that is what `read-snapshot-native` needs, make it an integration test (an `integration` file starting the standard stack, reading through the TS reader) and delete the build wrapper. If either one cannot be expressed either way, STOP on that file and report exactly what it checks and why; Program decides.

Do, per file:
1. Read the test and say in your RESULT, in two sentences, what it actually asserts (the real invariant, not the mechanism).
2. Express it as a Java test (or the integration test above) with the same strength; for the union test the per-class count comparison against authored `@Test` methods can become a Java/Maven-surefire-based check or be dropped if Maven itself already guarantees "every @Test ran" (say which, with evidence: surefire fails on a missing test class, tests are discovered by class). Do not weaken: if an assertion is dropped because it is redundant with Maven, state why.
3. Run it where it now lives (the Maven test via the image build under the heavy slot: `task goal -- slot --heavy -- docker build -f infra/jena/Dockerfile -t <pin> .` after `task gen`; or the integration file alone), delete the TS wrapper, and check no other file imports or lists it (`grep -rn "semantic-source-readiness-union\|read-snapshot-native" scripts tests infra services docs`, including test registries/affected maps/Taskfile).

Native change: after `task gen` the image pin moves because test sources are inputs; rebuild the image, report the Maven totals and the new pin. G-1515 (bulk composition commit, native, running) lands first: rebase on main after it lands and recompute the pin; do NOT run `dev:refresh` (Program refreshes once after the native changes). Keep your Java test names descriptive.
