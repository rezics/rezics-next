## Outcome

Trust-ops' T6 (merged f0616aaa3) bounds every pool checkout and detects a
nested checkout: holding a client from pool P while borrowing another from P
deadlocks under load (`REZICS_NESTED_POOL_CHECKOUT=throw` makes detection
throw). It found five such sites in kernel's area:

- `work/restore-lineage.ts:338` holds the Access client from :312 while
  `assertAccountDeletionJournalCoverage` (`outbox/account-deletion-journal.ts:51`)
  queries that pool;
- `restore-lineage.ts:339`: `assertGraphDeletionEvidence` connects the same
  Access pool at :151;
- `restore-lineage.ts:181` holds the client from :151 while
  `assertDeletionRecoverySet` (`work/pg-recovery-frontier.ts:55`,
  `work/access-recovery-coverage.ts:69` and :90) uses that pool;
- `owner/relay-gap.ts:139` holds the relay client from :108 while
  `verifiedRetainedRelayRange` connects at `outbox/relay.ts:197`;
- `owner/operations.ts:202` holds the relay client from :169 while
  `releaseRestoredGraphHold` connects at `restore-lineage.ts:351`.

Pass the held client down at each site. Where a callee runs inside the
caller's transaction after the change, check that it still sees what it saw
before (its own committed reads versus the caller's uncommitted writes, row
locks, statement timeouts) and say so per site in the handoff. Look for other
nested checkouts in the claimed files and fix them the same way.

Not to build: no pool wrapper, client registry or new transaction helper; the
existing functions gain an optional client parameter at most.
