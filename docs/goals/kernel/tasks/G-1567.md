## Outcome

Launch (review of G-1557) asked for one source of a Zone's disclosure. Today there are two: the Space's `rv:disclosure` (changed by `PUT /v1/spaces/{space}/settings`) and the Zone node's own `rv:disclosure`, written at creation from the create input (`zone/owner-create.ts`, `input.disclosure`, also copied into the component manifest by `prepareComponent`) and cross-checked by the Zone reader (`zone/configuration.ts`: `config.disclosure !== head.disclosure`, `?spaceDisclosure`). The settings command changes only the Space's, so a Zone created Private cannot become public through it, and a PUT that succeeds while the Zone stays private would be a lie. Fix it at the source: the Zone's effective disclosure IS its Space's disclosure. Do not refuse the change, do not make Launch work around it.

Method (investigate first, then pick the smaller change and say why in RESULT):
1. Map every reader and writer of the Zone's own disclosure: `grep -rn "disclosure" services/main/src/modules/zone services/main/src/routes/zones.ts services/main/src/modules/space`, the component profile (`zone-presentation-v1/v2`, `zone-capability-v1`, `space-zone-v1`), the manifest `prepareComponent` input, `zone/publication.ts`, `route.ts`, `route-population.ts`, `structure-profile.ts`. List them in RESULT with what each does with it.
2. Preferred: remove the Zone-level copy. Zone create takes no separate `disclosure` (the Space it is created in already has one; a request that supplies a different value is refused with the existing problem shape, an equal value is accepted); readers take the Zone's disclosure from the Space (`?spaceDisclosure` is already read beside it); the component manifest and the Zone node stop carrying `disclosure`; the profile drops the field in a NEW version only if an exact stored artifact pins the old one (stored artifacts stay immutable; read how `zone-presentation-v1` to `v2` was done and follow it; do not edit a persisted profile in place). A Zone already stored with its own `rv:disclosure` stays readable: the reader ignores it and uses the Space's.
3. Fallback only if (2) needs a stored-artifact break: the settings command writes the Space's disclosure AND the Zone node's `rv:disclosure` in ONE graph update (same receipt, same outbox event), and a unit test proves no path writes one without the other. Say which blocker forced it.
4. Proof: `services/main/tests/zone-disclosure-source.test.ts` (unit/owner): a Zone created Private in a public Space (and the reverse) resolves the Space's disclosure; changing the Space's settings changes what the Zone reader returns, with no second write. Integration: extend `tests/qa/integration/zone-document-home.test.ts` or add one file: create a Zone, flip the Space private -> public -> private through the settings command only, and assert the Zone's public presentation, route resolution and listing follow each time (the case G-1557 documented as a gap). Run the neighbours: `grep -rl "zone" tests/qa/integration -l | head -30`, run those that mention disclosure (`grep -l disclosure`), report run ids.
5. NET LINE DECREASE in non-test source is expected (a representation is removed); report `git diff --stat main...HEAD`.

Do not edit Launch's web app. If a web screen or the Account/ranking read depends on the Zone-level field, list it in RESULT and keep an adapter in the API response so the response shape is unchanged. Commit after each step; `task gen` and commit generated files.
