## Outcome

`services/main/tests/seal-on-visibility.test.ts` scans each function body: a catch of `WorkReadMissing`/`TargetUnavailable` followed by a receipt write in the SAME body fails unless the allowlist gives the reason. Program found the hole: it does not follow helpers defined in the same file. Launch's realm reply `create` sealed a denial through `replyQuestionDenied` / `sealsReplyRefusal`, and the guard still passed with the allowlist entry removed. A guard that a one-line extraction defeats guards nothing.

1. CLOSE THE HOLE. In the same module (file), the scan resolves each call made from a catch handler, or from the code that runs after the catch in the same function, to a function or arrow function declared in that file, and treats its body as part of the caller's: a receipt write reached through any depth of same-file helpers counts, with cycle protection. Cost note in the test: one pass over each file, bounded by file size.
2. REFUSE A DELEGATED DECISION. A catch whose handler passes the caught error (or a value derived from it) to a function that is NOT declared in the same file (an imported helper) and whose result decides the response or the receipt: the scan cannot see through it, so it refuses unless the allowlist names the site and gives the reason the imported helper does not seal. Calls to a fixed set of known-pure error mappers (logging, `problem()` constructors, `commandError`'s mapping) are listed explicitly in the test with a reason each; keep that set small.
3. FIXTURES THAT FAIL. Add small fixture sources under `services/main/tests/fixtures/seal-on-visibility/` (plain `.ts` text the scan reads, never imported): (a) a seal reached through one helper, (b) a seal reached through two helpers, (c) a mutually recursive pair that seals, (d) a catch delegating to an imported helper, (e) a clean catch that only maps to 404/503, (f) a helper that seals only on a branch not reachable from the catch (the scan is conservative: it fails and says so; allowlisting is the answer). The test asserts (a)-(d) and (f) are reported and (e) is not. The fixtures are excluded from the production scan.
4. LIST WHAT SURFACES. Run the stronger scan over `services/main/src`. Every new finding is a hidden seal or a hidden delegation. Do NOT allowlist silently: for each, in the RESULT give file, function, what is sealed, and whether you fixed it (decision of 2026-10-11, Program: a hidden or absent target answers 404 on reads and writes alike and the two stay identical; whether a key is sealed follows from the outcome, never from the status class, so a refusal before any effect answers 404 and leaves the key open; 503 is only for a dependency that failed) or allowlisted it with the reason. Fix those inside the listed paths; a site outside them goes to the RESULT as a proposed task and an allowlist entry that says "owner: <module>, listed".
5. Launch's realm reply files are under a live claim of another Goal until it lands: if the scan reports them, list them, do not edit them.

Add a proof to `tests/qa/integration/command-retry-after-visibility.test.ts` for each site you fix: same key, target made visible, retry succeeds, one receipt. Commit after every step; the connection drops.
