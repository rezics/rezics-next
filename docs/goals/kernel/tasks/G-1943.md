## Outcome

A diagnosis (`docs/goals/kernel/reports/content-projection-stop-diagnosis.md`, read it fully first; evidence at `.temp/ref/`) found a PRODUCT defect: the Content projection stops on the first publication that the PUBLIC API wrote, because the eligibility owner proof is judged "unresolved": `services/main/src/modules/content-publication/eligibility.ts` `contentSearchEligibilityDigest` hashes `JSON.stringify({ family, ...input })`, which depends on property INSERTION ORDER. The API writer (`services/main/src/routes/content.ts` around lines 53-58 and 342-343, v2 around 360-365) builds the input with `disclosure` before `rightsBasis` (and `profile` after `assessmentId` for v2); the reader (`eligibility-state.ts` `eligibilityDigestMatches`, around lines 489-503) reconstructs it with `rightsBasis` before `disclosure`, so the digests differ (retained `0cfd677b...` equals the API order, reader order gives `66d59f8b...`), `parseEligibilityProof` fails its final digest predicate, and `relayContentProjectionOnce` defers the publication forever. The same reader serves delivery and rebuild preflight, so production has the same persistent failure; it is the cause of the "public Content search anchor is closed before restriction" gap in the composed public rights proof.

Fix the class with ONE representation of the digest input:

1. `contentSearchEligibilityDigest` must not depend on the caller's property order: it builds the hashed JSON from an explicit, fixed field order of its own (document that order in one place with a comment), for v1 and v2. Decide that canonical order with evidence: it must equal what the API wrote for every receipt retained so far (the API order shown above), so receipts the API already retained verify; verify the claim against the route code and the retained receipt in the diagnosis.
2. The reader verifies a proof by recomputing through THAT function only. Receipts written by DIRECT OWNER calls before this change (tests and retained fixtures) may have hashed a different property order: enumerate those retained serializations explicitly and finitely (a small named list of `RETAINED_DIGEST_FORMS`, each one a documented field order with the reason it exists), checked after the canonical one; no open-ended tolerance, no "try permutations". If you find that no direct-owner receipt with a different order can exist in any retained fixture or backup (check `git grep` for direct-owner callers of the digest and the fixtures/backups that carry eligibility receipts: `tests/qa`, `tests/fixtures`, `scripts/dev/seed`), say so and keep only the canonical form: the simpler outcome is preferred and must be justified.
3. The writer in `routes/content.ts` must stop building the digest input by hand: it calls the same function with the same typed input, so there is exactly one place the order is decided.

Proof (Main tests, no integration needed): a digest round-trip test `content-eligibility-digest-forms.test.ts`: v1 and v2 proofs written the way the API writes them verify in the reader; a direct-owner form (if kept) verifies; a tampered field (resource, variant, decision, head, actor, basis, assessment) refuses; a proof hashed in some unlisted order refuses.
