## Outcome

G-1514's run of `tests/qa/integration/g-1051-query-scale.test.ts` (QA 20261009t060403-17fcf9) got past the author-name fence but the page-size matrix still fails after the 1,000-Work population: the anonymous page `page-size-dense-updated-64` does ONE extra `access.admitted_type` catalog read (69 postgres statements versus 63 at page size 1; page size 16 matches page size 1). That statement is not an author-reference lookup; `access.admitted_type` is read by `services/main/src/modules/types/store.ts`. The request-cost contract says cost must not grow with the page size (the cap/contract is asserted in the test; do not change it).

Find which code path reads the admitted types only when the page is full (64 items, or when the 64th item is of some type) or when a second page slice is needed (read the test's matrix to see the exact request: `grep -n "dense-updated" tests/qa/integration/g-1051-query-scale.test.ts` or the scale helpers it imports, and run the file's 1,000-Work portion alone to reproduce; the file is large, the 10,000 part can be skipped by the file's own scale switch if it has one, otherwise run it and stop at the first failure). Remove the extra read by loading the type catalog once per request (it is a bounded table: cache within the request, or read it in the statement that already runs), without changing disclosure, without a cross-request cache that could serve stale admission. State where the read came from and why it appeared only at 64.

Tests: a unit/owner test that counts the `access.admitted_type` reads for a page of 1, 16 and 64 on the same data and expects equal counts; then the scale file again to its next failure (report it; the 10,000-Work import depends on the throughput task and may still fail on the shared 430 s deadline: say so).
