## Outcome

READ-ONLY DESIGN, one document, dispatched now because the implementation waits on it (class A, Program). From source (to be CONFIRMED by launch's G-1968 profile): `services/main/src/modules/work/read-session.ts` records the DATASET position (`dataEpoch:sequence`) when a session starts and, after the operation, compares it again and throws `WorkReadMoved('Graph changed during the read')` when the sequence differs (lines ~391-398; the summary generation compare at ~247-252). The sequence is the whole dataset's write sequence, so ANY committed write elsewhere replays the session (up to six attempts against ONE 160-call, 4 MiB budget shared with attempts, `workRead` lines ~344-421), and a rich Zone/Work page (about 33 Fuseki calls) fails under ordinary write load with a budget error: a busy site is a failed read, the exact shape of the gated-reads rule (`docs/goals/kernel/reports/gated-reads-design.md`: an unrelated write must never fail a read; an affected change must exclude or mark only that unit).

Design (do not implement) the smallest change that makes a work read session immune to unrelated writes while keeping every existing safety fence (current authority, disclosure and Rights re-checks at the end of each attempt, erasure, media owner epoch, avatar and dependency tokens, realm membership proof). Cover, with file:line evidence for each:
1. Inventory every comparison in `read-session.ts` and its callers that uses the dataset-wide position (`position(deps, options.localBasis)`, `result.generation.graph`, `session.stale`, `movingGraph`, `graphSnapshotFenced`), who sets `movingGraph`/`localBasis` today and why.
2. Candidate designs, with the one you recommend and why: (a) pin every graph read of the session to ONE consistent cut (what the graph store can give: a read transaction/snapshot per session? what the Fuseki client can pin across calls? which reads cannot be pinned: SQL Access/Media vs graph); (b) replace the global compare by per-unit fences (the session already tracks `token`s for selected head, dependency, summary, media rows, realm membership: say exactly which of those a page needs and which writes can move each); (c) `movingGraph` marking stale-and-serve for reads that tolerate it (which pages). For each: what an unrelated write does, what an affected write does, the call cost, and the failure mode if the unit changed mid-read.
