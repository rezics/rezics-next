## Outcome

Launch's class finding (G-1577 review): `publicWorkRead` (`services/main/src/modules/work/read-session.ts`) takes the disclosure viewer from the bearer, so "public" Work reads (`GET /v1/works`, concept-works and resource-list `POST /v1/query`, the followed-concept-feed template, typeahead's presentation selection) answer differently for a signed-in reader through age and category opt-ins and mutes, yet their cursor bindings (`discovery-works-v1`, `concept-works-v1` and others) exclude the viewer. A continuation token minted for one viewer is accepted for another, so a list's pages can disagree: gated Works vanish mid-list or appear after page 1.

1. AUDIT. List every read that mints a cursor and runs under a disclosure viewer: `grep -rn "decodeReadCursor(\|encodeReadCursor(\|bindCursor\|readCursor" services/main/src | head -80` (about 30 modules). For each: does its binding array include the effective viewer (`session.viewer`, as `discovery/concepts.ts` does) or not? Report a table: module, route, binding profile id, includes viewer yes/no, whether the read's answer can differ per viewer.
2. FIX BY CONSTRUCTION, not by patching each site. The binding is built through one helper on the session (for example `session.cursorBinding(profile, ...parts)`, or the existing `decodeReadCursor`/`encode` taking the session) that always includes a stable digest of the effective viewer (anonymous, or the principal's disclosure profile: the same value `disclosureViewer` uses for the disclosure statement; NOT the raw account id, so two principals with identical disclosure profiles share a continuation only if their answers are identical; say which you chose and why), and every cursor-minting read goes through it. A new read that forgets the viewer then cannot compile or fails a guard test (a unit test that scans cursor call sites for use of the helper).
3. BEHAVIOUR on a mismatch: the existing mismatch behaviour of `decodeReadCursor` (a changed binding is `read_basis_changed`/restart-from-first-page, whichever the module already returns); do not invent a new problem.
4. NOT in scope: the explicit `actingSubject`/public-mode API change Launch proposes long-term: that is a contract decision for Program; state in RESULT what the explicit form would touch (the list of routes) so it can be decided.
5. Tests: unit `services/main/tests/public-read-cursor-viewer.test.ts` (helper includes the viewer; two viewers with different disclosure profiles produce different bindings; the scan guard); integration `tests/qa/integration/public-read-cursor-viewer.test.ts`: a list read page 1 as anonymous, then page 2 with the continuation under a bearer with different opt-ins (and the reverse) restarts/refuses; same viewer continues. Run the existing cursor/paging tests of the changed modules (`grep -rl "cursor" tests/qa/integration services/main/tests | head -40`, run those touching changed modules; report run ids).
Commit after each step.
