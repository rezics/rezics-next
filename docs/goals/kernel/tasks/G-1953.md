## Outcome

Program's rule (class A by the scale rule, found by code reading, not yet measured): a user-facing command's work must touch a bounded neighbourhood, so a cross-parent GROUP MOVE (moving a group occurrence with its subtree to another parent in a Structure: a Collection, a Book composition, a Recipe section tree) must cost the same whatever the size of the moved subtree. Evidence staged in `.temp/ref/collection-change-cost.md` (section "Size-dependent branches outside the measured insert recipe"): `height()` in `services/main/src/modules/structure/change.ts` lines ~1134-1151, reached at ~1213-1215 for the depth check (maximum depth 16), walks ALL descendants through `segmentsOf`, `membersOf` and `get`, so one move visits the whole subtree: its read work is descendant occurrences and segments, not the number of submitted operations.

Do it the way the typeahead went: a growth check FIRST that reproduces the cost, then the fix against it.

1. GROWTH CHECK (integration, through the existing verdict in `tests/qa/support/work-profile.ts`: `assertWorkCostAtScales`, classes constant/logarithmic/linear/linearithmic, and the request profile helpers; read `tests/qa/integration/typeahead-growth.test.ts` and the Collection/composition growth tests for the pattern and `docs/testing/complexity.md` for the method): build a Structure with a group whose subtree has 16, 64 and 256 descendant occurrences (built through the product API, never raw writes; reuse the seed owner `scripts/load/work-profile-corpus.ts` and the composition API only if it fits, else a small local builder), move that group to a different parent (same Structure and cross-parent), profile the one move command at each size and assert the work counters (SQL statements, Fuseki requests, native adds/validation focuses) are CONSTANT across the three sizes. Commit it FIRST as `test.failing` with the measured values in the comment-free assertion message, and say in your result the measured slope (counts at the three sizes) BEFORE the fix.
2. THE FIX: the depth check must not enumerate the subtree. Maintain a bounded summary on the retained structure: the subtree height (and count if needed) stored on the segment/parent record that already exists in the immutable tree, updated incrementally on the same path as every other change (insert, remove, move) so a move reads O(1) summaries along the 16-deep ancestry of the target and of the moved group. One representation, no second index, no compatibility layer: a retained tree written before the summary exists must still verify and be moved; if that requires reading the old subtree once, say exactly how (a one-time lazy summary written on the first move, bounded per call by paging, or a refusal naming a repair command), and prove it.
3. Flip the growth check to a plain passing test (remove `test.failing`). Add the Main unit tests for the summary maintenance (insert deepens, remove shortens, move updates both ancestries, depth 16 limit still refuses, a legacy tree without summaries).
4. `docs/contracts/structure.md` (or the nearest contract): state the bound and the summary.
