## Outcome

Program's integration triage of regression run 5 (`.temp/ref/integration-triage-run5.json`, staged into this worktree; read the `clusters` list with `python3 -I`) found cluster `work-name-scope-not-prepared`: 7 files (g-1025-home-cost, g-1025-ranking-cost, g-1032-query-cost, g-1034-realm-ranking and three more; read the `files` array), each failing with "Work name scope is not prepared on this stack" and, behind it, Work reads that answer unavailable. Cause chain, all Kernel's: (1) the native module invalidates the Work name scope (`scopePhase`, `scopeQualification`) at every Fuseki startup (`PublicNameProjection.java`); (2) Main's startup now calls the `workScopeDirectory` maintenance command (`services/main/src/modules/query/seek-index.ts`, `prepareWorkNameScope`) which native refuses with the typed `writer-not-exclusive` when the Fuseki update service is not delta-exclusive; (3) the standard QA stack assembler (`infra/jena/fuseki-text-qa.ttl`) is not delta-exclusive, and only `tests/qa/integration/title-candidate-original-custody.test.ts` gets the one-time Fuseki recreate that lets `qualifyAtStartup` admit the exclusive writer (see `exclusiveWriterStartupFiles` in `scripts/qa/isolated-integration-files.ts` and the `--force-recreate fuseki` step in `scripts/qa/cli.ts`); (4) Main treats `writer-not-exclusive` as "not prepared on this stack" and carries on, so on every other QA stack the Work name directory stays unprepared and the reads that need it are unavailable. The triage's proposed fix: QA startup must acquire the exclusive Work-name writer.

Do:
1. Confirm the chain with evidence on one of the 7 files (run it alone; report the status/body/line of the first failing read and whether the directory phase is `complete` in the native state after startup).
2. Make the standard integration stack start with the exclusive writer admitted, once, for every integration file that needs the Work name scope (likely all: decide with evidence), without a per-file allowlist if a stack-level rule is cheaper: e.g. recreate Fuseki once after bootstrap as the custody test does, or have the QA bootstrap order guarantee that the text generation exists before the first Fuseki start so `qualifyAtStartup` admits at the first start. Measure the added stack startup time and keep it small (state the number). Tests that write raw SPARQL updates directly to Fuseki may be refused by an exclusive writer: find which integration files do (grep for raw `/update` or `fuseki.update` use in tests/qa), and fix those files to write through the API or the command module (the repo rule: writes go through the API), never by weakening the writer exclusivity or the CLEAR ALL guard. Program's G-1486 (QA reset command) is in flight on CommandService/PublicNameProjection and on `scripts/qa/cli.ts`: do not edit those files. If the fix needs a hunk in `scripts/qa/cli.ts`, write that exact hunk as a patch file in your worktree (`.temp/cli-exclusive-writer.patch`), prove it by applying it locally, and report it so the manager can have it folded into G-1486 or landed after it; prefer a solution that avoids cli.ts (bootstrap order, `stack-startup.ts`, `isolated-integration-files.ts`, the QA assembler).
3. Run the 7 files of the cluster alone with explicit `task goal -- test <paths>` and report run ids and pass/fail per file; for any that still fail, say whether it is this cause or another (name it) and stop at routing it.
4. Do NOT use Claude or Grok engines; do not run the whole integration tier.

Do not build: a second writer mode, a bypass of the exclusivity check in native, or a Main change that treats an unprepared directory as ready.
