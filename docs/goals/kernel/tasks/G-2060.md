## Outcome

Class A, a hard precondition of registering any production ancestry source. The landing review of the previous-behaviour change found one P1 and nothing else: legacy submissions run in chunks of 64 (`ownerSubmission`), and the final whole-batch registration check (`requireSelections` over ALL selections) that the earlier code ran after the work was dropped by the rebase, so `requireSelections` now runs per chunk only.

Failing sequence: 65 legacy selections, 64 Content targets then one Source target. While the Source chunk runs, Content's ancestry source is registered with missing evidence. Only the Source chunk is revalidated, so the earlier Content decisions return visible although Content now requires strict evidence. Registration happens at composition before any request and no production code registers a source today, which is why this did not block the refresh; it must be a test on main before any source is registered.

Do:
1. After the chunk loop of the legacy branch (in `ownerSubmission`, or in `captureDisclosure` and `fenceDisclosure` after `ownerSubmission` returns) call `requireSelections(env, <all selections>)` so a registration change at any point of a submission throws `DisclosureUnavailable` before any result is returned. Search the legacy path for every other chunked entry (inventory and resolve entries that submit through `ownerSubmission`) and give each the same final check.
2. Do not change the strict path: outside the legacy hooks it stays byte-identical to main.
3. Tests in `services/main/tests/disclosure-owner-fallback.test.ts`, the NAMED precondition test: `legacy submission of 65 selections rejects when an owner registers during the last chunk` for capture, and the same for fence, plus one case where registration changes during an EARLIER chunk. Expected: `DisclosureUnavailable`, no decisions returned.
