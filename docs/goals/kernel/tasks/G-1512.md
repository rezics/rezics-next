## Outcome

`tests/qa/integration/g-1014-structure-cost.test.ts` (10,000-chapter import, 450 s test budget) and `tests/qa/integration/g-1051-query-scale.test.ts` (10,000-Work imports, shared 430 s profile deadline) do not finish: an import through the API runs at about 1.1 s per 16-operation change. Program's decision: the budgets stay; writes go through the API, so slow writes are an API throughput defect. Production does the same per-change work, so fixing it speeds real imports.

Do:
1. **Profile one change by phase** on the composed stack (integration stacks now build Main through `services/main/src/composition.ts`, as production does) against the old hand-built stack (check out the commit before the composition change for the baseline: `git log --oneline -- services/main/src/composition.ts`, take its parent `c7490bdfd~` or the merge-base, and run the same file there in a scratch worktree). Phases: Access admission, rate limit, partition lease, receipt custody (`outbox/receipt-custody.ts` withReceipt), `types.refresh`, Fuseki command, Postgres statements, relay/outbox, anything else on the request path. Use the existing request-cost counters (X-Rezics-Command-Work, Server-Timing) and add timing spans in a scratch branch only; do not commit instrumentation unless it is the bounded kind the repo already has.
2. **Remove or bound per-change work that should be per batch.** Candidates the profile may show: a per-change `types.refresh`, partition lease acquire/release per change, a receipt custody lock per change that can be taken once per batch, a rate-limit write per operation instead of per request, an Access recovery fence probe repeated per operation. Fix with the smallest change that keeps each safety property (state which property each removal could affect and why it still holds). Never drop a fence, authority check or audit record; never raise a cap or a budget.
3. **Report before/after numbers**: seconds per 16-operation change by phase, and the time for 1,000 and 10,000 chapters (run the 1,000 sample first; the 10,000 only if the 1,000 projection says it can fit 450 s). Run `g-1014-structure-cost.test.ts` alone before and after (`USER=edge LANG=C.UTF-8 LC_ALL=C.UTF-8 task goal -- test <path>`); run `g-1051-query-scale.test.ts` once at the end.

If the dominant cost is native (Fuseki command, TDB2) and needs a Java change, stop at the profile, report exact numbers and the proposed change; do not edit the Java command module (another task holds it).

## Checks

- The profile table, the diffs for each removal with the safety-property note, run ids before and after, `task main:typecheck`, `task gen:check`, and the existing tests of every module you touched.
