## Outcome

Launch's G-1597 (Realm reply corpus) found a class defect: `TargetUnavailable` (`services/main/src/modules/target/resolve.ts`, thrown at ~177, ~356 and ~399) extends `WorkReadMissing`, so a caller that catches `WorkReadMissing` treated "this target is not a readable target of this grain right now" as a denial, and in the Realm reply path SEALED the idempotency key on it: a same-key retry then got 403 forever once the target became visible. Launch fixed the reply path locally (it catches `TargetUnavailable` first and answers 503 unsealed).

Kernel's read of the type (do NOT change the hierarchy; say why in RESULT): `TargetUnavailable` is the hidden==absent 404 by design ("Resource is unavailable"; Program's G-1605 rule). Its three throw sites are "no exact base row for the resource" and "a summary with status `unavailable`" (hidden, absent, erased, retired); transient conditions already have their own kinds: `WorkReadMoved` (409 read_basis_changed) and `WorkReadUnavailable` (503). Making it a sibling would break the one-answer rule for hidden vs absent reads. THE REAL CLASS is a command that records a refusal (a sealed receipt, a consumed idempotency key, a terminal "denied" state) from an outcome that depends on CURRENT VISIBILITY, not on the request's intent: the same key, same body, retried after the target became visible, must succeed or at least be re-evaluated; only a refusal that is a property of the request itself (invalid body, an authority decision on the principal at that time, a conflict with the key's earlier different body) may be sealed.

1. AUDIT, with a table in RESULT: every `catch` of `WorkReadMissing`/`TargetUnavailable` (and `instanceof WorkReadMissing`: about 50 sites across routes and modules; `grep -rn "instanceof WorkReadMissing\|instanceof TargetUnavailable" services/main/src`) that lies on a COMMAND path (a write with an idempotency key or receipt: realm replies and submissions, reviews, ratings, follows, post identification, progress, notification producers, semantic/context changes). For each: what is sealed or consumed on that outcome, yes/no; read paths (404 answers, cursors) are out of scope and listed as "read, no state".
2. FIX each command-path site that seals on a visibility outcome: the refusal is answered (404/503 per the module's existing convention) WITHOUT recording a terminal receipt or consuming the key, so a retry after the target becomes visible re-evaluates. Do not change authority decisions; do not widen what a hidden target reveals (the answer for hidden stays the same as for absent).
3. GUARD AGAINST THE CLASS: a test helper or lint-style unit test that fails when a command path's catch of `WorkReadMissing` is followed by a receipt write in the same function body (a conservative source scan with an allowlist per site and reason), so a new command cannot reintroduce it silently. Keep it simple; the allowlist is the audit table.
4. PROOF: `tests/qa/integration/command-retry-after-visibility.test.ts`: for the Realm reply path (already fixed locally by Launch: verify it, do not redo it) and for EACH other site you fix: issue the command with key K against a target that is not yet visible (404/503, no receipt row), make the target visible, retry with key K and the same body: it succeeds (201) and the receipt is created once. Unit `services/main/tests/seal-on-visibility.test.ts` for the guard. Run the changed modules' tests and report run ids; `task main:typecheck`, `task gen:check`.
Commit after each site. The connection drops: commit small.
