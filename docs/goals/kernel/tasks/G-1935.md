## Outcome

`services/main/src/modules/statement/seek.ts` (the projection turn around line 396-400) proves "no gap" for the sequences it is about to project by asking the graph for a PHYSICAL `rv:OutboxBatch` header per sequence in `GRAPHS.outbox`, and throws `WorkReadUnavailable('Statement index outbox coverage is incomplete')` when fewer headers than sequences come back. `docs/contracts/events-and-jobs.md` ("Slim commands are the exception to one physical header") says a slim command commits its receipt, stream position and compact commit proof WITHOUT the full physical batch header; its batch is reconstructed from the owner's receipt custody (`services/main/src/modules/outbox/receipt-custody.ts`) and "a real hole is a position with neither a physical header nor a custody record". A reader that asks the graph for the header only reports a slim command as missing. Observed: the `tests/qa/integration/local-read-basis.test.ts` child process exits 1 at this throw before its fixture runs (a Sol worker's run in the relay-header-cut task; the code is unchanged from main). This is the fourth reader of this class (the first three, the Zone browse reconciliation, the rebuild preflight and the feed cut, are fixed or in flight; see `docs/goals/kernel/reports/gated-reads-design.md`).

FIRST confirm the refusal is the slim class and not a real hole: on a small stack, which sequence lacked a physical header and does the owner custody (`env.receiptCustody`, the same source `relayMainOutboxOnce` gets as `ownerOutbox`, used in `content-publication/rebuild-preflight.ts`) hold a record for it? Mind the two position domains: `seek.ts` iterates GRAPH sequences (`rv:sequence`), custody is keyed by Main stream sequence (`CustodiedOutboxSource.read(dataEpoch, streamSequence)` in `outbox/relay.ts`) and a custodied batch carries its `graphSequence`; derive the mapping from the custody record, never from equality of the two numbers. Then fix the class in this file only: a graph sequence with no physical header is covered when exactly one custody record binds that graph sequence in this epoch; a sequence with neither refuses with the existing message; a physical header that disagrees with a custody record refuses. Keep the bound (`STATEMENT_SEEK_COST`): one custody lookup per missing sequence per turn at most, and say what the per-turn extra cost is in statements.

Also check every OTHER place in `services/main/src/modules/statement/` and `structure/` that asks `GRAPHS.outbox` for a physical `rv:OutboxBatch` by sequence (grep `OutboxBatch`), list them, and fix those that are projection coverage proofs the same way; for those that are not (exact header proofs inside a command), say so in one sentence each.
