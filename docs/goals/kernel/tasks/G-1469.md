## Outcome

On 2026-10-08 the shared dev Fuseki (Jena 6.2 TDB2, image `rezics/fuseki:6.2.0-cmd0.5.39-*`, database `rezics`) threw `RuntimeIOException: Out of bounds: (limit 21214764) 21216307` from `BindingTDB.get1(?batch)` via `TransBinaryDataFile.checkRead` <- `TReadAppendFileTransport.read` <- `NodeTableTRDF.readNodeFromTable` <- `NodeTableCache._retrieveNodeByNodeId`: a NodeId read beyond the node data file's committed length, 1,155 times, every outbox-batch query failing. A plain container restart stopped it, and 400 s of Main traffic afterwards produced none. Production runs the same store, so this needs a proven root cause before launch. Evidence: the full docker log is preserved at `.temp/incidents/fuseki-tdb2-oob-20261008.log` (stage a copy under your worktree's `.temp/ref/` first if you cannot read it; 618 errors, first fault 12:47:24 UTC). Program's hypothesis to test first: a write transaction aborted when Main or the relay was stopped mid-command; its node-table appends were truncated but the Node->NodeId cache kept the entries; later writes stored those stale NodeIds in the indexes. A restart clears the cache but not the indexes, so after later appends those offsets point into other nodes' data and read back wrong values silently.

Do, in order, and report evidence for each:

1. **Upstream:** search the Apache Jena issue tracker and mailing list for a TDB2 node-table cache not invalidated on abort/rollback (or on a failed/aborted write transaction), the exact `Out of bounds` + `TransBinaryDataFile.checkRead` signature, and whether 6.x fixes it. Cite issue numbers and the fixed version; say if nothing relevant exists.
2. **Reproduce** against a COPY of a dev-sized store, never the shared one: take the copy with Fuseki's own consistent snapshot (admin backup API or `tdb2.tdbbackup` on a stopped copy; do not stop `rezics-dev-fuseki-1`, do not write to its volume). Use the repo's Jena test container pattern in `infra/jena/tests/` (e.g. `command.integration.test.ts`, `compaction.test.ts`) to run a throwaway Fuseki with the command module image. Provoke aborted update requests the way the stack did: a command or SPARQL update that adds many new nodes and is aborted by (a) a client disconnect mid-request and (b) an in-process `abort()` after node allocation (the command module paths that `dataset.abort()`), then keep writing and querying. Look for the same exception and for silent wrong reads.
3. **Integrity scan** of the current dev dataset (via a snapshot copy as above): decode every quad from every TDB2 index (GSPO, GPOS, GOSP, SPOG, POSG, OSPG) and compare the indexes with each other and with the node table; report counts, any NodeId beyond the node file length, any quad whose nodes decode differently across indexes. Commit the scan as a reusable test/tool under `infra/jena/tests/` or `scripts/ops/` (small; one Task entry), because we will need it against production-like data.
4. **Conclusion:** state whether damage exists and what caused it. If confirmed, propose the smallest fix (a Jena upgrade or setting, or the command module never leaving an update half-sent / always completing or aborting through one path) with a failing-then-passing test, plus a recovery path for the dev store (restore from a consistent backup or rebuild from the retained outbox) written as an operating procedure in `docs/operations/` (short, only what code cannot carry). If damage is NOT confirmed and the fault is not reproducible, say what remains unexplained and what monitoring would catch a recurrence (the anomaly watcher already alerts on "Out of bounds" in the dev Fuseki log).

Hard rules: never stop, restart or write to the shared dev stack or its Fuseki volume; never use the vault; no sanctioned reset credits; take copies, not the live files. Do not change Main/Account/relay code in this task. If you need a native change, stop and report the exact change.
