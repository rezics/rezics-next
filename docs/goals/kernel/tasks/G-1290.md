## Outcome

Design record §1 (`.temp/ref/target-architecture.md`, "漸近可擴展"): every
write touches a bounded neighbourhood; cross-partition effects propagate
asynchronously. When a name's public status changes, the native public-name
projection walks dependent populations in the writing transaction:
`PublicNameProjection.java:132` copies `resources` and iterates every
dependent `space`, `:147` finds every `skos:inScheme` subject and `:154`
every `conceptRealm` subject. The work grows with the number of dependents,
so one popular name can make one write unbounded. Trust-ops' note on it:
`.temp/ref/private-name-callsites.md`, row "Kernel native projection".

Replace the dependent walks with:

- **parent fences**: the write records, in bounded work, that the parent's
  name status changed (a generation or fence on the parent), and readers of a
  dependent check the parent's current status, so a dependent never shows a
  name the parent has withdrawn even before repair runs;
- **resumable bounded repair batches** that bring dependents' projected
  names in line after the commit, each batch with a fixed upper bound, a
  durable continuation and idempotent replay.

Agent preference suppression and restoration keep working (the existing
integration test exercises them). A withdrawn name must be hidden at once
through the fence; repair only tidies stored projections.

Not to build: no job framework, scheduler service or generic graph-repair
engine; use the module's existing maintenance or projection entry points.
