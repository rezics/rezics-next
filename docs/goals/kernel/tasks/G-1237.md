## Outcome

Prove with one integration test, through Main's HTTP API only, that an author
can recover a Content document after saving a bad revision. Today the pieces
exist but no test exercises the journey: `GET /v1/content-revisions/:revision`
reads an earlier revision, `POST /v1/content-drafts` appends a revision under
CAS on the draft head, and publication requires the current draft head
(`services/main/src/routes/content.ts:341`, `services/content/src/core.ts:605`,
`services/main/src/modules/content-publication/publish.ts:426`).

Write `tests/qa/integration/content-document-recovery.test.ts`, following the
setup and helpers of `tests/qa/integration/content-publication-native.test.ts`
(copy what you need; do not edit that file):

1. Create and publish a structured document (good revision G).
2. Save a bad edit (revision B) and publish it.
3. Read G with `GET /v1/content-revisions/:revision`.
4. Save G's document as a new draft with `expectedHead` = B, then publish.
5. Assert the published content equals G's, a new revision and receipt exist,
   and the bytes of G and B are unchanged when read again.
6. Assert a save with a stale `expectedHead` (G instead of the new head) is
   refused, and a retry with the same Idempotency-Key returns the same result.

If any step fails because the product does not support it, stop and hand off
the failing step with the response; do not change product code.

Do not change any file outside the claim.
