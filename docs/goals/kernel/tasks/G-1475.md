## Outcome

Launch found (mail `launch` re G-1471; QA 20261008t142955-393e9f, t142326-20cd77) that for a freshly published Work `GET /v1/resources/{id}/statements` answers 503 `work_read_unavailable` while `/page` answers 200, because `StatementSeek.projectOnce` (services/main/src/modules/statement/seek.ts, the `main_relay_retry` consumer `statement-seek`) throws `Statement index source moved` whenever the graph position changed while it processed a batch: the transaction rolls back and coverage stays behind, so under steady writes it never catches up and `readSubjectStatements` keeps refusing.

Fix `projectOnce` so that it makes progress under concurrent writes. The batch is the contiguous sequences `prior+1 .. through` it read from the outbox before the position moved; those sequences are already committed, `readReferences`/`replace` are idempotent and read the current graph (which may already include later sequences, which replay later), so it is correct to commit the batch and set `through_sequence` to `through`, not to the newer position. Remove the post-batch `Statement index source moved` throw in `projectOnce` and keep every other safety: the empty-epoch proof (`Empty Statement source position moved`) stays as is; `rebuild()` keeps its strict position check; the outbox coverage check (`Statement index outbox coverage is incomplete`) and the reference bounds stay; coverage never moves backwards (use `GREATEST` or an equivalent guard in the UPDATE); a restore hold still refuses (`position()` without `held`). Reads remain bounded and `readSubjectStatements` still refuses while coverage is behind its basis, unchanged.

Prove it: a unit test (fake graph and a real or in-memory pool as the existing seek tests use; find them with `grep -rl StatementSeek services/main/tests tests/qa`) in which the graph position advances between the start and the end of a `projectOnce` call: before the fix it throws and coverage stays; after, it returns true and `through_sequence` equals the batch end; a second call continues from there until current. Add an isolated integration test through the API: write Statements in a loop from one client while another repeatedly calls `GET /v1/resources/{id}/statements` for a just-published Work and `projectOnce` runs through the real relay consumer; assert the read becomes 200 within a bounded number of relay turns while writes continue (do not use sleeps as the assertion; poll with a bound and report the observed number of turns). If an existing test asserts that `projectOnce` throws on a moved position, replace that expectation with the new behaviour and say so in your report; do not weaken anything else.

Do not build: a new worker, a lock that blocks writers, changes to `rebuild()`, `readSubjectStatements` or the outbox, or any web change.
