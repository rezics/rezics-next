## Outcome

Slice 3 of `docs/goals/kernel/reports/G-1800-specification.md` (read the whole report first; section "3. Media-owned imported-cover provenance" and "Identities and storage"). Program classed it A (2026-10-11). The Media owner is Trust-ops' area: Trust-ops reviews the representation and the migration before landing; mail the manager a diff summary at the end.

Extend the upload intent and the asset revision manifest with a Media-owned typed validator for verified provenance (source record or component, observation, original bytes digest; holder only as evidence, never as an accepted ownership statement). Persist the asset's cover-only invariant at creation and an indexed exact-revision projection for source record/observation to asset/original queries, using the current Content save and receipt transaction patterns; the index can be rebuilt from sealed owner manifests and must not outlive erased evidence. Add current source-record/component and observation lookup indexes, not a provider table. Old ordinary assets need no invented provenance and no backfill. Extend the existing SQL asset immutability guard (`services/content/migrations/070_media_owner.sql:216-232`) in the new migration `services/content/migrations/2130_media_imported_cover.sql` (range claimed `content:2130-2130`). Projection repair runs on both the successful historical receipt path and the new save path (`media/store.ts` about 484-496) or is atomic with revision insertion. Imported media with a sealed manifest but a missing or unverified index stays unavailable. Read `services/content/src/core.ts:698-739` only: additional manifest metadata is permitted there, no change.

Owner decisions that bind this slice (2026-10-11): the imported cover is admitted only to the identifying-cover use (the existing avatar slot of its own Work: Work edit authority, `media.avatar`), never another Work, a Person, a Realm or showcase art, so the cover-only invariant is a creation-time property of the asset. Trust-ops: a later notice suppresses the EXACT revision and the Use it names plus every Use of the SAME BYTES (same revision digest), not the whole Asset, so the provenance index must key by revision digest and exact revision, never only by Asset. Slice 1 and 2 of the same report (candidate and frozen bytes, task running) define the candidate fields; if their branch has not landed, take the field names from the report and keep the validator in one place so they converge.

Proof, new `services/main/tests/source-cover-provenance.test.ts` with the named cases `cover provenance is sealed to the exact asset revision`, `replacement cannot clear imported cover purpose`, `provenance reconstruction keeps digests and refuses absent evidence`, plus: mismatched observation/original, same-key altered intent, ordinary non-imported assets, and interrupted revision creation resumed through the existing upload receipt including a crash after manifest sealing but before projection indexing and a successful-receipt replay.
