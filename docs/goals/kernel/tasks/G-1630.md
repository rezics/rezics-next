## Outcome

Regression run 9 has 30 files that fail with `Fuseki update returned N`: 23 get 404 at `/rezics/update`, 7 get a 400 from the fixture assembler's raw-update guard. Kernel's reading, from the harness source (verify each step; it is research first):

1. `scripts/qa/cli.ts:414` gives a shard the PRODUCT assembler (`fuseki-text.ttl`, no `update` service) when `integrationStackAdmitsWorkScope(files, rawUpdate)` is true, i.e. no raw update overlay and every file is absent from `rawSparqlIntegrationFiles` (`scripts/qa/stack-environment.ts:70`). That list is hand-maintained and has a "only shrinks" ceiling (`scripts/qa/raw-sparql-integration-files.test.ts`).
2. 24 of the 30 failing files call `nativeFuseki.update(...)` (directly or through a support helper) but are NOT in the list. They pass only when the shard planner happens to put them on a stack with a listed file, which has the fixture assembler. A file that "passed eight hours earlier" and fails now changed shard, not behaviour. That is the one cause. The other 6 are listed and fail because the fixture assembler's raw guard (`TemplateIndexService.RawMembershipUpdate`) refuses what they send (no named graph, `WITH`/`USING`, `CLEAR ALL`, over 2 MB): their updates are real defects of the test.

What the task delivers, in this order, one commit per step. STEP A LANDS ON ITS OWN FIRST (Program, 2026-10-11): the scan test and a deterministic choice of assembler per file, merged before any migration, because until then the same commit passes or fails by shard placement and every regression comparison is noisy. Migration batches follow as separate landings.

A. DETERMINISTIC CLASSIFICATION. A unit test in `scripts/qa/` scans every integration test file and its imported support helpers for a raw-update call (`.update(` on a Fuseki client, `nativeFuseki`, `/update`, `sparql-update`). `rawSparqlIntegrationFiles` becomes the DERIVED set (the scan's result), so a file that sends raw update always runs on the fixture assembler and a file that does not never needs it; shard placement no longer decides. The 'only shrinks' ceiling is rewritten once to the union of today's list and the 24 unlisted callers (with the reason in a comment), then shrinks as files migrate. The scan fails with file and call site when a helper is not resolvable. Add the test, derive the set, update `scripts/qa/cli.ts:414` / `stack-environment.ts:70` to use it. Steps B to D are the separate task G-1636 (class table and migration), not this one.

Turns green / proves: the new scan test; `scripts/qa/raw-sparql-integration-files.test.ts`; and one run of two of the 24 formerly unlisted files (`tests/qa/integration/g-506-target.test.ts`, `tests/qa/integration/podcast-playlist.test.ts`) alone, each passing on the fixture assembler by itself.
