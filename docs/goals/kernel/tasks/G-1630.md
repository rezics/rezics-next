## Outcome

Regression run 9 has 30 files that fail with `Fuseki update returned N`: 23 get 404 at `/rezics/update`, 7 get a 400 from the fixture assembler's raw-update guard. Kernel's reading, from the harness source (verify each step; it is research first):

1. `scripts/qa/cli.ts:414` gives a shard the PRODUCT assembler (`fuseki-text.ttl`, no `update` service) when `integrationStackAdmitsWorkScope(files, rawUpdate)` is true, i.e. no raw update overlay and every file is absent from `rawSparqlIntegrationFiles` (`scripts/qa/stack-environment.ts:70`). That list is hand-maintained and has a "only shrinks" ceiling (`scripts/qa/raw-sparql-integration-files.test.ts`).
2. 24 of the 30 failing files call `nativeFuseki.update(...)` (directly or through a support helper) but are NOT in the list. They pass only when the shard planner happens to put them on a stack with a listed file, which has the fixture assembler. A file that "passed eight hours earlier" and fails now changed shard, not behaviour. That is the one cause. The other 6 are listed and fail because the fixture assembler's raw guard (`TemplateIndexService.RawMembershipUpdate`) refuses what they send (no named graph, `WITH`/`USING`, `CLEAR ALL`, over 2 MB): their updates are real defects of the test.

What the task delivers, in this order, one commit per step:

A. DETERMINISTIC CLASSIFICATION. A unit test in `scripts/qa/` scans every integration test file and its imported support helpers for a raw-update call (`.update(` on a Fuseki client, `nativeFuseki`, `/update`, `sparql-update`) and fails when a file does it and is not in `rawSparqlIntegrationFiles`, or is in the list and does not do it (a stale entry). Output names file and call site. After this a raw caller cannot pass by luck: it is listed (and so always runs on the fixture assembler) or it is migrated.
B. CATEGORISE THE 30. In the RESULT, a table: file, what each update writes (graph, subject kind, predicate), and why the product API cannot produce that state. Expected classes, confirm or correct them: (1) retire/erase a revision (`rv:ErasedRevision`); (2) disclosure or visibility toggles (`rv:disclosure`, `catalogueVisible`), which have a Space/Work settings command; (3) a protection head or ownership link; (4) legacy-shaped data for migration or repair tests (`rv:manifest` rewrites, name records, profile handles), which is a RESTORE state, not an operation; (5) bulk graph seeding for scale tests (`relation-star-cost`, `g-854-large-library`).
C. ONE SUPPORTED WAY PER CLASS, no new write backdoor. There is no `fixtureApply` and no raw update endpoint on the product assembler; do not add one. For each class name the mechanism: the product command (classes 1 to 3: use the API the product exposes; if none exists the test is asserting something only reachable by corruption and should be a native Java test), a restore from a backup built once by the product (class 4: follow `docs/storage/` and the existing slim-metadata restore tests), or a bulk-load fixture builder that runs the product's own import (class 5). Implement the shared helper(s) in `tests/qa/integration/support/` once.
D. MIGRATE the unlisted 24 and the 6 broken ones to those mechanisms in small batches; every migrated file leaves `rawSparqlIntegrationFiles` (the ceiling test keeps shrinking). A file you cannot migrate in this task stays listed with the reason in a comment, and is named in the RESULT.
E. The cost budgets of migrated files must not rise: report before/after seconds per file in the RESULT.

Do not "patch tests one by one" before A and B exist. If step B shows a class that needs a product decision (a state only reachable by raw writes), stop and write it in the RESULT as a question for Program.
