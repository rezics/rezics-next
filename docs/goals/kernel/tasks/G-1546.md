## Outcome

Program's decision (G-1534 finding): `POST /v1/erasures` (`content-revision-erasure-v1`, `services/main/src/routes/erasures.ts`, `services/main/src/modules/erasure/`) tombstones only content revisions (`urn:rezics:content:revision:{uuid}`). Reads already honour `rv:ErasedRevision` on other kinds of revision, and tests need those states (for example `tests/qa/integration/g-506-target.test.ts` lines ~218, 248, 260 types by hand: an unpublished text-contribution draft revision without moving the published pin, a published contribution draft, a semantic component revision, a release revision, a Work head and a composition structure revision). **Build it as an extension of the ONE erasure operation:** every revision kind the reads already honour (text-contribution drafts, published contributions, semantic component, release, Work head, composition) gets the same tombstone with erasure epoch, receipt and sequence through `POST /v1/erasures`. Identity resolution (mapping a request's revision id to its owner and graph resource) is the ONLY per-kind part: no per-kind erasure policy, no second path, no new route. User-authored revisions must be erasable in any case (authority: the existing erasure authority rules; state who may erase each kind).

FIRST check whether the operator erasure campaign already resolves these kinds (`docs/operations/recovery.md` "Offline physical erasure campaign", `infra/jena/purge-tdb2.sh`, the purge campaign target resolver, `services/main/src/modules/erasure/graph.ts` / `reconcile.ts` / `replay-graph.ts`, `ErasurePolicy.java`): if it does, EXTEND THAT RESOLVER rather than adding one; say in your RESULT what exists.

Requirements: the response `targets` list names the new kinds (owner/kind/ref); replay, held replay and the restore reconciliation (`reconcile.ts`, `replay-graph.ts`) handle the new kinds the same way as content revisions (exact epoch, receipt, sequence); the purge campaign handles them (if it does not, say so and stop at a note: do not extend the offline script in this task); the reads that honour `rv:ErasedRevision` keep their behaviour. Tests: unit per kind for identity resolution (right owner, wrong owner refused, unknown id refused, already erased idempotent), Java tests if the native policy changes, an isolated integration test through the API: for each kind create the revision through its real route, erase it, assert the read answers as the reads honour (404 or hidden), and that the erasure record shows epoch, receipt and sequence, plus replay idempotency (same key).

This is the erasure contract, which Trust-ops owns: keep the diff small and readable; list the files you changed in your RESULT; Program sends it to Trust-ops before landing. The Java command module is held by another running native task (G-1542): if the extension needs a native (Java) change (for example `ErasurePolicy.java` accepting the new kinds), do the TypeScript side, write the exact Java change as `.temp/erasure-native.patch` in your worktree, and STOP on that part; report it so the manager sequences it after the native task.

Do not build: a new route, a per-kind policy, offline script changes, UI. Never weaken an authority check. Commit after each step.
