## Outcome

Contract C2, second slice. Launch's L4 (a Zone without a Realm whose home page
is a Content document; design record §8: pages are Content DocumentSnapshots
on the Blocks profile, reusing the draft, revision and publish machinery) is
blocked because Content admits only Work and Post targets:
`draft.ts` `assertCurrentTarget` (Work/Post or catalogue description),
`publish.ts` publication graph targets, `publish-admitted.ts` `canReadWork`,
and the exact-revision reads in `routes/content.ts`.

Lift those checks from fixed kinds to the **server-resolved target**: Content
accepts a target whose admitted type the server resolves, and asks that
target's owner authority, never the client's description of it. The first
new target is a Zone page.

- **Draft save** (language variants, draft CAS, exact revisions, unknown
  blocks kept as opaque payloads): authority is the Zone's `zone.edit`
  through trust-ops' G-1288 bridge (on `main` before you start; its handoff
  names the function). Do not call `requireZoneEditor` directly and do not
  write a second check.
- **Pin an exact page revision** under the same `zone.edit` authority. Binding
  it to the site publication's terminal graph receipt is Zone code and
  launch's; expose what launch needs to settle a pinned revision against that
  receipt, and do not edit `zone/**`.
- **Read and export exact revisions:** drafts under the editor bridge;
  published revisions through `readZonePublication`
  (`zone/publication.ts:23`) plus `discloseContent`
  (`disclosure/assembly.ts:10`). Which exact revisions a publication contains
  is launch's; read it through the function launch provides, or hand off
  if it does not exist yet.
- Work and Post behaviour does not change.

Do not rely on Composition's `resolveTargets` for Zones (`summaryBases.zone`
is null).

Not to build: no target-kind registry, plugin table or per-kind handler; no
new document version; no Zone-side publication changes.
