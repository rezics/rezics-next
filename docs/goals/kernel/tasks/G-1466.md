## Outcome

Trust-ops traced Main's nested pool checkout fault to `services/main/src/modules/library/backfill.ts:117` (a long-lived `content.connect()` attributed to the content projection worker's async context; Launch's G-1464 fixes that file with its own `AsyncResource`). Two second suspects in Kernel's area follow the same isolation pattern as `services/main/src/modules/notification/realtime.ts`: `services/content/src/projection-cursor.ts:34` (reached via `relay.ts:364`) and `services/content/src/core.ts:374` (via `relay.ts:365`).

First verify each with evidence: read how the pool-checkout hold is tracked (`services/main/src/infrastructure/pg-pool.ts`: `trackNestedCheckout`, `checkoutHolds`, `adoptHold` using `AsyncLocalStorage.enterWith`), then for each suspect decide whether a long-lived `connect()` made inside a worker's async context is inherited by that worker's later short checkouts of the same pool (a real nested checkout, logged as `main.database.nested-checkout`), with the exact call chain from `relay.ts`. Prove it with a failing unit test that sets `setNestedPoolCheckoutMode('throw')` and reproduces the nested checkout through the real relay entry (not a mock of the pool), for each suspect that is real.

Then fix each real one the way `notification/realtime.ts` does (the long-lived connection is created inside its own `AsyncResource`/detached async context so it is not a hold of the worker), without changing what the worker reads or writes. If a suspect is not a nested checkout, say so with the evidence and change nothing there. If `pg-pool.ts` itself needs a change, stop and report instead (it is shared).

Do not build: a new pooling abstraction, a lint rule, or changes in services/main outside what the suspects force.
