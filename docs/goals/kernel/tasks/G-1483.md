## Outcome

Launch's recipe-authoring journey on a base that contains the seek-progress and worker-tick changes (QA 20261008t165710-8e4ed0, in the G-1471 worktree) passes, nested faults fell from about 93 to 9, but the published recipe's "Explore the wiki" still says "The wiki could not be loaded" and the log no longer shows `statement-seek` relay retries. So something else fails the Work's Statements read. The list of the 9 remaining nested faults is in `.temp/ref/nested-holders-165710.txt` (staged into this worktree). Kernel owns two of them:

- `statement/publication-seek.ts:111` `transact`, nested under `statement/seek.ts:119` `capturePublicationBasis` (still nested after the tick-isolation change: this is a hold inside one request/tick, not a worker-context leak: `capturePublicationBasis` holds a pool client while `transact` checks out a second one from the same pool, or the reverse).
- `outbox/receipt-custody.ts:87` `withReceipt`, nested under `access/topology-control.ts:54` (the holder is Trust-ops' `controlTransaction`; the victim here is Kernel's `withReceipt`, which must not need a second checkout from a pool the caller already holds: make it use the caller's client when one is passed, or take its own connection from a pool that is not the held one; do not edit topology-control.ts). The other faults (alias registry `withRead`, `access/admission.ts` canReadAsBaselineMember/canReadScopedResource, `disclosure/read.ts`, `topology-control.ts`) are Trust-ops'; leave them and list them in your report.

Do, in order:
1. **Find what actually fails the read.** Reproduce with the real routes (isolated integration test through the API: publish a Work, then `GET /v1/resources/{id}/statements` and `/page`, with `REZICS_NESTED_POOL_CHECKOUT=throw` if the QA stack can take it, as the nested guard only logs by default and throws in test mode) and report the exact status and error of the Statements read, with evidence (response body, logged fault, code line). If the failure is not a nested checkout, say what it is and fix it only if it is in Statement seek/subject read; otherwise route it with evidence in your report.
2. **Fix the two Kernel sites** so they never check out a second connection from a pool the same call already holds (pass the client down, or restructure so the first is released first). Keep behaviour, bounds and the fence semantics identical.
3. **Test:** a failing-then-passing unit/owner test with `setNestedPoolCheckoutMode('throw')` for each of the two paths through their real entry points (real `boundedPool` or the repo's pool test double, not a mock that skips the guard).

Do not build: new pooling abstraction, any change to `pg-pool.ts`, or edits in `access/`, `disclosure/`, `address/`, `library/`, `event/`.
