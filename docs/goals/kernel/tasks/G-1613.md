## Outcome

Program ran the G-1600 resume on the shared stack (~08:36 UTC, dev stopped, Fuseki healthy, job file `.temp/stack/rezics-dev/content-rebuild.json` = `{"id":"08d89a2a-b1ac-49cf-884b-3a70c7a6a673"}`): `task search:rebuild` exited 1 after 16 s, only output `content-rebuild step: quarantined` then `rebuild command: timed out` (log `.temp/goal-program/search-rebuild3.log`). Two defects: (1) `rebuild command` is the step label of at least eight different reads in `services/main/src/modules/content-publication/rebuild.ts` (lines ~227, 245, 255, 282, 482, 491, 511, 548), so the line names neither the read nor the page, which G-1587 was meant to guarantee; (2) one of those reads exceeds Fuseki's 10 s query timeout on the real dataset: the resume path's new reads (`readContentRebuildProgress`, `readLatestOffline`, `readAdoptedQuarantineJob`, `readActivationGeneration`, `askContent('units'|'malformed')`, `isReceiptCommitted`). Suspects: reads that bind receipts by predicate and a `FILTER(STRSTARTS(STR(?receipt), ...))` over the whole receipts graph (millions of operation receipts) with `ORDER BY DESC(xsd:integer(?sequence))`, which scans the graph; keyed lookups by receipt IRI (`receipt('cleared', id)`, `receipt('activate', id)`) are fast.

1. REPRODUCE ON A COPY, per read, with timings. The dev dataset copy is the docker volume `kernel-g1584-fuseki` (22 GiB, taken before the first rebuild attempt, so its receipts graph has the real size; it is NOT in the post-attempt state: say so). Make YOUR OWN writable copy (`docker run --rm --network none --user 0:0 -v kernel-g1584-fuseki:/from:ro -v <yours>:/to --entrypoint sh <postgres image of infra/dev/compose.yaml> -ec 'cp -a /from/. /to/'`; delete it when done; 460 GiB free), start a throwaway Fuseki of the CURRENT pinned image (`infra/dev/compose.yaml`, no Main, a spare port) and time EVERY read of the resume path (the eight above plus the quarantine/clear/offline/replay/activate helpers) individually through `curl`/the module's `FusekiClient` (report ms and row counts). Report which read(s) exceed the 10 s query timeout (or the module's per-read budget) and the receipts-graph size.
2. FIX AT THE READ: every read in the resume path is keyed (receipt IRI known from the job id: `receipt('quarantine'|'cleared'|'offline'|'activate', id)`) or bounded by a keyset on an indexed leading term; none scans a graph by predicate. "Latest quarantine job" / "latest offline receipt" are replaced by lookups the CLI can key: the job id from the job file or `--job`; when no id is known, find it from a bounded structure (a control-graph pointer written by the quarantine command, or the stored quarantine receipt IRI listed in the job file) rather than scanning receipts; if neither exists for the observed shared-stack state (quarantine written by the OLD tool), derive the id from one bounded read that is KEYED (the job file's id, or a single known IRI prefix lookup using `rv:rebuildJob` as a bound object with LIMIT 1 and NO ORDER BY over the whole graph) and prove it under budget on the copy. Keep every refusal that protects a live index.
3. NAME EVERY READ. Replace the shared `rebuild command` label by one unique, stable label per read (`progress: anchor`, `progress: quarantine receipt`, `progress: cleared receipt`, `progress: content units`, `progress: malformed content`, `progress: index control`, `progress: offline receipt`, `progress: activation receipt`, `adopt: quarantine job`, `clear: page <n>`, ...). A timeout error carries `<label>: timed out after <ms>ms (budget <ms>ms)` and, for paged reads, the page ordinal. The CLI prints it as the exit line. A unit test (`content-rebuild-bounds.test.ts`) fails when two reads in `rebuild.ts` share a label or when a read lacks one (scan the source for `readContentRebuildStep('` literals and assert uniqueness).
4. PROVE ON THE COPY: with the fixed code, run the rebuild's resume READ phase (`readContentRebuildProgress` and the adoption read) against your Fuseki and show every read under 1 s (or its stated budget); then run the full `search:rebuild` resume against your copy, taking it through quarantine on the copy first with the module's own commands (so the copy reaches the observed shared-stack state: quarantined, anchor absent), and show it finishes. If a full rebuild on 22 GiB takes more than the shared stack's patience say how long. Report all numbers. Do NOT touch the shared stack or `kernel-g1584-fuseki`.
5. Update the operator note in `docs/operations/search-index.md` with the new step names. Commit after each step.
