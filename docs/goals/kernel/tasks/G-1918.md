## Outcome

Program's finding (2026-10-12, class A by the scale rule, URGENT: two shared-stack refreshes failed on it and Main was down): `services/main/src/modules/statement/seek.ts` line about 395 runs
`SELECT ?sequence ?batch WHERE {{ VALUES ?sequence {{ 10837 }} GRAPH <outbox> {{ ?batch a rv:OutboxBatch ; rv:dataEpoch "..." ; rv:sequence ?sequence }} }}`
which Fuseki evaluates TYPE-FIRST, so it visits EVERY outbox batch: measured on the dev dataset (10,837 batches) at 0.97 s warm and over 10 s right after a cold container restart under load, which is Fuseki's query limit (hence "Fuseki query returned 503", failing `dev:prepare --seek-only` and the refresh at align-model, 10.07 s and 10.66 s). With the sequence triple FIRST (`?batch rv:sequence 10837 . ?batch a rv:OutboxBatch ; rv:dataEpoch "..."`) the same lookup takes 0.045 s. The scan grows with the whole write history, in production source (the Statement seek), not only the dev tool.

Do: (1) rewrite that lookup so it starts from the sequence value (a pattern that binds the object `rv:sequence <n>` first, the type and epoch as filters after; no change of result shape or ordering semantics; check that `?sequence` must stay bound by VALUES for multiple sequences: with several values keep the per-value start); (2) AUDIT the other statements in `seek.ts` and its callers (and `git grep -n "a rv:OutboxBatch" services/main/src scripts`) for the same TYPE-FIRST shape where the subject is a VARIABLE and a sequence, epoch or identity is bound (patterns where the subject is a bound IRI are fine): fix the ones in this Goal's modules (statement/, work/, outbox/, rankings/, search/, feed/ read-side); list the others (Launch or Trust-ops areas) by file and line in your result without editing them; (3) test `services/main/tests/statement-seek-outbox-lookup.test.ts`: (a) a query-shape guard that the audited statements bind the sequence (or identity) before the type pattern (a pure string test over the built query), and (b) a Jena-level work check at two outbox sizes: an in-process or fake-graph count of visited batches (if there is an existing native test pattern for counted visits, such as `RealmSearchSeekTest`, use it from the Java side; if not, build a small counting fake of the Fuseki client that evaluates the pattern order) showing the visited batches do NOT grow between N and 16N. Say in your result which form you used. Do not change the outbox schema or any other behaviour.

Worktree discipline: relative paths only. QA discipline (Program): ONE goalctl test call; no reruns of passing files; fixtures grant access through grantFixtureAuthority. One session; commit and report. It must land BEFORE the next image build (each refresh restarts Fuseki cold and hits this again).
