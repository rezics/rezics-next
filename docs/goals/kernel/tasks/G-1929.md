## Outcome

`graphPositionAtRelay` in `services/main/src/modules/feed/source.ts` resolves a relay (Main stream) position to a graph sequence from `relay.delivered_event` and refuses (`Main feed graph reference cut is unavailable`) unless exactly one event row group exists there. A retained batch with `event_count = 0` is legal (docs/contracts/events-and-jobs.md: "including zero-event batches"): it has a `relay.delivered_batch` row and no event row, so the graph cut is not recorded anywhere and a feed cut that lands on it refuses; after a review revocation the whole projection refuses (launch's run: `.temp/ref/g1590-realm-ranking-final-handoff.md`, "Priority 3": after cut 5633 has 1 event, through cut 5634 has 0).

## Analysis already done (a Sol worker, read it and verify against the code, do not redo it)

`.temp/ref/G-1928-analysis.md`: a zero-event batch's graph sequence is unrecorded in the retained relay header. `readNextMainOutboxBatch` reads the physical header's `rv:sequence` into `graphSequence`, separately from the Main stream sequence; `retainBatch` discards it; `deliver` keeps it only inside event envelopes; `retainedEnvelopePosition` and `scanRelayCoverage` do not reconstruct it. Receipt custody admits exactly one event, so it cannot supply zero-event batches. Reader audit: only `feed/source.ts::graphPositionAtRelay` resolves a POSITION to a graph cut; the other `relay.delivered_event` readers scan events or reverse-map and already accept empty batches. `mainSequencesForGraphReferences` stays unchanged.

## The change (one representation, no compatibility layer)

1. `services/main/src/modules/outbox/relay.ts::retainBatch`: store the validated `batch.graphSequence` in the batch-header INSERT for EVERY batch and include it in the replay-equality check; a missing graph position is rejected, never replaced by the stream sequence. THIS FILE IS CLAIMED by Trust-ops' G-1900 and is NOT in your paths: Trust-ops approved a LOAN of `retainBatch` and its header INSERT / replay-equality check ONLY. Do not touch `scanRelayCoverage`, the cut-bounded prefix verifier near it, or anything else in that file; the hunk is about 15 lines. Whichever of us lands second rebases.
2. Additive relay migration `services/main/migrations/relay/024_batch_graph_sequence.sql` (relay is at 023 on main; G-1900 adds none): nullable positive-integral `graph_sequence` on the batch header, backfilled ONLY from complete retained envelopes that agree on one valid product graph position for that header. A header it cannot verify (a zero-event header has no envelope) stays NULL.
3. `feed/source.ts::graphPositionAtRelay` reads the header's graph cut: it refuses an absent header, a NULL cut (explicitly, with a message naming the repair), incomplete members, and envelope/header disagreement; it never substitutes the stream sequence. A retained zero-event batch with a cut resolves.
4. Repair of a NULL header (rows retained before this change, for example in restored fixtures): an owner command that, for a named data epoch and Main sequence, re-reads the exact retained physical header through the relay's own reader (`readNextMainOutboxBatch` / custody), verifies batch id, routing epoch and event count equal the retained header, and atomically fills the missing cut; unavailable source evidence refuses. Put it in an existing relay/operations entry point and run it through an existing Task entry; do NOT edit `Taskfile.yml` (claimed by another running task): if a new Task entry is unavoidable, say so and name it, and the manager adds it.
5. Contract: one sentence in `docs/contracts/events-and-jobs.md` where batch headers are described (the header carries the graph cut), and one line in the gated-reads report's last section that the case is resolved by this change.
