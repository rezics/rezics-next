## Outcome

Program's design (decision for this follow-up): integration stacks now restart Fuseki once after every maintenance dataset reset so Fuseki's startup `qualifyAtStartup` re-admits the Work-name exclusive writer, and keep their database on a project volume instead of tmpfs for that. About 475 of 591 integration files pay about 6 s each, roughly 48 minutes per regression run (run 5 spent 603 minutes on integration). Change: **re-admit the writer inside the process at the end of the maintenance dataset reset.** After the fresh graph is stored, run the same qualification that startup runs (`SearchDeltaJournal.qualifyAtStartup` and the Work-name admission it implies; read `CommandModule.java` around lines 81 to 95 and `DatasetResetPolicy.java`), in the process that already proved exclusivity at its start, admitted only through the maintenance capability. That is the same admission at a second moment, not a second writer path. The stacks then go back to tmpfs, and the restart and durable-volume code goes away.

Soundness first: before coding, read why G-1493 concluded that "calling `qualifyAtStartup` inside `reset()` returns false" (its report: `qualifyAtStartup` admits only when a delta-exclusive Fuseki process STARTS with a text generation already stored; `DatasetResetPolicy.reset()` deletes that generation and withdraws the writer). Establish what makes it return false there (a startup flag? the text generation missing at that instant? the process-level exclusivity proof?), and design the smallest honest way to re-qualify at the end of the reset: store the text generation first, then qualify, then admit, all inside the reset's write section; the exclusivity proof is the one the process made at start (it must not be re-derived or assumed on a process that never proved it: a non-exclusive Fuseki must still refuse). If there is a real soundness reason this cannot be done, write that reason as a comment at the admission, then cut the restart cost another way (for example one restart per stack instead of per file, or admission without a restart if the proof allows) and report before/after numbers.

Then remove the now-unneeded harness code: the post-reset Fuseki restart in `scripts/qa/cli.ts`/`scripts/qa/stack-startup.ts` (`admitIntegrationWorkScope` restart part), the durable-volume compose override (`infra/dev/compose.qa-work-scope.yaml`) and its flag, so stacks use tmpfs again. Keep the page-the-directory-to-complete step if it is still needed (it runs in Main's startup preparation; the harness may still need to wait for it).

Ratchet: add a unit test that fails if `rawSparqlIntegrationFiles` (in `scripts/qa/isolated-integration-files.ts`; grep for its exact name) gains an entry: that list may only shrink, since moving files onto the command API is the class fix for them.

Tests: Java unit tests for the in-process admission (admits after reset in a process that started exclusive; refuses on a process that did not; the Work-name directory can be prepared right after the reset); the two-file integration check (`work-name-scope-a-startup`, `work-name-scope-b-after-reset`) must pass with NO restart between files; measure the added time per reset (before: restart 5.6 s + prepare 0.47 s) and report it.

This is a native change: after `task gen`, build the image under the heavy slot (`task goal -- slot --heavy -- docker build -f infra/jena/Dockerfile -t <pin from compose.yaml> .`), report Maven totals and the new pin. Do NOT run `dev:refresh` (Program refreshes once after this and the bulk-commit change). Another native task (bulk composition commit in CommandService, queued) will rebase on your pin: keep your edits to CommandService.java minimal (this task should not need it).
