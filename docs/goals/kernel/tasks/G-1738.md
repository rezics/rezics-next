## Outcome

Suspicion from the G-1713 audit (`docs/goals/kernel/reports/G-1713-specification.md`, "Potential pre-existing mine dispatch defect"), static evidence only: a compiled filtered-mine Query input carries `actingSubject` and `scope: mine`, but `services/main/src/routes/query.ts` (lines about 141 to 143) sends it through `publicWorkRead`, whose nested request drops authorization (`services/main/src/modules/display-language/public-request.ts`), and `services/main/src/modules/work/read-session.ts` (about line 386) then rejects an acting subject without authentication. If that holds, a signed-in user's filtered "mine" list fails. REPRODUCER ONLY, no product change in this task: write `tests/qa/integration/query-filtered-mine-owner.test.ts` against the real API: a signed-in member with at least one Work in their own inventory (use the product's own commands to create it, as the neighbouring Query and discovery integration tests do; find the closest existing test with `grep -rl "scope: 'mine'\|scope:\"mine\"" tests/qa/integration services/main/tests`), then `POST /v1/query` with a concept filter and `scope: mine` as that member, and assert (1) status 200, (2) the member's own Work is in the items, (3) the same request as another signed-in member and anonymously does NOT return it (and answers the existing denial, not a 5xx), (4) a continuation page binds the same scope. Run it alone and report the result in the RESULT with the QA run id and the exact response of any failing step. If it passes, the suspicion is refuted: commit the test as a regression proof (it must stay green) and say so. If it fails, commit it red-by-design is NOT allowed on main: keep it on the branch, say so, and name the failing step and the two lines responsible; a repair brief follows. Class A if it fails (a function is incomplete).
