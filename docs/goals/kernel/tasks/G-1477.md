## Outcome

Launch (mail `launch-nested-holder-event-projection`, QA 20261008t145336-1b55cf, grouped list in `.temp/goal-launch/nested-holders-145336.txt`; copy it under `.temp/ref/` if unreadable) and Program (decision): with the nested-checkout faults now naming their holder, 32 faults on pool `access` in one journey trace to `services/main/src/modules/event/projection.ts:133` (`EventTemporalProjection.tick`: its `this.access.connect()` hold stays attached to the async context) and `statement/publication-seek.ts:104`. Every worker that ticks after it in the same async context faults as nested: `statement/seek.ts` projectOnce/coverage/capturePublicationBasis, `projectPublicationOnce`, `notification-producers/producer.ts`, `notification/store.ts`, `rights/counter-notice-worker.ts`, `safety-queue/retention.ts`, `horizon/lag.ts`. So Statement seek coverage can lag for this reason as well as the rollback G-1475 fixed, and notification producers lose ticks.

Program's rule: fix the class where workers are run. Every worker tick, whoever schedules it (interval loops, `runMainRelay` consumers, the Statement/Event/notification workers), runs in its own async resource via ONE wrapper, so a connection held in one tick can never be inherited by another worker in the same context. One wrapper (a small module such as `services/main/src/worker-tick.ts` exporting `runWorkerTick(name, fn)` built on `AsyncResource`/`AsyncLocalStorage` the way `notification/realtime.ts` isolates its long-lived connection and `infrastructure/pg-pool.ts` tracks holds: read both first), used by EVERY interval or relay worker; no per-site `AsyncResource`. Find every scheduling site (`grep -rn "setInterval\|setTimeout\|runMainRelay\|while (this.running\|StatementSeekWorker\|Worker(" services/main/src services/content/src`) and list them in your report with how each now goes through the wrapper. Also fix the two named holders so they stop attaching a hold to their caller's context (their tick's `connect()` is released or isolated within the tick).

Guard test (failing before, passing after): a tick that holds a pooled connection for its duration and a second worker that checks out the same pool both run cleanly with `setNestedPoolCheckoutMode('throw')` when scheduled through the wrapper in one process context; and a repository scan test that fails if a known scheduling primitive in services/main/src runs a worker body outside the wrapper (keep the scan narrow and documented in a comment; an allowlist of non-worker timers is fine).

Do not build: a scheduler framework, per-worker config, changes in `pg-pool.ts` semantics (report instead), or changes to what any worker reads or writes. Library backfill is fixed by Launch's G-1464: do not touch `services/main/src/modules/library/`.
