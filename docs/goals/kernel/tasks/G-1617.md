## Outcome

Program ran the resume on the shared stack (~11:04 UTC, G-1613 code, dev stopped, Fuseki healthy): exit 1 after 3 s, output `content-rebuild step: quarantined` then `activate: offline index evidence is absent` (log `.temp/goal-program/search-rebuild4.log`). It skipped clear, offline index and replay and went straight to activate. Reading the code (`scripts/operations/search-state.ts` `rebuildPublicContentSearch`, `services/main/src/modules/content-publication/rebuild.ts` `nextContentRebuildStep`): the job's replay cursor (Postgres `content.projection_checkpoint`, consumer `content-rebuild.<id>`) is already AT the cut (`replayStarted` and `atCut`), so the decision table says `activate`; but the offline evidence receipt (`readLatestOffline`, the cleared-family receipt with `rv:indexRebuildDigest`, written only by the G-1600 code) does not exist, because the interrupted attempt ran the OLD code, which never recorded it. State: quarantined, cleared once, an offline indexer pass of unknown validity, replay done up to the cut (units back in the graph through job-scoped projection receipts that cannot be inserted again), no activation. Program's rule: every state converges on rerun (G-1600's contract); "missing evidence" must mean "not yet indexed", not "refuse".

DESIGN (a decision, change it only with evidence): a job that has replayed past sequence 0 cannot be re-cleared and re-replayed under the SAME job id (its projection receipts exist). So when activation lacks offline evidence, the rebuild starts a FRESH JOB under a new id from the quarantined state:
1. Detect in the decision table: not activated, quarantine receipt present for this job, replay started, and no offline evidence for the current generation/sequence (`offlineDigest` null) -> a new typed outcome `{ restart: 'fresh-job' }` (not a refusal). The reason is logged as one fixed line.
2. `quarantinePublicContentSearch` accepts a NEW id while the anchor is already absent: if no activation receipt exists after the latest quarantine receipt (no job has completed), it writes a quarantine receipt for the new id WITHOUT deleting the anchor (condition: the anchor is absent; the cut is the current Content owner position, `content.ownerPosition()`), plus the profile command as today. If the anchor is present it behaves exactly as now. A job id that has an activation receipt is never adopted again.
3. The CLI (`scripts/operations/rebuild-content-search.ts`) on `restart: 'fresh-job'` generates a new uuid, rewrites the job file `.temp/stack/<stack>/content-rebuild.json`, prints `content-rebuild step: fresh job <uuid> (previous job <old> had no offline evidence)` and reruns the whole sequence once under the new id: clear (units present from the old replay are removed in bounded keyed pages), offline index, replay (new job-scoped receipts, new cursor row `content-rebuild.<newid>`), activate. A second `restart` in one invocation is a refusal naming both ids (no loop).
4. Writers stopped (the existing check) stays a precondition of every step.

PROOF (fault tier, real rebuild; no copy of the shared stack): extend `tests/qa/fault-recovery/search-rebuild-interrupted.test.ts` with the exact observed state: run the real rebuild, crash after replay, then DELETE the offline evidence receipt of that job (a graph write through the test's raw-update seam in the fault tier, as the file's existing seams do; the file may use the assembler's raw update) so cursor-at-cut + no evidence is reproduced; run the rebuild again: it finishes through a fresh job, the anchor is present, `deltaSince=-1` is available, typeahead answers the published text, and the units equal the Content population. Unit (`content-rebuild-resume.test.ts`): the decision table row (replayed, no evidence -> fresh job), the second-restart refusal, a job with an activation receipt is never adopted, an existing live anchor still takes the old quarantine path. Run them, report run ids; `content-rebuild.test.ts`, `content-search-rebuild.test.ts` stay green. Update `docs/operations/search-index.md`: the new step line and what it means. Commit after each step; the connection drops: commit small.
