## Outcome

`graphPositionAtRelay` in `services/main/src/modules/feed/source.ts` resolves a relay (Main stream) position to a graph sequence from `relay.delivered_event` and refuses (`Main feed graph reference cut is unavailable`) unless exactly one event row group exists at that sequence. A retained batch with `event_count = 0` is legal (docs/contracts/events-and-jobs.md: "including zero-event batches"): it has a `relay.delivered_batch` row and no event row. Launch's run (QA 20261011t232333-ad92f4, evidence in `.temp/ref/g1590-realm-ranking-final-handoff.md`, section "Priority 3") shows the feed `after` cut 5633 (1 event, binding present) and `through` cut 5634 (0 events, no binding) in epoch faa698ed-f444-49f7-b1f2-cd6a2ed43212; the refresh then throws and the whole projection refuses after a review revocation. The report `docs/goals/kernel/reports/gated-reads-design.md`, last section, names this case: a cut position is whole when its batch is retained; the graph sequence must come from the batch's own record, never from event rows only. The reverse lookup `mainSequencesForGraphReferences` needs event rows only and stays.

Your first job is analysis, in this order, and the answer decides the change:

1. What is a retained batch's graph sequence? Read `outbox/relay.ts` (`retainBatch`, `readNextMainOutboxBatch`, the custodied/native `graphSequence` versus graph-batch `sequence`, `retainedEnvelopePosition`, `deliver`, `scanRelayCoverage`) and `docs/contracts/events-and-jobs.md`. State, for a ZERO-EVENT batch, whether the graph sequence is equal to the stream sequence, derivable from custody, or unrecorded. The domains differ (a Main stream sequence is not a graph revision; launch measured graph 100 versus Main 3).
2. Fix the class, one representation per meaning, no compatibility layer: the position-to-graph-cut mapping must be stored where every retained batch has it (the batch header row for ALL batches, including zero-event ones), written by the same transaction that retains the batch, and read by `graphPositionAtRelay`. If that needs a relay-schema column, add ONE additive migration under `services/main/migrations/relay` (next free number; say which) with a backfill that derives the value from the retained event envelopes for event-bearing batches and refuses to guess for a zero-event batch it cannot derive (it then fails closed as unavailable, with the exact repair command named); if the value is already derivable without a migration, say how and do it without one. A retained zero-event batch must resolve to its own graph cut; an absent batch row, or event rows that disagree with the batch row, still refuse.
3. Check every other reader of `relay.delivered_event` by position for the same omission and list them (`grep delivered_event`: work/serial-projection.ts, feed/refresh.ts, feed/target-index.ts, event/source.ts, rankings/realm-threads.ts, recommendation/ranking.ts, notification-producers/producer.ts, discovery/source.ts, zone-browse/store.ts, erasure/custody.ts). Fix only those that resolve a POSITION to a cut the way feed does; for pure event scans a zero-event batch simply contributes nothing, say so in a sentence. Do not widen the change beyond that.

Proof (Main test, new file, real Postgres relay schema via the existing relay test harness the neighbouring `services/main/tests/` relay/feed tests use): an event-bearing batch then a zero-event batch retained in sequence; the feed cut `after` = the first, `through` = the second resolves to graph sequences without throwing and `feedReferences` over that range returns the same references as over the first position alone; an absent batch row refuses; disagreeing event rows refuse; a replay of the same retention is idempotent. If a migration was added: a retained-row backfill case.
