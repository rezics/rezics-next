## Outcome

Public search on the shared dev stack is down and a restart did not fix it. Facts (Program, my own reproduction, all on the live dev Fuseki `rezics-dev-fuseki-1`, image `rezics/fuseki:6.2.0-cmd0.5.39-2ac8356548f3`, dataset `rezics` in volume `rezics-dev_fuseki_data`, 22 GiB TDB2 plus a 3.7 MiB Lucene index last written 2026-10-07 13:52): `GET :3030/rezics/command` is healthy (instanceId valid, `textIndexUncertain` false, `publicSearchDeltaAvailable` true, both write epochs 0, no `rv:restoreHold`), the control graph names profile `search-index-cjk-bigram-v3` and generation `urn:rezics:text-index-generation:fd5c289a-e3fe-4a6e-b5fa-b183e31af7d9` at sequence 10312, but `GET /rezics/command?deltaSince=-1` answers `{"available":false}`, so Main's `assertPublicTextReady` throws `SearchIndexUnavailable('public text generation has no native qualification')` and typeahead answers 503. It worked until about 01:00 UTC on 2026-10-10 on the same process; after a restart at 01:05:10 it still answers false, and the Fuseki log carries no qualification or journal line either way.

Native path: `SearchDeltaJournal.qualifyAtStartup` (-> `qualify` -> `auditGeneration`) installs the baseline and `qualifiedProof` answers `available:false` when none exists or after `invalidate(data)`. `auditGeneration` returns null (and `qualify` invalidates, `recovery` retries with back-off) for ANY of: control position missing/held/no text generation, the public anchor absent, `CanonicalPolicy.auditRealmOwners` false, a public body document that differs from RDF (several `IllegalStateException`s), `TextIndexException`/`IOException`, or population != public MatchUnit count. All of them are silent.

Do, in order, committing after each step:
1. LOG THE REASON. Every `return null`/catch in `auditGeneration` and every `invalidate(data)` caller records a short fixed reason through the module's slf4j logger (see `CommitHalt` for the pattern) at WARN, with the subject IRI where the check names one and never document bodies: startup-audit failed: <reason> [subject]; journal invalidated: <reason> [caller]. A baseline installed logs one INFO line with epoch, generation, population and luceneGeneration. This is the permanent diagnostic; no behaviour change.
2. FIND THE CAUSE ON THE REAL DATASET. Build the image with step 1 (Maven suite must pass; `task goal -- slot --heavy -- docker build -f infra/jena/Dockerfile -t <tag> .`; tag from `task gen`), COPY the dev dataset (do NOT touch the running dev stack, it is the shared stack): `docker run --rm -v rezics-dev_fuseki_data:/src:ro -v <scratch-volume-or-dir>:/dst alpine cp -a /src/rezics /dst/` (about 22 GiB; 460 GiB are free; put it under `.temp/` or a named docker volume and delete it when done), start a throwaway container of your image on the copy (same entrypoint and environment the dev compose uses for the `fuseki` service: read `infra/dev/compose.yaml`; a different host port, no Main), read its startup log and `curl :<port>/rezics/command?deltaSince=-1`. Report the exact logged reason and subject.
3. FIX THE CAUSE in product code. Classes of cause and what is right: (a) a legitimate state the audit wrongly rejects (e.g. a document class or rank-metadata rule added after the dataset was written, an ordering or case issue in the Realm-owner audit): fix the audit, with a Java test that builds that dataset shape and expects qualification; (b) real drift between RDF and the Lucene index left by an earlier writer (e.g. a bypass or in-process writer that updated one and not the other): the startup path must repair or rebuild the index from RDF (the existing empty-index rebuild/`rebuild` command is the operator tool; if startup can detect drift, it should rebuild the Lucene index from the RDF public units once, bounded, and log it, instead of staying closed forever), and say which writer produced the drift and fix THAT writer if it is still live; (c) a bug in the journal replay (`proof`/`qualifiedProof` epoch/generation comparison after a restart). Do not weaken the audit to accept a document that differs from RDF.
4. TEST (Program's ask): `infra/jena/tests/search-journal-restart.test.ts` (QA/integration tier, real image, same shape as the other `infra/jena/tests/*.test.ts` that start the image): start Fuseki on a dataset with public text units and a qualified baseline, stop it WITHOUT a clean shutdown (kill -9 the container) and restart it on the same volume: after restart `GET /command?deltaSince=-1` is `available:true` within the startup bound and a typeahead-equivalent query sees the units. Add a second case for the cause you found in step 2 (a dataset shaped like the real one). Plus the Java unit for the audit rule you changed.
5. OPERATOR NOTE: if the real dataset cannot be repaired by startup alone, state in RESULT the exact operator command that brings search back on the shared stack now (rebuild command, parameters) and run it ONLY against your copy to prove it; the manager runs it on the shared stack.
Do not edit Main's TypeScript except to mirror a renamed reason (there should be none). Do not touch `ClaimStatementFoldPolicy` or the erasure files (other native tasks hold them; rebase conflicts on the Fuseki pin files are resolved by taking main's and regenerating).
