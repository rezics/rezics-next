## Outcome

G-1512 profiled one 16-operation composition change on the composed stack: about two-thirds of each change is ONE TDB2 commit (journal force), so a 10,000-chapter import projects to 800 to 1,000 s against the 450 s budget of `tests/qa/integration/g-1014-structure-cost.test.ts` (Program: the budget stays, the API must be faster; writes go through the API). Its proposal: admit `composition.change` items to the existing one-commit bulk writer in the command module (the writer that `catalogueBatch` uses: `CommandService.java`, `CommitHalt.commit`, groups of at most 64 Work-name owners), keeping the 16-operation cap per change, receipts, head CAS, validation and per-item cancellation. Read the profile first: the G-1512 worktree is gone, so re-measure quickly (see item 1).

Do, in order:
1. **Confirm the cost** on a 100-chapter import: seconds per change, and how much of it is the native commit (Server-Timing and `X-Rezics-Command-Work` on the command response; Fuseki log timings). Compare one change per commit against 16 changes in one commit by timing a native-level experiment through the command API (a scratch script), to confirm that a commit group is the lever (state the speed-up).
2. **Design the smallest bulk path:** a bulk composition write that carries up to N (<= 16 or the existing bulk limit, state it) independent `composition.change` items, validates each (same policy/CAS/SHACL as a single change), applies them in one TDB2 write transaction and one commit through `CommitHalt.commit`, and returns a per-item result (applied, conflict on head CAS, refused) with receipts per item. An item that fails validation or CAS must not roll back the others (applied items commit; failed items are reported) unless the transaction itself fails, in which case none commit and all are reported pending (idempotent retry by key). Items that depend on each other's head (two changes to the same composition) must either be sequenced inside the group with the head carried forward, or refused as a conflict: choose and justify; the importer sends one composition's changes in order, so supporting the same-composition sequence matters.
3. **Wire the importer:** `services/main/src/modules/work/catalogue-import.ts` (or the structure change client) uses the bulk path for sequences of changes to the same composition. Keep the single-change API unchanged and available.
4. **Tests:** Java unit tests for the bulk writer (commit once, per-item outcomes, CAS conflict does not roll back others, halt on commit failure goes through `CommitHalt`); a TS unit for the client; an isolated integration test through the API (100 and 1,012 chapters) with the before/after seconds. Then run `g-1014-structure-cost.test.ts` alone and report time at 1,000 chapters and the projection for 10,000.

This is a native change: after `task gen`, build the image under the heavy slot (`task goal -- slot --heavy -- docker build -f infra/jena/Dockerfile -t <pin> .`), report the Maven totals and the new pin; do NOT run `dev:refresh`. Do not weaken any safety property (receipts, CAS, validation, the 16-operation cap per change, per-item idempotency), do not raise a cap or the 450 s budget. If the design needs a decision beyond the above, stop and report options.
