## Outcome

Program's performance method (report `.temp/goal-program/audit/G-1633-perf-method.md`, row 3): a growth check cannot see a scan inside ONE query unless the native visit counters Jena already keeps reach the request profile. Today the Fuseki command module counts work in `CommandWork.count(name, n)` (for example `public_name_labels_visited`, `work_name_scope_links_visited`, `catalogue_name_values_visited`, `realm_owner_qualification_visits`) and answers it in the `X-Rezics-Command-Work` header (`CommandService.java`), but the telemetry whitelist `commandCounters` in `packages/observability/src/http-measurement.ts:29` names only the fixed write counters, so `fusekiCommandWork` drops every visit counter and the API request profile never shows them.

Do:
1. Decide the form in one place: either extend the whitelist with a bounded, data-driven rule (a name is exported when it matches `^[a-z_]+_(visited|visits|scanned|seeks)$` and the profile keeps at most 32 distinct names per request with a fixed numeric cap), or enumerate the existing names. Do not export free-form names (cardinality and private data). Say which and why in the commit message.
2. Make sure every visit counter the native query path keeps (search `CommandWork.count` for names ending `visited`, `visits`, `scanned`, `seeks`) is in the header for the read paths too (`RealmSearchSeek` is a read: check that its counters leave the module the same way the write counters do; if a read path does not set the header, set it there).
3. `services/main/src/infrastructure/fuseki.ts` passes the parsed counters to the request profile the way the command counters already go; `tests/qa/integration/support/query-cost-meter.ts` can read them by name.
4. Proof: `RealmSearchSeekTest` asserts the native counters of a seek at two sizes (existing assertions stay); one API profile test (integration) runs the same seek through the API and asserts the profile shows the SAME numbers; a unit test in `packages/observability/tests` for the whitelist rule (an unknown name and an over-cap name are dropped, a visit counter is kept).

Do not build: a second registry, new counters in Java, a growth check (Program lands it as a separate task), any change to production behaviour of the queries.
