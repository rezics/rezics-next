## Outcome

Kernel's decision on the g-1042 zone fetch (Program asked for ONE policy in the immutable-object or component read path, not a zone-only read-order rule). Finding (G-1541): zone-home, zone-presentation and zone-banners each pay an extra `404` GET because `readWorkComponentState` (work/history.ts) reads `semantic/work/sha256/<digest>` through `S3ImmutableObjects.get` (services/main/src/infrastructure/immutable-objects.ts), the object store 404s, and the reader falls back to the filesystem copy the zone create/configure path wrote. The object store stays AUTHORITATIVE (`services/main/tests/revision-read.test.ts` requires a corrupt object-store body to fail even when a valid local file exists). Do NOT add a read-order exception for Zones and do NOT edit `services/main/src/modules/zone/` (Launch's patch is withdrawn).

Build **a per-process cache of verified bytes, keyed by digest, in the immutable-object read layer** (one place; every reader benefits):
1. A hit returns the bytes with no store call; the first read of a digest still verifies (sha256 of the bytes equals the digest) and a body that fails verification is NEVER cached and still fails the read as today. Content addressed by digest never changes, so a cache hit needs no re-validation of freshness.
2. Where the read falls back to the verified local file after a store 404 (the current behaviour), the fallback bytes are verified against the digest and then cached too, so only the first read per digest per process pays the 404; every warm request pays none. State exactly what the fallback path is today (read the code) and keep its rules.
3. Safety (state each in a comment at the cache): (a) bounded memory: an LRU with a max entry count AND max total bytes (choose conservative defaults, for example 512 entries / 32 MiB, objects over a per-object limit are not cached) and a short TTL (for example 60 s) so a destroyed object cannot be served for long from a long-lived process; (b) erasure: the in-process erasure/destruction paths (find where objects are destroyed or purged: `services/main/src/modules/erasure/`, custody, replay-objects, `infra/jena/purge-tdb2.sh` is offline and out of scope) evict the digest from the cache; the cache is only reached after the caller has resolved a graph revision that is not tombstoned, which is why a cached copy of erased bytes is not reachable through an erased revision: say in your RESULT whether any reader reads an object by digest WITHOUT a graph gate (then it needs the TTL only) and list them; (c) the cache is per process (Main and the relay do not share it) and never holds anything that failed verification or was a partial/aborted read; (d) metrics: expose hit/miss counters (a function used by the tests, no new endpoint).
4. Tests: unit (`services/main/tests/immutable-object-cache.test.ts`): hit avoids a store call; a failed-verification body is not cached and the error is the same; fallback bytes cached after verification; LRU/byte bound evicts; TTL expiry refetches; eviction on erasure; concurrent first reads of one digest share one fetch (single-flight) if cheap. `revision-read.test.ts` stays green UNCHANGED (corrupt body fails). Then the integration cost file `tests/qa/integration/g-1042-community-cost-realmSize-surfaces.test.ts`: the zone cost assertions must hold on a warm request (the measurement should come after one warm-up request of the same surface, as the file's other surfaces do; if the file measures cold requests, add the warm-up and say so; caps are NOT raised). Run it alone before and after (`USER=edge LANG=C.UTF-8 LC_ALL=C.UTF-8 task goal -- test <path>`).

Never raise a cap, never weaken `revision-read.test.ts`. Commit after each step.
