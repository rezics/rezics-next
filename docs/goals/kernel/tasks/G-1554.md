## Outcome

G-1542 made native validation of a composition change constant (143 focuses and 1,144 quads at 10, 100 and 1,000 chapters; validation ~14 ms, native update ~22 ms). `tests/qa/integration/g-1014-structure-cost.test.ts` (100 + 1,000 + 10,000 chapter builds within 450 s) still fails: a quiet run reached 7,960 chapters in 429 s and then a batch returned HTTP 202 `reconciling` (a second run got a 503 at 8,312 under other QA load). The remaining time is CLIENT side in Main: a single insert costs ~210 ms with **15 graph queries** per change and a log-depth object tree (7 pages at 100 chapters, 13 at 1,000), and the planner cost grows with depth. Program decision: the budget stays (450 s); a slow write is an API defect; the cost of a change must touch a bounded neighbourhood.

Do:
1. **Profile one change's client path by query**: list the 15 graph queries (the SPARQL text names or counters in `X-Rezics-Command-Work`/Server-Timing, or a scratch counter in `FusekiClient`) with what each reads, and the object-tree reads and writes (pages read/written per change at 100 and 1,000 chapters). Say which are redundant (re-reading the head or manifest already known from the previous change in a sequence, reading a coverage already proven, per-change fences that could be per request), which grow with the structure, and which are needed.
2. **Remove or bound** what is redundant or grows, with the smallest change that keeps every safety property (CAS on the head, receipts, validation, policy checks, fences): for a sequence of changes to ONE composition in ONE request/import loop the head and the manifest root known from the previous change's receipt can seed the next change (carry the known state; the CAS still protects against concurrent writers); the object tree is log-depth, so pages read/written per change must be bounded by depth (say the numbers); a query that scans something proportional to the structure must become a seek. Say per removal which property it could affect and why it still holds.
3. **The HTTP 202 `reconciling` at ~8,000 chapters**: find out what makes a batch answer 202 (the command's deadline or a reconciliation after an unknown outcome) and why it appears with size; if it is a deadline that grows with the structure it is part of the same defect; if it is a legitimate "outcome unknown, retry with the same key" the import client must retry with the same key and the test's client must too (the production import client already?): say which and fix the client side, not the status.
4. **Re-measure** `g-1014-structure-cost.test.ts` alone (`USER=edge LANG=C.UTF-8 LC_ALL=C.UTF-8 task goal -- test tests/qa/integration/g-1014-structure-cost.test.ts`) after each step: report buildMs per scale and the total against 450 s, plus the per-change query count and tree pages at 100 and 1,000 (the tests/qa/integration/composition-change-cost.test.ts from G-1542 may be extended with a bound on graph queries and tree pages per change independent of size: add that assertion once the numbers are stable).

Do not edit the Java command module (a native task is sequenced separately; if the dominant cost proves native, stop and report numbers). Never raise a cap or the budget; never drop CAS, receipt or validation. Commit after each step (the session can drop).
