## Outcome

Launch reports (mail `launch` re G-1433, `services/main/src/modules/recipe/work-page.ts` around lines 219-253): the page loop allows one data read per call (`dataReads > 1` throws) and breaks as soon as it descends into a group, so a call returns at most one frame's children and ends at every section heading. A two-section, four-step recipe takes about four calls and its first page is only the "Cake" heading: every ordinary sectioned recipe opens nearly empty.

Change the loop to fill a page in depth-first order across frames until `RECIPE_WORK_PAGE_OCCURRENCES` (100) occurrences or a small constant number of composition reads per call, with the bound stated in one constant and comment (use the existing `RECIPE_WORK_PAGE_READ_BOUND` shape, e.g. 2 x maxDepth + 2 reads; update the constant, its comment and `cost-contract.md` together). A typical recipe is then one call; a very long or deep one still pages with constant cost per call. Keep the cursor format (it must still resume exactly where the page stopped, now possibly mid-section), the revision and servings pin, the MAC, the stale 409 and the per-page 1 MiB ceiling unchanged; `measures` stay on every page; record order and `parent` fields unchanged.

Tests: keep every existing assertion in `recipe-work-page.test.ts` and the integration test unless a number they pin is the old per-frame behaviour (then change only that number and say so in your report); add cases for: a two-section four-step recipe returns all occurrences in ONE call; a recipe with 10,010 occurrences in nested groups is still complete, ordered and every call stays within the read bound; the cursor resumes correctly when a page ends mid-section and when it ends exactly on a section boundary.

Do not build: any change to Structure reading, a second cursor format, caching. Do not edit apps/web (Launch removes its interim follow-up after this lands).
