## Outcome

Row 1 of the growth-check method: the VERDICT. In `tests/qa/support/work-profile.ts` (and a new `tests/qa/support/work-profile-verdict.ts` it imports) each measured operation DECLARES its dimension (the population axis it scales with: for example Works, occurrences, history length) and a COST CLASS f(n) from exactly: `1`, `1+log2(n)`, `n`, `n(1+log2(n))`. For every pair of scales (i, j) of the same operation the check requires, on EACH counter, `W(j) <= 1.20 x W(i) x f(nj)/f(ni)`. Counters: exchanges and bytes, SQL statements, Fuseki calls, object visits (native visits join when the native visit counters land: leave the counter list extensible, typed). A counter that is structurally ZERO stays zero (0 at every scale: pass; 0 at one scale and positive at another: fail). The 20 percent margin is FIXED in code and is never re-baselined to pass; absolute caps (the existing budgets) stay and are checked too. A failure writes a QA ARTIFACT (JSON beside the profile's existing artifacts) naming the operation, its owner file, the dimension, the scales, the counters, the expected ratio and the observed ratio, and fails the run with that path in the message.

Proof (unit tier, `tests/qa/unit/work-profile-verdict.test.ts`, no stack): the calibration PASSES for a constant operation and for a linear operation measured at 4/16/64; and FAILS for an injected linear-where-constant operation and an injected quadratic-where-linear one (assert the artifact content and the exact counter named); a structurally zero counter case; the margin constant is not configurable by callers (a test asserts the exported constant and that the verdict ignores any override); two scales equal; a single scale (no pair) is refused as "not a growth check".
