## Outcome

Launch L20b (Program: A, decided 2026-10-11: the recipe export KEEPS its 4,096 occurrence limit and names it in the API contract). Today `GET /v1/recipes/{id}/exports/schema-org` is declared `response: { 200: t.Any(), 413: problemResult(413), ... }` and the traversal helper `allOccurrences` in `services/main/src/routes/recipes.ts` (about line 162) throws a `CompositionConflict('recipe calculation exceeds 4096 occurrences')` at the 4,097th occurrence, so the typed `RecipeExportLimit` (413 `recipe_export_too_large`, handled at about line 114) is never reached for the export route. Do: (1) give `allOccurrences` the limit error as a parameter (the export route passes `RecipeExportLimit`; the scale and nutrition routes keep their own conflict answer unchanged); (2) replace `t.Any()` on the export 200 with the typed export envelope schema so the contract names it (profile `recipe-schema-org-export-v1`, structure, revision, the exported recipe members, `sourcePosition`, `cost`) and keep the declared 413 with its code, and say the limit (4,096) in the route's description; (3) regenerate the OpenAPI output (`task gen`) and keep `task web:typecheck` green (Launch's client consumes it).

Proof: extend the existing unit tests for the export helper (`grep -rl "exportRecipe" services/main/tests tests/qa`; create `services/main/tests/recipe-export.test.ts` only if none exists) and add `tests/qa/integration/recipe-export-limit.test.ts` through the API: a Recipe with exactly 4,096 occurrences exports with 200; with 4,097 answers 413 `recipe_export_too_large` (not a composition conflict); an exact `revision` read still works and returns that revision; a denied reader still gets the existing denial (hidden equals absent, no limit information leaks to a caller who cannot read the Recipe). Build the 4,096 fixture through the product's own import or edit commands in batches (the 10,000-chapter fixtures use the `large-tmpfs` resource class; follow `scripts/qa/resource-classes.ts`).
