## Outcome

Maintainer direction (via Program): nothing gets built for Bangumi. Bangumi is configuration of general REZICS features; the only Bangumi code is its dataset mapping in `scripts/datasets/bangumi.ts`. The rights module already exists (`services/main/src/modules/rights`, README, `docs/contracts/` rights and content-governance contracts): rights **material** (expressionKind fact / expression / media), **use assessment** (wiki_display, media_delivery, ...; exception fair_use), **obligations** (attribution, share_alike, change_indication, ...), and complaint decisions/restrictions that reuse Access governance cases, decisions and enforcement fences. An imported summary, an imported fact set and an imported cover are each a rights material with an assessment and obligations; a user's upload with the source they enter uses the same records; reads expose obligations for any source; an edit of share_alike material is a derivative that keeps the obligation by the general rule, for any licence; takedown = complaint -> Access governance decision/enforcement fence on the rights material, and source acquisition rechecks rights before fetching and before storing. The Work cover is the Work's existing image selection (`selectAdmittedAvatar` / the Use machinery, same scope as showcase art); if cover and avatar differ, the CoverSet in `docs/contracts/media.md` is built as the general media contract, without its own mark or fence.

This task is **phase 1: an audit only. Do not build or change anything in Main.** Deliver an audit (as your RESULT and also saved as `.temp/audit-bangumi-rights.md` in your worktree) that:

1. **Maps each need to the existing mechanism with file citations (path:line):**
   a. licence mark / attribution on imported text (summaries) and on imported fact sets, and how a read exposes the obligations for any source (which route returns them? for a Work's description and for Statements?);
   b. ShareAlike on edits: what happens today when a user edits an imported (share_alike) text natively: does the derivative keep the obligation by a general rule? If not, exactly where would the general rule live;
   c. a cover shown as "(c) rights holder, via source": how an imported or uploaded image becomes rights material (media expressionKind), how its attribution obligation (rights holder name, source, link) is stored and read, and how the Work's cover selection (avatar/Use, showcase art scope) relates to it; is the CoverSet needed at all for a single cover;
   d. takedown that survives re-import: complaint (`POST /v1/rights/complaints`) -> Access governance decision/enforcement fence on the rights material; what the fence blocks today (delivery? fetch? store? refresh?), what "source acquisition rechecks rights before fetching and before storing" means in the code (find the source acquisition path used by dataset imports and the catalogue import API) and whether it already consults the current assessment/fence;
   e. user-entered source: how a user-facing contribution/import tool records the source the user enters, using the same rights records.
2. **Lists real gaps** (each with the smallest GENERAL feature that would close it, never per source), and says which needs have no gap.
3. **Reviews what G-1513 put in Main** (`git show 857f41606` on the landed commit, or `git log --grep "Bangumi subject and character text"`) and states precisely, per hunk, which part duplicates the rights records and must be replaced: the CC BY-SA 3.0 constants, the `rv:source`/`rv:licence` literals on the Work description, the adaptation-note text, `statement/read.ts`, `work/read-header.ts`, `work/read-contract.ts`, `work/metadata-command.ts`, `work/catalogue-import.ts`; and what stays (Statement `rv:evidence` stays; `scripts/datasets/bangumi.ts` mapping stays).
4. Proposes the **rework plan** onto the rights records: ordered small tasks with files and tests, and what the Bangumi mapping must declare (material, assessment, obligations).

Read, do not edit. Do not run heavy test suites; reading code and running a few `bun test` files to confirm current behaviour is fine. No Claude/Grok engines.
