## Outcome

`tests/qa/integration/g-1014-structure-cost.test.ts` (100 + 1,000 + 10,000 chapter builds in 450 s) does not finish. Program's decision: the budget stays; writes go through the API; slow writes are an API defect. The profile (G-1512, then G-1515 on branch `goal/g-1515`, commits `032890caf` and `c87b13fb1`, kept for reference, NOT to be merged) established:
- One 16-operation composition change costs about 0.65 s on average at 1,000 chapters and about 1.1 s at larger sizes, inside a ~2.3-2.5 s native command at the largest measured: native `validation` about 1.0-1.2 s, graph `update` about 0.5 s, the journal commit only 5-14 ms. Grouping commits (the G-1515 bulk path) made 1,000 chapters only 9-16% faster: not the lever.
- Each 16-change native commit validates about **4,000 SHACL focus nodes** and reads about **4,200 current quads**: the work grows with the SIZE OF THE STRUCTURE, not with the change. That violates the asymptotic-scale rule (every operation touches a bounded neighbourhood) and makes a 10,000-chapter import quadratic.

Fix it where it lives, in the native command module: **a composition change validates only the nodes it edits and the neighbours whose constraints it can change, and reads only those quads.** Do:
1. **Locate and measure.** Find the native path that validates a composition change (`CommandService.java` composition/structure command, `HeadCasPolicy`, the SHACL validation call and the focus selection; `services/main/src/modules/structure/change.ts` sends the change; read how the shapes in `model/definitions` for the Composition/Structure profiles are authored). Use the existing counters (`X-Rezics-Command-Work`, `Server-Timing`) to report, for a 16-operation change at 100 / 1,000 chapters: focus nodes validated, quads read by validation, validation ms, update ms. Expected: it grows with the structure.
2. **Design the bounded validation.** For each constraint the validated shapes impose (cardinalities, order keys, parent/child, depth, role rules, uniqueness...), say whether its violation can be caused by an edit only at the edited node(s) plus a bounded neighbourhood (parent, adjacent siblings, the head record), or needs a global view. Build the focus set from the change's edited nodes plus exactly that neighbourhood (the "affected focus" rule), and validate with the same shapes (do not weaken or fork the shapes: one source of constraints). A constraint that truly needs a global view (for example a total count bound) must be checked from an incrementally maintained value (a counted root, `STRUCTURE_LIMITS`), not by rescanning. Document the rule in a comment at the focus selection and in `infra/jena/command-module` README or the contract doc where the Structure commands are described (short).
3. **Prove equivalence.** Java tests: for generated structures of size 10, 100 and 1,000 (and malformed variants: duplicate order key between neighbours, wrong parent role, depth overflow, orphaned child, wrong head CAS, a violation placed in an UNEDITED node that the old full validation would have caught), the bounded validation accepts and refuses exactly what full validation does for changes that are made through the command (a violation not caused by the change is not the change's responsibility: say how the old behaviour treated pre-existing violations and keep that behaviour or state the difference explicitly), and a test that the focus count and quads read are the same at 100 and 1,000 chapters (bounded by a constant): assert it.
4. **Then the update:** report the ~0.5 s update's cost sources (is its SPARQL `WHERE` scanning the structure? an obvious bounded fix?), fix it only if it is the same class and small; otherwise report.
5. **Re-measure** `g-1014-structure-cost.test.ts` alone (`USER=edge LANG=C.UTF-8 LC_ALL=C.UTF-8 task goal -- test tests/qa/integration/g-1014-structure-cost.test.ts`): report buildMs per scale and the total against 450 s. If it still does not fit, say which phase now dominates (client planning in `structure/change.ts` was named as most of the 1,000-chapter wall clock: if so, report what the client does per change that grows with the structure, and fix it in a SEPARATE commit if small).

Native change: after `task gen` rebuild the image under the heavy slot (`task goal -- slot --heavy -- docker build -f infra/jena/Dockerfile -t <pin> .`), report Maven totals and the new pin; commit the generated pin files; do NOT run `dev:refresh`. Never raise a cap or the budget, never weaken a shape or a policy check, never drop CAS/receipt/validation. Commit after each step (the Cursor session can drop).
