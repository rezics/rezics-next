## Outcome

Program asked for the remedy of the idle public search timeouts to be briefed from the shared stack's Main diagnostics. Evidence read at 19:25 UTC (`task aspire -- logs main`): four `worker_fault` events `main.route.search_index_unavailable`, `SearchRequestTimedOut`, code `public_search_request_exceeded_w`, at 18:47:01 to 18:47:05 UTC, and NO `public-search-timeout` event with the bounded call diagnostics (the Main change 137ae2c86 and the native phase of b1963a04b are live on that stack since 17:19 UTC). The reason is in code: `logSearchFailure` in `services/main/src/routes/search.ts` (about line 80) is called only on the structured `query` and `query-page` routes, and the diagnostics budget (`createFusekiReadDiagnostics`, `search-readiness.ts` about line 86) is only opened on that path; `GET /v1/search/typeahead` (about line 258), the route that timed out on the shared stack, opens no diagnostics and logs only the generic worker fault. So the evidence the diagnostics were built to give is missing exactly where the timeouts happen.

Do: give the typeahead route (and any other public search route that can answer `SearchRequestTimedOut` without diagnostics: check `services/main/src/routes/search.ts` and the Work search routes) the SAME bounded call diagnostics: open the diagnostics budget around its Fuseki reads (the same bounds: 8 history, 8 active, redacted, no query text, no prefix), carry them on the thrown `SearchRequestTimedOut`, log the `public-search-timeout` event with `route: 'typeahead'` (extend the route union) and the active native phase if the budget carries it (the native side reports the phase; read how the query route consumes it, `x-rezics-search-budget-ms` and `PublicSearchPhaseEvidence`). The prefix must never be logged. Keep the response (503 problem) exactly as it is. Prove at the unit tier in `tests/qa/unit/search-budgets.test.ts`: a typeahead request that exceeds its deadline against a stalled fake Fuseki logs one bounded event with the active call family and phase, no prefix, and the 503 body is unchanged; plus the cap on history and active entries. No integration run needed.

Also report in your result the typeahead call sequence from the code (the Fuseki call families in order and their budgets), because the remedy (is the typeahead's work proportional to the matched population or to the page?) is decided from that, and say whether `querySearchFields(..., true)` reads more than the page it returns.
