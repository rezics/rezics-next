## Outcome

Launch's board contract (mail `launch` to kernel, 2026-10-11, K39), to be specified over the classification capability as it stands in the tree (`services/main/src/modules/classification/*`, `docs/contracts/classification.md`, `docs/contracts/context.md`):
- A board is a Concept in the Realm's own board scheme, edited through the Realm's governance settings; no board tables.
- A thread (root reply) has zero or more board tags: Statements `thread -> board` in the Realm's Context, admitted and accepted through the shared classification capability. The author proposes tags when posting; members with the classify permission add or remove; moderators accept or reject.
- At most one primary board per Realm and thread, a separate Statement that must name one of the thread's accepted tags; moderators set or clear it; it never moves ownership or placement.
- Tags are per Realm Context (a thread placed in another Realm carries that Realm's tags only).
- Reads, bounded and keyset-paged: (a) the Realm's board list (cap 64); (b) the Realm's threads filtered by one board (any tag, or primary only) in the Realm's existing orders `best`, `new`, `top` (see `services/main/src/modules/realm-reply/thread-store.ts`; the thread list reads Postgres rows with keyset keys); (c) a thread card's accepted tags and primary board (cap 8) read with the card. Hidden equals absent: a filter on an invisible board answers 404 and writes nothing.

Kernel's first reading of what does NOT fit as it stands; confirm or correct each with file and line, then specify: (1) `classification/proposition.ts` creates schemes and concepts only in the GLOBAL Context (`GLOBAL_CLASSIFICATION_CONTEXT`); a Realm-owned scheme with its governance authority does not exist (there is a Realm classification Context in `classification/context.ts`); (2) whether a thread (a realm reply root) is an admissible subject of a classification Statement and decision; (3) the primary-board invariant (object is an accepted tag of the same subject in the same Context; at most one per thread and Realm) is not a plain Statement, it needs a guarded command; (4) read (b): the thread list is a Postgres keyset seek over `access.realm_reply` rows with rank keys, tags live in the graph; a filter by board needs one projection (realm, board, placement with the rank keys) fed from accepted-tag events through the outbox, otherwise the filter scans the ranking order and is unbounded; with at most 8 tags per thread the write cost is bounded.

Specify, as slices each fitting one Luna session at `max`: the kernel part (Realm-owned scheme and concept, the tag and primary Statement kinds with their admission and acceptance, the guarded primary command, the accepted-tag outbox event) and the part that is realm-reply's (projection table and reads a, b, c, in Launch's files), with the order, the tests that prove each slice, the acceptance IDs, which slice needs the native image, what needs Trust-ops' admission or a platform capability exposure, and which part Launch can build against a stubbed read first.
