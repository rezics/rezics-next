## Outcome

Main produces the width renditions that
[showcase art](../../../contracts/media.md#showcase-art) needs, and reads
return them as `srcset` candidates. Today `transform_job` and
`representation.kind = 'rendition'` exist but nothing produces renditions, and
no read offers more than the original.

1. **Request.** A function the media owner calls for an exact Use queues jobs
   for its crop at a fixed width ladder, in AVIF and WebP, never wider than the
   cropped source. `(source, profile, crop)` stays unique, so asking twice
   queues nothing new. Later tasks call it when showcase art and Zone slide art
   are selected; call it nowhere yet except tests.
2. **Executor.** A worker in Main that leases rendition jobs as
   `media-screen/worker.ts` leases screening jobs, and runs each transform in a
   bounded child process as `classifier-process.ts` does (pixel, byte and time
   limits, one still frame, `sharp.cache(false)`). It applies the Use's
   `xywh=percent:` crop to oriented pixels, resizes without upscaling, keeps the
   alpha channel (logos and cutouts need it), stores the bytes under the
   asset's object prefix and settles the job with a `rendition` representation.
   A rendition is as public, screened and erasable as its source: it never
   outlives the source's availability, suppression or erasure.
3. **Read.** A batch read that, for the Uses a caller resolved, returns the
   available renditions as `{ url, width, height, type }` candidates, with no
   extra query per Use. Bytes go through the existing representation bytes
   route and its access rules.
4. Update `services/main/src/modules/media/README.md` with the rendition
   lifecycle; delete what code now states.

Smallest change: reuse the job, lease, representation and object owners that
exist. Do not build on-demand transforms, URL parameters for sizes, a CDN or
Cloudflare Images, a new service process or a general image API.
