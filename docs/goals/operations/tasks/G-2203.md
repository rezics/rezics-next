## Outcome

A fault-recovery drill reaches its first step. In the regression run of 2026-10-13 on `main` six files stop before the drill, on the Fuseki container the drill's support starts (D016, D075 and D109 in `.temp/ref/regression-operations.md`; the clusters and file lines are in `.temp/ref/regression-disposition.md` under those codes).

1. D109: `tests/qa/fault-recovery/comment-source-erasure.test.ts` compares against an old Fuseki image tag written into the test. The tag is content-addressed and derived by `scripts/dev/fuseki-image.ts` (`docs/development/toolchain.md`, the Fuseki entry); the test takes the tag from there.
2. D016: the disposable Fuseki copies of the physical-erasure drills do not become ready (`Fuseki at http://<ip>:<port>/rezics/ did not become ready`; `erasure-custody-restore.test.ts:194`, `erasure-graph-purge.test.ts:108` and two more). Find why from the container's own log: its start, and whether the command module it keeps is compatible with the image. Fix the support, not each test.
3. D075: `search-ops-generation.test.ts:70` loses its Fuseki container before the explicit restart (`Fuseki container is unavailable before start`).

State the cause of each in the handoff with the log line that shows it. A cause in the erasure service or in an API contract is not fixed here: hand off `partial` naming it. Do not build: a change under `services/`, a retry that hides a container that died, a drill's assertion made weaker.

D108 is a separate fixture-evidence cause and gets a separate brief.
