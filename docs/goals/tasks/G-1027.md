## Outcome

The maintainer's priority (2026-10-03): the APIs' own performance matters most,
and complex search is the place where an outstanding performance problem is
most likely. Search here means the unified Query behind the header search and
Discover (type facet, text, topic include and exclude chips, other Facets,
sorts, keyset continuation; G-939), typeahead, Work search and Discover's
sections. [Search](../../contracts/search.md) and
[recommendations](../../contracts/recommendations.md) record the ranking
decisions: measure against them; research only what they leave open (for
example relevance across types and languages on one page).

Start now with what exists (`scripts/load/search-probe.ts`, the Fuseki meter in
`scripts/load/measurement.ts`, Main's OpenTelemetry spans) and adopt G-1024's
API work profile and Fuseki plan helper when they land in this worktree.

Build an adversarial query matrix and measure each cell at three corpus scales:
common and rare terms, CJK and mixed-script text, no text; one type and All;
1, 3 and 8 included topics, excluded topics, include plus exclude; selective and
unselective Facet combinations; every sort; continuation pages 1, 10 and 50;
anonymous and signed in (disclosure and private admission). For each cell
record Fuseki requests, engine time and bytes, PostgreSQL statements, latency,
candidates examined versus returned, and correctness. Find every cell whose
work grows with unrelated corpus, history or vocabulary, or that examines far
more candidates than it returns (negations, low-selectivity intersections,
sorts that cannot use an index, deep pages), and fix it by query plan, index or
data layout. A bounded partial result with an honest "at least" count is
acceptable only where the contract says so.

## Method

Use G-1024's API work profiles (`tests/qa/support/work-profile*.ts`, Fuseki
engine time and plans, the scale recipe; read `docs/testing/complexity.md` first).

1. **Model.** Write down the cost model each request on this surface should
   have, from the owner's cost contract, code comments and docs: round trips by
   kind and how each grows with every dimension (unrelated corpus, follows,
   memberships, history, page size, viewer kind). Where no contract exists,
   write it beside the owner.
2. **Measure.** Profile the APIs at the three scales, one dimension at a
   time, cold and warm, anonymous and signed in where both apply. The APIs'
   own cost comes first (maintainer, 2026-10-03); look at a page's fan-out
   only after the APIs meet their models.
3. **Compare and fix.** Report every gap between model and measurement (work
   that grows with unrelated data, N+1 hydration, repeated Access or session
   checks, duplicate reads between server components, rescans of completed
   prefixes) and fix it by algorithm and data layout, never by a bigger budget,
   a timeout or a cache that hides growth
   ([perf by algorithm](../../storage/workload-budgets.md#complexity-contracts)).
4. **Algorithm.** Where an owner doc records a decision with research for the
   ranking or selection algorithm, keep it and measure against it. Where none
   exists, research current best practice and published work, decide in the
   owner doc with sources, and implement it.
5. **Guard.** Encode each cost contract as a test with the profile assertions
   so a regression fails, and put a before/after table in your handoff.
