## Outcome

The browser half of G-520 and G-521. A new user comes back from Accounts to
an onboarding screen with an empty, required public-name field ("shown on your
profile and contributions"). No name, email or other Account data is filled in.
Nothing public exists until they submit. The identity picker lists every Agent
from `GET /v1/me/agents` with its kind and localized name. Identity selection,
consent recovery and the callback's error pages speak all eight UI locales. A
failed sign-in says what actually failed.

## Approach

- Callback: `public_name_required` → onboarding. Only `error=access_denied`
  goes to consent recovery; other callback errors get a general sign-in failure
  with a retry.
- Onboarding renders without calling onboarding when no Person exists. The
  finish route posts the typed name, then the handle. Handle suggestions come
  from the typed name, never from Account data.
- The picker uses the new list, shows kind (person, pen name, organization,
  service) and sets `lang`/`dir` from each label.
- `identity/select`: use `isUiLocale`, and derive the idempotency key from the
  form's expected revision so a browser retry replays.
- `messages.ts`: load all eight catalogs, so the consent page and profile
  settings stop falling back to English.
- Flip `onboarding-journey.e2e.ts:92,120`, which currently asserts the Account
  name is shown. Fix the stale "Continue to home" step in
  `first-party-signup.e2e.ts`.

Note (manager): G-522 is still in review and owns `apps/accounts/tests/first-party-signup.e2e.ts`; leave that file alone and state in the handoff which of its onboarding steps must change. Read the merged G-520/G-521 code (commits 209944b5, 810105c8) for the API shapes; discovery requires the `agent:create` scope.

## Do not build

No client-side eligibility rules, name suggestions from Account data or new
settings screens (G-524 owns the identities settings). No task-profile default
UI.
