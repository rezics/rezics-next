## Outcome

G-394 found that `GET /v1/works/:id/also-enjoyed` (G-381) answers `422
work_read_budget_exceeded` or `503` while the graph sequence is advancing,
so the Work page's "Readers also enjoyed" row vanishes intermittently. With
the graph still, limits 6–20 answer in about 0.25 s. On a live site the graph
is always moving; the read must not depend on it standing still.

Find out why a moving graph costs this read its budget: re-reading on each
sequence change, a fence that restarts, per-candidate reads that multiply
on retry. Make the read answer from one consistent position within its
budget:
- pin a position once;
- or answer from the derived co-reader generation, with fallbacks read at
  that pinned position;
- and report staleness honestly instead of failing.

Keep the privacy rules and the exclusions.

Add a test that advances the graph during the read (as other read-stability
tests do; see `tests/qa/integration/read-stability.test.ts`) and asserts a
200 within budget.

## Verify

On the shared stack, request the read for Pride and Prejudice and 雨夜书店
ten times while a `task dev:seed` replay is running, and show every call
answering 200. Use only the backend; no web dev servers.
