## Outcome

The dev AppHost now runs Main's outbox relay (G-260), but in an isolated stack
the relay stopped at batch 1 while the demo seed ran (32 Works created, 0
Realms completed). Many new command families landed today (Work reads and
metadata, Agent profiles and credits, Realm public profiles, Realm submissions,
baseline member permissions, session Agent, discovery projection). Likely some
new outbox event kind has no handler or a mapping throws, which blocks the
ordered relay.

1. Reproduce in `task dev -- --backend` in your worktree with the demo seed
   (`bun scripts/dev/seed/cli.ts`; the seed is claimed by G-265, so run a temporary copy under your worktree `.temp/` pointed at your stack, and propose making it accept the target stack from
   the checkout's environment or a `--stack` option instead of assuming the
   shared stack), read the relay logs, and find every failing event kind.
2. Fix the handlers/mappings at their owners (owner files are outside your claim: run `goalctl owner <file>`; unclaimed files may be changed minimally and listed; realm-reply and publication are claimed by G-265, so hand those off) (see
   `docs/implementation/api-and-events.md#owner-extension-points` for how
   handlers are discovered). A relay must never wedge on one event: unknown or
   poisoned events must be recorded and surfaced (dead-letter with a clear
   reason and a metric/log), not block every later event — if the current
   design blocks by intent for ordering reasons, keep ordering per partition
   but make the failure loud and diagnosable, and say so in the handoff.
3. Add a unit test that every outbox event kind any owner can emit has a
   registered handler (a static inventory check), so a new family cannot land
   without one.
4. Rerun the seed until it completes (Works, Realms, contributions, ratings,
   collections) and report the counts.
