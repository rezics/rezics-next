## Outcome

The main site's reader needs a Work's contents (chapter list of the selected version and language) and chapter bodies with previous/next, reusing composition pages, exact Content and progress APIs. Define the Work-to-composition selection.

## Read first

- `docs/plan/read-api-design.md` (the read-side design from G-212): the
  shared read contract (cursor envelope, byte budgets, disclosure), the Work
  template, and your row under "Dispatch remaining families", which gives your
  API, dependencies and the cost/disclosure contract to implement.
- The template itself: `services/main/src/modules/work/read-contract.ts`,
  `services/main/src/routes/work-reads.ts`, `services/main/tests/work-read*.ts`.
  Follow its structure, naming, schema style, OpenAPI security export and test
  style instead of inventing a new one.
- `docs/plan/frontend.md` for how the main site consumes these reads.

## Deliver

Typed GET routes registered as the worker protocol describes (one import and
one `.use()` line in the last plugin group of `services/main/src/app.ts`),
owner reads with the stated cost contract and complexity bound, disclosure
rules, and unit plus integration tests covering public, private, erased,
missing, pagination, scope and stale cases. Confirm the routes type-check in a
web-style `treaty<MainApp>` consumer. Register integration tests in the typed
QA declarations (`scripts/qa/cases/*.ts`) if that is how the template did it.

You may take the human role: if the design is wrong for your family, fix the
design row in the same change and explain why.

- `task main:typecheck`; `node_modules/.bin/biome lint services/main/src`;
  type-aware oxlint on your directories

- `bun scripts/goal/goalctl.ts test --affected --list`; list tests outside
  your claim in the handoff
