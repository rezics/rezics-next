## Outcome

REZICS gets its Accounts site: a new app `apps/accounts` in the spirit of
Google Account (accounts.google.com + myaccount.google.com), kept simple
because few people use it early on. Read `docs/plan/frontend.md#accounts-site`
for the decision: a separate app on the Account origin that hosts sign-in,
sign-up, recovery and OAuth consent for every REZICS product, plus the account
centre, and later the operator admin panel (a separate task).

Today the Account service (`services/account`, Elysia + Better Auth 1.7.5 as
OAuth 2.1/OIDC provider on :3002) is JSON only; its `oauthProvider` config
points `loginPage: '/sign-in'` and `consentPage: '/consent'` at pages nobody
hosts, and the web app signs in through its own proxy, so the Account session
cookie lands on the web origin.

## Deliver

1. **App and origin.** `apps/accounts` on the same stack as `apps/web`
   (vinext App Router on Vite for Cloudflare Workers, React 19, Tailwind 4,
   `@rezics/ui` with the Rezics Aura theme, envalid config, native-i18n with
   per-feature `en`/`zh-CN` catalogs; copy the web app's patterns, do not
   import from it). It is the public Account origin: it proxies
   `/api/auth/*`, `/api/account/*`, `/oauth2/*` and `/.well-known/*` to the
   Account service, so Better Auth's cookie is first-party to it. In
   `scripts/dev/config.ts` point `ACCOUNT_BASE_URL`, `ACCOUNT_ISSUER` and the
   web app's `ACCOUNT_ORIGIN` at the Accounts app while Main keeps fetching
   JWKS and introspection from the service directly; keep QA stacks working.
   Add it to the Aspire AppHost and `task dev` on fixed port 3004 in the main
   checkout (random in worktrees), and to `task urls`. Add the workspace to the
   root `package.json`.
2. **Sign-in flows** (centered single-column card, Google style: identifier
   first, then password; clear errors that never reveal whether an account
   exists): sign in, create account, forgot password and reset (the Account
   API for email flows is being built in parallel by G-205; call Better Auth's
   standard endpoints and show a friendly "not available yet" state if they
   are missing), email verification landing, and the OAuth continuation
   (after sign-in, return to the pending `/oauth2/authorize` request).
3. **Consent** `/consent`: shows the app name, the signed-in account with a
   "not you?" switch, requested scopes in plain language grouped by what they
   allow, and Allow/Deny. G-205 is replacing the stubbed consent endpoint;
   build against Better Auth's oauth-provider consent API and adapt to what
   exists.
4. **Account centre**, signed in: left navigation on desktop, tabs on phones.
   - **Home**: greeting with avatar and name, cards for "Security checkup"
     (verified email, sign-in methods, sessions), "Connected apps" and
     "Personal info" with direct links.
   - **Personal info**: name, avatar placeholder, email (change with
     verification), language preference.
   - **Security**: password change, sign-in methods (passkeys and 2FA appear
     when G-205 lands; show them as "coming soon" until then), your devices
     (sessions with device, last active, this-device marker, sign out one or
     all others), recent security activity (placeholder until G-205's API).
   - **Connected apps**: apps with access and revoke (installations API
     exists; the user list arrives with G-205).
   - **Data & privacy**: delete account with a typed confirmation and clear
     consequences (uses the existing delete-user flow when enabled).
   Every page has loading, empty, error and signed-out states.
5. **Web integration.** The web app's sign-in should become a redirect into
   the OAuth flow that lands on the Accounts site. The web session task G-203
   owns `apps/web/app/sign-in/**` and `app/auth/**`; do not edit them. In the
   handoff, state exactly what the web app must change.
6. **Stories and tests.** Stories for every page state (light, dark, phone,
   zh-CN) with play tests; unit tests for the proxy and config; a Playwright
   e2e for sign-up → sign-in → account centre → sign out, and for the web OAuth
   round trip through `/sign-in` and `/consent` if the dev client can be
   switched to require consent.
