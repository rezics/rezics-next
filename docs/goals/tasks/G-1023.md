## Outcome

Read [durable addresses](../../product/urls-and-seo.md#durable-addresses) as
revised on 2026-10-03: "alias" names the chosen, unique, optional key (a handle
is an Agent's or Space's alias; a Work address and a Zone route title are
aliases too), "readable suffix" names the derived words after an ID, and the
registry keeps one stored form per alias. Make the code say the same:

1. **Contracts.** `canonical.slugSource` becomes `canonical.suffixSource`; the
   `name-write-v1` receipt becomes an alias receipt without `display`; scope
   policies `name`/`id` become `alias`/`id`; problem codes and messages say
   alias (UI copy keeps "handle" for people and communities and "address" for
   Works, as the doc says). Pre-launch, so no compatibility shims; regenerate
   contracts with `task gen` and update every caller.
2. **Code.** `NameRegistry`, `NameRow`, `NameScope`, `normalizeAddressName`,
   `deriveAddressSlug` and their files take the alias and suffix names.
3. **Storage.** Migration 1029 renames the Access `name_*` tables and columns to
   their alias names and drops `display` from the registry and history,
   rewriting the constraints that mention it; idempotent and tested on a
   restored dataset.
4. **Docs.** Other docs that use "name" for the chosen key or "slug" follow the
   revised vocabulary (`task docs:check`).

Behaviour does not change except that nothing returns `display`. Tests outside your claim that use the old names follow `goalctl owner`. Run the
address unit, integration and browser tests that the affected plan names
through `bun scripts/goal/goalctl.ts test`.
