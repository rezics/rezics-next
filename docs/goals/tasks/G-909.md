## Outcome

`task dev:seed` replays cleanly on a fresh stack (G-905), but on the shared
stack, which holds data seeded under older contracts, it stops: first an
`idempotency_conflict` on a release PUT whose body changed under the same key
(now retried once under a body-bound key, `scripts/dev/seed/api.ts`), then
`release_basis_changed: Refresh the release and retry with a new key`
(`seedReleases`, `releases-step.ts`). After this task the seed converges: a
run on a stack seeded by any earlier version brings every seeded record to the
current plan and exits 0, and a second run changes nothing.

## Approach

- Generic in the seed transport: on a `*_basis_changed` or stale-head
  conflict for a PUT, read the resource, and if it already matches the plan
  skip it; otherwise retry with the current basis/expected head and a key
  bound to that basis. POSTs keep stable keys (never duplicate records).
- Apply to every PUT step, not only releases.
- The manager permits running `task dev:seed` against the shared stack for
  acceptance (it is idempotent); do not start or stop stacks.

## Do not build

No direct database writes, no contract changes in Main.

## Acceptance

`task dev:seed` exits 0 on the shared stack twice in a row; the second run
reports every step replayed with no writes.

## Checks

`bun test scripts/dev/seed tests/qa/unit/dev-seed-plan.test.ts`; `task dev:seed` twice.
