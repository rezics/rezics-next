## Outcome

Security pass 1 (`/home/edge/projects/rezics/rezics-next/.temp/manager/archive/G-895/report.md`, M1)
found that wiki candidate intake matches guessed names against all Collection
members (`canReadTarget: async () => true`) and answers `unavailable` for a
hidden match but `new` for no match, so a caller with `wiki:propose` can probe
up to 64 names per request for embargoed or private entities. After this task
matching uses only members and name records the caller may read, with a final
disclosure fence, and the response for a hidden member is identical to its
absence.

## Approach

Replace the always-true reader with the caller's real disclosure check before
matching. If duplicate prevention needs restricted members, return one
scope-level result that does not depend on which guessed names matched. Update
the G-845 test that expects the old behaviour.

## Do not build

No new endpoint, no rate-limit change, no new tables.

## Acceptance

Response-equivalence test: private member present versus absent gives
byte-identical responses, including a public/private alias collision.
