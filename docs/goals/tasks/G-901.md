## Outcome

The editors UI (G-839, review `/home/edge/projects/rezics/rezics-next/.temp/manager/reviews/G-839.md` item 4)
hard-codes eight relation kinds and which write each uses
(`apps/web/features/work-levels-edit/kinds.ts`: rewrite, reboot and
adaptation through `POST /v1/resources/{id}/derivations`; sequel, spin-off and
three correspondences through relation occurrences), because Main serves
definitions only by key. Backend one, frontend free: a new kind must be data.
After this task a public read lists the admitted relation definitions an
editor may record, each with its stable key, its write path
(`derivation` | `relation`) and its role constraints, and the eight kinds are
seeded with that data.

## Approach

Add the write path and an `editorRecordable` flag to the existing definition
record or its admitted projection, whichever already carries per-definition
metadata; list read `GET /v1/lexicon/definitions` (public, paged, filter
`recordable=true`), classified for rate limits. Reuse the existing definition
render for labels.

## Do not build

No new table, no UI change (the web switches in a later task), no per-kind
code branches in Main.

## Acceptance

API: the list returns the eight seeded kinds with their write paths; a newly
admitted definition marked recordable appears without code changes; private
or retired definitions do not.
