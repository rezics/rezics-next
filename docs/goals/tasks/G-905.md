## Outcome

G-852 found two defects on main. (1) The demo seed posts a `ModPackage` as a
contributor's own work; G-653 made that type administrator-only, so
`task dev:seed` stops before the franchise, Light Novels and Visual Novels
steps. (2) `tests/fixtures/catalogue/load.ts` posts catalogue Works without
the `grain` and `candidateReceipt` that `POST /v1/works` now requires (G-842
search-first intake, G-892 grain), so replaying
`tests/fixtures/catalogue/franchises.yaml` gets HTTP 400 and loads 0 Works —
the M6 catalogue acceptance fixtures cannot load. After this task
`task dev:seed` completes on a fresh stack and the catalogue fixtures load
through the current API (search first, declared grain, the candidate receipt
the search returned), so the franchise Works appear in the Light Novels Zone.

## Approach

- Seed: create each record as the principal class the served registry
  admits for its type (administrator for `ModPackage`), or drop the
  `ModPackage` record if nothing on the launch path needs it.
- Loader: follow the intake API exactly as a client would; never write
  owner tables.
- Class guard: a unit test validates every seed and fixture write body
  against the generated request schema (`generated/openapi/main/public.json`)
  so a contract change fails the test, not the seed at runtime.
- `g-852-zones.test.ts` reads the content-addressed copy under
  `tests/fixtures/seeds/vndb/`; delete the identical `tests/fixtures/vndb/slice.json`.

## Do not build

No contract relaxations to make fixtures pass; no new seed data.

## Acceptance

`task dev:seed` completes on a fresh isolated stack; replaying
`franchises.yaml` loads every fixture Work; the franchise Works appear in the
Light Novels Zone; the schema-validation guard passes.
