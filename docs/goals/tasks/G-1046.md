## Outcome

G-1023 renamed the Access `name_*` tables to `alias_*` (migration 1029) while
G-1025 wrote a new query against `access.name_registry`
(`services/main/src/modules/feed/frame.ts`); nothing caught it until the
manager's integration run hit `relation "access.name_registry" does not exist`
(fixed on main in "fix(feed): read handles from the alias registry"). Rename
races between parallel work will recur.

Add a fast check (unit tier, or a `task check` gate if that fits the existing
static checks better) that extracts every schema-qualified relation
(`access.*`, `content.*`, `relay.*` and the other owner schemas) referenced in
SQL strings across `services/`, `scripts/` and `tests/`, and fails when one is
not created by the migration set at the current head (or was renamed or dropped
by a later migration), naming the file and line. Tests that deliberately
exercise old names (migration tests such as `g-937-migration` and
`g-1023-alias-migration`) declare that explicitly. Prove it catches the
`name_registry` case on the parent of the fix commit.

## Checks

Run the new test through `bun scripts/goal/goalctl.ts test`; scoped oxlint;
scan changed files with `task ast-grep -- scan`.
