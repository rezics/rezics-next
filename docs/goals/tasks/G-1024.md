## Outcome

The maintainer wants the performance of the feed APIs (Home, a Realm's feed)
and of search, above all complex search, measured with OpenTelemetry and
compared with each owner's cost model
([complexity contracts](../../storage/workload-budgets.md#complexity-contracts),
[fixed bounds for interactive requests](../../storage/workload-budgets.md#fixed-bounds-for-interactive-requests),
[complexity verification](../../testing/complexity.md)). The maintainer's
judgment (2026-10-03): the APIs' own cost dominates; a page's fan-out from the
web server is secondary, so web tracing is out of scope here. Main already
exports spans for HTTP, outbound fetch (Fuseki and Account) and PostgreSQL
([observability](../../operations/observability.md)); `scripts/load` holds a
corpus builder, baselines, a k6 run, a Fuseki load meter and a search probe:
reuse them.

Build the shared tool G-1025 to G-1027 use:

1. **API work profile.** A helper that collects the spans of one Main API
   request (the caller sets `traceparent`; group by trace) and reports Fuseki
   requests with bytes and duration each, PostgreSQL statements with duration,
   Account calls, other fetches, and server latency; plus an assertion API so a
   test can state a cost contract (for example "at most 3 Fuseki requests and
   6 statements, independent of corpus size"). It works in QA integration runs
   (an in-process OTLP sink) and against the shared dev stack.
2. **Engine time.** Request counts do not show what a SPARQL query costs inside
   Fuseki. Separate engine execution from transfer for each Fuseki call (from
   Fuseki's own request timing or a server-side span), and add a helper that
   captures the ARQ algebra and optimizer plan and the text-index candidate
   counts of a given query, so the slowest queries can be explained.
3. **Scales.** A corpus recipe that grows one dimension at a time (unrelated
   Works and posts, follows, memberships, history depth, Realm size, Concept
   vocabulary) through the public API, built once per dataset and restored
   ([data preparation](../../storage/workload-budgets.md#data-preparation-and-import)),
   at three scales a laptop can prepare within the preparation budget.
4. Document the method in `docs/testing/complexity.md` (what is observed, what
   stays unobserved).

Prove the counters detect a known expensive case before trusting their zeros.
Run your tests with `bun scripts/goal/goalctl.ts test`.
