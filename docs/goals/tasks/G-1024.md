## Outcome

The maintainer wants the performance of the feeds and search (anonymous Home,
signed-in Home, a Realm's page, search) measured with OpenTelemetry and
compared with each owner's cost model
([complexity contracts](../../storage/workload-budgets.md#complexity-contracts),
[fixed bounds for interactive requests](../../storage/workload-budgets.md#fixed-bounds-for-interactive-requests),
[complexity verification](../../testing/complexity.md)). Main, Account and the
relay already export spans for HTTP, outbound fetch (Fuseki and Account calls
included) and PostgreSQL ([observability](../../operations/observability.md));
the web server exports nothing, so a page's fan-out to Main is invisible.
`scripts/load` already holds a corpus builder, baselines, a k6 practical run and
a Fuseki load meter: reuse them.

Build the shared tool the three surface tasks (G-1025 to G-1027) will use:

1. **Web traces.** The web server (vinext) starts the same
   `@rezics/observability` runtime, emits one server span per page render and
   per BFF route with bounded route names, and propagates W3C trace context to
   Main, so one trace shows a page and every Main, Fuseki, PostgreSQL and
   Account call below it. Keep the export allowlists (no raw URLs, query
   strings or identifiers).
2. **Work profile.** A helper that collects the spans of one request (a test
   sets `traceparent`; the profile groups by trace) and reports, per request:
   Main calls from the web, Fuseki requests and bytes, PostgreSQL statements,
   Account calls, other fetches, server and total latency; plus a small
   assertion API so a test can state a cost contract (for example "at most 3
   Fuseki requests and 6 statements, independent of corpus size"). It works in
   QA integration runs (an in-process OTLP sink) and against the shared dev
   stack (the same sink, or the Aspire dashboard's API, whichever is reliable).
3. **Scales.** A corpus recipe that grows one dimension at a time (unrelated
   Works and posts, follows, memberships, history depth, Realm size) through the
   public API, built once per dataset and restored
   ([data preparation](../../storage/workload-budgets.md#data-preparation-and-import)),
   at three scales that a laptop can prepare within the preparation budget.
4. Document the method in `docs/testing/complexity.md` (what the profile
   observes and what stays unobserved, such as native Jena operators).

Prove the counters detect a known expensive case before trusting their zeros,
as the complexity guide asks. Run your tests with `bun scripts/goal/goalctl.ts test`.
