## Outcome

Two workers saw Fuseki killed for memory during large preparations: G-1022
staging a 10,000-chapter story, and G-1032 preparing a large catalogue (killed
after 256 Works with classification). QA stacks keep TDB2 on tmpfs inside a
2 GB container (`scripts/qa/stack-environment.ts`: 512 MB heap, 128 MB direct),
and TDB2 is copy-on-write: writes grow its files until compaction, and on
tmpfs those files are memory. G-1024 also measured about 600 ms per public Work
written through the API (64 Works in 38.7 s), so a 10,000-Work corpus would
take over an hour, far beyond the
[preparation budget](../../storage/workload-budgets.md#data-preparation-and-import).

1. **Environment.** Large-scale corpora and performance runs use a
   disk-backed (persistent) QA or load stack with heap and container limits
   sized for them; ordinary tests keep tmpfs. Make this one explicit setting of
   the scale recipe and the load task, documented in `docs/testing/complexity.md`.
2. **Write cost.** With G-1024's work profile, break down one public Work
   write and one classification write (Fuseki requests and engine time,
   PostgreSQL statements, validation, indexing, projections) at catalogue
   sizes 100, 1,000 and 10,000; fix any part whose cost grows with the
   catalogue, and bring per-Work cost to what the model allows
   ([writes go through the API; a slow API is a defect to fix](../../storage/workload-budgets.md#data-preparation-and-import)).
3. **Storage growth.** Measure TDB2 growth per Work and per classification
   write between compactions; report it, and fix write paths that rewrite
   large values per small change.

Report before/after tables and the time to prepare 10,000 Works. `infra/jena` and `modules/work/activate.ts` belong to G-1022 until it lands: ask through `goalctl owner` for changes there. When the disk-backed recipe works, rerun G-1032's query matrix (`tests/qa/integration/g-1032-query-cost.test.ts` and its scale probe) at 1,000 and 10,000 Works and report it.
