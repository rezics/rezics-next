## Outcome

The Opus review of G-542 (`/home/edge/projects/rezics/rezics-next/.temp/manager/reviews/G-542-r2.md`,
"Export outbox gap") found that `export/store.ts:105,187` advances
`content.owner_control.sequence` and writes only a receipt, with no outbox
row, so the relay meets a sequence gap and stops; `session/store.ts:164` looks
like the same class. After this task no Content transaction advances the
sequence without writing the outbox event for that position, and the relay
never stops on a gap produced by our own writes.

## Approach

- Find the relay's contract for Content positions (what it reads, what a
  gap does) and confirm the defect with a failing test first.
- One small helper owns the advance: it bumps the sequence and inserts the
  outbox row for that position in the same transaction (an event with no
  consumers is still an event; receipts that change nothing observable may
  emit a no-op event if that is the relay's convention). Use it in export and
  session. List other raw advance sites (`grep -rn "owner_control SET sequence"
  services`) under OWNER CHANGES for their owners to adopt; do not edit files
  claimed by running tasks.
- Class guard: a test fails when source outside the helper contains a raw
  `owner_control SET sequence` advance, with an allowlist of the listed sites
  that shrinks as owners adopt it.

## Do not build

No relay redesign, no gap-skipping in the relay, no new tables.

## Acceptance

Integration: create an export and record a reading session, then assert the
relay consumes past both positions (no gap, no stop). Unit: helper writes both
rows in one transaction; rollback leaves neither.
