## Outcome

Every web catalog has every English key in zh-Hant, ja and ko, and each of these
locale files is typed complete (`satisfies <Messages>`, not `Partial<…>`), so a missing key is a
type error from now on. Measured on 2026-09-30 before G-531: 142 keys missing per locale in the
web split catalogs (manage 71, studio 50, profile 11, workPage 7, feed 3); G-531 adds about 110
more (communities 71, post-composer 32, condition-bar copy 18, one work-page key), so expect about
255 keys per locale, about 765 strings. Accounts is already complete (verified at runtime,
including the spread `additions*.ts` files), and so are the other web catalogs; the claims cover
only the eight catalogs with gaps.

## What to read

`scripts/i18n/check.ts` output (`task i18n:check`); each feature's English `messages.ts` and the
existing zh-Hant/ja/ko files beside it for established terms (Realm, Zone, Work, Main Version,
Studio and so on); there is no glossary document, so the existing translations are the glossary.

## Approach

Translate from English, not through zh-Hans. zh-Hant is Taiwan usage written natively, never a
character conversion of zh-Hans. Keep each `insert()`/`plural()` shape, binding names and
placeholders exactly; keep uncertainty, permission and pending wording as strong or weak as the
English (a "could not" is not a "did not"). After filling a file, change its
`satisfies Partial<X>` to `satisfies X`.

## Do not build

Do not edit English sources, components, other locales, the checker or Zone `strings.ts` (G-503
translates Zone strings). Do not add keys. No machine placeholder text, no copied English: a term
that stays in Latin script (REZICS, API, URL) is fine when the existing translations do the same.

## Acceptance

  translated.

## Checks

Manage, Studio, Profile, communities and post-composer stories.
