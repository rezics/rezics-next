## Outcome

The manager's final browser run on main (`.temp/manager/direction-9-final.log`,
main checkout, read-only; 69 of 72 passed in 37 minutes) failed three phone
journeys late in the run:

1. **en and zh-Hant phone › visibility: outsider requests, manager approves…**:
   `selectActor` gets **401** from `/api/main/v1/me/session-agent`
   (`direction-9.e2e.ts:102`). The proxy refreshes expired access tokens and
   forwards them in the same request, and Account rotates refresh tokens, so a
   saved storage state reused by several contexts presents an already-rotated
   refresh token after the access token expires. That is correct product
   behaviour; the suite must keep each context's session valid (G-1000 solved
   it for its spec in `account-sign-in.ts`: reuse that, do not weaken checks).
   Confirm the cause from the evidence before fixing; if a fresh, unshared
   session also gets 401, it is a product defect: report it under PROPOSED
   TASKS with the exact steps.
2. **relationships zh-Hant phone**: `[data-relationship="…"]` resolved to two
   elements (strict mode) while waiting for `data-hydrated="true"`
   (`direction-9-relationships.e2e.ts:417`). Scope the locator to the control
   the person uses on that viewport; if two visible controls for the same Space
   render at once, that is a product defect to report.

Run the whole of both specs once end to end (about 40 minutes, so expired
tokens are exercised) on the shared stack with the environment from G-1000's
brief, through `bun scripts/goal/goalctl.ts slot --`, and give the counts.
