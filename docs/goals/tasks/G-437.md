## Outcome

The maintainer, looking at the left navigation: "the whole site is like
this; it shouldn't be — whatever language I choose is the language, with
fallback rules; look at ../rezics". Realm names read "Fiction · 小说",
"Books · 图书", people "Daniel Chen 陈丹尼", Works "雨夜书店 · 连载小说",
organizations "North Star Editions · 北辰出版", in every UI language.

The rule is decided and recorded in `docs/plan/frontend.md` ("Names show in
the reader's language, one at a time"): names are stored per language (open
BCP 47 tags, one original); each field is chosen independently by explicit
`?language=` → the reader's ordered content languages → UI locale → browser
languages → the object's original; tags match exactly, then by language and
script (`zh-TW` = `zh-Hant`), then by primary language; reads return value,
language, direction and basis (`requested`/`fallback`). The old site's
precedent: `../rezics/apps/web/i18n/use-localization-languages.ts`,
`apps/web/lib/localization.ts`, `services/main/src/services/units/localization.ts`
(read-only reference; don't copy its whole-row fallback).

What exists: Work titles already come back as `readName` with language and
basis (`services/main/src/modules/work/read-contract.ts`); Concepts carry
per-language labels (G-426). Realms have two names: a plain Realm/Space name
string (what the navigation, directory and feed show, seeded with both
languages glued) and a profile `localizedName` fixed to exactly `en` +
`zh-CN`, both required (`services/main/src/modules/realm-profile/schema.ts`).

Deliver:

1. **One localized name set per Realm** (and Zone, which is a Realm's
   publication): labels in any language, 1–20 of them, one original, for name,
   description and rule titles/bodies. Replace the fixed `en`/`zh-CN` shape
   through a new profile/contract revision (persisted ids change only by
   revision), migrate existing rows (`zh-CN` becomes `zh-Hans`), and make the
   plain Realm name the original label rather than a second source of truth.
2. **Selection in Main, once.** A `display-language` module takes the
   reader's ordered languages (from a `languages` parameter the web sends, else
   `Accept-Language`) and selects per field with the rule above. Every Main
   read that returns a Realm, Zone or Organization name (navigation, directory,
   Realm reads, feed rows' Realm, Zone headers, editor lists, Manage reads)
   returns the selected value with language, direction and basis, keeping the
   existing field so clients keep working, plus `original` where a page needs
   it.
3. **The web sends the reader's languages.** One helper builds the ordered
   list (explicit `?language=`, the profile's content languages from G-413's
   settings, UI locale, browser languages) and the shared API clients
   (`apps/web/features/api`) send it on every Main read, server and browser.
   The navigation renders names with `lang`/`dir`.
4. **Seed names per language.** Split every glued name in the seed into
   language labels (Fiction / 小说, Books / 图书 …), give each demo person one
   display name (the one that person would pick; a romanization becomes an
   alias), remove descriptors glued into titles ("· 连载小说"), and give
   organizations localized names. Keep the seed replayable on existing stacks
   (new keys where request bodies change).

G-436 owns `services/main/src/modules/realm-directory/**` (the `/r`
directory); make the selection a function it can call and name the exact call
in your handoff, and the manager passes it on (or widens your claim once G-436
merges). Other running tasks own feature screens (G-436 communities, G-431 Home,
G-433 Zones, G-435 Manage, G-434 Search): they get correct names through the
unchanged fields once Main selects them. Adding "Add a translation" to the
community create form and Manage settings is a follow-up after this lands;
note the API they should call in your handoff.
