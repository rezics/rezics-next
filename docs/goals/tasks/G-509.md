## Outcome

Main stores versioned suitability assessments for any admitted resource. For a batch of targets
and the requesting viewer it answers with the assessment (`unassessed` when there is none) and
whether the viewer is eligible, with reasons. One pure policy function decides eligibility for
every channel; M5 wires it into delivery. Media, derivatives and history follow their resource's
assessment, so no media target is needed.

Verified gap: no suitability owner exists. There is no assessment, label or source signal
anywhere in `services/main/src`, so every resource is effectively shown as general. The only
adult control is `adultContent` in `access.person_preferences`. `valid()` in
`modules/preferences/store.ts` forces it to `false`; that store belongs to G-514, and this brief
leaves it alone. No age evidence exists (Account has no birth month), so every viewer's age is
`unknown`.

## Approach

- Labels: `general` is the empty set; `r15` stands alone; `r18` and/or `r18g`. No row means
  `unassessed`.
- Migration 876 creates one append-only `access.suitability_assessment` table: target IRI,
  labels, basis `author | platform | source`, source id, assessor, predecessor and created_at,
  with a current-head constraint.
- Add a `suitability` row (all five bases) to G-506's capability table, and resolve targets
  through `resolveTargets`.
- `policy.ts`: `eligible({ assessment, viewer: { signedIn, age: 'unknown'|'under-15'|'15-17'|'adult',
  country, optIns: { sexual, grotesque } }, realmCeiling?, channel })` returns
  `{ eligible, reasons }`. The rules:
  - Unknown age or country never grants r15, r18 or r18g.
  - r18 needs the sexual opt-in and r18g the grotesque one; material with both needs both.
  - KR and GB never admit r18 or r18g.
  - Email and push never carry r18 or r18g.
  - Index and preview channels use the anonymous viewer.
  - A Realm ceiling only restricts.
  - Unassessed is eligible on read and index channels and is never reported as `general`. The
    manager may change this default (see the summary's open question 1).
- Commands: `PUT /v1/suitability/{target}` with `expectedRevision` and an idempotency key.
  - The `author` basis needs Work edit authority on the resolved target's `work`, and it cannot
    weaken a `platform` head.
  - The `platform` basis uses an existing platform moderation authority if Access has one.
    Otherwise leave it out and propose it for M5.
- Read: `POST /v1/suitability/reads` (≤64 targets). It also returns the viewer's evidence
  summary: age `unknown`, and that the opt-ins are unavailable and why. With no age evidence the
  opt-ins are always false and not stored.

## Do not build

- No model profile, graph writes or Realm rule storage.
- No importer mapping, UI or age collection.
- No preference storage, and no enforcement in feeds, search or media (M5).
- No second label vocabulary: Concepts and review scores are not suitability.

## Acceptance

- Policy truth table (unit): every combination of label, age, opt-ins, country, channel and
  Realm ceiling. It includes compound r18+r18g needing both opt-ins, unknown age denying r15,
  KR/GB, and email/push.
- A property test: a Realm ceiling or a stronger label never widens eligibility.
- API (integration):
  - create, correct and read an assessment on a Work, a release and a character;
  - replay the same key; a stale revision returns 409;
  - an author weakening a platform head is denied, and so is a revoked editor;
  - an anonymous read of an r18 target is ineligible;
  - `unassessed` never serializes as `general`.
