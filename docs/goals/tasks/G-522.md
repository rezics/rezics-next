## Outcome

Decision 33 ("First-party REZICS shows no consent and appears in Accounts as a
product session"). Verified defects:

- `readConnectedApps` (`connected-apps.ts:25-31`) lists every first-party grant
  as a connected app with capability summaries and "Remove access". Signing in
  silently re-grants (`messages/en.ts:249,266,270`).
- Signing out a "REZICS · Chrome" device deletes only the Account `session` row
  (`security-activity.ts:97-113`). REZICS refresh tokens survive, because
  `oauthRefreshToken.sessionId` is `on delete set null`.
- Admin client badges use `skipConsent` (`clients.tsx:66`), not the
  first-party registry (`056_first_party_clients.sql`). Seeded operator
  clients are mislabelled as a result.
- `webClientCurrent` (`web-auth-bootstrap.ts:326-336,376-383`) never checks
  `skipConsent`, so a stale registration survives.

`docs/contracts/connected-apps.md#first-party-sessions-and-developer-extras`;

## Approach

1. Connected apps lists only clients with a consent row. Delete the
   first-party branches and copy from `connected-apps.tsx` and messages.
2. Signing out a session also revokes the refresh tokens issued under it.
   First verify that the provider fills `sessionId` on REZICS refresh tokens.
   If it does not, bump that user's first-party grant generation and say so in
   the handoff. "Sign out of other sessions" does the same for each session.
   Retitle the section "Devices and sessions" in all eight locales. REZICS
   sessions read as product sessions with a Sign out action.
3. Admin list and `clientView` expose `firstParty` from the registry; the badge
   uses it.
4. Bootstrap selects and requires `skipConsent = true`; add the test case.

## Do not build

Do not remove or bypass OAuth, PKCE, state or issuer checks, token ceilings or
the generation fence. No new tables, grant model or "product sessions" service.
No developer settings, app installations or MCP management (decision 33 defers
them to M7). The web callback's error pages are G-537.

## Acceptance

- API: after sign-in, `GET` connected apps has no REZICS entry and a
  consented third-party app still appears. Revoking the REZICS device session
  makes the next refresh fail. State the remaining access-token lifetime in the
  handoff. Removing a third-party app keeps today's semantics.
- Bootstrap: a registration with `skipConsent=false` is reconciled.
- Update `first-party-signup.e2e.ts:52-58` (REZICS moves from connected apps
  to sessions); G-537 later edits its onboarding steps.
- Browser (Accounts, phone and desktop, `en` and `ko`): connected apps shows
  only third parties, or an empty state. Devices and sessions shows "REZICS ·
  Chrome" with Sign out, and after it the web app asks to sign in again. Admin
  → Clients marks only registry clients First-party.
- Class guard: a registry-by-`skipConsent` matrix test fails if either
  classification is derived from the other.
