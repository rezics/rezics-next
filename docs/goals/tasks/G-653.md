## Outcome

An administrator can admit a descriptive type through `POST /v1/types`. The type has a base of `work` or
`resource`, eight-locale labels, a presentation, a cover, and a creation authority. Once admitted, and without a
restart, deployment or source change, it:

- appears in `GET /v1/types`, with a new digest;
- is accepted when a Work is created or retyped;
- shows in Work reads and the type facet;
- receives the capabilities its base binds.

The closed type lists are opened once:

- `work-kind-v3` and `work-type-v3` copy v2 without the `sh:in` list;
- `ModelMutationPolicy` accepts v3 anchors next to v1 and v2 (`:244-245`).

This is the last Java or profile edit that adding a type requires. It is off the launch path.

## Approach

1. **Profiles.** Add `work-kind-v3` and `work-type-v3`. They keep `hasValue schema:CreativeWork`,
   `maxCount 4`, `nodeKind sh:IRI` and `rv:mainVersion`. Create and type-edit write v3, and v1 and v2 records
   stay valid. Add `work-type-v3` beside v1 and v2 in the historical-anchor check.
2. **Migration 961.** Create `access.admitted_type`: type IRI, base, labels (jsonb), presentation, cover,
   creation, interest, primary action, revision, admitted_by, lifecycle. Admission is idempotent and requires a
   new grant scope, `type:admit`. Retiring a type blocks new use; existing Works keep it.
3. **Registry.** The registry module serves the compiled entries together with the active rows.
   `WORK_SEMANTIC_TYPES` and the other derived lists refresh in place when the digest changes: on each admission,
   and on a bounded TTL across processes. Their call sites do not change. Derive `onboarding/choices.ts` `choiceTypes` from the registry as well.
4. **Admission rules.** `normalizeWorkSemanticTypes` and `checkedWorkTypes` check against the live registry. The
   combination rule keeps its current meaning.

## Do not build

- A proposal or review workflow for types; only administrators admit.
- Manifests, namespaces or stewards.
- Per-type capabilities, routes or pages.
- Structural types; bases stay code.
- Types that set `sh:closed` or add properties.
- Any Fuseki change beyond the single Java line and the rebuilt module.

## Acceptance

Through the API, on an isolated stack:

- **Admission.** Admit `rv:WebNovel`, with base `work` and labels in all eight locales. Then:
  - create a Work of that type, read it and retype it;
  - find it in the type facet;
  - discuss it through `/v1/resources/:id/discussion`.

  None of this needs a restart.
- **Denials.** A non-administrator's admission is denied. An unadmitted type is rejected. Retiring the type
  blocks new Works of it.
- **Old records.** v1 and v2 Works still edit.
- **Class guard.** Removing v3 from the Java anchor check fails the integration test for retyping an old Work.
