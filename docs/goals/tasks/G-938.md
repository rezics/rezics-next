## Outcome

Implement [Follow, Join and notification](../../contracts/community-interactions.md#follow-join-and-notification)
and [recipients and levels](../../contracts/notifications.md#recipients-and-levels);
read both sections first, they are the spec. Today there are three follow
mechanisms (`access.follow` with a closed kind list, Concept follows that create
Saved Filters through a trigger, and `access.proposal_subscription` shown as
Watch); Realm and Zone are separate follow targets; joining does not follow on
the server (the web sends a second command); no read lists joined Realms; only
Work and Agent follows notify; `GET /v1/me/follows` returns at most 8 per kind
although its contract says 20; notification code reads `access.follow`
directly.

After this task:

1. A follow targets any admitted resource IRI or saved view, its kind taken
   from the type registry. Existing Realm and Zone follows become one Space
   follow; feed matching and "new since" work on Spaces. Following any saved
   view works; a Concept follow keeps creating its one-Condition view.
2. Each follow has `level` (all, highlights, off) and `source` (explicit, join,
   library), with the documented defaults per kind, and a pinned order.
3. Join admits the member and writes the join-sourced follow in one
   transaction; leaving removes only that follow. `GET /v1/me/memberships` and
   `GET /v1/me/follows` are cursor-paged, filter by name (`q`), order by recent
   activity or pinned order, and share the list shape `{ items, nextCursor,
   complete }`. Batch changes cover unfollow, level and pin for the manage page.
   A person's follow count has a generous ceiling enforced as a budget, not as
   a page size.
4. Putting a Work on Reading or Plan to read writes a library-sourced follow at
   level all; removing it removes only that follow.
5. Watch replaces the proposal-only subscription for threads, proposals,
   releases and Collections (participating, all, ignore); migrate existing rows.
6. Producers choose recipients as the notifications section orders them: direct
   involvement first, then follows and joins by level, then Watch overrides,
   reading follows through the follows store, rechecking disclosure and paused
   follows at delivery. Use only event kinds that exist today; list missing
   ones (for example Space announcements) as proposed tasks.

## Do not build

No paid tiers, new channels, digest cadence settings, follower-list privacy,
recommendation changes or web UI (G-944 builds it). Keep the API verbs Follow,
Join, Leave, Invite, Ignore and Block. Fix web fixtures and types only where a
served contract changed, and list web readers under OWNER CHANGES.
