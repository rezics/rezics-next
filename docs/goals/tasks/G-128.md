SYS13 per `docs/testing/backend-integration.md`: a restore loses a later receipt
while a client retries its old command. The new data epoch rejects unproved old
intent, and external effects reconcile before replay. The governing rules are
`docs/contracts/commands.md` (a new restored data epoch does not reset
idempotency; an old-lineage request with a preserved receipt resolves that
outcome; a missing receipt after rollback requires recovery reconciliation, not
fresh admission of the same logical effect) and
`docs/contracts/events-and-jobs.md` (restore fences the old writer and starts a
new data epoch; never compare sequences across epochs or treat a missing old
receipt as proof that an earlier side effect did not occur).

(`services/main/src/modules/protection/README.md`, last paragraph) names the
remaining assertion: restoring a cut that lost Work protection or correction

graph hold can be released. `tests/qa/integration/protection-work-api.test.ts`
already proves that a sealed Access admission with a missing graph receipt stays
pending. Recovery coverage discovers tables from the catalog
(`services/main/src/graph-recovery-coverage.ts`, G-075).

Build one real fault/recovery test: commit a protected Work correction through
the API, take the stopped owner cut that loses the later graph receipt, restore,
then (a) retry the client's old command with the same key and prove it resolves

different digest and get a conflict, (c) replay the retained protection and
correction events into the restored graph and prove the hold releases only after
recovery coverage passes, and (d) prove that an external effect (outbox or
notification delivery already sent) is reconciled, not re-sent. Change owner code
only for a proven gap.
