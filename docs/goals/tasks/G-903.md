## Outcome

G-902 found that no client could publish a Realm post because a value the
next call needs (`revisionDigest`) was only reachable with SQL, and the tests
hid it by reading the database. Its audit
(`/home/edge/projects/rezics/rezics-next/.temp/manager/archive/G-902/g-902-sql-audit.md`)
lists 29 integration tests that read an owner table to obtain an input for a
later API call. Writes go through the API (maintainer direction), so each is
either a test shortcut or an API gap. After this task every listed test gets
those values from an authorized API response, and every real gap is closed in
the read or write result that should carry the value.

## Approach

- For each row, find whether an authorized read already returns the value
  (scope authority epoch, group/representation generation, grant ID, review
  decision ID, notification item ID, governance case ID, Realm policy
  revision). If yes, switch the test to it.
- If not, return the value from the write that created it or from the
  existing read of that resource the caller is entitled to (never a new
  endpoint just for tests; never expose another principal's internals). The
  seedHome helper (`feed-read-support.ts:217`) uses the digest from the draft
  write (G-902).
- Class guard: a test fails when a file under `tests/qa/integration/` both
  queries an owner schema with SELECT and sends an HTTP request built from the
  result, with an allowlist that must stay empty for new files (setup-only
  reads such as fixture inspection stay allowed when no request uses them).

## Do not build

No new routes unless a value has no owner read at all (list it first); no
change to authority semantics.

## Acceptance

All listed tests pass with API-derived values; the guard passes.

`task main:typecheck`; `task goal -- test` over the changed integration
files; `bun test services/main/tests/g-543-rate-limit.test.ts`.
