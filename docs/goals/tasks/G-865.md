## Outcome

Anyone may propose a change to a catalogue fact on any admitted resource; a
steward reviews it; the proposer revises; a steward applies or rejects; the
proposer withdraws; an applied change is reverted by a compensating proposal.
One lifecycle through the API, with typed blockers and the viewer's allowed
actions, so the UI (G-867), notifications (G-866), wiki bundles (M6 G-846)
and wiki deltas (G-693) all bind to it. Today only a Content draft and the English Work
title have corrections, a superseded revision can still be approved
(`protection/content-store.ts:258-278`), and nothing can be withdrawn or reverted.

## Approach

- Access tables (880–882): proposal (kind, target ResourceRef, proposer principal and Agent, `proposer_key`), immutable revisions (n, candidate ≤1 MiB, candidate digest, base heads, ≤32 evidence refs), immutable reviews (revision n, reviewer, `approve` | `request_changes` | `comment`, message ≤4,000 chars) and one terminal decision (`applied` | `rejected` | `withdrawn`, owner receipt, optional `reverts`). State is derived from rows, never a mutable status column.
- An approval counts only for the latest revision; a new revision makes earlier approvals stale by computation. Apply requires the required approvals on the latest revision from eligible reviewers who are not the proposer, not the proposer's other Agent or operator, and hold review authority at decision time. The deciding steward's approve-and-apply is one owner commit, as in the current protection template.
- Required reviewers: the target Work's maintainers, else holders of the review scope (G-508) on the target's context. One approval by default; an adapter may require two, which M6's identity merge (G-836) needs if it binds here.
- Each kind is an `editorial-review/<kind>-adapter.ts` file, discovered by file name so a new kind needs no shared edit, implementing one TypeScript interface: `validate`, `preview` (list of before/after changes), `apply(expectedHeads) -> receipt`, `compensate(receipt) -> candidate`. Implement `component-correction` over those two commands, called in-process with the proposal revision as the idempotency key. Apply with a moved head returns a `stale_base` blocker; the proposal stays open for revision.
- Operations (Idempotency-Key, RFC 9457 problems, cursor pages of ≤50, declared like `routes/reports.ts` `openApiOperations` so SDK and MCP expose them): create, revise, review, decide, withdraw, revert, get (timeline, typed blockers, `allowedActions` for the viewer), list (`mine`, `review-requested`, by target).
- A revoked or replaced agent credential leaves its proposals, reviews and receipts readable and attributed.

## Do not build

A workflow engine, a per-kind state machine, a rule language (CODEOWNERS-style),
comment threads, batch review, saved queues or dashboards (deferred), UI,
notifications (G-866), a new model profile, or a change to the Content-draft and
Work-title correction routes, which stay as they are.

## Acceptance

- API journey in `tests/qa/integration/g-865*.ts`: propose a Work synopsis and date correction with evidence → request changes → revise → a second reviewer's approval from revision 1 does not count → apply → receipt; replaying the lost apply response returns the same receipt; a moved head gives `stale_base`; self-review through a second Agent and a revoked steward are refused; withdraw; revert restores the prior value through a new proposal; the proposal and receipt survive revocation of the agent credential that submitted them.
- Class guard: one conformance suite that every adapter runs (stale approval, self-review, apply without receipt, implicit second decision), failing on a deliberate regression. Mark the pending subcases this qualifies in `scripts/qa/cases/editorial-protection.ts`.
