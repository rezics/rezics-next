## Outcome

The main site's UI consumes Main's APIs, and Main has a large command surface
but almost nothing a catalogue UI can browse. A scout found: no
`GET /v1/works/{id}` (only `GET /v1/resources/{id}`, `GET /v1/public-previews/{id}`,
`POST /v1/resources/summaries` for a few kinds, `/v1/revisions/{rev}` and
`/v1/main-versions/{mv}/...` reads), no list or browse reads for works, realms,
agents or users, search requires a 2–80 character phrase, no Realm read, no
public Agent profile read, no "my works/contributions" lists, no moderation
queues, and no audit-log read. Verify these in code first.

Design the read side for the main site and implement its first template.

## The main site's first slices (manager decision; consumers of your APIs)

1. **Work page** `/w/{slug|id}`: header (localized title and original title,
   Work type, cover, Main Version label, credited Agents with display names
   and handles), a scope bar (Global | a Realm | Mine) that re-scopes rating
   summary with distribution and count, classification/tags with relevance,
   and adoption badges; tabs Overview, Contents, Versions (editions,
   translations, releases filterable by language), Discussion, History.
2. **Reader**: contents (chapter list of the selected version and language),
   chapter body, next/previous, reading progress (`routes/progress.ts` exists).
3. **Search and Discover**: browse without a phrase (recent, top rated in a
   scope, by classification term, by Work type), plus phrase search with scope;
   results say why they matched and whether counts are exact.
4. **Library and profiles**: a person's shelves/lists and ratings;
   `/@handle` for people, pen names and organizations (Agents).
5. **Realm home**: Realm read (name, description, banner, rules summary,
   member count, moderators), the Realm's works in Realm scope, a public
   decisions log (adoptions, classification decisions, rule changes).
6. **Management**: a Realm moderation queue (reports, pending contributions,
   corrections) filterable by state and type, and an audit log.

## Deliver

1. **Design** (`docs/plan/read-api-design.md`, short; it will be deleted once
   code carries it): the read families above with paths, parameters, response
   shapes, pagination (cursor), scope and disclosure rules (private Realm data
   never leaks; erased or unreviewed content excluded), cost contracts and
   complexity bounds in the style the backend already uses (see
   `docs/testing/complexity.md` and existing cost contracts), and which
   existing endpoints each reuses or supersedes. Prefer resource-oriented reads
   that Server Components can call in parallel, each bounded; add a composite
   read only where one bounded call is cheaper than several. Split the
   remaining families into worker-sized tasks with claimable paths and say
   which can run in parallel.
2. **Template.** Implement the Work page reads (item 1) end to end:
   route module(s), owner reads, OpenAPI/Eden types, disclosure, cost
   contract, and integration tests covering public, private, erased,
   missing-translation fallback, scope switching and pagination. Add one
   browse list (Discover: recent public Works with cursor) as the list
   template. Register routes as `docs/goals/worker.md#shared-artifacts`
   describes (one import and one `.use()` line in the last plugin group of
   `services/main/src/app.ts`; union merge; add lines only).
3. Make the typed client usable from the web app: the web app uses
   `treaty<MainApp>` from `@rezics/main/app`; confirm your routes are typed there.
