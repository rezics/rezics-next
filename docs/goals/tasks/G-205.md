## Outcome

The Account service (`services/account`, Elysia + Better Auth 1.7.5 as the
OAuth 2.1/OIDC provider) gains the APIs that an Accounts site in the spirit of
Google Account and a genuinely good operator admin panel need. The frontend is
built in parallel in a new `apps/accounts` app that sits in front of this
service on the Account origin and proxies `/api/auth/*`, `/api/account/*`,
`/oauth2/*` and discovery to it; design the APIs for that consumer (typed,
paginated, stable error codes, no account enumeration in public errors).

## What exists (confirm in code)

Email/password sign-in and sign-up, get-session, update-user, change-email,
change-password, delete-user, session list/revoke (Better Auth defaults);
`/oauth2/authorize|token|introspect` with `update-consent` stubbed; OIDC
discovery and JWKS; installations and installation changes; guardian recovery
policy and claims. Operators are a fixed env list `ACCOUNT_OPERATOR_USER_IDS`
used only for OAuth clients and installations. No email sender, no email
verification or password reset, no passkeys or 2FA, no user-facing connected
apps list, no admin plugin, no audit log.

## Deliver, in this order (commit each coherent step)

1. **Email delivery.** An SMTP sender configured through envalid config
   (Mailpit at `127.0.0.1:1025`/UI `:8025` in dev; see `docs/email-delivery.md`),
   localized (en, zh-CN) plain+HTML templates kept in code. Email verification
   on sign-up and email change, password reset request and completion.
   Rate-limit and never reveal whether an address exists.
2. **Consent.** Make the consent step real: the consent page (hosted by the
   Accounts site at `/consent`) needs an endpoint to read the pending request
   (client name, requested scopes with human descriptions in en and zh-CN,
   resource) and to accept or deny it. Remove the stub.
3. **Sign-in methods.** Passkeys (`@better-auth/passkey` or the maintained
   equivalent for 1.7.x) and TOTP two-factor with backup codes, each with
   enrollment, listing, renaming, removal and protection of the last remaining
   method (see `docs/services/account.md`). Step-up (recent re-authentication)
   for sensitive changes.
4. **Security activity.** A per-user security event log (sign-in with coarse
   device/location from user agent and IP, sign-out, failed attempts summary,
   password/email change, method added/removed, session revoked, consent
   granted/revoked, admin actions on the account) with a paginated read for
   the user. Sessions list with device labels and "this device" marker,
   revoke one or all others.
5. **Connected apps.** A user-facing list of OAuth clients and installations
   the user has granted, with scopes described, last used time and revoke
   (consent and refresh tokens revoked through the existing fence).
6. **Operator administration.** Replace the env list with stored operator
   roles (bootstrap the first operator from `ACCOUNT_OPERATOR_USER_IDS`), at
   least `owner`, `admin`, `support` with a typed permission table. Endpoints:
   user directory with search (email, name, id prefix), filters (status,
   verified, has 2FA, created range), sort and cursor pagination; user detail
   (profile, methods, sessions, apps, recent security events, operator notes);
   suspend/unsuspend with required reason and optional expiry (suspension
   blocks sign-in, revokes sessions and refresh tokens, and must stop Main
   access tokens through the existing introspection or fence path — confirm
   how Main validates tokens and close the gap); revoke sessions; require
   password reset; resend verification; OAuth client management already
   present stays and moves under the role check. Every operator action writes
   an append-only audit record (actor, action, target, reason, before/after
   summary, request id, time) with a filterable paginated read. No
   impersonation.
7. **Contract for the frontend.** Export the Elysia app type so the Accounts
   site can use Eden, or document the Better Auth client plugins it should
   use; add typed error codes. Keep the service's OpenAPI generation working.

Write integration tests with each step (see `services/account/tests/*.integration.test.ts`
for the pattern) covering denied, stale, concurrent and enumeration cases.
Prefer code to documents: when `docs/services/account.md` restates what your
code and tests now say, shorten it to intent and decisions.
