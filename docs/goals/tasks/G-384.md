## Outcome

G-379 made the web's session consistent within a request and a web isolate,
but one race remains. Two web isolates (or two devices sharing a cookie jar)
can refresh the same rotated refresh token at the same moment. The loser
presents a token the provider has already rotated and is signed out, or,
with the provider's replay window turned on, a rotated response can be
replayed after the person withdrew consent. G-379 tried the provider's global
30-second replay window and reverted it for that reason
(`.temp/goal-orchestration/runs/G-379/attempt-1.last.md`; QA runs
`20260928t050814-917ee9` and `20260928t051015-8d55a1`).

Coordinate refresh in the Account service so that:

- concurrent refreshes of the same token within a short window get the same
  new token pair, and nobody is signed out;
- a refresh after consent withdrawal, token revocation, account disable or
  erasure is refused even inside that window: the fences are checked for
  every answer, including a repeated one;
- a refresh token presented after the window, or by a different client,
  counts as reuse and revokes the family, as today.

Tests: concurrent refreshes from two clients of the same session; withdrawn
consent between the two; revocation between the two; a stale reuse after the
window. Account migrations 073–077 are reserved if the coordination needs a
table.

## Verify

Against the shared stack: sign in as Daniel (credentials in
`scripts/dev/seed/plan.ts`) and fire two concurrent refreshes with the same
refresh token at the Account token endpoint. Show both succeed with the same
pair, then withdraw consent and show a repeat is refused. Use only the
backend; no web dev servers.
