## Outcome

The notifications page has Inbox, Saved and Done views and a reason filter
(Review requested, Changes requested, Participating, Mentions). Each item opens
its exact destination and can be saved, marked done and undone. After a reload
the page shows what the API says. A watch or mute toggle sits on the proposal
page. Notification settings list the topics the API returns instead of a
hard-coded copy. Today the page supports only read and mark-all-read
(`features/shell/notifications/notifications-view.tsx`), and the settings list
repeats the backend topics by hand (`features/settings/settings-sections.tsx:30`).

## What to read

- G-866's routes (`view`, `reason`, triage, proposal subscriptions), through the generated client in `apps/web/features/api/main.ts`.
- `apps/web/features/shell/notifications/{notifications-view.tsx,window.ts,notifications.stories.tsx}`, `apps/web/features/shell/unread.ts`, `apps/web/features/settings/settings-sections.tsx`.
- G-867's `apps/web/features/proposals/proposal-page.tsx`: add one embed of `WatchToggle` there, nothing else.

## Approach

Follow the existing notifications view and stories. Keep the view and filter in
the URL. Derive the settings topics from the preferences API; labels are keyed by
topic in the settings messages, and a typed map fails compilation when a topic
has no label.

## Do not build

Thread grouping, bulk actions beyond the existing mark-all-read, keyboard
shortcuts, a second unread counter, or any client-side eligibility rule.

## Acceptance

- Browser against the local stack at phone and desktop widths (screenshots reviewed): save, mark done, undo, filter by reason and reload; new activity after Done appears in the Inbox; watch and mute on a proposal change what arrives.
- Stories for the empty, mixed, saved-only and error states in light and dark themes.
- Class guard: a test fails when the settings page shows a topic the API does not return, or omits one it does.
