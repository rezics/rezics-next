## Outcome

From the milestone review (`.temp/manager/milestone-review.md`, findings 2, 17,
31, 33, 34 and 35; screenshots in `.temp/manager/milestone/`):

1. **Sign-in never breaks on the dev stack.** The Aspire AppHost captured a
   stale web client ID at startup, so every sign-in failed `invalid_scope`
   after the client was re-registered. The web app must read its client from
   the current `web-auth/public.json` at start (not a snapshot), `dev:prepare`
   must re-register when the Account-side installation lacks a requested scope
   (not only when the local file differs), and readiness must fail loudly when
   the installation does not cover the site's scopes.
2. **The first-party app is "REZICS".** It shows as "QA-only loopback PKCE" in
   "to continue to …", sign-up and Connected apps. Register the local web
   client with the product name and first-party marker; Connected apps shows a
   first-party app as REZICS with grouped, human permission summaries instead
   of ~76 raw scopes.
3. **Sessions**: "Signed in on 36 devices", mostly "Unknown device". Group by
   client and user agent, name web sessions "REZICS on Chrome · Linux", and
   keep revoke per group.
4. **Seed clients**: the official-Zone seed creates a new OAuth client on
   every run; reuse one.
5. **Sign-up handoff**: after email verification the person must sign in
   again, and onboarding carries `next=/studio` for someone who joined from
   home. Continue the original authorization after verification and keep the
   original destination.
6. **Brand**: both sites use one logo mark with a product label beside it
   ("Account", "Admin").
