## Outcome

`task goal -- <goalctl arguments>` runs `bun scripts/goal/goalctl.ts` with the
arguments unchanged, from the repository root, and exits with goalctl's exit
status. It sets `GOAL_MAX_WORKERS=5` unless the caller already set it; it leaves
`GOAL_QA_SLOTS` unset so goalctl keeps its default. This restarts the stopped
G-536 with a smaller scope: the earlier `task production` facade is dropped
because `scripts/production` does not exist yet; deployment work adds its own
Task entry when it has commands.

## What to read

`AGENTS.md`; `Taskfile.yml` (follow how existing tasks forward `{{.CLI_ARGS}}`);
`docs/goals/README.md`; the argument parsing at the end of
`scripts/goal/goalctl.ts`.

## Do not build

No new TypeScript wrapper, dispatcher, command discovery or plugin mechanism:
one Taskfile entry is the whole feature. Do not change `goalctl.ts` behaviour.

## Checks

- `task goal -- status` and `task goal -- dispatch docs/goals/tasks/G-536.md --dry-run`
  behave like the direct `bun` calls (the dry run may refuse because G-536 is
  open; the refusal and its exit status must come through unchanged).
- A malformed call such as `task goal -- resume` exits non-zero with goalctl's
  usage text.
- `task goal -- test <path>` and `task goal -- slot -- true` still acquire and
  release a QA slot.
- Update the command table in `docs/goals/README.md` and the goalctl mentions in
  `docs/goals/worker.md` to `task goal -- …`; run `task docs:check`.
