## Outcome

Both sites ship eight UI locales: `en`, `zh-Hant`, `zh-Hans`, `ja`, `ko`, `de`,
`fr`, `es` (see `docs/plan/frontend.md`, "Languages and themes"). The web app
now routes all eight (G-280), but its catalogs keep every locale inline in one
`messages.ts` per feature, so translators working in parallel would all edit
the same files. The Accounts app already keeps one file per locale
(`apps/accounts/features/<feature>/messages/<locale>.ts`) but offers only `en`
and `zh-CN`. This task makes the layout uniform so per-language translation
tasks can run in parallel without conflicts. It does not translate.

1. **Web layout.** For the features in your claim (home, shell), keep English in `messages.ts` as the typed source and move every
   other locale to `features/<feature>/messages/<locale>.ts` (a `Partial` of
   the English shape), loaded per locale like the Accounts app does. Rename
   `zh-CN` to `zh-Hans`. Discover, search and work-page belong to G-283, studio and work to G-289,
   and auth to G-292; leave them and write the one-paragraph recipe for moving a feature in the
   handoff so the owner can follow it.
2. **Accounts to eight locales.** Replace `zh-CN` with `zh-Hans` everywhere,
   add the other six to the registry with English per-key fallback, and put
   a language picker in the Accounts footer, as Google Account does. Keep
   `?hl=`, `ui_locales`, cookie and `Accept-Language` resolution. Admin
   catalogs belong to G-262; leave them to your recipe.
3. **Account service.** The stored account language (`account-settings.ts`)
   accepts the eight BCP 47 tags; migrate stored `zh-CN` to `zh-Hans`.
4. **Coverage check.** A `task i18n:check` (script under `scripts/i18n/`)
   lists per app, locale and namespace the missing keys, extra keys and
   placeholder mismatches (`insert()` variables must match English). Extra
   keys and placeholder mismatches fail; missing keys are reported, not failed.
   Record the tool in `docs/development/toolchain.md` if it adds one.
