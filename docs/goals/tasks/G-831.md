## Outcome

The Work relations the catalogue fixtures need exist, and every relation reads in
both directions through the lexicon (decisions 45 and 49):

- Derivation kinds become lexicon DefinitionRefs, so Rewrite and Reboot are
  seeded data and a later kind needs no profile, TypeScript or Java change.
  `POST /v1/resources/{id}/derivations` writes v2; v1 records keep reading, their
  three fixed kinds mapped to seeded definitions, and the v1 route in
  `routes/works.ts` stays untouched until G-844 retires it. Unresolved sources
  stay representable.
- Sequel, SpinOff, correspondence (`equivalent`, `partial`, `revised`) and credit
  roles the native credit profile lacks (illustrator, concept supervision) are
  relation occurrences on G-832's definitions. Asserting one needs edit authority
  on the subject Work, as derivations do, not a root grant. Correspondence moves
  no progress or facts by itself.
- `GET /v1/resources/{id}/relations` is the one relations read: occurrences and
  derivations in both directions, with evidence, unresolved sources marked, the
  counterpart's summary and G-832's rendering contract for the requested
  languages, paged, with private participants withheld without existence
  leakage. T's generic page (G-629) links this read as its relations section
  instead of building a second one.
- A franchise is a Collection; the read also names the Collections that contain
  the resource, without a new membership relation.

## Approach

- `work-derivation-v2` stores `rv:derivationKind` as an exact relation-definition
  revision, validated by SHACL as a registry-only binding. If no generic check is
  possible, fall back to a closed five-kind v2 in TypeScript, SHACL and Java, and
  say so in the handoff.
- Relation occurrences reuse `relation/change.ts`; add only the Work-edit
  authority adapter in `work-authority.ts`.
- The read batches counterpart summaries (one page) and calls G-832's renderer
  once per definition.

- Stable keys (manager, 2026-10-01): G-832 merged with seeded lexicon definitions under random IDs, and its seed wrote a key→definition map only to a machine-local `.temp/seed/relation-lexicon/*.json`. Do not depend on that file. Store each seeded definition's stable key with the definition (for example `skos:notation`, written by the lexicon seed loader) and resolve derivation kinds (Rewrite, Reboot, Sequel, SpinOff, …) by key through Main; production bootstrap must work from the API alone.

## Do not build

- No new relation store, inverse facts, per-kind modules or franchise Work.
- No correspondence inferred from titles, numbers or text.
- No event-overlap relation (events are deferred); no UI (G-837).
- No change to native author, translator and editor credits.
