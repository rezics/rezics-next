## Outcome

`PUT /v1/works/{id}/reader-status` treats an omitted `startedOn`/`finishedOn` as "keep", `null`
as "clear that field" and a date as "set". Changing status from a card, a Work action or the API
never erases recorded dates; dates may be kept on any status. Old idempotency receipts replay
with their original meaning.

Verified defect, three layers: the Work/card quick action sends `startedOn: null, finishedOn:
null` with every status (`apps/web/features/catalogue/reader-store.ts`, `setStatus`); the route
requires both fields (`services/main/src/routes/library.ts`, `.put('/v1/works/:id/reader-status'`);
`ReaderLibraryStatusStore.write` rejects dates unless status is `read` and replaces the whole row
(`services/main/src/modules/library/status.ts`); and the Content constraint `library_status_dates`
(`services/content/migrations/370_reader_library.sql`) forbids dates on any other status. So
"read → reading" or re-marking "read" from a card wipes both dates.

## What to read

`docs/product/design-principles.md#meaning-survives-every-adapter`; the four locations above;
`apps/web/features/library/api.ts` (`setDates`, the detailed editor, which sends explicit dates);
`tests/qa/integration/library-status.test.ts`; `docs/goals/worker.md`.

## Approach

- Route: both date fields `t.Optional(t.Nullable(date))`. Store: under the existing row lock,
  merge omitted fields from the current row, then validate the merged row (valid dates,
  `started_on <= finished_on`). Drop the "dates only with `read`" rule.
- Migration 500 replaces `library_status_dates` with the order check alone.
- Digest: a request naming both fields keeps today's digest form byte for byte, so stored receipts
  still match; a request omitting a field uses a distinct canonical form in which omitted differs
  from `null`. Same key with a different form conflicts as today.
- Web: `setStatus` in `reader-store.ts` stops sending dates. Nothing else in the web changes;
  reading stats already count only `status = 'read'`.

## Do not build

No patch format, versioned command profile, new table, new route or client-side merge (never read
the row and send a full replacement). No change to `setDates`, the library page or stats.

## Acceptance

API (integration, `g-517`): set dates as read → status-only change to reading → read back both
dates; mark read again from a status-only request → dates unchanged; explicit `null` clears only
that field; `""` and invalid dates are 422; a replayed old full-form key returns the original
receipt; the same key with omitted fields conflicts; a concurrent stale write is 409 and loses
nothing; a revoked acting Agent is denied. Property test over the store: every omitted field
survives any sequence of status-only writes. Browser acceptance is in G-530.
