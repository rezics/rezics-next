## Outcome

Implement [visibility, listing and history](../../contracts/space.md#visibility-listing-and-history)
and the "addresses never grant reading" paragraph of
[durable addresses](../../product/urls-and-seo.md#durable-addresses). Today a
person-created Space is always public (`space/create.ts` writes
`disclosure: 'public'`), there is no unlisted state, the directory lists every
public Realm, admission is `self_join` plus `membership_policy`, and no setting
controls what a new member of a private Realm reads.

After this task, through Main's API:

1. A Space manager reads and changes four settings with one command and the
   usual authority, revision and idempotency: visibility (public, private),
   listing (listed, unlisted), history (everything, from admission; Realms) and
   admission (open, request, invitation), reusing the existing disclosure,
   `self_join` and `membership_policy` state rather than duplicating it. A
   person can mark their Agent unlisted.
2. Reads honour them: a private Space answers 404 to readers Access does not
   admit, except a join page (name, description, rules, request action) when
   admission is by request; members of a private Realm read history according to
   the setting; unlisted Spaces and Agents stay readable by link and are flagged
   so search, Discover, suggestions and sitemaps exclude them; responses for
   unlisted pages carry what the web needs to send `noindex` and
   `Referrer-Policy: no-referrer`.
3. A change takes effect on the next read and is covered by tests for denied,
   stale, concurrent and repeated changes.

G-937 (names, Space creation), G-938 (follows: paused follows of non-members)
and G-939 (query, directory and Discover exclusion) are running in parallel and
own those files. Expose one function other owners call to ask "may this reader
see / find this Space or Agent" and list the integration points in each of
those owners under PROPOSED TASKS; the manager resumes you to wire them after
their merges.
