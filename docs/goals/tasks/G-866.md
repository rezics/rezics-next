## Outcome

Stewards learn that a review is requested, proposers learn that changes were
requested or that their proposal was applied, rejected or reverted, and reviewers
learn of a new revision or a withdrawal, each with an exact destination
(proposal and revision) and a reason. Each person can mark an inbox item Saved
or Done independently of Read, undo either, and watch or mute a proposal.
Today the inbox has only read state (`440_notification_item_read.sql`), and no
producer fires for corrections (`notification-producers/producer.ts`).

## What to read

- `docs/contracts/editorial-protection.md#shared-collaboration-lifecycle` (Read, Saved, Done).
- `services/main/src/modules/notification/README.md` (the template's rules), `store.ts` (`SETTINGS_NOTIFICATION_TOPICS`, `StreamItem`), `dispatcher.ts`, `digest.ts`; `services/main/src/modules/notification-producers/producer.ts`; `services/main/src/routes/notifications.ts`.
- G-865's event rows and `allowedActions` (your producer source; read, do not change).

## Approach

- Migration 883: per-item triage (saved, done, revision) for the recipient, with undo by expected revision; Done applies to one item, so new activity creates a new inbox item.
- Migration 884: proposal subscriptions (principal, proposal, reason `author` | `reviewer` | `steward` | `manual`, level `participating` | `ignore`). Proposing, reviewing and being a required steward subscribe automatically; a person can watch or mute.
- Topics under purpose `governance`: `review-requested`, `changes-requested`, `proposal-revised`, `proposal-decided`, `proposal-withdrawn`, `proposal-reverted`. Append them to `SETTINGS_NOTIFICATION_TOPICS`, whose rule is that settings show only topics with an active producer. Email reaches them only through the existing digest counts and preferences.
- Extend the producer and store: one item per event and recipient (deduplicated), with disclosure rechecked at read and delivery as the dispatcher already does.
- Routes: triage `PUT /v1/me/notifications/{item}/triage`; `GET /v1/me/notifications?view=inbox|saved|done&reason=`; `PUT /v1/me/proposal-subscriptions/{proposal}`.

## Do not build

A second notification owner or outbox, thread grouping, notification rules,
per-resource watches for arbitrary resources (follows cover Works, Realms and
Concepts), push or email templates, signed unsubscribe (M8 G-731), or UI (G-868).

## Acceptance

- API (`tests/qa/integration/g-866*.ts`), over G-865's journey: the steward receives `review-requested`; the author receives `changes-requested` and later `proposal-decided`; a revision notifies reviewers; a duplicate event yields one item; Saved and Done are independent of Read and undoable; new activity after Done appears in the inbox; a muted proposal stops items; losing access to the target withdraws the item at read.
- Class guard: a conformance test that maps every G-865 event kind to exactly one topic, subject (proposal and revision) and reason. It fails when a lifecycle event has no producer.
