## Owner design decision before dispatch

The admitted operation is an **Org B operational-roster membership change**.
Its target remains the existing `(kind: org, ownerSubject: B, memberSubject)`
tuple and recipient consent; the selected issuer is A. Require one current
P-to-A representation for `access.membership.manage.org` and one B-issued,
A-recipient grant for the same action and exact B roster resource. Keep B's
existing direct manager path intact. A's own roster membership, editor role or
administrator role is never a substitute for P-to-A representation, and a
personal P-to-B grant cannot be combined with P-to-A representation. The effect
and immutable receipt bind principal P privately, issuer A, target B, the
selected representation identity/generation, B-to-A grant identity/generation,
and the original membership intent. The public response omits P's Account ID.

Extend the existing recipient-request/issuer-acceptance lifecycle with a
distinct action and profile; do not silently repurpose a `work.create` request
or mandate. Access migration 031 or later must admit the new action while
preserving existing request/mandate immutability, one-use request and exact
receipt replay. Scope and resource binding need an owner key for B's roster;
the current `work:create:root` gate alone is not a B resource proof. The owner
transaction must lock the recovery fence and relevant authority gate before
checking current principal, A and B subject state, exact representation and
grant generations, policy/terms, recipient consent and tuple generation.
After a successful change, the existing membership history and dependent-grant
revocation rules remain the source of truth. A separate IAM25 selector task
must test eligible-set rights without granting an acting A identity.
