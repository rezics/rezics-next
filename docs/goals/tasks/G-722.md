## Outcome

`task release:images` builds OCI images with pinned base digests for every
runtime role (Main API, Main relay and relay init, Account, the migration job)
beside the existing Fuseki image, and records their digests in the release
manifest. `task ops:migrate` applies Access, relay, Content and Account
migrations as a standalone, idempotent, locked job. Readiness reports storage,
schema head, graph epoch and index generation. `task ops:env-check -- <file>`
refuses a production environment file that carries development defaults (a
loopback SMTP host or Mailpit, fixture roots, example secrets, loopback public
origins) and refuses a payment provider row, so no sale is possible before
Stripe approval. The web, Accounts and about Workers build with a `production`
environment. Nothing is pushed or deployed.

## Approach

- One multi-stage Dockerfile in `infra/release/` from a digest-pinned Bun image, with the role chosen by command. It contains the application only: no dev dependencies, no `.temp`, no fixtures.
- `scripts/ops/migrate.ts` moves `migrateTracked` and the Content runner out of `release-artifact.ts` so that both use one implementation, with an advisory lock per database.
- `scripts/ops/production-env.ts` imports the existing specs and checks a production file against them. Encode dev-only defaults as data in that checker, not as edits to every spec. The container entrypoint runs the check before the process starts.
- Readiness: `services/main/src/schema-ready.ts` checks the recorded migration head against the release's expected head and, in production, an empty `commerce.payment_provider`. `services/account/src/schema-ready.ts` does the same for Account. Wire each with one line into `services/main/src/routes/health.ts` and `services/account/src/app.ts` as owner changes; if an open task claims either file, hand the wiring off.
- Add the Task entries as owner changes to `Taskfile.yml`.
- Write `docs/operations/release.md` (build, verify, migrate, roll out, roll back to the previous digests). It includes the **edge pause procedure**: Cloudflare rules that close sign-up, upload and posting paths while report, appeal, recovery and export stay open. List those paths from the route declarations.

## Do not build

Nomad jobspecs or GitHub workflows (the maintainer's `nixos` repository and the
deployment phase own them), a registry push, Kubernetes or Compose production
files, a second configuration system, per-service Dockerfiles, app-level pause
switches (deferred G-737), telemetry (deferred G-730), or Stripe integration.

## Acceptance

- `task release:images` twice gives identical digests for unchanged inputs. Each image starts, passes `/health/live`, and reaches `/health/ready` only after `task ops:migrate` against an isolated QA stack.
- `ops:migrate` run twice applies nothing the second time; two concurrent runs serialize.
- `ops:env-check` rejects each seeded development default and accepts a complete production example. The production Worker builds fail on loopback origins.
- Class guard: a test fails when a new envalid variable with a loopback or example default is not classified in `production-env.ts`.
