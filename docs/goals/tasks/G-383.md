## Outcome

Home is how people consume REZICS, and it waits on Main. On the shared stack,
with warm caches and a small seed, each call takes the following times
(the manager measured three calls each):

- `GET /v1/feed?sort=best&scope=all&limit=20` answers in 0.83–0.89 s;
- `GET /v1/onboarding/suggested-follows` answers in 0.37–0.39 s.

G-353 measured the signed-in home at 5–16 s to settle, with the feed as the
largest single wait. Set and meet a budget:

- **Budget.** Signed-in and signed-out `/v1/feed` (Best, New and Top;
  Following and All), `/v1/continue` and `/v1/onboarding/suggested-follows`
  answer in under 150 ms warm and 400 ms cold at the seed's size. They must
  stay under 300 ms warm at 10,000 Works and 1,000 followed items. Use the
  load corpus `scripts/load/`, which G-362 used to build 10k Works.
- **Find where the time goes** before changing anything: Fuseki queries,
  Postgres statements, sequential awaits, per-card reads. Record it in the
  handoff as a before/after table.
- **Fix it in the read path.** Batch per-card reads. Run independent reads
  concurrently. Precompute what the ranking needs in the existing feed
  projection (`feed/refresh.ts`, `feed/store.ts`) rather than at request
  time. Cache immutable card parts by generation. Keep every privacy,
  disclosure and staleness rule and the ranking constants in
  `feed/ranking.ts` as they are. Access migrations 800–809 are reserved if a
  projection table or index is needed.
- **Keep it fast.** Add a test that fails when a read exceeds its statement
  or query budget (count queries, as the recommendation README's cost
  contract does), and a load check at 10k Works.

Use only the backend; no web dev servers.
