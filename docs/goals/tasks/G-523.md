## Outcome

Decision 8 (the YouTube model): an Agent's controllers invite people to
co-control it, to act publicly as it or to manage its resources as themselves,
and they can change, revoke or leave. The storage exists, but product code
cannot drive it:

- `requireMandate`/`grants.authorize` demand exact mandates such as
  `access.invitation.issue`, which only tests insert.
- A new Organization gets an `agent.control` mandate but no `agent_control`
  row, so the last-controller trigger skips it (`054:155`).
- Invitations offer only `work.create`.
- The `agent-controller` protected change exists in the DB (`051:11`) but not
  in `ProposalInput`.
- Removing a controller bumps no work-scope epoch.

## Approach

1. `agent.control` on A satisfies the issuing mandate and ceiling for authority
   over A only, as `realm-management.ts:82,129` already does.
2. Migration 873: the trigger applies a floor of one controller when no
   `agent_control` row exists. Invitation acceptance may record an edge instead
   of a grant: `grant_id` becomes nullable, with a nullable `edge_id` and a
   CHECK that exactly one is set.
3. An invitation to a Person Agent offers one of:
   - `control`: acceptance applies the `agent-controller` change.
   - `represent`: chosen actions and expiry, stored as a `representation_edge`.
   - `manage`: a `permission_grant` on A's resources.
   Accept and revoke carry the expected authority epoch.
4. Leaving is `removeController` on one's own mandate, under the floor. Removal
   and recovery bump A's work-scope epochs, so admitted but unclaimed work as A
   fails at claim. Running work uses the existing strong-revocation drain.
5. Reads for G-524:
   - `GET /v1/agents/:id/access`, controllers only: Agents with offer, actions
     and expiry. The caller's own direct mandate is "you"; other principals'
     mandates appear only as a count. Pending invitations issued.
   - `GET /v1/me/agent-invitations`: invitations addressed to the caller.
   Transfer is invite, accept, then leave.

## Do not build

No new grant table, `scoped-authorization-v1` profile or authorization object:
`permission_grant`, `grant_lineage` and `representation_edge` are the object.
No transfer command, installations or AI assignments (M5), and no refactor of
the other modules' `'agent.control'` alternatives. Do not touch `admission.ts`
(G-508) or `provision.ts` (G-525).

## Acceptance

API journey (`tests/qa/integration/g-523-agent-control.test.ts`):
- A creates Organization O, invites B as controller, B accepts, A leaves; B's
  own leave → 409. Stale or expired acceptance → 409/410.
- A `represent`(`work.create`) delegate publishes as O but cannot invite. A
  `manage` delegate edits O's Realm as itself and cannot publish as O.
- Revoking between admission and claim → claim denied. B acting for O cannot
  read A's library. `/v1/agents/O/access` never returns a principal ID.
Class guard: the principal × Agent × action matrix fails if control leaks
across Agents, represent and manage merge, or the floor is removed.
