## Outcome

`docs/contracts/work-and-release.md#catalogue-acceptance-fixtures` defines
twelve queries over `tests/fixtures/catalogue/franchises.yaml`.
`tests/qa/integration/g-840-catalogue.test.ts` passes eight and still
asserts that queries 5, 7 and 12 are *refused* (`expectRejected`, pending
G-652, G-655, G-831, G-835 and G-847, all now merged); G-841 found query 2's
digital entry has no resolution route. After this task all twelve pass as
real assertions through the public API, and the PENDING list is empty:

- 2. Any ISBN *or digital entry* (provider + identifier) resolves to its
  release, realization, parent Work and Main Version.
- 5. Edition, story, translation, manga and anime reviews filter separately,
  and every aggregate states its scope.
- 7. Contradictory wiki facts ("dies in the web version", "survives in the
  books") coexist, each with its continuity scope and spoiler boundary.
- 12. Franchise and event membership never merges Works, and a contributor
  keeps one identity across Zones.

## Approach — express before you build

For each query, first try to express it with what exists, and change the
test, not the product, when it already holds: reviews target any resource
(G-650/G-652), so a "grain" is the target's base (release = edition,
realization = translation, Work = story; manga/anime are adaptation Works
reached by relation); Statements carry `applicability` (continuity scope as
an IRI) and G-846/G-847 give revelation positions (spoiler boundary);
contributors are one Agent IRI everywhere; event membership is a G-831
relation. Add product code only where a query cannot be expressed:
likely a digital identifier lookup on the existing release identifier
records, and a scope field on review aggregates. Backend one: no domain
branches, no new tables unless a lookup has no index.

## Do not build

No new review or statement model, no UI, no new Zone concepts.

## Acceptance

`g-840-catalogue.test.ts` asserts all twelve queries and its PENDING list is
