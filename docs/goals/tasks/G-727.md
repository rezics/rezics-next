## Outcome

`task ops:backup -- --out <dir> --recipient <key>` fences writers, records one
recovery cut, and captures every owner: TDB2 and its assembler and pins, the
Access, Content, Account, relay and operations PostgreSQL databases with WAL
positions, immutable objects, receipts and outbox positions, and signed coverage.
It encrypts the set to an off-host recipient and writes a manifest with
checksums and release digests. `task ops:restore -- --set <dir> --project <new>`
verifies the set and restores into new isolated volumes. It then applies the
current authority and erasure frontier, reconciles through
`POST /v1/owners/reconciliations`, rebuilds text, checks exact samples and
authorized and denied reads, and leaves the graph held until verification
passes. A timed drill proves the restore within the recorded budget at launch
data scale, and takeout (Account archive and library export) works on the
restored copy. Today these steps exist as parts plus a manual runbook
(`docs/operations/recovery.md`).

## Approach

- `recovery-set.ts` defines the manifest (owners, cut positions, checksums, release digests, coverage signature) as a typed schema. Backup and restore are thin sequences over the existing fence, coverage and fixture-owner functions.
- Encrypt with standard `gpg --encrypt` to a recipient whose private key lives off-host. Use no custom cryptography, and keep `RECOVERY_MANIFEST_HMAC_KEY` outside the set.
- Restore always targets a new project and refuses a running or original one. Serving stays held until coverage matches.
- Run the timed drill on an isolated copy of a launch-sized fixture. Record elapsed time per phase in the drill's evidence and state the budget in `recovery.md`.
- Replace the manual steps in `recovery.md` with the two commands, keeping the reasons and failure handling. Record gpg in `docs/development/toolchain.md` as an owner change (hand it off if an open task claims that file).

Manager note (2026-10-01): about 20 workers share this host now. Build the commands and their tests and prove them on a small restore of your own QA stack; do not run the full timed drill at scale — report its command, and the manager runs it with exclusive host capacity later.

## Do not build

Continuous replication, a backup scheduler or service (Databasus and the
deployment phase own scheduling), cross-host transfer, a new backup format per
owner, custom encryption, or a restore UI.

## Acceptance

- Drill (`tests/qa/fault-recovery/g-727*.ts`): back up a launch-sized stack under writes; restore into a new project; the samples, a deleted record staying deleted, a revoked grant staying revoked, search results and a user's takeout all match; elapsed time is within the recorded budget.
- A tampered checksum, a missing owner, an older coverage frontier or a restore over the original each fail closed.
- Class guard: the recovery coverage discovery test fails when a new owner table is neither in the set nor explicitly excluded.
