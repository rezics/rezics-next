## Outcome

G-1031 measured, on a disk-backed QA stack at 100 public Works
(`tests/qa/integration/g-1031-catalogue-write.test.ts`, commit `606611a9`;
profiles under `.temp/` in the `green-5` worktree): **one public Work write
takes 2.71 s and grows TDB2 by 6.21 MB; one classification decision takes
0.82 s and 1.60 MB.** A 10,000-Work catalogue would add about 60 GB before
compaction and take hours to prepare through the API, which
[writes go through the API](../../storage/workload-budgets.md#data-preparation-and-import)
and [perf by algorithm](../../storage/workload-budgets.md#complexity-contracts)
treat as a defect.

1. **Native phase timers.** Add timing and size counters inside the Fuseki
   command module for each write phase (validation, revision manifests,
   current-graph updates, projections, text indexing, commit), exported with
   the request trace so G-1024's work profile shows them.
2. **Find the amplification.** Identify what a small write rewrites in full:
   large literals (manifests, JSON states, validation reports), whole
   component graphs, copy-on-write index paths touched per triple, per-write
   history that duplicates unchanged data, repeated SHACL validation of
   unchanged shapes. TDB2's node table is append-only, so a rewritten large
   literal is a new node every time.
3. **Fix by layout and algorithm.** Store immutable payloads once by digest,
   write only the delta, validate only what changed, batch index updates, and
   keep audit history without duplicating unchanged data. Target a per-Work
   cost that does not grow with the catalogue, and report latency and bytes per
   write at 100, 1,000 and 10,000 Works before and after (disk-backed recipe).
4. Then prepare the 10,000-Work corpus once, keep a consistent backup, and
   rerun G-1032's query matrix (`tests/qa/integration/g-1032-query-cost.test.ts`
   and its scale probe) at 1,000 and 10,000 Works.
