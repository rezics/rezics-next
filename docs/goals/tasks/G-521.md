## Outcome

Decision 8: "Discovery is independent of task eligibility." Today discovery
(`contexts.ts:21-23,241-286`), the session Agent and the main-Agent preference
(`session-agent.ts:58,86-95,145-148`) all require `work.create` and the
`work:create` OAuth scope. So an Organization the operator controls (only an
`agent.control` mandate, `provision.ts:156-158`), a Person with only Realm or
moderation roles, or anyone while the `work:create` gate is closed has no
identity to pick. After this task one task-independent read lists every Agent
the operator may act as, with a localized label. Selecting any of them as the
session Agent works. Each task still checks its own eligibility at preflight
and admission.

## What to read

`docs/contracts/identity-and-access.md` (acting identity layers; one authority
model); `contexts.ts`; `session-agent.ts`; `routes/acting-contexts.ts`;
`services/main/src/modules/display-language/select.ts` and its use in
`services/main/src/modules/profiles/read.ts:46-67`; `representations.ts` and
`topology.ts` for how Access already walks complete representation paths.

## Approach

1. Add `GET /v1/me/agents`. It lists active Agents reachable through any live
   representation action (including `agent.control`), active provisions of any
   kind and live direct attributions. For Agent-to-Agent edges, reuse the path
   evaluation Access already does for admission; do not write a second
   traversal. Keep `bounds.actingContexts` and fail closed on overflow. Require
   the scope every first-party session holds, not `work:create`.
2. Each item has `{actingSubject, kind, handle, displayName: {value, language,
   direction}}`, chosen by `selectDisplayName` with the reader's languages.
   Define the schemas in the route file; do not edit the shared `api-responses.ts`.
3. The session-Agent and main-Agent reads and writes use the same "may act as"
   predicate instead of `eligibleSubject`/`directWorkCreateProof`. Keep the
   existing tables, revisions and receipts.
4. `/v1/me/acting-contexts?task=work.create` stays as the per-task eligibility
   read.

## Do not build

No new table, preference kind or profile. No task-and-profile defaults or layer
resolver: the pending IAM01 subcase for saved native-book defaults stays pending
(deferred). No roster of other controllers here (G-523). Do not change
`provision.ts` or the representation request flow.

## Acceptance

- API matrix (`tests/qa/integration/g-521-discovery.test.ts`), one row per
  identity: an Organization held only by `agent.control`; a Person with only
  `realm.members.manage`; an Agent with a `work.create` representation and no
  grant; any Agent while the `work:create` gate is closed. Each one appears in
  `/v1/me/agents` and can be set as the session Agent. `work.create` as each is
  still 403 where ineligible. After the representation is revoked, the Agent
  leaves discovery and a stale session selection cannot admit anything.
- It proves the pending IAM01 subcase: switching the session Agent after an
  admission leaves the admitted `acting_subject` unchanged.
- Class guard: filtering discovery through any single task makes the matrix fail.
- The picker and locale work is G-537.
