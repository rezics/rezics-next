## Outcome
A reader with thousands of Works can do the following, through the API and on
the Library page:
- page every status shelf and custom shelf in any supported sort and filter;
- see accurate counts;
- get reading statistics over the whole library;
- press "Read" on any Work and continue at its next unread chapter, even when
  that Work is not among the six in the Continue strip.

No request bound acts as a product limit. The Continue strip stays a declared
six-card preview. This is foundation 12
(`docs/contracts/queries.md#complete-traversal`) for the launch library.

## What to read
- Verified bounds:
  - `apps/web/features/library/read.ts:18-31`: the web reads a shelf whole, twelve pages of twenty, and sorts it itself. Main fails closed past 240 Works (`library/canonical.ts:5` `CANONICAL_STATUS_COST.candidates: 240`). There are five custom-shelf pages and 100 members per Collection.
  - `library/status.ts:20`: reading stats stop at 240 finished Works and 2,400 occurrences.
  - `collection/visible-page.ts:45`: 8 pages and a 100-item lookahead.
  - `apps/web/features/work-page/read.ts:314`: "Read" asks `/v1/me/continue` with `limit: 6`.
- `services/main/src/routes/library.ts` (shelves, `reader-state`); `modules/library/{canonical,public,read,stats,status}.ts`; `modules/continue/read.ts`.
- Content migrations 425–431 (library status tables).
- M4 G-517 (quick status edits keep dates) and M6 progress briefs touch nearby code; keep their semantics.

## Approach
- Status shelves get indexed keyset continuation in SQL for each supported sort: added, updated, title, rating, last read. Add indexes or sort-key columns in migration 602 only where a sort needs them. Title sorting uses the sort key the shelf already stores or a stored projection; never read the whole shelf.
- Counts are exact from SQL, or labelled as estimates.
- Custom shelves and Collections page members by continuation beyond 100.
- Reading stats are SQL aggregates over the whole library.
- Add a per-Work next-unread read, or extend `reader-state`, that uses the same chapter logic as Continue for one Work. The Work hub page (G-850, which depends on this brief) switches "Read" to it; this brief leaves `work-page/read.ts` alone.
- The web library adapter requests one page with the cursor Main returns. Delete the client-side whole-shelf sort and the page caps. Keep the existing UI; wire only the pager.

## Do not build
- No client-side "fetch N pages then sort".
- No new library table family and no search index for shelves.
- No change to shelf semantics, dates or statuses.
- No UI redesign.
- No discussion, Studio or catalogue traversal (G-553, G-554, G-556).

## Acceptance
- API integration tests, with a fixture reader of 1,000 Works:
  - Every shelf and sort is traversed; the concatenated pages equal the expected population, with no duplicates or gaps.
  - A Work added between pages behaves as documented.
  - A custom shelf of 250 members is traversed.
  - Stats count 300 finished Works.
  - Per-Work resume works for a Work ranked 500th by recency.
- Browser: open `/library` for the fixture reader, go to a late page, change the sort and reload. Counts and position hold. For the old Work, the API returns its next unread chapter.
- Class guard: fixtures exceed every former constant (240, 100, 8×100, 6). A test fails if the web adapter reads more than one Main page per rendered page.
