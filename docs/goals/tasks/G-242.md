## Outcome

The main site's session layer (merged in G-203: `apps/web/features/auth/**`)
lets people pick the public Agent they act as, but three Main gaps make it
awkward. Close them in the API, not the client:

1. **Labels.** `GET /v1/me/acting-contexts` returns Agent identifiers without
   display labels, so the picker shows "Agent 1a2b3c4d". Return each eligible
   Agent's public display name, handle (when one exists) and kind (person, pen
   name, organization), disclosure-safe, batched and bounded.
2. **Session Agent.** Implement the planned `GET/PUT /v1/me/session-agent`
   and the account's main-Agent preference (see the pending session-Agent
   operations retained in `docs/contracts/identity-and-access.md`), with
   compare-and-set and receipts like the existing preference routes. The web
   app currently keeps the session Agent in a cookie started from the
   `work.create` preference.
3. **Stale default.** Discovery returns `preferredActingSubject: null` for both
   a cleared and an ineligible default. Return `{ actingSubject, eligible }`
   (or equivalent) so the site can say which saved default stopped applying.

Keep backward compatibility where the web app depends on the current shape, or
update `apps/web/features/auth/**` in the same change through `goalctl owner`
(it is unclaimed after G-203 merged) and report it.
