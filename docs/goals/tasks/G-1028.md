## Outcome

On the shared stack, after a day of Main hot reloads, `/en` and
`/en/discover` sent their first byte in about 1.7 s and then never finished:
the route's loading skeleton (`RouteLoading`, app/loading) stayed for 60 s+
while Main's `/health/ready` answered in 8 ms. The web log showed
`[vinext] Server render error: Network connection lost. { retryable: true }`.
Restarting only the web resource fixed it (both pages then finished in 3–8 s).
G-1017's whole browser matrix failed for the same reason ("pages stay on
Loading…"). In production, every Main deploy could leave the web stalled.

Reproduce it: run the web against Main, restart Main a few times (and kill it
mid-response), then load pages; find each await that never settles (pooled
keep-alive connections to a dead Main, fetches or Eden treaty calls without a
deadline, an in-process cache or dedupe map that keeps a pending or rejected
promise, a stream never closed). Fix the class:

1. Every server-side read from the web to Main, Account or other origins goes
   through one helper with a per-request deadline proportional to the request
   (and the caller's remaining budget), aborts the connection on timeout, and
   retries an idempotent read once on a fresh connection after "connection
   lost".
2. In-process caches and dedupe maps never keep a pending promise past its
   deadline nor a failure as a value (G-1003's address cache, G-998's bounded
   reads, session refresh).
3. A failed or timed-out read renders its section's unavailable state; the page
   always finishes streaming.
4. A test that restarts or kills the Main stand-in mid-read and proves pages
   finish and later reads recover without restarting the web.
