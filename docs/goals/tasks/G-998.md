## Outcome

The manager's browser run 8 on main (`.temp/manager/direction-9-run8.log`,
main checkout, read-only) fails the addresses journey in every locale and
viewport, intermittently and differently per run, while curl from an
anonymous client gets the right 301 for the same URLs afterwards:

- en desktop: `GET /en/a/DFC1030E-EFA0-4041-A686-BEBCE31F645C?direction9=preserved`
  (a signed-in `page.request`, `maxRedirects: 0`) answered **503**.
- zh-Hant desktop and phone: `page.goto` of the upper-case UUID form ended at
  `/zh-Hant/a/dfc1030e-efa0-4041-a686-bebce31f645c?…` (lower case, never the
  canonical `/a/{sid}-{slug}`).
- en phone: the page never rendered an h1.
- run 7, under load: a 180 s timeout on the terminal GET and `/@agent-{uuid}` not answering 301.

`apps/web/proxy.ts` resolves addresses through `readAddress`
(`features/address/client.ts`), mapping any non-OK answer or a 10 s timeout to
503. Find what returns non-OK or stalls (Main's resolver, rate limits, or the
proxy's session refresh racing the resolve) and where the lower-case URL comes
from, and fix the cause. Also: `readAddress` sends no client IP, while
`features/api/bff.ts` forwards `x-rezics-client-ip` to Main's trusted-proxy
budgets, so every anonymous visitor's address lookup shares the web server's
single budget in production. Make every server-side web-to-Main read forward
the client the same way (one helper).

Unit-test the proxy decisions, including a transient Main failure (which
must not become a permanent-looking identity URL). Run browser journeys on the shared stack (from `apps/web`) with `REZICS_WEB_E2E_BASE_URL=http://localhost:3000 ACCOUNT_ORIGIN=http://localhost:3004`, `REZICS_WEB_AUTH_PRIVATE_PATH=/home/edge/projects/rezics/rezics-next/.temp/stack/rezics-dev/web-auth/private.json` and `REZICS_DIRECTION_9_ADMIN_PRIVATE_PATH=/home/edge/projects/rezics/rezics-next/.temp/datasets/administrator-72a030c5f7e58beba90986153ae1ef6c70b965857dcb6fad4e63970d132cdea3.json` (read those files at those absolute paths; never print them), `--project desktop-chrome --workers=1`, through `bun scripts/goal/goalctl.ts slot --`. The shared stack serves the main checkout, so product fixes reach it only after the manager merges: prove them with unit tests and stories, and say which journeys await the merge. Run `--grep "addresses: named"`
once your fixes are merged-equivalent, or explain what waits for the merge.
