## Outcome

The web's surface for `anime/continue-progress-across-devices-two-device-progress` replays this row's record through the production readers. For the visitor the record holds `GET /v1/resources/<Work>/parts?limit=7` (empty) and `GET /v1/reading-positions/<Work>?position=start&limit=1`, which is not enough to open the page as production opens it for someone signed out: the page's frame and opening reads are missing.

What must be true afterwards:

- The row's test records, for the visitor, every read the production Work page and its frame send when a signed-out reader opens this Work, with the query parameters and headers production sends. Take them from the production readers (`apps/web/features/work-page/read.ts`, `apps/web/features/work-levels/read.ts`, the Work page's route and the frame it renders in), not from the existing test. The visitor sends no `actingSubject` and no personal read; a request production does not send for a visitor is not recorded.
- For the five signed-in personas, add a read only where the handoff of your own reading shows the production page sends one that the record lacks; list them.
- The visitor's empty parts answer stays as the API gives it. No assertion and no cell changes; existing samples keep their answers apart from identities. The handoff names old and new identities and lists every new label with its request and status.
- If a read is answered 5xx, hand off with the request and the answer; do not vary it.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a visitor request with a bearer, a new row.
