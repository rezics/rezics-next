## Outcome

`services/main/src/infrastructure/pg-pool.ts` detects code that checks out a pool connection while it already holds one from the same pool. Under load that pattern exhausts the pool and deadlocks. QA stacks and owner tests run the detector in log mode, so new sites pass every gate and are fixed one at a time after they show up in logs: G-2540, G-2542 and G-2571 today. Fix the class.

1. Fix the sites still logged in QA runs since 18:00 UTC on 2026-10-14. For each one, reuse the held client or move the inner read outside the hold, with no behaviour change:
   - `library/copies.ts:91 libraryRecordWrite` → `media/store.ts:1684 avatarRows`
   - `realm-directory/index.ts:253 page` → `address/registry.ts:174 currents`
   - `library-import/reader-import.ts:170 withBatch` → `file-store.ts:161 pending`, `apply.ts:185`, `reader-import.ts:90/92 beginBatch`, nested `withBatch`, `library/status.ts` (87, 275, 331, 443), `library/follows.ts` (31, 53) and `media/store.ts avatarRows`
   - `access/topology-control.ts:24` → `preferences/store.ts:75 languagesForReader`, if G-2571's reader-language fix did not cover it
   Find any others by running the owner and integration suites with `REZICS_NESTED_POOL_CHECKOUT=throw`. G-2571's fixes in Content, Access, Media and rights are on wave/2 and show the pattern.
2. Then make throw the mode for every QA stack's services and for owner test processes, set in the QA harness's environment and not by each test. A test must fail when it causes a nested checkout. Production keeps log mode: it reports and does not refuse. Leave a test that proves a QA stack runs in throw mode.
