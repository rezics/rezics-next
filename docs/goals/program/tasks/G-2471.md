## Outcome

Web's G-2238 replays `recipes/collection-tracking-and-progress` through the production `/library` page and its collection views. Its first attempt found reads and command prerequisites missing from the record; `.temp/ref/g2238-library-records-mail.md` lists each one with persona, path and query.

What must be true afterwards, each request taken from the production client (the web's library readers and collection command clients, imported, not copied) with the path, query and body production sends (a request production does not send is not recorded):

- For each signed-in persona, the whole `/library` visit as production sends it: the persona's own shelf directory, the reading preview the directory leads to, the collection views, and the shelf's work-state read for exactly the occurrences the view holds (a Work that occurs twice is sent as production sends it). Record each read as production sends it, not as the mail paraphrases it.
- Before each recorded collection change (the owner's `remove`, and the others' `collection-change-denied`), the read production sends first (`?limit=1`), then the change with the body production builds. Keep each recorded body. If the read's answer stops the persona before the change, record where it stops and say so.
- Foreign shelf probes (another person's `actingSubject`): record them only if a production page sends them. The signed-in route uses the session's own acting Person. Say in the handoff which foreign-person refusal, if any, the route actually reaches.
- The visitor is sent to sign-in before any read: record nothing for the visitor and say so.
- Read the production path of `/library` and the collection view once and compare it with the record's labels for each persona; record every read or write still missing and list those beyond the reference.
- The reads one render sends together start together (`Promise.all`); writes and reads that need an earlier answer keep their order. A label names what the request is and is fixed where the request is written, never a counter: the web chooses a sample by its label and expects exactly one.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; if recording refreshes identities, every sample changes together.
- The record's requests run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's. One console line per persona gives the elapsed time of the proof and of the visit. The file has a 480 s wall.
- A 5xx that is the final answer: hand off with the request and the answer, do not vary it; do not run a third time.

The handoff summary names old and new identities, every new label with its request and status, and the states each persona reaches.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a read at the Account origin.
