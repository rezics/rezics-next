## Outcome

Measured 19:45 to 20:45 UTC on 2026-10-14: 179 worker turns did nothing but poll a running command, costing 29.3M of 105.1M input tokens (28%). Each poll re-reads the worker's whole context, about 150k tokens.

The cause is `task goal -- job`. It holds a command inline for up to `JOB_INLINE_MS` (90 s) before it parks. Meanwhile the worker's tool call returns after its own yield (1 to 30 s), so the worker polls about five times per job. Parked jobs run a median of 473 s. The coordinator wakes the worker a median of 36 s after the job ends (p90 61 s, max 237 s).

Make both waits short:

1. Park once the command has run about 20 s, so one tool call returns either the result or `PARKED`. State the bound in `docs/goals/worker.md` with the exact yield to use for a `job` call: one call, no polling.
2. Wake the worker as soon as the job ends, not at the next coordinator pass. The job's executor process, which already owns the command, records the exit and triggers the same wake path. The coordinator pass stays as the fallback for a lost executor, keeps the single-continuation guarantees, and never wakes twice.

Prove it:

- tests for the 20 s park;
- the immediate wake;
- no double wake when both the executor and the pass see the end;
- the fallback when the executor dies.

Then a live measurement on this host: a 60 s command run through `job` in a real worktree is woken within 5 s of its end. Report it.
