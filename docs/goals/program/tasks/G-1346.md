## Outcome

Changing the shared dev stack (refresh, AppHost restart, a manager's repair)
should never wait behind QA that runs on isolated stacks, and a queued refresh
should never run stale code. The shared backend is pinned (G-1347), so merges no
longer reach it. Two problems remain from 2026-10-07:

- Kernel's AppHost repair waited behind browser jobs for the heavy lock while
  Main was down. Later refreshes queued behind unrelated browser runs.
- A refresh imports its inspection code in the CLI process before it waits. When
  kernel repaired inspection while trust-ops' refresh was queued, that refresh
  would have run the old code. Ever since, each Goal's refresh announces a
  "hold all Main code merges until my checkpoint", which stalls every Goal's
  merges for each wave.

1. Give shared-stack lifecycle its own lock, one holder at a time, separate from
   the heavy QA lock and QA slots. It covers `task dev:refresh` (keep G-1332's
   coalescing) and a manager's repair command (`task goal -- slot --recovery --
   <command>` or similar). Browser runs and Storybook keep the heavy lock among
   themselves. Memory-heavy lifecycle steps (image and native builds) wait
   through `scripts/qa/host-admission.ts` instead.
2. After acquiring its lock, a refresh re-executes itself from the staged
   revision's checkout in a fresh process, so it never runs code loaded before
   it waited. Merges can then continue while a refresh is queued or running;
   the refresh stages the revision it froze.
3. Update the refresh and recovery paragraphs in `docs/goals/README.md`, and say
   that merges need no hold while a refresh is queued.

## Checks

Unit tests with stub locks:

- A refresh starts while a browser run holds the heavy lock.
- A repair takes no QA slot.
- A queued refresh whose own inspection code changed on `main` while it waited
  runs the new code from the staged checkout.

Then run one real `task dev:refresh -- --wait` on the live stack while a browser
run holds the heavy lock, and report both timings.
