## Outcome

Changing the shared dev stack (refresh, AppHost restart, a manager's repair)
should never wait behind QA that runs on isolated stacks, and should always run
against one revision. On 2026-10-07 it did neither:

- Kernel's AppHost repair waited behind two browser jobs for the heavy lock,
  then for an ordinary QA slot behind its own tests, with Main down throughout.
- A refresh failed with Main stopped. In the two seconds before its retry queued,
  a browser run on an isolated stack took the heavy lock.
- Kernel's first Turtle refresh failed because a second material merge
  fast-forwarded `main` mid-refresh. The native image came from one revision
  and model alignment read the next.

1. Give shared-stack lifecycle its own lock, one holder at a time, separate from
   the heavy QA lock and QA slots. It covers `task dev:refresh` (keep the
   coalescing G-1332 adds) and a manager's repair command
   (`task goal -- slot --recovery -- <command>` or similar). Browser runs and
   Storybook keep the heavy lock among themselves. Memory-heavy lifecycle steps
   (image and native builds) wait through `scripts/qa/host-admission.ts`
   instead.
2. Serialise material merges with refresh. A `goalctl merge` whose diff
   changes what `refreshPlan` treats as material takes the lifecycle lock for
   its fast-forward. Code-only merges do not. A refresh therefore reads every
   input from the revision it recorded at start; if it can still see a moved
   `main`, it re-plans rather than failing.
3. Update the refresh and recovery paragraphs in `docs/goals/README.md`.

## Checks

Unit tests with stub locks:

- A refresh starts while a browser run holds the heavy lock.
- A repair takes no QA slot.
- A material merge waits while a refresh holds the lifecycle lock; a code-only
  merge does not.
- A refresh whose `main` moves mid-run converges on one revision.

Then run one real `task dev:refresh -- --wait` on the live stack while a browser
run holds the heavy lock, and report both timings.
