## Outcome

What landed in the tool is what the coordinator does next, and one busy file never stops it. Five defects met on 2026-10-13, each a step committed when its test passes:

1. **A landed change of the tool takes effect without a hand.** The coordinator is one long process (`coordinatorCommand` in `scripts/goal/manager-commands.ts`; the pump imports `settle.ts` once): the queue's pass and the planning event landed at 12:42 and 12:59 UTC and the process started at 12:07 UTC ran neither until the supermanager restarted the service. Restarting kills what runs in the service's control group, and a landing is usually in it. When a file under `scripts/goal/` on `main` differs from what the process loaded, the next pass runs the new code, and no landing, gate or turn in flight is ended for it. Choose between running each pass in its own process and ending the process between passes when nothing it started is alive (the unit restarts it; say what the unit must contain if it must change, and do not edit files outside the repository); give the reason in the handoff.
2. **A locked event store is waited for.** The process exited at 12:07 UTC on `database is locked` after 52 minutes and systemd restarted it. A store's statement that meets a lock waits within a bound and is tried again; the process ends only on an error that a wait cannot cure, and says which statement.
3. **A row under an open outcome task is not uncovered.** `task goal -- planning` counts 23 rows for the api while ten Realm closure rows are being re-proved by one outcome task that names them. A row is covered by an open task of kind `implementation` or `outcome` whose `rows:` names it.
4. **The queue lends an area.** `task goal -- queue <brief> --allow-area` keeps the loan with the entry and dispatches with it; without the flag a brief that names another Goal's file is refused at queueing, as `dispatch` refuses it.
5. **A brief that waits for the program's reading says so.** The api's mechanism brief stood an hour with `Held for Program's read` in it and no mail. The manager's role card (`MANAGER_ROLE_CARD` in `scripts/goal/coordinator.ts`) gains one line: a brief that needs a reading or a ruling by the program is mailed to the program at once, with the brief's path and the question in one sentence.

Do not build: a change to a turn's bound, to mail's delivery, to `settle.ts`, `regress.ts`, `check.ts`, `merge.ts` or `unit-gate.ts` (other tasks hold them), a second service, a change to the planning event's text beyond step 3.

`task goal -- check`, and the three test files once with `CLAUDECODE=1`. Then give the output of `task goal -- planning api` on the real state in the handoff. Wait on a running command with one long call (`yield_time_ms: 300000`).
