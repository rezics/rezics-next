## Outcome

`scripts/load/work-profile-corpus.ts` seeds a corpus through public commands and defines `CorpusBackupDriver`, but only unit tests implement that interface. `scripts/load/catalogue-backup.ts` already retains and restores a stopped copy of a QA stack (`retainCatalogueBackup`, `restoreCatalogueBackup`). Join them so there is one way to seed performance data.

1. One real `CorpusBackupDriver` built on the stopped-copy code in `catalogue-backup.ts`: `backup` quiesces writers and retains all owner stores; `restore` produces an isolated writable copy and returns only after migrations, readiness and a smoke read pass. Reuse the existing functions; move shared code rather than copy it.
2. `prepareWorkProfileCorpus` with that driver builds the corpus once and retains a checkpoint at each of the three scales of a dimension; a later call with the same recipe finds the compatible retained manifest and builds nothing.
3. `restoreWorkProfileCorpus` restores one checkpoint as an isolated copy. Two restores of the same checkpoint do not share state: a write to one is not visible in the other.
4. The memberships dimension becomes 2/8/32 so every dimension is geometric.
5. Restore, start and readiness of one checkpoint finish within 600 seconds, enforced by the existing deadline, and the test prints the measured time.

Smallest change: one driver file and the calls that use it. No new corpus format, no raw writes into the stores, no larger scales, no change to the profile children that still grow their own live corpora (they move later).
