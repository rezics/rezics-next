## Outcome

`recipes/catalogue-pagination-in-its-zone` has its record, `tests/qa/fixtures/outcomes/recipes/catalogue-pagination-in-its-zone.json`, written by its own outcome test. The test on `main` already records as `OutcomeRecorder` in `tests/qa/support/outcome-test.ts` asks; two recordings on 2026-10-13 stopped before any proof because the Recipes fixture builder demanded 201 from a write the busy host answered with 202 `reconciling`. The task this one depends on makes that preparation read the write to its end.

1. Run the row's outcome test so that it records, and check in the record. The six persona proofs pass unchanged; no assertion changes and no cell changes state.
2. The record holds what the row's page reads to render: confirm against the web route that shows the row under `apps/web/features/` (read it, change nothing there) and add to the test, for one persona and under a label a story can name, any read the page makes that the proofs do not: the first page, a following page by its cursor, the last page, and the empty answer where the API gives one. Never write an answer by hand.
3. `scripts/api/answer-records.guard.test.ts` passes. The handoff gives the record's bytes and samples, the recording run's seconds, and any read of the page that could not be recorded, with the reason.

An answer of 500 or above is a fault of the API: hand off `partial` with the request and the answer, never recorded under a refusal's label. If preparation still stops on a 202, hand off `partial` with the request, the pending answer and the builder's line: the helper has missed a preparation write.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or the fixture builders, another row's record.
