## Outcome

The competitor coverage report (`.temp/ref/competitor-coverage.md`, row **B04**, and its closing decision) finds that recipe managers on Paprika or Mela shop and cook from their list. A set of recipe links cannot tell them what to buy or what is already done, and the report says not to court them until the capture–plan–shop loop works. Capture is done: Paprika and Mela import, G-2632.

This step defines the capability API-first (`docs/goals/method.md`), on the engine's existing owners. There is no shopping backend.

1. **Decision note.** Write `docs/architecture/actionable-collections.md`. Base it on the report's smallest capability:
   - Collection entries and run state, keyed to occurrence identity, with checked or pending status;
   - an optional declared action or query binding;
   - a separately named, unit-aware sum and stock-offset procedure over ingredient occurrences.

   Read the existing Collection, Recipe occurrence and quantity owners first. Decide what is reused, what is added, and why. Quantity arithmetic is optional, not a property of every list. Checking an item never edits the recipe.
2. **Contract.** State each new or changed operation's request and response at the API, in the owning contracts.
3. **Outcome row.** Declare `recipes/cook-and-shop` with six pending persona cells. Write its outcome test against the public API using the report's falsifying scenario:
   - a shared list from two recipes;
   - compatible eggs add;
   - flour used in two steps keeps its provenance;
   - "to taste" stays unresolved;
   - incompatible units stay separate;
   - two shoppers' retried checks converge;
   - each persona sees only what its role allows.

Do not implement the capability in this step. The row stays pending and its tests fail for the stated reason. Program reviews the decision note before an implementation step is briefed.
