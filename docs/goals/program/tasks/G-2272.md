## Outcome

The checked-in record of `visual-novels/catalogue-browse-and-search-in-its-zone` is the one its outcome test writes today. The test on `main` asks two reads the record does not hold, the catalogue's release-filter query and the platform-access read: they were added to the test after its first recording, and the second recording's preparation failed once with 503 `dependency_unavailable` while the host ran seventy processes. The record on `main` is that first recording (1.9 MB, 175 samples).

1. Run the row's outcome test so that it records, as `OutcomeRecorder` in `tests/qa/support/outcome-test.ts` does for every row, and check in the record it writes. The six persona proofs pass unchanged; no assertion changes and no cell changes state.
2. Change the test only if a recorded read's label, request or order must be corrected for the two reads to be recorded; no existing sample's label changes. Never write an answer by hand.
3. `scripts/api/answer-records.guard.test.ts` passes. Give in the handoff the samples added (persona, label, method, path, status), the record's bytes and samples, and the recording run's seconds.

If preparation answers 503 again, run it once more. A second 503 is a fault of the API's preparation under load, not of the record: hand off `partial` with the request, the answer and the run's log path, and leave the record on `main` as it is. An answer of 500 or above inside a proof is likewise handed off, never recorded under a refusal's label.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record, the conditional reads whose data the fixture does not hold (release detail, custom shelf, showcase media).
