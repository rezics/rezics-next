## Outcome

The first real enrollment (trust-ops, session `01a114cb-4d63-7f23-bf70-1610b4db2b2b`)
was refused, and it could never succeed on this host. `nativeOwner` in
`scripts/goal/coordinator.ts` treats every Codex process on the same account
home, other than `codex exec`, as owning the session. On this host that
includes:
- the account's long-lived `codex app-server daemon` (PID 22199, 34 hours old);
- the ChatGPT desktop app's bundled `/usr/lib/chatgpt/resources/codex ... app-server`
  and `... exec-server --remote ...` processes, which share `~/.codex`.

None of these owns the session, and they cannot be stopped. Open files cannot
identify the owner: Codex appends to the rollout file and closes it. What does
identify it is the environment Codex gives the tools it runs: they carry
`CODEX_SESSION_ID` and `CODEX_THREAD_ID` equal to the session (for example
trust-ops' `next-event.sh` child).

Make enrollment an explicit handover:

1. `coordinator enroll` takes `--previous-owner-pid <pid>`. The enrolling
   manager names it: the interactive Codex process for that session. The
   coordinator records that PID with its start time and treats the session as
   owned while that exact process lives.
2. A process also owns the session if its argv contains `resume <session>`, or
   its environment has `CODEX_SESSION_ID` or `CODEX_THREAD_ID` equal to the
   session (a running tool of that session). Ignore all other Codex processes on
   the account, including `app-server`, `exec-server` and the ChatGPT app's.
3. Enrollment may happen while the previous owner still lives. The first wake
   waits until it has exited; status shows "waiting for previous owner <pid>".

## Checks

Unit tests with fake `/proc` entries:
- the named owner alive blocks, and its exit allows;
- a reused PID with a different start time does not block;
- `resume <session>` in argv blocks;
- `CODEX_THREAD_ID=<session>` in the environment blocks;
- `app-server`, `exec-server` and the ChatGPT-bundled processes do not block.

Then run `nativeOwner` against this real host for the trust-ops session with
`--previous-owner-pid 3999388`, and report what it returns. It should block only
because of 3999388 and its `next-event.sh` child. Do not enroll or stop any
manager.
