## Outcome

The web's surface for `zone/a-zone-without-a-realm` replays this row's record through the Zone's management page and its saved preview. The published standalone visit is recorded and its surface passes; management and the saved preview are not: `.temp/ref/g2333-record-gaps.md` lists what the surface's first attempt found missing.

What must be true afterwards, each request taken from the production client and sent with the path, query and body production sends (a request production does not send is not recorded):

- For each signed-in persona, the management visit as the production route sends it, from its first read to the state the persona ends in: the configuration read (`GET /v1/zones/{zone}/configuration?actingSubject=…`), the Zone read with the acting Person (`GET /v1/zones/{zone}?actingSubject=…`), the address read that follows the owner's configuration (`GET /v1/addresses/resolve?scope=space&key=…`), and whatever else the page sends. A persona without editor authority gets the refusal production reaches, recorded where it stops.
- The saved preview as production sends it: follow `loadCompleteZoneNavigation` and the composition reads in the web's source and record the whole sequence it actually sends, not a guessed one.
- For each persona that reaches the editor: save, reopen, the stale-draft 409 and publication, in the order and with the bodies, retry keys, revision and home document identity the editor sends. `realm` stays null; the original saving Agent's credit is kept.
- The visitor's management visit redirects to sign-in before any editor read: record nothing for it and say so in the handoff. No synthetic visitor authority.
- Read the production path of the management page and the saved preview once and compare it with the record's labels for each persona; record every read or write still missing and list those beyond the reference. This is meant to be the row's last re-recording.
- The reads one render sends together start together (`Promise.all`); writes and reads that need an earlier answer keep their order. A label names what the request is and is fixed where the request is written (for example a name in an `AsyncLocalStorage` the recording fetcher reads), never a counter: the web chooses a sample by its label and expects exactly one.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; if recording refreshes identities, every sample changes together.
- The record's requests run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's. One console line per persona gives the elapsed time of the proof and of the visit. The file has a 480 s wall.
- A 5xx that is the final answer: hand off with the request and the answer, do not vary it; do not run a third time.

The handoff summary names old and new identities and every new label with its request and status.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a read at the Account origin, a change to the shared editor (it belongs to the Zone authoring surface).
