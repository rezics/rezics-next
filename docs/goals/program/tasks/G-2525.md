## Outcome

Program measured where workers wait, from 06:00 to 09:25 UTC on 2026-10-14. 37% of worker input tokens were polls: a worker re-sending its whole context (median 144k tokens) to ask whether a command had finished. A Codex poll blocks at most 60 s. By command waited on: the worker's own `task goal -- check` 43%, tests that start a QA stack 15%, type checks and tests chained after `task gen` 12% (`task gen` itself takes 1-2 s). Inside a check, the 38 repository guards run one after another in a single `bun test` process: 295 s summed, 301 s wall. Six files cost 81%: authentication-subject 74 s (one case 45 s), mechanism-dependencies 65 s, serialization-points 31 s, web-acting-identity 27 s, g-543-rate-limit 22 s, g-1046-sql-relations 20 s. The type check had a median of 52 s but p75 of 172 s while queued for memory (web needs 5.5 GiB plus 8 GiB reserve). Type-aware lint took 60 s and peaked at 9.2 GiB.

Four guards spend their time parsing the repository in JavaScript: mechanism-dependencies (65 s, it runs dependency-cruiser over the whole import graph and holds 2.5 GiB), serialization-points (31 s), g-1046-sql-relations (20 s) and web-acting-identity (27 s; it already uses ast-grep). The maintainer's direction: dev tools with performance requirements may be written in Rust.

1. Profile each of the four first and write down where the time goes. If a guard is slow because of its own algorithm, fix it in TypeScript; Rust is for parsing.
2. Where parsing dominates, build one Rust tool (a Cargo package under `tools/`, pinned with the repository's Cargo 1.98.1) that parses the repository once: TypeScript and TSX with oxc (oxc_parser and oxc_resolver, the engine inside oxlint) for the import graph and the facts these guards need, and SQL with the real PostgreSQL parser (libpg_query, through the `pg_query` crate) for relations and serialization points. It writes one JSON index, and an unchanged input set reuses its last index by content digest.
3. The guards keep their rules, debt lists and messages in TypeScript and read facts from the index. Every existing guard test keeps passing unchanged, including the ones that must fail on a new violation.
4. Record the tool, its crates and the build command in `docs/development/toolchain.md`. `task gen` or the guard runner builds it when missing.

Target: each of the four guards under 3 s on a warm index, and the index itself built from scratch in a few seconds. Report before and after per guard.
