## Outcome

The record of `realm/roles-and-team` holds the answers to the requests the production roles and members pages send, so their stories run the production readers on a replaying fetch. Web read the pages' request graph and found four groups the record lacks (mail of 2026-10-13 20:05 UTC). Identities below are this recording run's: the row's Realm, its personas' subjects, its role and its member. No identity of an earlier record is kept.

Read the pages and readers under `apps/web/features/manage/` (`admin-api.ts`, `roles-view.tsx`, `members-view.tsx` and the Realm frame's header reader) only to copy each request's exact spelling, parameters and client; change nothing under `apps/`.

1. Owner's members page: `GET /v1/agents/<the member's agent>`, no query and no body, as production's anonymous public profile client sends it (`member-profile`; record it for the owner through the visitor's session, as `work-showcase` is recorded in `tests/qa/integration/outcomes/anime/navigate-a-thousand-episode-inventory-thousand-chapters.test.ts`).
2. The frame of each persona but the owner: `GET /v1/realms/<Realm>?actingSubject=<the persona's subject as the row uses it>&language=en`, no body (`frame-realm`). The existing header samples without `language` keep their labels and requests.
3. Owner's preview: `POST /v1/realms/<Realm>/role-impact`, no query, with the body of the row's existing `/role-changes` request less `impactDigest` (`role-impact-preview`). The existing 201 save receipt stays; no pending answer is asked for or invented.
4. The members page of each persona but the owner: `GET /v1/realms/<Realm>/invitations?actingSubject=<the persona's subject>`, no body, as the page's parallel read spells it (`members-invitations`).
5. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes.
6. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added (persona, label, method, path, status), the record's bytes and samples before and after, the recording run's seconds, and any read of the two pages' server render that is still not in the record, listed and not recorded.

An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation: run once more, then hand off `partial` with the request, the answer, the host's load (`cat /proc/loadavg`) and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record.
