## Outcome

The supermanager tells the maintainer on Telegram and records his answers. Telegram is a notice board: nothing listens there. The module is `scripts/goal/notify.ts`, run as `bun scripts/goal/notify.ts <command>`. Wiring into `task goal --` is one line for each command after the `goalctl.ts` split lands and is not this task: do not touch `goalctl.ts` or `coordinator.ts`.

- `ask --goal <goal> [--task <id>] --question <text> --option a=<text> … --recommend <letter> [--default <letter> --default-at <UTC time>]`, with two to four options, records the question under the next decision code (`D-1`, `D-2`, …, never reused) and sends one message: first the code in code style; then the Goal and task, the question, the options by letter, the one recommended, and the default with its time when given; the last line is the recommended answer ready to copy, in code style, such as `D-12 a`.
- `tell --event start|pause|stop|fault|allowance|host --goal <goal> [--task <id>] [--note <text>]` sends a notice from one fixed template for each event.
- `decide <code> <letter> [--note <text>]` records the answer and its time; a second answer to a code is refused without `--replace`. `decisions [--all]` lists the open questions: code, age, question, recommended, default and its time.
- A send that fails (network, a status that is not 2xx, `ok: false`, a 429) leaves the message in an outbox; the command has still recorded it, says it is queued and exits 0. `flush`, and `ask` and `tell` before their own message, send the outbox oldest first; no message is sent twice. The flush function is exported for the coordinator.
- One HTTPS call: `fetch` to `sendMessage` with `parse_mode: HTML` and escaped text. No library, no listener, no button, no `getUpdates`.
- The store is one SQLite file in the Goal state directory, opened as `scripts/goal/mail.ts` opens its store, with the directory as an option so tests use a temporary one.
- Configuration: the token is `telegram[0].token` of the file named by `GOAL_TELEGRAM_SECRETS` (default `../.secrets/bots.json` from the main checkout); the chat is `GOAL_TELEGRAM_CHAT` or the file `telegram-chat` in the state directory; the API base is `GOAL_TELEGRAM_API` (default `https://api.telegram.org`). A missing token or chat queues the message and says what is missing.
- Safety: the token appears in no output, error, log or stored row, and the request URL is never printed. Every field is plain text with a limit (question 500, option 200, note 300 characters); a field over its limit, with a line break or with a code fence is refused, not cut. Messages carry a Goal, a task, a question and numbers.

Never read the real `bots.json` and never call the real API. Tests and your own runs use a fake Bot API (`Bun.serve` on a local port) and a temporary secrets file. The first real message is the supermanager's.

Do not build: a daily digest, message editing or deletion, reading replies, more events, documentation.

## Checks

`task goal -- test scripts/goal/notify.test.ts`, and once with `CLAUDECODE=1`. It covers: the exact text of an ask with and without a default; each event's template; the code sequence across two processes; `decide`, `--replace` and `decisions`; a failed send queued and sent once, in order, by a later flush; a 429 that stays queued; the token absent from stdout, stderr and the store on every failure path; each limit and refusal. `task scripts:typecheck`; oxlint and ast-grep on the two files; `task guards` once. Wait on each running command with one long call (`yield_time_ms: 300000`).
