## Outcome

The record of `realm/membership-and-admission` holds the answers to the requests the production join, requests and joined-Realm pages send, so their stories run the production readers on a replaying fetch. Web read the pages and found the gaps below (mail of 2026-10-13 20:22 UTC). Identities are this recording run's: the row's Realms and its personas' subjects. No identity of an earlier record is kept.

Read the pages and readers under `apps/web` (`readSpacePage`, `loadRealmView`, `readRequestsAtAddress` and what they call) only to copy each request's exact spelling, parameters and client; change nothing under `apps/`.

1. Requests inbox, stranger, member, moderator, operator: `GET /v1/realms/<Realm>/join-requests?actingSubject=<persona>&limit=50&q=` (`requests-refused`); the existing 403 samples without `limit` and `q` keep their labels.
2. Requests inbox, owner: the same request with the owner's subject (`requests-first-page`) and the page its continuation opens with the cursor unchanged (`requests-continuation`); the inbox after the decisions with `limit=50&q=` (`requests-after-decisions`). Make the fixture hold more than fifty requests only if the proofs already do; otherwise record the first page and say in the handoff that it has no continuation.
3. Join page, stranger: `GET /v1/realms/<Realm>?actingSubject=<stranger>` (`join-realm`); `GET /v1/realms/<Realm>/join-requests/mine?actingSubject=<stranger>&limit=50` once while the request is pending (`own-request-pending`) and once after it is withdrawn (`own-request-withdrawn`); and each further read the signed-in join route makes before it can send the recorded request.
4. Join page, operator: the supporting reads of the signed-in join route that make the recorded 201 reachable, as in 3.
5. The withdrawal and the decisions: where a proof already makes them, they are recorded under labels with their real method, path, body, expected revision and command key. A state the proofs do not reach (an invitation, a pending 202) is listed in the handoff and not invented.
6. Joined Realm, member and moderator: each request `loadRealmView` and the production frame make for one visit, the presentation and the own-ban read where platform access opens it included (`frame-*`).
7. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes.
8. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added (persona, label, method, path, status), the record's bytes and samples before and after, the recording run's seconds, and each read of those pages that is still not in the record, with the reason.

An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation: run once more, then hand off `partial` with the request, the answer, the host's load (`cat /proc/loadavg`) and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record, a new endpoint.
