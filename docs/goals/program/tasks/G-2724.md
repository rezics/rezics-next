## Outcome

Surface and landing gates for web tasks select shared QA-harness tests that the change cannot affect, and those load-sensitive tests then fail the gate. `selectSurface` (`scripts/goal/surface-gate.ts:121`) adds affected consumers through `scripts/qa/affected.ts`, which seeds modules from textual path references and follows reverse imports (`affected.ts:546`). A changed registry or record file therefore pulls in everything that imports its reader. Two recorded paths: G-2331 changed `scripts/static/web-continuations.inventory.json`, and selection reached the repository guard registry, the unit gate, QA slots and `tests/qa/unit/memory-admission.test.ts`. G-2461 changed an outcome test, and selection reached the launch-coverage registry, outcomes, the regression runner, `scripts/qa/core.ts` and the harness tests. The research report in your refs has the evidence.

Distinguish a reference to a data or registry file from a runtime dependency. A changed registry entry selects the guards that validate that registry, not every importer of its reader. Keep the relevant web and API guards and the genuine runtime consumers. Do not exclude `tests/qa/unit` wholesale: some guards there validate web and API changes legitimately. A change to the harness itself still selects the harness tests.

## Checks

Unit tests in `scripts/qa/affected.test.ts` that replay both recorded change sets (G-2331's and G-2461's changed files, from `git diff --name-only main...goal/g-2331` and `goal/g-2461`) and show that they still select their validating guards and no unrelated harness test. A change under `scripts/qa/` must still select its harness tests. `task goal -- check`.
