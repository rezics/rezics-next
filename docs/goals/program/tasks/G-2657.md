## Outcome

The competitor coverage report (`.temp/ref/competitor-coverage.md`, row **B03**, and its closing decision) finds that "will this fit my available time?" is HowLongToBeat's core job and VNDB exposes lengths. Percentage or chapter completion cannot answer it, and the report says to prove B03 before trying to replace a duration-driven game or visual-novel task.

This step defines the capability API-first (`docs/goals/method.md`) on existing owners. There is no game-only telemetry service.

1. **Decision note.** Write `docs/architecture/activity-duration.md`. Base it on the report's smallest capability:
   - reuse Observation, metric, unit and sessions;
   - admitted duration capture;
   - aggregate queries grouped by release, platform and method or playstyle, with sample count, provenance, missingness and a disclosed estimate;
   - a source's aggregate kept separate from native samples.

   Read the existing Observation, session, progress and aggregate owners first. Decide what is reused, what is added, and why. Each aggregate read must touch a bounded neighbourhood. The same mechanism should serve reading pace and recipe preparation estimates.
2. **Contract.** State each new or changed operation's request and response at the API, in the owning contracts.
3. **Outcome row.** Declare `games/play-duration-estimates` with six pending persona cells. Write its outcome test against the public API using the report's falsifying scenario:
   - two playstyles and two platforms give separate estimates;
   - incomplete runs and unknown durations are not zero;
   - changing one observation changes only its eligible cohort;
   - export keeps the procedure and unit;
   - private sessions stay private.

Do not implement the capability in this step. The row stays pending and its tests fail for the stated reason. Program reviews the decision note before an implementation step is briefed.
