## Outcome

Analysis only: read the tree, change nothing, and return a report as your final answer (at most 1,800 words, files cited with line numbers).

The maintainer's requirement: "肯定是要一套 seed 方法 + 性能测试方案的，就是 seed 规模数据之后的性能测试，不需要太大的规模，但是要能检测复杂度估算如果出问题了." One way to seed data at scale, and one performance check run on that data, small enough to run routinely, that fails when an operation's cost grows faster than its declared complexity. Costs are judged by how they grow, never by how fast this machine is.

The report has five parts:

1. **What exists.** A table of every seeding and cost-measuring mechanism in the tree: what it seeds, whether through the product API or by raw writes, at which scales, build and restore time, what it measures (statements, rows, Fuseki queries, bytes, wall time) and which tests use it. Start from `scripts/load/`, `scripts/fixture/`, `tests/qa/integration/*cost*`, `*scale*`, `*profile*`, `services/main/tests/*profile-child*`, `docs/storage/workload-budgets.md` and the load tier.
2. **Gaps.** Which first-public-scope operation families (book library, recipes, VNDB-like and Bangumi-like catalogues, Realm, Zone, search, feeds) have a declared cost class and a growth check today, and which have neither. Name the families, not every route.
3. **The smallest scheme that meets the requirement.** One seed method (data enters through the API or a restore of a backup built that way; built once; restore, start and readiness under 10 minutes; three geometric scales that fit this host). One growth check (counters, not wall time; the growth between scales compared with the declared class, with a stated margin). Where an operation declares its class. How a run reports a breach so the owner can act.
4. **What to merge or delete** so that there is one way to seed and one way to check, with the callers each removal touches.
5. **Tasks.** One-session tasks in order, each with its files and the test that proves it, marked A (a first-public-scope operation with no proof of bounded cost) or B.

Do not design: a new load-testing framework, wall-clock thresholds, a production-size corpus, capacity qualification at hundreds of millions of entities, or anything for an external condition (`docs/operations/external-conditions.md`). Prefer extending what part 1 finds over anything new.
