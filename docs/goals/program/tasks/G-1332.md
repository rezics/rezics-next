## Outcome

A full `task goal -- regress` should finish in about four hours on a busy host;
on 2026-10-07 run 2 finished only unit and model in 1.5 hours, because:

1. Every integration and fault/recovery batch takes the single heavy lock, so
   about 40 batches run one at a time behind every Goal's browser runs (one
   batch held the lock 33 minutes). With memory admission (G-1299) in place,
   run these batches without `--heavy`: up to the QA slot count at once, each
   admitted by measured memory. Keep the heavy lock for browser journeys and
   Storybook only.
2. The owner tier (about 2,000 tests) went void at its 600-second deadline under
   load. Split it into shards that each fit the deadline.
3. Browser journeys (317 e2e files) and Storybook suites do not belong in every
   four-hourly run: add a selection (`--only` already exists; make the default
   regression exclude e2e and Storybook, and document a nightly full run that
   includes them).
4. `goalctl merge`'s unit gate treats a guard failure as inherited when it is
   already on `main`. For a task merged more than once (a stream), a failure
   its own earlier merge introduced must count as introduced: compare against
   the commit before the task's first merge. (Kernel's single-row
   verification head slipped through this way.)

Update the regression paragraph and merge row in `docs/goals/README.md`.

## Not in scope

No change to the harness's resource classes, memory admission or slot count;
no scheduler service.

## Checks

Unit tests with a stub runner: integration batches run concurrently up to the
slot count and take no heavy lock; browser batches still take it; owner shards
each finish within the deadline in a measured real run; the default selection
excludes e2e and Storybook; a stream's second merge that keeps a guard failure
from its first merge is refused. One real run with `--only unit,owner` plus
three integration batches, reporting wall time and concurrency.
