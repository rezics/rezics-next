## Outcome

In main-wide regression run 5 (main a5de93040), about 26 of 62 failing
integration batches fail in the reset between files, not in a test.
`resetGraph` in `scripts/qa/integration-reset.ts` sends `CLEAR ALL`, and
Fuseki answers 400 in 2 ms:

```
(pass) a kind seek returns discussions that are older than the newest catalogue posts [118.46ms]
error: Fuseki update returned 400
      at update (services/main/src/infrastructure/fuseki.ts:467:33)
      at async resetGraph (scripts/qa/integration-reset.ts:43:16)
      at async resetIntegrationState (scripts/qa/integration-reset.ts:54:22)

fuseki-1 | 16:28:23 INFO Fuseki :: [4] POST .../rezics/update
fuseki-1 | 16:28:23 INFO Fuseki :: [4] Update
fuseki-1 | 16:28:23 INFO Fuseki :: [4] 400 Bad Request (2 ms)
```

It is intermittent and started around 2026-10-07 22:00 UTC+8. Logs that contain
it: `grep -l '^error: Fuseki update returned 400'
~/.cache/rezics-r/*/*/.artifacts/qa/*/logs/*.log`. The stack log beside each
one (`*-stack.log`) has Fuseki's side.

1. Find why `CLEAR ALL` gets a 400. Fuseki maps an `UpdateException` raised
   during execution to 400, so look at what else is running against the stack
   at reset time: Main's workers, the jena-text index, or a test that leaves
   Fuseki in a fault state. To see the message, make `FusekiClient.update`
   include the response body in its error. That is the only change allowed in
   `fuseki.ts`.
2. Fix the cause so that the reset succeeds whenever the stack is healthy. If
   the stack really is broken, the reset reports that as a harness failure
   naming the stack. It is never reported as a failure of the test file that
   ran before it.

## Review outcome (program, after attempt 2)

The cause is right: the raw update servlet refuses `CLEAR ALL` while
`urn:rezics:projection:public-name-repair` holds state. Skipping that graph is
wrong, though. It holds per-run repair cursors, label-copy phases and retained
title candidates, so the next file would inherit them. Instead:

- The reset clears every graph, including that one, through a supported
  maintenance path. Use an existing maintenance-capability command if one
  clears it.
- Otherwise add a narrow `DatasetResetPolicy` command to the Jena command
  module. It is admitted only with the maintenance capability, it empties the
  whole dataset including the proof graph, and it is not reachable through raw
  update.
- Never bypass the guard through the Graph Store Protocol or raw update.

The command module is in kernel's area; program has allowed this change and
will tell kernel.

## Checks

- A test where one file leaves repair state behind and the next file starts
  with the repair graph empty.
- The Java test for the reset command: refused without the maintenance
  capability, and complete with it.


- A harness unit test covers the cause you found and the attribution rule.
- Re-run two integration batches that hit the error, with `task test --
  <files>`, and give the artifact paths.
- Run `task goal:typecheck`. Do not run `goalctl gate` or land; program does
  both.
