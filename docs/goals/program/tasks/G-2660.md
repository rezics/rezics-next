## Outcome

The competitor coverage report (`.temp/ref/competitor-coverage.md`, row **B05**) finds that Paprika and Mela weekly meal plans, Discourse return reminders and Bangumi's daily airing make a future intention actionable. A date on a Work or a list is not a schedule. The recipe-manager loop is capture–plan–shop: capture is done (Paprika and Mela import), and shop is decided in `docs/architecture/actionable-collections.md`. This step decides plan.

Write `docs/architecture/scheduled-plans.md` as a proposal for program review. Base it on the report's smallest capability: extend **Scheduled** over the existing Event and Activity owners, Collection entries (reuse the runs and entries of `actionable-collections.md`) and notification delivery.

- Private occurrence time and time zone.
- Optional bounded recurrence.
- Cancellation.
- A durable due action through the notification owner.
- Export.

Meal plans, reading-club meetings and release or airing calendars are bound by configuration; there is no competing calendar owner.

Read those owners first and decide what is reused, what is added and why. Reuse existing vocabularies (`schema:Schedule`, `schema:Event`, iCalendar RRULE semantics) before adding local terms.

Every due-action sweep and every read must touch a bounded neighbourhood, whatever the number of plans or recurrences. Recurrence never materialises unbounded occurrences.

Use the report's falsifier:
- moving or cancelling a recurring dinner or reminder around a DST boundary;
- only the current authorised recipient gets exactly one due notification;
- a known airing date stays distinct from unknown availability.

Write the per-persona authority matrix. Do not write contracts, rows or code in this step. Hand off the note for review.
