## Outcome

Landing gates run on a host with 30 to 40 workers and up to eight QA stacks; the one-minute load is 50 to 75. Four harness tests fail there although nothing they test is wrong, and each failure stops a landing that has to be run again:

- `tests/qa/unit/integration-shards.test.ts`, "measured integration files plan into projects within 60% of the budget": 10.6 s and 19.5 s against its 5 s limit (api's G-2208, 03:3x UTC on 2026-10-14).
- `tests/qa/unit/affected.test.ts`, "affected selection defers retained seed preparation even when its own file changes": the synchronous plan took 11 to 37 s under memory pressure; it runs in under a second on a quiet host (web's G-2215 gate).
- `tests/qa/unit/memory-admission.test.ts`: "ten waiting processes share one failed measurement and refresh after expiry" (two readings instead of one), the same test for a successful measurement (`measurement failed: database is locked`), and "pressure waiting keeps load deadline admission and its final memory recheck" (timeout) (G-2215, run-K0mVhf).
- `scripts/load/docker-env.ts`: `docker info` with a 10 s limit answers late while stacks start, and four `tests/qa/fault-recovery/` tests failed in a web gate with "Docker is unavailable" while Docker was running (G-2232, run-Toxy1I).

First, and before the four tests, a deadlock that stopped every QA run on the host for 25 minutes (03:27 to 03:52 UTC on 2026-10-14). A fault-recovery test of api's G-2249 started \`stack:up --profile qa --persistent\` as a child with \`GOAL_IN_SLOT=0\`. In \`scripts/qa/memory-admission.ts\` that start-up became the first fitting waiter of the start-up queue while it waited in \`waitForStartupSlot\` for one of the 16 QA slots; all 16 slots were held by runs waiting in the same queue behind it. No stack ran, the host's load fell from 73 to 21, and nothing moved until I stopped that process. \`.temp/ref/qa-startup-deadlock-0352.sqlite\` is the start-up database at that moment (15 waiters, the slot-less one first, all with \`load_wait = 1\`).

- No waiter that lacks its slot may hold the queue's head against waiters that hold theirs: either a start-up takes its slot before it joins the queue, or the selection of the first fitting waiter skips a waiter whose slot is not ready. Choose one, say why, and prove the deadlock with a unit case first: sixteen slot holders queued behind one slot-less start-up must make progress.
- A child start-up of a run that already holds a slot runs under that slot (the parent's), as \`scripts/qa/test.ts\` runs do; find why this one carried \`GOAL_IN_SLOT=0\` and close that path, or say why it must take a slot of its own.
- A waiter at the head that has not advanced for a bounded time (say 10 minutes) is reported by name in \`task goal -- status\`, so the next one is seen in minutes.

Afterwards each passes on a loaded host and still fails on the fault it exists to find:

- Find the cause of each slow case before changing a limit, and say it in the handoff with a measure. Where the work grows faster than its input (a planner, a selection over all files), fix the algorithm and add a case that would catch it at twice the input. Where a test waits on real time or on a real database lock, give it injected time or its own database file, as G-2389 did for the start-up tests. A limit is raised only where the work is bounded and measured, and the handoff names it.
- The Docker probe tells a slow engine from a stopped one: it keeps trying within one bounded wait (say up to 60 s, backing off), and only an engine that never answers, or answers with an empty version, is "unavailable". Unit cases on an injected probe prove both.
- Prove each under load: run the four files while `stress-ng` or an equivalent loads every processor (or with a slowed injected clock where the test owns time), and give the timings before and after.

Do not build: a retry that hides a failure, a skip, a test moved out of the gate, a change to what any test asserts about the harness's behaviour.
