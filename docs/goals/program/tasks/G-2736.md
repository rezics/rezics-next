## Outcome

Two of the last four main confirmations left six catalogue cells not run, because a backing service of the outcome's stack stopped answering mid-run:

- `confirm-20261016t175704-204af4`: Anime catalogue browse. Setup answered 503 `dependency_unavailable` ("A required authority service is unavailable") after `AccountAssertionUnavailable` (`qa/outcome-2/attempt-1/20261016t175732-2e8bb9/logs/integration-1.log`).
- `confirm-20261016t220449-f6ba1b`: Visual Novel catalogue browse. At 22:44:33Z, workers hit `ECONNREFUSED` and setup answered 503 "Work operation could not be completed" (`qa/outcome-47/attempt-1/20261016t224408-21d7df/logs/integration-1.log`).

Both directories are under `.temp/goal-orchestration/confirm/`. Both are large catalogue rows, so they need the most memory and run longest. Find which container or process stopped answering and why: an OOM kill, a reaper or cleanup race removing a live stack's container, a restart under memory admission, or a host-port collision. Use Docker events, the reaper's records, the kernel log and the stacks' logs for those times. Fix the cause, so that a running stack's dependencies stay alive until its run releases them. If a service can legitimately restart, its clients must recover within the run's deadline instead of failing the row. No row is skipped or retried around a dead dependency.
