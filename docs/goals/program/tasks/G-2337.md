## Outcome

The record of `books/catalogue-browse-and-search-in-its-zone` holds the answers to the requests the production browse page sends. Today it has first pages with `limit=10` and continuations with `limit=1`, which the proofs use to walk the catalogue; `RealmBrowseRoute` sends its queries (`mainBrowseQuery`, `catalogueBrowseQuery`) with no `limit`, so a story that runs the production route finds no answer (the web Goal, 2026-10-13 20:57 UTC).

1. Read `RealmBrowseRoute` and the query builders it uses under `apps/web` (read only; change nothing there) and record, for each of the six personas with that persona's client and acting subject as production sends them, the page's own reads spelled exactly as the builders spell them: the first page, a title search that matches, a search that matches nothing, and the continuation of the first page with the cursor its answer gave. Use `tests/qa/support/frame-reads.ts` for the frame's reads of the browse route.
2. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's.
3. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added per persona (label, method, path, status), any read of the page that could not be recorded with the reason, and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. If the recording run fails on a 503 or a timeout, run it once more when the host's one-minute load is below 64 (`cat /proc/loadavg`); then hand off `partial` with the request, the answer, the load and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or the helper, another row's record.

## Decision — 2026-10-13: the page's exact requests

From the web Goal's reading of the production browse page (its Books surface, attempt 1). Where this section and the outcome differ, this section holds.

- The browse reads carry no `limit`, no `type`, no `actingSubject` and no body, for every persona: production sends them through its anonymous client. The frame's reads keep the client production uses for each.
- Shapes, each recorded for all six personas: the default page; `sort=newest`; `sort=updated`; `q=<text that matches>`; the same with `sort=relevance`, `sort=newest` and `sort=updated`; `q=<text that matches nothing>`; the same with `sort=relevance`.
- For every answer that has a `nextCursor`, its continuation: the same query plus that cursor, unchanged. A chain recorded with `limit` is no substitute.
- `sort=relevance` with no text is not recorded: production turns it into the default page before it asks.
- For the five signed-in personas the frame also asks, with no `actingSubject`: `GET /v1/realms/{realm}` and `GET /v1/addresses/resolve?scope=space&key={space}`. Record them too.
- The handoff names every request the page can send that is still not in the record.

## Decision — 2026-10-14 00:20 UTC: cut

Two recordings stopped on a time limit: the first on fixture and persona time-outs while the stack gate ran above its limit, the second (QA `20261013t235617-fe03de`) with five personas passing in 24 to 55 s each and the operator still waiting for `GET /v1/realms/<Realm>/modules/browse?sort=newest` when its 60 s ran out. Since `0d17d81bb` every persona request pending past 10 s or completed past 5 s is named in the run's log under `[persona-request]`.

The cut: rebase onto `main`, then one recording run, unchanged. If it passes, check in the record and hand off `done`. If a proof runs into its limit again, do not run a third time and change nothing: hand off `partial` with every `[persona-request]` line of the run, the per-persona times and the host's one-minute load at the start and the end. Those lines go to the owner of the browse read; whether the limit or the read is wrong is decided from them, not here.

## Decision

2026-10-14 00:40 UTC: design note.

The third run named the cause, and it is not a slow read: five personas passed in 43 to 57 s and the operator ran into the file's 60 s test limit, while the request watch logged one request over 5 s in the whole run (5.9 s). The time is the count of ordinary requests. The proof itself is bounded by its own 45 s deadline; the production reads recorded after it are replay material for the surface, not the proof, and they share the proof's 60 s test limit only by accident of living in the same test.

So the record's reads get their own budget, and no proof budget changes:

- The proof keeps its 45 s deadline and every assertion.
- `productionReads` runs under its own deadline of 120 s, and each persona's test limit becomes the sum the two need (180 s), set on those tests only, with one comment saying which part is the proof's and which the record's.
- Where the production page sends reads together (its server reads under separate Suspense boundaries, a card's reads), send them together; do not serialise what production sends in parallel.
- Rebase onto main, then one recording run. All six pass: commit the record and hand off done. A proof that fails inside its own 45 s, or a 5xx: hand off with the request, the answer and every `[persona-request]` line; no further run.
