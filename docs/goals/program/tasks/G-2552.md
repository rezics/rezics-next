## Outcome

`docs/architecture/content-adoption.md` (Decision section) and the contract G-2550 wrote, `docs/contracts/content-adoption.md`, define three Content-owned capabilities. Implement them in the Content owner and its public API:

1. **Procedure block.** A bounded procedure block (ordered sections and steps; text, media and resource references inside steps), validated as a Content document extension payload. It is the single stored structured-instruction form, and `HowToSection`/`HowToStep` are its projection vocabulary.
2. **Resource reference.** A general Resource reference, inline and as a block, with grain-qualified selectors (Resource, Revision, Occurrence, Fragment, Representation), resolved through Semantic and Media under disclosure. The existing Work reference block keeps its meaning.
3. **Derivation record.** A Content derivation record with PROV-O qualified derivation: exact input revisions or fragments (block, span, time segment), output revision, activity kind (transcribed, summarized, structured) and the responsible public Agent, human or AI. It asserts no equivalence, correctness or authority. Private principal authorization stays private.

Also settle G-2550's shared prerequisite: its outcome proofs create a Post with `POST /v1/posts`, which answers 404. Find the public operation that authors a Post today and align the outcome test with it, or add the missing operation if Posts cannot be authored through the public API, following the Post contract (`docs/contracts/work-and-release.md`).

Keep every operation bounded and authority-checked like its owner's existing ones. Write owner tests for each capability, including refusal, revision pinning and disclosure. G-2553 builds Recipe adoption on these in parallel: push the API shapes early, then refine.
