## Outcome

In G-2462's landing surface gates, two shared harness tests fail on the candidate every time, but pass in worker worktrees and in the main checkout, and pass on main inside the same gate:

- `tests/qa/unit/container-reaper.test.ts`, "a shim run records every scope marker and removal deletes the container and the marker", misses `rm -f marked-container` at about 2.1 s. It still fails after G-2686 made the reaper tests wait on conditions.
- "finished fixture preparation releases its lease before drill startup admission" times out at 302 s.

Evidence is in `.temp/goal-orchestration/merges/surface-gate/run-89rpzN/` (`evidence.json`, `output.log`, `tests-*.log`), and in earlier runs `run-jPHLGj` and `run-Tqn5Bz`. G-2462 changes only its own fixture and outcome test.

The failures are consistent, so the cause is a property of the candidate's environment: its checkout path, labels derived from the path, environment variables, the order of shards it shares with other files, a shared marker or lease directory, or the working directory. Reproduce them in a candidate checkout built the way `scripts/goal/surface-gate.ts` builds one, find the dependence, and remove it so each test is isolated, for example with its own temporary directories and labels. Prove that both pass in a reproduced candidate checkout and on main. Then mail program.
