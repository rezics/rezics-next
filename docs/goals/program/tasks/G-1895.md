## Outcome

The warm stack pool is on (`.temp/goal-orchestration/qa-stack-pool` = `on`) and works when one tree runs twice by hand: on 2026-10-11 a second `task goal -- test tests/qa/integration/typed-progress.test.ts` from the main checkout leased the first run's stack and finished in 26 s against 182 s.

In the main-wide regression it almost never happens. Run `20261011t183010-e1edd1` (pinned checkout under `~/.cache/rezics-r/`, one tree for every batch, three batches at a time) had finished 12 integration batches, all with ordinary projects and most of them passed, and exactly one lease is recorded ("Integration shard 20261011t193206-cdde84-1 leased from rezics-qa-20261011t192840-c3a912-1, parked for 7563 ms"); no pool-miss note explains the others. The pool state directory (`.temp/goal-orchestration/qa-stack-pool-state`) then held one entry with a holder and an EMPTY fingerprint. The batch summaries are under `.temp/goal-orchestration/regress/20261011t183010-e1edd1/qa/integration-<n>/attempt-1/<run>/summary.md`; they are outside your worktree, so the manager has staged copies of twelve of them and the pool state in `.temp/ref/pool-evidence/` of your worktree.

What I read in the code, to start from, not to trust: in `scripts/qa/cli.ts` a stack is parked only `if (lease && run.ok && record.stage === 'test')`, and `lease` exists only when `stackPool.acquire(fingerprint)` returned one, which needs a fingerprint before startup. A run that starts a fresh stack because nothing matched, or because the fingerprint could not be taken yet, seems to finish without parking, so the pool is only ever fed by a run that already leased. If that is right, the pool cannot fill under steady load.

Required:
1. Find the actual reason from the evidence and the code, and state it in the handoff in three sentences.
2. Every passed ordinary integration project that is eligible (`integrationStackPoolEligible`, not isolated, not kept) parks its stack after the verified reset, whether it leased it or started it, up to the pool's capacity; over capacity the stack is destroyed as today. A stack started when the fingerprint could not be taken before startup gets its fingerprint after startup, as the earlier task intended.
3. A summary line for every eligible project says which of four things happened: leased, started and parked, started and destroyed (with the reason: failed, reset failed, capacity, switch off), not eligible. So the hit rate can be read from summaries.
4. Nothing changes with the switch off.

Tests: unit tests for the park decision in each of the four outcomes; then the real proof on this host with the switch as it is (on): run the same small ordinary integration file three times in a row from your worktree in three separate `task goal -- test` calls and show from the three summaries: started and parked, leased, leased. Then run two different small ordinary files in ONE call and show both projects' lines. Report the run IDs and the lines.

Do not change the fingerprint's inputs, the reset, the startup admission or the 15-minute idle limit.
