## Outcome

The supermanager knows from measurement where the second three hours' input went, whether the first reading's changes worked, and which change now lands the most features for each token. The staged `.temp/ref/efficiency-audit-2.txt` and `.json` read the sessions begun from 12:36 to 15:40 UTC on 2026-10-13: 392 sessions, 6,817 steps, 426.7M input tokens, 95% cached; workers by step read 39%, wait 34%, edit 12%, test 6%; 16% of worker input in tasks with thirteen or more turns. `.temp/ref/efficiency-audit-1-researcher.md` is the first reading. You change no file of the repository.

What happened in the window, to test against the sessions and not to take on trust: (a) from 14:21 to 14:39 UTC the coordinator started up to 44 manager sessions for one event (fixed at `a8a5d1d7e`); the reading seems to count those sessions as workers of the task the event named (G-2148 66 turns, G-2174 54, G-2096 36, G-2170 25). (b) Only 8 to 11 of 34 workers were live for most of the window; the maintainer's review at 15:05 UTC called that the fault: efficiency is features landed for the tokens, and an idle account with ready work is the waste. (c) The api manager's turns have a median of 532k input tokens each and take one event a turn; six exited tasks stood for 40 to 60 minutes behind eight unanswered mails. (d) After 15:15 UTC the width was raised to 27; since then eight QA slots are busy and six runs wait for memory.

Read the event streams in the main checkout (read only): workers `.temp/goal-orchestration/runs/<id>/attempt-<n>.json`, manager turns `.temp/goal-orchestration/manager-runs/<token>/output.jsonl`, `scripts/goal/efficiency.ts` for how a step and a session are classed, `task goal -- coordinator turns --goal api` for the turns. Write `.temp/goal/audit.md` in your worktree, at most ninety lines:

1. **The reading corrected.** Separate manager turns from workers. Give for the window: worker input, manager input (the storm apart), tasks landed, input for each landed task, and the same for the first window, counted the same way.
2. **Did the first reading's changes work.** The wait share was 41% and is 34%: is that the long wait call, the mix of tasks, or the miscount of (a)? Which of its three changes are in the tool or the protocol now, and what does `goalctl test --affected --list` still cost while it takes a QA slot?
3. **The manager.** What a 532k-token turn reads, which part of it repeats every turn, and how many events a turn could settle; the time from a handoff to its decision, median and worst, and what the task did meanwhile.
4. **Attempts.** For the six tasks with the most attempts in the window: what each further attempt was for (a decision that waited, a refusal of the tool, a real fault), and which would not have happened with a brief sentence or a tool default.
5. **Three changes, the largest gain in landed tasks for each token first.** For each: the measure now, the expected measure after, where it is made, what it risks. Then what is not worth changing.

The handoff repeats sections 1 and 5 in at most forty lines.

Do not build: a change to any file of the repository, a new tool, advice without a measure.
