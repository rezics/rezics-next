## Outcome

A stack start is held while the host's one-minute load average is above a limit times its processors (`hostLoad` and `loadLimit` in `scripts/qa/memory-admission.ts`; the limit is the file `qa-load-limit` beside the admission directory, 1 when absent). The signal is wrong in both directions, measured on this host of 64 processors on 2026-10-13:

| UTC | limit | active stacks | load (1 min) | busy processors | CPU pressure `some avg60` | waiting runs | what happened |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 23:16 | 1 | 5 | 63.7 | 39.8 | 6.5% | 13 slot, 9 memory | 24 processors idle while 22 runs wait up to ten minutes |
| 22:31 to 23:04 | 1.2 to 1.5 | 7 | 80 to 95 | 60+ | 20 to 26% | few | runs failed on 10 s to 120 s request limits; passed runs did not rise |

The load average counts threads blocked on the disk as well as those waiting for a processor, and it trails by a minute. Pressure (`/proc/pressure/cpu`, the `some` line) is the share of time a runnable task waited for a processor, which is what the gate means to bound.

What must be true afterwards:

1. The gate holds a stack start while processor pressure is at or above a limit, read from `some avg10` of `/proc/pressure/cpu`. One signal, one limit, in the one place the load is read today. The source is injectable for tests the way `REZICS_QA_LOADAVG_FILE` is. Where the kernel offers no pressure file, the gate keeps the load average as it is now, and says so once in its wait message.
2. The limit lives in one file an operator changes at run time without restarting anything, as `qa-load-limit` does today. Default 12 (percent). The old file is not read as a pressure limit: a value of `1` must not come to mean one percent.
3. A start the gate has just admitted counts against the next decision until the signal can show it: a stack's cost appears over about half a minute, so thirteen waiters must not be admitted in the instant pressure dips. Use the admission state the gate already keeps (`startup_promises`, `startup_waiters`); arrival order is kept.
4. The wait message names the reading, the limit and the count of recent starts, so a waiting run's log says why it waits.
5. Unit tests with injected readings prove: held at the limit and released below it; no burst when pressure dips (a second waiter is held until the first start's window has passed or a fresh reading is below the limit); fallback without the pressure file; the limit file's change taking effect on the next poll; the deadline behaviour of the load wait unchanged.
6. The comment at the gate carries what a document would: the signal, the file, the default, and why the load average was dropped (it counts threads blocked on the disk). No document is written.

Do not build: a second scheduler or queue, a change of memory admission or of the slot count, a gate for runs that start no stack (`need.vm` of zero stays ungated), tuning by trial on the live host. State the default and the file in the handoff; the program measures before and after and sets the limit.
