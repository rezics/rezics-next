## Outcome

Web's G-2241 replays these two rows' records through the production `/library` page and finds reads missing. `.temp/ref/g2241-record-gaps-mail.md` names them: the collection member's work-states read (`GET /v1/me/work-states?works=…&actingSubject=…`) and Read-shelf read (`GET /v1/me/shelves/status/read/works?…&sort=added&order=desc&limit=20`), and the whole `/library` visits of the two-device member and the owner after their winning completed version-2 marks.

What must be true afterwards, each request taken from the production client (the web's library readers, imported, not copied) with the path, query and body production sends (a request production does not send is not recorded):

- For each persona of each row, the whole `/library` visit as production sends it, from its first read to the state the persona ends in: every shelf, state, continue and supporting read it reaches, including the empty and refusal states that route actually reaches. Record each read as production sends it, not as the mail paraphrases it.
- Two-device row: the member and the owner after their winning completed version-2 marks (the Works and Persons named in the mail). Record their `/library` visit and the Work page visit after the progress is saved. If neither production page requests progress, record nothing extra and say so; choosing the page is the web's decision.
- Read the production path of `/library` and the Work page once and compare it with the record's labels for each persona; record every read still missing and list those beyond the reference.
- The reads one render sends together start together (`Promise.all`); writes and reads that need an earlier answer keep their order. A label names what the request is and is fixed where the request is written, never a counter: the web chooses a sample by its label and expects exactly one.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; if recording refreshes identities, every sample changes together.
- The record's requests run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's. One console line per persona gives the elapsed time of the proof and of the visit. Each file has a 480 s wall.
- A 5xx that is the final answer: hand off with the request and the answer, do not vary it; do not run a third time.

The handoff summary names old and new identities, every new label with its request and status, and which states each persona reaches.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a read at the Account origin.
