## Outcome

G-2540 removed a nested Content-pool checkout on wave/1. Its Recipes run (QA 20261014t134031-4dd19c) still logs the same fault class on the Access pool:

```
"event":"worker_fault","rezics.worker.name":"main.database.nested-checkout","error.class":"NestedPoolCheckoutError",
outer: services/main/src/modules/governance/store.ts:1712 withPublicationFence
inner: services/main/src/modules/access/admission.ts:326 admissionClient   (pool: access)
```

Taking a second connection from the pool that already holds one can deadlock under load. Make the admission read inside `withPublicationFence` use the fence's connection, or move it before the fence takes its connection. Keep the fence's serialization and the admission decision unchanged. Add a unit test that fails on a nested checkout of this path, as G-2540's `progress-completion-media-checkout.test.ts` does. Then search the wave diff (`git diff main...wave/1 -- services/main/src`) for other new calls that take a pool client inside a held one, and fix them the same way or list them.
