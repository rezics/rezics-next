## Outcome

The record of `zone/home-rendering` holds the answers to the requests the production Zone home sends, so its story runs `SiteHomeRoute` and `loadRealmView` on a replaying fetch. Today the story takes its masthead from the presentation body and reads beside the production readers, because the frame's reads are not recorded (web's mail of 2026-10-13 20:27 UTC). Identities are this recording run's; none of an earlier record is kept.

Read `SiteHomeRoute`, `loadRealmView`, `readRealmHeader`, `readFacets` and the host client under `apps/web` only to copy each request's exact spelling, parameters, headers and client; change nothing under `apps/`.

1. Each persona's proof records, under labels of the form `frame-*`, each request the production home route and its frame make on the server for one visit of the published home and one of the empty home:
   - the reads production sends through its anonymous client, with no query, for every persona: the Realm header `GET /v1/realms/<the row's Realm>`, the facets, the address resolution (record them for a signed-in persona through the visitor's session, as `work-showcase` is recorded in `tests/qa/integration/outcomes/anime/navigate-a-thousand-episode-inventory-thousand-chapters.test.ts`);
   - the reads that carry the persona: presentation, routes, and for signed-in personas joining, follow, platform access, the own-ban read where platform access opens it, session-agent with the session-key header, person-preferences.
   The record of `visual-novels/catalogue-browse-and-search-in-its-zone` is being given the same frame reads now; where it has landed, use its labels and spelling.
2. A read of the route that a persona's session cannot make as production does is listed in the handoff with the reason and not recorded another way.
3. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes.
4. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added (persona, label, method, path, status), the record's bytes and samples before and after, and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation: run once more, then hand off `partial` with the request, the answer, the host's load (`cat /proc/loadavg`) and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record.
