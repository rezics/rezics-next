## Outcome

Starting one task does not stop every other command of every Goal. `dispatch` (`scripts/goal/tasks.ts:62`) runs `git worktree add` and `corepack yarn install --immutable` inside `withLedger`, so the ledger lock is held for the whole preparation: about 35 seconds a task on 2026-10-13 (thirteen dispatches in a row took eight minutes). Every command that changes the ledger waits behind it for up to 120 seconds and then fails; at 15:57 UTC, with 28 workers and three managers, the api manager's `new` timed out and two of its turns asked the program to release the lock.

1. The lock is held only to decide and to record. Under the lock: validate, check claims and admission, and record the task in a state that holds its claims and counts as live for the width (a new state such as `starting`, or `running` with no attempt yet; choose what the readers of the ledger need least change for). Outside the lock: the worktree, the install, the brief's copy, the staged references. Under the lock again: launch and record the attempt.
2. A preparation that fails releases what it recorded: the task entry and its claims are removed (or the task is left in a state `dispatch` can retry, as `removeDispatchLeftover` already cleans a half-made worktree), and the error names the install log as today. A second `dispatch` of the same brief while the first prepares is refused with that reason.
3. `status` shows a task that is being prepared, and the width counts it.
4. Look for the same fault elsewhere and list it in the handoff without fixing it here: every `withLedger` callback that starts a process, runs `git` on a worktree or waits on anything (`resume`'s rebase is one candidate). Give for each the seconds it can hold the lock.
5. Measure on the real checkout, once, before and after: the time `task goal -- new --goal program --kind tooling x` waits while a `dispatch` of another brief prepares (use `--dry-run` only where it shows nothing; cancel the task you created).

Tests in `scripts/goal/dispatch-lock.test.ts` with a temporary repository: while one dispatch prepares (a slow install stub), another ledger command completes; the claims of the preparing task refuse a conflicting dispatch; a failed install leaves no task and no claim; the width counts the preparing task.

Do not build: a second lock, a lock for each Goal, a change to the lock's waiting time, a pool of prepared worktrees, the fixes of step 4.
