## Outcome

The record of `books/work-hub-and-edition-choice` lacks two reads the production Work hub sends for the member when the Work is the empty one of the row (no edition, nothing read): `GET /v1/me/edition-preferences/{work}?actingSubject={member}` and `GET /v1/me/progress-summaries/{work}?actingSubject={member}&language=en`. The web Goal's surface replays the record and finds no answer for them (its gate evidence, 2026-10-13).

1. In the member's proof, where the empty Work is read, add those two reads as the page sends them, each under its own label, with whatever status the API gives; an answer with no body is recorded as that. Assert only the status and, where there is a body, what the member is shown.
2. No existing sample's label or request changes, no other assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's.
3. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the two samples (label, method, path, status) and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. If the recording run fails on a 503 or a timeout alone, run it once more when the host's one-minute load is below 64 (`cat /proc/loadavg`); then hand off `partial` with the request, the answer, the load and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or the helper, another row's record.
