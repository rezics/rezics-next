## Outcome

Stack startup is the test limit on this host. `withMemoryStartup` (`scripts/qa/memory-admission.ts`) holds one host-wide SQLite write lock from the memory reading through `start()`, that is through Compose readiness, so that the next process measures the containers this startup created. One startup at a time: measured on 2026-10-11, 85 stack-starting runs an hour, each holding the turn 14 to 30 s, eight runs queued at once, and one 4-second test spent 30 s waiting for its turn.

Change the turn into a promise:

1. The lock covers only the admission decision, never `start()` and never a wait. Under the lock a process:
   - deletes promises whose process is gone (pid plus the process start time from `/proc/<pid>/stat`, so a reused pid does not count) or older than 15 minutes;
   - takes ONE memory reading (no waiting under the lock) and admits only if the reading still leaves the usual need and reserves after subtracting every live promise's `vm` and `host` need;
   - admits only while fewer than K promises are live;
   - asks for its QA slot exactly as today (`waitForStartupSlot`);
   - on admission inserts its own promise (pid, process start time, `need.vm`, `need.host`, admitted at) and commits.
   Not admitted for any reason: roll back, announce, sleep `pollMs`, read again. The announced lines keep their exact prefixes (`Waiting for another QA startup;`, `Waiting; QA memory:`): `scripts/qa/cli.ts` parses them, and it is outside this task.
2. `start()` runs outside the lock. A `finally` removes the promise when it resolves or throws. From then on the stack's containers are in every reading, which is the same guarantee as today.
3. K comes from the file `qa-startup-concurrency` beside the QA slots directory (`dirname(goalSlotDirectory(root))`, next to `qa-slot-count`), a positive integer; absent or invalid means 1. With K = 1 the order of events is today's: a second startup is not admitted until the first one's `start()` has finished.
4. The promises live in the same SQLite file as the lock (`options.lockFile`), in one table created if missing. An existing file without the table keeps working.

Tests in `tests/qa/unit/memory-admission.test.ts`, with the injected clock, reader and sleep the file already uses:
- K = 1: the second `start()` does not begin before the first resolves.
- K = 2: two `start()` calls overlap; a third waits and begins when one resolves.
- Memory: a reading that fits one need but not two admits one startup at K = 3; the second is admitted only after the first resolves and the reading includes it.
- A promise whose process is gone, or whose pid now belongs to another process start time, is ignored and removed.
- A `start()` that throws removes its promise.
- No sleep and no `start()` happens while the lock is held (assert on the lock state inside the injected sleep and inside `start`).
- The waiting lines are unchanged.

Proof on the real host, after the unit tests: with a temporary state directory holding `qa-startup-concurrency` = 2, start two ordinary integration runs together (one small file each, for example `tests/qa/integration/typed-progress.test.ts` twice in two commands) and show from their logs that the two Compose startups overlapped; report both run IDs and the two intervals. Do not change the real `qa-startup-concurrency`: program switches it.

Do not build: fairness or priorities, a daemon, changes to QA slots, to `cli.ts`, to the stack pool or to how much a stack needs.
