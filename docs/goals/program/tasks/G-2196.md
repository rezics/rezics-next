## Outcome

The surfaces of these proved rows can be built from what the API answered. A surface's stories are fed by its row's record, `tests/qa/fixtures/outcomes/<vertical>/<row>.json`, which the row's own outcome test writes. Only the Books catalogue row has one: `tests/qa/integration/outcomes/books/catalogue-browse-and-search-in-its-zone.test.ts` is the example to follow, with `OutcomeRecorder` in `tests/qa/support/outcome-test.ts`. Rows: `realm/create-a-realm`, `realm/membership-and-admission`, `realm/roles-and-team`, `realm/rules`, `realm/moderation-and-appeal`.

1. Each row's outcome test records its six persona proofs as the example does, and each row's record is checked in. No assertion changes and no cell changes state; a proof that fails is reported, not edited.
2. The record also holds what the row's page reads to render. Find the web route that shows the row under `apps/web/features/` (read it, change nothing there) and, for each read the page makes that the proofs do not already make, add that request to the test for one persona under a label a story can name. Where the row has them, add the request that gives the page's empty state and one refusal the API gives. Never write an answer by hand.
3. `scripts/api/answer-records.guard.test.ts` passes with the new records. Give in the handoff each record's bytes and samples, the recording run's seconds, and any read a page makes that you could not record, with the reason.

Do not build: a change under `apps/` or `services/`, a change to the recorder, to the record's format or to the guard, a record for a row not listed here.
