## Outcome

A surface's stories are fed by what the API answered in the row's own proof. The design note (staged as `.temp/ref/surface-design-note.md`, sections 2 and 4) was read by the program on 2026-10-13, which decided: the outcome test writes the record, and no second recipe of requests does; records are checked in; a record is judged stale by the operation's schema alone, with no fingerprint (what the API does is proved by the outcome run, not by the record). This is the first of the pilot's tasks: the record of one Books row. Steps, each committed when its tests pass:

1. **The envelope** in `scripts/api/answer-record.ts`: version, row, and for each persona its labelled samples (`operationId`, method, path with query, body, status, answer, and only the response headers a client reads). No credential, cookie, bearer or idempotency secret, no set-up call, no measurement. Opaque cursors and the answer's own timestamps and identifiers stay as answered; nothing is normalised. `scripts/goal/persona.ts` takes its envelope and redaction from here and keeps its behaviour.
2. **Validation against the contract:** each sample's operation exists in the generated OpenAPI (`generated/openapi/main/public.json`, `scripts/api/generate.ts`), its status is one the operation declares, and its answer matches that status's schema, references, unions and problem answers included. The failure names the row, persona, sample and the JSON pointer.
3. **Capture in the harness** (`tests/qa/support/outcome-test.ts`; `tests/qa/support/personas.ts` is another task's file, so wrap the session's call and do not edit it): a row test labels the calls that are samples; with recording switched on (an environment variable naming an output directory under `.temp/`) the record is written once, and only when all six persona tests of the file passed and every sample validates. Off by default; a normal run writes nothing.
4. **The pilot record:** `books/catalogue-browse-and-search-in-its-zone`. Label in its outcome test the populated reads (the three orders, a continuation), the refused shape (`400 unsupported_query_shape`) and the supporting reads its page needs; add to the test a search with no match and its proof for all six personas, since an empty state is never made by editing a populated answer. Run it once with recording on and check in the result as the fixture.
5. **The guard** `scripts/api/answer-records.guard.test.ts`, registered in `scripts/qa/repository-guards.ts`: every checked-in record validates as in step 2 against the contract generated from the tree. A renamed operation or a changed schema fails here, before any browser.

Do not build: the replay for stories, a change to the gate, a pending (`202`) sample for this read (its contract admits none), a record for another row, a mock of any kind.

## Checks

`task goal -- check`, the three test files once with `CLAUDECODE=1`, and the Books outcome file once in admitted QA with recording on (`CLAUDECODE=1 task goal -- test <file>`). The tests cover: redaction of each secret kind; a failed persona test or an invalid sample publishes nothing; the validator on a reference, a union, a nullable field, a numeric query and a problem answer; the guard failing on a fixture record with a renamed operation and on one with a changed field. Give in the handoff the record's size, its samples by persona and the seconds the recording run took. Wait on a running command with one long call (`yield_time_ms: 300000`).
