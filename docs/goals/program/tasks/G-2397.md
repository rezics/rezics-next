## Outcome

The web's surface for `realm/membership-and-admission` replays this row's record through the production readers (`apps/web/features/realm/membership.tsx`, `membership-state.ts`, `realm-page.tsx`, the address readers in `apps/web/features/address/` and the Realm frame). The record holds the commands as production sends them, and the surface still finds no answer for reads the pages send around them. The web manager listed them in `docs/goals/web/tasks/G-2232.md` under "Decision — 2026-10-14 task:G-2232:3"; read that section first. This task waits for the Realm Zone read's repair (its owner test on main), because four of the missing reads are that read and it answered 503 before.

What must be true afterwards, each request taken from the production client and sent with the path and query production sends (not from this list; a request production does not send is not recorded, and the handoff says which listed one that was and why):

- The owner's members page after an invitation: the members read, the roles read and the invited Person's agent read, so the page that shows the pending invitation is reached from records.
- The Realm frame's Zone read (`GET /v1/realms/{realm}/zone?actingSubject=`) for the stranger, member, moderator and operator on the Realm whose management frame refuses them, and for every persona wherever the frame sends it.
- The refresh after each command. After a withdrawal (stranger, operator), an accept and a decline (owner) and the invitation (owner), record the reads the production page sends to show the new state, in the order it sends them, so the transition from before to after is in the record and not two separate states. A decision's receipt and the read that restores the selected request belong to this.
- This is meant to be the row's last re-recording for the surface. Before recording, read the pages' whole production path once and compare it with the record's labels for each persona, the visitor included; record every read still missing and list those beyond the items above.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; the commands, their bodies, keys and compare-and-swap heads stay exactly as recorded now. No 202 exists for the invitation (it answers 200 with `invitation.state: "pending"`); do not invent a pending state.
- The record's reads run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's.
- A 5xx: hand off with the request and the answer, do not vary it. The log names slow requests under `[persona-request]`; quote them if a proof meets its limit, and do not run a third time.

The handoff names old and new identities and every new label with its request and status, in a file under `.temp/` of the worktree as well as in summary.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer.
