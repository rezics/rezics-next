## Outcome

An answer that contradicts the contract its operation declares fails the proof that received it, in every run. Today only the recorder checks (`OutcomeRecorder.publish` in `tests/qa/support/outcome-test.ts`, through `AnswerRecordValidator`), and only when a record is being taken with all six personas passed. Two faults were found that way by accident on 2026-10-13, hours after their rows were declared proved: the Recipes export answers a member (`importability`) that its closed response schema refuses, and the reader's settings answered a number where the contract said a string. The scheduled run on `main`, which is the judge of a proved row, would never have seen either.

1. **Measure first, with no stack.** The checked-in records under `tests/qa/fixtures/outcomes/` are answers the API gave. Validate every sample of every record against the operation's declared response schema for its status, by the validator the recorder uses, and list what fails: row, persona, label, operation, status, the member's path, expected and received type. Give the list and the seconds it took in the handoff. A record that fails here was published before a contract changed or is a fault; do not judge which.
2. **Check each sampled answer as it is taken.** In every run of an outcome test, recording or not, a sample whose answer violates its declared schema fails that persona's proof with the same six facts. The validator is built once for a process and shared with `publish`; the answer-record guard once compiled 243 schemas against the whole contract in 28 s and stopped a landing, so measure what the check adds to one outcome file and to the unit tier, and keep it under one second for a file.
3. **No proved row turns red by this task.** Each violation found in (1), or by one run of the outcome tests you can reach, becomes one entry of `tests/qa/support/answer-contract-debts.ts`: operation, status, member's path and the date. An entry silences exactly that member of that operation; a test fails when an entry no longer matches any violation (so a repaired contract removes its entry) and the handoff lists the entries for the api Goal, which owns each repair. An empty list is the expected result for most rows.
4. Decided in code and tested without a stack: a conforming answer; a member of the wrong type; a member a closed schema does not declare; a status the operation does not declare; a debt entry that silences its member only; a stale debt entry fails.

Do not build: a change to any contract, operation, generated file or record; a change to what the recorder writes; validation of requests.
