## Outcome

`scripts/goal/goalctl.test.ts` lost its stopwatch assertions today, but it still failed inside a merge gate at 10:38 UTC while three gates and twelve workers ran:

```
error: resume G-001 -m continue --engine claude --force-usage did not exit: SIGTERM
  at run (scripts/goal/goalctl.test.ts:2537)   # spawnSync(..., { timeout: 45_000 })
  at scripts/goal/goalctl.test.ts:4143
```

The gate's full log is in `.temp/ref/merge-G-1630.log` in this worktree (staged by the manager; search it for "did not exit"). Every CLI spawn in the file goes through helpers like the one at line 2532 with a fixed timeout, so any of them can fail the same way.

1. Find what that `resume` waited on for more than 45 seconds. Candidates: a launch step that does real work in the fixture repository (an install, a worktree operation), a lock shared with the real repository's orchestration state instead of the test's own, a read of the real host (`/proc/meminfo`, the real usage files, real processes), or plain CPU starvation of a child `bun`. Reproduce it under load and name the cause with evidence.
2. Remove the cause where it is a dependence on the real host or the real repository's state: a test's CLI child must use only the test's own directories and its fake engines.
3. Where a spawn is simply slow under load, make the helper's limit a deadline that reflects "the child is hung", not "the host is busy": one constant for the file, generous, and the failure message says which command and how long. Do not hide a real hang: a child that never exits must still fail the test.
4. Report the ten longest spawns in the file before and after, idle and under load.

Smallest change: fix the cause in one place. No retries, no skipped cases, no weaker assertions.
