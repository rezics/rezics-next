## Outcome

G-1370 stopped heavy runs from holding an ordinary QA slot while they wait. Light
runs still do: a run takes its slot (`acquireRunSlots` in `scripts/qa/cli.ts`),
then waits inside it for memory admission or for another run's stack startup
(`Waiting for another QA startup` in `scripts/qa/memory-admission.ts`). On
2026-10-07 two slots sat in that state for minutes while seven light runs from
kernel, launch and trust-ops waited for any slot.

Change the order so that no slot is held idle. A run waits for its memory
admission and its startup turn first, then takes a slot when both are granted.
Alternatively it releases its slot for the whole wait and re-acquires it,
without losing its place in the fair queue. Choose one and explain why.

Keep memory admission and the one-startup-at-a-time rule exactly as strict as
today. Only the order changes. A stack that has already started keeps its slot
until it finishes.

## Checks

Tests through the real `scripts/qa/cli.ts` path, stubbing only stack startup:
- With memory short, a waiting run holds no slot and another run can take it.
- When memory frees, the waiting run gets a slot and starts.
- With two runs waiting for one startup turn, neither holds a slot during the
  wait.

Run them with `task goal -- test <files>`. Do not run the full `--affected` set;
list it in the handoff.
