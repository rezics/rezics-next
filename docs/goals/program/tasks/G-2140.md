## Outcome

A manager writes a brief once and nobody has to remember it. Today a brief whose `depends:` has not landed, or whose path another open task holds or has changed, is refused by `dispatch`, and a manager must come back and try again; a landed task raises no event, so on 2026-10-13 the api manager held a brief "until the other lands" with nothing to wake it, and the program dispatched three tooling briefs by hand after watching for the landing each waited on.

- **`task goal -- queue <brief>`** validates the brief as `dispatch` does, then starts it at once when nothing holds it, and otherwise records it as queued with what it waits for (the tasks it depends on, the open tasks that hold or have changed its paths). A brief with an error that waiting cannot cure (a bad field, a missing section, a method error) is refused as `dispatch` refuses it.
- **The pump starts it.** After each settling pass (`settlePass` in `scripts/goal/settle.ts`), every queued brief of an active Goal whose waits are over is dispatched, the oldest first, through `dispatch` itself and under its launch gates (memory, usage, the Goal's state). One that a gate refuses stays queued with the gate's reason; one that `dispatch` refuses for another reason leaves the queue with that refusal recorded for its Goal's manager, as a settled task's reason is.
- **A task it waited for that is cancelled** does not start it: the brief stays queued and its line says so, for the manager to decide.
- **Seen and undone.** `task goal -- queue` with no brief lists the queued briefs with what each waits for and since when; `task goal -- queue --drop <id>` removes one. `task goal -- status` is another task's file: do not change it.
- A manager queues only its own Goal's briefs; the program may queue any.

The queue is part of the ledger, written under its lock; read `dispatch` in `scripts/goal/tasks.ts` (not yours) and call it. A command is a file in `scripts/goal/commands/`.

Do not build: priorities, a change to `dispatch`'s checks, an event or a mail when a brief starts (the task's own events follow), a change to `tasks.ts`, `coordinator.ts` or `manager-commands.ts` (other tasks hold them).

## Checks

`task goal -- check`, and both test files once with `CLAUDECODE=1`. The tests use a temporary repository and the recording launcher of `scripts/goal/handover.test.ts`, and cover: a free brief starts at once; one that depends on an open task is queued and starts in the pass after that task is verified; one whose path another task has changed starts after that task lands; a cancelled dependency keeps it queued with its line; a memory gate keeps it queued and the next pass starts it; a refusal that waiting cannot cure is refused at `queue`; the listing and `--drop`; another Goal's manager refused. Wait on a running command with one long call (`yield_time_ms: 300000`).
