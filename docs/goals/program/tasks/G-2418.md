## Outcome

The web's surface for `recipes/author-a-recipe` replays this row's record through the Recipe editor and its destination Work page (the authoring route and editor under `apps/web/features/`). The record on main lacks reads the pages send. The web manager's list is staged at `.temp/ref/g2236-record-gaps.md` in this worktree; read it first.

What must be true afterwards, each request taken from the production client and sent with the path and query production sends (not from that list; a request production does not send is not recorded, and the handoff says which listed one that was and why):

- Every persona's record holds every Main read and write the pages send on the row's path: the frame's reads, the page's own, and those of the page a successful action leads to. Read the pages' whole production path once and compare it with the record's labels for each persona; this is meant to be the row's last re-recording for the surface.
- The reads one render sends together start together (`Promise.all`), as the page sends them; writes and reads that need an earlier answer keep their order. A label names what the request is and is fixed where the request is written (for example a name in an `AsyncLocalStorage` the recording fetcher reads), never a counter: the web chooses a sample by its label and expects exactly one.
- Say in the handoff whether the sample `file-import-stale` is reached through the editor path with editor authority, with the requests that lead to it, or that production cannot reach it.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; if recording refreshes identities, every sample changes together.
- The record's reads run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's. One console line per persona gives the elapsed time of the proof and of the visit. The file has a 480 s wall.
- A 5xx that is the final answer: hand off with the request and the answer, do not vary it. The log names slow requests under `[persona-request]`; quote them if a proof meets its limit, and do not run a third time.

The handoff names old and new identities and every new label with its request and status, in a file under `.temp/` of the worktree as well as in summary.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a read at the Account origin (`/api/account/…`, recorded once for the frame elsewhere).
