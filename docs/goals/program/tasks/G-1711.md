## Outcome

Analysis only: change nothing and return a report as your final answer (at most 1,600 words, files cited with line numbers).

Evidence so far (launch's analysis of one Realm reply, measured on main with the complete owner composition, identical at 100 and 1,000 threads): one reply runs four commands and costs 63 Content, 471 Access and 198 Account SQL statements and 70 Fuseki reads. Local batching would save 13%. The stated cause: each owner boundary (route preflight, owner root binding, Access baseline evaluation, admission claim) opens a fresh envelope and rebuilds facts the previous one already read; account verification runs once per command. The full breakdown is in `.temp/ref/g1619-spec.md` and `.temp/ref/g1619-breakdown.md` in this worktree (staged by the manager; if they are missing, work from the code).

The question is whether this is one reply's problem or every command's. Answer:

1. **The fixed overhead of a command.** For three different write commands and two different authenticated reads from the first public scope (a Realm reply, a library status change, a recipe edit; a signed-in list, a Work page), count from the code and the existing profilers (`tests/qa/support/work-profile.ts`, the cost tests) what each spends on account verification, admission and authority evidence before it does its own work. Say which statements repeat within one request and across the commands of one user action.
2. **Why each repeat exists.** Separate the repeats that are deliberate (a freshness or revocation check that must see the latest state, with the invariant it protects) from those that only exist because evidence is not passed along.
3. **The smallest change that verifies once per request** and carries the evidence across owner boundaries without weakening any deliberate check: what the evidence is, who issues it, how an owner trusts it, its lifetime, and what happens on revocation between two commands. Prefer an existing mechanism (the authority witness, the admission claim, the request context) over a new one.
4. **Sizes and owners.** One-session slices in order, each with files and the cost test that proves the saving, the Goal that owns each (kernel, trust-ops, launch), and the expected statements per command after each slice.
5. **Classification input.** Is any of today's cost unbounded (growing with a population), or is it a large constant? State the measured or derived latency share if the profilers give it.

Do not design a cache with invalidation rules, a session store or a token format change. Do not propose removing a revocation or freshness check.
