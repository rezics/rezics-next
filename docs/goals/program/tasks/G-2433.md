## Outcome

The supermanager knows from measurement what the hours from 00:48 to 03:34 UTC on 2026-10-14 cost for each landed task, where the attempts that landed nothing went, and which change gains the most landed tasks an hour now. `.temp/ref/efficiency-audit-6.txt` reads the sessions begun in that window: 230 sessions, 198 workers, 5,676 steps, 460.6M input tokens, 96% cached; wait steps took 36% of worker input (25% in the fourth reading). `.temp/ref/efficiency-audit-6-attempts.txt` counts attempts from the ledger: 27 tasks landed (api 11, program 7, web 6, operations 3).

What the supermanager found in the window, to test against the records and not to take on trust:

(a) Records blocked by the host. Between 02:41 and 03:17 five program record tasks (G-2397, G-2410, G-2418, G-2419, G-2422) handed off `blocked` on 503 answers (`dependency_unavailable`, `work_read_unavailable`, `acting_context_unavailable`) and connection resets; commands took 7 to 10 s. Two others found real defects: G-2396 (the access summary omits deployment-opened groups, now api's G-2431) and G-2422 (the Zone editor saved under the Zone's identity, repaired by web's G-2267; an operator's Zone read answers 404 where the editor read answers 200).
(b) The host. From about 02:20 to 02:57 swap was 31 of 40 GiB and memory pressure 14 to 23%; a fourth zram device at 02:57 brought it under 1%. Landing gates failed on load-sensitive harness tests in that time (G-2215 merged four times, G-2234 once). At 03:32: 36 workers, 16 of 16 QA slots held, nine runs waiting for memory or for another run's start-up while the Docker VM had 13.2 GiB free and the host 11.9 GiB available.
(c) Main red. `apps/web/tests/realm-member-reads.test.ts` failed alone on main from web's frame-reader commits until `3d36fe9e8` (03:09) and failed G-2234's step landing; `scripts/static/qa-runtime-pools.test.ts` failed from `22053e9cd` until `1fb0b1b77`.
(d) Managers. A web surface waits on a program record, which waits on an api repair: G-2355 (contents read) holds five records and five web surfaces behind it.

Read in the main checkout (read only): workers' `.temp/goal-orchestration/runs/<id>/attempt-<n>.json`, `attempt-<n>.last.md`, `settle.log` and `land.log`; the ledger `.temp/goal-orchestration/ledger.json`; the QA lock and admission files under `.temp/` that `task goal -- status` reads; each worktree's QA artifacts under `.temp/worktrees/<id>/.artifacts/qa/`; `git log` of `main`; and the session files that `scripts/goal/efficiency.ts` reads. `.temp/ref/audit-5.md` is the fifth reading and its three rules.

1. **The six windows, counted one way.** The five of the fifth reading and this one: worker input, manager input, tasks landed, input for each landed task, workers with a live process (median), landings an hour.
2. **Where the attempts went.** For each Goal: attempts for each landed task and the share of ended attempts not `done`. Class every `partial` and `blocked` attempt by what stopped it: the host; its brief forbade the repair or rerun; a real defect it found (name it); a question the contract already answered; a tool fault; other. Count the attempts and the tokens of each class.
3. **What the wait steps are.** Name the commands behind the 36%: QA slot, memory, start-up order, landing lock, a worker polling its own run, other. Tokens for each, and how many of those waits ended in a run that tested something. Then what would cut that input without fewer workers, with the measure now and after.
4. **QA throughput.** Runs started and ended an hour; minutes waited for a slot, for memory and for another run's start-up; the start-up time itself. Whether start-ups in order are the narrow place while memory is free, and what one more slot or stack is worth and needs.
5. **What waited on a manager.** For each of the four managers: median and longest time from a worker's exit to that manager's next command on the task, and the task-hours that waited behind the longest five.
6. **Three changes, the largest gain in landed tasks an hour first.** For each: the measure now, the expected measure after, where it is made, what it risks. Then what is not worth changing.

The handoff repeats sections 1, 2, 3 and 6 in at most forty-five lines.

Do not build: a change to any file of the repository, a new tool, advice without a measure.
