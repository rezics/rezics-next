## Outcome

A test run that asks first starts first, and the time it waits is bounded by the runs ahead of it. Tests are what bounds this host: 27 workers ran at 16:22 UTC on 2026-10-13 and their test runs waited far longer than they ran.

What was measured then (`.temp/goal-orchestration/qa-slots/waiters`, `qa-slots/0` to `7`, `docker ps`, `/tmp/rezics-qa-memory-startup.sqlite`):

- Eight of eight ordinary slots held; thirteen waiters, six for memory and seven for a slot.
- The memory waiters had waited since 15:28:20 (54 minutes), 15:39:16, 15:45:44, 16:06:19, 16:15:37 and 16:17:46, while stacks that asked later started at 16:15:34, 16:17:48, 16:18:57 and 16:19:38. Four record tasks stood 42 to 54 minutes inside one test run whose tests take about 90 seconds.
- One waiter reported `Docker VM needs 5.38 GiB + 0.00 GiB reserve, free 11.46 GiB; host needs 1.00 GiB + 8.00 GiB reserve, available 19.35 GiB` and still waited. Five reported `Waiting for another QA startup … free unknown`: `withMemoryStartup` (`scripts/qa/memory-admission.ts:228`) polls every three seconds with `BEGIN IMMEDIATE` and `busy_timeout=0`, reads the memory while it holds the transaction, and admits whoever holds it when the numbers fit. There is no order among waiters. `qa-startup-concurrency` was 3.
- Six test stacks ran with 1.2 to 2.5 GiB of real use each, against 5.38 GiB promised at startup; the Docker VM has 23.5 GiB and the host 62 GiB with about 20 GiB available.

1. **Say first where the time goes.** On the live host, for each waiting run: its class (ordinary slot, heavy turn, memory startup), since when it waits, what it holds while it waits, and which later run was admitted before it and why. Give the cause of a 54-minute wait from that evidence in the handoff, in five lines; the list above is what was seen, not yet the cause.
2. **Admission follows arrival.** Among waiters of one class the oldest whose need fits is admitted first, and a newer run cannot overtake it indefinitely. A waiter that is gone (dead process) gives up its place. Reading the memory does not hold the lock other waiters need.
3. **A run that only waits holds nothing a runnable run needs.** If a run holds an ordinary slot, a heavy turn or a startup place while it waits for another of them, order the acquisitions so that it does not.
4. **State the host's capacity.** From measured use, how many stacks this host runs at once, what bounds it (the VM's 23.5 GiB, the 8 GiB host reserve, the startup promise of 5.38 GiB, the startup concurrency), and which setting would admit more with what evidence. Record it in `docs/storage/workload-budgets.md` where the test memory bound is described. Change no VM size and restart no Docker: that stops every running test, and the supermanager chooses the moment.
5. Unit tests with an injected clock and reader, no real stack: three waiters are admitted oldest first; a waiter that fits is not starved by later arrivals; a dead waiter's place is released; a waiting run holds no ordinary slot.

Do not build: a scheduler service, another lock store, a change to container memory caps, a lower host reserve without the measurement of item 4, the list-only plan (it is another task and holds `scripts/goal/admission.ts`).
