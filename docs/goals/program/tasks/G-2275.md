## Outcome

A test run that waits for memory does not load the host by measuring it, and does not fail because the measurement was slow. `readMemory` (`scripts/qa/memory-admission.ts`) runs `docker info` and `docker stats --no-stream` with a ten-second limit, and every waiter calls it at every poll. On 2026-10-13 twelve runs waited at once beside 33 containers: one `docker stats --no-stream` took 4.2 s on its own, the Docker backend stood at 160% of a processor, and a run's two startups ended after their whole wait with "free unknown … available unknown … failed docker stats measurement" and no assertion reached (QA `20261013t183513-73c1e9`).

1. **One reading, shared.** A reading is written with its time where every waiter of the same state directory reads it; a waiter uses one younger than a few seconds and otherwise takes the turn to measure, so that one process measures at a time and the others wait for its result instead of starting their own. A failed measurement is shared as failed, with its reason, for the same few seconds: no stampede after a failure.
2. **Admission stays as strict as now.** Arrival order, the one startup at a time, the reserve and the rule that admission needs a reading ("unknown" never admits) do not change. A reading taken before the last admitted startup ended is not used to admit the next; say in the handoff how the code guarantees it.
3. **A cheaper measurement, if the figures support it.** Measure twenty calls of the present command on the host as it is and give the median and the worst. The Engine API answers one container's memory without the sampling wait (`GET /containers/{id}/stats?stream=false&one-shot=true` on the Docker socket); use it or another single call if it gives the same sum within the reserve's tolerance and is faster, and keep the present command otherwise. Choose the limit from the measured worst, not from a guess.
4. Decided in code and tested without Docker: ten waiters and one measurement in the sharing window; a failed measurement shared; a stale reading refused for admission after a newer startup; a measuring process that dies leaves the turn to the next waiter.
5. The handoff gives, before and after on the same host: measurements a minute with ten waiters, seconds for one measurement (median, worst), and the wait lines that said "unknown" in one hundred polls.

Do not build: a change to what a stack needs or to the reserve, a daemon, a second admission path, a change under `scripts/goal/`.
