## Outcome

The QA harness can be trusted by a supermanager that schedules heavy work for
four Goals on one 62 GB host:

1. **No stack starts without a slot.** `acquireQaSlots` (`scripts/qa/core.ts`)
   returns `count: Math.max(1, held + acquired.length)`, so a run started
   outside `goalctl test`/`slot` while every slot is taken still starts a stack
   (`scripts/qa/cli.ts` sizes its shards from it). In Goal mode (the slot
   directory exists) a run that holds no slot and can take none waits for one
   with a deadline and says so, or fails with a clear message; it never
   starts a stack on zero leases. Leases are released on normal exit, error,
   SIGINT/SIGTERM and the run's deadline; a dead holder's lease is still
   reclaimed. Outside Goal mode behaviour is unchanged.
2. **A failed restore cleans up.** `restoreCatalogue` in
   `scripts/load/catalogue-backup.ts` leaves the target directory, copied
   volumes and possibly a running stack behind when a volume copy fails or
   the 600-second budget is exceeded after `stack:up` (the caller never gets a
   `stop` handle). Every failure path, including the time-budget throw, tears
   down what the restore created (and nothing it did not create), and the
   error still reaches the caller.
3. **Front-end changes never silently drop out of `--affected`.** `apps/**`
   and `packages/ui/**` are classified `ignore` ("frontend, outside the backend
   Goal"), so a wave touching them prints only "no tests for N paths" and, with
   no backend change, "no affected backend tests". The plan instead names,
   per changed front-end workspace (`apps/web`, `apps/accounts`,
   `packages/ui`), the checks that cover it and runs the cheap, targeted ones
   (that workspace's type check and the unit/component tests of changed
   files); Storybook suites and browser journeys are listed as not run, with
   the command that runs them and the reason (program tier), never dropped.
   A plan's summary never says nothing is affected when front-end paths
   changed. `apps/about` keeps its own `about:check`.

## Smallest change; do not build

No new scheduler, daemon or lease service: the slot directory stays the lease.
Do not expand front-end changes into whole-site Storybook or journey runs, do
not build a route-to-journey or component-to-story mapping, and do not touch
the e2e runner (`scripts/qa/e2e.ts`; Storybook de-duplication is a later
task). The pinned regression command (`goalctl regress`) and the JSON plan
output are a later task (P3).

## Checks

- Unit tests, each failing before the change: zero leases never start a stack
  (and the wait ends at its deadline with a message); a lease is released on
  SIGTERM; a restore whose volume copy fails, and one that exceeds its budget
  after `stack:up`, leaves no target, volumes or stack (inject the Docker and
  Task calls; no real volume copy); a change set of only `apps/web` and
  `packages/ui` files lists the front-end checks, runs the targeted ones and
  does not print "no affected backend tests".
- `task test -- tests/qa/unit/core.test.ts` plus your new unit files, the
  harness test you change, and the type check covering `scripts/`.
- Show `task test -- --affected <base> --list` output for a base where only
  front-end files changed, before and after.
