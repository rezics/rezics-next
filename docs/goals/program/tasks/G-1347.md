## Outcome

The shared stack's Main, Account and relay run `bun --watch` from the main
checkout. Every merge therefore reloads the backend before any refresh has
prepared storage or the model for it. On 2026-10-07 each Turtle or native merge
wave left shared Main unready until the merging Goal's refresh finished: 08:41
to 08:57, and again from 09:13, with others earlier. Frontend workers lose
their backend, and browser runs are stopped for recovery.

In the shared stack (`REZICS_DEV_MODE=main`), run the backend executables
without `--watch` from a dedicated detached worktree under the stack's private
directory. Pin that worktree to the revision the last successful refresh
recorded. `task dev:refresh` advances it:

1. Check out the new revision in the backend worktree.
2. Install dependencies if the lockfile changed.
3. Generate the backend's artifacts there.
4. Prepare storage and align the model from those artifacts.
5. Restart the resources.

A refresh that fails before mutating storage leaves the backend serving the previous revision. Web,
Accounts and Storybook keep hot-reloading from the main checkout. Worktree
stacks (`frontend` and `backend` modes) keep today's behaviour.

Since code-only backend merges now also need a refresh to go live, the merging
manager's `task dev:refresh -- --wait` becomes the one way the shared backend
changes. Make that cheap when the plan has no storage or model step: check out,
restart, wait ready.

Update `docs/development/README.md`. Put the new wording for the refresh
paragraph of `docs/goals/README.md` in your handoff, since another task holds
that file.

## Checks

Unit tests with a stub stack:

- A merge to `main` does not change the backend revision.
- A refresh advances it and restarts.
- A refresh that fails before its first storage- or model-mutating step keeps
  the previous revision running. One that fails after mutation began (storage
  preparation, model alignment) leaves writers stopped and prints the step,
  error and retry command. Migrations and alignment are forward-only (manager
  decision at review, 2026-10-07: a 69 GB volume rollback per maintenance
  refresh is out of proportion).
- A code-only refresh skips storage and model steps.

Do not restart the shared AppHost: the manager switches the live stack over at
merge. Prove the pinned mode on a stack of your own instead. Start an isolated
backend from your worktree with `REZICS_DEV_MODE=main` semantics on its own
ports, or a test seam that does the same. Then commit a no-op, confirm the
backend revision holds, refresh, and report the duration. Give the manager the
exact switch-over steps.
