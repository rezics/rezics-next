## Outcome

The record of `visual-novels/catalogue-browse-and-search-in-its-zone` holds, for each of the six personas, the answers to the requests the production Zone frame and browse page send, so the page's story runs the production readers on a replaying fetch. Today the story builds its frame from the presentation body, because these reads are not recorded, and the empty catalogue is recorded for the member alone. The list below is web's reading of the page's request graph (mails of 2026-10-13 19:50 and 20:08 UTC).

1. Each persona's proof records, under new labels, the requests below, each spelled exactly as the production readers spell it. Read the Zone browse route, `loadRealmView`, `readRealmHeader`, `readFacets` and the host client under `apps/web` only to copy each request's spelling, parameters and headers; change nothing under `apps/`.
   - Anonymous for every persona, with no query, because production reads them through its anonymous client (record them for a signed-in persona through the visitor's session, as `work-showcase` is recorded in `tests/qa/integration/outcomes/anime/navigate-a-thousand-episode-inventory-thousand-chapters.test.ts`): `GET /v1/facets` (`frame-facets`), `GET /v1/realms/<the row's Realm>` (`frame-realm`), `GET /v1/addresses/resolve?scope=space&key=<the row's space>` (`frame-address`).
   - With the persona's acting subject when signed in, and as the visitor sends it otherwise: `GET /v1/zones/<the row's Zone>/routes?path=browse` (`frame-route`); `GET /v1/realms/<Realm>/modules/browse?sort=relevance&limit=20&type=https://schema.org/VideoGame&q=<a text the fixture cannot match>` (`browse-search-empty`; the member's existing empty sample keeps its label and request).
   - For signed-in personas only: `GET /v1/realms/<Realm>/joining?actingSubject=<persona>` (`frame-joining`), `GET /v1/follows/<Realm>?kind=realm&actingSubject=<persona>` (`frame-follow`), `GET /v1/me/platform-access` (`platform-access`; the member's existing sample keeps its label), `GET /v1/realms/<Realm>/member-ban?actingSubject=<persona>` where the persona's platform access opens it (`frame-member-ban`), `GET /v1/me/session-agent` with the session-key header production sends (`frame-session-agent`), `GET /v1/me/person-preferences?actingSubject=<persona>` (`frame-preferences`).
2. A read of this list that a persona's session cannot make as production does is listed in the handoff with the reason and not recorded another way. A read the page's server render makes for one visit that is not on this list is listed too, and not recorded.
3. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes.
4. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added (persona, label, method, path, status), the record's bytes and samples before and after, and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation or of the catalogue's search: run once more, then hand off `partial` with the request, the answer, the host's load (`cat /proc/loadavg`) and the log path, and leave the record on `main` as it is.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record, a rewrite of the recorded presentation request (the replaying fetch reads an empty query as none).
