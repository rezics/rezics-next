## Outcome

When the web app's requested scopes or grants change (`MAIN_SITE_SCOPES` in
`apps/web/features/auth/scopes.ts`), `webClientCurrent` reports the shared dev
stack's registered web client as stale. The bootstrap then registers a new
client with a new `client_id`. That changes `WEB_OAUTH_CLIENT_ID` in the
stack's environment, and the AppHost must restart to pick it up. On
2026-10-07 this cost the shared stack restarts.

Update the existing client in place instead: its scopes, grant types and
first-party installation. Keep its `client_id` (and secret, if any), so a
scope change needs no environment change and no AppHost restart. Register a
new client only when none exists, or when the existing one cannot be updated
(for example, it was revoked). Say which case applied in the output.

Use the Account service's supported client-update path, the same way the
bootstrap registers clients today. Do not write Better Auth tables directly
unless registration already does so.

## Checks

Unit tests:

- A stale client is updated in place, and its `client_id` is unchanged.
- A missing client is registered.
- A revoked installation is re-registered and reported.

Run `task goal -- test scripts/dev/web-auth-bootstrap.test.ts`. Start nothing
on the shared stack.
