## Outcome

Program measured where workers wait, from 06:00 to 09:25 UTC on 2026-10-14. 37% of worker input tokens were polls: a worker re-sending its whole context (median 144k tokens) to ask whether a command had finished. A Codex poll blocks at most 60 s. By command waited on: the worker's own `task goal -- check` 43%, tests that start a QA stack 15%, type checks and tests chained after `task gen` 12% (`task gen` itself takes 1-2 s). Inside a check, the 38 repository guards run one after another in a single `bun test` process: 295 s summed, 301 s wall. Six files cost 81%: authentication-subject 74 s (one case 45 s), mechanism-dependencies 65 s, serialization-points 31 s, web-acting-identity 27 s, g-543-rate-limit 22 s, g-1046-sql-relations 20 s. The type check had a median of 52 s but p75 of 172 s while queued for memory (web needs 5.5 GiB plus 8 GiB reserve). Type-aware lint took 60 s and peaked at 9.2 GiB.

Two guards are slow because of database work. Rust would not help them. `services/account/tests/authentication-subject.test.ts` (74 s) guards "every Account request cookie parser must use the provider-exact authentication selector", and `services/main/tests/g-543-rate-limit.test.ts` (22 s) guards "every installed Main route and generated operation must have a rate-limit family". Both files also hold PostgreSQL behaviour cases. One case, "P23: trusted ingress normalizes repeated metadata without changing the provider subject", takes 45 s by itself.

- Split each file. The static rule stays a repository guard and needs no database (under 2 s each). The behaviour cases move to a file in the tier that runs on a stack in the prove phase and the merge gate, registered as the test registry requires. Keep every assertion.
- Find why P23 takes 45 s. Repair a sleep, a timeout or repeated setup. If the time is genuinely needed, explain it.
