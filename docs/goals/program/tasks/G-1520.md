## Outcome

The maintainer suspects that much of the code breaks good abstraction and modularity and Occam's razor. The suspected forms are: one concept implemented more than once; source-, vertical- or feature-specific code where a general capability should be configured; and layers, files and options that do not earn their cost. Today's example: the Bangumi import (commits 49283cecb, 0fb8d328e) added `rv:source`/`rv:licence` literals, an adaptation note and a CC BY-SA constant to Main. But `services/main/src/modules/rights` already models material, use assessments and attribution/share-alike/change-indication obligations. A cover task was also about to add its own mark and fence beside the Access governance enforcement fences. Intended architecture: `docs/product/platform-thesis.md` (mainline abstraction base, capabilities, vertical manifests), `docs/product/goal.md#backend-one-frontend-free`, `docs/product/design-principles.md`.

This is read-only research. Change no tracked file and run no tests or dev servers. One-off analysis tools may run through `bunx` (for example jscpd, knip, madge, dependency-cruiser) without being added to the repo. Write the report to `.temp/report.md` in your worktree, at most about 400 lines, and end with the usual handoff message. Cite every claim as `path:line`. Mark what you verified and what you inferred.

Scope: `services/main/src`, together with `model/definitions` and the native command layer where Main depends on it.

1. For each cross-cutting concept, list every implementation:
   - provenance, evidence, source and licence;
   - rights, restriction, fences and holds;
   - receipts, idempotency and compare-and-swap heads;
   - outbox and events;
   - authority and access checks;
   - caps, pagination and bounded reads;
   - media selection and Use;
   - read projections and summaries;
   - text and language fields;
   - visibility and disclosure;
   - quotas and rate limits;
   - other concepts you find.
2. Rank the concepts that have two or more implementations by cost: size, number of call sites, and the risk of the two diverging. For each, name the mechanism that should remain or the general replacement, and estimate the lines that could be removed.
3. List source-, vertical- or feature-specific code inside the engine that should be configuration over a general capability. Start with the named modules (recipe, realm-*, zone-*, library-*, work-*, wiki, catalogue*, source/open-library) and anything that names a provider.
