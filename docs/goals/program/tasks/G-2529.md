## Outcome

Each QA run starts a private stack (PostgreSQL, Fuseki, RustFS, toxiproxy, mailpit). Admission charges it its container caps, 10.38 GiB, so few stacks start at once. Startup and restore are budgeted at under 10 minutes (`docs/storage/workload-budgets.md#data-preparation-and-import`). The prove phase runs hundreds of outcome and integration files, so stack time sets the pace of every wave.

Write a design note, `docs/storage/qa-shared-databases.md`, for review by the supermanager. It should cover:

1. **Measurements on this host:** time from admission to ready for a QA stack now, split by phase (container start, restore of the fixture backup, migrations, Main and Account start), and memory actually used per stack against its caps.
2. **The proposal:** one long-running PostgreSQL and one Fuseki shared by ordinary runs. Each run gets its own databases and datasets, cloned from a fixture template (`CREATE DATABASE ... TEMPLATE`, a TDB2 dataset copy or an equivalent), and they are dropped afterwards. Measure clone time for the small and medium fixtures.
3. **Which tests keep a private stack, and why:** fault injection through toxiproxy, restore and erasure drills, process kills, version pins. Name the files or their markers.
4. **Isolation guarantees:** credentials per run, no cross-run reads, cleanup after crashes.
5. **Migration steps and risks**, and how the harness chooses shared or private per test file.

No code changes beyond the measurement scripts the note needs, kept under `.temp/`.
