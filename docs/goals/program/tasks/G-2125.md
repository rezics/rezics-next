## Outcome

A worker learns of a landing its own change failed from the tool, as the failure alone, and no manager call is spent on it. Today the settling pass (`scripts/goal/settle.ts`) leaves every stopped landing to a manager, who reads the output and resumes the session with a summary of it.

- When the landing of a task stops on a check the worker can answer, the pass resumes the worker's own session as a fix round (`resumeTask`, `scripts/goal/tasks.ts`) with a message that holds only: which check stopped it, the failing cases and the first lines of each error, sixty lines at most, and the path of the whole output. Such checks are the pre-merge type check, the unit gate, a repository guard, and a review finding that comes with a failing test.
- What a worker cannot answer stays with the manager as today, with its reason: a scope violation or a claim conflict, a brief or a task that changed during the review, a stale review, a merge conflict the tool could not rebase, a dependency that has not landed.
- One function classifies a refusal into those two kinds from the refusal the landing records; a refusal it does not know stays with the manager.
- The tool sends at most the two fix rounds the tool allows today and never writes a `## Decision` into a brief: when the cap refuses the resume, the task is settled for the manager with the cap's line and the last failure.
- `status` shows beside the task that a fix round was sent by the tool and for which check, and the manager's task event is raised only when the task is settled, as today.
- Nothing is sent to a task whose landing was started by a manager's own `land` command: that manager is watching it.

`resumeTask` and the landing are other tasks' code: call them, and say in the handoff if either needs a change.

Do not build: a new check, a change to a gate or to the review, a change to the cap, a retry of the same landing without a change by the worker, mail to anyone.

## Mechanisms

none

## Checks

`task goal -- check`, and `settle.test.ts` once with `CLAUDECODE=1`. The tests cover, with the recording launcher: a unit-gate refusal sent back with its bounded failure and landed after the worker's fix; each kind that stays with the manager; an unknown refusal; the cap reached; a landing a manager started; a restart of the pass between the refusal and the resume. `land.test.ts` is another task's file: if one of its tests must change, name it in the handoff. Wait on a running command with one long call (`yield_time_ms: 300000`).

## Decision — 2026-10-13

The handoff is right: since the settling pass landed, `wait` on a task with `land: auto` and a `partial` handoff exits 0 and prints the settlement reason, and `land.test.ts` (`auto wait prints a partial stop reason and leaves the task open`) still expects status 1 and `RESULT is partial` on stderr. The behaviour stands: `wait` reports, and a partial handoff is not its failure. `scripts/goal/land.test.ts` is now in this task's paths: change that one expectation to status 0 and stdout containing `RESULT: partial`, change nothing else in the file, run `task goal -- check` and hand off.
