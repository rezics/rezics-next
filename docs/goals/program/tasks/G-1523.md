## Outcome

The maintainer suspects that much of the code breaks good abstraction and modularity and Occam's razor. The suspected forms are: one concept implemented more than once; source-, vertical- or feature-specific code where a general capability should be configured; and layers, files and options that do not earn their cost. Today's example: the Bangumi import (commits 49283cecb, 0fb8d328e) added `rv:source`/`rv:licence` literals, an adaptation note and a CC BY-SA constant to Main. But `services/main/src/modules/rights` already models material, use assessments and attribution/share-alike/change-indication obligations. A cover task was also about to add its own mark and fence beside the Access governance enforcement fences. Intended architecture: `docs/product/platform-thesis.md` (mainline abstraction base, capabilities, vertical manifests), `docs/product/goal.md#backend-one-frontend-free`, `docs/product/design-principles.md`.

This is read-only research. Change no tracked file and run no tests or dev servers. One-off analysis tools may run through `bunx` (for example jscpd, knip, madge, dependency-cruiser) without being added to the repo. Write the report to `.temp/report.md` in your worktree, at most about 400 lines, and end with the usual handoff message. Cite every claim as `path:line`. Mark what you verified and what you inferred.

The other three audits (G-1520 to G-1522) find the instances. Your question is the root cause and the fundamental fix: how to keep a codebase built mostly by AI workers, each working from a short brief, to one mechanism per concept, without relying on reviewers to notice.

1. Diagnose how duplication enters here. Read `docs/goals/manager.md`, `docs/goals/worker.md`, the goalctl land and merge gates (`scripts/goal/goalctl.ts`), the lint and ast-grep rules (`task ast-grep`, `scripts/static`), the capability registry (decision 14, `docs/contracts/api.md#executable-capability-registry`) and recent briefs under `docs/goals/*/tasks`. Use G-1513 and its stopped successor G-1518 as a worked example.
2. Survey the established options and the evidence for each:
   - architecture as code: module boundary rules, dependency-cruiser, eslint boundaries, Nx-style tags, ArchUnit-like tests, fitness functions;
   - a machine-checked registry of concepts and their single owner mechanism;
   - generation from model definitions;
   - clone and dead-code gates;
   - deep-module design (Ousterhout);
   - reuse-first brief and review protocols;
   - published findings on LLM coding agents re-implementing instead of reusing.
3. Recommend, ranked by expected effect for cost, what REZICS should adopt: in code (gates, rules, registry), in the Goal workflow (brief template, manager review, merge gate), and in architecture (which generic capabilities would make the per-feature copies unnecessary). For each, give the smallest first step and how to verify that it works. Use web sources and cite them.
