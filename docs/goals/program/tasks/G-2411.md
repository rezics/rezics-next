## Outcome

The web's surface for `anime/continue-progress-across-devices-two-device-progress` replays this row's record through the production Work page and its episode control (`apps/web/features/tracking/episode-api.ts`, `episode-progress.tsx`, `episodes.ts`, the Work frame in `apps/web/features/work-page/`). The record's conflict probes use bodies no production control can send: an unmark at version 0 (version 0 is never watched) and a mark at version 1 (after one mark, version 1 is never unwatched). Those probes prove the API's compare-and-swap and stay as they are. What a person's two devices really do is missing from the record, and so are the relationship reads the signed-in Work frame sends. The web manager's reading is in `docs/goals/web/tasks/G-2329.md` under its last decision; read it first.

What must be true afterwards, each request taken from the production client and sent with the path, query and body production sends (not from this list; a request production does not send is not recorded, and the handoff says which listed one that was and why):

- For every signed-in persona who may write progress, the reachable conflict in both directions, as two sessions of the same Person:
  - both devices read the episode unwatched at the same version; the first marks it watched; the second marks it watched with the body its stale view makes the control send; the answer (409 or whatever the API gives) and the reads the control sends to recover are recorded;
  - both devices read it watched at the same version; the first clears it; the second clears it with its stale body; the answer and the recovery reads are recorded.
  The mark body is production's: the position `markPosition` gives when completing, none when clearing. Never set a version by hand to reach a state; a state is reached only by reading and writing as the two devices would.
- The signed-in Work frame's relationship reads (the read behind the relationship control that now shows "unavailable" without a sample) and every other read the frame and the page send for each persona, the visitor's refusal or absence included.
- Use an episode the proof does not assert on, or run after the proof's assertions, so no existing sample's answer changes; say which you chose.
- This is meant to be the row's last re-recording for the surface. Before recording, read the page's whole production path once and compare it with the record's labels for each persona; record every read still missing and list those beyond the items above.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; their bodies, versions and retry keys stay exactly as recorded. Name any existing sample whose answer changed and why.
- The record's reads run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's.
- A 5xx: hand off with the request and the answer, do not vary it. The log names slow requests under `[persona-request]`; quote them if a proof meets its limit, and do not run a third time.

The handoff names old and new identities and every new label with its request and status, in a file under `.temp/` of the worktree as well as in summary.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a forced version, a normalised or adapted body.
