## Outcome

The maintainer's question: tests cost this host far more than implementation; would one set of infrastructure serving many test runs be clearly more efficient? Measured on run 9 (idle host, 140 integration batches of five files): a stack costs a median 33 s outside its tests (start, bootstrap, cleanup; 90th percentile 42 s) against 73 s of tests, 19% of 6.3 hours. A worker usually runs one to three files, so for it the stack costs about as much as the tests, and stack startups are serialized host-wide ("Waiting for another QA startup"), which is where queues of 8 to 13 waiting runs came from today. Each run today starts and destroys its own Postgres, Fuseki, object store and services.

Inside one run the harness already shares a stack across files and resets it for fresh-state files (`scripts/qa/integration-shards.ts:86-111`, "One stack/bootstrap per worker. Fresh-state files reset that stack between commands"). Extend that across runs.

1. **Record the phases.** `ShardRecord` has `startupMs`, `bootstrapMs` and `cleanupMs` (`scripts/qa/core.ts:433-435`) but a run's summary omits them and admission waits are not timed. Put queue wait (memory, startup turn, slot), startup, bootstrap, tests and cleanup, in seconds, in each run's `summary.md` and in one JSON line appended to a host file beside the QA slots, so the effect of everything below is measured, not estimated.
2. **A host pool of warm stacks for the ordinary class.** When an ordinary-class integration stack finishes its run cleanly, reset it to the fresh state with the existing reset and park it instead of destroying it. The next run of the same class whose infrastructure fingerprint matches (compose configuration, image digests, migration set, assembler) leases a parked stack instead of starting one and skips the startup turn. Rules:
   - a parked stack is owned by nobody; a lease names its holder's pid, and a stack whose holder died without releasing is destroyed, never reused;
   - a stack whose run failed in the stack or bootstrap stage, or whose reset fails, is destroyed;
   - parked stacks count in memory admission as what they are (running containers), the pool never exceeds the QA slot count, and a stack parked longer than fifteen minutes is destroyed;
   - never pooled: command-only files, non-ordinary resource classes, fault/recovery, the e2e tier, anything in `isolated-integration-files.ts`, and any run started with `--keep` or `--backend`;
   - the pool is off unless `qa-stack-pool` beside the QA slots says `on` (program switches it), so landing this changes nothing until it is switched.
3. **Proof.** Unit tests for lease, release, dead holder, fingerprint mismatch, age and the off switch; `tests/qa/integration/shared-stack.test.ts`: two consecutive runs where the second leases the first's stack, sees none of its data, and is faster by the recorded startup; a run after a crashed holder gets a new stack.

If the cross-run reset cannot guarantee a fresh state with the existing reset (name what leaks), stop after item 1 and return that as the finding with the smallest fix; do not invent a second reset.

Program decision after the first handoff: this task lands item 1 only (the recorded phases). The worker found that the existing reset keeps RustFS objects and Mailpit messages, so items 2 and 3 move to a following task that first extends the reset.

Smallest change: one pool module and the calls at stack start and stop. No new container, no shared database server across runs, no change to what a fresh state means.
