## Outcome

The coordinator pilot works with a real manager. On 2026-10-07, trust-ops (Codex,
default account) was handed over by explicit handover. Its first coordinator-started
turns acknowledged all 22 of its mails and ended cleanly (attempts `41f1a042` and
`91cba0bf`).

The pilot code still refuses a second enrollment ("This pilot enrolls one manager;
unenroll before a new handover", in `goalctl.ts`). Kernel runs on the second Codex
account (`codex-1`, `CODEX_HOME=~/.codex-1`) and should move next.

1. Let the coordinator hold one enrolled manager per Goal. Each Goal gets its own
   wakes, attempts, backoff and single-flight turn, so one Goal's failures or
   quota denial never delay another's. Keep each descriptor's account home exactly
   as goalctl launches that engine (`codex-1` uses `~/.codex-1`).
2. Ownership and handover stay as G-1384 and `44f60f64d` define them: the named
   previous owner, `resume <session>` in argv, and session variables, except for
   processes under a `codex exec` of another session.
3. In `docs/goals/manager.md`, add the explicit-handover procedure as the
   managers' practice. The steps are: checkpoint; mail program the session UUID
   and interactive PID; program enrolls with `--previous-owner-pid`; exit the
   interactive session. Also say that Claude managers stay interactive for now:
   program runs in the maintainer's own terminal, and launch's interactive
   session serves its UX review.

## Checks

- Unit tests: two Goals enrolled on different account homes wake independently; a
  failing Goal's backoff does not delay the other; one Goal's live attempt does not
  block another's.
- A real `task goal -- coordinator status` with trust-ops enrolled stays
  unchanged after your change. Do not enroll kernel; program does that handover.
