## Outcome

A demonstrated failure never waits for someone to notice it. A `pending` cell on `main` is a request the API answers wrongly; its Goal's manager must turn it, with the others of its cause, into one implementation task. Today a task that lands raises no event (`managerEvents` in `scripts/goal/manager-commands.ts` skips a `verified` task), so on 2026-10-13 nine pending cells landed and nothing started their planning until the program wrote a mail by hand.

- **Uncovered rows raise one event.** A row is uncovered when a cell of its declaration on `main` is `pending` (`scripts/qa/cases/outcomes.ts` reads the declarations and prints the scope line) and no open task of kind `implementation` names the row in `rows:`. While a Goal has uncovered rows in its area, `managerEvents` raises one planning event for it.
- **Never two at once, never the same twice.** No planning event is raised while one of that Goal is not yet acknowledged. After its turn ends, the next is raised only when the set of uncovered rows differs from the set that turn was given, so a turn that left a row uncovered on purpose is not started again for it.
- **The event carries what the turn needs,** in at most sixty lines: for each uncovered row its id, the pending personas with the note each `pending(...)` gives, the declaration's file, and the task that landed it with the path of its last handoff under the state directory. Rows past forty are counted. It ends with the order: one implementation task for each cause and not for each cell, a fixture that cannot reach the state counts as a cause, and a row left uncovered is named with its reason in the Goal's `state.md`.
- **Which Goal.** A row belongs to the Goal whose task landed its declaration; a declaration with no such task in the ledger goes to the Goal that owns its file (`task goal -- owner`).
- A Goal with no enrolled manager gets no event. `task goal -- planning [goal]` prints the uncovered rows of each Goal as the event would (a command is a file in `scripts/goal/commands/`), for a manager with no coordinator and for the program.

Put the reading and the set in `scripts/goal/planning.ts` and call it from `managerEvents`. Change `coordinator.ts` only if the acknowledgement or the one-at-a-time rule cannot be kept in the event store's existing calls; say in the handoff what you changed there.

Do not build: a change to mail, to a turn's bound or to the role card, a brief written by the tool, an event for a row that is proved or missing, a change to `status`, `settle.ts` or `tasks.ts` (other tasks hold them).

## Checks

`task goal -- check`, and both test files once with `CLAUDECODE=1`. The tests use a temporary repository with declaration fixtures and a ledger and cover: a pending row with no task raises the event with its personas and notes; an open implementation task naming the row covers it, and a closed one does not; no second event while the first is unacknowledged; none after the turn when the set is the same, and one when a row joins; two Goals each get their own rows; the sixty-line bound; no manager, no event; the command's output. Then run `task goal -- planning` once on the real state and give its output in the handoff. Wait on a running command with one long call (`yield_time_ms: 300000`).
