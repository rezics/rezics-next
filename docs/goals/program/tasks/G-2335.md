## Outcome

An integration run that starts a stack waits for memory today and for nothing else. On 2026-10-13 from 20:00 to 20:55 UTC the host (64 processors) ran ten or eleven stacks at a load of 85 to 103, and eight recording runs in a row failed on answers that came too late: 503 `work_read_unavailable`, 503 `zone_route_unavailable`, 60-second proof timeouts, tokens that ended on the way. Each lost eight to sixteen minutes of a worker and was run again, which added to the load. A run that waits two minutes and passes is worth more than one that starts at once and fails.

1. The admission in `scripts/qa/memory-admission.ts` that holds a stack back for memory also holds it back while the host's one-minute load divided by its processors is above a limit. The limit is read from a file `qa-load-limit` beside the slots, as `qa-slot-count` is (`qaSlotCount` in `scripts/goal/qa-slots.ts` shows the form); without the file it is 1.0. The load is read from `/proc/loadavg`, or from the file an environment variable names, so that the rule is tested without a host.
2. Runs that wait for load start in the order they came, one at a time and at least twenty seconds apart: the load average falls slowly, and releasing every waiter at once would bring the collapse back.
3. A waiting run is visible the way a memory waiter is (a `load-…` entry in the waiters directory with its command), and its log says at admission what the load was and how many seconds it waited. The present memory deadline bounds the wait; a run that reaches it starts and says so, it does not fail.
4. A run that starts no stack (a unit lane, a type check) is never held by this rule.
5. Tested without a host: held above the limit and admitted below it; the order and the spacing; the deadline; a unit lane passes; the limit file's value and its absence.

Do not build: a change to the slots, to the memory rule or its numbers, to any time limit of a test, a second scheduler, a change under `scripts/goal/`.
