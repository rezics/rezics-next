## Outcome

`recipes/exchange-recipes` has its record, `tests/qa/fixtures/outcomes/recipes/exchange-recipes.json`, written by its own outcome test. The test already records as `OutcomeRecorder` asks; no record is on `main` because the export's answer did not match its declared schema and the recorder refused to publish. The api task that aligns that schema adds `services/main/tests/recipe-export-contract.test.ts`; this task starts when that file is on `main`. Web's surface for the row waits for this file.

1. Run the row's outcome test so that it records, and check in the record it writes. The six persona proofs pass unchanged; no assertion changes and no cell changes state.
2. The record also holds what the row's page reads to render. Find the web route that shows the exchange under `apps/web` (read it and its readers; change nothing there) and record, for each of the six personas with that persona's acting subject and with none for the visitor, each request the page's server render makes for one visit, spelled exactly as the page's request builders spell it, the frame's reads included (see the `frame-*` samples of a record that has them, if one has landed). The handoff lists any read of the page that could not be recorded, with the reason.
3. `scripts/api/answer-records.guard.test.ts` passes. The handoff gives the record's bytes and samples, the labels per persona, and the recording run's seconds.

If the recorder still refuses an answer against its schema, hand off `partial` with the operation, the path in the answer and the validator's message: that is the API's, not a thing to work around. An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation: run once more, then hand off `partial` with the request, the answer, the host's load and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or a fixture builder, another row's record.
