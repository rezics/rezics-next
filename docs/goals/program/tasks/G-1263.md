## Outcome

`goalctl merge`'s pre-merge unit gate (`preMergeUnitGate` in
`scripts/goal/goalctl.ts`) runs the affected unit files in one `task test`
call. bun runs test files one after another, so a change in Access selected
482 files and the gate ran past 25 minutes while the merging manager waited.

1. Split the affected set into `GOAL_UNIT_GATE_SHARDS` parallel `task test`
   calls (default 4), balanced by file count, and merge their results. Read
   failing files with the existing `failingTestFiles` on each shard's output.
2. Give the whole branch side a time budget, `GOAL_UNIT_GATE_BUDGET_MS`
   (default 12 minutes, across all shards). When it runs out, stop the shards
   and report the gate as inconclusive, not blocking, naming the files that
   did not finish, as the current code already does for an unfinished run.
3. The rerun of failing files at main's boundary uses the same shards and
   budget.

Keep everything else as it is: the gate runs before the ledger lock,
`--skip-unit-gate` skips it, and only failures the task introduces block.

## Read

`scripts/goal/goalctl.ts` (`preMergeUnitGate`, `failingTestFiles`,
`mergeUnitFiles`, `mergeTask`) and its tests in `scripts/goal/goalctl.test.ts`
(the parameterised "pre-merge unit gate handles … failures" tests and "runs
without holding the ledger lock").

## Do not

Change which files are selected, add a cache or a daemon, or move the gate
inside the ledger lock.

## Checks

Unit tests: a set of eight files runs as four shards whose union of failures
is reported; a shard that exceeds the budget makes the gate inconclusive and
the merge proceeds; existing gate tests still pass. Then one real measurement:
time `task test -- --affected <main> --list`'s unit files for a recent
Access-touching commit run through the new gate, before (one call) and after
(four shards), and report both durations.
`task test -- scripts/goal/goalctl.test.ts` and the type check covering
`scripts/goal`.
