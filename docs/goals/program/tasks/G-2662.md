## Outcome

The maintainer asked on 2026-10-15 for a standardized goalctl configuration in a `.goalctl/` directory, like `.vscode`, so the tool works on any computer without configuration conflicts and machine-local details stay out of Git.

Today goalctl hard-codes two Codex accounts by name and home: `dispatchEngine` and `tasks.ts`, `solAccount` in `handover.ts`, `efficiency.ts`, `measures.ts`, `coordinator.ts` and `REVIEW_ENGINES` in `land.ts`. It also reads ad-hoc one-value files from `.temp/goal-orchestration`, among them `codex-service-tier`, `review-engine`, `confirm-interval-minutes`, `gate-lanes`, `qa-slots`, `regress-lane-count`, `unit-gate-scope`, `unit-gate-shards` and `telegram-chat`.

1. **Format.** Define one versioned settings format with a JSON Schema at `.goalctl/settings.schema.json`, tracked. Settings come in layers, each later one overriding the earlier:
   - built-in defaults;
   - `.goalctl/settings.json`: tracked project defaults with no account, machine or person detail;
   - `.goalctl/settings.user.json`: ignored by Git, for machine- and person-local values.

   Add the ignore rule for `.goalctl/*.user.json`. Validate every layer against the schema at load and name the file and field on error. `task goal -- config` prints the effective settings and the layer each value came from.
2. **Accounts.** Codex accounts are a user-layer setting. Each account has its engine name as used by `dispatch --engine`, `resume` and the coordinator; its launcher or Codex home; a dispatch preference weight; and an ordered list of what it may use past its allowance, empty by default. Every place above uses the configured set:
   - dispatch, resume (an attempt stays on its account) and the coordinator;
   - automatic selection for new work, by weight and current usage;
   - efficiency and usage readouts per account, review engines and measures.

   With no accounts configured, there is one, the default `codex` launcher.
3. **Existing one-value files.** Move each configuration value goalctl reads from `.temp/goal-orchestration` into the settings: project defaults in the shared layer, machine and operational choices in the user layer. Migrate an existing value once, on first load, into the user layer, and report it. Runtime state stays in `.temp`: ledger, runs, mail, locks and last-start times.

Tracked code, tests, schema examples and documents name no real account and no policy. Tests use synthetic accounts and temporary settings directories. Document the layers and fields, not this machine's values, in `docs/goals/manager.md` under Resources and in `docs/development/toolchain.md`.

Prove it:
- with three configured accounts, `dispatch --engine <third>` launches through its launcher;
- automatic selection follows the weights;
- a resumed attempt stays on its account;
- the efficiency readout lists all three;
- an invalid user file is refused with the field named;
- removing the user file falls back to the shared layer and the defaults;
- each migrated one-value file still takes effect.
