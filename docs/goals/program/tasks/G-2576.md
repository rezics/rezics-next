## Outcome

Twice in five minutes on 2026-10-14, a surface's Storybook run (`task storybook:test`, vitest browser project `storybook` in `apps/web/vitest.config.ts`) ran zero tests because "The iframe … .stories.tsx did not become ready within 60000ms": G-2325's `recipe-reading-recorded.stories.tsx` at 21:54 and G-2235's `realm-team-recorded.stories.tsx` at 22:02, 73 s in total. Both worktrees had just been rebased onto main. The host load was about 60. The project sets no `optimizeDeps`, so Vite discovers and bundles dependencies at the first story request and can reload mid-run.

Make a story test start reliably:

- pre-bundle at server start, with `optimizeDeps.entries` covering the stories and their production imports, or an equivalent, so no discovery reload happens during a run;
- give the browser iframe readiness a limit that fits a loaded host, as `testTimeout` already does.

Prove it:

- reproduce first: clear `apps/web/node_modules/.vite` and run one recorded story with the host loaded by other stacks, and show the timeout;
- then show it passing the same way;
- report the time to first test, cold and warm.

## Mechanisms

none

## Checks

The reproduction red and then green, `task storybook:test` on three recorded stories, and `task goal -- check`.

## Decision — program, 2026-10-14 22:39 UTC

Design note: the 180 s readiness limit landed as a step (`f0336bff6`). Dependency discovery is ruled out, since Vitest already scans every story at startup. The next step diagnoses the real failure. Reproduce a failing multi-story run (three to six recorded stories at once, and the two failing ones, `recipe-reading-recorded` and `realm-team-recorded`, alone after a rebase). Capture the browser console and network log of each iframe and the Vite server log, using Playwright tracing or a page `console`/`requestfailed` listener in the browser provider configuration. Name the module that fails to fetch and why: a transform error, a server restart, a memory kill or a request timeout. Then fix that cause, and prove it with three multi-story runs in a row with no initialization failure.
