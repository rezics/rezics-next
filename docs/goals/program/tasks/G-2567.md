## Outcome

`GET /v1/search/catalogue` answers its first page with bounded native work, whatever the size of the population. Today it does not. `realm/closure-search` fails with 503 for all six personas once the stack holds another file's population, and passes alone. `realm/closure-directory` fails the same way, with 422. Commit `496d6e644` hid this by giving both outcomes their own QA stacks. An operation whose work grows with the whole population breaks the scale rule: every operation touches a bounded neighbourhood.

Earlier measurement (packet in `.temp/ref/`) correlated the growth for the identical word page-zero native query. Size 26 made 59 `next` and 163 `advance` calls, and size 74 made more. The work sits in the Jena text extension: `FilteredGraphTextIndex`, `RankedFunction.exec` → `ranked(...)`, `RankSearcher.createWeight` and `observedIterator`. The source-level candidate is the catalogue's global entity `PrefixQuery` filters (Realm OR work-name prefix, admitted body and name kinds), which Lucene expands across every matching term.

Find the operator that scales with the population and fix it at its cause. Possible fixes:

- a filter on an indexed exact field instead of prefix expansion;
- a per-Realm or per-kind term so that the filter is a single term lookup;
- early termination at the page bound.

Keep ranking and disclosure exactly as they are. Prove it with a growth check on seeded sizes 10, 26, 74 and 200: native `next`/`advance` calls and served time for the same page stay flat within a stated constant, red before and green after. Then remove the own-stack isolation for `closure-search` (and for `closure-directory` if the same cause explains it) so that both pass on a shared stack beside other files. If the directory has a different cause, fix it too or hand it off precisely.
