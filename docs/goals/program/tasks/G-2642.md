## Outcome

The maintainer allows upgrading every package to its latest available release. Packages pinned to a prerelease are pinned that way to stay current. Today many are behind:

- `elysia` is at 2.0.0-beta.16, with `next` 2.0.0-beta.32;
- `@elysia/eden` and `@elysia/openapi` are at beta.5 and beta.4, with beta.6 available;
- `next` is at 16.3.6 against 16.4.1;
- `react` is at 19.3.0 against 19.3.1;
- Storybook is at 11.0.0-alpha.1 against alpha.6;
- `vitest` is at 5.0.2 against 5.0.4.

Upgrade every dependency in every workspace to the newest release on the channel it already tracks. A prerelease pin moves to the newest prerelease of that line (`next`, `beta` or `alpha`); a stable pin moves to `latest`. Never move a stable package onto a prerelease. Use Yarn for the install (`task install`, `yarn up`) and keep the lockfile immutable-clean.

Work in groups, and run the checks after each one, so a breakage points at its group:

1. the Elysia family (`elysia`, `@elysia/*`), with the API contract generation (`task gen`) and the Eden gate;
2. web (`next`, `react`, Storybook);
3. test and build tooling;
4. the rest.

Fix every breakage the upgrade causes, at its cause; read each package's changelog for breaking changes first. If `@elysia/openapi` beta.6 fixes the overwrite of authored `detail.responses`, remove the overlay in `scripts/api/generate.ts` that G-2586 added; otherwise keep it. If a package's newest release is broken for us in a way we cannot fix cleanly, pin it to the newest working release, with the reason in `docs/development/toolchain.md`.

Update `docs/development/toolchain.md` in the same change, per AGENTS.md.
