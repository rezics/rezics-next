## Outcome

Each QA run starts and destroys its own stack. A stack costs a median 33 s outside its tests, and stack startups take turns host-wide; with a dozen workers that queue, not memory, is what holds tests back (2 stacks running, 12 runs waiting, 19 GiB available at 15:47 UTC on 2026-10-11). The previous task recorded each run's phases (`qa-phase-times.jsonl` beside the QA slots) and stopped before pooling, correctly: `resetIntegrationState` in `scripts/qa/integration-reset.ts` keeps RustFS objects and Mailpit messages, so a reused stack would show one run another run's objects and mail (`chapter-seek` writes digest-keyed objects into the fixed bucket and prefix; `access-baseline-seed` sends real SMTP messages).

1. **The reset reaches every store.** Extend `resetIntegrationState` to empty the QA bucket in RustFS and delete every Mailpit message, and to verify both are empty before it reports success. A reset that cannot clear or verify a store fails, and its caller treats the stack as unusable. This also closes the same leak between fresh-state files inside one run today.
2. **A host pool of warm stacks for the ordinary class.** When an ordinary-class integration stack finishes its run cleanly, reset it and park it instead of destroying it. The next run of the same class whose infrastructure fingerprint matches (compose configuration, image digests, migration set, assembler) leases a parked stack instead of starting one, and skips the startup turn. Rules:
   - a parked stack is owned by nobody; a lease names its holder's pid, and a stack whose holder died without releasing is destroyed, never reused;
   - a stack whose run failed in the stack or bootstrap stage, or whose reset fails, is destroyed;
   - parked stacks count in memory admission as what they are (running containers), the pool never exceeds the QA slot count, and a stack parked longer than fifteen minutes is destroyed;
   - never pooled: command-only files, non-ordinary resource classes, fault/recovery, the e2e tier, anything in `isolated-integration-files.ts`, and any run started with `--keep` or `--backend`;
   - the pool is off unless `qa-stack-pool` beside the QA slots says `on` (program switches it), so landing this changes nothing until it is switched;
   - a leased run records `leased: true` and its saved startup in the phase line, so the effect is read from `qa-phase-times.jsonl`.
3. **Proof.** `tests/qa/g-955-harness.test.ts`: after a reset the bucket and the mailbox are empty, and a store that cannot be cleared fails the reset. Unit tests for lease, release, dead holder, fingerprint mismatch, age and the off switch. `tests/qa/integration/shared-stack.test.ts`: two consecutive runs where the second leases the first's stack, sees none of its rows, objects or mail, and its phase line shows the lease; a run after a crashed holder gets a new stack.

If another store survives the reset (name it and what writes to it), fix it in item 1 the same way; if one cannot be cleared without a restart, stop there and report it.

Smallest change: the two clears in the existing reset, one pool module, and the calls at stack start and stop. No new container, no shared database server across runs, no second reset.
