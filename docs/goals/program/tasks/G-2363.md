## Outcome

The record of `anime/collection-tracking-and-progress` lacks requests the production page sends, so the web Goal's surface cannot be drawn from it. The page's requests are those of `apps/web/features/tracking/api.ts`, `apps/web/features/tracking/episode-api.ts`, `writeStatus` and the reader-state read in `apps/web/features/catalogue/reader-store.ts`, and the Library reader in `apps/web/features/library/read.ts`. Read them; they are the authority for every query below. A query matches by its parameters, not their order. The visitor sends no `actingSubject`; a signed-in persona sends its own, encoded as production encodes it.

Known to be missing:

1. Every persona, the episode opening: production sends `GET /v1/reading-positions/{work}?position=start&limit=20` (with `actingSubject` when signed in). The record has it with `limit=1`.
2. Each signed-in persona: `GET /v1/works/{work}/reader-state?actingSubject={self}`, which `writeStatus` reads before the status `PUT` the record already holds. Record it at that point of the proof, before the write.
3. Each signed-in persona: `GET /v1/me/shelves?actingSubject={self}&limit=20`. The record has the shelves read with no `limit`.
4. Whatever else those readers send for this Work's collection controls, its episode progress and the Library visit that a persona's record lacks. Production makes no reader-state read without an acting Person and redirects a visitor before the Library reads: add none of those for the visitor.


Rules of the record:

- Each added request has its own label and is made inside the persona's proof, in the state of the proof where the page would make it. No existing sample's request or answer changes, no assertion changes, no cell changes state.
- Record whatever status the API gives below 500, a refusal included; assert the status and, where there is a body, the fact the person is shown.
- A request the production page does not send for a persona is not added for that persona. The record's existing refusals to callers the page never produces stay as they are: they prove the API, and no page is drawn from them.
- Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's; the handoff names the resources' IDs and the five acting Persons, because the web surface is written against them.
- `scripts/api/answer-records.guard.test.ts` passes. The handoff lists every added sample (persona, label, method, path with query, status) and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. If the recording run fails on a 503 or a timeout alone, run it once more; then hand off `partial` with the request, the answer and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or a helper, another row's record, a sample for a state the row does not reach.
