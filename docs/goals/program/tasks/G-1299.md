## Outcome

Memory on this host runs out because of tests, not coding: QA stacks fill the
Docker VM (24 GiB, shared with the dev stack) and browser runs, Storybook and
type checks fill the host (62 GiB). Today a QA run starts whenever it has a
slot, whatever memory is left. Make starting a run memory-aware:

1. Before a QA run starts its stack, it waits until the Docker VM can hold that
   stack's limits (Fuseki by resource class from `resource-classes.ts`, plus the
   PostgreSQL, RustFS, Toxiproxy and Mailpit caps in `infra/dev/compose.qa.yaml`)
   on top of what its containers use now, and until the host keeps at least
   8 GiB available after the run's host-side need (a browser or Storybook run
   about 4 GiB, others about 1 GiB). Measure VM use from Docker (container
   memory against the VM total), not from estimates of other runs. While it
   waits it prints what it needs and what is free, and it times out with that
   message at the run's deadline. Thresholds are environment-overridable.
2. Program regression batches (`scripts/goal/regress.ts`) yield: before each
   batch, if another heavy run is queued, wait for it, so merge-blocking work
   goes first. Regression keeps its pinned commit and resumes as before.

## Not in scope

No scheduler service, no change to slot counts, the heavy lock's code or the
resource classes themselves.

## Checks

Unit tests with injected memory readings: a run waits while the VM or the host
is short and starts once it has room; the wait message names both numbers; the
deadline ends the wait; a regression batch waits behind a queued heavy run.
Show one real run printing its admission numbers. `task test --
tests/qa/unit/memory-admission.test.ts tests/qa/unit/core.test.ts
scripts/goal/regress.test.ts` and the type check covering `scripts/`.
