## Outcome

The web's surface for `anime/collection-tracking-and-progress` replays this row's record through the production pages: the Library with its watching shelf (`apps/web/features/library/`, `readCustomShelves` in `read.ts`), the Work page reached from the shelf with its series-progress panel (`apps/web/features/work-page/`, `apps/web/features/tracking/series-progress-panel.tsx`), the status control (`writeStatus` in the tracking store, which reads the reader state before it writes) and the episode control (`apps/web/features/tracking/episode-api.ts`, `episode-progress.tsx`, `episodes.ts`). The record on main holds the proof's requests and a first set of production reads, and the surface still finds no answer for the rest. The web manager's reading is in `docs/goals/web/tasks/G-2328.md` under "Decision — task:G-2328:2"; read that section first.

One body is settled here. The proof marks an episode with `position: null`. The production control sends, when it completes an episode, the position `markPosition` gives (`episode:<number>`, or `special:<number>`), and no position when it clears one. The API accepts both (`position` is a nullable string). The proof's samples and assertions stay as they are; the record gains the write as production sends it, with the answer the API gives to that body.

What must be true afterwards, each request taken from the production client and sent with the path, query and body production sends (not from this list; a request production does not send is not recorded, and the handoff says which listed one that was and why):

- The Library page for every persona who has one: the frame and session reads, the shelves read as `readCustomShelves` sends it, the watching shelf's items and whatever the shelf's rows read to show a Work. The visitor's and any refused persona's Library answer is recorded as the page meets it.
- The Work page reached from the shelf: every read the page and its series-progress panel send for a signed-in persona, the Work read the panel needs included.
- A status change through the real control: the reader-state GET that precedes the write, the write with production's body, and the reads the page sends afterwards.
- Marking an episode watched and clearing it through the real control: the progress read, the write with production's body, its answer, and the refresh that follows. Use an episode the proof does not assert on, or run after the proof's assertions, so no existing sample's answer changes; say which you chose.
- This is meant to be the row's last re-recording for the surface. Before recording, read the pages' whole production path once and compare it with the record's labels for each persona; record every read still missing and list those beyond the items above.
- No assertion and no cell changes. Existing samples keep their answers apart from identities; `limit=20`, the bodies, versions and retry keys of the existing samples stay exactly as recorded. Name any existing sample whose answer changed and why.
- The record's reads run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's.
- A 5xx: hand off with the request and the answer, do not vary it. The log names slow requests under `[persona-request]`; quote them if a proof meets its limit, and do not run a third time.

The handoff names old and new identities and every new label with its request and status, in a file under `.temp/` of the worktree as well as in summary.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a normalised or adapted body.

## Decision

2026-10-14 01:54 UTC, program. The first recording run ended at the 480 s wall with four personas passed: each signed-in persona took about 105 s, because some seventy requests of one visit were sent one after another on a busy host. The wall stays; the visit gets shorter.

- The reads one render sends together start together (`Promise.all`), as the production page sends them. Writes, and a read that needs an earlier answer, keep their order.
- A label names what the request is and is fixed where the request is written (for example a name carried in an `AsyncLocalStorage` the recording fetcher reads). No label comes from a shared counter or from arrival order: the web chooses a sample by its label and expects exactly one. The order of samples in the file is free.
- One console line per persona gives the elapsed time of the proof and of the visit.
- One more stack run is authorized. A 503 the persona transport retries and that then answers is not a reason to stop (Main's nested pool checkout at `progress/completion.ts` is reported to api); a 5xx that is the final answer is.
