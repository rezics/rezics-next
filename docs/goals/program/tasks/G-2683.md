## Outcome

The package upgrade (G-2642) landed `markdown-it` 15 in `yarn.lock`, with code that uses its new public `ParserBlock`. The main checkout's `node_modules` still held 14.3.2, so goalctl's `close` failed with "undefined is not a constructor (evaluating 'new MarkdownIt.ParserBlock()')". G-2248's merge check on its rebased worktree failed for the same reason. Program reinstalled by hand.

Make dependency state follow the lockfile automatically:

- After a landing changes `yarn.lock` or any `package.json`, the main checkout runs `yarn install --immutable`, serialized with other landings, before the next goalctl command depends on it.
- Before any check, gate or test runs in a worktree, a lockfile that differs from what that worktree last installed triggers `yarn install --immutable` there first. This covers a rebase onto main, a resume, a merge candidate, or a confirmation checkout.
- The last installed lockfile digest is recorded per checkout, so an unchanged lockfile costs nothing.

Prove it with tests that simulate a lockfile change landing, a stale worktree being rebased, and an unchanged lockfile that triggers no install.
