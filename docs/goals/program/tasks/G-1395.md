## Outcome

`legacyHostJenaGateFiles` in `scripts/qa/acceptance.ts` lists five Main integration
tests: activate, edit, full-work, outbox and recovery. They start their own Fuseki
from a separately installed host JVM and Jena runtime. The harness excludes them,
"while they are migrated to QA", so none of them runs anywhere.

On 2026-10-07, launch's G-1368 needed `full-work.integration.test.ts` and could
not run it. A host run with Java 25 failed at bootstrap, because a stock Fuseki has
no `/command` service: that is the project's own Fuseki command module, which is
only in the QA image.

Make each of the five run through the QA harness like every other integration
test, against a QA stack's Fuseki (the project image, with `/command`) and the
stack's PostgreSQL. Do not start a JVM on the host. Then remove each one from
`legacyHostJenaGateFiles` and register it in its tier. If a test needs an isolated
project (it replays outboxes from zero, needs a fresh graph, or similar), register
it in `scripts/qa/isolated-integration-files.ts` with the reason. Keep every
assertion. If a test truly asserts something only a host runtime can show, say so
in the handoff and leave that one listed.

`full-work.integration.test.ts` is still claimed by launch's G-1368. Migrate the
other four first; program adds full-work to your claim once G-1368 lands.

## Checks

Run each migrated file once with `task goal -- test <file>`, and report the QA run
IDs. Also check that `task goal -- test --affected --list` now selects them for a
change in their area.
