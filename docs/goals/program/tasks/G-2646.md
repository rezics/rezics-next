## Outcome

Step 5 of the maintainer's API elegance report (`.temp/ref/report.md`). The audit (G-2640, `.temp/ref/audit.md`) and the spike (G-2641, `.temp/ref/spike.md`) concluded that native Elysia is enough for:

- explicit per-status TypeBox schemas, with literal codes kept through `.model()` references;
- a contract module exporting `{method, path, options} as const`, bound natively to a separate handler module that the compiler checks;
- `problem(...)` for expected failures;
- authentication, exposure and rate limits as macros that enforce at runtime and document.

An error class alone cannot be a runtime schema, so a domain error declares its code, status and Problem schema together. The `@elysia/openapi` overlay stays, because beta.6 still overwrites authored responses.

Convert exactly these three operations, chosen by the spike:

1. **Public read:** `GET /v1/works/{id}` (`routes/work-reads.ts`). Keep the public-read session, hidden-equals-missing behaviour and the response headers. Replace the raw success wrapping with checked values.
2. **Authenticated command:** `PUT /v1/me/acting-context-preferences/work.create` (`routes/acting-contexts.ts`). Its auth macro delegates to the existing verifier. Keep the body idempotency key, the revision conflict, the nullable choice, replay and unavailable-service handling.
3. **Several typed failures:** `POST /v1/works/{id}/scalar-value` (`routes/works.ts`). Keep its codes and statuses, the literal 409 alternatives, the 200 versus 202 distinction, Idempotency-Key validation, replay, the expected-head conflict, access checks and omission semantics.

Organise each as a contract declaration (method, path, schemas, per-status success and Problem variants with literal codes, policy metadata), a handler implementing it against inferred types, and a native binding. Domain errors move to their domain owner with one authoritative code, status and schema, and the central problem file keeps only the shared opaque fallback and logging for these operations. Do not build a routing layer over Elysia, and do not change operation IDs, codes, media types, headers, extensions or policy semantics.

Measure before and after for these three, with the audit's and spike's scripts and `scripts/api/` tools:

- lines and declarations per operation;
- the files you must change to add one domain error (repeat the audit's scratch experiment);
- the Eden types: discriminable error union with literal codes;
- the generated OpenAPI diff, which may only add precision;
- `tsc` time and instantiation counts;
- the runtime regression tests of the three routes.

Write the comparison and a recommendation on whether to expand to more routes, and how, into `docs/architecture/api-contracts.md` as a decision note: what is decided and why, not what code already enforces.
