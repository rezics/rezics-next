## Outcome

`scripts/goal/goalctl.test.ts` and `tests/qa/unit/qa-harness.test.ts` pass on `main`, on a host that runs seventy other processes. The staged `.temp/ref/tool-tests-red-1906.log` is one run of both files on 2026-10-13 at 19:06 UTC: 348 passed, 25 failed. Every red test here is charged to each tool task whose change reaches these files, and a test that is red for no fault teaches workers to read past red.

Three kinds are in that log; class every failure before changing anything, and give the table in the handoff (test, kind, what you did).

1. **The test is behind the tool.** The status line of a waiting run gained `; since <time>`; a heavy waiter's timeout message changed ("before the deadline"); `new` requires `--kind`; a brief's refused efforts changed. Among them: "rejects efforts the engine does not accept", "the unit gate refuses a checkout too deep for a PostgreSQL socket", "a heavy waiter that times out leaves no ticket", "a heavy waiter names its turn in output and status", "status identifies memory waits and removes records from dead processes", "a slot waiter reports its reason and appears in status until a slot opens", "refresh precedes round-robin Goals and each Goal keeps its arrival order". Correct the expectation to what the tool does now, after reading the commit that changed the tool to see that the change was meant. Three of this kind were corrected on `main` after the log was taken (the waiter-status tests of the harness file, the `new` test); start from `main` as it is.
2. **The tool is wrong.** Where the test states the intended behaviour and the tool has lost it, do not edit the test: name the test, the tool file and the commit in the handoff. The program briefs the repair; this task claims no tool file.
3. **The test measures the host.** Thirteen failures are five-second limits and "Timed out waiting for memory wait" in tests that start real processes ("integration project summary records …", "real CLI integration holds no slot during memory shortage …", "a missing local image starts normally …"). A test that proves an order of events takes its clock, its sleep and its process start as parameters where the code already offers them, and waits for the event, not for a duration; where a real process is the point of the test, its limit only ends a hang (the unit gate lengthens a default limit on its retry, never one written in the test). Do not delete a test and do not weaken what it asserts.

Also in the log and to be classed the same way: the two Goal mail tests ("lost sender response and acknowledgement retries preserve IDs", "a closed registered Goal keeps its durable address").

Run the two files three times in a row at the end and give the three results. A test that still fails once in three is listed with its cause, not hidden behind a retry.

Do not build: a change to any file but these two, a retry wrapper, a skip, a `todo`, a list of flaky tests.
