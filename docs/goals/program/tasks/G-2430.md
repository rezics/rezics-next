## Outcome

A row is proved by what each kind of person gets from the API. A 5xx is never what a person is meant to get: it is a fault. Twice an outcome test accepted one as an expected answer (a 503 among the allowed statuses of a hydration read and of an absence control in the closure search row, corrected on main in `f79772d890`), and the row could have been declared proved over a broken read.

Afterwards a static test refuses an outcome proof that expects a 5xx:

- It reads every file under `tests/qa/integration/outcomes/` and every helper those files import from `tests/qa/` with the TypeScript parser, not with a text search: a number that is a duration, a count, a port or part of an identifier is not a finding.
- A finding is a 5xx status literal (500 to 599) used as an expected answer: an argument of `toBe`, `toEqual`, `toContain` and their kin on a status; a member of an array or set of accepted statuses; an argument in the status position of a row helper such as `denied(persona, status)`; a `case` or comparison that lets a 5xx pass.
- A retry that waits out a 5xx and then requires another answer is not a finding; say in one comment how the test tells the two apart.
- The findings that exist today are written to the baseline file, one entry per file and expression with the row's ID. The test fails when a finding is not in the baseline and when a baseline entry no longer matches, so the list only shrinks. The handoff gives that list grouped by row, so each row's owner can be told.
- The test proves itself on fixtures in its own file: each kind of finding above is detected, and a duration of 500 and a port of 5432 are not.

Do not build: a change to any outcome test or helper, an exemption by comment, a lint rule in another tool.
