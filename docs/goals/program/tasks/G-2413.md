## Outcome

The web's surface for `anime/navigate-a-thousand-episode-inventory-thousand-chapters` replays this row's record through the production Work page and its inventory (`apps/web/features/work-page/`, the inventory reader and its route under `apps/web/features/`). This task starts when the Work contents read accepts an engine-authored composition (its owner test is on main); before that the contents read answered 503 and the row was not proved. The record on main was made with the proof's small pages and lacks what the page sends. The web manager's exact list of five families is staged at `.temp/ref/g2224-record-gaps.md` in this worktree; read it first. Its identities are from the current record and change when you record again.

What must be true afterwards, each request taken from the production client and sent with the path and query production sends (not from this list; a request production does not send is not recorded, and the handoff says which listed one that was and why):

- All six personas: the Work contents read (`GET /v1/works/{work}/contents`, no query for the visitor, `actingSubject` for the others) with the answer the repaired API gives, and the Work header and supporting reads of the page.
- All six: the inventory's first window as production reads it (`position=start`, the language, `limit=100`) and the continuation with that answer's own cursor at the same page size. A cursor from a `limit=2` page is never sent at page size 100.
- All six: the distant-episode search carried through its continuation at page size 100, with the entered `q` kept and the persona's own cursor from the recorded first window. A first answer with no items and visibility pending is recorded as answered (it is not a 202), followed by the window production reaches next.
- The private inventory and the cursor refusal as production's route reaches them at page size 100, for each persona those probes apply to. Read the Work, persona, cursor and query from the row's existing private and refusal samples and from the production reader; say which probes production reaches and which it cannot.
- This is meant to be the row's last re-recording for the surface. Before recording, read the page's whole production path once and compare it with the record's labels for each persona; record every read still missing and list those beyond the items above.
- No assertion and no cell changes. Existing samples keep their answers apart from identities, except where the contents repair changed an answer; name each such sample. If recording refreshes identities, every sample changes together.
- The record's reads run under their own deadline (120 s) after the proof, and the persona tests get the limit both need; the proof keeps its own deadline. One comment says which part is the proof's.
- A 5xx: hand off with the request and the answer, do not vary it. The log names slow requests under `[persona-request]`; quote them if a proof meets its limit, and do not run a third time.

The handoff names old and new identities and every new label with its request and status, in a file under `.temp/` of the worktree as well as in summary.

Do not build: a change under `apps/web/` or `tests/qa/support/`, a new row, a request with another persona's bearer, a transplanted or invented cursor.
