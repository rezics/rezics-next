## Outcome

The record of `recipes/catalogue-browse-and-search-in-its-zone` holds the proofs' reads with small `limit` values and one language; the production browse page sends neither a `limit` nor a language taken from a record, so the web Goal's surface finds no answer. This brief waits for the api Goal's repair of the Recipes catalogue's exact counts (its contract test), because that repair changes the answers recorded here.

1. Read `RealmBrowseRoute` and the query builders it uses under `apps/web` (read only; change nothing there) and record, for each of the six personas with that persona's client and acting subject as production sends them, the page's own reads spelled exactly as the builders spell them, with no `limit` and no language that production does not send: the first page, a title search that matches, a search that matches nothing, and the continuation of the first page with the cursor its answer gave. Use `tests/qa/support/frame-reads.ts` for the frame's reads of the route, the session and language reads and the conditional reads included.
2. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's.
3. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the samples added per persona (label, method, path, status), any read of the page that could not be recorded with the reason, and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. If the recording run fails on a 503 or a timeout alone, run it once more when the host's one-minute load is below 64 (`cat /proc/loadavg`); then hand off `partial` with the request, the answer, the load and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or the helper, another row's record.
