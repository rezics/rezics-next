## Outcome

A recommendation the maintainer can decide on. Should our Goal orchestration
adopt, borrow from, or ignore existing multi-agent tools, and what is the
smallest first step? Write the report to `.temp/goal/report.md` in your
worktree; commit nothing. This is research: read, clone and try, but change
no repository code.

### What hurts today (2026-10-07)

Four managers run in separate CLI sessions (two on Claude Code, two on Codex
CLI), each in its own tmux session. They dispatch workers through
`scripts/goal/goalctl.ts` across Claude, Sonnet, Codex Sol (two accounts),
Luna, Grok CLI and Cursor Agent. Every session keeps its own wake-ups and
messaging alive:

1. **Messaging.** Claude sessions can message each other; Codex sessions
   cannot receive messages. So Codex managers write files
   (`.temp/goal-orchestration/messages/<goal>.md`), and Claude managers must
   watch theirs. Claude Code reaped one manager's watcher, and only that
   session's user may restart it, so the program manager now relays nudges,
   which costs its turns. Loan requests sat unread for over an hour.
2. **Lifecycle and wake-ups.** Each manager runs its own background waits,
   inbox batchers and host watchers (`scripts/goal/next-event.sh`,
   `goalctl wait`). Sessions compact or restart, Codex has no background
   notifications, and nothing outside the sessions guarantees anyone wakes.
3. **Shared resources.** `goalctl` uses file locks: ledger, three QA slots,
   a heavy lock with a fair queue, and memory admission. Today's defects
   included an inverted lock order (heavy held idle while waiting for a
   slot) and refresh coordination done by chat ("hold merges until my
   checkpoint").
4. **Shared dev stack lifecycle.** Refreshes, AppHost restarts and their
   holds were coordinated by messages between managers.

### Tools to evaluate

In depth: <https://github.com/osteele/agent-loom> and
<https://github.com/gastownhall/gastown>. Clone them under your worktree's
`.temp`, read the code and docs, and run them there if that's cheap; stop
anything you start.

Then find three to five others that address the same problems (for example
agent mail or bus servers over MCP, tmux or worktree orchestrators, issue
trackers built for agents). Use web search.

For each tool, report:
- what it is and how mature it is (activity, license, tests);
- which of our engines it can drive, headless;
- its messaging and wake-up model;
- persistence and crash recovery;
- how it handles locks or shared resources;
- what it needs from us.

Map each to problems 1–4 as **adopt**, **borrow the design**, or **not
useful**, with the reason.

### Constraints for any proposal

- One local Linux host (62 GiB RAM, Docker). Zero budget. No repository data
  sent to third-party services.
- Must drive every engine above headlessly. Must keep `goalctl`'s claims,
  merge gate, Sol review and QA memory admission, or replace them with
  something strictly better.
- A long-running process is acceptable only if it is supervised (for
  example a systemd user unit) and fails safe.
- Incremental: the first slice should fit in a day and fix problem 1 or 2.

### Deliverable

`.temp/goal/report.md` with:
- a one-paragraph answer;
- the comparison table;
- the recommended architecture, naming who owns messaging, wake-ups, locks
  and lifecycle;
- the first slice as a brief-sized task, plus later slices;
- risks and an effort estimate.

Put the paragraph and the first slice in your handoff.
