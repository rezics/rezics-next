## Outcome

`goalctl merge` refuses a task whose new SQL migrations are numbered below the
highest migration already on `main` in the same directory
(`migrationsBelowMain`), because Access and relay migrations apply in
file-name order. With four Goals merging in a different order than they
reserved numbers, managers renumbered by hand three times on 2026-10-07, and
one hand renumber (1260→1310→1399) turned a test red. Any reservation scheme
has this problem; numbers have to be assigned when the merge happens.

During `merge`, after the rebase and before the fast-forward: for each
directory where the task's added migrations sit below `main`'s highest, rename
them, in their original relative order, to the next free numbers above it,
and replace the old file name and the old number, as a whole token in a
migration context (the file name, `migration <n>`, a version constant), in
the task's own changed files. Commit that as a goalctl normalization commit,
like the composition-root one, and print the renaming. Refuse instead, as
today, when the old number also appears in a file the task did not change
(another owner refers to it) or when a renamed migration's contents name its
own number in a way the rewrite cannot prove safe; the manager then renumbers
by hand. The unit gate runs on the renumbered branch.

Update `docs/goals/worker.md` (workers no longer need to guess numbers above a
moving head; reserved ranges become a hint) and the merge row in
`docs/goals/README.md`.

## Read

`scripts/goal/goalctl.ts` (`migrationsBelowMain`, `mergeTask`, the
composition-root normalization commit, `preMergeUnitGate`); a migration
directory listing such as `services/main/migrations/access/` and how a
migration's number is referenced in tests (`git grep -n "1399"` for the recent
case).

## Do not

Renumber migrations already on `main`, touch other tasks' files, change
migration contents beyond the number token, or relax the ordering rule.

## Checks

Unit tests with temporary repos: a task migration below main's head is
renumbered with its references and merges; two task migrations keep their
order; an old number referenced outside the task's files refuses the merge
with the reason; a task already above the head is untouched.
`task test -- scripts/goal/goalctl.test.ts` and the type check covering
`scripts/goal`.
