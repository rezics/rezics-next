## Outcome

A worker's `check`, the pre-merge unit gate and the surface gate run a repository guard only when the change touches what that guard reads. Today every gate runs all of them (`mergeUnitFiles`, `scripts/goal/unit-gate.ts:472`, adds the whole `repositoryGuards` registry of `scripts/qa/repository-guards.ts:59`), because an inventory guard reads files beyond its import graph and the affected plan cannot see that.

What it costs, measured on the first surface's landing on 2026-10-13 (`.temp/goal-orchestration/merges/surface-gate/run-TNvisH/`): the gate took 265 s, of which the guards 185 s: 36 files, unit tier 55.8 s and owner tier 128.5 s (`services/main/tests/api-contract.test.ts`, `g-543-rate-limit`, `g-829-public-reads` and five more of the service) for a change of six files under `apps/web/`. Twenty-six more surfaces follow, each with a worker's `check` and a landing; every api task pays the three web scans (`scripts/static/web-*.test.ts`, 17 to 22 s each beside twenty workers).

1. **A guard declares its inventory.** Each registry entry gains `reads`: the repository paths or globs whose content can change the guard's verdict, taken from what the guard's code opens or scans (read each guard; do not guess from its name). An entry without `reads` runs at every gate, as today; that is the default for a guard whose inventory is the whole tree.
2. **The gates select by it.** Given the changed files of the task against `main`, a guard runs when a changed file matches its `reads`, when the guard's own file or the registry changed, or when it has no `reads`. One function decides, used by `check`, the pre-merge unit gate and the surface gate; each prints one line: how many guards ran of how many, and for which changed paths.
3. **The registry cannot rot silently.** A test fails when an entry's `reads` matches no tracked file. For the guards built on a file scan (a glob in their source), a test compares the declared `reads` with the scan's own pattern, where the guard exports it or can export it cheaply; say in the handoff which guards are checked this way and which rest on the reading alone.
4. Nothing else changes: the main-wide run and `regress` still run every guard; a task that changes no file runs none.
5. Tests: a change under `apps/web/` runs the web guards and not the service's; a change under `services/main/src/` runs the service's and not the web scans; a change to the registry runs all; an entry without `reads` always runs.
6. Show it on the real tree in the handoff: for the six files of the first surface (`git show --stat 88a5010d4` names them) and for one api change of today, the guards selected and the seconds of the guard part before and after.

Do not build: a tracer that records the files a guard opens at run time, a cache of guard results, a change to what any guard asserts, a change to the affected plan.
