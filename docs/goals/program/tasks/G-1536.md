## Outcome

Read `.temp/ref/G-1522.md`, finding 6, including its limits.

1. **Startup.** The three fault tests that wrap recovery startup and reset
   themselves call the admission-aware startup in `scripts/qa/stack-startup.ts`.
   That file is held by another task: consume it as it is, and if it needs a
   change, report the change instead of making it.
2. **Migration.** The Access migration loops in the fault tests and
   `search-ops-support.ts` use the QA bootstrap's migration step
   (`scripts/qa/bootstrap.ts`), which knows about concurrent indexes. A test
   that runs a subset of migrations still passes its subset.
3. **Preparation** (the `cli.ts` half waits for its holder): `api-fuzz.ts`
   reads the stack env and dispatches bootstrap through the path `cli.ts` already
   uses, without editing `cli.ts`.
4. **Readiness.** One deadline-bounded poll (`scripts/qa/readiness.ts`)
   replaces the loops in `api-fuzz.ts`, `e2e.ts` and
   `scripts/dev/seed/readiness.ts`. It stops at the deadline and always releases
   the response body. Each caller keeps its own probe; HTTP success is not graph
   or index readiness.

Do not build a lifecycle framework or callbacks. Keep fault points, admission
evidence and distinct Compose projects.

Acceptance:
- An interrupted startup is reaped.
- The subset migration tests still select their subset.
- The readiness poll stops at its deadline with no open body (unit test).

5. **Finish the class** (second pass, now that `cli.ts` is free): `cli.ts`
   stages bootstrap through `stageQaBootstrap` at its three sites;
   `source-field-child.test.ts` resets through the admission child; the Access
   loops in `content-rebuild-positive`, `search-raw-import` and
   `rights-restriction-replay` use `applyQaSqlMigrations`. Keep the combined
   load-preparation deadline in `cli.ts` bounded.
