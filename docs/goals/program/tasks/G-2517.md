## Outcome

wave/1 changes about 140 test files, among them outcome tests under `tests/qa/integration/outcomes/`, integration and native tests, `scripts/qa/cases/outcomes/` and the gate registries in `scripts/qa/`. A green prove run means something only if the tests still assert what the rows promise. Review `git diff main...wave/1` for test files and test support:

- any assertion weakened, removed or made conditional;
- a cell or expected status changed;
- an answer or record written by hand instead of reached through the API;
- a timeout or budget raised without a cause;
- a skipped or focused test;
- a registry entry dropped or duplicated;
- a test that cannot fail.

Compare each changed outcome test with its row in `scripts/qa/cases/outcomes/` and the brief of the task that changed it (the commit message names the task). Restore a weakened assertion and push it, unless the task's brief records the decision to change it. Then it is a finding to report, not a defect.

## Wave

Build task of wave/1: follow docs/goals/wave.md and start no stack. The prove phase's confirmation and regression runs show what fails. This review finds what a passing run would not show. Other wave workers push to the same branch: rebase before each push.

## Checks

`task goal -- check --only types,lint,guards` on your own commits. Rebase onto wave/1, run types again, push to wave/1. Hand off `RESULT: done` with:

- each finding, with its file, line and the commit that introduced it, marked fixed (with your commit) or left (with the reason);
- the test files the prove phase must run for your fixes.
