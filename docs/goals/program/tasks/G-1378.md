## Outcome

The repository's online-index convention is a migration that holds exactly one
`CREATE INDEX CONCURRENTLY` and the marker `-- migrate: concurrent-index <schema.name>`.
`services/content/src/migrate.ts` already applies such a migration outside a
transaction and repairs an invalid leftover index before retrying. Migrations 871 and
1701 rely on this.

On 2026-10-07 kernel's refresh failed at rehearsal with "CREATE INDEX CONCURRENTLY
cannot run inside a transaction block". `rehearseRefreshMigrations` in
`scripts/dev/refresh-stack.ts` runs all pending migrations in one rolled-back
transaction. Kernel then dropped `CONCURRENTLY` from 1703 just to pass rehearsal,
and launch's pending G-1365 (1491/1492 on `structure.progress`) waits on the same
problem. A plain `CREATE INDEX` blocks writes on a large table for the whole
build, which breaks the scale rule. So migrations must keep the marker form, and
the tooling must handle it.

1. **Rehearsal.** Rehearse a marker migration inside the rolled-back transaction
   with `CONCURRENTLY` removed. That still validates the table, columns and
   predicate, but locks nothing that matters, since the transaction rolls back.
   Keep rehearsing every other migration exactly as today.
2. **Every runner.** Check that each owner's apply path used by
   `task dev:refresh` and the QA harness (access, relay, account, content)
   honours the marker the way `migrate.ts` does. Route a missing one through
   the same shared helper, with minimal changes to unclaimed files.
   `scripts/ops/migrate.ts` is in trust-ops' area; trust-ops has been told and
   agrees to the minimal change. If a runner sits in another Goal's area and
   needs more than routing, list it under PROPOSED TASKS instead.
3. Do not edit migrations that have already been applied (1703 stays as it is).

## Checks

- Unit tests: rehearsal accepts a marker migration and still rejects a broken
  one (wrong column).
- A real check against a QA PostgreSQL through `task goal -- test`: rehearse,
  then apply, a marker migration on a populated table, and show the index is valid.
- An interrupted build leaves an INVALID index that the next apply repairs.
