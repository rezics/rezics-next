## Outcome

On 2026-10-07 a trust-ops heavy run took the heavy lock at 12:26 and then
waited about 15 minutes for one of the three ordinary QA slots
(`withSlot` in `goalctl.ts` takes heavy first, then a slot). The heavy lock
sat idle, and every browser run and shared-stack refresh queued behind it.
The opposite order would hold a slot idle instead.

1. **Heavy runs take no ordinary slot.** The heavy lock already makes them
   exclusive, and memory admission (`scripts/qa/host-admission.ts`) now
   bounds what any stack may start. So a heavy run takes the heavy lock
   only. If you find a real reason a heavy run must also hold a slot, take
   both without holding either idle: wait for both to be free, then take
   them together. Explain the choice.
2. **Honest status.** While a run waits, `task goal -- status` and the run's
   own output say what it waits for (heavy turn, slot, or memory), and the
   heavy holder line shows whether its command has actually started.
3. **Regression share.** `task goal -- regress` uses at most two of the
   three ordinary slots at once, so Goals' own test runs always have one.

4. **Repeated diff lines.** G-1356's gate compares failure signatures as
   sets, so repeated diff lines collapse. In a review probe, `main` failed
   `alice.permission` and the branch failed both `alice` and `bob`; both
   diffs reduced to the same `"permission": false,` signature, and the new
   failure passed as inherited. Compare signatures as counts (multisets),
   so a signature the branch has more often than `main` blocks. Keep
   structural context where Bun's diff provides it.

Update the QA paragraph in `docs/goals/README.md`.

## Checks

Unit tests with stub locks:

- A heavy run proceeds while all ordinary slots are busy.
- A waiting run reports what it waits for.
- The regression never holds a third slot.
- The alice/bob diff case blocks; identical repeated diffs stay inherited.

Run them with `task goal -- test <files>`.
