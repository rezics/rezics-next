## Outcome

`telemetryLog` in `packages/observability/src/log.ts` writes one JSON line per
event, and every log, including `worker_fault`, goes through it. The line has no
time, and `trace_id` appears only when an OTel span is active. When Launch's
journey got a composition 503, the matching `main.database.nested-checkout`
faults could not be tied to that request.

1. Every console line carries `time` (ISO 8601, UTC). Add it in
   `telemetryLog`, not per event.
2. A line logged while an HTTP request is being handled carries that request's
   `trace_id`, on the shared dev stack and on QA stacks, whether or not an
   exporter is configured. Find out why no span is active there today (the
   Elysia plugin in `elysia.ts`, or how `runtime.ts` registers the context
   manager), and fix it in the one place that sets up the request context. Do
   not add a second request-ID scheme beside the trace ID.
3. Keep the personal-data rules unchanged: the sentinel check still runs on the
   composed line, and `time` and `trace_id` are the only new fields.

## Mechanisms

none

## Checks

`packages/observability/src/log.test.ts` covers both of these:
- a line has `time`;
- a line logged inside a request handled through the Elysia plugin has that request's `trace_id`, with no exporter configured.

Also run the observability typecheck task, `task main:typecheck`, and
`oxlint --type-aware` on the changed files. Then make one request to a QA or
worktree Main that logs a `worker_fault`, and show the line.
