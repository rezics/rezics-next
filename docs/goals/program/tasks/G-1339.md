## Outcome

G-1299 merged memory-aware QA admission with two review findings left open
(the reviewer's text is in `.temp/ref/g1299-open-findings.json` in your
worktree):

1. Some QA tests start stacks inside their own 180-second `spawnSync`
   wrappers (`work-title-control` and `protection-restore` among them), which
   also buffer admission events, so a memory wait over three minutes kills
   startup before the run deadline. Route those callers through the same
   admission-aware, streaming startup the harness uses; find every such
   wrapper, not only these two.
2. Fixture restore budgets exclude the admission wait, but `elapsedMs` still
   includes it, so consumers that check elapsed time (`fixture-phase-d.ts`
   rejects over 600 s, recovery evidence, `G727_LAUNCH_PREPARATION_MS`) reject
   a restore that only waited for memory. Report active duration and admission
   wait separately, and have every budget check use the active duration.

Other files that need the same change are unclaimed: change them minimally and
list them under OWNER CHANGES.

## Checks

Unit tests with injected memory readings: a wrapped test startup survives a
four-minute wait inside its run deadline; a restore that waited five minutes and
worked four is accepted with both numbers reported. Run each changed QA file
once through `task goal -- test <file>`.
