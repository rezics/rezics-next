## Outcome

Every page under a Realm or a Zone renders inside the same frame, and the frame makes the same reads on the server whatever the page. A story that runs the production route on a replaying fetch needs those answers in the row's record. Seven rows have been found without them, one mail at a time. This task writes the reads once, as a helper, and uses it for `manga/catalogue-browse-and-search-in-its-zone`, whose surface waits for them.

Read `RealmBrowseRoute`, `loadRealmView`, `readRealmHeader`, `readFacets` and the address resolver under `apps/web` only to copy each request's exact spelling, parameters, headers and client; change nothing under `apps/`.

1. `tests/qa/support/frame-reads.ts` exports one function that records, for one persona and one route, each request the production frame makes on the server. It takes the recording, the persona, the persona's session, the visitor's session, the Realm, the Zone when the page is under one, the address scope and key the route resolves, and the route's path. It sends:
   - the reads production sends through its anonymous client, with no acting subject: the Realm header, the facets, the address resolution. For a signed-in persona these are recorded through the visitor's session (`recording.session(persona, sessions.visitor)`), as `work-showcase` is in `tests/qa/integration/outcomes/anime/navigate-a-thousand-episode-inventory-thousand-chapters.test.ts`;
   - the reads that carry the persona: the Zone's presentation and routes for the path, and for a signed-in persona joining, follow, platform access, the own-ban read where platform access opens it, session-agent with the session-key header, person-preferences.
   Labels have the form `frame-*`. If a record on `main` already has `frame-*` samples, use its labels and spelling. The function is small and has no knowledge of a vertical.
2. `manga/catalogue-browse-and-search-in-its-zone` calls it for all six personas for the browse route: the address resolution is the site's (`scope=space` with the Zone's key, an answer that carries the Zone capability), the routes read is for `path=browse`. The owner's existing resolve of another key stays as it is.
3. No existing sample's label or request changes, no assertion changes, no cell changes state. Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's.
4. `scripts/api/answer-records.guard.test.ts` passes. The handoff lists the helper's signature, the samples added per persona (label, method, path, status), any frame read that could not be recorded with the reason, and the recording run's seconds.

Known and not yours to repair: a scheduled run on a loaded host read the visitor's and the stranger's filtered traversal of this row as empty (0 items where 7 are expected). If your run sees that, hand off `partial` with the request, the answer, the seconds since the fixture was published, the host's load (`cat /proc/loadavg`) and the log path. An answer of 500 or above inside a proof is handed off, never recorded. A 503 in preparation: run once more, then hand off `partial` the same way.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format or the guard, another row's record, a use of the helper in another row.
