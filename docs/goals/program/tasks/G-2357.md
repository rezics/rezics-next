## Outcome

The record of `games/work-hub-and-edition-choice` lacks reads the production Work hub sends, so the web Goal's surface cannot draw the release list or the edition chooser from it. The page's requests are those of two functions in `apps/web/features/work-page/hub-sections.tsx`, `PrimaryAction` and `Availability` (its branch for a Work that is not a book), and of the readers they call in `apps/web/features/work-page/read.ts`, `apps/web/features/work-page/books-edition-page.read.ts` and `apps/web/features/work-levels/read.ts`. Read those; they are the authority for every query below. A query matches by its parameters, not their order. The visitor sends no `actingSubject`; a signed-in persona sends its own.

Known to be missing:

1. All six personas: `GET /v1/works/{work}/releases?limit=20` (with `actingSubject` when signed in). The record has the list only without `limit`.
2. Stranger, owner, moderator, operator: `GET /v1/works/{work}/realizations?limit=20&actingSubject={person}`. The member has it.
3. Stranger, owner, moderator, operator: `GET /v1/me/progress-summaries/{work}?actingSubject={person}&language=en`, which `PrimaryAction` reads for every signed-in person. The member has it.
4. Whatever else those two functions read for this Work that a persona's record lacks: check `readStart`, `readEditionPreference` and `readParts(id, { limit: 1 })` against the record, persona by persona, and add each missing one exactly as its reader sends it. A read those functions do not make is not recorded.

Rules of the record:

- Each added read has its own label and is made inside the persona's proof. No existing sample's label or request changes, no other assertion changes, no cell changes state.
- Record whatever status the API gives below 500; assert the status and, where there is a body, the fact the person is shown (the release in the list, the empty chooser).
- Never write an answer by hand: run the row's test so that it records, and check in the record it writes. Identities are this run's; the handoff names the Work's ID and the five acting Persons, because the web surface is written against them.
- `scripts/api/answer-records.guard.test.ts` passes. The handoff lists every added sample (persona, label, method, path with query, status) and the recording run's seconds.

An answer of 500 or above inside a proof is handed off, never recorded. If the recording run fails on a 503 or a timeout alone, run it once more; then hand off `partial` with the request, the answer and the log path.

Do not build: a change under `apps/` or `services/`, a change to the recorder, the record's format, the guard or a helper, another row's record, a sample for a state the row does not reach (no 202, no stale-preference 409).
