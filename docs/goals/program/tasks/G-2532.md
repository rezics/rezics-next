## Outcome

`docs/storage/qa-shared-databases.md` found that persistent fixture restores start from the base Compose topology. PostgreSQL, RustFS, toxiproxy and Mailpit ran with `HostConfig.Memory = 0` and only Fuseki had its 7 GiB limit, while admission charged 10.375 GiB as if every cap applied. Make restored stacks run under the same caps admission charges: the QA override's limits, or the resource class's, as for a fresh QA stack. A test asserts that each restored service's container has the limit admission counted.

Then measure one small and one medium restore on this host's native engine. Volume copies use `cp -a`, which reflinks on btrfs, so the medium restore that took 292 s under Docker Desktop should now take seconds. Record admission-to-ready and the copy phase in the note's measurement section. If a fixture backup volume carries the no-copy-on-write attribute (`lsattr` shows `C`), which blocks reflinks, report it.
