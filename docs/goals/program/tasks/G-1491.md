## Outcome

On 2026-10-08 kernel's G-1436 (631 files) and trust-ops' G-1488 (577 files)
were refused with "unit gate inconclusive: the affected run did not finish (289
files)". Neither had a failing case. `planUnitGateShards` always makes
`GOAL_UNIT_GATE_SHARDS` (4) round-robin shards with a fixed 12-minute budget,
whatever the plan size. About 144 files per shard can't finish in that budget
on a host running three Goals' QA. The files a shard never reached then make the
whole gate inconclusive. Evidence: `.temp/trust-ops/g1488-land.log`,
`.temp/kernel/merge-G-1436.log` and `.temp/kernel/merge-G-1436.json`.

Fix the class:

1. **Size shards to fit the budget.** Use measured per-file durations where
   they exist, such as earlier gate evidence files or QA `*-durations.json`.
   Otherwise use a conservative file-count cap. Run the shards through a
   bounded queue, so a wide plan becomes more shards rather than bigger ones.
   Concurrency stays memory-bounded, as it is today.
2. **Continue unfinished files.** When a shard reaches its budget, its
   completed files keep their results, and the files it never reached go back
   into new shards. A file that started and then timed out keeps today's
   isolated-retry rule.
3. **Inconclusive only without progress.** The gate is inconclusive only when
   continuation makes no progress, or when the whole gate passes a total
   ceiling. The message names the unfinished files.

The same applies to main's side of the comparison.

## Checks

Use stub-runner unit tests:
- A 600-file plan whose shards each finish only part of their files ends with
  every file run and no inconclusive result.
- A shard that makes no progress is still inconclusive and names its files.
- Duration-based planning puts known-slow files in their own shards.

Run `task goal -- test scripts/goal/goalctl.test.ts` and
`task goal:typecheck`. Do not run `goalctl gate` or land; program does both.
