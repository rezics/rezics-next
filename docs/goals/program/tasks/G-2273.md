## Outcome

A fixture's preparation does not fail because the host is busy. A compound write the API has not finished answers 202 with `pendingOperation` (`services/main/src/api-contract.ts`: `operationId`, `status: "reconciling"`, `phase`, `result: null`, `retry: {allowed: true, afterMs}`), and the same request with the same idempotency key reads its end. Preparation helpers demand the final status from the first answer instead. On 2026-10-13, with seventy processes on the host, the Recipes pagination recording stopped twice in `fixtureAnswer` (`scripts/qa/cases/outcomes/recipes/read-a-recipe.ts`): "Recipe setup expected HTTP 201, got 202" in phases `realm-adoption` and `contribution-draft`; persona setup stopped the same way on `POST /v1/agents` and was repaired alone in `tests/qa/support/provisioned-agent.ts`.

1. **One helper.** `tests/qa/support/settled-write.ts` wraps a persona's call (`PersonaSession['main']`, the `Call` of `tests/qa/support/personas.ts`): it sends the request with one idempotency key (the caller's, or one it makes), and while the answer is 202 with a valid `pendingOperation` it waits `retry.afterMs` and sends the same method, path, body and key again; it returns the first other answer as a `Response`. Bounded by a number of resends and a deadline, each resend bounded too; an invalid pending body, a changed `operationId` or the bound reached is an error that names the request and the last answer. `assertCommandRace` in `tests/qa/support/command-race.ts` already validates and follows such an answer: share that code, do not copy it, and leave its behaviour for its 34 users unchanged.
2. **Preparation uses it; a proof does not.** Every write the Recipes fixture builders in `read-a-recipe.ts` send before a proof goes through the helper. A proof keeps asserting the first answer it is about. `provisionedAgent` uses the helper for the Agent provision's pending answer if its body fits the same rule; if it does not, say why in the handoff and leave it.
3. Decided in code and tested without a stack: first answer final; pending twice then final with one key and the waits the API asked for; invalid pending body; changed operation; bound reached; a hung resend.
4. The handoff lists every other preparation under `scripts/qa/cases/outcomes/`, `tests/qa/support/` and `tests/qa/integration/outcomes/` that sends a write and demands the final status from the first answer: file, line and request. Change none of them here; the program routes them by their claims.

Do not build: a retry of a refusal or of a 5xx, a change to a proof's assertion, a longer limit anywhere, a change under `services/`.
