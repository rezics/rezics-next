## Outcome

A manager resumes a task once. Today `resume` fails when the host's available memory is below the floor ("Memory floor reached …; let running workers finish", `scripts/goal/launch.ts`), nothing remembers the resume, and the manager must notice and call again in a later turn: on 2026-10-13 at 20:08 UTC a resume of the api Goal was refused at 6.64 GiB and its task sat until another session resumed it. A queued brief already waits and starts by itself; a resume does the same.

1. A `resume` refused for the memory floor, the worker cap or a reached Codex account is kept with its message and its options, the command says that it waits and why, and exits 0. Every other refusal fails as now.
2. The pass that starts queued briefs starts a waiting resume when its refusal is gone, before a queued brief of the same Goal, with the message it was given. A second `resume` of the same task replaces the waiting one. `stop` or `close` of the task removes it.
3. `status` shows a waiting resume beside the task with its reason, and the task counts as waiting, not as handed off.
4. Tested without a host: refused and kept; started when memory allows; replaced; removed on close; a refusal of another kind still fails.

Read how `queue.ts` keeps and starts a brief and reuse it; add no second scheduler and no new file of state outside the ledger.

Do not build: a change to the floor, the cap or the account rule, a change to `launch.ts` beyond exporting what the pass needs, a change to how a brief is queued.
