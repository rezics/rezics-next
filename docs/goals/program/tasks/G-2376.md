## Outcome

The Manga browse record's frame reads describe a site production never shows the Realm browse page on. Read from main on 2026-10-13:

- The record asks `GET /v1/addresses/resolve?scope=space&key=<id>` with the id of the persona fixture's second Space (`tests/qa/support/personas.ts`: `POST /v1/spaces` with `profile: 'space-zone-v1'`, `capabilities: ['zone']`, then `defaultRealm` in its configuration). The answer carries `capabilities: { zone }` only and canonical `/z/<key>`.
- Production (`ZoneSiteRoute` in `apps/web/features/zones/site-route.tsx`, `resolveSite` in `apps/web/features/realm/read.ts`) reaches `RealmBrowseRoute` only when the resolved Space carries both a Realm and a Zone capability and the Zone has no route at `browse`. A Space with a Zone only is a standalone site, where `browse` without a mount is not found; `/r/<realm>` has no browse page.
- The Realm's own Space is created as production's form creates it (`space-realm-v2`, `capabilities: ['realm']`) and has no Zone.

So the web's story for this row cannot be the production page at a production address. The API proof of the row (the Realm's `modules/browse` reads) is right and stays.

What must be true afterwards:

1. `tests/qa/support/frame-reads.ts` offers one setup a browse row calls before it records: as the owner it gives the Realm's own Space a Zone through the API operation that adds one to an existing Space (`POST /v1/zones` with `space`; read `services/main/src/routes/zones.ts` for its body), and returns that Zone and the key production's URL carries for the Space (the canonical key of its address, which is its handle). Nothing in `tests/qa/support/personas.ts` changes, so no other row's answers move. If the API refuses a Zone on a Realm's Space, stop and hand off with the request and the answer: that is a finding for the API's owner, not something to route around.
2. `recordFrameReads` records the address read as production sends it: `scope=space` with the key in the URL, and, when the answer's canonical key differs from the key asked, the read by the canonical key as well. For the Manga row the answer carries both capabilities.
3. The frame's Zone reads (presentation, navigation pages, `routes?path=browse`) go to the Realm's own Zone. `routes?path=browse` answering 404 there is the production path to the Realm browse page and is recorded as such.
4. The Manga browse row is recorded once with these reads, for all six personas. Its existing samples keep their answers apart from identities; the handoff names the old and new Realm, Space and Zone identities and lists every frame label with its request.
5. The handoff says, for the other rows whose tests call `recordFrameReads` when you start, what each needs to follow (one line each); do not change them here.

Do not build: a change of the persona fixture, a change under `apps/web/`, a second Space or a mount named `browse`, any change of the row's assertions or cells.
