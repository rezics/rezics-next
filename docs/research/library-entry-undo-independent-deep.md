# Independent entry-slot undo and replacement safety

Research date: 28 October 2026. Evidence and implementation recommendation, not an adopted schema, API, permission or retention policy. Inspected REZICS commit: `b58e45bb553591a0bc7102855b2f7c7bff7ce1e1`. This investigation did not read the sibling entry-undo report. Reference repositories were read as untrusted text; none was installed, built or run, and no implementation is proposed for copying.

## Recommendation

Keep `library.entry` as the live slot with its existing primary key `(route, account_id, subject_id)`. Atomically move a cleared row's complete, private snapshot into an entry-specific deleted table. Retain **each deletion independently**, including when the slot is filled and cleared several times. Restore inserts into the unchanged live primary key; an occupied slot returns conflict and leaves both rows untouched. Purge deletes only the precisely addressed retained deletion, never a live slot.

Use the already supplied delete idempotency key, together with owner, the observed source incarnation and delete-time revision, as Web's Undo address and guards. A native typed index must resolve that address without searching receipts. This preserves DELETE's HTTP 204 and needs neither a bearer token nor a new random restore identifier. Distinguish the source incarnation UUID from the particular deletion command: restoring and clearing the same incarnation again creates a new deletion address. The proposed names below describe one implementation, not new public Library vocabulary.

One separate compatibility issue needs explicit adoption: today's revision-only live mutation CAS cannot distinguish a replacement whose revision restarted. Expose the existing incarnation as opaque version metadata and bind it on new CAS writes. The entry API/client owners must settle that additive contract and its legacy-request transition; a restore handle alone cannot repair stale DELETE or PUT requests. This report does not silently change those shared routes or their frozen acceptance.

## Primary-source comparison

### Trash separate from the current location: Nextcloud

Nextcloud's [documented trash API][nc-api] addresses a user's trash separately from the live Files location and exposes original location/deletion time. Its [user documentation][nc-user] describes restoring associated versions and choosing a different name when the live name is occupied. That last policy is unsuitable here: an exclusive subject slot cannot be renamed into another slot.

The inspected [`LegacyTrashBackend.php`][nc-backend] delegates restore/removal using a particular trash path/deletion time. [`Trashbin.php`][nc-trash] retains original location and versions, restores mtime, checks target writability, and chooses a non-overwriting restored filename. Its timestamp-suffixed legacy storage also checks an existing trash pathname and can unlink it before moving another item there. Therefore **a timestamp alone is not evidence of collision-free independent retention**. Adopt separation of source location and retained item, preservation of user times, and explicit destination checks; reject timestamp naming, silent replacement of trash, fallback location and automatic renaming.

### Stable object IDs with soft deletion: Discourse

Discourse's [`Trashable` concern][dc-trash] scopes normal reads to `deleted_at IS NULL`, provides explicit with-deleted reads, and recovers by clearing deletion metadata. Its [post controller][dc-controller] calls `guardian.ensure_can_recover_post!` before recovery. [`PostDestroyer`][dc-destroyer] separately restores statistics, events and related state. This supports current native authority and explicit projection repair, rather than treating an unfiltered row read as restore authorization.

A Discourse post has an object identity that survives trash; a later post does not replace it at an account/subject primary key. This is evidence for in-place soft deletion of independently identified objects, not proof that setting `deleted_at` on REZICS's existing slot can retain A while allowing B at the same key. Its default scope also does not protect arbitrary raw SQL; every native live query needs the predicate if retained rows share its table.

### Product-level independent identity and authorization: Google Drive

Drive's [trash guide][drive-trash] distinguishes trash from permanent deletion and describes a 30-day window. [Untrash][drive-restore] addresses a `fileId` and requires the currently authenticated owner's authority, or the documented shared-drive role. This supports an address that is not itself permission. It does not provide evidence about Google's physical storage or a unique filename slot. Drive also permits some other users to access trashed files; REZICS's stricter immediate concealment rule must prevail.

### PostgreSQL: what uniqueness and keysets actually guarantee

PostgreSQL supports uniqueness over only rows satisfying an explicit predicate, such as `deleted_at IS NULL`. Queries need to imply that predicate to use the corresponding partial index. Therefore a multi-incarnation table can enforce one active slot while retaining several inactive rows, but adding `deleted_at` while retaining the existing full slot primary key cannot. A partial unique index is not a replacement primary key for identifying every retained row. [Partial-index documentation][pg-partial]

An empty-slot pre-read is insufficient against a concurrent insert. Use the unique index/primary key at the actual insert. `ON CONFLICT DO NOTHING` can provide an occupied outcome; `DO UPDATE` would overwrite the occupant and is the wrong restore primitive. Under the native serializable executor, serialization failures must retry through its existing deadline/authorization machinery. Unique enforcement considers concurrent tuple visibility and can wait; it is not just a lookup in the command's snapshot. [INSERT][pg-insert], [uniqueness checks][pg-unique]

For ordered source enumeration use non-null typed tuples with a matching B-tree order and strict `>` seek, not OFFSET or “latest history” searches. Row comparisons are lexicographic and nullable fields can make their result unknown. Explicit `MATERIALIZED` prevents a source-page CTE being folded into later filtering. Data-modifying CTEs share a snapshot; dependencies must use `RETURNING`, and trying to modify the same row twice within one statement is unsupported. Separate sequential statements inside one command transaction are simpler for restore. [Row comparison][pg-row], [WITH][pg-with]

A due partial index cannot depend on a moving `now()`: PostgreSQL's [`CheckPredicate`][pg-predicate] rejects mutable predicate functions. Index a stored due timestamp and use time as a query bound, or use a genuinely maintained pending flag with an exact predicate. Do not advertise `WHERE restore_until <= now()` as a working index or infer that a “pending” index excludes legal holds without an authoritative transactional maintenance protocol.

The shared patterns are independently addressed retained data, current authorization, explicit live-disclosure filtering and conflict handling. None supplies a generic permission-free undo token, a universal 30-day policy, or proof of bounded physical IO. Nextcloud's collision/rename behavior and Drive's retained sharing are counterexamples to importing an entire product's trash semantics.

## Exact proposed private identities and fields

Write `S = (route, account_id, subject_id)` for the live **logical slot**. The route is the owner's route, not the subject's. `requested_subject_id` remains its stored alias/provenance field. `I = incarnation_id` is an internal source-life UUID: new fill gets a fresh UUID; normal state changes keep it; undo restores it. Neither `I` nor a redirect changes the public identity S.

Let `K` be the parsed, existing delete `Idempotency-Key`, not its HTTP quoted representation. The private **deletion address** is `D = (route, account_id, K)` in the entry-delete namespace. That namespace is implicit in the entry-specific table; there is no new object-type enum. Each successful new deletion requires a fresh K. An authorized exact replay reuses D. Clearing a restored I again uses a different K and a newer delete revision. No extra random deletion UUID is needed for this address choice. Every destructive or restore use also binds S/I/deleted revision: D alone must not become lifetime authority if the separate receipt owner eventually collects an old receipt and a caller reuses K.

Proposed table `library.entry_deleted`:

Due ordering uses D to disambiguate equal times, never user `updated_at`.

Snapshot values are immutable until successful restore consumption or authorized purge. Do not copy only HTTP fields, derive pins from current type, infer completion time from state or use browser dates. Preserve original creation/update/activity/finish times and exact accepted pin. Restore's audit transaction is new; retain original transaction provenance in the snapshot and minimal restore receipt metadata rather than pretending the undo happened in the old transaction. Session history and existing command receipts remain untouched. This preserves the last accepted entry value; it does not invent an entry state-change history API. User-visible history timestamps need not become the time of undo; use separate command/tombstone times.

No permanent absent-slot subject directory or `MAX(revision)` over historical deletions is needed for this restore algorithm. An old D can only consume its own snapshot. Any broader bulk absent-slot admission fence remains with its existing owning contract; do not claim this archive replaces that protocol.

## Command transitions, liveness and races

All public operations start with the real signed actor and native current account/scopes/resource/gate checks **before looking up any receipt**. The delete scope remains `library_entry:delete`; the proposed restore uses the existing owner-management `library_entry:update` scope, subject to API-owner adoption. This grants no platform early-purge authority. New write attempts also take `shareAccount` in their command transaction before changing native state. Replays must still reject terminal, fenced, suspended, revoked, stale-epoch, foreign and anonymous callers; possession of K or I is no exception.

1. **Delete miss:** after authorization and exact receipt lookup, lock/read the precise live S and compare its expected incarnation/revision when supplied by the adopted CAS contract. Copy its full snapshot to D with r+1 and command-derived deadline; remove only that matched live row. Archive insertion, removal, hide/counter effects, ordinary receipt and outbox commit together. If insertion fails or CAS loses, roll everything back. A deletion is a logical soft delete even though the live-only table loses a row: the retained native payload, time and undo are authoritative.
2. **New fill:** insert B into the original live PK with a fresh incarnation and the normal active-profile validation. It never updates or garbage-collects any D. Concurrent restore/fill is resolved by the live PK; exactly one wins. A failed restore must not consume its archive. No hidden all-history read is part of creation.
3. **Undo miss:** authorize owner management, then look up D directly. Verify supplied stored subject, I and deletion revision, current source-read eligibility, identical pin provenance and kernel `now < restore_until`. Lock D and recheck current terminal/disclosure guards. Attempt to insert its exact accepted values at S with I and a newer revision. If S is occupied, return 409 and retain D. Consume D only after successful insertion; commit new receipt/events/active counters in the same transaction. A fresh undo key retries a resolved conflict while time remains. A legal hold only suspends purge: it neither denies an otherwise valid undo nor extends its deadline, and undo does not cancel the hold owner's custody of the restored source.
4. **Purge:** address D/S/I/deleted revision, recheck authoritative time or terminal account T and current legal hold in the writing transaction, and erase only that retained snapshot. It performs no `DELETE ... WHERE S` against live storage. If restore consumed D, a late task sees absence and is harmless; if I is later cleared again, its new D differs. If purge wins at the deadline, restore sees missing/expired state and conflicts. No second visible counter decrement occurs.

Use the current `subject:read` implementation for newly restored/emitted subjects; an entry pin or owner check is not catalogue-read authority. Check the stored source through native eligibility, following redirects for eligibility without changing S or `requested_subject_id`. A new restore must conceal an inaccessible source and not become a redirect-based migration. Clearing remains independent of active **profile** capability; deletion never accepts a new profiled value. An authorized exact replay returns its stored outcome before reselecting profile/source membership, as the [profile consumer contract](../library-profile-consumers.md#authorization-receipts-and-replay) requires. Current owner/resource authority is still checked first.

Undo restores the old accepted value, not a new current-profile write. A missing current profile does not prevent exact pinned undo. An absent immutable pinned release or corrupt pin is an explicit unavailable/incompatible result, never permission to guess from today's type. For genuinely legacy null pins preserve the existing legacy adapter boundary until the profile migration owner pins both live and retained legacy rows. Do not fabricate accepting-type evidence from shelf observations or revive the retired type dictionary.

Moving a state row out of live storage immediately excludes it from existing entry pages and shelf indexes. Every built-in dynamic Collection, member adapter, Everything/state/Continue page, source count and any search/export/sitemap/feed adapter must use live facts and recheck source liveness. The archive is never an Everything support fact. Other live sessions/labels/copies can still support the subject; this is not a count bug. Private entry facts have no independent public membership projection to decrement. On restore, current shelf/type admission and reconciliation still govern derived buckets: the snapshot's old `type_source_*` observation is not current catalogue truth or historical accepting-type evidence. Preserve the pin and user values while applying that existing projection protocol; never require a new current profile merely to undo. Existing public Collection listing must continue its own source checks/freshness protocol; do not add public entry events or broaden disclosure.

## Undo addressing with DELETE 204

For the recommended handle, Web retains the canonical stored `subjectId`, observed I, successful DELETE's existing K and deletion revision r+1 alongside the Undo action. I comes from the adopted opaque version metadata, not a post-delete GET. Its knowledge of r+1 is a proposed deterministic protocol, not a browser assertion of time or authorization. If the response was lost, retry the exact DELETE with K; it returns the stored 204 after current authorization, without a live pre-read. HTTP success from a different key must not be attached to an old Undo button. A legacy client with no I cannot synthesize this stronger handle; the transport owner must expose it or select the explicit-ID alternative.

A proposed new operation is `POST /v1/libraryEntries/:subjectId/restore` with body `{ deleteKey, incarnationId, deletedRevision }`, plus its **own** fresh `Idempotency-Key`. The owner is the current authenticated account, never a trusted body field. Include literal stored subject, K, I and deleted revision in canonical restore input; compare them with the native row, which supplies payload and deadline. A successful restore can return the normal live entry response; Web refetches normal views. The precise route spelling/status/body remains an API-owner adoption, not an asserted existing endpoint.

K must be bound to the deleting owner, not accepted as a global capability. Do not put retained state, pins or arbitrary subjects into an unauthenticated lookup or URL token. A stolen handle cannot bypass current owner management, authentication epoch, account fence or gate checks. Unknown and unauthorized private identities share concealment behavior. A different current owner cannot adopt an archived fact. Browser storage and countdowns only support presentation; kernel time and the native row decide eligibility.

The current [typed client](../../packages/client/README.md) is generated from route declarations; it does not invent delete keys or infer server tombstone identity. Its DELETE return stays void with this choice. Web must retain its exact supplied key and original slot/incarnation/revision; it cannot reconstruct a handle from a replacement returned by GET. Regenerate declarations for the added restore route and adopted CAS metadata through the existing generator when implementation is authorized, rather than hand-editing generated types.

**Explicit cross-owner CAS decision:** prefer additive opaque incarnation/version metadata on live reads/writes, and an incarnation precondition on new revisioned PUT/DELETE requests. A response header and matching request header can avoid redefining subject as an object ID; a typed field is another transport choice. Bind the precondition into the new command's canonical digest. Entry command/API, generated-client and Web owners must agree the actual transport, error and old-client transition before claiming all live CAS requests reject ABA. Existing exact receipts must retain their original input digest and response. Requiring a new header on old requests would break existing clients/frozen acceptance; merely making it optional leaves their stale-write limitation. Do not secretly change revision allocation, invent permanent absent-slot history or weaken tests to hide this compatibility boundary.

## Bounded native purge and evidence custody

At deletion the archive itself is durable due work. Reuse existing command/outbox and `addEffects`/`registerEffects` to hand off work; use shared `WorkClient` enqueue/schedule registration and existing queues. [`work/retention.ts`](../../services/kernel/src/work/retention.ts) actually provisions a named UTC schedule with `client.applySchedules`; [`content/work.ts`](../../services/kernel/src/content/work.ts) also registers scheduled native collection. Register this adapter through that shared composition, not a Library process timer, token store or scheduler. The existing account-subject delete event can wake its owner's route dispatcher without adding K or private payload to the event. Persist route work admission in the delete transaction so a missing wakeup is recovered by the indexed periodic sweep. No exported general record-due/hold API exists today: lifecycle/work and hold owners must adopt the adapter/registration, not be assumed to have delivered one.

Smallest native route dispatcher: one persistent `entry_purge_progress` row per admitted route. Its fields are `route integer PRIMARY KEY`, `sweep_id uuid`, fixed kernel `cutoff timestamptz`, nullable after tuple `(after_due timestamptz, after_account uuid, after_key text COLLATE "C")`, `sequence bigint`, `segment_no bigint`, `pages_in_segment smallint`, `sweep_complete boolean` and `enqueue_pending boolean`. All except the after tuple are non-null; after fields are all-null or all-present, sequence/segment are nonnegative and pages are 0–100. Keep the exact last native page receipt PK locator (partition, principal kind/id, command kind/key), with outbox epoch/position only if needed for custody. A partial B-tree `(route) WHERE enqueue_pending` supports recovery; enumerate at most 100 progress source keys before other filters. This is the progress table's only index beyond its PK. Derive the bounded continuation identity from route/sweep/sequence, not retained domain JSON.

Advance by CAS on `(route, sweep_id, sequence)`. The progress row's pending continuation is the native enqueue intent; commit it with page effects/receipt, clear it only after idempotent enqueue acknowledgement under the same CAS. A new sweep resets the cursor under a new sweep ID; old continuations cannot advance it. Periodic fixed-cutoff sweeps revisit held rows. Do not retain per-account subject history in this checkpoint or introduce per-record timers. The exact receipt/continuation adapter belongs to shared work/command owners, rather than a second receipt store.

The following is query-shape pseudocode, not a production migration or a claimed measured plan:

```sql
WITH source_keys AS MATERIALIZED (
  SELECT restore_until, account_id, delete_key
  FROM library.entry_deleted
  WHERE route = :route AND restore_until <= :fixed_cutoff
    AND (restore_until, account_id, delete_key COLLATE "C")
        > (:after_due, :after_account, :after_key COLLATE "C")
  ORDER BY restore_until, account_id, delete_key COLLATE "C"
  LIMIT :source_limit -- 1..100, no additional lookahead allowance
)
SELECT * FROM source_keys;
```

Use a separate first-page form without the after predicate; never nullable sentinel comparisons. Materialize **source keys before any held/pending/claimed eligibility filter**, then point-read/lock and evaluate only those keys in the writing transaction. Advance after the last examined key, including held/rejected candidates. Do not put `NOT held`, a receipt join or `SKIP LOCKED` below LIMIT and call only changed rows the source budget. A contested candidate may defer the page within its deadline; skipping arbitrary locked index entries is not a 100-key proof. A proven maintained partial pending index is an alternative, not an assertion that PostgreSQL infers it.

A sweep finishes by indexed exhaustion at its fixed cutoff. Later sweeps revisit held/failed sources and newly due rows; hold release makes an already-due source eligible without extending undo. Each source is still revalidated, so no pending flag is required on immutable snapshots. Each page admits at most 100 raw source keys/effects with an explicit byte budget and finite command deadline; a segment has at most 100 pages and a durable continuation. Run the same raw-key discipline for migration and terminal-account archive scans, using the owner-leading PK for the latter and **no** ordinary deadline filter at T.

Every destructive transaction checks exact D/S/I/deleted revision, ordinary due time or the authoritative terminal account/T, and the current applicable legal hold. Hold scope may cover an incarnation or a broader source/account; only the hold owner's native check decides that coverage. Its lock/version protocol must serialize a newly effective hold with purge, not pass a cached boolean. Current native hold authority is missing; inventing a Library-local permission/hold table is not a substitute. Takedown withholds only the affected field/data, does not create trash or a purge deadline, and a notice never automatically authorizes purge. Early legal-order purge needs the separately explicit platform permission; ordinary delete/update scopes cannot supply it.

Terminal account deletion immediately closes owner reads and every producer at T, including undo. Account-private live entries and retained deletions are purge-eligible from T, subject to holds, rather than after their individual deadlines. Bind that system work to the native terminal account/T; do not impersonate the deleted account with `trustedAccount`, create account restoration/generation or wait synchronously for Library cleanup. Account erasure must inventory the new archive and its work/evidence locators as well as live rows.

The application-level bound is at most 100 selected logical source keys, not at most 100 physical tuples, buffers or total rows across all guard/evidence queries. MVCC can retain dead index/heap versions; a covering index can still need heap visibility visits. `MATERIALIZED` prevents predicate pushdown, not bloat, TOAST bytes or index-path mistakes. [Index-only scan documentation][pg-cover], [vacuum documentation][pg-vacuum] Future validation needs real `EXPLAIN (ANALYZE, BUFFERS)` with loops/removed rows, source keys and guard lookups counted, byte/statement budgets, churn and held-prefix populations at legal geometric scales. Do not claim a physical constant bound from SQL LIMIT alone; neither `ctid` nor `xmin` is a durable incarnation. [System-column documentation][pg-system]

| Library live/archive/checkpoint                                                               | Deletes the whole private retained entry/pin; no personal reading skeleton remains. For new DELETE receipts prefer minimal outcome metadata needed for 204 replay, not the retained state/pin. Preserve compatibility of already committed receipts. Restore returning a normal entry can itself duplicate that value in its receipt; this cost must be included, or its owner can explicitly adopt a minimal response plus ordinary refetch. Exact receipt/outbox/workflow locators and custody acknowledgements belong in native bounded work metadata. Prior historical PUT receipts are not discoverable merely from D: their owner needs an indexed evidence directory or another proven bounded owner mechanism. An unbounded JSON/principal/receipt-history scan is unacceptable, and no such missing cleanup is silently solved by this recommendation.

DBOS's inspected [`sleepms`][dbos-sleep] is durable only in workflow context, not inside a step. It can schedule a locator-only delayed attempt, but its wakeup time is not purge authority. A native due index/checkpoint still provides recovery/reconciliation and hold-release progress. Do not rely on workflow-ID deduplication after terminal history retention or create an unbounded workflow loop; old delivery must always fail closed against current native D and terminal/hold state.

## Migration and bounded capability splits

1. Add the typed archive and its two indexes (PK and route-due), without changing the live PK or rewriting existing receipts. Deploy writers that allocate I for every new fill and preserve existing non-null I on updates. Add archive inventory to the account purge adapter before enabling deletion retention.
2. Backfill legacy null incarnations in explicit source-key pages of at most 100, only after every fill writer allocates I and old writers are drained/fenced. Capture S/r, update only where the observed revision still matches and I remains null, and advance after the last examined key. New replacements are already non-null, so the null predicate also prevents a legacy revision-reset ABA during backfill. A null-only partial index is optional if its plan is proved; otherwise materialize raw PK pages before filtering. Preserve user revisions, values, pins, timestamps, transaction identity and aliases. No default UUID rewrite over the whole table. Complete this backfill before enabling the recommended K/I/revision Web handle: a UUID allocated only during DELETE would be unknown to a client receiving 204. If rollout instead accepts null-I deletes, allocation/archive can be atomic under the row lock, but returning explicit deletion metadata becomes an additional adopted transport cost.
3. Keep genuinely null legacy profile pins unchanged under the existing legacy adapter; coordinate the profile migration's pending coverage for retained rows before profile-aware cutover. This is not current-type reconstruction or a second profile registry. After writers/backfill prove no null live incarnations remain, validate/enforce their non-null invariant. Do not enforce it before compatibility is ready.
4. Adopt the restore request and explicit live CAS metadata compatibility plan with API/client/Web owners. Remove ordinary live pre-reads from the exact delete replay path; authorize first, seek the existing receipt, and resolve fresh domain input only on a miss. Preserve exact old request digests. Enable archive+hide and restore together with durable work custody, then enable due purge through the shared work owner.
5. Use forward migrations; do not edit frozen schema snapshots/tests or synthesize tombstones for rows physically deleted before deployment. Historical receipts cannot reconstruct complete lost pins/shelf columns reliably. Old lost rows are not newly restorable evidence.

The implementation should be delivered as bounded capabilities, each with **at most 400 changed lines and eight paths**, including its relevant verification; split again if generated/schema/test output exceeds that budget. These are review boundaries, not permission to ship an incomplete lifecycle:

| Immediate liveness                   | Owning dynamic-member/Everything/count adapters and source checks; verify no entry-derived presence after clear before workers, other-fact support survives, old cursor/cached positive cannot reintroduce the state, no second decrement at purge.                                                              |
| Durable purge and custody            | Shared lifecycle/work/hold owners plus entry adapter and account-purge inventory; verify native guard/hold races, raw-key bounds including held prefixes, commit-before-enqueue and before-commit crashes, continuation CAS, account eligibility at unchanged T and explicit evidence exceptions.                |

Existing deletion outcome tests are requirements, not an implemented engine or something to weaken. Extend the owning implementation's tests for repeated delete/recreate/reclear, two independent old deletions, stale deletion/revision collision and all snapshot fields. The current report's acceptance is only report existence; no production schema, API, test writer or architecture approval is part of this change.

Remaining costs and explicit ambiguities are one native archive plus bounded route work state, index/write amplification during the move, transient retained private storage, client retention of K/I/revision, the adopted live CAS compatibility boundary, integer exhaustion, legacy pin cutover and missing shared hold/evidence cleanup APIs. UUIDs must use the existing trusted allocator with bounded collision handling, not browser authority. Do not promise complete erasure while shared evidence custody remains unresolved. These are implementable owner decisions/dependencies; they are not evidence that account reports already solved ordinary replacement or that a broad new Library engine is necessary.
