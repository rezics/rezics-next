# Notification preferences: Accounts design status

Observed 2026-10-30 UTC (2026-10-31 Asia/Shanghai), in the assigned integrated development checkout.
This is desk-research evidence and recommendations for adoption, not another normative contract. No acceptance,
native, database, browser or remote verification was performed. Source tracing below does not certify outcomes.

## Boundary and present state

The user job is to choose which optional in-app notices this account receives, see the saved choice on another
device, and retain access to required moderation outcomes without revealing private content or preferences.
The exact [In row](../scope.md) is minimal reply, mention and moderation notices, per-kind preferences and
send-time Access checks; email is excluded. Accounts owns the private preference authority and lifecycle;
Web owns `/settings#notifications` and `/inbox`; Auth authenticates the acting account and owns security pages.
This assignment places actual notification delivery with Commerce, using the existing Content implementation.
The [Commerce Goal](../goals/commerce.md) does not yet record that responsibility; the scope table and
[Content Goal](../goals/content.md) still label Content as notification owner. Root/coowners should reconcile
that ownership wording without moving storage or creating another sender.

Normative behaviour lives in [Accounts §6](../accounts.md#6-auth-ownership-and-registration),
[Access: Viewer preferences](../../services/kernel/src/access/README.md#viewer-preferences),
[Content: Notifications](../../services/kernel/src/content/README.md#notifications) and [Deletion](../deletion.md).
The requested `docs/notifications.md` is absent. Content's notification section still calls delivery pending,
although the current checkout mounts [notice routes](../../services/kernel/src/content/notice-routes.ts) through
[the kernel](../../services/kernel/src/http/kernel.ts), registers notice effects and contains inbox/storage/work.
That wording and the old “specified red” capability status need owner reconciliation; they are not evidence that
the landed interface is absent. This report accepts that delivery implementation without a second audit.

## Actual UI ↔ API ↔ storage journeys

Source abbreviations: **P** = [preference commands](../../services/kernel/src/access/preferences.ts) and
[routes](../../services/kernel/src/access/routes.ts); **W** = [Web preference adapter](../../apps/web/src/settings/preferences.ts),
[server functions](../../apps/web/src/settings/actions.ts) and [page](../../apps/web/src/settings/settings-page.tsx);
**N** = [notice inbox/routes](../../services/kernel/src/content/notice-inbox.ts) and
[inbox BFF](../../apps/web/src/inbox/inbox-read.ts). Paths are application routes; served Web URLs include the
locale, for example `/en/settings#notifications` and `/en/inbox`. `a` below is the authenticated account ID.

Every Web preference request resolves its session through [prepareSession](../../apps/web/src/session/request.ts),
the `SESSIONS` Durable Object's stored `record`, and its current bearer; an expired access token may cause Auth
`POST /token` refresh before kernel access. Tokens stay server-side. Auth supplies identity, not preference storage.
Unsafe BFF requests require allowed origin and session CSRF. Kernel applies native authentication/Access; the
actor must equal the preference path account even if another account has a grant. An operator must open a
session acting as the automated account. T means the server's authoritative authorization time, never browser time.

## Gaps and decisions for adoption

1. **Consumption boundary, not another sender.** The helper, consumers, storage and `/settings#notifications`
   page exist; there is no standalone `/settings/notifications` route. The missing shared statement is exactly
   when an optional send becomes final relative to a saved
   preference change/deletion. The helper read, resource Access and recipient insert occur separately; the helper
   returns only a boolean, not a version/fence witness. A completed effect records suppression, but partial effect
   retry is not a per-recipient decision receipt. Commerce/Content and Accounts should clarify the send point and
   crash/replay obligation in their existing owner contract before choosing any stronger atomic mechanism.
   This source trace neither proves a race outcome nor authorizes cross-partition writes or a new delivery service.
2. **Usability/readback.** Existing switches, explicit reset, no-JS forms and conflict reload cover the principal
   page. Uncertain-save recovery and already-open cross-device freshness remain gaps. The API returns effective
   booleans, not override provenance/default metadata; UI cannot distinguish explicit choice from inheritance.
   Storing only non-defaults means saving true does not pin a value against a future catalogue-default change.
   Keep today's frozen defaults; changing that policy or adding provenance requires coowner adoption.
3. **Mute/unsubscribe and required notices.** Setting reply/mention false is account-wide suppression of future
   notices of that kind. It does not purge old notices, revoke source access or unfollow anything. There is no
   source-, sender-, Realm- or conversation-mute storage/API/page, and no single-notice DELETE route. These are
   absent capabilities outside the minimal contract, not guessed endpoints or existing-In implementation slices.
   Required copy currently mentions decisions about one's content; it should also explain reporter/appeal outcomes.
4. **Privacy and authority.** Private/no-store and self-only checks are appropriate; optional off must never
   suppress mandatory moderation or authorize forbidden content. Required inbox identity/decision access must
   survive suspension as specified. The raw unread count versus visible items and fallback after a retained seen
   notice expires need coowner semantics, not a claim that all inbox items are currently readable. The BFF's
   `readUnreadCount` currently collapses session preparation/native failures into a zero badge; that loses the
   distinction between no unread notices and unavailable data. Auth security delivery must stay separate from
   optional content-notice controls.
5. **Deletion/restore/operations.** The barrier removes live preferences, but successful preference receipts contain
   the full private response and effect/work histories can retain personal identities. Reuse the open preference
   receipt, shared-history, Auth-copy and locator-effect-admission producers recorded in the Accounts continuation;
   their contracts are not all runtime. No local continuation exists in this worktree; the exact main-checkout
   `.temp/goal/accounts/CONTINUATION.md` was read without writing there. Its audit-wave status is a dated handoff,
   not a completion claim. Queue lag, exhausted effects and restore admission need owner-visible operational
   outcomes; [existing lag reporting](../../services/kernel/src/events/README.md#consumer-lag) is reusable.

Recommendation: adopt clearer semantics and close the existing preference/lifecycle journeys using the current
API, Access formula, PostgreSQL rows and DBOS effects. Root should reconcile ownership/status wording; Accounts,
Web and the delivery coowner should adopt the send-point, count and defaults decisions in their existing owner
documents. This report does not adopt new notification types, delivery channels or subscription hierarchies.

## Ordered whole implementation slices for existing In gaps

1. **Confirmed preference editing across sessions and failures — ready for Web/Accounts.** Extend existing
   [settings page](../../apps/web/src/settings/settings-page.tsx), [adapter](../../apps/web/src/settings/preferences.ts)
   and [actions](../../apps/web/src/settings/actions.ts), consuming the real GET/PATCH map, shared version and
   idempotency key. Retain an ambiguous attempt's original input/key, resolve it through ordinary replay and fresh
   GET, and offer current-state reload; clarify optional-versus-required and future-versus-existing-notice copy in
   `apps/web/messages/`. Later acceptance: two sessions change different preference sections without lost updates;
   response loss after commit recovers the actual saved state; refusal never says Saved; reset and no-JS/CSRF paths
   still work. Extend the existing notification/settings suites rather than dispatch another preference backend.
2. **Private preference receipt erasure and replay — reuse the current Accounts producer.** Owning sources are
   [P](../../services/kernel/src/access/preferences.ts), [command execution](../../services/kernel/src/command/command.ts),
   [history locator/contracts](../../services/kernel/src/history/locator.ts) and
   [erasure coordinator](../../services/kernel/src/access/erasure.ts). Inputs are the actual preference receipt,
   current authorized principal and deletion obligation; this depends on the existing command-key/token producer,
   then feeds the existing shared-history producer. Their unlanded changes are not callable APIs today. Later
   acceptance: deletion removes live and historical preference values in every registered copy; authorized matching
   retries return only the adopted erased result, revoked retries disclose nothing, and restored/late copies cannot
   recreate preferences or produce a false completion acknowledgement.
3. **Close the existing preference-to-delivery outcome — coowner adoption first, then continue existing delivery
   and shared-history producers.** Use `notificationAllowed`, `content/reply-notices.ts`, `mention-notices.ts`,
   `notice-inbox.ts`, `events/effects.ts` and `content/erasure-workflow.ts`; input is the real committed source event,
   recipient account and current Access, not an invented Accounts sender. Depend on the existing locator-effect
   admission producer's landed code before consuming its proposed hook; today's `Effect` exposes `run` only.
   Later acceptance at the adopted send boundary: opt-out/revocation/deletion before send yields no notice; crash
   retry/replay never resurrects a suppressed send or duplicates delivery; mandatory outcomes remain available;
   post-send revocation hides target content; retention and erasure complete only with durable consumer custody.
   Bind/extend existing Content notification and Web native journeys and reuse owner delivery evidence; do not open
   another delivery implementation or repeat its native campaign during this research.

Content's native watch catalogue now includes independent default-on optional `thread_watch` and `board_activity`
preferences. The latter controls later first-published board openings only, without email or historical backfill;
changing a preference neither removes subscriptions nor reverses a finalized send/refusal. The exact mounted methods,
selection/cursor semantics and unavailable-row removal contract are in [Content](../../services/kernel/src/content/README.md#native-board-watches-and-private-management).
