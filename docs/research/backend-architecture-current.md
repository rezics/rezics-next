# Current backend architecture audit

Research date: 2026-10-31. Inspected worktree and `dev` revision:
`6d3f767467c85dbb9d3bb561d12af784407bd92c`.
This report is evidence for the owning documents, not an adopted design or delivery certificate.

The backend has a substantial shared engine: semantic statements, released definitions, Access,
single-partition commands, events, durable work and reusable presentation/filter contracts.
It is not simply eight unrelated vertical backends. However, the current implementation does not
meet the upper-bound architecture: Collections stop at 5,000 members, releases stop at 1,024 types,
summary reads do not share the required database snapshot, and Rating contains both fixed semantic
grains and a cross-partition aggregate join. Several carefully implemented consumer protocols still
lack their default native producer. More protocol scaffolding will not repair those missing seams.

## Genericity, hardcoding and actual contradictions

### Vocabulary is substantially better than the earlier fixed reader model

`packages/definitions/src/library-profile.ts` defines arbitrary state IDs, copy kinds/statuses,
unit descriptors, dimensions, decimal bounds and total policy. `kernel/library/profile.ts` resolves
the accepting type's explicit profile reference; it does not infer a vertical from its label or
invent a profile from current ancestry. `profile-source.ts` reads source identity/current Access
and pins the immutable release digest, accepting type and profile. Entry/copy model values are
strings, not backend enums for books or animation. Historical facts retain their accepting pin.

There are still fixed legacy sets in `entry-store.ts` and `progress.ts`: planned/in_progress/etc.,
and page/chapter/episode/volume/minute/percent. Their existence is not proof that every new command
uses them. The parsers accept descriptors; `numeric` applies profile decimal rules when supplied,
and the legacy unit restriction applies when the descriptor is absent. `nativeProgressUnit`
supports manual structures `none` and `session_local`; scalar amount, cursor position and completed
unit sets are finite engine algorithms, not a list of vertical meanings. Preserve this distinction.

There is a deliberate remaining value-dependent side effect: `entries.ts:371` creates a Library
follow only for the literal `in_progress`. The test `profile-entry-command.test.ts`, “game recipe
and record states use one HTTP entry slot and descriptive active roles do not create follows”,
explicitly protects that behaviour; another test protects the literal's follow and explicit unfollow.
Meanwhile `continue-source.ts:evaluateContinueSupports` uses the descriptor role `active`.
This is **documented compatibility coupling**, not evidence that Continue is fixed to book states.
Do not change it to “every active role auto-follows”: roles are descriptive and that would add
unrequested writes. If auto-follow is retained as extensible product behaviour, give it an explicit
shared policy separate from a state ID; otherwise keep the compatibility lane narrow and retire it
only through an adopted migration. Cause: old product effects survived vocabulary generalization.
Impact: new vertical states do not inherit that particular effect; owner seam: Library/Accounts.

Structured progress remains a different, absent capability: a session-local ID set does not know a
work's canonical episode graph, changing editions or completion denominator. `MAX_COMPLETED_UNITS`
is 20,000, per-record unit-ID count 100, locator length 256 and decimal precision 12 integer plus
6 fractional digits. These are explicit supported limits, not an automatically complete episode
engine. Keep structured progress closed until the owner defines versioned structure/identity and
reconciliation; do not turn a generic unit label into authority to traverse all relations.

a giant dropdown. The recommendation is bounded retrieval for either representation.

The first five findings are demonstrable source/architecture mismatches. Native integration and

latency or claim of an exploitable disclosure. In particular, independent current Access checks
may conceal a subject even when summary fields were assembled from inconsistent snapshots.

### Two patches have real gaps, but remain maintenance liabilities

The pinned DBOS source's `src/system_database.ts:deleteWorkflows` deletes payload/status rows in a
transaction. Deletion alone does not install a permanent per-workflow writer exclusion. The local
`patches/@dbos-inc%2Fdbos-sdk@5.4.6-preview.patch` adds `retireWorkflow`, a writer-fence query and
native permanent guards. `kernel/work/README.md` explains generation-one writing/generation-two
closed state and eight payload-table guards. This is a concrete erasure/late-writer gap, not merely
an aesthetic dislike of upstream retention. Cancellation and deletion do not prove no later write.
Retain only while an equivalent upstream guarantee is unavailable; isolate version compatibility
and native regression obligations. Existing `test/work/sdk-retirement-fence.test.ts` is not an
executed receipt in this audit. [Pinned DBOS source](https://github.com/dbos-inc/dbos-transact-ts/blob/980dc55095f445b189aecb59e7f3334345179f65/src/system_database.ts).

The pinned Better Auth `packages/oauth-provider/src/token.ts` explicitly identifies non-atomic
refresh-family deletion and the CAS-to-child-insert race. The local OAuth-provider patch adds a
family-level durable revocation boundary and transactional rotation. RFC 9700 requires replay
defence; deleting known rows while another transaction creates descendants is insufficient for
that adopted policy. This supports a narrow adapter fix, not a custom authentication server.
The upstream clone and local installed version are distinct evidence: no claim is made that every
current upstream release still has the same gap. Reassess equivalence before dependency upgrades.
[Pinned provider source](https://github.com/better-auth/better-auth/blob/860c4b936b897e664145b292e14551af1fa5e6a4/packages/oauth-provider/src/token.ts),
[OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html).

### Remove, consolidate, retain

Remove whole-Collection re-spacing as an ordinary synchronous fallback at the intended scale,
partition-looped summary transaction assembly, provisional production mapping claims, and
unbound-discovery readiness claims. Remove old unavailable diagnostics from documentation paths
once their actual runtime binding is verified; do not remove honest failure states from code.

Consolidate the shared source capture/current-generation/continuation contract consumed by Search,
Library and Zones; a common contract must not move native truth out of the owner. Consolidate
rating threshold computation and type/descriptor lookup. Consolidate deadline propagation and
per-database keyed reads before adding service clients. Retire legacy profile semantics only with
explicit historical pin migration and unchanged receipt/disclosure guarantees.

Retain PostgreSQL, OpenSearch, Better Auth, DBOS, the shared graph, separate private facts, exact
captured benefits and owner-specific erasure inventories. Replacing all of them with one more
generic “engine” would add complexity and erase important authority distinctions. RLS, OpenFGA,
SpiceDB, Kafka and Temporal are alternatives to compare against a precise gap, not automatic fixes.

## Disclosure, lifecycle, accessibility and surface consistency

Search/preparation/index state is derived candidate evidence. Native current subject, owner,
membership, benefit and source-rights checks remain necessary before serialization. Withheld,
unknown and dependency-unavailable must not be collapsed into known absence, particularly under
NOT. `packages/filter/README.md` itself warns that sampled relations and dropped unknown snaks
cannot certify negative predicates. An unavailable dependency must not turn into an empty shelf,
empty scope or an apparently completed deletion. Private page-work cursors retain the existing
encrypted viewer/Zone/body binding; the generic HMAC `tokens/seal.ts` must not carry confidential
owner positions merely because tampering is detected.

Lifecycle repair must cover current and historical pins, tombstones/Undo deadlines, output/source
publication episodes, retired generations, empty-with-next pages, permanent late-writer fences
and exact native plus external erasure obligations. A task marked done is not permission to
remove these contracts. Keep committed replay truth while rechecking current authority before
revealing receipt bodies. Neither deleting DBOS history nor dropping a search document proves
the owner erased its private facts or an external backup expired.

Shared descriptors must supply user-facing labels/count forms and preserved unknown historical
values across subject controls, private shelves, filters, Continue, imports and exported/API data.
Backend unit IDs should not become unexplained accessible names. Long kind catalogues need a
paged/searchable selector with stable IDs, keyboard navigation and announced loading/error states;
they cannot be rendered as 200,000 options. Retained `202` work needs an understandable pending
state and cancellable navigation; 503 needs retry without losing filter intent. These are consumer
requirements to coordinate with Web/UI, not visual findings proved by this desk audit.

Cover frame defaults and source dimensions are distinct. `TypeDefinition.listPresentation` and
composition appearance can choose a portrait frame while preserving landscape media metadata.
Do not infer semantic type, rights, progress unit or privacy from image ratio, title text or a

## Prioritized coherent delivery slices

Sizes below are design estimates for reviewable ownership slices, not promises or measured work.
S means roughly one owner adapter/contract; M several related modules; L a data/index/lifecycle
change with migration and consumers. Each slice includes ordinary API/default assembly, honest
states and its owner acceptance/physical evidence when execution is later authorized.

Exercise worst-case dense gaps, duplicates, hidden subjects, concurrent moves, interruption and purge. Depends on slice 1 for cross-home display reads. |

Preserve historical Library pins and current release admission. No giant client release map as the only path.                                                           |

Depends on owner mapping/current-source readiness. Test default server, not injected stand-ins; distinguish prepared, empty, denied and unavailable.                                                                       |

Do not create a generic saga/permission/source framework first and hope every producer later fits.
The first slices remove known architectural contradictions and deliver one complete native seam;
then consolidate repeated machinery revealed by those implementations. Preserve useful mature
engines and explicit honest failures throughout.

Genuinely maintainer-level future choices are limited to financial product semantics not settled
by today's account-bound sale: redeemable money versus nonredeemable points; transferable item
versus licence; settlement finality and allowed reversal; and market/exchange scope. Options are
to keep these deferred, or authorize a separate owner contract before implementation. Recommend
keeping them deferred now. They do not block this research or current Collection/definitions fixes.
Upper bounds, portrait defaults, search layout and ordinary API writes are already settled.

## Primary-source comparisons and shared patterns

Sources below were browsed on 2026-10-31. These are about twenty relevant infrastructure systems,
providers and standards, rather than an unrelated consumer-site UI survey: the question here is
backend architecture. Documentation is current at observation, not a promise about a pinned
dependency. For source inspection, exact revisions/licences appear after the table. Documentation
availability does not establish hosted-product access, benchmark suitability or local compliance.

| Primary source                                                                                                        | Relevant pattern, disagreement and recommendation                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)                           | RR gives a transaction snapshot. Several separately opened RR transactions do not become one snapshot by sharing a pool. Retain PostgreSQL and fix the caller boundary.                                             |
| [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)                                    | Useful defence in depth; owners/privileged roles have special bypass rules. RLS cannot replace full account/resource/current-source policy merely by existing in the database.                                      |
| [OpenSearch pagination](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/)                   | PIT/search_after avoids deep offset traversal and stabilizes ordering. It does not cap postings work or certify native current disclosure.                                                                          |
| [OpenSearch DLS](https://docs.opensearch.org/latest/security/access-control/document-level-security/)                 | DLS constrains reads, not writes. Owner-native write permission and current-source checks remain necessary; do not treat DLS as complete Access replacement.                                                        |
| [DBOS workflow semantics](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)                               | Resumable workflow execution and persisted steps reduce bespoke orchestration. At-least-once step effects still require idempotent owners; SDK retention does not erase every product copy.                         |
| [Better Auth OAuth provider](https://better-auth.com/docs/plugins/oauth-provider)                                     | Mature protocol implementation is preferable to custom OAuth. Version-specific adapter races still need source-level assessment and narrowly maintained fixes.                                                      |
| [OpenFGA production guidance](https://openfga.dev/docs/best-practices/running-in-production)                          | Check/list operations explicitly need depth, breadth and concurrency controls. A mature relationship engine does not eliminate the bounded-neighbourhood requirement.                                               |
| [SpiceDB consistency](https://authzed.com/docs/spicedb/concepts/consistency)                                          | Explicit freshness tokens and per-request consistency expose real tradeoffs. Its default cached reads do not automatically supply REZICS's current revocation semantics or a shared PostgreSQL snapshot.            |
| [Temporal workflow execution](https://docs.temporal.io/workflow-execution)                                            | Durable execution/replay is an alternative orchestration model, not a substitute for native product authority. Migrating from DBOS would add a service/control-plane boundary; no gap here justifies it.            |
| [Debezium outbox router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html) | Established CDC-based outbox transport can replace repeated polling, with operational/schema costs. Keep transactional owner outbox and idempotent checkpoints regardless of transport.                             |
| [Apache Kafka design](https://kafka.apache.org/41/design/design/)                                                     | Ordered partitions and transaction semantics are useful transport mechanisms. They do not automatically make external PostgreSQL/Stripe effects exactly-once or authorize owner mutations.                          |
| [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)                                             | Stream consumers/pending work are a mature queue option, but another durable system introduces recovery/retention reconciliation. No evidence warrants replacing current PostgreSQL/DBOS just to obtain a queue.    |
| [TigerBeetle financial accounting](https://docs.tigerbeetle.com/coding/financial-accounting/)                         | Debit-credit accounts/transfers are more relevant to future wallets than order status. Evaluate as a ledger authority only after units/holds/reversals and placement are specified; it is not a marketplace engine. |
| [LinkML JSON Schema generation](https://linkml.io/linkml/generators/json-schema.html)                                 | Classes/slots and inherited constraints can emit interoperable schemas; inheritance is flattened for JSON Schema. Useful comparator for reducing custom compilation, without adopting a second runtime authority.   |
| [JSON Schema 2020-12 core](https://json-schema.org/draft/2020-12/json-schema-core)                                    | Shared validation vocabulary avoids hand-written structural validators everywhere. It does not express native permissions, historical accepting pins or bounded database traversal.                                 |
| [W3C SHACL](https://www.w3.org/TR/shacl/)                                                                             | Graph constraint language is a comparator for semantic validation. It supplies neither REZICS editorial acceptance nor cheap arbitrary graph traversal under partition bounds.                                      |
| [W3C RDF concepts](https://www.w3.org/TR/rdf11-concepts/)                                                             | Shared identities/relations are semantic structure, not a requirement to put credentials or balances in one universal public triple table. Preserve typed owner invariants.                                         |
| [UCUM](https://ucum.org/ucum)                                                                                         | Physical-unit interoperability does not define a chapter, episode identity or completion policy. Keep semantic progress units descriptor-owned; use physical standards only for actual compatible dimensions.       |
| [CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)                              | Standard envelope interoperates with tooling; does not provide delivery, partition ordering, Access or erasure. Keep application event catalogue and custody explicit.                                              |
| [OAuth security BCP, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)                                           | Replay/refresh-token protections justify examining atomic native family invalidation. Token rotation alone is not proof that concurrent descendant minting is fenced.                                               |
| [Stripe webhook guidance](https://docs.stripe.com/webhooks)                                                           | Delivery may duplicate and arrive out of order. Retain provider IDs, immutable observations, reconciliation and idempotent owner transitions; do not order payment truth by arrival timestamp alone.                |
| [SQLite WAL](https://www.sqlite.org/wal.html)                                                                         | Durable local journal fits importer recovery, with a single-writer/concurrency boundary. It is not a cross-service catalogue/permission authority.                                                                  |
| [JSON canonicalization, RFC 8785](https://www.rfc-editor.org/info/rfc8785/)                                           | Standard canonical bytes support stable digests. A digest is content identity, not permission, freshness, complete source evidence or proof a native operation ran.                                                 |

Shared patterns are owner-native authority, explicit version/freshness, indexed finite traversal,
durable idempotent effects and reuse of specialized engines. Sources disagree in transaction and
consistency models: RR snapshots, ReBAC freshness tokens, search PIT and workflow replay are not
interchangeable. The recommended stack remains PostgreSQL + OpenSearch + Better Auth + DBOS with
small owner adapters; choose a replacement only against a demonstrated unfilled requirement.
