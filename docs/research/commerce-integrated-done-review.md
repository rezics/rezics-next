## Durability, concurrency and replay boundaries

1. **Commit before provider call/enqueue.** `checkout.ts:32-56` commits order creation before calling Stripe. The command executor writes receipt/outbox in the same transaction and commits at `src/command/command.ts:505-559`. The order-created effect later enqueues reconciliation with a deterministic identity (`commerce/work.ts:214-227`), covering a stopped request between creation and provider/session recording.
2. **Outbox checkpoint follows durable acceptance.** `src/events/effects.ts:76-83,135-143` awaits deterministic DBOS starts. Its `readBatch` implementation applies before checkpoint/commit (`src/events/log.ts:174-212`). A crash after enqueue and before checkpoint redelivers to existing workflow identities. Webhook intake likewise awaits durable acceptance before 200; enqueue failure returns 503 (`commerce/webhook-routes.ts:55-72`). Source ordering is sound; the focused native replay case is not an injected crash at each relay boundary.
3. **Concurrency is explicit.** Multiple event children can run for one Session. Locked settlement plus unique entitlement and balance-transaction keys prevent duplicate grants/accounting. `test/commerce/work.test.ts:32-90,143-162` contains concurrent duplicate and delayed-old-paid/newer-refund scenarios. Durable observation time is persisted before provider reads (`work.ts:59-95`), then stale observations are rejected. The no-op exception below limits this claim.
4. **Authorization precedes receipt disclosure.** `commands.ts` builds SHA-256 digests from canonical JSON; shared `command.ts:437-479` authorizes before receipt lookup, compares the digest and only then returns the old response. Commerce command tests at `test/commerce/commands.test.ts:233-279` cover revoked/suspended replay and delisted-offer receipt behaviour. `test/commerce/payout-mark-paid.test.ts:220` covers revoked payout replay. These are inspected assertions, not extra passes inferred from the native log.
5. **Trusted provider work is not buyer impersonation.** `applyCheckoutSnapshot` is an internal workflow port with a deterministic workflow-step key, not an exposed buyer command. Its receipt names the buyer but does not require the buyer still to be active (`commands.ts:349-367`). Stopping payment truth when an account is terminal would conflict with reconciliation. Its order-only digest relies on the DBOS durable step binding the exact snapshot to that key; do not expose it as an arbitrary external command.

## Concrete defects and missing native proof

### Offer revision omits the target from its semantic digest

`src/commerce/commands.ts:199-224` authorizes `id`, but hashes only `{unitAmountMinor}` at lines 209/214. Receipt identity is principal, command kind, key and partition, not target resource (`src/command/command.ts:457-467`). A seller revises offer A, then revises another owned offer B in the same partition using the same key and price: authorization for B succeeds, but A's receipt is returned and B is unchanged. This is a source-derived defect in the native command port, even though no HTTP revise route currently exposes it.

`test/commerce/revise-offer.test.ts:112-207` checks replay/conflict on one target and denial/delisting, but has no cross-offer same-key case. Add a new test file asserting conflict for a changed target, unchanged B and no second effect; retain all existing tests.

### Delisted offer remains readable by known ID

Commerce README line 19 says public catalogue reads exclude delisted offers. `src/commerce/routes.ts:223-235` returns any row; `store-offer-read.sql:1-3` has no active-state filter. The route's action metadata supplies a lazy authorization function, not an automatic per-resource read check (`src/http/app.ts:207-231`), and this handler does not call it.

Trigger: delist an offer, then anonymously GET its known `/v1/offers/:offerId` while purchases are open. The source returns its title, price and account-linked offer instead of concealed 404. `specs/commerce-outcomes.test.ts:470-479` checks new checkout rejection and existing benefit preservation, not that GET. This is a contradiction of the current owner document, not a proposed new deletion policy. Fix public visibility without removing captured buyer terms or existing paid benefits.

### A newer no-op observation does not advance the stale-snapshot boundary

`settlement.ts:67-68` rejects older observations, but lines 94-95 return unchanged when settlement, entitlement and transaction IDs do not change. `commands.ts:377-378` then rolls back without persisting the newer observation. A subsequently delivered older observation can still outrank the stored watermark.

Realistic missing case: an already-paid active order has watermark t0; workflow t1 reads a full pending refund with no balance transaction and is delayed; workflow t2 reads that refund canceled, also without a transaction. t2 is a no-op and leaves t0. t1 then revokes the entitlement from obsolete pending state. The pinned Stripe Refund type permits a null balance transaction and optional failure reversal (upstream `src/resources/Refunds.ts:117-157,208-211`); the adapter accepts those shapes. This is a source-derived ordering gap, not an observed provider incident.

The fixture always creates a balance transaction for pending refunds (`support/fake-stripe.ts:508-521`), so that shape is absent. Existing stale/no-op tests (`settlement.test.ts:339-367`) do not cover a newer no-op beating an older effective change. Generated histories assume accumulating transactions (`:369-385`). Native equal-clock observations and multi-request provider snapshots also lack an explicit ordering proof. Preserve existing no-op business semantics when repairing an internal observation watermark; do not weaken those tests.

### Reconciliation after a missed late refund/dispute is not demonstrated

Both delayed reconciliation and expiry work exit for paid/failed orders (`work.ts:156-201`). Component missed-event/restart cases at `work.test.ts:209-284` repair unsettled/expired Checkout; `:286-306` expressly skips terminal settlements. A paid order receiving a refund after those workflows finish depends on a webhook reaching durable intake. There is no inspected recurring paid-order reconciliation or external repair route to invoke after delivery is exhausted.

The original contract requires reconciliation but does not specify a periodic paid-history scan, repair SLA or operator API. The owner must state the intended missed-late-event recovery mechanism and add native proof for it. Do not silently invent an unbounded sweep or a second settlement engine. Stripe retry/redelivery facilities are not proof that Rezics exercises a recovery path.

## Shared deletion policy: Commerce-owned consequences

`docs/deletion.md:21-25` makes account deletion terminal at confirmation, with bounded private cleanup starting immediately; individual record Undo remains separate. Commerce README lines 11-39 accurately distinguish business facts from deletion and acknowledge no account consumer, minimization path or agreed retained evidence skeleton. Its forward-looking legal-hold language at lines 41-48 is not an implemented interface or authority for a new first-scope custody engine.

- **Private reads after terminal state:** production authentication reads current actor state on each request and rejects non-active/fenced actors or stale authn epochs (`access/authenticate.ts:210-226`). Thus an old bearer token alone does not establish an ongoing cross-request leak. Shared command admission also rechecks current actor identity/state before replay (`access/command-admission.ts:142-173`).
- **Read race still needs native proof:** order/entitlement handlers rely on the admitted actor plus scope, buyer equality and route (`commerce/routes.ts:386-412,435-500,510-533`). Payout handlers authorize the account anchor (`payout-routes.ts:130-183`) and stores enforce creator equality. No Commerce outcome admits a request, makes the actor terminal, then releases its delayed private read. Resolve whether current shared read authorization satisfies the terminal-T boundary, with the shared owner if its contract must change; do not label all stale tokens a demonstrated leak.
- **Financial facts survive Library Undo:** neither record restoration nor account erasure may turn a paid order unpaid or restore a refund-revoked benefit. Existing provider reconciliation may restore an entitlement only from newer authoritative payment state (`settlement.ts:71-89`); account restoration is not a Commerce port. Add Commerce assertions at this interface, without duplicating the Library builtin audit.
- **Private payloads remain:** buyer/creator links, captured title/target, Checkout URL/session, provider transaction IDs and paid references remain in `schema.sql:134-330`. Immutable transaction/royalty triggers (`:444,472`) prevent ordinary deletion; they do not establish a lawful retention exemption. Payment evidence, public offer skeletons and private purchase relations need explicit field-level disposition under the shared policy.
- **Shared history remains:** order/entitlement/account identifiers appear in closed outbox events, command receipts and durable workflow arguments/results (`commerce/events.ts`, `commands.ts:362-407`, `work.ts:76-95,204-227`). Identifier-only event schemas reduce payload, but do not make these relations nonpersonal. No Commerce terminal-account consumer or exact shared-history locators exist. Source store cleanup alone would not prove receipt/outbox/DBOS payload erasure. Use the shared lifecycle/checkpoint/cursor interfaces once their exact cleanup protocol and permitted retained fields are agreed; no broad principal/JSON deletion, default cascades or fresh custody system is recommended.
