# Binding common bulk preview to execution

Research evidence, 2026-11-02. Repository source inspected at `1556f48ef91b0aee8719fa6321e9b35d500c7dc0`.
This report proposes a handoff for adoption; it does not change contracts, install producers or establish native acceptance.

## Recommendation and unresolved boundary

Keep the existing private Library operation design and installed `bulk_target` manifest relation. Add preparation, sealing and explicit confirmation phases to that operation, before its designed independently receipted target effects. The completed preview describes immutable manifest membership and action intentions; execution consumes those exact rows, never another execution-time query. Shared Collection Source/filter owners must supply complete admitted selection evidence and currentness, rather than a second bulk query engine.

There is **no installed common protocol meeting this contract**: the bulk runtime is literal stubs, finite filtered preparation lacks its producer/consumer interface, and the confirmation currentness cut is unspecified. Native implementation needs the producer decisions below. Recommend that the owner decide whether “reject stale selection” means rejection at one provable confirmation cut, with subsequent target conflicts inspectable, or rejection of any drift before any effect. The latter needs additional native coordination across the participating homes. Neither interpretation is silently adopted here.

The later [common bulk requirement](../../services/kernel/src/library/README.md#bulk-library-operations), [Library](../library-and-collections.md), [filtered lists](../filtered-lists.md), [Collection Source](../collection-source.md), [dynamic Collections](../dynamic-collections.md), [owner queries](../library-owner-queries.md) and [profile consumers](../library-profile-consumers.md) govern this proposal. The older [bulk contract](../../services/kernel/src/library/bulk-contract.md) and [query-bulk research](library-query-bulk.md) supply action/receipt details, but their discovery-time matching, absence of confirmation and old delivery split are historical. No shelf survey is repeated.

## Three primary systems and their specific lessons

**PostgreSQL, documented facts.** Read Committed modification predicates are rechecked against a concurrently updated row; Repeatable Read retains its earlier snapshot. Serializable can reject a nonserializable transaction, but does not unite independently committed transactions. Row locks last until transaction end; locking existing rows does not lock absent predicate matches. See [isolation](https://www.postgresql.org/docs/18/transaction-iso.html) and [locking](https://www.postgresql.org/docs/18/explicit-locking.html). These support native conditional target writes, not a job-wide transaction.

An [exported snapshot](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION) is importable only while its exporting transaction remains open. Pinned [`src/backend/utils/time/snapmgr.c`][pg-source] removes exported files at transaction end and rejects import from another database. **Inference:** retaining its textual ID across preview, user think time and restart cannot supply the required durable population or fresh permission. Keeping a connection/transaction open across those stages would violate this journey's bounded native placement.

**DBOS, documented/source facts.** [Steps](https://docs.dbos.dev/typescript/tutorials/step-tutorial) checkpoint results and may execute more than once before checkpoint. Pinned [`src/dbos-executor.ts`][dbos-step] records output after the step body returns, leaving a commit/checkpoint crash gap. [`src/client.ts`][dbos-client]'s `enqueueInTransaction` uses the caller's system-database transaction: intent and local state can commit together. **Inference:** reuse REZICS's Core/WorkClient same-client enqueue and exact native receipts; a DBOS checkpoint is neither target authorization nor an effect receipt for a different native transaction.

**OpenTofu, documented/source facts.** A [saved plan](https://opentofu.org/docs/cli/commands/plan/) records intended changes; saved-plan [apply](https://opentofu.org/docs/cli/commands/apply/) consumes that plan without replanning. Plans may contain sensitive values. Pinned [`internal/backend/local/backend_local.go`][tofu-source] locks/refreshes state before comparing saved lineage/serial; `backend_apply.go` retains the state lock through apply. **Inference:** the useful pattern is an exact plan plus native currentness coordination. Its state serial works because participating state writers share that state/lock boundary; a Library source digest over multiple independent homes has no equivalent guarantee. Saved plans also do not freeze provider permissions.

The shared pattern is retained intentions, explicit commit, native concurrency controls and recoverable evidence. None of these systems supplies REZICS's admitted-source authority or complete cross-home population currentness. They constrain this design; they are not an impossibility proof for other primitives.

## The stale-confirm race requiring adoption

Let the operation and its owner-entry targets live on H; selected subjects A/B and excluded X have filter/identity dependencies on P/Q. A Collection action can instead put its target occurrences on a permitted Collection's home. The race does not require falsely routing owner entries by subject ID: independent target transactions suffice. A complete preview was valid when sealed.

1. Confirmation checks Q and the captured target expectations on H; it releases those bounded transactions.
2. A writer makes X match on Q, changes a NOT/order dependency, or changes B's captured entry expectation on H.
3. Confirmation checks P and commits `confirmed` on H; A's independent target command commits.
4. A subsequent Q check detects the mismatch. Stopping now retains A's effect: it is not rejection before any effect.

A final reread in Q's old RR transaction sees its old snapshot. A fresh reread can race the next writer. Per-target CAS protects A from A's concurrent writer, not an unseen mutation of X/B. Hashing headers cannot establish complete predicate coverage. Serializable per page/target cannot roll back earlier target commits. Same-home Source custody does not span these independent transactions. This demonstrates a gap in these proposed mechanisms, not universal infeasibility.

The owner must choose a temporal rule and its producer:

- **Recommended rule, pending adoption:** stale selection means a changed admitted population/meaning/identity/action expectation _before a defined confirmation cut_. Prove currentness for the whole selection at that cut; reject without dispatch when stale. Mutations strictly after the cut may become exact target conflicts or operation-wide authority stops, retaining prior effects. This still needs a native complete-validation/commit binding across the admitted dependencies; sequential validation plus operation-row CAS is insufficient.
- **Stronger rule:** reject any relevant pre-first-effect drift before **any** effect. This needs writer-participating reservations/barriers through that boundary, or another adopted native atomic primitive. If any CAS failure discovered later must also mean whole-operation stale rejection, protect all expectations through execution or commit all effects atomically; independent earlier commits cannot be undone by a later check. Define lock ordering, phantoms, revocation, crash release and bounded ownership. A new global gate or long-lived PostgreSQL snapshot is not an allowed shortcut.
- A genuinely single-home selection whose complete validation and all effects fit an existing bounded transaction could use that transaction. This is a placement-specific optimization, not a population cap or a solution for the required cross-home journey. Do not narrow common support to make the general race disappear.

The report recommends retaining independently receipted effects and deciding the first rule, but does **not** reinterpret the adopted stale requirement or invent a shared confirmation-fence ABI. Until the responsible owners adopt/provide the cut, a common confirm must be unavailable; discovery-only “confirmation” would be false.

## One end-to-end native journey, conditional on those prerequisites

The phase names and fields here are proposals for the existing operation, not additional exports or approved HTTP ABI.

Concrete case: an owner selects all matches of an admitted owner-state filter on their curated C; canonical A matches despite two C occurrences, and B is excluded. They choose subject-based removal from permitted curated D, whose A occurrences are d1/d2. The operation privately previews one confirmed subject and two captured removals. After explicit confirmation at the adopted cut, a new A occurrence d3 in D survives; d1/d2 have independent native receipt outcomes. A concurrent delete/Undo of d2 yields an inspectable lifecycle conflict. The UI reads the same operation's outcomes and can cancel remaining dispatch; restart resumes its exact receipts. A built-in source follows the same unique-subject path, with no invented C occurrence IDs.

1. **Select.** The existing Collection/Library or permitted mounted UI retains explicit subject IDs/real curated member IDs, or one server-admitted source + filter + order definition. Browser layout/page cursor and displayed page contents do not identify “all matches”. Source/filter/order admission uses the shared compiler and current viewer, including every OR/NOT leaf and foreign resource. A mounted grant does not grant subject or owner-private fact access. Never impersonate the curator; `self` is the actual verified principal.
2. **Admit privately.** Adapt `createBulkOperations().admit` and the proposed `/v1/libraryOperations` composition under `personal_library`, source/list/effect scopes and Collection gates. One idempotent native command freezes bounded request bytes, action, original IDs and authentic creation provenance; use `captureDurableInitiator` during admitted authorization preparation and `durableInitiatorCommitment`. Commit one operation header and durable continuation intent with its native receipt/outbox. Core must settle the command-to-WorkClient binding described below; enqueue must never be an unprotected post-response action. No target effect has occurred. Return a private recoverable operation locator; foreign/unknown operations share 404.
3. **Acquire admitted selection work.** Explicit inputs are deduplicated, authorized and canonically resolved while preserving original references for current checks. A filtered selection consumes the existing Source plus shared admitted filter plan, not `state`/`primaryType` shelf discovery. The producer must deliver a finite durable result/coverage binding. Existing native preparation authority covers a viewer-owned collection or admitted positive own presence; it does not authorize deriving arbitrary mounted/foreign populations. Unsupported placement is unavailable/rejected before enumeration, not privately evaluated by bulk.
4. **Enumerate into this manifest.** At each bounded step re-admit the real source/preparation episode, settle all Source/filter work under its existing reservation, and insert only proven canonical matches. Commit target rows, one frontier/checkpoint CAS and continuation atomically on the operation home. Foreign transfer needs the producer's committed bounded page evidence: release that connection before operation-home checkout, and acknowledge only after matching manifest adoption. Replay compares exact page/target bytes, not just a digest; page evidence grants no authority. No complete flag follows a missing, unknown, failed or empty-but-unexhausted prefix.
5. **Capture intentions before sealing.** Status/entry removal captures each exact native entry incarnation and revision; explicit absent status captures a genuine slot-generation witness. Add captures unique subjects and append intent, not fabricated occurrences. Subject-based Collection removal expands selected subjects into **all** matching actual member IDs in one complete native target-Collection scan before effects; explicit occurrence selection captures only those IDs. Bind `member_revision`/active deletion state to reject delete/Undo ABA. Reorder/note edits preserve occurrence identity and do not select replacement members. The native capture producer must prove a stable complete membership boundary, including behind-frontier changes; a mutable ordinal cursor/high-water alone cannot do this.
6. **Seal a useful preview.** After complete selection and occurrence coverage, source/meaning/identity/disclosure validation and immutable target binding, CAS the operation to awaiting confirmation with an immutable seal generation. Bind canonical definition bytes, action/target bytes, manifest cardinalities and ordered digest to the native completion receipt. The digest corroborates retained committed rows; it does not prove completeness. Compute totals incrementally from unique inserts, never `COUNT` the population on GET. Dynamic sources supply unique subjects without member IDs, notes or added times.
7. **Display only confirmed safe scope.** Private, no-store reads reauthorize operation/source and revalidate current disclosure for returned fields and any count. Show action, safe examples, safe exact confirmed subject/occurrence counts when allowed, expiry and incomplete/preparing/stale state otherwise. Public-source candidate totals and internal scanned counters remain private operational data; a private operation is no declassification of unsafe public query totals. Incomplete/unknown is not zero; only a genuinely completed, disclosure-safe empty selection seals zero. Entry removal text says copies, sessions/history, follows and Collection members remain.
8. **Explicitly confirm.** A separate idempotent command submits the operation ID and exact seal generation/action binding, not a fresh query or client target array. Restore/re-authorize at native command time; check expiry/cancel, current admission and all required shared freshness under the adopted confirmation-cut primitive. CAS awaiting-confirmation to applying and record the confirm receipt/continuation together. Stale previews remain inspectable as stale; they never refresh themselves into an accepted confirmation. No effect dispatch before this succeeds.
9. **Execute finite native targets.** The default Library DBOS segment seeks pending ordinals and freezes a dispatch attempt under the operation checkpoint, then releases its home before target checkout. Retain the proposed `BULK_SEGMENT_PAGES = 100` ceiling and bounded page checkpoints; actual `WorkIntent.input` requires `accounts: [ownerAccountId]` alongside operation/route/generation locators, which old `SegmentInput` omits. Never put manifest arrays in DBOS inputs. Each target restores the initiator in `CommandAuthorization.prepare` at the attempt's authoritative time, within its 1,000 ms evidence lifetime and native deadline; checks current source/Collection/target authority before receipt access; then returns the exact receipt or performs captured CAS/action. Dispatch grants no permission; stable keys bind operation + ordinal + command meaning, with no replacement-terminal recanonicalization.
10. **Acknowledge and inspect.** A real mutation, its normal domain events, Core receipt and compatible immutable `bulk_effect` evidence commit in the same target transaction. The source acknowledges exact receipt evidence with one pending/reconciling-to-terminal CAS, updating fixed counters once. An unknown commit remains reconciling; GET has no final summary until complete selection and every target are terminal. Adapt `pageBulkOutcomes` behind current owner authorization and the existing encrypted cursor owner, binding operation/viewer/filter/size; do not expose its internal decimal key as a wire cursor.
11. **Cancel, expire, recover.** Cancellation closes new dispatch via the operation-row generation/lock and drains already-dispatched attempts using their exact receipts; it does not undo committed effects. Each target enforces the absolute execution deadline even if DBOS resumes later. An old step may reconcile earlier evidence but cannot reopen dispatch. Source/account/consent/delegation/Collection gate loss stops the operation; target-specific denial/conflict does not stop other authorized targets. Retained private accounting can verify prior effects after revocation without disclosing them or minting effect authority.
12. **Dispose through existing custody.** Expire abandoned previews and completed operations with indexed, bounded child-first pages and target-home evidence acknowledgements; then minimize shared receipt/outbox/work payloads through their owners. Terminal account deletion conceals private operation data immediately and joins the existing Library erasure graph. Do not delete current physical custody, manufacture an empty-source ACK, or claim public A/fresh private B disposal is complete.

### Native action details that wrappers alone cannot supply

- **Status:** present `(incarnation, revision)` must match even when current state equals desired state; only an exact match can receipt `no_effect`. A missing/recreated entry conflicts. An absent explicit entry needs a writer-maintained absence witness that changes on create/delete/recreate. Present entry incarnations exist, but the proposed admission-sequence/absent-slot fields do not. The Library entry owner must choose a retained per-slot generation or equally complete indexed lifecycle witness; observing absence twice cannot reject ABA.
- **Collection add:** under the existing Collection command lock, active-subject presence check plus append is atomic. The existing `(route, collection_id, subject_id, member_id)` index includes tombstones: add a nonunique active partial index with these keys and `WHERE deletion_id IS NULL` so a failed presence seek cannot scan all deleted duplicate history. Present means no effect, absent appends one member; preserve the existing 5,000-member capacity, ordinal allocation/respacing, intentional ordinary duplicates and current subject read. Existing `addMember` always appends: calling it unchanged violates bulk semantics.
- **Occurrence removal:** `collection_member.member_revision` already increments on delete/restore, while note/move SQL preserves it. Expose it in a bounded capture projection and add an exact active-member/lifecycle CAS under the parent lock. Existing `removeMember` instead requires the whole Collection revision and its delete SQL lacks this lifecycle CAS; replaying a frozen parent revision would conflict with the operation's own first deletion. Preserve current notes/order in native tombstones, ordinary reduction events and retention; do not replay a subject-wide predicate. Later additions survive and do not conflict merely because the parent revision advanced.
- **Entry removal:** reuse ordinary deletion invariants/events with the exact incarnation/revision; remove only the entry, with no history/copy/member cascade. `createEntryCommands`/`createCollectionCommands` provide native semantics to factor, not HTTP commands whose current expectations can be silently refreshed.
- **No effect and denial:** Core `noEffect` permits no domain writes/events/callbacks. A no-effect target can commit its Core receipt, but cannot insert `bulk_effect` in that same no-effect body. `command/command.ts` already has `runCommand` and authorized `receipt-only` mode: the missing part is bulk's protected source-bound composition, not a new generic receipt engine. Denial before authorization cannot create an authorized effect receipt; source accounting records denial separately. Private reconciliation after revocation needs its own agreed evidence-only authority, not fake events or an Access bypass.
- **Profiles and replay:** current authorization precedes receipt lookup; an authorized exact receipt replay precedes _fresh_ profile/capability validation. A later release may reject a new target value without invalidating an already committed receipt. Pin accepted meanings per target; do not copy full manifests, expose private pins or substitute today's release for historical meaning.

## Concrete storage, locks and retention handoff

Implement the missing operation header under the existing Library schema owner: PK `(route, operation_id)`, exact account owner, unique admission key/digest within native principal/command scope; immutable request/initiator creation-receipt binding; source/preparation locators and complete dependency-binding provenance; phase/checkpoint generation/frontiers; seal generation/count/digest; confirmation/cancel receipts; fixed counters; absolute admission/execution/results times. Add owner-led lookup, phase/due-expiry keysets and account-erasure locators. A source revision/hash is an alarm component, not a complete selection witness.

Reuse `bulk_target` PK/subject/occurrence uniqueness and state/pending indexes. Freeze target/action/expectation/receipt bytes before seal; mutable columns only track dispatch/outcome evidence. Include seal generation in native provenance, either by a checked immutable root binding or an adopted column, not by trusting caller-supplied JSON. Page insert + checkpoint CAS + native continuation must be one operation-home transaction. Uniqueness conflicts must verify equality and ownership, never silently omit differing targets. Lock the operation row for seal/confirm/dispatch/cancel transitions; lock native entry slot or Collection/member rows for target CAS. Establish a consistent parent/child lock order and retry deadlocks with the same key.

Remote occurrence capture needs bounded page receipts with exact source operation/selection binding and acknowledged frontier, retained only until source manifest adoption/reconciliation. These are transfer evidence for the same manifest, not another workflow or population store. Neither existing raw ordinal prefix nor old proposed `admissionSequence` proves a complete stable capture. Source/Collection owners must select a writer-fenced finite generation or complete indexed membership-change repair/cut; do not invent admission-sequence fields as if already installed.

For subject removal, retain explicit subjects in the bounded request or bind the shared immutable filtered-result generation; transfer bounded pages into the old contract's target-home selected-subject lookup, keyed `(route, operation_id, subject_id)`, with page/ack keys `(route, operation_id, page)`. This staging is not installed DDL. It supports one raw Collection scan with indexed membership probes, then child-first disposal. Only captured occurrences enter the executable `bulk_target` pending set for this action; selected-subject transfer seeds must not become extra effect targets. The shared result/request and its completion binding prove selected membership; `bulk_target` is the operation's sole effect manifest.

There is also a concrete enqueue composition gap: `CommandTransaction` exposes queries, while `enqueueIntent` requires a registered live `OperationalTransaction` and exact fenced `accounts`; `enqueueWorkIntent` consumes the executor's actual `PoolClient`. Do not cast between these types or run a second transaction while claiming atomicity. Core must either provide the approved same-client domain-command adapter, or adopt the existing Core outbox/effect delivery path to drain a native operation intent through `libraryWorkModule` with deterministic workflow identity. Derived preparation already uses its own operational executor; that does not automatically give domain commands its ABI. Both options preserve the same operation/workflow and recoverable native intent, with no new scheduler.

Reuse `bulk_effect` for compatible applied-effect evidence, including exact target/source/receipt/request digests. The account-led target/effect erasure indexes are already present in `20261030071949_erasure_owner_keys.sql`; do not propose them as absent. However, [`library/erasure-participant.ts`](../../services/kernel/src/library/erasure-participant.ts) explicitly records the missing account-home target-effect locator/late-disposition fence and shared-history custody. Add those producer obligations before enabling effects; an expiry index is not terminal erasure authority.

Keep the existing proposed absolute 24-hour execution and 48-hour result horizons from admission; confirmation/retry cannot restart them. Preview validity ends no later than execution expiry or loss/expiry/eviction of its required shared proof. Shared preparation retains at most 32 live owner results and 24-hour idle expiry; reserving/retrying bulk must not touch/renew its LRU without the producer's actual admitted read. A sealed manifest may retain inspectable intentions after proof expiry, but cannot be confirmed from expired proof.

Bound stale/abandoned preview storage as well as completed effects: due-index cleanup visits at most 100 charged native child keys per step, including empty/tombstoned prefixes, with durable continuation and exact remote locators. Keep evidence until unknown in-flight receipts are reconciled or their native evidence disposition is explicitly established. Closed execution cannot extend data retention forever. If that cannot fit the results horizon, the owning retention/receipt contract must resolve it rather than drop unknowns or report a false terminal summary.

An expiry horizon alone does not bound concurrent byte custody under unlimited admissions. Bulk admission must consume the existing write-rate/chunk authority (`SpendBulkChunk`, stable monotonically indexed chunks, no renewal trick) and receive an owner-approved outstanding-operation/byte reservation policy. The preparation quota is not a bulk-manifest quota. No new numeric population/version cap is proposed; until byte/custody admission and minimizers are specified, aggregate retention is an explicit missing requirement.

## Costs: derived obligations, not measurements

Let N be all relevant raw Source candidates, D changed dependency/repair keys, M target-Collection raw members examined for subject-removal capture, T frozen native targets, J selection/capture steps and E target attempts including replay. Count aliases, duplicates, rejects, lookahead, failed/empty seeks and foreign work, not just matches. Relevant finite input may be large; there is no new population cap. Continuous relevant mutation can end stale/expired; it cannot produce a truncated “complete” preview or perpetual fake preparing.

Existing [filtered-list ceilings](../filtered-lists.md#cost) remain unchanged: direct page `s <= 100`, candidates `c <= min(600, 6s+3)`, three refill rounds, owner-index 3/engine 6 operations, points `16+8c`, examined rows `64+16c`, response `16 KiB+4 KiB*c`, request `64 KiB+1 KiB*c`, and at most 12 statements/one connection per backend. Composed reads retain `8+4R`, `R <= 16`, 128 total output slots. A ready result reads at most `2s+2` candidates/two result-index reads. Prepared steps retain 1,000 input/result rows, one frontier, eight points/input, examined `64+16*input`, 16 statements/backend, four engine operations, 4 MiB response and one connection/backend; **the stronger applicable native 100-raw-key bound still wins**. Identity metadata/witness work transfers through the same reservation and is not free. This report grants no renewed allowance or native growth waiver.

For one stable generation, total relevant candidate work should be `O(N + M + D)`, target/evidence work `O(T + E)`, with at most one unfinished-step reread per recovery and indexed repairs rather than full restarts. Total SQL is the sum of actual admitted Source/filter/Access/Core calls, plus two proposed manifest statements per page, target commands, acknowledgement CASes, continuation and cleanup. Total bytes include inspected candidate/dependency payloads plus `T * (bounded target + bounded receipt/evidence)` and replay, not merely the 16 KiB input. These are accounting formulas, not proven numeric bounds: the missing producer must supply inclusive row/statement/byte plans and completion evidence before implementation can advertise feasibility.

Durable storage is `O(T * admitted target/evidence bytes + retained dependency bindings + page frontiers + existing receipt/work history)`, with indexed seeks logarithmic in retained rows. Over a retention horizon H, aggregate bytes depend on admitted operations/targets/bytes during H and cleanup throughput; no constant-space claim follows from page size or TTL. Reuse the shared cost counters and deferred three-scale native proof later; no growth/custody harness, fabricated measurement or source execution was performed here.

## Failure and recovery cases for the owning implementation

| Boundary / race                                                                       | Required durable result                                                                                                                                                                    |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Crash before admission commit / after commit before response                          | No operation or enqueue in the first case; exact admission receipt returns the same operation in the second.                                                                               |
| Source page read then crash before manifest commit                                    | No frontier advance; repeat only the unfinished step under current admission. A revoked/changed source cannot be adopted from a stale page.                                                |
| Manifest commit before DBOS checkpoint / duplicate worker                             | Native checkpoint/page equality and target uniqueness prevent duplicate rows/counters; resume from committed frontier, not zero.                                                           |
| Arrival or reduction behind the enumeration frontier                                  | Complete indexed repair/cut includes it or invalidates selection. “Exhausted” over only the suffix cannot seal; unknown coverage never seals zero.                                         |
| Preview viewed, then source/meaning/identity/expectation changes                      | Confirmation rejects stale at the adopted cut; no automatic refreshed selection or dispatch. Include excluded/NOT/order-only dependencies.                                                 |
| Two confirmations / confirm races cancel or expiry                                    | Root lock + generation CAS produces one confirm receipt or a closed/stale result. Retained DBOS work cannot resurrect an expired generation.                                               |
| Effect commits before checkpoint/source ACK; transport fails                          | Reconcile exact original receipt/evidence. Do not inspect current row state to guess success, retry with a new key, or increment counters twice.                                           |
| Entry create/delete/recreate; occurrence delete/Undo; desired value changed away/back | Captured native slot/incarnation/revision/lifecycle rejects ABA. Exact receipt replay remains the earlier outcome after current authorization.                                             |
| Revocation after some effects, before another attempt/replay                          | Operation-wide stop or target-specific denial as appropriate; prior effects retained, unresolved attempts reconcile privately; no disclosure via denial reasons.                           |
| New target member / reorder during occurrence capture                                 | Stable capture producer repairs or stales before seal; post-capture additions survive. No mutable ordinal-only scan, fake member IDs or subject-predicate retries.                         |
| Cancellation with in-flight targets; restart past deadline                            | Close new dispatch, drain exact receipts and mark untouched targets cancelled. No rollback promise, zero summary over incomplete selection, or fresh effect after expiry.                  |
| Account terminal transition during capture, target commit or GC                       | Current native lifecycle fences defeat new effects/late adoption; existing custody records late disposition and shared-owner acknowledgements. Missing locator remains a real custody gap. |
