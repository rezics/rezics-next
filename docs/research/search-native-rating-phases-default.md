# Native phases for Global rating order

Research date: 2026-10-28. This is evidence and a recommendation, not an adopted contract or a runtime test.

## Answer

**Yes, conditionally for a fixed indexed state:** two native queries can produce exactly the same total order as the conditional-script proposal, without a per-match rating script. They cannot by themselves produce an exact order of _current native figures_ while publication or eligibility changes asynchronously. A bounded current-source check can prevent disclosure of an invalid numeric result, but cannot place an invalidated hit into its correct unscored position or discover a missing promotion. Nor do two ordinary searches form a snapshot. This distinction is essential to the answer.

The scope is [the Global standard question](../scope.md), not Realm scores. [Rating](../../services/kernel/src/rating/README.md) requires the appropriate public figure and a prior from the same question and population with at least 50 votes. The current strict subject mapping has no rating fields, and [query.ts](../../services/kernel/src/search/query.ts) does not implement rating sort; the fields and protocol below are a candidate, not a description of shipped behavior. The independent `docs/research/search-rating-epochs.md` report (read from its landing worktree) recommends one conditional numeric script and a negative unscored sentinel. This report reaches an independent recommendation for native phases, subject to the invariants below; neither report is runtime proof or authority.

## Fixed-state construction and proof

Let U be the fixed set satisfying the identical subject text and filter query, with the same generation, mappings and indexed state in both searches. Let E be the selected current, _eligible_ native Global prior epoch. Define P as `term(rating_prior_epoch, E) AND exists(rating_score)` when E is eligible; when native state is known ineligible or epoch is null, define P as `match_none`. A is U AND P; B is U AND NOT P. Put both predicates inside the query filter, not `post_filter`: otherwise aggregations and related accounting may see a different population. A sorts `rating_score desc, name_sort asc, id asc`; B sorts `name_sort asc, id asc`. Concatenate A then B. For B use a single `must_not` around the whole P, not separate negative clauses: the latter computes NOT epoch AND NOT score and drops documents with only one mismatch.

For every document in U, Boolean P is either true or false. Thus A and B are disjoint and exhaustive, including missing/null epoch, absent score and stale epoch. Score **0** exists and is in A; score absence is B. Even an old valid indexed numeric score is in B if its epoch differs. Known ineligibility produces A empty and B all. Unknown or unavailable native state is an error, not evidence of ineligibility. If every valid score is finite and nonnegative, concatenating A and B is equivalent to the script's score-descending order with a strictly negative sentinel, followed by the same name and ID keys. Tied scores, including zero, use name then ID; every unscored subject uses name then ID. This is a mathematical equivalence over the indexed fixed state, not a claim that every indexed figure is still public.

Required producer/mapping invariants: one scalar epoch and one scalar finite nonnegative score, atomically projected from the same public Global figure, with absent/null score actually absent from indexed/doc values, no numeric `null_value`, and no silently ignored malformed score. A multivalued epoch can match E while a multivalued score sorts by a different selected value; `exists` does not prove cardinality or finiteness. Enforce the invariant before indexing, fail closed on violations, and do not claim that native exists validates it. Epoch must uniquely identify each eligible prior version; never relabel an old score as a new epoch. Use stable, unique, nonmissing `id` across all shards and compatible mapping/sort semantics across the single physical generation. `name_sort` must have one stable scalar key, or both phases and the script must use the _same explicit_ missing policy and round-trip its actual returned sort value. A missing name remains sortable, with ID resolving its ties; verify the native missing representation can be encoded and replayed rather than inventing a string sentinel. No numeric missing sentinel is used in A: `exists` excludes it. A numeric sentinel in B would be unnecessary; any sentinel in the script comparison must lie strictly outside the valid score domain.

OpenSearch merges the per-shard top hits under the requested field sort. With the globally unique final ID, the lexicographic keys define one order regardless of shard placement; shard-local document IDs are not an adequate cross-shard tie breaker. This conclusion assumes successful complete shard responses, compatible field mappings, and no timeout, early termination or partial shard failure. Reject incomplete responses rather than asserting their totals or exhaustion. Test the behavior on multiple shards even though the current subject mapping configures one.

## Bounded paging and totals

Resolve the active alias to exactly one concrete generation _before_ either phase. Both requests target that physical name, including zero-hit and `size: 0` requests; generation identity therefore does not depend on a hit's `_index`. Validate the resolved name and cursor generation, handle a missing/deleted generation as restart/not-ready, and ensure generations cannot be deleted and recreated under the same identity. A switch of the alias between A and B cannot mix generations when both are pinned. Whether an alias switch forces an immediate restart or permits completion against a retained old generation must be a stated service policy; for the current restart semantics, verify the active generation with an authoritative, non-stale read at the response/continuation boundary and restart on mismatch. A cached alias lookup or the existing `generationOf` zero-hit fallback alone is not proof of the generation actually searched. [Aliases](https://docs.opensearch.org/latest/im-plugin/index-alias/) can switch atomically but do not make two separate searches a snapshot.

The signed cursor binds operation, normalized request and viewer, Global/question, the native eligible epoch (including null), physical generation, phase, and the raw native sort tuple _of the last consumed hit in that phase_. Validate arity/types and preserve the engine's returned values, including missing-name representation; never reinterpret an A tuple as a B tuple. Represent B at its start explicitly without an `after` tuple. The phase also prevents going back to A after the boundary. Authenticate and expire the token as existing [cursor.ts](../../services/kernel/src/search/cursor.ts) does for request and generation. Do not infer current public eligibility from the index.

One bounded round can search A first if still in A, then B with the remaining bounded candidate quota if A is demonstrably exhausted; otherwise the B request is `size: 0` for its total. In B, use `size: 0` for A and the bounded B hit request. Thus there are at most two phase searches in a round, including count-only requests, and the sum of returned candidates fits the service's existing per-round cap. A search returning fewer than requested and all returned hits consumed proves fixed-state exhaustion; an exactly full batch does not, even if its last hit happens to be the last match. An additional bounded round may be needed to discover the boundary. If A is exhausted after yielding fewer hits, start B without an A `search_after`; if the page ends exactly at the boundary, a phase-start B cursor is valid. A count-only response cannot prove that the remaining A suffix is exhausted.

Run current disclosure and figure checks on a bounded batch. Consume every rejected candidate and advance to its raw tuple; once the requested page is full, stop before the next acceptable lookahead, while rejected lookahead can still be consumed. Leave any fetched but unconsumed acceptable hit for the next request by retaining the preceding consumed tuple; if no B hit was consumed, retain the explicit B-start state. If the bounded refill budget expires, return the permitted partial page and continuation, including a phase-start state when necessary. A per-figure loss of public eligibility or changed score/revision witness rejects a numeric A hit; do not expose its old score, mutate its tuple to an unscored key, or silently add it to B. It becomes safely placeable there only after index convergence or another globally ordered design. This can temporarily omit a valid unscored subject, so it cannot satisfy exact _current-source_ completeness. B hits also need normal current disclosure checks. The present [service.ts](../../services/kernel/src/search/service.ts) already consumes rejected hits and bounds rounds, but does not implement these phase and figure rules.

For cap C, request each phase's total with a threshold sufficient to establish C (the current C is 10,000); ignore `search_after` for total accounting. For phase totals `(a, ra)` and `(b, rb)`, set `v = min(C, a + b)`. Return exact only when both relations are `eq` and `a + b <= C`; otherwise return `v` as a lower bound. An `eq` sum equal to C is exact; a `gte` at C is not. Two `gte` values are lower bounds, not exact counts, even when their sum is below C. Never sum a missing or failed total as zero. Both totals are needed even when only one phase supplies hits. This is an honest capped total for the **fixed indexed candidate set**, not a proof of current authorized/eligible matches. If current figure validation, disclosure rejection or unresolved relation overflow makes that count unsafe, follow the existing conservative lower-bound behavior based on actually disclosed results and retain its inexact state in continuation; do not subtract only observed rejections and call the remainder exact. Aggregation/overflow queries must account for U across both phases, not only the currently paged phase.

## Changes during a request or traversal

Read the native selected state before the searches and verify it again before response; bind it on continuation and restart when it differs. A change from E1 to E2 between requests or phases invalidates the combined result. An end check is detection, not isolation: it does not prove that the index, individual figures, or native state stayed fixed between observations. A matching nullable epoch at both ends means only that the _current ordering predicate_ is the same at those observations. In particular null → eligible → null has the same all-unscored current order at both endpoints, but the nullable value does not prove there was no intervening eligibility or publication. A stronger requirement to detect every such transition needs an additional monotonic native transition/version history, sampled and bound with appropriate atomicity; it is not present in this proposal. Similarly, non-reused eligible epochs are required to detect E1 → another eligible prior → E1 by equality. Even a transition counter would not freeze documents or prove every per-figure state.

With no PIT, two searches can observe different refreshes and phase counts need not describe one instant: a document moving from A to B between requests can be counted twice, or missed if it moves the other way. A before/after epoch check does not detect same-epoch projection updates. Therefore the capped-sum proof applies only to the fixed-state assumption; for live operation do not present the sum as an exact or guaranteed lower bound of a single instantaneous union without additional snapshot/immutable-generation machinery or a separately justified conservative count. Key movement during continuation can also cause duplicates or omissions, even with a signed cursor and stable tie breaker. Neither this design nor the conditional script promises duplicate-free traversal under updates.

## Cost and recommendation

Native filters and native doc-value field sorts avoid executing the conditional rating script for each matching candidate. They do **not** make search O(1): matching, predicate evaluation, per-match native sort/collection, top-k selection, shard coordination and merge can grow with engine work; exact counts can visit all matches. Two queries can evaluate the common text/filter twice and may be more expensive than one script query for some distributions; a `size: 0` count still has engine work. Index layout and engine optimizations may reduce work, but there is no general constant bound. Separately, bounded page sizes, source batches and refill rounds cap returned candidates and application/source work, not the matching population or engine CPU. Neither this report nor the other report supplies benchmarks.

Recommend the manager adopt native phases as the default **if** the indexed-state order, producer invariants, conservative live totals, bounded phase protocol and current-public-figure revalidation are adopted together. It avoids a script on matches while preserving the fixed-state sentinel ordering, at the cost of a second query, more cursor states, and harder count/boundary handling. The conditional-script alternative has one query and simpler unified `search_after`, but per-match script cost and script operational controls. Immutable published generations or a snapshot mechanism are alternatives for a stronger stable traversal; they add lifecycle and retention costs and are outside this candidate. Benchmark broad and selective queries, mixed epoch distributions, multiple shards, count-only requests and page boundaries before choosing on cost.

Implementation verification should cover the partition truth table including null/zero and stale values, producer rejection of bad cardinality/numbers, missing names and raw tuple round trips, tied keys across shards, all quota and lookahead boundaries, rejected hits, phase-start continuation, exact and lower-bound totals, timeout/partial failure, zero hits, alias switch and physical deletion, epoch changes during both requests, null → eligible → null, and live index movement. These are proposed follow-up checks, not evidence that an engine test has passed here.
