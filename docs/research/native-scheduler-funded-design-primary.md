# Native autonomous discovery: funded design and admission limits

Research date: 2026-11-02. Repository source pin:
`129bf1ff7be77f5ceec93f503d77ba870bcea9d6`.

## Finding and recommendation

The adopted accounting boundary is coherent: Work can own a finite autonomous
invocation without possessing a Source maintenance frame. The complete class is
**not yet production-admissible from the available bodies and authority**. An
agreed payer is not a price, and an installed writer fence is not a discovery
index, an inventory removal hook, or an autonomous Source mutation capability.

This report supplies a concrete candidate protocol, its SQL shapes, durable
progress rules, call-site integration, and the prices that can actually be
derived. It also identifies exactly where a full finite inclusive price cannot
be supplied. Those entries are unavailable, never zero. In particular:

- The original native deletion method has an unlimited retry wrapper. Even a
  one-ID call has no finite maximum number of dispatched attempts in that body.
- The 139-row History certificate is conditional on a particular inspected
  execution. It is not a bound on every workflow reachable by normal retention.
- Existing Source-owned History callbacks require the original Source authority
  and aggregate. No autonomous owner-approved replacement callable is supplied
  by the accounting dispositions.
- Original native text/input domains do not have the small universal byte limits
  necessary to turn the candidate's row counts into the requested literal byte
  grant. New index-key restrictions would be a compatibility decision.

Recommend a global per-queue Session directory with commit-ordered finite epochs,
four exact application/version head probes, and a separate creation-ordered
retention summary. This avoids version fanout and bounds each queue discovery
step. The retention construction below is a correctness-oriented candidate with
an explicit large cost; it is **not a claim to fit the frozen physical allowance**.
Do not admit an implementation on the strength of the metadata counts alone.
First obtain the missing owner compositions and a complete executable price
declaration; retain the stopped implementation and all original proof obligations.

The counterexamples here reject particular existing bodies or candidate designs.
They do not establish universal impossibility of funded native scheduling.

## Native semantics that the design must preserve

For a named worker, application scope is its exact application **or SQL NULL**.
Nameless native application scope has different, broad semantics; it must not be
implemented by treating an empty application string as an ordinary named bucket.
Nulls below are tagged values, not sentinel text that can collide with input.

For the current native version `v`, latest means the latest registered version
among the worker application's own and unclaimed version rows, or no registered
version. Named peer applications do not demote it. If latest, ENQUEUED candidates
may have `application_version = v OR application_version IS NULL`; otherwise only
exact `v` is eligible. The SDK's two owner-specific latest-version probes already
avoid a residual scan through another application's version history
(`system_database.js:1049–1077`). Preserve their ordering/tie behavior.

All non-ENQUEUED states are excluded from queue selection. DELAYED activation,
SUSPENDED/resume, recovery, cancellation, terminal completion, and administrative
version/application changes maintain the structure when their actual native
transition occurs. A stored queue name on a non-ENQUEUED row is not eligibility.
The original partitioned selector also requires a non-null partition key;
preserve that exclusion. Null application/version eligibility does not authorize
claiming a null-partition-key row through the partitioned path.

For partition concurrency one, **any PENDING row for `(queue, Session)` vetoes a
claim**, across applications and versions. Do not put application/version filters
on that veto. Compare compatible ENQUEUED heads in native priority then creation
order. Native unspecified ties may gain an ID tie-breaker, but priority/creation
comparisons cannot be reversed. No cross-Session random distribution, global FIFO,
or cross-Session priority promise is required. Nonpartitioned native selection
retains its compatible priority/creation ordering.

Use the actual native partition advisory lock, fixed-ID row lock, current owner
token, and conditional recheck. A hash collision may cause a paid busy result;
it must not merge Session identities. A stale candidate, a row skipped because
it is locked, a migration gap, or an exhausted paid step is not empty.

Retention has a different contract: return eligible results in original creation
order. For fixed invocation time `T`, days `D`, and `C = T - D*86,400,000`, both
`created_at < C` and `completed_at < C` must hold. Completion must be non-null.
Terminal means exactly SUCCESS, ERROR, CANCELLED, or
MAX_RECOVERY_ATTEMPTS_EXCEEDED. Application scope remains own-or-null, days stay
7–365 inclusive/default 30, batch size stays 1,000, and the sweep retains its
60-batch bound and fixed original time. The existing adapter subtracts one
millisecond because native list cutoffs are inclusive. Do not round to days or
substitute completion-first order.

The exact original scheduler is at upstream `wfqueue.ts:716–1023`; installed
distribution `wfqueue.js` has the same relevant call chain. `pollQueue` presently
returns a contention boolean. The selectors return ID arrays. Both interfaces
must carry additional result information; an independent new wrapper that the
actual runner never calls would not implement the contract.

For unbounded native queue-catalog population, replace `Array.from(states)` and
the due-queue sort with a persistent due directory indexed by
`(next_poll_at,qid)`. One control admission peeks one due key, locks that fixed
control row with NOWAIT, and conditionally assigns a finite dispatch lease.
After settling that control call, `runQueuePoll` performs its distinct ordinary
admission for the leased queue. Its completion conditionally updates the due
time and releases that lease through a separately priced control transition.
An expired lease is reclaimed by another bounded control transition with exact
generation recheck. Neither control call re-admits an exhausted discovery body.

Queue registration/deletion/configuration maintains that directory at the real
SDK writer. Reconciliation visits one catalog key per committed paid step;
new registrations behind its keyset frontier maintain their own entry through
that hook. Initial coverage uses the same hook/barrier rule as status coverage.
An unknown queue configuration refuses before its selector I/O. Changing a
queue between partitioned and nonpartitioned invalidates its projection layout
and requires bounded repair before trust; it cannot reinterpret existing Session
aliases silently. Keep only active leased lanes in the runner's working set.
At most the existing lane limit runs concurrently, but issued admissions and
control/catalog row work still require their own complete prices. This is the
concrete change needed at `schedulerLoop`/`scheduleDueQueues`, rather than hiding
a catalog-sized sort or `listQueues` read outside the funded invocation.

Supported placement is the existing unsharded kernel/native schema on the same
physical database and actual Pool. Sharded `dequeueScopes` cannot be called and
then treated as a constant one-element scope. This report grants no sharded or
moved-home support. Native queue configurations beyond the mounted definitions
still require declared bodies; an unpriced rate/concurrency branch must refuse,
not silently use the old unlimited selector.

### Reservation lifetime and default admission

The following is an interface/design, not an installed port:

```ts
type Axes = { rows: bigint; points: bigint; statements: bigint; bytes: bigint; engineRequests: bigint };
type NativeCall = Readonly<{ invocation: object; pool: Pool; deadline: number }>;
type Plan = Readonly<{ kind: string; manifest: string; ceiling: Axes }>;

class WorkDiscoveryIssuer {
  // Work owns this instance; callers cannot manufacture a valid invocation.
  private live = new WeakMap<
    object,
    { pool: Pool; deadline: number; remaining: Axes; active: boolean; manifest: string }
  >();

  admit(plan: Plan, actualPool: Pool, originalDeadline: number): NativeCall {
    requireProductionCallerAndCompleteManifest(plan); // no optional callback
    requireFiniteFutureDeadline(originalDeadline);
    requireFiniteComponentwisePrice(plan.ceiling); // unavailable != zero
    const invocation = Object.freeze({});
    this.live.set(invocation, {
      pool: actualPool,
      deadline: originalDeadline,
      remaining: plan.ceiling,
      active: true,
      manifest: plan.manifest,
    });
    return Object.freeze({ invocation, pool: actualPool, deadline: originalDeadline });
  }

  spend(call: NativeCall, actualPool: Pool, dispatch: string): void {
    const f = this.live.get(call.invocation);
    require(f?.active && f.pool === actualPool && actualPool === call.pool);
    require(f.deadline === call.deadline && Date.now() < f.deadline);
    const price = completeInclusivePrice(f.manifest, dispatch);
    require(price !== undefined && componentwiseLE(price, f.remaining));
    f.remaining = subtract(f.remaining, price); // debit BEFORE affected I/O
  }

  settle(call: NativeCall): void {
    const f = this.live.get(call.invocation);
    if (f) f.active = false;
    this.live.delete(call.invocation); // no refund or retained token
  }
}
```

Use the existing epoch-millisecond operation-deadline convention consistently,
including native maintenance and Source APIs. A monotonic duration can bound a
wait, but cannot be compared directly with that absolute deadline or used to
renew it.
Do not reinterpret a trusted domain `KernelClock` as an operation deadline.

Default production admission is a mandatory branch in `runQueuePoll` and the
real maintenance registration, not an optional test injection. Its plan selects
a complete manifest for one discovery step or one complete maintenance body.
The issuer allocates that full finite maximum once. Child debits consume that
allocation; an inclusive parent's allocation is not a second charge for the
same dispatch. Actual dispatch debits must include every nested trigger/hook.
No dispatch happens unless its complete registered price fits.

Reserve failure cleanup before BEGIN/checkout, including the possible ROLLBACK.
An ambiguous commit stays charged. A retry spends another full attempt from the
same live invocation and same original deadline. If no full attempt fits, return
incomplete or the original error without further I/O. Refund, balance reset,
deadline reset, and automatic re-admission inside that call are prohibited.

Only a later ordinary scheduler dispatch can request a distinct invocation.
Incomplete is scheduling information, not permission to replenish an exhausted
attempt. Operational admission also needs finite issued work over time and fair
service of due queues/repair: one paid transition per due dispatch is a concrete
default policy, with issuer refusal when its configured service budget is spent.
The numerical service budget cannot be selected until the full prices below are
available. A factory with no usable default price is fail-closed scaffolding,
not a delivered autonomous scheduler.

Do not export an ambient Work ALS getter to Source code. Pass the opaque native
capability through the SDK runner, system database call, and internal query
dispatch adapter. If an internal callback needs context, scope it to that exact
native call and invalidate it before dispatching user workflows. Capturing it
in a timer or reusing it after settlement must fail. Existing Source ALS remains
separate and keeps its exact `current.getStore() === frame` check.

## Concrete queue structure without version fanout

A useful simplification is to iterate a **global Session directory for a queue**,
not an eagerly materialized ready set per version. Incompatible Sessions cost
paid steps. That is now permissible and eliminates the O(V) wake-up problem.

Store a Session while it has any ENQUEUED native row, regardless of application
or version. Keep its ticket unchanged while that count stays positive. If a
Session is continuously eligible in a particular domain, this global membership
is continuously present even when its eligibility moves between null and exact
version/application buckets. Separate per-bucket tickets would not prove that
property under adversarial membership switching.

Illustrative additive DDL follows. `qid`, `sid`, `aid`, and `vid` are exact
owner-bound aliases, not truncated strings or collision-assumed hashes. Their
byte-safe resolution is an explicit outstanding item below. Null uses a tagged
alias. A nonpartitioned queue uses one distinguished synthetic Session alias;
it does not acquire the partitioned PENDING veto.

```sql
CREATE TABLE dbos.discovery_domain (
  singleton boolean PRIMARY KEY CHECK (singleton),
  restore_id uuid NOT NULL, layout_id uuid NOT NULL, hook_id uuid NOT NULL,
  coverage_state text NOT NULL, coverage_after text,
  coverage_generation uuid NOT NULL
);
CREATE TABLE dbos.discovery_queue (
  qid bigint PRIMARY KEY, revision_generation uuid NOT NULL,
  revision bigint NOT NULL, first_segment uuid NOT NULL,
  tail_segment uuid NOT NULL, tail_ticket bigint NOT NULL
);
CREATE TABLE dbos.discovery_segment (
  qid bigint NOT NULL, segment uuid NOT NULL, next_segment uuid,
  PRIMARY KEY (qid,segment)
);
CREATE TABLE dbos.discovery_session (
  qid bigint NOT NULL, sid bigint NOT NULL, enqueued_count bigint NOT NULL,
  segment uuid NOT NULL, ticket bigint NOT NULL,
  PRIMARY KEY (qid,sid), UNIQUE (qid,segment,ticket),
  CHECK (enqueued_count > 0)
);
CREATE TABLE dbos.discovery_item (
  workflow_uuid text PRIMARY KEY, qid bigint NOT NULL, sid bigint NOT NULL,
  aid bigint NOT NULL, vid bigint NOT NULL,
  priority integer NOT NULL, created_at bigint NOT NULL,
  source_revision uuid NOT NULL
);
CREATE INDEX discovery_head ON dbos.discovery_item
  (qid,sid,aid,vid,priority,created_at,workflow_uuid);
CREATE TABLE dbos.discovery_frontier (
  domain_id uuid PRIMARY KEY, qid bigint NOT NULL,
  restore_id uuid NOT NULL, layout_id uuid NOT NULL, hook_id uuid NOT NULL,
  worker_application_alias bigint NOT NULL, worker_version_alias bigint NOT NULL,
  epoch_id uuid NOT NULL, segment uuid NOT NULL, after_ticket bigint NOT NULL,
  end_segment uuid NOT NULL, end_ticket bigint NOT NULL,
  start_revision_generation uuid NOT NULL, start_revision bigint NOT NULL,
  start_version_generation uuid NOT NULL, all_checks_authoritative boolean NOT NULL

```

Build indexes on initially empty projection tables, then populate them by paid
steps. A new native status index built over all history is not a bounded migration
just because a later SELECT uses it. Existing native primary indexes can locate
one old row at a time during coverage. The exact PENDING veto needs an equality
prefix index or a separately covered projection of all PENDING rows; without
either, it too is unavailable. A covered PENDING projection must include _all_
applications/versions and participate in the same transition/erasure protocol.

### Commit-ordered tickets and finite epochs

Allocate a new Session ticket while holding `discovery_queue`'s row lock, keep
that lock through the native transaction commit, and update membership in the
same transaction. The epoch-start transaction takes the same allocator lock
before capturing its finite tail `(segment,ticket)`. Thus a new lower ticket
cannot commit later behind the frontier. `nextval()` plus `MAX(ticket)` does
not have this property: PostgreSQL sequence allocation is not commit ordered.

Use linked finite ticket segments. When a signed bigint ticket is exhausted,
append one new UUID segment under the allocator lock and start its ticket at
one. Do not wrap a ticket in place. An epoch captures the current tail segment
and ticket, then follows the existing segment chain only as far as that tail.
Moving to the next segment is a separately priced bounded step. New segments
cannot extend an old epoch. This avoids a lifetime counter overflow becoming
a population/version cap. Empty segment metadata contains no Session identity;
its eventual cleanup is still paid, owner-classified work.

On restart, use the committed frontier. Cursor advance and any claim commit
together. A crash before commit may repeat one paid candidate; it cannot commit
a claim while losing its associated cursor progress. Epoch rotation is another
paid transition, never an unlimited loop after a miss.

Arrivals append membership after the epoch tail. Removal deletes that membership
atomically; re-entry from zero gets a new ticket. Changes to priority, version,
application, or PENDING state increment one queue revision without enumerating
consumer versions. Version registration updates a shared version-generation
record, not all queue/domain frontiers. Revision overflow rotates its generation
under the same lock; an equality proof compares both fields.

Frontiers bind restore, hook, layout, queue, application, native version, and
coverage generation. Any mismatch invalidates an empty proof. Restart does not
restart a compatible epoch; an actual domain/version transition creates a new
domain frontier. Old incompatible frontiers cannot claim or certify empty.

### One candidate transition

```text
queueStep(call, domain):
  prepay complete admitted transition, including rollback and native descendants
  BEGIN; set statement/lock deadlines from call.originalDeadline
  validate exact Pool, layout, hooks, restore generation and complete coverage
  lock this domain's frontier (NOWAIT); on conflict return paid incomplete
  if epoch not started: capture allocator tail; persist start; COMMIT; incomplete
  read at most ONE next directory entry before the captured tail
  if segment exhausted: persist one segment transition; COMMIT; incomplete
  if epoch exhausted: run the closing proof below; COMMIT; return its result
  read the two native own/null latest-version probes for the initial predicates
  probe at most four exact compatible heads for this Session; merge <=4 scalars
  probe global PENDING(queue,Session) if partitionConcurrency=1
  if no head or veto: advance cursor; COMMIT; incomplete
  try original native partition advisory lock (partitioned path)
  lock ONLY the chosen native workflow ID with FOR UPDATE SKIP LOCKED
  if either fails: record nonauthoritative epoch; advance; COMMIT; incomplete
  re-read latest-version identity and exact compatible heads after locks
  recheck fixed ID, status, queue, Session, application, version, priority/creation
  conditionally UPDATE that fixed ID with a fresh native owner_xid
  maintain every old/new projection and native writer fence in this transaction
  advance frontier; COMMIT
  return claim(workflowID,owner_xid) only if the conditional update succeeded
```

The two application alternatives times the two latest-version alternatives give
at most four equality-prefix probes. Nonlatest uses at most two; identical/null
alternatives are deduplicated. Nameless/all-application operation needs a
separately ordered covered head index with application omitted, rather than
enumerating applications or pretending that four probes cover arbitrary owners.

Query shape for one exact component:

```sql
SELECT workflow_uuid,priority,created_at,source_revision
FROM dbos.discovery_item
WHERE qid=$1 AND sid=$2 AND aid=$3 AND vid=$4
ORDER BY priority,created_at,workflow_uuid LIMIT 1;
-- Never residual-filter application/version after an overfetch LIMIT.

SELECT workflow_uuid FROM dbos.workflow_status
WHERE workflow_uuid=$1 FOR UPDATE SKIP LOCKED;
-- This is a fixed candidate, not a growing ordered SKIP LOCKED scan.
```

The conditional claim repeats membership/ownership/version predicates at the
native write. A compatible earlier head found on recheck causes incomplete,
not a claim of the later row. All claimers use the native partition lock. New
maintenance cannot bypass native `owner_xid` checks on completion. The original
writer-fence guard remains active on claim and all later output/status writes.
Concurrent enqueue/priority changes must serialize or be linearizable before or
after the conditional head check; this requires the actual covered writer hook,
not an assertion that advisory locks automatically constrain ordinary writers.

Never hold a directory lock and then wait indefinitely for a native status row.
Old row writers already take native row locks before row triggers. Fixed-ID
SKIP LOCKED/NOWAIT acquisition, finite lock deadlines, and consistent ordering
of multiple old/new Session metadata locks prevent an unbounded lock scan;
conflicts/aborts stay charged. Exact serialization with all old native writers
is a required implementation proof, not established by this pseudocode.

### Three outcomes and closing proof

| Outcome      | Required evidence                                                                    | Scheduler action                                                         |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| `claim`      | Native conditional claim committed with owner token and frontier                     | Dispatch after leaving discovery authority; retain later fair discovery. |
| `incomplete` | Bounded paid step, including no head, busy, conflict, uncovered data, or budget stop | Keep a future ordinary due opportunity; do not terminate a drain.        |
| `empty`      | Authoritative complete-domain proof at a defined native instant                      | May apply ordinary empty backoff; never erase future scheduling.         |

Epoch exhaustion alone returns incomplete. For an authoritative empty result,
the closing transaction locks the queue revision control row and version-control
generation, obtains a fresh Read Committed observation, and verifies:

1. coverage/layout/hook/restore identities still match;
2. every directory ticket in the captured finite epoch was examined;
3. no lock skip, unresolved candidate, failed conditional claim, or uncovered
   observation made the epoch nonauthoritative;
4. queue and version generations/revisions equal those at epoch start, so no
   predicate, membership, or PENDING-gate transition invalidated earlier checks;
5. there is no membership after the captured tail in the closing observation.

All writers affecting those predicates must participate in the revision lock
protocol. The proof linearizes while those control locks are held. A pending
writer blocked from committing is later work. Under continuous mutations this
proof may repeatedly return incomplete; that is honest. An empty-compatible-head
proof can be stricter than necessary and still correct. Local capacity zero is
incomplete/no-capacity, not native empty. Engine locks without logical mutation
cannot be ignored: an epoch containing a lock skip cannot certify empty.

For fairness, fix a compatible domain with repeated ordinary paid admissions,
finite committed state at each captured tail, and eventual sustained availability
of the required locks/capacity. A continuously eligible Session keeps one global
ticket. A frontier advances over finitely many earlier tickets per epoch; new
arrivals cannot lengthen that epoch. It therefore receives another candidate
opportunity in finitely many committed steps. Repeated restarts preserve that
progress. This proves opportunity, not completion within one poll or a wall-clock
bound. Mere instantaneous lock availability chosen adversarially between every
probe cannot imply liveness for any polling algorithm; fair admission/lock
service or eventual sustained availability is the operational premise.

## Creation-ordered retention candidate

An ordinary `(application,created_at)` index still walks the old ineligible
prefix in the inversion fixture. `(application,completed_at,created_at)` changes
the output order or sorts an arbitrarily large completed backlog. Neither is
the required repair. Do not cache a last-created cursor across retention runs
and permanently skip an old workflow whose completion later becomes eligible.

One implementable, deliberately explicit alternative is a fixed-depth creation
radix with minimum-completion summaries. This supplies a finite candidate to
price, not a claim that PostgreSQL supplies this structure automatically.

Map signed native `created_at bigint` to its unsigned-order 64-bit bit pattern
by flipping the sign bit. Use `bit(64)` or two int32 words in SQL; do not convert
all bigint values to lossy JavaScript Number. Store one summary path of depths
0 through 64 for each application bucket. A leaf represents one exact creation
timestamp; its value is the minimum non-null completion of all terminal rows at
that timestamp. An internal node stores the minimum of its two children.

```sql
CREATE TABLE dbos.retention_item (
  workflow_uuid text PRIMARY KEY, aid bigint NOT NULL,
  created_at bigint NOT NULL, completed_at bigint NOT NULL,
  source_revision uuid NOT NULL
);
CREATE INDEX retention_leaf ON dbos.retention_item
  (aid,created_at,completed_at,workflow_uuid);
CREATE TABLE dbos.retention_node (
  aid bigint NOT NULL, depth smallint NOT NULL,
  prefix bit(64) NOT NULL, min_completed bigint NOT NULL,
  PRIMARY KEY (aid,depth,prefix), CHECK (depth BETWEEN 0 AND 64)
);
```

Only the four terminal statuses with non-null completion contribute to
`retention_item`. For a created timestamp below cutoff, descend in creation
order, pruning any subtree whose minimum completion is not below cutoff.
Subtrees wholly above the creation cutoff are also pruned. At a leaf, an exact
`(aid,created_at)` completion-prefix seek returns only completion-eligible IDs.
Thus the leaf's completion ordering breaks creation ties only. Merge own/null
application results by creation. Do not read payloads to discover IDs.

```text
retentionSelect(T,D):
  C := exact original T - D*86,400,000; validate D in [7,365]
  for the two application roots, in one paid native selection body:
    traverse the finite creation radix left first
    prune ranges with created >= C or min_completed >= C
    at each eligible leaf, seek completed < C and emit IDs in that creation group
    stop after at most 1,000 IDs per root, retaining their creation keys
  merge the at most 2,000 results and take the first 1,000
  fixed-ID recheck original native status/application/creation/completion
  delete only the eligible prefix using native deleteWorkflows(ids,false)
```

Selection and deletion must not race a rewind/application change. The actual
retention owner needs fixed-ID locks and current writer-state/owner readiness
before removal; a preselected ID is not deletion authority. Permanent native
writer fences survive deletion. Technical retirement cannot manufacture Source
discharge. If native deletion opens its own transaction, an outer selection lock
on another connection is not a same-transaction guard; the native owner port must
accept the guarded composition or acquire/recheck inside its actual transaction.
No such complete retention composition is installed at this pin.

A changed terminal row updates old and new contributions in the same native
transaction. Recompute a changed leaf with one exact minimum-completion seek,
write/delete that leaf, then recompute each ancestor from its two child rows.
Retirement/deletion removes the contribution and recomputes ancestors before
commit. Rewind, cancellation, application changes, completion overwrite, and
restore all use this same old/new transition. Removing the last account-bearing
leaf must remove its value; an empty placeholder must not retain workflow IDs.

### Literal size and the physical-limit warning

The depth 64 comes from the native bigint field, not a chosen history cap.
For **one** changed leaf, this simple body performs:

| Operation                                                    | Logical rows | Point/range starts | Native statements, including nested SQL |
| ------------------------------------------------------------ | -----------: | -----------------: | --------------------------------------: |
| Read new minimum at exact creation leaf                      |            1 |                  1 |                                       1 |
| Write/delete leaf summary                                    |            1 |                  1 |                                       1 |
| Read both children, write parent, repeated at 64 levels      |          192 |                192 |                                     128 |
| Total excluding transaction/root locks and original mutation |      **194** |            **194** |                                 **130** |
| Old and new distinct leaf paths                              |      **388** |            **388** |                                 **260** |

Each level uses one SELECT of at most two full keys and one UPSERT/DELETE.
Missing children still consume their two point starts. A failed ancestor update
does not refund earlier levels. A single deletion of 1,000 distinct creation
leaves can therefore add 194,000 logical row operations and 130,000 nested
statements, before original deletion costs. Shared ancestors can reduce actual
work; a price cannot assume that reduction without a different batched body.

A conservative literal traversal limit for one root returning at most 1,000
IDs is `1 + 2*64*(1000+1) = 128,129` node reads, allowing a final unsuccessful
search path; for two independent roots it is **256,258**. Leaf row output adds
at most 2,000 rows and two root-start operations. These are design-visible
operations, not excluded MVCC visibility. A server-side function does not turn
its nested point probes into one free statement or one free index descent.

This candidate removes dependence on unrelated history at fixed bigint width,
but its literal constants are large. It has **not** established compatibility
with the retained `indexProbes: 4000` physical allowance. The allowance remains
unchanged; no benchmark has been run, and these counts are not permission to
raise it. A tighter batched/native ordered reporting structure and its complete
writer/removal body would be necessary to recommend this retention construction
for production. This is a limitation of this candidate, not a lower bound on
all creation-ordered two-predicate data structures.

### Short batches and durable continuation

Retention's public batch return remains the number actually deleted. A return
below 1,000 may terminate the existing sweep only after authoritative exhaustion
of eligible results at the original cutoff. An internal selection/repair budget
stop must produce an internal `incomplete` result, not return a short count as
though discovery were exhausted. Persist repair/frontier state and continue at a
later ordinary paid admission. Within one sweep, repeated batches consume the
same original invocation allocation and deadline; they cannot mint allowances.

The frozen warmup/probe fixture requires 1,000 results immediately from its
supported, covered native batch path. Queue's bounded-incomplete amendment does
not authorize changing that retention assertion. If coverage/repair cannot meet
that batch contract, fail visibly as unavailable rather than claim a successful
short batch. A new internal retention result type must be handled by the real
sweep without losing the original count/exhaustion semantics. This remaining
integration is part of the complete class, not a separate interface delivery.

### Bounded coverage protocol

1. Add new empty projection/control tables and their indexes in an additive
   SDK-owned migration. Append a migration; never edit positional historical
   migrations or the frozen acceptance file. Preserve existing native rows and
   permanent fence tables.
2. Install/version all actual native mutation hooks and establish a schema/owner
   barrier against old in-flight unhooked writes. Waiting for that barrier obeys
   the original finite admission deadline; a timeout remains charged. A hook hash
   or a fixture flag without that barrier proves nothing.
3. One paid backfill step peeks one old native primary key after the committed
   keyset frontier, locks that fixed row, reads its **current** projection, applies
   its contribution, and commits the frontier with the effect. New native writes
   are maintained by the installed hook even if their text key sorts behind the
   frontier. A deleted row is a paid miss. Do not use OFFSET.
4. Concurrent updates either serialize with that fixed row or change its stored
   generation so the backfill retries later as another paid step. Each attempt
   reserves its failure/rollback path. Cursor advance cannot certify a stale
   contribution as current.
5. Drain a durable dirty-ticket queue one entry per paid step if compatibility
   repair requires it. Do not append unpriced dirty work from an old writer and
   call that full synchronous maintenance. Dirty entries carry exact generation
   and owner inventory; acknowledgment is conditional on current generation.
6. Publish coverage only after the finite base frontier is exhausted, all needed
   old-row projections are current, the dirty barrier is drained, and hook/layout/
   restore identities still match under the publishing lock. Before that point,
   selectors may report incomplete/unavailable but cannot certify empty.
7. A crash repeats at most an uncommitted step. An actual layout/hook/restore
   mismatch invalidates trust; it does not reset every ordinary restart's cursor.
   Repairs themselves have paged durable progress and priced control work.

Keyset backfill has bounded work per step using an existing exact primary index;
its total work follows old rows. Building a new index on a populated native table,
an unrestricted validation `COUNT(*)`, and `UPDATE all due` at startup would each
move the census rather than repair it. PostgreSQL's schema/index DDL and engine
maintenance need their own operational admission; no per-row grant prices an
unbounded index build by labeling it migration.

### Restore and permanent closure

The installed fence migration uses permanent rows with no workflow FK, prevents
DELETE/TRUNCATE, and enables ALWAYS guards on eight native tables. Its guard
checks old/new workflow IDs and changed parent/fork IDs. Restore generation is
separate from permanent per-workflow closure. Retain these properties.

The candidate discovery restore admission must preserve closed fences first,
rotate the restore domain through the existing owner-approved procedure, mark
all old discovery coverage untrusted, and repair using bounded steps. Do not
rotate the permanent closures themselves or reopen them with restored status
rows. A restore unable to preserve those fences fails closed. Coverage promotion
requires both the current restore generation and complete restored-row hooks;
it cannot be inferred merely because a database is reachable.

### Inventory and same-transaction removal

Session keys, workflow IDs, alias bindings, native head projections, retention
leaves, dirty entries, resumable pages, and frontiers that identify an account
or its work are account-bearing copies even when no payload is stored. A numeric
alias or hash is not automatic anonymization. Inventory must associate each copy
with the actual owner-bound native identity and enumerate its removal locations.

For an owner-authorized native removal transaction, remove the per-workflow
projection, adjust/remove Session membership, remove retention contribution,
recompute nonidentifying summaries, and remove/advance identifying dirty and
continuation entries **in that same transaction**. Multiple workflows sharing a
Session do not license removal of another owner's live contribution. Membership
disappears only when its exact count reaches zero. Permanent writer-closure
receipts remain permanent under their original separate authority.

`hasRetainedWorkCopies` currently checks eight native families, not these new
tables. The installed History minimizer's before/after inspections also name
those eight. Both inventories and all original owner callbacks must be extended
by their owners before an all-copy absence receipt can include the new copies.
There is no released autonomous inventory-removal callable for this new schema.
The separate WorkClient pending locator/hook must not be assumed to supply one.
An after-commit janitor or Work-only funding wrapper would not satisfy atomic
owner-authorized removal.

## Literal inclusive accounting

The actual native aggregate type is
`services/kernel/src/semantic/identity-epoch-contract.ts:NativeStepWork`:
`rows`, `points`, `statements`, `bytes`, `engineRequests`.
All five must be finite nonnegative safe integers at the installed Source API.
Use checked arithmetic; an overflowing sum is refusal, not saturation into a
smaller grant. A new internal bigint planner must validate representability
before passing an amount to that API.

Source also owns a **separate** Library ledger with axes `candidateKeys`,
`identityMetadataRows`, `nativeRows`, `nativePoints`, `witnessKeys`, `statements`,
`bytes`, and `emptySeeks`. A composition that reaches Library needs that
ledger's actual declaration as well; native rows do not fund it. Pure native
discovery does not invoke Library. An unknown hook might, so its Library cost is
unavailable until its body is known, not a blanket vector of zeros.

Rows include all design-visible read/write and candidate/trigger work; points
include missing exact seeks and index/range starts. Statements include nested
native SQL and controls, not just JavaScript `query` calls. Bytes include bound
keys, projected/copy data, control/frontier material and transitive conversions
required by the owning accounting contract. `engineRequests = 0` in the existing
native declarations means no request to the separate engine service. It does
not mean zero PostgreSQL B-tree, heap, WAL, lock, or buffer work.

Exclude engine-only MVCC visibility work only on the existing proof boundary.
Do not exclude live incompatible rows filtered by a selector, live locked rows
walked by SKIP LOCKED, summary nodes, trigger rows, or aliases created by this
design. Logical point bounds do not establish a uniform physical buffer bound;
PostgreSQL B-tree descent/split work follows index height and engine state.

The following fixed-slot transition makes the writer side concrete. Add a
`discovery_projection_state(workflow_uuid PRIMARY KEY, source_revision, state,
qid,sid,aid,vid,created_at,completed_at)` receipt, and a covered
`discovery_pending(workflow_uuid PRIMARY KEY,qid,sid)` table with a secondary
`(qid,sid,workflow_uuid)` index. The latter supplies the exact global veto without
a new index build over old native status history. Neither table stores payloads.

```text
applyProjection(tx, OLD, NEW):             # actual native row transaction
  read incorporated receipt by fixed workflow ID
  read old discovery_item by fixed workflow ID
  read old retention_item by fixed workflow ID
  validate incorporated generation/state, or reconcile one uncovered fixed row
  lock at most two old/new queue allocator rows in canonical order
  if incorporated state is ENQUEUED:
    DELETE old discovery_item by fixed ID
    SELECT its old Session membership FOR UPDATE
    UPDATE count=count-1, or DELETE membership when count was one
  if new state is ENQUEUED:
    SELECT new Session membership by full key
    if absent:
      allocate one ticket under held allocator lock
      if ticket segment overflows:
        INSERT one new segment; UPDATE old tail's next pointer
      UPDATE queue tail/ticket                     # one row, also on rollover
    UPSERT membership with exact resulting positive count
    INSERT new discovery_item                     # old item already removed
  DELETE discovery_pending by fixed workflow ID    # paid miss when not PENDING
  if new state is PENDING: INSERT discovery_pending
  increment each of at most two old/new queue revisions
  if incorporated state contributes to retention: DELETE its retention_item
  if new state contributes to retention: INSERT its retention_item
  lock at most two old/new application retention roots in canonical order
  recompute each distinct changed creation leaf and its 64 ancestors
  UPSERT incorporated receipt with exact NEW revision/state
  # DELETE uses NEW=absent and deletes, rather than retaining, identifying receipt
```

The old/new retention root locks above must precede their leaf-summary writes;
they may be acquired earlier with the other canonical metadata locks. All leaf
changes/recomputation remain inside the same transaction. New Session creation
allocates one ticket; an ENQUEUED→ENQUEUED move changes at most two Session
identities but creates at most one new membership. The old membership is not
deleted/recreated when old/new Session and ENQUEUED state are unchanged: update
its head projection in place and preserve its ticket. That fast path only
reduces the bounds below and is necessary for continuous-membership fairness.

At most two source queue revisions change, independent of V. Receipt/state
equality must be checked before counter subtraction. A disagreement does not
trigger an unlimited recount: refuse/promote one paid repair step. The original
native writer guard runs independently; this routine cannot retire or reopen
its fence. Alias resolution, owner inventory, and the guard are outside the
following **metadata-only** counts and remain mandatory additional costs.

For clarity, these counts include primary and the declared secondary index
maintenance starts: deleting/inserting a head item, Session membership, PENDING
projection or retention item has two index starts, not one. Reading two fixed
keys counts two even on misses. Transaction controls belong to the enclosing
native attempt and are added once.

### Native deletion descendants: exact shape, no invented bound

The original native `deleteWorkflows(ids,false)` performs BEGIN, four DELETEs
for input/output/operations/status, COMMIT, and possible ROLLBACK. Status cascades
delete events, event history, notifications, and streams. `false` avoids recursive
child-workflow enumeration; it does not bound these descendant rows.

For a concrete set of `d` workflow IDs, the affected-row operand is:

```text
d_status + d_input + d_output + c_operations
         + c_events + c_event_history + c_notifications + c_streams
```

Each `c_*` is an actual native child population, not a symbolic allowance.
The schema supplies no 64/8/64/0/0 global constraints for them. Consequently
this expression is a **gap inventory**, not a delivered finite reservation.
The owner would need certified exact counters maintained by all child writers,
or a bounded fenced inventory phase, and a native deletion composition priced
from those certified operands. Count reads, counter updates, inventory coverage,
fence acquisition, failed paths, bytes, and all new DELETE hooks are additional.

Example: an otherwise eligible terminal workflow with 65 operation outputs is
permitted by the native operation-output schema. Its operations delete already
exceeds the single-attempt adapter's 64 operand. A terminal workflow with live
notifications or streams also violates that adapter's absence prerequisites.
This does not make legitimate O(d+c) deletion impermissible; it prevents treating
the special inspected History price as a universal retention price.

The original `deleteWorkflowsInternal` is `@dbRetry()`-decorated. In installed
`system_database.js:565–600`, `withDbRetry` is `while (true)` and has no maximum
attempt count; shutdown abort is not this invocation's funding deadline. An
arbitrary number of retryable connection failures therefore produces an
arbitrary number of charged BEGIN/DELETE/ROLLBACK attempts. For any proposed
finite grant of S statements, choose more than S such attempts. This exact
source counterexample defeats a wrapper that charges the method once.

An implementable repair is to make the actual native retry dispatcher consume
the same immutable call's full attempt price before every retry, propagate a
non-retryable funding refusal, and retain the original deadline. It must be on
the real `deleteWorkflows(ids,false)` delegation path. Switching silently to an
unrelated private deletion API would not prove the retained native acceptance.
The existing single-attempt port illustrates the mechanism but does not install
that behavior in the ordinary method.

### Bytes and conditional versus uniform bounds

The original migration declares workflow IDs, partition keys, application names,
versions, and serialized inputs/payloads as text without the proposed small
CHECK limits. `WorkIntent.input.accounts` is not universally length bounded.
The 1,024-byte workflow-ID check in the new writer-state port does not retroactively
bound every old enqueue, completion, retention row or old writer. Class/config
varchar(255) and the worker executor-ID validation are real limits for those
fields only. A bound for one field cannot fund all other columns.

There is a concrete hidden byte body: the installed ALWAYS fence trigger derives
the workflow key using `to_jsonb(NEW)` and, on UPDATE, `to_jsonb(OLD)`. On input,
operation output, event or stream tables, that conversion may materialize the
whole payload even though only an ID is returned. Parameter/return-byte-only
instrumentation would miss it. New discovery hooks must not add another
whole-row conversion and label it a scalar projection.

PostgreSQL documents a 1-GB field ceiling and relation/page limits conditional
on its build ([limits source](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/doc/src/sgml/limits.sgml)).
Those are conditional engine-domain bounds, not a REZICS guarantee of small
keys/inputs. Large text can also exceed a composite B-tree tuple's capacity.
Declaring `(application,version,Session,workflow_id)` in an index is therefore
not a compatible universal key implementation for all admitted old text values.

A collision-free chunked exact-key dictionary could preserve old inputs with
paid bounded chunk steps. Its digest collision verification, ordering, chunk
ownership, removal, restore and byte-copy bodies must then be specified and
priced. A digest-only equality assumption is insufficient. This report does
not assign a guessed key-width operand, an unrelated verifier allowance, or a
1-GB-per-row headroom multiplier and call that an inclusive default grant.

The distinction is material: finite actual input length can support a
per-input price if the entire body is known, but does not prove one uniform
small cost over all original native inputs. Neither a fixed text/version cap
nor rejection of arbitrary previously valid rows is silently adopted here.

## What the established projects demonstrate

Temporal's pinned `RateLimitedScheduler.TrySubmit` checks admission before
submitting and intentionally does not return a token when the downstream
scheduler is busy. That is useful support for charging attempted work. Its
`wait` path, however, can log a failed reservation and continue, and shadow mode
can bypass throttling. `MultiReservationImpl` also supports cancellation/refund.
Those are valid Temporal policies, but are unsuitable defaults for this adopted
fail-closed/no-refund accounting contract. Token rate and task admission do not
derive SQL rows, bytes, or nested owner authority.

Temporal's `queue_base.go` separates a finite readable range from the following
unreadable range using an exclusive high-read watermark. Checkpointing shrinks
completed slices, retains reader scopes, advances deletion only through safe
completion, and persists queue state. Borrow the separation of progress from
completion and the durable watermark pattern. Do not infer that its checkpoint
ordering, retries, or persistence model proves a same-transaction PostgreSQL
claim/frontier protocol for REZICS.

Kubernetes client-go's pinned workqueue maintains separate dirty and processing
sets. Add during processing records dirtiness; Done requeues a dirty item.
That is the relevant lost-wakeup pattern for generation-conditional repair.
It is an in-memory queue, not durable coverage, a commit-ordered epoch, an
invocation ledger, or an all-copy erasure mechanism.

DBOS's actual scheduler already distinguishes running capacity from polls,
keeps older due times ahead of freshly scheduled queues, and binds claims to
owner tokens. Preserve these behaviors while adding explicit outcome/funding
plumbing. Its recursive distinct-Session enumeration and random sort before a
returned limit are the specific discovery body to replace, not an upstream
example of bounded candidate discovery.

PostgreSQL's primary documentation explains that SKIP LOCKED provides an
inconsistent view suitable for queue consumers and that a LIMIT stops locking
after enough rows have been returned. That does not bound skipped live rows.
Use fixed-ID locking after bounded selection. Its Read Committed semantics
provide fresh statement observations and conditional-update rechecks; they do
not make cross-statement head/coverage evidence atomic without a lock/revision
protocol. Its nontransactional sequence behavior is why the candidate uses a
commit-serialized allocator. See the pinned SGML sources and official
[SELECT](https://www.postgresql.org/docs/18/sql-select.html) and
[transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)
documentation.

The shared patterns are admission before the operation, explicit charged
attempts, progress distinct from completion, dirty generation repair, and
durable bounded-range processing. None of these projects supplies REZICS's
inclusive native price or Source permission boundary. Implement the patterns
in the existing TypeScript/pg/DBOS stack; do not copy upstream files or long
passages, introduce a different orchestrator, or execute reference code.
