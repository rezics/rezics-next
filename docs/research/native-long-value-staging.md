# Native staging of long exact type values

Research evidence, inspected 2026-10-27; this is a recommendation for the owning contract, not a change to it. The local [shelf contract](../../services/kernel/src/library/shelf-contract.md) accepts exact ASCII CURIEs without a per-identifier cap, within a 4 MiB release; its collision trie has at most 256 bytes per edge and 100 edges per continuation. The full input remains in a native reservation, and workflow state carries only bounded identifiers and checkpoints. [Type identity research](library-type-keys.md) explains why exact collision handling matters. The two requested temporary schema briefs were not present in this worktree; the published contract and the task's stated requirements are the available schema evidence. No implementation was inspected or assumed to depend on a slicing strategy.

## Recommendation

Keep the required full text in the reservation. In addition, create an immutable, unindexed `bytea` staging copy from the already validated ASCII input once at reservation creation, and set that column's storage strategy to `EXTERNAL` before inserting it. Record its byte length once as immutable scalar metadata. On each continuation, read one `substring(bytes FROM offset + 1 FOR least(25600, byte_length - offset))` from the stored column, then split only that bounded result into successive 256-byte edges inside the native transaction. `offset` is the number of bytes already committed, starts at zero and advances by the actual bytes staged. Do not apply a conversion, cast, concatenation, function that materializes the full value, or text substring to the input before the bytea substring. Keep the original text for exact publication and the existing port contract; do not put either whole representation in DBOS arguments, results or checkpoints.

This is an inference from the source paths below, not a PostgreSQL guarantee about arbitrary expressions or physical I/O. `EXTERNAL` plus **bytea** matters: ASCII content alone does not make PostgreSQL's `text` substring use byte offsets in a UTF-8 database. Create and validate the bytea once in a native step; ASCII has identical byte values in UTF-8, and a known source encoding must be used explicitly. Bind or compute it from the same immutable accepted input, never from an untrusted independent argument. For example, `convert_to(full_input, 'UTF8')` is suitable once where the database encoding and input contract make that conversion exact; it is not suitable inside every page. The additional representation costs O(L) space and initial conversion, rather than imposing a new input limit. A schema change is required even if the reservation already has text and an offset. Configure storage on the actual sliced column and verify the representation of newly written data; `SET STORAGE` does not retroactively rewrite old compressed values. Do not make correctness depend on `pg_column_size` proving compression or externalization.

At completion, publish the exact retained text and terminal together in the existing native transaction. A one-time O(L) final read/copy and any required exact check are consistent with linear total bytes, but must not be repeated on every continuation. If a bounded final transaction must exclude even that O(L) copy, the owner must choose a different publication representation; this recommendation bounds staging pages, not input acceptance or final publication. The normal root-miss and exact-primary comparison work also remains O(L); the collision path does not make that work disappear.

## Verified PostgreSQL behavior

The documentation describes [TOAST](https://www.postgresql.org/docs/17/storage-toast.html): `EXTENDED` permits compression and out-of-line storage, while `EXTERNAL` permits out-of-line storage without compression. Out-of-line values are stored in chunks indexed by value and sequence, with a small pointer in the main row. Values can remain inline; EXTERNAL does not force every value out of line. [ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html) documents that changing storage affects future operations and does not itself rewrite existing rows. Unchanged out-of-line attributes are normally retained during updates. [Binary substring](https://www.postgresql.org/docs/17/functions-binarystring.html) uses byte positions; [text substring](https://www.postgresql.org/docs/17/functions-string.html) uses character positions. SQL positions are one-based. PostgreSQL documentation and source use the [PostgreSQL licence](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/COPYRIGHT).

The following are observations of PostgreSQL source at pinned commit [`700b422af7e26cf310caf3fb76d78f4c8ca39c1f`](https://github.com/postgres/postgres/tree/700b422af7e26cf310caf3fb76d78f4c8ca39c1f), read from the cached `.reference/library-shelf-maintenance/postgres` clone, without running it. This snapshot is not a claim that every deployed PostgreSQL version has identical internals; verify the deployed version and access method. The versioned documentation above is PostgreSQL 17.

- [`src/backend/utils/adt/bytea.c`](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/src/backend/utils/adt/bytea.c) implements bytea substring through `DatumGetByteaPSlice` at the requested zero-based byte offset. Explicit finite nonnegative length and safe integer arithmetic matter: an omitted length or overflow can request the remainder.
- [`src/backend/access/common/detoast.c`](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/src/backend/access/common/detoast.c) takes the non-compressed on-disk external fast path to `toast_fetch_datum_slice(offset, length)`. That allocates the requested result and calls `table_relation_fetch_toast_slice`. Inline ordinary data is already in the main tuple and the requested segment is copied; inline compressed data is decompressed through the requested end. Expanded or indirect in-memory values have other paths. A direct stored-column reference is important to preserve the on-disk pointer.
- [`src/backend/access/heap/heaptoast.c`](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/src/backend/access/heap/heaptoast.c) maps the offset and end to TOAST chunk numbers and uses the `(valueid, chunkidx)` index for equality or a range, checks the selected chunks and copies only the requested portions into the result. For chunk payload size C and a nonempty B-byte slice at offset o, it reads `floor((o+B-1)/C) - floor(o/C) + 1` logical chunk tuples, not every preceding chunk. Actual page reads, cache, index traversal, MVCC, dead tuples, WAL and lock waits are not bounded by this logical-byte calculation. C is a build/type-dependent internal constant, not an API-sized promise; the docs describe typical chunks of about 2 kB.
- With compressed external data, the same detoast code must start from zero to decompress through the requested end. PGLZ bounds the compressed prefix needed for that end; LZ4 fetches the entire compressed datum in this source. Repeated later pages can therefore reread and decompress growing prefixes, or read the entire compressed value each time. `EXTENDED` is insufficient for a worst-case linear bound, even if incompressible test inputs happen not to compress.
- [`src/backend/utils/adt/varlena.c`](https://github.com/postgres/postgres/blob/700b422af7e26cf310caf3fb76d78f4c8ca39c1f/src/backend/utils/adt/varlena.c) uses direct offset slicing for text only when the **database encoding's maximum character width** is one. For multibyte encodings it requests a conservative prefix from byte zero and scans characters, even if this particular value is all ASCII. Thus `substring(full_text, ...)` in UTF-8 can be quadratic even with EXTERNAL. `octet_length(text)` instead uses `toast_raw_datum_size` and reads the raw size from the external pointer or compressed header without fetching the value; `length(text)` may detoast and scan in multibyte encodings. Read stored immutable length metadata in continuations, not an equality test or `length(text)` over the input.

## Cost and alternatives

Let L be input bytes, E = ceil(L/256), P = ceil(E/100) = ceil(L/25600), and Bᵢ the actual nonempty slice on page i. With one bytea slice per page, sum Bᵢ = L. Each page returns/copies at most 25,600 payload bytes into the native transaction, splits at most 100 chunks and does at most 100 edge point operations (plus bounded reservation/guard/checkpoint and final-publication statements). A straightforward implementation uses one slice statement and up to 100 edge statements per page; batching edge work can change the statement count, not the bound. Total slice statements P, edge operations E, checkpoint transactions P, and staged payload L. If empty input were admitted, handle it as an explicit zero-edge terminal; do not issue a negative or unbounded slice. At 4 MiB, the conservative maximum is 16,384 edges and 164 pages; the final page has 84 edges. This does not declare a new identifier cap.

For uncompressed external bytes, the total logical TOAST chunk payload fetched is at most L plus less than 2C per page from boundary overlap, bounded by L + 2CP; returned slice bytes are exactly L. For an inline value each page accesses a main tuple containing the small value; its size is bounded by the configured page/tuple storage, not by arbitrary L. These are successful-pass bounds, excluding retries, simultaneous reservations, full-value initialization/publication, index navigation and physical I/O. An interrupted transaction can redo its page; unbounded retries cannot have a fixed total bound. Processing each edge with its own substring instead still has linear asymptotic bytes for EXTERNAL, but repeats TOAST chunk access and up to E slice calls; one page slice reduces that overhead. Repeated text substring in UTF-8 or compressed prefix slicing instead sums growing prefixes, Θ(LP) in the worst case, which is quadratic as L grows at fixed page size.

An alternative is immutable **native chunk rows** keyed by reservation and ordinal, each holding at most 256 bytes (or bounded blocks of 25,600 bytes), plus length metadata. Continuation seeks from the ordinal and reads at most 100 edge rows or one block row; total successful traversal payload is L with E rows or P blocks, respectively. This makes the logical bound explicit and avoids relying on TOAST's bytea slicing path. However, generating and inserting E rows up front is unbounded in transaction statements/rows; resumably creating them must itself use a proven bounded slice from a native input or an upstream chunked ingestion protocol. Repeatedly slicing a compressed/text whole input merely moves the quadratic problem. It adds schema, indices, write amplification, checkpointing and ordered bounded cleanup; reconstructing the full text by repeatedly concatenating a growing accumulator would also be quadratic. The existing reserve/continue port already has a full native input and needs no independently addressable chunks, so the auxiliary EXTERNAL bytea is the smaller adjustment. Native chunk rows remain a viable alternative if measurement or a deployment version invalidates the direct-slice assumptions.

## Transaction and lifecycle implications

Reserve the immutable full text, bytea, length, root binding, candidate and initial offset atomically. Capture byte length with `octet_length` when creating the representation and retain it as read-only metadata; check offsets and sizes against that scalar without fetching the whole datum. Do not allow updates to input or its length during staging. Storing a second representation requires ensuring that retries cannot associate bytes from a different source with a reservation.

Serialize continuations for a reservation with its row lock or equivalent compare-and-swap on the expected offset and progress node. In the same transaction, read the bounded slice, insert/follow edges in root-to-leaf order using scoped unique keys, advance node and offset, and commit. A rollback loses both page progress and page edge writes; a retry starts from the last committed checkpoint. Other reservations can share prefix nodes; uniqueness and conflict handling must converge rather than alias. A terminal must identify the full exact input and become visible atomically with its full value, and a candidate UUID conflict must retry without turning a collision into identity. A committed intermediate node alone is not publication. The existing account guard, epoch, source revalidation and purge precedence remain authoritative.

Delete the bytea with the reservation after successful publication or cancellation, and make its cleanup idempotent and fenced against active continuations. PostgreSQL removes the associated TOAST data through normal row lifecycle; native chunk-row alternatives require ordered bounded row cleanup. Count retention and shared trie-node cleanup separately: deleting one reservation must not delete shared or published paths. Changes in storage settings or migration from prior compressed reservations require explicit rewrite/recreation before claiming the bound, including crash-safe migration and no concurrent use of mixed representations.

Before adoption, verify on the deployed PostgreSQL version and driver with near-release-sized compressible and incompressible ASCII values, UTF-8 database encoding, forced digest collisions, and many shared prefixes. Instrument bytes and statements per page and across geometric input sizes, including TOAST boundary crossings; compare bytea slicing to text/EXTENDED and test that the actual query plan/expression leaves the source as a direct stored datum. Race same and distinct inputs, inject rollback and replay at each checkpoint and final publication, exercise UUID conflicts, fencing and cleanup, and confirm no whole input enters workflow history. Measure initial conversion and final publication separately. These are recommended implementation validations, not claims of benchmark results.
