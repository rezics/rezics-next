# Native TypeList order with a bounded Zone residual

Research evidence, 2026-10-28. This report recommends an owner handoff; it adopts no runtime, HTTP, SQL or frontend design.

## Finding

Use Search's native ordered candidate stream as the driving relation and evaluate Zone membership as a current, bounded residual. This preserves `TypeList.sort` without changing the already decided canonical UUID order of `GET subjects`. The hypothesis is sound **conditionally**, but no inspected production seam currently implements it end to end. The smallest addition is an ordered sibling of Search's canonical `prefix`, prepared through the same service-bound compiler, index coverage and current evaluator. Commerce needs its actual current `containsSubject` adapter, not a new ranking operation.

An encrypted position can hold one complete native seek tuple and one pending owner/alias/leaf with the approved existing Search profile. That answers capacity only. It cannot make native canonical coverage true, supply absent owner implementations, or solve the open bounded final multi-leaf proof. Production remains dependent on those independent proofs. In particular, nine distinct material-property leaves with 32 last-positive selections need 288 raw examinations; retaining one leaf still leaves 257. No cursor layout licenses that work within 256.

The accepted operation decision supplied with this assignment governs: every viewer of `POST /v1/zones/{id}:readPage` uses the fixed existing Search encrypted profile, fifteen-minute TTL and sixty-second future skew. GET subjects/collections retain the existing default profile, including timeless deterministic anonymous tokens. Stable AAD contains only the literal POST operation, viewer-or-null, Zone ID and body-shaping digest. Structural basis belongs inside the encrypted position. Valid-shaped unusable, expired, principal-changed or basis-mismatched continuation restarts current authorization into 202/200; body validation and current denial remain unchanged. This supersedes the older general POST reading of the default-profile wording in the documents below; it is not a proposal for another codec/profile.

## Minimum ordered composition proposal

This section is inference from the contracts and source. It describes the smallest owner contract to review, not approved exports.

### One ordered driver; current residuals

1. Prepare the TypeList's actual positive type filter with Search's existing admission/compiler. Add an optional `sort:'name'|'collections'` to prepared options, retaining canonical-ID preparation as the default. Include the pinned immutable release digest. Preparation must bind the full order/template/profile, physical generation/incarnation and real canonical coverage, even at zero hits. It receives explicit metadata/native reservations; no free global preparation sweep.
2. Add one `orderedPrefix(prepared,{afterTuple,quota,reservation})` sibling to the same `createSearchScopeForService` result. It uses `searchSubjects` and the same released template/compiler, with the prepared physical target. Return real `SearchHit[]`, full typed last-covered tuple, truthful exhaustion, basis and actual candidate/native usage. Tuple types are `[string|null,UUID]` for name and `[int32,string|null,UUID]` for collections; preserve the engine values exactly. Charge every fetched key. Bound quota to 1..100 plus at most one reserved lookahead. Return no total. Preserve the existing UUID `prefix` contract unchanged.
3. For each candidate in that exact order, prove the current TypeList predicate AND `(any admitted saved scope OR any readable mounted Collection membership)` AND actual subject Access. Saved scopes use Search's `evaluate`; mounts use the real Commerce `containsSubject`; each owner's actual alias/original/terminal composition remains authoritative. A currently true readable source can settle the OR. An unknown source is immaterial only if another current true source settles it. An unknown TypeList predicate or subject authorization is still essential.
4. Final current rechecks are part of settling, not work after a published cursor. Only settled accepted or definitively rejected candidates advance the native floor. Stop before the first essential unknown; preserve its group and owner progress. Do not emit a later true candidate while that predecessor is unresolved. Already settled earlier results may underfill; no-prefix actual progress can use the accepted 202 handoff, while no phase progress is readiness with retry advice.
5. On resume, revalidate current Zone/source/actor and structural basis. Reread the first unconsumed native candidate from the retained tuple, charged again. Check that it is still the pending canonical group; then resume the same original/leaf first. If an intervening live candidate now precedes it or its name/count moved, do not apply pending proof to a different candidate or silently jump ahead: discard unsafe phase and restart current traversal. No public hidden ID, source ordinal or raw tuple is disclosed.

The driver is internal indexed discovery, not a global public unfiltered list. There is no Zone query language, ranking function, list crypto, index, holder directory or permission engine. Collections provide point membership and repair, not all-member prefetch. Do not derive names from display projection or relabel alias raw hits as canonical results. Rendering uses current safe owner DTOs only after proof.

Canonical-once output requires **real canonical driving hits**: one live terminal ID per equivalence class, physically indexed at the native sort fields of that terminal, with Search's current coverage certificate. Under a fixed basis, a strict total order and settled floor then replace a traversal-sized seen set. Aliases are residual proof drivers, not independent ranked output candidates. If that coverage has not been established, the ordered method is unavailable; post-page normalization, arbitrary representatives, seen sets and duplicate-dropping repair are invalid substitutes.

Because only one pending source/leaf is stored, earlier sources and positives may need replay. Every replay costs keys again. The shared owner final-proof dependency must demonstrate that the decisive final proof, current authorization and all replay fit the same 256 ledger and native axes. Neither this scheduling proposal nor a compact continuation establishes that property. Keep the entire admitted grammar and scope; do not repair the gap by assuming negative results, caching truth/witness vectors or trimming filters. Search owns that independent proof and native acceptance.

### Progress and termination argument, with explicit premises

For a fixed finite ready canonical candidate basis, each successful step either increases the settled native tuple, consumes a strictly advancing bounded raw owner phase for the same candidate, or finishes the stream. Source/leaf ordinals are structural scheduling positions, never cached verdicts. An essential unknown without actual progress is readiness. A full, definitively settled rejected window may produce an advancing empty page.

This yields finite termination only if actual owners can definitively settle every essential candidate in finite repair/probe work **and** complete final current proof within one allowed disclosure step. Exhaustion requires complete native search plus no unconsumed/unknown pending candidate. Quiescence alone does not supply an absence certificate. A token that repeatedly resumes one leaf but cannot ever afford final replay fails liveness even if its byte encoding is perfect. Ordinary mutation or late eligibility behind the floor may require a fresh traversal, as the existing contract permits.

### Exact accounting requirements

Before any call, reserve from one request-wide 256 raw-key ledger covering every participating TypeList/source, not 256 per owner or read. For observed work:

`ordered hits + duplicates + alias keys + internal fact drivers + lookahead + rereads + final revalidation keys <= 256`.

These categories describe encounters, not distinct identities: seeing the same key in discovery, replay and final proof charges each encounter. Categories in owner receipts must be disjoint so a single encounter is not counted twice; aggregation must not omit keys hidden by grouping or rejection. Fetched but unused lookahead is charged and cannot advance coverage. Reservations are not actual usage. An unallocated owner cannot refill. Exhaustion probes and zero-result seeks still need their reserved native work; any key they actually inspect also debits the ledger.

Reserve independent `points`, `witnesses`, `rows`, `bytes`, `emptySeeks`, statements and engine work bounds. Scope's `rawKeys` may be zero; a native leaf call needs its own positive axes, at most 101 keys including explicitly reserved lookahead and at most 100 witnesses. The ordinary `SubjectSource.read` cap of 256 IDs does not account internal evidence work. Capture every pool, Access preparation, rejected row and returned/discarded byte; also capture native engine candidate fetches, partial responses and requests. An engine window size does not cap postings or top-sort work.

Each actual `readIdentityBasis` probe pays **two released 4096-home sweeps: 8192 metadata rows plus core epoch/home observations**. This applies at prepare, continuation and final use wherever called, including partial/unavailable sweeps. Coverage's bracketed reader additionally pays both native basis reads, 4096 coverage comparisons and physical metadata reads: at least 16384 identity metadata rows plus those separate observations. Do not bury this fixed cost in leaf usage, call it constant and exempt it, or repeat it once per candidate without a reservation. Certification/polling is separate from a reader; it has its own home/checkpoint costs. These are the costs specified by the [Search README](../../services/kernel/src/search/README.md#L1039) and [Semantic identity contract](../../services/kernel/src/semantic/README.md#L755), not measurements made here.

## Cursor capacity and binding

### Native name bounds are a production dependency

[`bounded-sort-keys.ts`](../../services/kernel/src/search/bounded-sort-keys.ts) asks the real engine's `name_key` normalizer for each value, validates a single scalar token, and retains the full normalized key only when its JavaScript length is at most 512 UTF-16 units; oversized keys become null. For scalar strings this bounds UTF-8 to 1536 bytes, or **1537 including the `s` tag**. A legal 250-CJK key needs 750 bytes plus the tag, already far beyond a default 256-byte key. There is no justification for truncating, hashing or copying a display name into the seek position.

This helper is not currently called by [`indexer.ts`](../../services/kernel/src/search/indexer.ts): the actual apply body directly builds `documentActions` and bulk-writes them. [`document.ts`](../../services/kernel/src/search/document.ts) also still uses `MISSING_NAME` for an absent first label; [`subjects.json`](../../services/kernel/db/search/indices/subjects.json) normalizes `name_sort` but does not enforce the helper's length bound. Therefore 1537 is the accepted **target contract and helper bound**, not demonstrated production coverage of every existing normalized index key. The [native bounded-name cursor outcomes](../../services/kernel/test/search/bounded-name-cursor-outcomes.test.ts) require actual API-created long/expanding names, raw engine nulls, normal worker/rebuild and continuation. That independent writer/replay proof must precede claiming bounded native tuple production.

### The actual profile API is adequate for one proposed position

[`tokens/list-cursor.ts`](../../services/kernel/src/tokens/list-cursor.ts) selects profile with the final `{profile:'search'}` option on **both** `encodeListCursor` and `decodeListCursor`. Search profile selection is authenticated in AAD. It enforces eight keys, 2560 UTF-8 bytes/key, 3072 aggregate string bytes, 3584 serialized plaintext bytes and 4864 token characters. The 34-byte envelope is version/key ID, salt and AES-GCM tag. Search profile is timed and randomly salted even for `viewer:null`; default anonymous mode remains deterministic/timeless. No codec widening is needed.

The public [`search/cursor.ts`](../../services/kernel/src/search/cursor.ts) currently calls the older `tokens/cursor.ts`, not this encrypted profile. Its existing `s/n/z` tuple tagging is useful contract evidence, not proof that native Search has already migrated its public token path. Keep that independent encrypted Search migration and its native outcome tests explicit.

A reviewable eight-key candidate layout is:

| Key | Meaning and largest proposed representation                                                                                         |
| --- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Composite structural/query/order/Zone basis digest, 64 ASCII hex bytes                                                              |
| 2   | Last settled native count: empty for name/start, otherwise `n0`..`n2147483647`                                                      |
| 3   | Last settled full name: empty only at start; `z` for native null; `s` plus complete native string, at most 1537 bytes               |
| 4   | Last settled native ID: empty at start or `s` plus canonical UUID, 37 bytes                                                         |
| 5   | First unconsumed canonical group UUID, or empty                                                                                     |
| 6   | Versioned read/lane/source ordinal record, bounded by sixteen reads and 32 sources; version consumes bytes here, not a ninth key    |
| 7   | Actual alias/original progress UUID, or empty                                                                                       |
| 8   | One tagged owner record: Search composite-owner digest plus 24-character leaf record, or Commerce digest plus 77-byte source record |

`position.epoch` can retain the actual positive physical generation; it is not permission or a replacement structural identity basis. One composite digest commits current Zone revision/configuration, admitted pinned definitions, order/template/profile, concrete index identity and owner structural/source meaning. Explicit tags/ordinals have to be validated against the actual prepared plan, not just their storage maxima. Definition bodies, private facts, source names/IDs, Access verdicts, witness vectors and totals never enter public output or position. Hashing structural metadata is distinct from hashing a sort key: the latter loses native ordering and is forbidden.

[`scope-progress.ts`](../../services/kernel/src/search/scope-progress.ts) already packs exactly one 18-byte leaf record into 24 base64url characters: version/leaf ordinal, phase/value ordinal, and one padded u64 sequence or UUID. Witness-start null differs from a nil UUID; whole null differs from pending with null `after`. It contains no group/source/actor/basis by itself. Pair it with the enclosing fields; it cannot replace those bindings or encode multiple pending leaves. Search `aliasAfter` retains the original under evaluation and resumes it FIRST while a leaf is pending. Commerce `aliasAfter` is the last settled alias and its own source record advances its pending source work; do not conflate the two semantics.

Keep just **one last-settled native tuple**, not a second pending name/count tuple. The pending group must be verified by a paid native reread from that floor. This trades repeated charged work for bounded position capacity. A group ID alone cannot seek in name order. If the owners require independent unconsumed tuples for several reads or sources at once, this capacity argument no longer applies; owner agreement is required before promising that layout.

The existing pure [ordered-cursor-capacity test](../../services/kernel/test/search/ordered-cursor-capacity.test.ts) was run unchanged here: `bun test services/kernel/test/search/ordered-cursor-capacity.test.ts` passed **4 tests, 307 assertions**.
