# Global rating ordering across prior epochs

Research date: 2026-10-28. Evidence, not an adopted specification or runtime proof.

## Answer and scope

Use a fixed, versioned numeric `_script` sort whose parameters contain the **current native** Global prior eligibility and epoch. Return the indexed public score only when the prior is eligible and the document's prior epoch equals that epoch; otherwise return a finite negative sentinel. Sort descending, then by `name_sort` and unique `id` ascending. This supports a deterministic total order over a mixed-epoch index without treating an old score as current. It preserves a real score of zero above every unscored document. OpenSearch supports numeric script sorting; its derived fields currently do **not** support sorting. [Sort documentation][sort], [derived-field limitations][derived], [numeric sort implementation][script-sort].

This does **not** provide snapshot-stable pagination while documents are being republished. `search_after` is stateless: a document moving from the sentinel group to its current score can cross an already-consumed boundary and be missed. Changes in the opposite direction can repeat a document. Stable tie breakers remove ambiguous equal-key ordering, but do not freeze changing keys. Binding the prior epoch and index generation into a signed cursor rejects obsolete query semantics; it does not detect every update inside that epoch/generation. An exact, duplicate-free, omission-free traversal needs immutable ordering data for the traversal, or a snapshot mechanism. The contract excludes engine PIT. [Pagination documentation][pagination].

The scope authority is [docs/scope.md](../scope.md): only the Global standard-question public aggregate enters this recommendation. The task supplies the frozen-prior epoch, bounded republication and below-50 invalidation contracts. The existing rating README's broader Realm sorting language does not expand that scope. No private population join, rating computation change or recommendation service is proposed.

## Fixed template design

Use dedicated flat fields for the Global standard question: illustrative names `public_rating_prior_epoch` (`keyword`) and `public_rating_score` (`double`), both with doc values. Publish the epoch and score atomically in one document replacement from the same native public figure. A missing/null score must remain absent from doc values; a producer must not relabel an old score with the new epoch. Treat these as proposed mapping names, not existing schema. The current strict subject mapping contains neither field.

The fixed numeric script can be:

```painless
if (!params.eligible) return -1.0;
if (!doc.containsKey('public_rating_prior_epoch') ||
    !doc.containsKey('public_rating_score')) return -1.0;
if (doc['public_rating_prior_epoch'].size() != 1 ||
    doc['public_rating_score'].size() != 1) return -1.0;
if (!doc['public_rating_prior_epoch'].value.equals(params.epoch)) return -1.0;
double score = doc['public_rating_score'].value;
return Double.isFinite(score) && score >= 0.0 ? score : -1.0;
```

The negative sentinel is internal ordering data, never a displayed rating. This design chooses nonnegative finite published scores and scalar epoch/score fields; validate those properties at the native projection boundary. `size() != 1` also rejects detectable multivalued input rather than silently choosing a minimum/maximum. Epoch is an opaque keyword string supplied by the native authority, avoiding numeric-ID precision or type-coercion assumptions. Unknown native state is an error, not `eligible: false`; known ineligibility makes every document unscored.

The template's rating branch fixes this sort structure (the script above is stored under the illustrative versioned ID):

```json
[
  {
    "_script": {
      "type": "number",
      "order": "desc",
      "script": {
        "id": "subjects-global-rating-sort-v1",
        "params": { "eligible": true, "epoch": "native-epoch-token" }
      }
    }
  },
  { "name_sort": { "order": "asc", "missing": "_last" } },
  { "id": { "order": "asc" } }
]
```

Prefer a separately versioned stored Painless script referenced by the versioned stored Mustache template. Alternatively embed the identical fixed Painless source in the template if inline execution is already permitted. Neither approach accepts caller-supplied source, script ID, field name or sort direction. The server constructs a bounded object such as `rating_params = {eligible, epoch}` from current native evidence and inserts it into `script.params` with `{{#toJson}}rating_params{{/toJson}}`; it inserts `after` as an array with `toJson`. Do not interpolate epoch text into Painless source or treat it as executable Mustache. The current `query.ts` already serializes sort/after containers this way and documents the separate scalar-string quoting hazard.

Create a new template version; do not mutate released `subjects-search-v2`. That template currently accepts a server-built `sort` container. The new fixed rating branch can live directly in the new template, or its trusted repository builder can emit the fixed structure; in either case HTTP input selects only the admitted sort enum. OpenSearch stored IDs are mutable by API, so immutability is a repository/deployment rule, not an engine guarantee. [Templates][templates], [stored script resolution][script-service].

Expected tuples are `[8.25,"alpha","subject-a"]`, `[0,"beta","subject-b"]`, and `[-1,"gamma","subject-c"]`; these are illustrative, not captured responses. A missing name may produce `[-1,null,"subject-d"]`. Preserve the engine-returned normalized name key, numeric value and null exactly, including tuple order and length, across JSON and signing. Do not substitute displayed labels, round the score, stringify numbers, coalesce null to zero, or reconstruct keys from current source data. The repository's `search/cursor.ts` already distinguishes finite numbers, strings and null. Use its copied keyword `id`, not engine `_id`, as the unique final tie breaker. The searched generation must contain one document per subject. [Sort tuple source][sort-values], [continuation source][after-source].

## Alternatives and shared patterns

| Approach                                    | What works                                                                                                                                                                                                                                        | Cost or limitation                                                                                                                                                                                                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fixed conditional `_script`                 | Immediately masks stale-epoch documents without rewriting them; preserves all subject candidates and gives unscored documents a name/id order. One compiled program spans epochs.                                                                 | Executes against matching documents; no immutable snapshot, per-figure freshness guarantee or indexed numeric-sort optimization follows. Recommended initial mechanism.                                                                                                                           |
| Derived field / runtime field               | OpenSearch derived fields support some query-time transformations and retrieval.                                                                                                                                                                  | Officially unsupported for sorting in the inspected documentation. Elasticsearch runtime-field examples are not a substitute. Not a supported implementation choice.                                                                                                                              |
| Single materialized score plus epoch        | Fast ordinary numeric field sort.                                                                                                                                                                                                                 | A raw score sort cannot condition that value on another field. Sorting by epoch then score incorrectly orders epoch groups; filtering to current epoch removes unscored/stale subjects instead of putting them last. Asynchronous clearing of one shared score field leaves a stale-order window. |
| Epoch-specific numeric fields               | Sort an allowlisted current-epoch field with `missing: -1`, then name/id; unreached subjects naturally lack that field.                                                                                                                           | Explicit mappings, producer retention and cleanup are required; accumulating epoch-named fields grows mappings. A fixed template needs a trusted field selection mechanism or new version for new fields. Publication still changes keys during an epoch. Never accept arbitrary field names.     |
| Materialized generation and alias promotion | Build all subject documents, including unscored ones, for an epoch in a separate generation; atomically switch the read alias once ready. Ordinary field sorting can serve an immutable published generation. [Atomic alias operations][aliases]. | Requires storage, catch-up/publication coordination and restart/readiness policy. An alias switch alone does not make the destination immutable; ongoing figure/name updates restore pagination drift. Never keep using an old generation's score as the new native epoch's score while waiting.  |

The shared pattern in OpenSearch's docs and source is to keep executable definitions fixed, parameterize changing data, read columnar doc values in ordering work, and use explicit stable tie breakers. Materialization trades query-time work for publication work. Neither parameterization nor materialization makes the search index an authority for present native eligibility. [Field access][field-access], [script cache][cache-source], [pagination][pagination].

## Current proof and consistency limits

1. **Before discovery:** Read current native Global/standard-question prior state, including eligibility and its epoch/invalidation identity. Bind that state, the fixed sort/template version, canonical query/principal and index generation into the signed cursor. Reject continuation on a new epoch, loss of eligibility or generation change. Recovery must not reuse an invalidated epoch identity: a below-50 transition followed by recovery must still invalidate an earlier cursor. These are application contracts, not OpenSearch facilities.
2. **During a request:** Hold the admitted state fixed across bounded candidate rounds; re-read authoritative state before responding and fail/restart if it changed. This detects transitions visible to those reads, but is not a transaction across native storage and OpenSearch. It cannot prevent a transition immediately after the final read, or detect an ABA transition if the authority reuses the same identity. An unavailable current-state read must fail closed rather than fall back to indexed eligibility or an old cached eligible state.
3. **Prior invalidation:** If native state reports the prior below 50, an old document with an apparently matching epoch is still unscored because `eligible` is false. Existing eligible cursors restart. Current native proof must account for its own delayed aggregate processing; Search cannot prove an unprocessed vote/eligibility event has already affected that proof. This is read-time evidence, not instant consistency with every underlying event.
4. **Per-subject threshold/revision:** A current prior epoch alone does not prove that a subject's figure still meets its disclosure threshold or still has the indexed score. A figure may fall below threshold or change within the same prior epoch. Bounded current-source checks need the figure's public eligibility and revision/score witness as well as subject disclosure. If a numeric-ranked candidate has lost that proof, consume and reject it; never disclose its old score or relabel its existing tuple as sentinel. Safely including it later as an unscored result requires reindexing or another ordering strategy, not in-place reshuffling of one fetched page.
5. **Republication and reindex lag:** With native epoch E2 and mixed E1/E2 documents, only E2 scores rank numerically; E1 or missing scores occupy the sentinel group. Newly eligible figures not yet indexed can be absent from the numeric group. A current-source check can reject an unsafe candidate, but cannot discover a missing candidate or globally rerank all other hits. It cannot prove completeness or the current top-N. Display/source freshness and indexed ordering freshness remain separate.
6. **Continuation:** Advance from the last consumed engine tuple, including rejected candidates, as existing `service.ts` does; leave an unconsumed acceptable lookahead for the next page. Retain existing bounded refill rounds. If proof is unavailable, use the existing typed failure pattern; if the budget is exhausted, keep existing partial-result semantics. Do not issue an unbounded score join or repeatedly restart internal scans until a full page appears.

Even when native epoch and generation stay unchanged, a previously unscored subject promoted above the cursor is missed; a scored subject demoted below it can repeat. Name changes, deletes and ordinary updates have similar effects. Exact stability therefore cannot be claimed for the requested live, asynchronously republished index. The manager can adopt deterministic ordering plus restart on state changes and explicitly eventual traversal, or separately specify immutable generation publication if exact traversal is required. This limitation is documented engine behavior, not a contradictory acceptance test. [Pagination][pagination].

## Cost, security and recommendation

Script evaluation work grows with matching documents evaluated, not just returned hits; sort selection and shard merging add work. Small pages, `search_after`, capped hit totals and a 600-candidate disclosure ceiling do not establish a constant engine-work bound. The docs recommend indexed filters to reduce script work and materializing frequently calculated values. Here the script only gates an already computed score; it does not recalculate ratings or query native storage per matching engine document. The pinned script-sort builder has no direct `search.allow_expensive_queries` guard; do not mistake derived fields' required expensive-query setting for a script-sort resource budget. [Sort implementation][script-sort], [field access][field-access].

The existing search README's three rounds, at most 200 hits per round and bounded source reads are **local budgets**, not engine complexity guarantees or measured latency. Keep them. Before production adoption, measure broad-match and selective rating queries at repository growth scales, with cold/warm compilation and missing/old/current epoch distributions. Monitor node script compilations, evictions, limit trips and search latency. Keep `_score` unused and score tracking off for this sort. No benchmark or runtime proof is supplied by this report. [Script settings][script-settings].

Allow only trusted deployment identities to create/update stored scripts. A separately stored Painless program permits `script.allowed_types: stored`; the Mustache template and numeric script require the `template` and `number_sort` contexts alongside contexts other installed features need. A stored template with an inline inner script requires inline scripts to remain allowed. Painless allowlisting and type/context restrictions supplement application validation; they do not authorize exposing engine requests to callers. Keep limits enabled and use parameters rather than generating a different source per epoch. [Script security][security], [context documentation][contexts], [script resolution][script-service].

Recommend adopting the conditional numeric script first, with atomic public epoch/score projection, native state in cursor bindings, bounded current figure proof and explicit live-pagination limits. Consider immutable generations only if measured script cost or an adopted exact-traversal requirement justifies the publication machinery. A two-slot score scheme cannot safely overwrite a slot while cursors still depend on its contents. Per-epoch fields without retention limits are not a bounded alternative. These are design recommendations for this stack, not source to port.

Implementation follow-up should prove on the pinned engine: unmapped fields, mapped-but-absent fields, explicit null, real zero, old/current epochs, invalid prior with matching epoch, detectable multivalues, missing name, mixed shards, exact numeric/null tuple round trips through signed cursors, state/generation restart, current-source rejection/refill and key movement during republication. It should also verify allowed script types/contexts and missing stored-script handling. Those checks belong to the implementation contract; this research task's acceptance is the nonempty report only.
