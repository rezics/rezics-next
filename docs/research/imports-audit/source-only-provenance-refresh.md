# Source-only provenance refresh

## Defect and correction

Bangumi retains admitted native date, tags, platform, infobox and NSFW fields in its source digest without
inventing catalogue mappings. A date-only change therefore changes the digest while the same converter's name
and identifier statements remain equal. The former retained-proposal decision accepted those older statements
without checking the digest, then rejected the changed record with `Conversion has no justified final plan`.

The bounded current-candidate matching now pairs each retained candidate with its matching proposal. Outside
the confirmed statistic-only exception, an older digest removes that pair from retention, producing ordinary
owned retractions and fresh cited proposals carrying the actual new digest. A candidate acknowledged by this
same immutable run remains eligible by its existing exact signature. No RunStore, converter, public schema,
action, rights, authorization, source projection or digest algorithm changes.

The explicit VNDB exception is evaluated only after matching every existing semantic candidate and every
non-create proposal and after a successful source-statistic effect. Partial retention, converter transitions,
fenced groups and deferred covers cannot use it to acknowledge an unrelated empty plan. Its existing tests
remain unchanged.

## Native caller and observation

One existing `api-runtime` world supplies real Auth, Access, public bulk commands, claims, receipts, fences and
observer reads. The ordinary CLI uses a private account key provisioned through the existing `identitySupport`
stage/approve/apply credential effects. Input is one synthetic native Book; only its date changes. The caller
observes actual candidate IDs/digests/retractions, exact original native receipts and bootstrap journal, same
native claim and subject, and an independent editor's accepted/adopted Context selection. It also checks absent
date slots, unchanged no-write reopen, and current fenced source disclosure. SQL is exact-key observation only;
all grants, adoption and fences use existing native support or public commands. Keys and SQLite fixtures use
tmpfs; no raw private/user-post source input is imported.

The separate local recovery case uses real SQLite/Importer/registration with only typed external transport.
It first acknowledges fresh proposals while an old retraction fails, closes/reopens, loses the replay
response before acknowledgement, then reopens and replays the immutable envelope. It checks that fresh
acknowledged candidates survive, prior receipts/bytes remain immutable and unchanged input creates no writes.
This is bounded coordination proof, not native authorization evidence.

## Cost and decisions

Only already bounded current owned candidates and existing indexed source, subject, fence and journal reads
supply comparison evidence. There are at most 300 current candidates, the existing envelope limit remains
100 commands/65,536 bytes, and the existing changed-record delta times q work and unchanged/replay caps remain.
No catalogue/history/source scans, new lookup authority, new growth series or future statistic-clear API is added.

Digest equality is required for ordinary semantic retention even when values and citations match. The confirmed
statistic-only exception stays separate; successful statistic publication alone cannot retain a partially
matching semantic plan. Native candidates include read-time statement identity/revision metadata, so equal
semantic values are compared by property, value, qualifiers, references and rank rather than identity metadata.

The extra file outside declared paths is `services/importer/tests/source-provenance-recovery.test.ts`: the frozen
local acceptance cannot be edited, and the changed retention rule needs a partial-acknowledgement/response-loss
reopen proof. No frozen acceptance file was changed.

digest and proposal construction; the existing source-statistic, converter-revision/fence and deferred-cover
