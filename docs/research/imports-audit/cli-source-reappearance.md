## Bound journey

database and registered worker. `identitySupport` stages, approves and applies an operator key through actual

ordinary `--source`, `--dump -`, `--state`, `--api`, `--auth`, `--account-key`, `--account` and `--client` arguments.

and receipts are never synthesized. `openApiObserver` creates and selects an independent editor candidate and
sets each exact facts fence through the existing public governance route. Runtime owns the existing media boundary
and registered worker; these metadata-only records request no media jobs. The existing `sourceStatistics:'vndb'`
setup registers the ordinary VNDB CLI's required `source_statistic:write` scope through the actual fixture. It
also performs its existing public exposure setup; the supplied zero-vote records never call the statistic route.

`/works/OL930001W`–`/works/OL930005W`, Wikidata `Q930001`–`Q930005`. Titles are generated synthetic text, with only
the first key changing. Bangumi remains genuinely unversioned; the other sources use native revisions 7 → 8 → 9
for the returning key. VNDB input is six tar members containing the native `vn`, `vn_titles` and `entry_meta`
headers and COPY rows; zero vote counts and null averages avoid a statistic journey. Source digests come from
the real conversion and persisted baseline, never fixture predictions. Converter revisions are read from actual
CLI registration and persisted source rows, and the evidence prints the actual bundled release and digest.

Each source first publishes five records. Exactly one disappears under the unchanged default 20% safety bound.
Its changed permitted title then returns to the original native external claim and subject. Old owned candidates
remain retracted, while new independently read proposals must match the actual changed digest/revision.
Original bootstrap journals and native receipt rows remain identical. A second admitted disappearance precedes
the public tuple fence; the next changed return emits no facts writes, candidate disclosure hides that tuple and
old request replay returns actual fenced command problems without old native IDs. An unchanged reopen emits no
bulk writes. Every other source's local state, native claims and all captured receipt rows are compared before/after;
the other four members and all five original bootstraps of the active source also remain unchanged.

The importer companion has four local protocol tests, one per provider, for the real coordinator and reopened
SQLite. It also verifies late acquisition failure has no effects. Those explicit protocol doubles provide local
proof only; they do not replace the ordinary native CLI acceptance.

## Scope and decisions

Reappearance already has production primitives in `runImportCli`, `Importer.runRecords`, `RunStore` and
`RecordBindings`; the missing connected caller does not justify manufacturing a production defect. The second
return changes the permitted title again while the exact facts tuple is fenced. Synthetic keys are not claims
about live provider objects. Cross-source isolation uses four feeds in the same ordinary CLI state and native
world, with all providers initialized before any removal. Fenced bulk replay uses the existing HTTP 200 envelope
with individual 409 `fenced` problems.

No frozen tests or peer reviewed-reduction fixtures change. No sourceRecords metadata ACK migration, cover,
summary/list API expansion, vocabulary seed, recipe-site method text, user posts or six-surface discovery is added.
Existing byte/row/execution bounds, canonical PostgreSQL/derived suites and Cost ordering stay unchanged. There
is no new growth series or invented native block count. This outcome alone does not prove broad producer growth
or full imports promotion.
