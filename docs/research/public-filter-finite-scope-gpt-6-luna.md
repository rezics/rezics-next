# Finite-scope completeness under delayed home delivery

Research date: 2026-11-11. This report evaluates the finite native witness requested by the Search consumer contract. It is background evidence, not an implementation or acceptance result.

## Finding

A delayed derived projection can be kept from disclosing stale membership if the page remains bound to its original native observation and final revalidation checks committed relevant reductions since that observation's covered cut. A live repair ACK cannot erase the fact that an older PIT may still contain the removed value. An unrelated finite query can remain useful only when complete dependency routing classifies the committed reduction as irrelevant and its returned rows still pass their own current checks.

This recommendation follows the existing [Filtered lists contract](../filtered-lists.md) and [Search consumer contract](../../services/kernel/src/search/public-filter-consumer-contract.md). The external sources below support the storage, progress, and visibility boundaries; they do not prove that this repository's native producer implements them. Only the requested two-home test can establish that finite feasibility. No native test or server run was performed in this worker.

## Primary-source evidence

- PostgreSQL defines statement snapshots for Read Committed and a transaction snapshot for Repeatable Read. These are transaction-local visibility rules, not a cross-home change feed or proof that a later committed reduction has been incorporated into an older search observation. See [Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) and the project [license](https://www.postgresql.org/about/licence/).
- Kafka retains consumer progress by partition. Its [design](https://kafka.apache.org/40/design/design/) describes each partition as totally ordered, with a consumer position for each partition; I infer that these positions do not define one total order across partitions. The [distribution documentation](https://kafka.apache.org/40/implementation/distribution/) describes committing offsets per partition, and the consumer API recommends committing processed offsets only after the corresponding work completes. This is a useful precedent for keeping independent home positions, but a consumer offset remains delivery progress rather than permission to publish a query result. See the [KafkaConsumer API](https://kafka.apache.org/40/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html) and the cloned [`KafkaConsumer.java`](https://github.com/apache/kafka/blob/62dca4dd544bddfc0913ca199a704b95c94d23e1/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java) at `.reference/search-finite-scope/kafka/clients/src/main/java/org/apache/kafka/clients/consumer/KafkaConsumer.java` (revision `62dca4dd544bddfc0913ca199a704b95c94d23e1`, Apache-2.0; see its [`LICENSE`](https://github.com/apache/kafka/blob/62dca4dd544bddfc0913ca199a704b95c94d23e1/LICENSE)). The clone was read only; no code was installed, built, run, or copied.
- OpenSearch separates a write response from search visibility. A refresh moves buffered operations into searchable segments; `refresh=wait_for` waits for that visibility boundary, while the default write does not. This supports placing a test barrier around the real write/refresh interaction, but a successful refresh alone cannot prove the Source has repaired every dependent subject. See [Refresh Index API](https://docs.opensearch.org/latest/api-reference/index-apis/refresh/) and [Document APIs](https://docs.opensearch.org/latest/api-reference/document-apis/index/); the documentation source is [`_api-reference/index-apis/refresh.md`](https://github.com/opensearch-project/documentation-website/blob/main/_api-reference/index-apis/refresh.md) (Apache-2.0; [license](https://github.com/opensearch-project/documentation-website/blob/main/LICENSE)).

## Recommendation for this repository

Use one finite native schedule before making growth claims: capture a public page and retain its continuation; commit a subject-wide hide for a non-Book author through its native command; delay only the real dependent projection write at the OpenSearch transport; and read the authoritative home head while delivery remains paused. Confirm the old PIT still produces its old positive IDs, then require both the old page and continuation to return a current preparing/blocking outcome before and after repair ACK. During the pause, a separate language-filtered Book query should still return useful results. After repair, a new traversal should recover the newly eligible Books.

Keep the authoritative reduction append in the owner transaction. Bind the query to its native covered cut and check retained relevant changes at the final boundary; retain changed heads after ACK so an old PIT cannot become safe merely because current pending work is empty. Treat per-home positions, outbox delivery, sink write receipts, and refresh visibility as distinct facts. Permit the independent query only after complete query-key routing and returned-subject checks establish that it is unaffected.

The resulting witness is deliberately finite. It does not establish browser behavior, promoted-main acceptance, all-home feasibility, latency or cost at 64/512/4096 homes, or a generally bounded growth path. Those remain separate verifier evidence.

## Confidence and falsifiers

Confidence is high for the PostgreSQL, Kafka, and OpenSearch substrate behaviors cited above. Confidence is medium for the repository recommendation until the integrated native driver runs. If the native home head does not advance with the owner commit, if a pending or ACKed relevant change allows the old page or continuation through, or if the unrelated language scope cannot return useful results during the held write, the native implementation does not meet this finite witness and should remain unaccepted. A passing witness would establish this one schedule only, not broad completeness or growth.
