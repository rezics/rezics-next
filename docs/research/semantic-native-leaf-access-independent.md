# Independent native selected-evidence access: a coverage restriction conflict

Research evidence, 2026-10-28. No implementation, adoption, admission, accounting, permission, ABI or wire change.

## Result and decision requested

**The unchanged coverage contract prevents a universal final proof within aggregate 256 raw keys.** This is an
access lower bound on a legal material-negative shape, independent of forward replay order, matching ordinal,
relation repair or the quality of positive locators. A positive-anchored filter consisting of a current type
and NOT of a false 16-child OR needs complete negative evidence for 16 material slots. Fifteen slots contain
32 selected facts and the sixteenth contains 31. Its required selected-fact subtotal is **511**, before any
outer work. One label makes exactly 512 current facts, within admission. The same obstruction exists in compact
and expanded representations.

This answers the new access question differently from the established nine-slot 288/257 replay counterexample:
**even perfect discovery of where all the values are does not supply the existing negative certificate without
reading the complete selected slots in the current observation.** Neutral ordered indexes can reveal a gap;
the current contract does not accept that gap as either of its two coverage kinds. This report proves a
restriction conflict, not a data-structure impossibility after changing the certificate contract, and not an
impossibility of efficient positive-only leaves.

The smallest question for Root is: **must material `selection` coverage continue to mean reading the entire
selected slot in the final observation?** If yes, universal final completion, current admission and aggregate256
cannot all hold. If no, Search and Semantic need explicit authority to design a different complete-coverage
capability, with a decision about neutral key seeks versus the present SQL range/qualifier prohibition. This
report does not choose that exception. Merely permitting positive candidate narrowing would not resolve the
coverage conflict. Source ownership cannot change Access authority or authorize cached permissions.

Positive finite completion and negative capability must remain separate promises. A historical, nonempty,
unreadable relation pair is still allowed to remain unknown. The example below uses **material slots whose
complete selection is the expressly available negative capability**, and produces a true, positive-anchored
whole filter. Calling every such result permanently unknown would withdraw the requested all-admitted final
completion promise, rather than satisfy it.

## The exact operations and authority boundary

The [Semantic contract](../../services/kernel/src/semantic/README.md#current-leaf-evidence) says:

> Statement constraints may select a proven complete possible-witness pair range for item values; otherwise
> read the property's bounded selected slot. Range/qualifier predicates are not SQL filters.

It also says:

> `selection` means the ENTIRE bounded current native selected slot has been read in this observation,
> including all relevant current target/fence checks.

The available negative alternative is an exactly empty **full possible-identity pair prefix for every requested
item pair**, with synchronous writer and bootstrap completeness. A range gap, positive hint miss, historical
nonempty pair with no visible witness, end of a rejected stream or local generation is not that certificate.
The closed `LeafCoverage` union contains only `selection` and `empty_pair`.

The current ABI takes one `subject`, one admitted `FactClause`, `after: LeafProgress | null`,
`revalidate: string | null` and `budget: LeafWork`; options are actual Access/actor/routeKey/deadline/nativeT.
`after` and `revalidate` are exclusive. Revalidation is an opaque identity previously returned by this reader,
at most 128 ASCII bytes; it is neither a body nor a guessed selected ordinal. Outputs are unavailable/basis
change with actual usage, or current source type, selected normalized facts, coverage and progress with usage.
There is no accepted boundary-tuple/gap proof input to Search's matcher and no range-index certificate output.

no `relation` declaration. The type lists these sixteen facets and properties. An optional item qualifier

Create one readable, visible, unredirected source with label `{ en: 'Source' }`. For properties p00..p14 create
32 normal native assertions in each property slot; for p15 create 31. Assertion j has
`{ type: 'value', content: { amount: '+' + j, unit: '1' } }`, with empty qualifiers/references. Current selected

const filter = {

## Access lower bound under the unchanged operations

Write `S_i` for the current selected facts in property i, and `N = sum |S_i| = 511`. The following is a
contractual access proof, with a narrower indistinguishability argument for today's unindexed access:

1. Each quantity R(p) is false. With no matching current witness, Search needs nonnull current coverage to
   assign false. Its shared plan cannot turn partial nonmatches into false, including below NOT.
2. Quantities have no requested item-pair prefix. `empty_pair` is inapplicable. No historical relation-pair
   assumption participates. The only available material-negative certificate is `selection`.
3. By the explicit definition, a valid selection certificate for p requires reading **every** current fact of
   S_p in this observation, with relevant foreign checks. In this native, public fixture every member is a
   separate actual fact/candidate identity. A maintained copy in a shared selected-data index does not change
   that identity count; returning a JSON array or owner row containing 32 identities does not charge one key.
4. Slots are disjoint. Request-local sharing can cover several clauses over the same slot once, but cannot
   cover sixteen different slots with fewer than 511 distinct fact examinations. Reading all once is the most
   favorable assumption. Acquisition already satisfying final freshness is counted once, not reread by fiat.
5. Every R(p) must be false to obtain this true whole-filter result. Therefore every valid final request needs
   the union of the sixteen complete selections. No legal progress field carries earlier selection coverage.

Consequently, even granting zero internal overhead and perfect locators:

```text
K_outer + sum_i(K_discovery_i + K_acquire_i + K_final_i)
  >= K_outer + |union_i S_i|
   = K_outer + 511
   >= 511 > 256.
```

This is independent of selected order and of how the rows were discovered. An index could make discovery zero;
it cannot make the required full acquisition zero. Even illegally granting one complete 32-fact slot's old
coverage for free leaves 479 > 256. The actual one-record contract grants much less.

For the explicit currently specified scan/opaque-point operations there is also an adversarial access argument:
until all potentially selected rows have been observed, an unread row can have quantity1000 instead of its
nonmatching quantity, with identical identity, selection membership/order, public rank and shape. The final
filter then flips. Each partial view is compatible with that completion. A structural digest may detect a
change; it neither reveals the unread value nor certifies its nonmatch. Searching a digest for the answer is
not an available operation. This argument does **not** assert identical transcripts for arbitrary future
value-index pivots or summaries: those might reveal the change without reading the row. The five-step lower
bound still applies to them because their gap/summary is not an accepted current coverage certificate.

This distinction is essential. The conflict is with the explicitly required observation/certificate, not an
information-theoretic claim that all selected-data indexes must scan every fact to answer every predicate.
It neither relies on ordinary first-positive samples nor says reversing/rotating the last ordinal helps.

### Shrinking ledger and independent native axes

The following deliberately grants the producer one raw key per selected fact, with all final checks fused.
Actual slot heads, length sentinels, revisions, bodies, duplicates, rejects and rereads can only add debits.

| One final request, optimistic calls without lookahead                                                 | Raw used | Shared keys remaining | Selected facts still required |
| ----------------------------------------------------------------------------------------------------- | -------: | --------------------: | ----------------------------: |
| No outer work, start                                                                                  |        0 |                   256 |                           511 |
| Call 1                                                                                                |      100 |                   156 |                           411 |
| Call 2                                                                                                |      100 |                    56 |                           311 |
| Call 3, fitting remainder only                                                                        |       56 |                     0 |                           255 |
| Illustrative real outer path instead: one prefix entry plus lookahead, one alias entry plus lookahead |        4 |                   252 |                           511 |
| Then calls of 100, 100 and 52                                                                         |      252 |                     0 |                           259 |

The four-key outer row is an example path, not a claimed complete outer allowance: original/terminal/source
checks, basis reconstruction, other sources/candidates/aliases and final work retain their real charges.
With an already known live source there may be no alias window; the zero-outer lower bound already fails.
Calls may not reserve101 in a Zone step with100 total remaining including lookahead. Choose at most the actual
remaining allowance, at most100 ordinary owner keys plus one expressly reserved lookahead; with a 100-key
reservation and one lookahead, ordinary work is at most99. An unused charged lookahead cannot advance coverage.

No native-axis credit offsets that key deficit. Necessary independent reservations are as follows; these are
lower bounds/accounting identities, **not observed SQL totals or proposed quantitative upper bounds**:

- Selected traversal needs at least 511 raw selected entries/physical rows for this proof. On the existing
  per-fact evidence path it also examines 511 witnesses. One call allows at most100 witnesses, independently
  of keys<=101. At least six witness batches would be needed if the key cap were removed.
- On the inspected body/normalization path for this quantity data, amount strings plus units alone total1900 UTF-8 payload bytes:
  `15*(9*2 + 23*3 + 32) + (9*2 + 22*3 + 31)`. Actual bodies, property names, identities, releases, revisions,
  metadata, discarded payload and returned fields add bytes. Metadata/length sentinel probes count before
  bounded bodies; no arbitrary body fetch is exempt.
- For actual distinct full basis reads B and canonical-coverage observations C,
  `Rows_reserved >= 511 + 8192*B + R_core + 4096*C + R_comparisons + R_other`.
  Required prepare/continuation/final identity phases each include a full basis read. Each coverage bracket
  includes two full bases (16384 metadata observations plus core), 4096 coverage points and 4096 native
  home/core comparisons. B counts those bracket bases too; do not add them twice when an actual read is shared.
- `Points_reserved >= P_selection + P_authority + P_foreign + P_basis + P_coverage` and
  `EmptySeeks_reserved >= E_selection + E_authority + E_foreign + E_coverage`, with actual observed terms.
  In particular an empty pair/value seek uses points/emptySeeks even when it yields no raw fact key.
  The number64 of requested alternatives is not automatically64 returned raw keys or a free batch.
- On that path, `Bytes_reserved >= 1900 + B_metadata + B_authority + B_other`; any different stored encoding needs its own actual byte accounting. Statements and transaction controls must
  independently cover slot/native/foreign/basis/coverage work. Engine postings, sorting, bytes and requests
  need their own measurements; the raw ledger and a result limit do not bound them.

The fixed-home and bracket costs are specified in [Search's scope/coverage contract](../../services/kernel/src/search/README.md).
No new constant points/rows/bytes envelope or native execution measurement is claimed here. The raw-key lower
bound alone falsifies the requested conjunction even with arbitrarily generous other reservations.

### Progress and convergence

On fixed finite ready input, a single selected-slot traversal has finite remaining work: at most its32 selected
identities (or33 compact operations), with a consumed ordinal advancing whenever sufficient work is reserved.
For the actual relation maintenance, a build's finite unprocessed possible-identity suffix shrinks by each
successfully committed page, followed by publication; after the last input change, fair completed maintenance
can finish. No constant whole-history rebuild cost or convergence time is claimed.

These measures do not give a final multi-leaf measure. After a request consumes256 keys, the unobserved final
selection deficit is at least255. The next request may retain one original, leaf ordinal and raw position,
but carries no certificates for the previously read slots. Reconstructing their **current** coverage restarts
their required observations. Thus no sequence of these calls reaches a final certificate within a request;
the final deficit has a positive floor. This holds after all maintenance is complete in a fixed state.
Permanently repeating readiness would be safe but fails the requested completion, and is not a proposed repair.

## Index alternatives: data access versus filter interpretation

Consider the strongest relevant neutral proposal without treating it as permission. Shared selected evidence
could maintain the following **query-independent** data, generated by the one existing resolver/normalizer:

| Proposed stored bytes                                                                                                           | Classification and authority                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `(sourceRoute, sourceUUID, property, witnessUUID, slot identity/version, release, recording/proposing revision, selected rank)` | Source-owned selected-data locator and local derivation version. Not an actor verdict or current foreign observation.                                                                                              |
| Normalized item/code value, finite amount+unit or year, with witness identity                                                   | A covering data copy/index payload for one selected fact. Still one fact identity per charged examination; not32 bodies packed as a single key. Public leaf data only, no private Collection/candidate-body cache. |
| `(source, property, qualifierProperty, qualifierItemUUID, witnessUUID)` for each actual item qualifier                          | Query-independent same-statement data membership. No saved qualifier conjunction, filter result, principal or arbitrary AST. Each examined posting/driver is accounted.                                            |
| Per-source requested/active/published generation and durable page frontier                                                      | Coalesced repair scheduling/completeness metadata, not current permission or negative truth. No request digest-to-locator map.                                                                                     |
| Provenance/target dependency locator                                                                                            | Owner routing metadata for a specific native identity, never cached fence/target/consent allow. These rows could be useful access structures. They do not implement a second selection truth: changes must
derive from `resolveSlot`/Global adoption and shared `indexedStatement` plus witness/fence/disclosure machinery.
No query-specific witness vector, saved range truth, encrypted owner body cache, permission store or hidden
holder directory is authorized. No such material index is asserted to exist today.

Here are exact hypothetical SQL operations, with route/source/property fixed to one native anchor. Snippets
describe the boundary under examination, not executable repository migrations or approved table names.

```sql
-- Identity enumeration: params (r int, s uuid, p text, after uuid, q int).
SELECT witness_id, normalized_data, release, revision, rank
FROM shared_selected_data
WHERE route = :r AND subject_id = :s AND property = :p AND witness_id > :after
ORDER BY witness_id LIMIT :q;

-- Ordered successor: params additionally (kind text, consumed_key bytea, consumed_witness uuid).
SELECT order_key, witness_id, normalized_data
FROM shared_selected_order
WHERE route = :r AND subject_id = :s AND property = :p AND order_kind = :kind
  AND (order_key, witness_id) > (:consumed_key, :consumed_witness)
ORDER BY order_key, witness_id LIMIT :q;
```

Identity enumeration and resuming after a genuinely consumed order key do not interpret R(p). Search would
still run its actual pure matcher. Even granting an index-only implementation and perfect completeness, these
operations cannot satisfy the existing whole-slot coverage condition without the511 charged fact identities.
Reading min/max once per slot would be a different absence proof, not `selection` as currently defined.

Now instead supply an encoded key computed from `(quantity, unit, filter.gte)` as the initial successor bound,
or use typed SQL `unit = :unit AND amount >= :gte AND amount <= :lte`. This does query-dependent range candidate
narrowing. It can return native data for Search to rematch, but the database has already used range/unit
comparisons to exclude candidates. Calling the operands bytes or the operation `seek` does not remove that
fact. Under the literal existing “Range/qualifier predicates are not SQL filters” clause this is prohibited
pushdown. Whether a **generic comparator over Search-encoded keys**, with no leaf AST received by Semantic,
should receive an exception is a concrete owner question. Neither the clause nor this report silently grants
one. Even a permissive answer about generic seeks would leave the explicit coverage definition unresolved.

Similarly, passing `(qualifierProperty, requestedItemValues)` into an SQL posting lookup, then intersecting by
witness ID (or requiring all qualifier postings by a HAVING count) performs qualifier candidate narrowing and
same-statement constraint work. Keeping a final Search matcher does not make that SQL operation neutral to the
qualifier rule. Merely sorting all qualifier atoms or returning them without query-based exclusion is innocent
data access; it may require reading many atoms. A composite order keyed by every possible requested conjunction
or precomputed filter class requires a specified storage/maintenance bound and interpreter boundary. It is not
proved by naming a B-tree, a bitmap, a cube, or a useful hint.

For64 alternatives, an equality-pair approach may try64 seeks per leaf before finding useful data; empty seeks
still spend native axes, and nonempty posting/candidate work spends actual raw keys. Qualified ranges can require
intersection of independently placed values/qualifiers on the same32 selected facts. A scalar order does not
prove a constant candidate count for that intersection. The actual expanded-leaf limit constrains the number
of qualifier clauses across the plan; it does not guarantee one-key discovery for each surviving clause. No
`four keys per leaf` upper bound follows, even though there are at most32 plan leaves and512 current facts.

### Other unadopted tradeoffs

- **Cross-request locator data:** query-independent shared selected-data rows are different from a per-request
  locator vector. The former may be ordinary source indexes with complete maintenance; the latter is excluded
  whether stored in a token, server map, digest lookup or encrypted owner record. Even permitting all positive
  witness locators would not discharge this example's whole-slot negative observations. A persisted coverage
  receipt would additionally change freshness/coverage authority, rather than just locator transport.
- **Query-dependent candidate narrowing with the same final matcher:** a possible design space if Root grants
  the boundary change, but not a proof of the current contract. It also needs complete negative certificates
  and independently bounded foreign residual work. Index work, failed candidates and revalidation still count.
- **Ledger/admission changes:** a ledger of511 is only this fixture's selected-fact subtotal, not a sufficient
  new universal budget. Outer work, expanded candidate/revision drivers, foreign checks and final checks remain.
  Reducing leaves, values, facets, selected facts or Boolean forms changes product admission. These are owner
  tradeoffs, not recommendations to enact. This report keeps every current limit and acceptance unchanged.

PostgreSQL's executor obtains tuples from an access method and applies residual qualification, retrying on
failures; index-only scans can still recheck lossy conditions. Its B-tree search uses explicit scan-key
comparators. These mechanisms separate access from residual truth, while making candidate exclusion real
work. Keeping a residual matcher therefore does not imply that an earlier native range operation did not
interpret the range. [PostgreSQL multicolumn-index documentation](https://www.postgresql.org/docs/18/indexes-multicolumn.html)
also explains why later-column constraints need not bound the scanned portion; naming a composite index is
not a cardinality proof for arbitrary qualifier conjunctions.

Jena's `TupleTable` updates each configured index on add/delete and chooses an index by the bound tuple pattern.
`TupleIndexRecord.findWorker` constructs min/max prefix records and scans residual fields when a useful prefix
does not cover the pattern. This is an established query-independent indexing pattern with query-dependent
access and explicit fallback, not a claim that all patterns touch one tuple. Its tuple membership also supplies
no REZICS viewer permission. The recommended transferable pattern is shared data/index maintenance and
explicitly accounted residual work, not copying Jena's query engine.

[PostgreSQL's covering-index documentation](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)
separates stored payload from MVCC visibility and explains the visibility-map/heap check. That supports the
general distinction between covering data and independent visibility authority. Applying it to REZICS's
foreign Access/fences is an inference from REZICS contracts, not a PostgreSQL authorization guarantee. Neither
source overrides the explicit full-selection negative certificate or authorizes a permission cache here.

The common pattern is precise access semantics, one maintained data authority, complete index coverage and
explicit residual/visibility checks. It supports investigating an owner-approved coverage/index seam; it does
not establish one under a rule that still requires reading all511 selected identities.
