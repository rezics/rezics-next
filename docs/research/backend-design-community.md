# Backend completeness: accounts, identity and community

Research date: **2026-10-31**. Inspected dev/worktree revision:
`6d3f767467c85dbb9d3bb561d12af784407bd92c` (the local `dev` and worktree HEAD agreed).
This is evidence and a recommendation, not an adopted contract or a completion certificate.
No installation, application startup, runtime measurement, test, compiler, gate or acceptance campaign was run.

## Findings that change the delivery assessment

There is substantially more backend implementation than the historical inventory suggests. Notifications,
content appeals, Realm/Space setup and lifecycle, identity presentation, mixed catalogue/account discovery and
Zone composition all have actual code and mounted operations. Calling these systems wholly absent would be
wrong. Calling them complete because their routes, declarations or stories exist would also be wrong.

The most consequential gaps are at **composition and release boundaries**:

1. Public scope admits static Zones, follow edges and minimal notifications; advanced search, dynamic Zones,
   hosted works, following feeds and recommendations have different closed/deferred boundaries. A UI request
   cannot make those capabilities public. The requested mixed home requires a coherent product slice and a
   scope amendment before exposure, rather than silently assembling a feed from follows or Search.
2. Source/Scope, Collection and Zone integrations are partly executable and partly deliberately unavailable.
   Some source comments/status reports now understate implementation; other missing native producers still
   prevent readiness. The particular request, owner support and current gate matter more than a module label.
3. In-scope moderation spans multiple authoritative owners, but content's minimal appeal implementation covers
   thread/post takedowns. It does not establish a common appeal journey for semantic facts, media, containers,
   account sanctions and commerce. A common case envelope with owner-specific remedies remains a design repair.
4. Accounts/Auth contain explicit outstanding erasure custody and producer obligations. An erasure request,
   immediate read fence, a participant ACK and actual deletion of all copies are four different facts.
5. The header has a real scope-chip abstraction; it is not an end-to-end scoped search implementation for
   Library, Collection, Realm, Space, Zone and Agent. The current public mixed search domain is Subjects plus
   Accounts, not all product records. Current Subject discussions/reviews and Collection cover code are more
   capable than older design-status text and the supplied filter screenshot imply.
6. Existing tests include native HTTP/database/effect fixtures as well as mocked transport/render tests and
   recorded UI data. None was executed here. Neither file presence nor a fixture's selective opening proves
   production exposure, upper-bound behavior, default worker assembly or a deployed journey.

## Backend capabilities the frontend actually needs

### Scoped search is membership plus disclosure, not a label

`search/header-search/types.ts` has Library, Collection, Realm, Zone and Agent kinds and optional `searchAction`.
It has no distinct Space kind. `authority.ts` allows scoped submission only to a supplied valid local action;
an unavailable scope must not silently search globally. `shell-search.tsx` passes scope/history/form fields but
does not supply `loadScopedSuggestions`; the header's scoped loader path can consequently be unavailable.
This is a valid safety fallback, not a delivered scoped product. Space inclusion/exclusion needs an explicit
backend domain adapter rather than treating Space, Realm and Context as synonyms.

The current mounted `subjects:search` has an actual `discovery-v1` branch. `DiscoveryKey` admits Semantic
Subjects and Accounts, `DiscoverySummary` has typed Subject/Account summaries, kind pages are capped at eight,
and `discovery-request.ts` explicitly closes saved/private domains and limits mixed sorting to id/name/relevance.
This corrects the old “Subject-only, no mixed route” claim, but it does not add posts, Collections, Realms or
private Library membership. Trending also has actual native storage/route/UI code; its README explicitly says
publication remains preparing because the qualified identity/definition/Account reduction binding is missing.

### Mixed home, sections and covers

The current `routes/index.tsx` calls `homePageQuery` for the common anonymous `/` configuration, then reads
personal Continue separately with private/no-store transport. This separation protects public SSR caching.
It does not produce a single mixed following stream. The SignedIn story in `stories/home.stories.tsx` explicitly
expects the unavailable Continue fallback; it is evidence that the refusal is represented, not that Continue
or a feed works against native Auth and Library. Kind-specific catalogue rows remain consistent with current
scope but do not satisfy the requested future mixed home.

For a future adopted feed, use one bounded heterogeneous item envelope and continuation across types, with
explicit ranking/selection basis, native author/target/cover summaries and final current disclosure. A fixed
number of deliberately curated home sections can coexist with that stream. Generating one section/request per
kind or per Realm/Context fails the settled upper bounds and must not become the default.

Subject sections have real newer wiring: `subject-community.ts` reads at most one native page per placed
discussion/review kind (preview five, full page twenty), checks returned subject/kind/publication and resolves
authors through a shared identity batch. `overview.tsx` connects `ThreadList`/`ReviewList` to those regions;
`RatingSummary` deliberately refuses Realm population. Therefore the old missing-callback report is not current
evidence of total absence. Sections still need coherent unavailable/closed/empty states, explicit continuation,
same question/population rating metadata and stable cover/rights summaries across home, search and Subject.

The supplied REZICS image has no visible covers in its title list; current `library/collection-page.tsx` imports
shared `Cover`, `CoverCard`, `CoverGrid`, reads native variants and builds `coverSrc`. The cause of that supplied
capture cannot be assigned to missing storage without its revision/variant. Audit the current chosen list mode,
summary projection and rendered slot together. The correction remains portrait **default** covers for every
kind, using the shared placeholder when absent; preserve landscape original dimensions/artwork inside the
portrait frame instead of forcing crop or distorting pixels. No new media type or per-kind renderer is needed.
Permission/withheld status, usable variants, intrinsic dimensions, credit/licence and accessible text must come
from the authoritative summary. An external image URL or a fixture cover is not proof of lawful availability.

## Authority, disclosure and lifecycle across areas

The architecture's one graph vocabulary does not mean one SQL join or one universal permission flag. Account
principal, acting human, operated account, client, Agent Subject, Realm membership, Semantic Context, Space
container, publication, content place, Collection membership and Zone membership have different meanings.

`deletion.md` sets soft delete/30-day restoration, separate least-data purge, takedown without deletion,
legal hold and minimal evidence. Account erasure is irreversible at T and does not wait for 30 days. Retention
exceptions and backups are separate from active cleanup. A source can de-identify eligible public contribution
attribution while erasing private/deleted material and published reading logs. Exact per-owner disposition is
needed for bodies, revisions, media, reports, actor/operator links, event/receipt payloads and prepared cursors.
The financial retention schedule remains an explicit external condition in the owning document; this report
does not invent a jurisdictional retention duration.

Community's container restoration already requires exact action, expected head/version and eligible current
native role; removing the Space hides its Realm and does not transfer the Context. Zone delete/restore routes
exist, but the README correctly lists native withholding/purge/account cleanup and worker completion as pending
obligations. Source-free public exposure is not an excuse to omit configuration/author/retained-work cleanup.
Content's 183-day minimal appeal window and notice retention of 180 days are different lifetimes: expiry of a
notice must not erase the independent decision/appeal read needed during the remaining appeal period.

## Upper-bound costs: static derivations, not measurements

probes, ancestry, foreign keys, allocations/bytes, retained work, lock duration and failure/retry work as well.

interpreter. A queued proof is not failed proof; no runtime proof was attempted here.

### Standards informing the recommendation

- [HTTP Semantics, RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted): 202 accepts work,
  not completion. Zone preparation, membership transition and erasure admission must retain distinct terminal
  meanings. IETF document copyright/BCP78 applies; code components use the document's stated licence.
- [OAuth 2.0 Security Best Current Practice, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), January2025:
  authorization-code/redirect/token protections remain an Auth protocol responsibility. Shared UI login state
  or a generated client does not replace current API authorization. This report does not certify conformance.
- [Google AIP-158 pagination](https://google.aip.dev/158): continuation tokens are opaque and not authorization;
  short pages need not mean exhaustion. Apply this to permission-filtered queues and immutable query binding,
  while retaining REZICS's existing token custody and limits.
- [ActivityPub Delete](https://www.w3.org/TR/activitypub/#delete-activity-outbox), W3C Recommendation 2018-01-23:
  protocol deletion/tombstone is distinct from physical all-copy erasure. No federation requirement is inferred.
- [WCAG 2.2 Understanding status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html):
  preparing, unavailable, closed and updated-count outcomes should be announced without unnecessary focus
  movement. This guidance supports, but does not prove, accessible implementation of the required phone panel.
