# Library abstraction: one engine, many verticals

Research evidence and recommendations, 2026-10-28. This report does not amend the contracts.

## Answer

The product rule calls for **one generic library capability**, configured by the subject type and the user's intent. The current kernel already has useful generic pieces, but its closed vocabularies, one exclusive entry state and physical-copy model are not sufficient to express the examples. Renaming book fields alone would not make a game library, recipe box and record collection equivalent. Use the same entry, session, copy, Collection and publication engine for all three; add the generic capabilities below, not vertical-specific subsystems.

An entry state is one explicit, optional personal assertion; independent labels and lists can overlap it. A session is a distinct occurrence, not proof of ownership or an automatic rating. A copy is an identified holding, not a right to run software. A Collection is a curated sequence of subject occurrences; a saved query is a different kind of view. Keep these distinctions even when a UI presents them together.

### Local evidence and constraints

- `services/kernel/src/library/README.md` describes owner-partitioned private entries, sessions, copies, and ordered Collections, including repeated subject occurrences; only public Collections and explicitly published logs are public. `collection-model.ts` and `entry-model.ts` show occurrence identity, one entry state per subject, and multiple private copies. `copies.ts` validates a fixed status list and has no copy kind, condition or rights model.
- `entry-model.ts` fixes `planned`, `in_progress`, `completed`, `paused`, `dropped`; `progress.ts` fixes `scalar_amount`, `cursor_position`, `completed_units`, and page/chapter/episode/volume/minute/percent. The three modes are different algorithms, not interchangeable labels. Sessions have explicit active/completed/abandoned transitions and a reread is a new session. `progress-model.ts` stores the mode and unit but does not itself provide the accepted structure revision and migration protocol.
- `packages/definitions/README.md` and `packages/definitions/release/rezics.json` show compiled type metadata such as `coverRatio`, class annotations, inheritance, and existing game and recipe filters. A new library profile needs schema/compiler/release changes; arbitrary nested annotations in the example below are a **proposed release representation**, not current supported catalogue syntax.
- The read-only discussion reference `docs/engineering/11-schema-classification-and-vertical-profiles.md` §§6–9 specifies stable unit identity, explicit session completion, sparse completed-unit sets, version-aware migration, separate ratings and copies, and private personal data. Its `GLOSSARY.md` distinguishes Library from Collection. `docs/engineering/07-whole-system-and-product-capabilities.md` and `contracts/definitions.schema.json` provide broader capability and existing view context. The glossary's reading vocabulary is a historical example, not authority to restrict other verticals. Current repository contracts take precedence when they differ.
- `bulk-contract.md` describes a proposed bounded operation protocol with selection binding, per-target outcomes and slot-generation fencing; `listing-freshness-contract.md` describes a privacy defect and proposed monotonic projection repair. Neither should be described as already implemented solely because the contract exists.

## Proposed definitions annotations

Compile a type's inherited `library` annotation alongside `coverRatio`, with explicit deterministic nearest-base precedence and ambiguity rejection. Example is illustrative release JSON; names, source syntax and limits need owner agreement:

```json
{
  "library": {
    "entryStateSet": {
      "id": "game-state-v1",
      "states": [
        { "id": "planned", "labels": { "en": "Want to play" }, "role": "planned" },
        { "id": "playing", "labels": { "en": "Playing" }, "role": "active" },
        { "id": "finished", "labels": { "en": "Finished" }, "role": "completed" }
      ]
    },
    "progress": {
      "allowed": [
        { "mode": "scalar_amount", "units": ["minute", "percent"] },
        { "mode": "completed_units", "units": ["achievement"] }
      ]
    },
    "copies": {
      "kinds": [
        { "id": "physical", "statuses": ["ordered", "owned", "lent", "disposed"] },
        { "id": "digital_license", "statuses": ["ordered", "owned", "disposed"] }
      ]
    },
    "importSources": ["steam", "backloggd"]
  }
}
```

- **Entry state sets:** stable scoped identifiers, localized labels, optional semantic role and explicit permitted transitions/defaults if needed; never use label as identity. One state slot remains exclusive. Labels, wantlists, holdings and sessions remain independent, so `playing` and `wishlist` can coexist. A type without a profile may omit the capability; the existing five states form a migration profile preserving existing values.
- **Progress modes and units:** types declare allowed pairs and unit metadata (identifier, label, dimension, numeric bounds/precision and optional total policy). The engine still implements and validates the three generic algorithms; definitions select them, they do not inject executable code. Unit conversion requires an explicit compatible rule; percent remains bounded. Mode additions require engine support, not configuration masquerading as new code. Stable episode IDs and structure revisions are required for sparse sets; time, episode count and cursor cannot be silently converted to each other. Achievements in the example are selectable only after a separately supported unit-identity contract; otherwise omit them.
- **Copy kinds and statuses:** declare type-appropriate stable kind/status IDs, localization, allowed pairs and typed bounded attribute schemas; keep record identity, revision and privacy in library. Structured platform, store, condition, folder and external entitlement provenance are future primitive fields, not arbitrary unvalidated blobs. A digital holding is a personal assertion, never an entitlement grant.
- **Import sources:** use stable source IDs, compatible subject types, supported bounded record kinds and mapping version in the definition profile; credentials, endpoint configuration, OAuth and permissions belong to kernel-wide trusted adapters, not public definition data. A declaration alone does not enable an adapter. Import identity and provenance must distinguish observation from user assertion.

Bind every stored value to the exact definition release/profile revision under which it was accepted. Compile validation and localized labels from that release, constrain inherited conflicts and limit configuration sizes. Additive labels can evolve without rewriting data; removing/renaming IDs, narrowing allowed pairs, inheritance changes or changing a role needs a versioned migration, explicit mapping and compatibility policy. Preserve unknown historic values for reads; reject unsupported new writes and do not silently coerce or delete existing data. Pin query/cursor meaning to the resolved profile and handle retired definitions deliberately. Defaults must never manufacture a completed session, holding or external identity.

## Ordered contract changes for owners

Costs below are proposed worst-case work/resource bounds, not measured estimates; each contract change needs tests for these bounds before adoption. `P` is configured page size, `N` selected targets, and fixed caps must be stated by the owning contract.

1. **Definitions and library: versioned profiles and migration.** Define the four annotations, inheritance/conflict rules and release pinning; inventory existing rows and map current fixed keys without semantic loss. Compiler/read validation is bounded by declared profile size, independent of library size; writes require one profile lookup, and migration scans at most `P` rows per checkpoint. Test old release replay, unknown IDs, inherited conflict, rollback and all three sample verticals.
2. **Library: independent state, labels, sessions and projections.** Specify optional exclusive state plus bounded independent labels, repeat occurrences, partial dates and aggregate observations. Define explicit command intent and session count/last-activity projection, including imported counts with unknown dates. Single-target writes touch a fixed number of rows; aggregate repair is paged `O(N)` with `O(P)` memory, never a full synchronous scan. Test simultaneous wishlist/playing, two reads, two cooks, sparse episode set and count-only import.
3. **Library and definitions: typed holdings.** Add kind/status, typed attributes, copy-level folder membership and source-scoped access observations. One copy mutation touches a fixed number of rows with bounded attribute bytes; folder changes use paged bulk work. Test two copies of one release with different grades, multiple storefronts, and shared access without ownership.
4. **Kernel-wide query/list owners: saved query views and shared cursor.** Define bounded query language and indexed predicates for personal data, disclosure, sorting, release/generation binding, and dynamic versus manually curated lists. Page reads examine a contractually capped candidate budget and return at most `P` items; unsupported filters fail explicitly. Test hidden state, dynamic membership changes, private-data isolation and cursor basis changes. Apply to Collections, rankings, wishlists and Zone curation as their owners adopt it.
5. **Kernel-wide import and library adapters.** Define source IDs, authorization, source record identity, preview/confirmation, bounded batches, idempotent receipts, mismatch and deletion policy, partial/fuzzy dates and provenance. Work is `O(N)` in pages of at most `P`, with bounded retries, source rate limits and per-item outcomes; no full account-sized transaction. Test duplicate replay, ambiguous matches, partial remote results, revoked access and preservation of local edits. External account connectivity is subject to provider access and terms.
6. **Publication, rating and goal owners: occurrence-linked snapshots and goals.** Specify optional per-session rating references, independently published snapshots, aggregate observations and rule-versioned goals/challenges. Recompute in bounded `P`-sized pages, update incrementally with idempotent event identity, and define visibility before any aggregate is disclosed. Test historical ratings versus current vote, reread eligibility, undated events and withdrawal.
7. **Kernel-wide list/work owners: extract protocols, retain domain adapters.** Generalize bulk, retention, cursors and monotonic projection only after the existing library defects and prerequisites have owners. Each batch has fixed candidate and write budgets, no fan-out proportional to the entire account in one transaction; total maintenance is `O(N)` with checkpoints. Test stale-event reversal, authorization revocation, delete/recreate ABA, cancellation, crash/replay and purge fences for each adopter. Preserve the library's existing 5,000-member and outcome-page bounds unless its owner changes them.

Shared source patterns are explicit personal state, independent named groupings, repeated activity and externally sourced data. The differences that matter are equally clear: an exclusive anime status cannot express concurrent game wishlist and backlog; an aggregate reread count cannot recreate dated history; Discogs folders classify individual copies; and Steam family access is not permanent ownership. These are reasons to add generic primitives with explicit contracts, rather than encode each product as a separate vertical engine.
