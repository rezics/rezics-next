# Access growth shadow triage

The unit of this report is one listed check/metric occurrence. File paths in the table are relative to
`services/kernel`. R means work exceeding its declared derivation; B means an inadequate bound/model;
N means state noise; T means a defective measurement fixture or scale axis. Each row has one primary class:
a known fixture defect takes precedence over attributing its effects to noise.

The derivations come from the [Access Cost rows](../../services/kernel/src/access/README.md#cost), the eleven
listed test files and their native SQL/index definitions in `db/access/schema.sql`, the Community Realm role
reader, and Auth's `current-consent.ts`/schema. Measurement semantics come from the kernel README's
[Growth checks](../../services/kernel/README.md#growth-checks) and `test/support/growth{,-cost,-bound,-model}.ts`.
No production code, existing test, bound or calibration value is changed by this report. Access owns the
test/SQL corrections; Performance owns classifier changes, with Access adopting any revised Cost bound.

Use the supplied calibration, not the looser checked-in shadow defaults: rows have radius 22, blocks have
radius `max(9, 0.03 × median)`, and statements have radius zero. The maximum implements the harness's absolute
floor/relative allowance convention. A constant row series therefore needs a common intersection of its
22-row intervals; a range exceeding 44 fails even if every increase is below the old 10% slack. A decrease
can fail the new rule too: every allowed family has a nonnegative slope, while the old step rule lets cheaper
later plans pass.

`classifySeries` tests affine constant/log/linear curves, which are narrower than Big-O classes. Indexed
buffer work is a sum of discrete tree traversals and page accesses. A depth or layout transition shared by
many point probes can exceed the calibrated block allowance without becoming a full relation scan. Such a
model mismatch is B; it is not evidence that the repeatability calibration should be enlarged.

Unless a row says otherwise, the harness supplies one warm-up per scale and five measured repetitions.
The declared bounds are constant rows/statements and logarithmic blocks, except manifest changed resources,
the evaluator K axis and total operator fanout, which declare all three metrics linear.
`[occurrence 2]` identifies another occurrence in the supplied coverage list. There is only one source
check declaration for each corresponding name; the duplicate receives its own row and the same derivation.
The coverage run's original counts/plans were not supplied, so a new run must not be presented as a replay
of either original occurrence. Classifications identify the defect or model correction justified by the source;
static plan-crossover explanations are not claims that a particular original EXPLAIN plan was recovered.
Here `L(R) = O(log(2+R))` is indexed point work. Access's Cost section qualifies temporal GiST work as
`I_T(x)`: selective measured paths can follow `L(T)+x`, but the schema alone does not guarantee that
worst-case shape. The B rows preserve that qualification rather than granting every GiST traversal a
logarithmic guarantee.

Measurement notes: static analysis left supporting-history plan choices and GiST layout ambiguous, so only
`growth-durable-initiator.test.ts`, `growth-evaluator.test.ts` and `growth-operator-fencing.test.ts` were profiled.
One completed normal `bun run --cwd services/kernel check` invocation named those three files with
`GROWTH_PROFILE` set; the normal runner automatically retried the failing fencing file alone. An earlier
transport failure interrupted the command after durable initiator; it supplied no returned profile and was retried.
The numbers in the table come from the first execution of each check in the completed command, reclassified
offline with the supplied calibration. They are not the checked-in shadow defaults or the original coverage run.
Durable initiator's 12 tests and the evaluator's two tests passed. Fencing's unrelated-account first/late pages
and total fanout failed the old rule as well, on unchanged base SQL/tests; the isolated retry had identical row
series. Its other two tests passed. These existing fixture failures are evidence for the report, not code changes
to make in this specification task. No additional growth command was run.

The 27 listed metric occurrences classify as **R: 0, B: 5, N: 0, T: 22**. Duplicate coverage labels count
separately in those totals. This does not certify every production path: the test fixes must establish
representative point access before the old rule can be replaced safely.

The recurring test defect is an unseeded supporting history, even where the main account or responsibility
relation already has thousands of decoys. Receipt, continuation-entry and fence-receipt work belongs to the
operation's cost. Tiny-table scan crossovers and repetition-driven history are predictable fixture effects,
not justification for raising the 22-row floor. The manifest uses the wrong independent variable, and the K
evaluator grows the supposedly fixed reference population.

The B cases point to the model family rather than a universal uncertainty increase: an affine logarithmic
curve does not cover discrete indexed page transitions, and total fanout buffers include changing index sizes
as well as changed-account count. Keep the Cost derivations, constant row/statement obligations and named
access assertions; change the model features or bound description explicitly. No row establishes a noise
mechanism that independently requires more than 22 rows or `max(9, 3%)` blocks. Hint bits, visibility-map
changes, HOT pruning and vacuum can affect buffers, but naming them without equivalent-state repetitions is
not evidence for class N or for a new calibration. Cache warming alone cannot explain this block metric:
it sums shared hits and reads.
