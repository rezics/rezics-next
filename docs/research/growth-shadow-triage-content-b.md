# Content growth shadow triage

Inspected on 2026-10-28, at base `cb7f4b3e99`. This is a diagnosis and an owner
follow-up list; it changes neither production code nor acceptance tests.

The uncertainty supplied for this triage is 22 rows, and `max(9, 0.03 × blocks)`
blocks per median; statements are exact. The maximum, rather than the sum, is
how `growth.ts` interprets absolute and relative uncertainty. The checked-in
`growth-uncertainty.ts` still contains the older defaults. Any measurements below
are reclassified with the supplied values, without changing that file.

Here, N is the check's scale; H is the actual indexed relation size, including
pre-existing fixtures; k is the operation's changed-document count. A point read
has constant logical candidates and O(log(2 + H)) indexed blocks. A fixed page
has the same bounds multiplied by its fixed candidate cap. This follows the
content README's Cost rows, including their Access (A) and command (C) terms,
and the actual keys in `db/content/schema.sql`, `db/access/schema.sql` and
`db/community/schema.sql`. Shared indexes grow across routes; a hot partition
is not a physically separate B-tree.

Rows include scan candidates removed by filters/rechecks, multiplied by loops
(`growth-cost.ts`), rather than just returned objects. A small sequential scan
can therefore make an exact lookup appear to have *decreasing* row cost when
it switches to an index. That is not vacuum or hint-bit row noise. Blocks count
shared hits plus reads, so merely warming the buffer cache does not remove a
block access. `classifySeries` requires a nonnegative affine constant, log or
linear curve through every median interval; the old step rule can pass a large
decrease or a plan transition. Neither result alone establishes its cause.

All checks use one warm-up per scale. The table gives the explicit number of
measured repetitions (five where the check leaves the default). A T classification
identifies a concrete fixture, state or measurement-axis defect; it does not
assert that every SQL statement used the same plan in the original coverage run.
Small-fixture plan transitions are test defects here because the kernel growth
contract requires representative, growing read relations at the first scale.
They are not a reason to enlarge calibrated uncertainty.

Counts: **R 2, B 1, N 0, T 19** (22 metric rows). Both R rows are the same
intentional negative control; they require correct inventory handling, not a
production fix. T takes precedence where the code proves a fixture/state/axis
violation of the kernel README, even though that defect does not identify every
plan in the historical coverage run. No unmeasured row is attributed to vacuum,
hint bits, visibility-map state, HOT pruning or random statistics without evidence.

The main pattern is small first-scale read populations and non-equivalent write
state. Constant row cost is appropriate for exact identities and fixed candidate
caps; filtered small-table scans can make that series drop by far more than 22.
The measured `read` series demonstrates this directly. Increasing row uncertainty
to cover it would hide scans. The protected-member series exposes a separate
classifier issue: the specified affine-log operational family is narrower than
the README's indexed-work derivation. Its stable repetitions and simultaneous
per-probe block steps are structural work, not within-scale state noise. The
calibrated 9-block/3% allowance should not silently absorb that model difference.
No global uncertainty increase is justified by these diagnoses.
