# Collections and covers: source, product evidence and delivery gaps

Research date: 2026-10-31. This report is evidence and a recommendation for adoption by the owning documents. It does not change a contract, activate a capability or establish acceptance.

The user job is to recognise, find, browse and curate works in a Collection, including a mixed Collection with millions of items. Readers need the work's image identity, title and useful supplied facts; curators additionally need occurrence notes, ordering and safe edits. Anonymous readers, another signed-in reader and the curator have different disclosure rights. A missing image must not make an otherwise readable work disappear.

The main findings are:

- Current Collection rows do render member covers and useful placeholders. The regression is more specific than “covers are absent”: the hero drops its frame when its cover is null; mixed grids apply incompatible per-kind frame shapes; the single header search is not connected to Collection scope or its Filters action.
- Old REZICS already separates a universal portrait frame from the source image: its foreground uses `object-contain`, with a blurred image behind it. This is a directly relevant behaviour reference. Current shared `Cover` already has most of the necessary image-preservation machinery.
- The public mixed grid visibly contradicts the settled portrait default. Its Film and Recipe frames are landscape and its Album frame is square. The current source retains the same policy in both released presentation hints and client fallbacks. A renderer that supports several ratios is not evidence that its defaults are correct.
- Backend capability is neither wholly absent nor complete. Real FULL cover projection, native list-fact production, configured Collection media authorization and a substantial Collection Source implementation exist. Complete nonempty automatic kind derivation, ordered member-cover fallback, scoped text search, current query-level disclosure and several source/preparation bindings remain separate gaps.
- Existing tests protect valuable components and native boundaries, but count checks, source-string assertions, constructed facts and small recordings cannot certify a useful Collection journey. The reused public audit even records a failed phone story assertion alongside a readable screenshot.

## Current dev: the exact presentation and search seams

### Covers, missing art and heterogeneous rows

`apps/web/src/library/collection-page.tsx` exports `CollectionReadMembers`. Readable members use `CoverCard` in grid mode and the shared member list row in list mode, passing the member's own `subject.cover`, actual type, optional released presentation and supplied FULL facts. Occurrence notes remain separate from subject facts. Public rendering filters inaccessible subjects before display; the owner/editor can retain an unavailable occurrence. A null subject takes a text-only unavailable branch in this renderer, unlike an ordinary readable subject with `cover: null`.

The header at `data-slot="collection-hero"` renders its `Cover` only inside `page.cover ? ... : null`. Consequently, a Collection without an authorized cover loses its Collection frame. Member-cover policy and Collection-cover policy are separate: satisfying one does not satisfy the other. Recommend a stable generic Collection placeholder for the hero, and an identity-free placeholder for an already-authorized unavailable occurrence; never disclose a hidden subject to fill a frame. The public renderer must continue omitting concealed occurrences altogether.

`apps/web/src/library/collection-presentation.ts` has explicit fallbacks: Book/Instance/comic/publication volume 3:4; Movie/TV/Season/Episode/AnimeRelease and Recipe 16:9; Album 1:1; unknown uses `coverRatio` then square. A released `listPresentation.imageAspect` wins first. `packages/ui/src/components/list-presentation-model.ts` repeats the released-type fallback policy. `docs/collection-presentation.md` and `packages/ui/README.md` still describe the earlier landscape/square defaults. This is a concrete policy-propagation gap against the newer settled universal portrait requirement, rather than a missing low-level ratio capability.

`packages/ui/src/components/cover-card.tsx` resolves a member presentation and passes it into `Cover`; `cover.tsx` selects that presentation aspect before the surrounding ratio. Thus `CoverGrid`'s Collection-level ratio does not enforce a common visual slot. The reused public mixed grid exposes the consequence. Collection kind must not change member type, but neither should type metadata silently override a surface's agreed default frame.

`packages/ui/src/components/cover.tsx` and `cover-model.ts` already provide:

- Reserved aspect-ratio boxes and intrinsic image dimensions, lazy loading, AVIF/WebP variants, focal position and source credit.
- Deterministic subject-ID colour/title placeholders; bounded decoded-placeholder cache; the same box on missing variants or image error.
- A contain strategy when source/frame aspect differs by more than 15%, with a blurred decorative background; near-ratio images use cover and may crop a little.
- A suitability-withheld/reveal UI. This UI capability does not establish that a real backend response supplies every suitability state. Security-denied/taken-down media must remain absent and must never be revealed by a client control.

The normal `SubjectCover` in `apps/web/src/library/subject-row.tsx` uses a 96-pixel `sm` frame. Collection's actual `MemberListRow` is in `packages/ui/src/components/list-presentation.tsx`; the published list appears approximately 96 pixels on desktop and 72 on phone. The screenshot is the visual evidence; a different shared row's named size alone is not a final rendered measurement.

Grid auto-fill in `cover-card.tsx` has medium minimum 8.75rem (140 pixels), small 8rem and large 10.5rem, with an 8-pixel gap. Collection currently uses its default density. The optional fixed-density mode is a component capability, not a Collection setting exposed to readers. `coverSizes('fill')` in `cover-model.ts` returns `100vw`, which overstates a multi-column card's actual width and can select unnecessarily large variants. This is a resource-selection defect even when the frame looks correct.

### Header field exists; Collection scope does not reach it

The common header is real: `apps/web/src/shell/shell.tsx` installs `HeaderSearchFilterProvider` and `ShellSearch`; `apps/web/src/search/header-search/header-search.tsx` contains a scope chip, one search input, a trailing Filters action and a responsive phone full-screen dialog. `filter-region.tsx` provides an explicit route-to-header registration port. `authority.ts` refuses scoped submission without a safe local `scope.searchAction`; a label alone never supplies authority.

However, `apps/web/src/routes/collections/$id.tsx` neither supplies a Collection scope/search action to the shell nor registers its filter region. It validates `cursor`, `layout`, `type`, and `f.*`/`r.*`/`l.*`, without a Collection `q`. `ShellSearch` therefore remains global on this page. `collection-page.tsx` and `dynamic-collection-page.tsx` mount their own `CollectionFilters` in the body. A component containing a scope chip is not an exposed scoped Collection journey.

`apps/web/src/library/collection-filters.tsx` puts a substantial form inside shared `Menu` custom content. The exact width disagreement is visible in source: `packages/ui/src/components/menu.tsx` sets the desktop custom-content wrapper width to `Math.max(trigger.width, 128)`; the child form requests up to 32rem from the `sm` breakpoint. The wrapper background and child controls can disagree by hundreds of pixels. This explains the supplied crop without attributing it to a random missing CSS rule. The shared menu's generic item sizing was reused for a form requiring a different measured surface.

Other capability limits are explicit:

- The form exposes the first eight configured facet properties for one chosen type; the Collection page defaults that filter type to Book. This is configuration-driven, but it is not a complete heterogeneous query composer.
- Concept suggestions request global `/api/search/suggestions`, then filter the returned small set by target type and slice to eight. This can miss relevant allowed choices outside the global top results. It is neither a complete facet dictionary nor scoped Collection suggestion search.
- `collection-filter-params.ts` adapts property membership and inclusive quantity ranges to the shared `FilterDocument`; it does not invent a separate backend interpreter. The range form has only from/to bounds. “Over 1,000,000” must not silently mean inclusive 1,000,000; absent values must remain nonmatches. Current shared `packages/filter/src/filter.ts` admits `gte`/`lte`, not a `gt` key. An exact admitted expression needs to be agreed with the existing compiler, including integer versus general-quantity semantics; a UI label cannot repair this.
- Curated pagination correctly uses `collectionViewAddress` in `collection-page.tsx`, which wraps `collectionPageAddress` and restores `layout=grid`. In contrast, filter submission in `collection-filters.tsx` constructs a new URL from type/facet fields without layout, so applying a filter resets a selected grid to the default list. The precise defect is filter-state transport, not an absent grid renderer or broken curated continuation.
- The shell search container is `flex-1 md:ms-6 md:max-w-[40rem]` beside asymmetric branding/actions. That caps width without guaranteeing centring in the whole viewport. Header search also applies focus-within rings and distinct expanded surfaces. These source facts explain the class of complaint; this report does not duplicate the independent header research's full visual investigation.

The correction is one route-owned query model connected to the existing shell ports: centred field, visible Collection scope, right-end Filters, and phone full-screen search. The form may live in the opened filter surface; there should be no second persistent inline panel or separate Collection search input. Scope removal must be explicit, clear stale cursors and visibly change the destination; an unavailable scoped operation must not silently run a global search.

## Backend truth and capability matrix

Status words below are deliberately narrow. “Implemented” means a callable body was inspected. “Exposed” means an actual route/DTO or interface wiring was found. Neither means executed or complete. No test in this report was run.

### Cover and fact authority

`services/kernel/src/semantic/summaries.ts` owns the bounded shared `SubjectSummary`, including actual type/ancestry and nullable `CoverSummary`. The latter carries media identity, dimensions, placeholder, variants, focal point and credit. It selects adopted `schema:image` facts and uses Content checks; it is not a browser guess at an image URL. `services/kernel/src/content/cover-reference.ts` and `media.ts` own native media reference/download authority. Imported-source fences and takedowns remain Content/Imports responsibilities. A Collection membership grant never grants image access.

`services/kernel/src/library/views.ts` implements curated FULL member reads with the native ordered member page, current Access, signed cursors and final membership revalidation. The page limit is at most 100. `collection-list-facts.ts` then makes one original-keyed fact batch over the raw prefix, preserving duplicate multiplicity for its 100-input bound; it batches summaries, checks original-to-terminal mappings again and verifies equality before attaching facts. Its source explicitly requires releasing the Collection checkout before foreign reads.

`services/kernel/src/semantic/list-presentation.ts` now has a substantial native `readListPresentationFacts` body, not an unavailable stub. It observes released type/property selection, statements/provenance, original and terminal identity, account/source/tuple disclosure, related-item labels and repeated currentness; unready evidence throws `semantic_not_ready`. The output limit is four configured properties and three values each, not a licence for unbounded hidden work. `packages/definitions/src/compile.ts`, `src/portable.ts` and `schema/release.json` also now compile/validate `listPresentation`, including inherited whole-object replacement and effective fact keys.

Configured Collection cover support also exists: `collection-presentation.ts` validates the existing media reference through `checkMediaObject`, `decideDownload`, then rereads the descriptor. `collection-reads.ts` exposes only authorized cover data, separately limits configured media identity to the editor, and rereads Collection source/revision after foreign work. But `collectionPresentation` returns only `owner`, `none` for proved empty, or `pending`: its actual body does not produce the DTO's `member` fallback. A schema union permitting `member` does not implement ordered fallback.

Automatic presentation kind has a complete reduction function and native preparation integration in `collection-kind.ts` / `collection-kind-preparation.ts`. The latter explicitly leaves complete nonempty audience/type evidence unavailable pending the scoped producer. It must not count the first page, count duplicates as extra votes, or disclose hidden types. A portrait default removes any need to wait for kind derivation before giving a readable Collection a stable frame.

### Search/source authority

`services/kernel/src/library/collection-routes.ts` mounts `GET /v1/collections/:collectionId/members` with BASIC/FULL, signed cursor, optional serialized `filter` and `sort`, and explicit 202/422 outcomes. There is no named Collection text `q` transport on this route. Filter/sort reads dispatch through the common Collection read machinery; an unfiltered curated FULL read uses `views.ts`. Treat these as distinct paths when assessing readiness.

`services/kernel/src/library/collection-source.ts` now implements `createCollectionSource`: prepare, prefix, contains, raw/ordinal traversal, work receipts, current metadata authorization and source/identity checks. Its fixed storage drivers are entry, label, session, copy, curated member and output mechanisms, not a hardcoded list of book/anime kinds. Ordinary ready handling explicitly accepts curated/private builtin authority and rejects unsupported public/frozen capture authority. Missing canonical evidence returns typed unavailability. This is substantial native work, but does not prove complete public membership/search execution.

Search's service-bound scope is in `services/kernel/src/search/scope-source.ts`, `service-scope-order.ts` and the native scope adapters; Library's owner filter bindings and publication/kind preparation consume it. The `scope-source.ts` prepare path still explicitly refuses a Collection-native path after checking its prerequisites, and the Search README records incomplete scoped leaf/public capture/current owner authorization and query-level privacy-reduction acknowledgement. Public output, private owner facts and current semantic disclosure are different authorities. A successful global subject search or Collection ID chip cannot substitute for them.

There are document/source contradictions worth handing back to owners. `docs/collection-presentation.md` still says definitions have no `listPresentation` and the list-fact helper is not implemented; both now exist. `docs/research/design-status-search.md` describes Collection Source as unavailable in a way that predates the substantial native factory now present. Conversely, a new factory does not invalidate the remaining native-readiness limitations in Search/Library READMEs. `docs/research/design-status-commerce.md` describes missing kind/cover enrichment broadly; configured cover projection and native FULL facts are now narrower real capabilities. These inventories need dated updates, rather than replacing pessimistic prose with a blanket “done”.

### Shared patterns and real disagreements

The common pattern is a stable visual identity plus adjacent truthful title/metadata, multiple presentations over the same membership, explicit local scope, and separation of manual organisation from live rules. Missing/deleted/unavailable records need a meaningful state, and Collection deletion differs from deleting the underlying work or media. Preview artwork, user-selected artwork and the member's own cover have different jobs.

Products disagree about ratio, density, masonry versus ordered grids, limits, and whether state or a manual list is the primary organisation. Steam's portrait library capsule and landscape hero show why an asset's orientation must not define every slot. Notion and old REZICS show whole-image fit; YouTube shows a valid landscape-first video product; Jellyfin makes shape configurable. None overturns the already-selected universal portrait default here. IMDb and Discogs document limits rather than claiming unlimited scalability. No inspected product source proves that its complete user journey supports a million-item Collection with REZICS's disclosure model.

## Recommended presentation at 1280 and 390

This is an adoption proposal, not a new default silently implemented by this report. Resolve the existing portrait ratio token to 3:4 for Collection slots: it is already released, used by old REZICS and current Book lists, and changes fewer contracts than introducing another ratio. The component's old 5:7 work-family fallback remains a separate compatibility concern for its owner. All kinds, including anime, games, albums, recipes and unknown future kinds, receive the same default portrait slot on Collection browse surfaces. Preserve explicit image dimensions and any intentionally selected alternate presentation; never infer layout policy from an image's width or a kind label.

Desk geometry, not measured acceptance: with a 256-pixel navigation column and 24-pixel content margins at 1280, available width is about 976 pixels. For minimum width `m=140` and gap `g=8`, `floor((W+g)/(m+g))` is six columns, with actual frames about 156 pixels. At 390 with 12-pixel margins, W=366 gives two 179-pixel frames. The exact shell container must be observed after adoption; a fixed card count in a four-member fixture cannot establish these limits. A 72-pixel 3:4 list frame is 96 pixels high; with 16 pixels of vertical padding, a 112-pixel base row can display roughly five rows in a 600-pixel member region, before expanded notes. Long localized titles and facts legitimately reduce that density.

### Landscape in a portrait slot without identity damage

Use one reserved portrait box with an uncropped, correctly proportioned foreground. `object-fit: contain` preserves the source aspect and the complete image; `cover` can crop. This is the standard sizing distinction in [CSS Images Level 3](https://www.w3.org/TR/css-images-3/#the-object-fit), retrieved 2026-10-31, a Candidate Recommendation Draft with W3C document-licence terms. Do not stretch, synthesize missing cover content, trim logos, or substitute unrelated artwork because a landscape image has empty space around it.

For a 16:9 image inside a 3:4 frame, a 179-pixel-wide image is about 101 pixels high inside a 239-pixel-high frame: approximately 69 pixels of space above and below. A 72-pixel list frame contains a 72×40.5 image inside 72×96. Those are honest constraints. Keep the title readable alongside the frame, allow opening the authorized full artwork, and permit a genuine alternate portrait asset only when the backend supplies a separately authorized, credited asset role. A blurred duplicate or neutral theme background may fill the space decoratively; prefer neutral fill for low-power/reduced-transparency contexts and never let the background become a second readable or independently loaded identity image.

Retain the current reserved-box, error and thumbhash/colour placeholder machinery. A large fallback can show a few title words; the actual adjacent title remains authoritative. Small placeholders should use a clear generic image marker rather than unreadable miniature text. Keep decorative duplicates out of the accessibility tree and avoid announcing the title twice. Credit remains available through a keyboard-operable control without creating a focus trap inside the stretched card link.

The current 15% ratio-tolerance crop is a separate choice from landscape containment: it can still trim near-portrait title lettering. Recommend whole-image containment by default for identity artwork, with explicit crop only for an intentionally authored alternate presentation. This is a local presentation policy correction using existing primitives, not a new backend image transformation capability.

At one million members, even an illustrative 1 KiB per client member would be about 1 GiB before images/DOM overhead; that is a reason to prohibit all-member client materialisation, not an observed record size. At K=200,000, even 100 bytes per kind is 20 MB before object/option overhead. A kind catalogue can be complete on the server without being rendered as a complete control list. Similarly, a public count may be maintained with proper audience/disclosure semantics; it must not be reconstructed by traversing pages or leaked from private source metadata.

Owner-private state, labels, holdings, progress and live dynamic rules must not appear in public Collection URLs/HTML, public exports, scope history or shared cache keys. Public output is an explicit complete publication, not an evaluation of a curator's current private facts. Unlisted discoverability, access by known URL and private membership are distinct. Signed cursors bind query/order/viewer/current source rather than granting permission; stale cursor recovery must keep the query and selected layout and explain a restart.

Image withdrawal/takedown must remove the usable media reference and derived identifying preview where required, not merely hide the `<img>` with CSS. Suitability blur/reveal is different from a security denial. Reimport must respect Content/Imports source fences. Collection deletion, removing an occurrence, clearing a Library state, deleting a subject, removing a downloaded copy and revoking publication are separate actions; compare-and-swap revisions, idempotent receipts and Undo cannot be replaced by optimistic local deletion.

Cross-surface consistency includes public/unlisted/private curated pages, Everything/state Collections, saved dynamic views when executable, mounted Zones, search results, Library rows and compact references. They should consume the same authorized cover/fact envelope and presentation policy. Any non-work subject uses the selected generic Collection frame without being recast as a work; person avatar treatment on an explicitly different identity surface remains an intentional, documented presentation choice.
