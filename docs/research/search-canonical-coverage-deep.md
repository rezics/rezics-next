## Finding and recommended decision

**A ready native identity basis is necessary but insufficient. Search needs a certificate connecting that basis to this exact physical index's completed writes.** A partition position can witness consumption through a structural change; it must never become the identity digest. Keep the native identity signatures, anchor-built public documents, shared query/compiler and current disclosure policy.

The cheapest certificate is a persisted verified structural basis per physical generation, obtained by capturing per-home structural tuples and source-position barriers, consuming through those fixed barriers, and revalidating native identity. It tolerates subsequent ordinary lag. It is sound only with a proven initial index lineage, complete relevant invalidations and a guarantee that an older in-flight apply cannot later restore a noncanonical ID. The audited implementation does not yet establish all three. In particular, repoint emits no Search-consumable anchor invalidation, and checkpoint CAS occurs after unlocked external side effects.

For the actual multi-worker composition, recommend **Search-owned, per-home coverage/attempt metadata bounded by `4096 × live generations`, using the existing consumer checkpoints**, with new-generation replay for uncertified old indexes. This metadata records catch-up and sink-write provenance, not identity or permissions. If the owner first proves an equally strong write/drain invariant without these rows, the smaller captured-checkpoint alternative is sufficient; rows are not intrinsically required to represent canonical identity. Do not require global `behind = 0` on every prepare. Do not promise that current rebuild count reconciliation alone proves canonical keys.

## What is being proved

Let `B` be the native digest of ordered `(partition, epoch, home, structural generation)` tuples, accepted only with zero native identity obligations in both fixed-home sweeps. Let `I` identify one concrete OpenSearch index incarnation, not merely an alias or generation number. A Search certificate `verified(I, B, protocol)` means all structural effects required for that identity basis have reached the searchable projection and no eligible write left over from an earlier basis can subsequently defeat them. Every raw hit in `I` must therefore have a stored `_id`, `id` and ascending sort key that already denotes its canonical subject for `B`.

This is coverage of the **indexed candidate order**, not an exact current source census, exact authorized total or an OpenSearch point-in-time traversal. Ordinary indexing may omit new subjects or retain obsolete labels, filters, security revisions or visibility. Source eligibility and the shared current evaluator still reject stale hits. An identity certificate does not turn sampled absence into current leaf absence, or raw originals into Access claims. Ordinary insertions/eligibility behind a consumed key require a fresh traversal, as the native contract already says.

The required A/B/C example follows directly. Index all three while legal and obtain genuine coverage for the unchanged structural basis. Hiding B changes current visibility and ordinary source position, but not canonical identity. A later raw prefix may return B with its original `matched_queries` and sort tuple; current disclosure rejects it. Consuming the hide just to prepare would remove B and conflate two guarantees. In contrast, merging B into A changes structural identity: residual rejection of stale B does not make its position in the canonical order valid. With raw `x < z`, normalization `x → y` where `y > z` would skip or reorder groups. Neither normalizing, sorting nor dropping stale raw IDs after fetch repairs a covered canonical frontier.

### Sound captured-barrier protocol without changing native ports

1. Pin concrete `I = (prefix, generation, index name, index UUID)` and protocol/bootstrap provenance independently of hits. Read actual `readIdentityBasis(pool,{deadline})`, obtaining ready `B0`. No caller-supplied canonical-ready string is accepted.
2. For each of the fixed 4096 homes, release a home-local RR client after reading `readIdentityHome(client,p)` and the exact core point's position on that same client. Save `T[p] = (epoch,home,generation)` and `barrier[p] = position`. Require native availability and pending zero. Never infer missing metadata as generation zero. The position read is a core observation/catch-up witness, outside the digest.
3. Independently read full native basis again, `B1`. Require `B1 = B0`; otherwise discard this attempted capture. These full basis observations bracket the capture sweep, so monotonic structural generations and correctly fenced home epochs tie all captured tuples to the same accepted basis. This avoids inventing another digest codec or changing `readIdentityBasis`'s return shape. It assumes home reincarnation cannot perform an undetectable ABA; otherwise the native basis contract itself needs a fence.
4. Let each existing generation consumer reach `checkpoint[p] >= barrier[p]`, checking compatible checkpoint/source incarnation. Absent checkpoint is zero only for a legitimately empty, fully initialized home/barrier zero; it is not proof for missing native metadata. Freeze barriers for this attempted B; ordinary writes after capture do not raise them. Do not skip a home because this filter has zero hits.
5. Before publication, independently revalidate full ready basis `B2 = B0`, physical UUID, pinned alias policy, producer protocol and the write-completion/provenance invariant. Persist a verified certificate for `(I,B0,protocol)` only after all evidence succeeds. Metadata publication is not an atomic transaction with OpenSearch plus all homes: equality is checked again by the reader, and a race after observation has the native contract's existing revalidation limits.
6. Prepare/final handoff/continuation independently use actual native basis and compare the certificate and pinned generation. An already verified B ignores ordinary checkpoint lag. Changed identity/physical generation is restart-required for an existing handle; missing proof is index readiness, native pending/unavailability is native readiness. Never repin silently. Check again after the engine call before exposing its covered frontier.

The proof is per home: every actual mapping mutation/seal dependency visible in `T[p]` precedes the captured source position. Complete atomic original invalidations must therefore be at or below that barrier. A refresh-visible contiguous consumer through the barrier has applied every such effect. Union of these fixed-home facts supplies global indexed identity coverage without a cross-home transaction, join or global write clock. Ordinary position changes do not alter `T` or B. The final equality checks reject intervening structural changes. This argument is conditional on initial lineage and preventing late stale effects; those conditions are substantial, not wording that makes existing checkpoints sufficient.

One may factor the owner's identical two-sweep implementation into a reviewed internal collector that also observes core position while retaining both public signatures. That could avoid the bracketing overhead. It is an implementation handoff, not permission for Search to replace native basis logic. The unchanged-port procedure above explicitly costs **three full basis reads plus one barrier sweep** for a cold certification, before any additional final request revalidation. A single full basis plus an unrelated sweep is not the same proof.

### Persisted per-home variant

Search can instead use one current row per `(partition_no, consumer)` carrying `physical_uuid`, protocol/bootstrap state, candidate `(epoch,home,generation,barrier)`, verified tuple and bounded apply state. Keep it in Search-owned schema/migration/SQL; do not change native tables or create another placement authority. Consumer name alone is insufficient after physical index loss/recreation. One row may hold both candidate and previous verified values; no append-only certificate history is needed.

Capture a candidate with native home metadata and current core position on the supplied same-home RR client. A source-home write transaction can store that candidate and compare the native tuple again under existing command serialization. Once pending is zero, freeze its barrier until consumed or a structural change supersedes it. A batch observing generation 7 at source position 900 while its checkpoint reaches only 850 cannot publish generation 7: the invalidation at 890 may name another ID. After checkpoint crosses the stored barrier, conditionally promote only that candidate, rechecking current native tuple/pending and physical generation. Late acknowledgements compare exact candidate/UUID and cannot overwrite a newer one.

The reader brackets its 4096 coverage-row observations with actual full native basis reads; it verifies each current native home tuple equals that row's verified tuple and all native pending is zero. With unchanged ports, this extra native-home verification is a charged 4096-point sweep; do not pretend the digest returns its preimage. A stale row or home move fails readiness. An internal shared collector can combine compatible observations, but its actual rows/statements must be reported. Ordinary writes neither reset verified tuples nor clear B merely because head exceeds checkpoint.

No new per-home table is needed *merely* to calculate the identity digest. Its benefit is durable partial coverage, deterministic bootstrap/recovery and, if used, the following producer-side sink guard. This is why it is the recommended actual implementation rather than an invented native callback.

### Late external writes are a separate proof obligation

`startRelays` prevents duplicate partition runs inside one runner; it is not distributed exclusion. Multiple `startWorker` instances can start the same configured Search service. `projectBatch` releases the checkpoint lock before source fetch/bulk, so two runners can apply from the same checkpoint. A particularly harmful schedule is:

1. Old runner captures an index action for original X at version 10 and stalls before its engine write.
2. Merge X → Y commits at 11. Another runner deletes X at 11, waits for refresh and advances checkpoint past the barrier. Native obligations seal and a proposed certificate for the new B is recorded.
3. After delete-version retention expires, the old action at 10 arrives. OpenSearch may accept it because X is now missing. The old runner's later checkpoint CAS fails, but X has reappeared under a noncanonical raw ID. B and the successful checkpoint have not changed.

An older writer can also receive 409 against a newer still-unrefreshed write: accepting that conflict proves version dominance, not visibility of the independent write. The current code treats typed version conflicts as successful items. Thus neither HTTP success, external versions nor checkpoint CAS alone proves the required sink invariant. This is a source-derived counterexample, not a claim that it has been reproduced by this documentation task.

The certificate must exclude unresolved earlier-basis applies, and every apply must enroll **before** obtaining its source snapshot. A bounded per-home/generation attempt slot can record its checkpoint/UUID and observed native tuple before source read, serialize participating writers, and mark completion only after actual refresh-visible acknowledgement plus checkpoint handling. A certificate for a newer basis waits for all older/unknown attempts to drain; attempts known to have taken their source snapshot after the already verified current tuple cannot introduce an older identity and need not invalidate that existing certificate during ordinary traffic. All write paths must participate.

A lease timeout or a lost process is not evidence that an HTTP write cannot arrive later. Keep an ambiguous older attempt unresolved; recover by a new physical generation rather than clearing the slot and blessing the old one. A session advisory lock or local pause alone does not fence an HTTP request already sent when its connection/process is lost. Physical names of unresolved retired instances must not be reused; implicit engine auto-creation must not resurrect an admitted generation. UUID checking detects recreation but does not itself fence a delayed name-targeted request into a reused name. Lifecycle issuance/reuse rules need explicit native tests.

Permanent version tombstones or a sink-enforced fencing scheme are alternative solutions, but would change the present delete/document protocol and shared query behavior. Merely increasing `gc_deletes` supplies a time assumption, not a proof under unbounded outage. Do not silently make either policy change as part of coverage. The smallest implementation may instead prove exclusive, fully drained writes for the deployed topology; the existing default worker currently provides no such cross-process proof.

## Bootstrap, helpers and default composition

An existing index cannot be certified just because all current heads equal checkpoints or native generation is zero. It may contain an obsolete extra key, lack a canonical key, have been populated before invalidations were complete, or belong to a recreated instance. Native rollout must first establish/seal old redirect obligations; Search rollout separately needs trustworthy index provenance. Do not scan all subjects/jobs in prepare, or use actor-authorized terminal null to decide how to repair concealed originals.

Prefer a new known-empty generation and zero checkpoints, replaying the retained complete creation/invalidation log with current anchor source reads. Old bodies are not replayed. Every original with a creation event is reconsidered even if its redirect invalidation was historically absent; current nonterminals delete in the new instance. Require complete creation coverage/retention or an owner-bounded resumable source enumeration for any imported legacy anchors. Otherwise replay cannot promise bootstrap. No arbitrary existing index should be relabelled as known-empty. Ordinary recall may lag after activation, but bootstrap must not invent provenance.

`rebuildSubjects` currently compares per-partition document counts only during quiet head/checkpoint observations. A stale X replacing missing Y can have equal counts and entirely wrong canonical order. New-empty lineage plus complete replay supplies the identity-key argument; counts are additional diagnostics. If those premises cannot be proved for old/imported data, implement bounded real reconciliation/enumeration or keep it unavailable. No count-only ready flag or unbounded request-time scan closes the gap.

The native actor-neutral `readSealedSubjectIdentity(client, original)` can support an owner repair page over stored originals: source-home exact existence/mapping/current obligation/seal/core points only, including hidden and denied originals. Null is missing original, never self/drop fallback. Its returned source home is neither current terminal-home truth nor global readiness; obtain full ready basis before repair and revalidate before coverage publication. For this public anchor projection, use the result to identify nonterminal originals to delete; do **not** copy their body to the returned terminal or synthesize an engine Hit. Build a terminal document only from its own actual source. No per-original 8192-row sweep, target walk, private holder index or actor allow cache is needed.

The raw-prefix fixture is important evidence of an **API gap**, not evidence that checkpoint provenance already exists: it calls `createSubjectIndex` and `client.bulk(bulkLines(documentActions(snapshot,...)))` directly, never starts this prefix's consumer, and hides B before prepare. Current `createSubjectIndex(search,prefix,generation)` has no pool/native context; its already-exists branch also cannot attest known-empty provenance. A checkpoint-only implementation cannot use that fixture to claim its consumer caught up; starting replay at prepare would erase B and violate its assertions. Querying all documents during prepare would violate the reservation assertion too. The empty-index positive fixture likewise requires genuine native initialization/coverage evidence without using a first hit to select a generation.

Preserve those assertions. The implementation adoption must include a real, charged coverage-producing path for legal helper writes/known-empty initialization **before** the hide, or an independently justified native invariant sufficient for that fixture. That requires actual dependency/API composition, not a test callback returning ready. A clean fully initialized zero-structural-change universe can justify self-key safety, but missing metadata/old-data rollout cannot be called that universe. Arbitrary direct engine bulk writes cannot inherit a certificate just because their documents look plausible. Until the concrete helper path exists, the positive fixture is not proved by any certificate design in this report; it is not permission to weaken it.

In production, [Search work registration](../../services/kernel/src/search/work.ts) constructs the actual source/indexer, while [default modules](../../services/kernel/src/work/modules.ts) and [worker startup](../../services/kernel/src/worker.ts) launch Search plus the separate link relay. The indexer can run before native registration/seals finish; readiness must observe that fact. Wiring `readIdentityBasis` into the scope factory alone does not add write lineage or coverage publication. Helper callers, direct runner users, default worker, rebuild/resume and replacement runners must use the same producer protocol. Private test composition cannot stand in for `startWorker` proof.

These are proposed ownership boundaries, not files changed by this research. Existing native public signatures stay unchanged; Search does not write the native metadata tables.

| Owner / small paths | Concrete missing work |
| --- | --- |
| Semantic `identity-maintenance.ts`, `identity-basis.ts`, their SQL/migration; existing `merges.ts`, `merge-moves.ts`, `account-agents.ts`, `events.ts` | Deliver native atomic structural counters/current obligations, truthful pending/seals/rollout and neutral mapping point. Audit and emit original-anchor invalidations on every actual writer, including repoint; fix larger-survivor retry. Native availability/home fences remain here. |
| Search `coverage.ts`, focused `coverage-*.sql`, Search-owned migration/schema | Define current per-home candidate/verified/attempt row and exact physical incarnation/protocol provenance. | Search `indexer.ts`, `runner.ts`, `work.ts` | Enroll and complete actual applies, integrate capture/promotion, refuse uncertified bootstrap, make ambiguous-attempt recovery truthful, propagate actual native dependencies in all entry points. | Search `indices.ts`, `generations.ts`, `retire.sql` | Return/bind physical UUID internally; separate activation and coverage metadata; initialize only genuinely new instances, replay/reconcile with provenance, prohibit unsafe name reuse/implicit recreation, retire coverage with checkpoints. Existing cap/grace behavior still applies. |

Persisting only `verified_basis` in `_meta` can implement the smaller option, but current activation writes replace metadata contents. A lifecycle owner must preserve fields and prevent stale writers certifying a different incarnation. A Search-owned table offers conditional updates more naturally. Neither storage choice turns metadata publication into a distributed transaction; request-side identity/incarnation revalidation remains mandatory.

A concrete additive Search-only budget surface could be `prepare(filter, { deadline, metadataBudget })`, returning `preparationUsage` with the opaque prepared handle, and a separate metadata allowance for prefix/final revalidation. `metadataBudget`/usage must cover native rows, points, statements and bytes; the existing raw `budget: number` remains candidate-only. A compatible one-argument helper may use a finite owned default allowance and still report usage, but caller composition must reserve that allowance before dispatch. Exact field names belong in the owning scope contract before implementation. The existing `ScopeNativeBudget` lacks a statement counter, and `PreparedSearchScope` currently exposes no preparation usage: these are real accounting gaps, not a reason to hide native work. No change to the native Semantic exports is required.

## Cost and native acceptance to require

Let `H = 4096`, `G <= 3` live generations, `b` deduplicated event anchors per batch, `r <= quota + 1` engine hits actually fetched, and `L` index-tree depth. All native metadata, empty seeks, transaction controls and rereads are charged independently of candidate keys.

| Operation | Work/storage bound and qualification |
| --- | --- |
| One native basis read | Two independently released H-home sweeps: **8192 metadata observations/rows plus core epoch/home observations**, including empty/unavailable seeks, actual SQL statements, blocks and bytes. Typically point lookup blocks scale with L; the exported digest's constant size does not make observation free. |
| Unchanged-port cold captured certification above | Three full basis reads: **24,576 metadata observations plus their core observations**; one H-home native/core-position capture; up to H checkpoint observations per polling round; one bounded certificate publication and physical metadata checks. Any later final request basis check adds another 8192 plus core. No per-candidate multiplication. |
| Persisted verified prepare/continuation | At least one actual full basis per required observation plus certificate/incarnation reads. If final use requires an independent read, reserve a second full basis. Ordinary head movement adds no identity work or recertification. Full revalidation is charged even for zero hits. |
| Per-home variant | At most `H × G <= 12,288` current coverage rows, bounded tuple/barrier/attempt fields, indexed by `(partition_no,consumer)` with consumer-leading retirement access. Capture/promotion are constant home-local points per attempt; total metadata writes scale with actual changed homes/attempts, not source population. Reader bracketing and tuple comparison costs are additional, as specified above. |
| Existing event apply | One contiguous batch of at most 64 envelopes; filter/selection proportional to its events, `b` current anchor reads and at most `b` engine actions per generation. Native payload/history source costs remain those of the actual source; coverage does not make them constant. Replayed/conflicting attempts still cost work. |
| Raw prefix | One shared query, at most quota plus one raw hits, no refill. Charge every fetched/repeated/rejected/lookahead key, including unused lookahead, against reserved aggregate 256. Returned size does **not** bound postings inspected, engine sort work, source history, SQL blocks or latency. |
| Rebuild/recovery | O(retained log + reconstructed source + affected engine data) total across bounded steps; metadata O(HG). Catch-up polling repeats fixed-home work and has no finite deadline under perpetual changes/outage. Retirement deletes at most H coverage/checkpoint rows per generation; deleting an index is not constant physical work. |

Native acceptance for adoption should establish the following, with actual migrated database, native commands/Access, real engine and production write paths. This research deliberately adds no executable tests or gates.

1. For every audited writer: mapping/generation/invalidation atomic commit, rollback/no-op/replay behavior, actual Search consumer selection of the original, and inherited larger-survivor completion. Native pending cannot clear before registration/repoint acknowledgement. Consume-through-barrier must delete each raw noncanonical ID, including concealed originals.
2. A legally built A/B/C index is genuinely certified at B; pause its ordinary indexer, hide B and make unrelated ordinary writes in the same and another home. B remains a charged raw hit with original matched/sort metadata, disclosure rejects it, and preparation/continuation retains B without behind-zero recertification. Prove the legal helper path as well as default worker.
3. Native identity can be ready while a generation has not consumed a structural invalidation: prepare stays unavailable. After real refresh-visible catch-up and certificate promotion, raw order contains only canonical stored IDs. Include a target whose UUID sorts above intervening hits; post-fetch sorting/dropping must never pass as coverage.
4. Place a mutation between each capture/read/consume/publication boundary. Verify same-client RR head/tuple pairing, pending/seal races, no batch stamping of an unseen later generation, stale candidate acknowledgement rejection and current basis/incarnation recheck around engine results.
5. Exercise zero-hit query, genuinely empty new index, missing native metadata, old-data migration, missing historical invalidation and equal-count wrong-key generation. None gets ready from counts/empty hits alone. Clean replay or bounded real reconciliation eventually establishes trustworthy coverage.
6. Run two actual runners/default workers against one generation, pause an old apply before engine execution, and test completion beyond delete-version retention. No certificate may coexist with an unresolved older-basis side effect. Test 409 against independently unrefreshed work, crash/ambiguous apply and replacement recovery; no timeout/lease may manufacture completion.
7. Move/fence a home, change epoch, repoint, unmerge, swap aliases, retire an index and recreate the same name with a different UUID while checkpoints exist. Old handles restart/fail readiness even with zero hits; old certificates and late acknowledgements cannot bless the replacement. Test name-targeted late writes and automatic-creation policy explicitly.
8. Measure real fixed-home rows/core points/statements/bytes at prepare, final and continuation, with fixed source payloads and growing irrelevant history/population; separately grow alias/affected structural sets and G. Confirm H×G storage and bounded per-step work, including failed/empty seeks and all rereads. Do not substitute constant returned hits for a physical-work measurement.

The recommendation is conditional only on these explicit implementation obligations, not on a new product identity decision. Adopt the certificate/provenance protocol in the owning Search README after the manager selects the storage variant; keep this report as the source audit, comparison and counterexample evidence.
