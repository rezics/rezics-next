## Reading the evidence and evaluating a larger limit

All paths below are relative to the source snapshot above. A citation such as `services/kernel/src/http/admission.ts:3` names the defining source line; the surrounding named function is the enforcement path. Schema constraints are enforcement too, but an unapplied migration or a schema dump is not proof of the live database. Tests, generated clients, fixtures, benchmark scales and old research proposals are not new product limits. Page sizes and worker pages are not total account quotas. A fixed schema version, HTTP status, cryptographic digest length, port or mathematical conversion constant is not an independent quota.

The repository's primary sources carry [AGPL-3.0-only](https://github.com/rezics/rezics-next/blob/a4faadd62b29a4b42cda4472c48071b83b87051f/package.json#L4); `packages/definitions`, `packages/filter`, `packages/composition` and `packages/document` declare Apache-2.0 in their `package.json` files. Conversion code declares AGPL-3.0-only. These are evidence citations, not recommendations to copy source. No external repository was needed or executed; no reference clone or reference index was changed.

The following expansion recipes apply to **every** detailed entry that cites them:

- **F (field/envelope):** a modest finite increase is C only after changing all validators, request/response envelopes and any database CHECK together. If persisted, migrate constraints before accepting new values; preserve old readers/cursors. Very large values require D: store separate chunks or addressed blobs, stream input/output, and bound normalization, validation, history, authorization and erasure. Cost is O(admitted bytes/items), not O(total population). Add exact-bound/above-bound, multibyte, escaped JSON and replay/retention tests. An unchanged `text` column does not make an endpoint unlimited.
- **P (page/work):** C for a measured finite page increase with synchronized source, caller, cursor and response bounds; D for unbounded results. Keep keyset indexes on full anchor/order keys, one bounded page/snapshot, and background continuations for whole-set work. At size p, rows/points/bytes grow O(p), index work O(p log N), and composition sums all pages and discarded/lookahead work. Migrate only if indexes/frontiers change. Test full/deep/sparse/hidden pages, no-progress, retries and growing unrelated history. Never replace a bound with an unrestricted scan.
- **Q (quota/fanout):** D for unlimited membership/assignment/reference sets stored or loaded as one neighbourhood. Normalize the set, retain indexed inverse edges and keyset enumeration, replace synchronous all-neighbour permission or projection work with an admitted plan/resumable job, and migrate/backfill under fences. At fanout f, current work is O(f) or O(p×f), not constant. Test admission races, removals, stale derived state, rollback, erasure and large/deep sets. Raising only a number can violate `docs/architecture.md:9`.
- **T (time/retention/rate):** C for finite policy changes after owner adoption and capacity evidence; lifetime extensions also extend the possible stale-authority/privacy/replay window. Expiry queries need indexed cutoffs and bounded deletion; longer retention increases stored history, total cleanup and operator cost. Keep request deadlines finite; move long work to resumable jobs. Test both sides of expiry/window boundaries, replay, clock handling and cleanup backlog. Removing security freshness/rate bounds is N.
- **B (measured budget):** D for very large requests. Re-derive the whole cost vector, including input, discarded candidates, metadata, native reads, witnesses, lookahead, SQL, engine iterator work, bytes and history/SDK writes. A larger output limit or timeout proves nothing. Add native growth evidence with a fixed selected neighbourhood and independently growing unrelated population, matches, history and privacy changes; an index or background preparation may be required. Keep limits at admission and fail/prepare before spending beyond them.

**Reason convention:** “NR” below means **no recorded reason for that exact number** was found in the defining code, owner document or relevant decision. It does not mean there is no architectural purpose. “Bounded work” is the architectural requirement; a specific unmeasured numeric choice is not thereby justified. Tests named by owner sources are future verification obligations for a change, not tests run for this report.

## Shared transport, execution and rates

**G01–G04.** `services/kernel/src/command/command.ts:2,54` defines the 2 s request default and 1,000-event cap; the command executor validates keys, refuses oversized event sets, sets a 200 ms lock timeout and bounds receipt recovery by 200 ms. HTTP uses the same deadline (`services/kernel/src/http/app.ts:50`). Expiry produces deadline/unavailability or overload; contention retries consume the original deadline, with jitter capped at 100 ms. A command is not entitled to run indefinitely. HTTP idempotency schemas on several product routes allow 3–1,024 characters while the executor accepts only a 1–255-character command key: the advertised larger envelope does not override the command validator. Event relay reads at most 64 envelopes (`services/kernel/src/events/log.ts:12`). Reason: bounded command/relay work, NR for the exact counts; recipes F/P/T/B. Longer business operations need durable bounded steps, not a longer transaction.

**G02–G03.** `services/kernel/src/http/admission.ts:3,30` enforces separate capacities of 8 ordinary and 2 reserved running requests and a shared queue of 32. Full/expired admission returns `overloaded` with `Retry-After: 1`. `services/kernel/src/http/body.ts:5` defines the default1,048,576 B and maximum4,259,840 B; the native server enforces that maximum through maxRequestBodySize (`services/kernel/src/server.ts:334`), and definition-publication routes explicitly select it; the streaming reader checks actual bytes, not just Content-Length. `services/kernel/src/http/app.ts:138` reserves aggregate ingress memory using `(8 + 32) × defaultBodyLimit + 2 × largestRouteLimit`; body budget exhaustion is overload and an individual oversized body is `content_too_large`. Reason: bound concurrent retained body memory, NR for 8/2/32; F/P/B, with ingress memory linear in concurrency×body size and parsing/copy amplification measured too.

**G05.** `services/kernel/src/route/route.ts:3–4` and partition/routing CHECKs, for example `services/kernel/db/access/schema.sql:1857`, bound routes to 0–65,535 and partitions to 0–4,095 (16 routes/partition). This is a routing format/capacity boundary, not a maximum number of product objects. Common revision APIs cap positive versions at 2,147,483,647 and expected-write versions at 2,147,483,646 where increment space is reserved (`services/kernel/src/access/routes.ts`, `services/kernel/src/rating/schemas.ts:6`). Library pins/counts explicitly stop at JavaScript's 9,007,199,254,740,991 (`services/kernel/db/library/schema.sql:1289,2323`); history positions stop at signed int64 9,223,372,036,854,775,807 (`services/kernel/src/tokens/session.ts:9`). Rating population-delivery serials share the int64 maximum (`services/kernel/src/rating/population-total.ts:20`). At the ceiling validation or storage rejects further values; there is no wraparound contract. Reason: wire/storage representation; D requires versioned decimal-string or wider representations, every counter/index/codec updated and overflow/migration/replay tests. Do not infer an int32 ceiling for an unrelated bigint field.

No fixed total quota was found for the number of Library entries, copies, progress sessions, owned Collections, owned labels, follows, owned Realms/Spaces/Zones, ordinary subjects, public keys or all retained releases. This is an **absence of an identified product quota**, not a promise of unlimited storage or proof every growth path is already bounded. Count types, route topology, per-object quotas, native fields, index limitations, admission and deletion still apply. In particular1,000 combined account memberships,100 pins,32 effective labels/subject and20,000 completed units/session are real set ceilings;20/100 list pages,20 rating questions/page and100 source keys/page are not whole-owner quotas. Enum cardinality and cryptographic sizes were excluded unless they bound a real extensible product/authority set or user-controlled envelope. Pure fixture numbers and build/test runner timeouts were excluded.

The sources share five patterns: reject malformed/oversized input before effects; keyset pages plus durable bounded continuation; finite full-key fanout; byte/row/statement/witness accounting across nested owners; and freshness/retention as part of authority rather than a cache hint. They also share a recurring weakness: independent HTTP, domain, stored-state and UI numbers can drift. A declared constant proves only that source's admission, not installation or a complete bounded plan.

Recommended adoption by the performance manager:

1. Keep this report as snapshot evidence. Move chosen policy into each owning document and publish a central generated catalogue only after an owner adopts one authority per limit. Store value, unit, scope, provenance, error, and enforcement links; do not make this research report a competing specification.
2. Prioritize the concrete cross-layer mismatches above before increasing numbers. Require a producer-to-consumer boundary case, migration/schema agreement and a recorded rationale for every changed ceiling.
3. Retain finite per-request/job budgets. For large product sets, use normalized indexed edges, full-key batches, keyset cursors, addressed large blobs and resumable background preparation. “Unlimited” should mean more independently admitted pages over a large set, not population-sized synchronous work.
4. Require `docs/architecture.md:9` evidence at each new size: fixed selected neighbourhood while unrelated population/history/matches grow; account discarded/hidden candidates and framework/custody writes; one repeatable-read snapshot and full routing keys. Re-derive aggregate composition and memory before changing a leaf constant.
5. Keep security/privacy/fiscal meanings separate from capacity: consent expiry, rate budgets, rating floors, normalized focal-point coordinates, single-benefit checkout and exact money are not generic knobs. Their owner must adopt a policy/design change.

Research decisions: the pinned current source is the supplied dev snapshot; later migration wins over an older dump only as evidence of the migration's intended result, not proof it is installed. Documented/proposed limits are listed with that status. UTF-8 B, UTF-16 units, code points and SQL characters stay distinct. Defaults, presentation truncations, time windows and operator-configurable finite budgets count, while mathematical constants and fixtures do not. Repeated declarations are grouped under one ID without hiding narrower consumers. Reasons are taken from current owners/recorded change where available; the remainder is explicitly NR. No product code, owner decision, dependency, database or service was changed or executed for this research; native/browser/acceptance verification remains deferred by the launch policy.
