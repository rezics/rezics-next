# Access and Auth erasure participants

Research evidence, 29 October 2026. This is a recommendation for Accounts to adopt in its owner documents, not an amendment to [Account erasure](../deletion.md#account-erasure). Inspected repository revision: `da107d37f4b90b508bd705e8d2b0eaa1b38c444b`. The findings come from source inspection; reference clones were not installed, built or executed.

## Recommendation and decisions

Neither participant can acknowledge today. Keep the existing tombstone effects, native Auth `eraseAccount`, delayed consent erasure and DBOS hosts. Add indexed, role-complete residue phases, then acknowledge from a final durable step. An enqueue, an expired credential, a cascade declaration and a successful first page are not erasure evidence.

Use `erased` for Access: every terminal account has its own lifecycle row. Auth may use `none` only if its persisted initial inventory found no applicable records in **any** role, including client ownership, operator/acting-human evidence and shared-copy obligations. A missing native `user` alone never proves `none`. Persist whether anything applied before deleting it so retry cannot change `erased` to `none`.

Decisions derived from the contract:

- No Access/Auth audit or security payload gets an invented retention exception. Erase it unless an adopted inventory specifies fields, purpose and expiry. Neither participant has a financial subset or an eligible published contribution in its credential/permission stores. Public contribution de-identification belongs to its content owner. Keep only the mandated tombstone/completion and impersonation-prevention skeletons described below.
- Preserve surviving accounts' permissions when the deleted account merely granted them. The grant tables have no granter column; erase/minimize the granter's command provenance through exact shared-copy locators. Remove grants whose **subject or account resource** is deleted. Never delete an entire surviving organization's data merely because one operator, member or reviewer was deleted.
- Retire handles permanently without forwarding, but sever the former owner's mapping and operation/reservation provenance. Retaining a historical handle-to-account link is not necessary to prevent reassignment. Existing non-null constraints need a retired-allocation representation; do not silently substitute another real account.
- Existing immutability/terminal-proof triggers protect replay and responsibility release. Do not disable them globally. Add narrowly checked platform purge paths, bound to an existing `access.erasure` obligation, after their consumers have finished. `access.erasure` and its acknowledgements remain permanent and unchanged.
- Indexed discovery may visit the fixed routing universe, one partition at a time. [Routing][RO] defines 4,096 partitions, each with sixteen routes. A route-leading index alone does not locate a non-owner role. Add the role-first native index, constrain each query to the current partition's route interval, and seek `(route, raw_key)`; alternatively issue sixteen exact-route seeks. Empty partition probes inspect no unrelated rows. This is a fixed routing cost, never a table, account or JSON enumeration. Account-owned stores need only the known route; route-zero stores only partition zero.
- Shared-history owns actual minimization of shared receipts, events and workflow payloads. These tasks supply atomic locators and wait only for the native producer's handoff to become durable; overall completion still requires shared-history's acknowledgement. Access/Auth must not wait for shared-history's **global** acknowledgement, which would create a cycle around their own final workflow/acknowledgement copies.
- Logs, delivery diagnostics, backups and replicas remain explicit custody findings. Do not represent these as cleaned by a SQL participant, or claim that `readErasureStatus().state === 'complete'` proves backup expiry. The current coordinator deliberately does not model backup custody [AR], [ER].

## Reading the inventories

`a` is the erased account, `r` a route, and `pk` the store's actual primary key from its cited schema. **Add** means the necessary index/relation does not exist today. Index suffix `pk` means the full unique tie-breaker, not OFFSET or `ctid` as a durable cursor. `ctid` may identify rows only inside the same locked page transaction. For long composite permission keys, add a native unique `erasure_key` and `(role_account, route, erasure_key)` index rather than a cursor containing action/reason/validity plus every subject key. A `valid` range used as a raw, indexed key is acceptable; recomputing/sorting historical ranges is not.

Every row below is covered by the common page protocol: choose **one store, role and partition**, seek strictly after the saved raw key with `LIMIT 100`, delete/minimize only selected keys and save progress in the same transaction. Select keys, not bodies or ciphertext; return at most 64 KiB of keys/progress. An individual locator is at most 1 KiB; reduce the page to meet the byte cap. Never aggregate all children or deserialize unbounded payloads. Parent deletion requires indexed `NOT EXISTS` probes for every child relation, including cascades, so the final cascade has zero account-owned children. Release the connection before another partition, Auth call or wait.

### Cursor cutover and coverage before release

An account id in `after_account`, `page_after`, `terminal_account`, `organization_close.cursor_member`, or an operator-page cursor is personal even when the row belongs to somebody else. Replacing it with a hash or encrypting it is not erasure. Introduce independent raw traversal ordinals for the corresponding native owner relation, indexed with the actual owner key; user/member deletion removes the id-to-ordinal binding. Cursor rows retain only the ordinal boundary. New writers must no longer persist account ids as cursors; DBOS results containing old cursors get shared locators.

This is a deployment cutover, not an erasure-time history sweep. Allocate ordinals in existing traversal order with a resumable raw-key backfill, translate each existing cursor through an indexed predecessor lookup, then switch producer and worker versions together. A deleted/missing cursor id can still map to the last predecessor ordinal without retaining that id. Keep compatibility refused after cutover so old recovered workflows cannot write old cursor shapes. Independent new ordinals can be assigned on insert; new registrations/memberships already require their normal coverage/fence checks. Backfill scans are explicit deployment work with their own bounded pages, never charged to deleting one account; acknowledgement requires its completion marker. If ordinal introduction is larger than a proposed slice, split the cutover before dispatch rather than accepting an id-bearing cursor.

## Acknowledgement points and service boundary

### Access

Register an `account-tombstoned` effect in the existing accounts work module [MW]. Persist phases and raw cursors in the account partition, outside DBOS history. Use workflow ids such as `accounts.access-erasure:<accountId>:<barrier>:<phase>:<page>`; the barrier is the committed erasure's T/version identity, validated against the native row. Delivery/replay must converge on the same root. Each DBOS step does one bounded native page; a successor workflow continues a long phase. Restore no initiator.

Order: fence producers at T; finish committed organization/operator/member/verification work; hand off shared copies; purge permission/provenance and relationship children; retire handle mappings; purge terminal evidence/continuation children; minimize account residuals; run indexed absence/minimization probes across the finite store/role manifest. Do not remove Auth's required fence witness or still-consumed continuation evidence: use a minimal durable dependency/completion marker, or keep that exact witness minimized until Auth's user deletion/release step signals completion. Access must not await Auth's final acknowledgement if Auth itself needs Access cleanup; only these specific native dependencies are ordered.

After the **last native purge transaction** and producer-locator handoff commit, call `acknowledgeErasure({ pool }, { accountId, participant: 'access', outcome: 'erased' })` in a separate platform transaction [ER]. Exceptions are absent under this recommendation. Replay calls the same immutable outcome. Retained allocation/tombstone skeletons are tested for minimal fields, not counted as unerased personal payload.

### Auth

The kernel effect uses a narrow trusted enqueue capability for Auth's existing DBOS host, `startAccountErasure({ accountId, barrier }) : Promise<void>`. Compose a DBOS client for Auth's configured system database/schema/application in the kernel worker; the kernel's ordinary `context.client` points at `dbos`, so it cannot enqueue this as a kernel workflow. This creates no public Auth route or kernel import in Auth. Missing enqueue composition fails closed. Success means durable obligation accepted, never acknowledgement. Register the workflow in the existing Auth host; use `accounts.auth-erasure:<accountId>:<barrier>:<phase>:<page>`. This is an internal service port, not a new public route/event/service. Preserve `eraseAccount(accountId)` as the native deleted/fenced-user deletion primitive. Ordinary deletion workflows and the erasure workflow must serialize on the same persisted obligation; an old workflow cannot run the old bulk cascade while the new one is draining children.

Add this narrow member to `SharedAccessPorts`, hence `TrustedAccessPorts`, in [the Auth contract][TP]:

```ts
acknowledgeErasure?(input: {
  accountId: string;
  outcome: 'erased' | 'none';
}): Promise<void>;
```

This follows the existing optional-capability convention, but production startup requires it when Auth erasure work is enabled; absence throws/unavailable and leaves Auth pending. Do not default it to a no-op. Add a callback of that type to `AuthBindingCapabilities` [AB]. `createAuthBindings` exposes it with native refusal/unavailability translation; `createNativeAccountBindings` [NB] composes it as `await acknowledgeErasure({ pool }, { ...input, participant: 'auth' })`, discarding the command result. The participant is fixed by the kernel closure: Auth cannot acknowledge another owner. Auth imports no kernel module/pool and receives no caller-controlled participant or platform principal.

The final Auth DBOS step invokes that port **only after** all these persisted facts hold:

1. T has fenced all related producers, owned clients and operating sessions; every native residue/role above has drained and user deletion actually committed through `eraseAccount`. Children were paged first, so this cannot hide an unbounded cascade or fail on client FKs.
2. The stored consent cutoff has elapsed. Today [SV] inserts `clock_timestamp() + interval '5 minutes 10 seconds'` in the user-deletion transaction. Keep at least that 310-second lower bound, covering 300-second access-token lifetime and ten seconds of margin. Record/verify the last possible issuance fence; increase the bound if composed verifier leeway/lifetime ever exceeds that margin. Current kernel token checks enforce `exp > now` and lifetime at most 300 [TK]; do not invent an existing ten-second leeway setting. Release DB connection while durably sleeping. Retries use the original due time.
3. The delayed consent consumer [CE] has completed **all** bounded client pages for this account, erased its marker and signalled native completion. The present function limits the number of accounts but loads **all** clients for each account; fixing this inner fanout is mandatory. A minute maintenance enqueue is not proof of completion, nor a deadline under backlog.
4. Post-user residue phases have drained registration/effect/provisioning/operating-human/opaque protocol/cursor/counter rows; no in-flight old writer can repopulate them. Indexed existence probes verify each applicable store/role and producer metadata coverage/handoff. Persist only minimal done/outcome state outside DBOS, then call the port in a separate step after releasing the Auth connection.

Even organization accounts with no native user need the all-role inventory before `none`; organizations may own an operator relationship, delegation, shared output or client. Auth retries failed port calls durably without treating retry exhaustion as completion under the erasure obligation's platform authority, not the deleted actor's expired continuation. The 310 seconds is a minimum safety delay, not an overall erasure deadline. Add overdue-obligation monitoring; never acknowledge a backlog, expired workflow or unknown custody as complete.

This is the smallest practical decomposition proposed here: discovery/cutover and copy recording are reusable prerequisites; native erasure groups share one raw-key driver rather than one workflow per table, and each owner has a single final acknowledgement slice. The service plumbing is separate so that Auth’s final port wiring and its real integration test fit eight files.

The final slices reuse the test fixtures/seed helpers introduced in their component suites, rather than fitting an entire fake service into 400 lines. Store-specific tests populate each inventory row, including secondary roles in other partitions. Their final integration tests must actually execute production dispatch and native purgers against Auth/kernel databases, not call acknowledgement directly or replace cleanup with permissive stubs. In implementation, use scoped native test commands for the listed files; changes to shared command/work runtime require `bun run --cwd services/kernel check` as required by [verification](../development/verification.md), plus root typecheck. The research acceptance remains `test -s docs/research/accounts-erasure-participants.md`.

### Cost: Native page

- Touches: one obligation/progress row, one store/role's indexed key range in one partition, at most 100 selected native keys, and a fixed number of parent/child point probes. Authorization reads the committed erasure obligation, never a restored initiator.
- Bound: at most 101 examined matching keys including lookahead, 100 selected-key writes, and at most three indexed child probes per selected parent in a child phase; otherwise split phases by child kind. At most 64 KiB returned; ≤1 KiB locator and no payload fetch. SQL statements ≤`8 + 4B` for `B ≤ 100`; each uses a fixed index seek or exact key. Parent final-delete transaction runs only after indexed child absence. Empty/denied paths are constant probes. B-tree height costs `O(log N)`; no linear scan with unrelated rows. Fixed routing discovery ≤4,096 partition visits per non-owner role, each ≤16 exact-route probes, not proportional to number of accounts.
- Growth check: each component's named test measures native examined rows/buffers/statements at 1/10/100 account pages while independently growing unrelated rows/history 1/100/10,000; hold selected page fixed and assert the same leaf/key/write budgets, allowing index-height growth. Exercise empty/deep/denied/retry paths, closed intervals, orphan evidence and roles absent from current inverse.

### Cost: Copy recording

- Touches: the copy's own write transaction and typed native account-role association rows; DBOS enqueue intent and actual copy transaction are separate explicitly tested boundaries.
- Bound: fixed role count derived from each typed operation, no JSON discovery. Ordinary operations record ≤16 associations per artifact; a bounded bulk page with ≤100 targets records at most `16 × 100` fixed-key associations in that page transaction, or emits per-target copies if its byte budget would be exceeded. Recorder keys/results ≤64 KiB per step; fanout splits before this cap. Each workflow child/message is its own exact copy, never recursive traversal.
- Growth check: named recorder tests compare one identical artifact amid 1/100/10,000 unrelated artifacts; verify equal association writes and indexed probes, failed-transaction rollback, missing bindings and no locator loss between native commit and durable enqueue. Tests for the shared-history owner must separately prove actual minimization; these slices do not implement it.

### Cost: Cursor cutover

- Touches: one native traversal-owner page or one exact cursor row and its indexed predecessor; independent ordinal-to-id binding only while native identity exists.
- Bound: deployment backfill ≤100 raw keys and ≤100 writes per transaction, resumable/versioned; total deployment work follows that native table, explicitly outside per-account erasure. Runtime erasure touches only indexed references to the deleted account and its mapping, with Native-page bounds; no reset/re-walk of somebody else's collection of accounts.
- Growth check: named cutover suites use live/completed cursors, removed ids, late insertions and recovered old workers at three scales; establish traversal coverage and constant per-erasure probes with unrelated owner population growth.

### Cost: Finalization and acknowledgement

- Touches: manifest progress, fixed store/role emptiness/minimal-field probes (one store/role/partition per step), producer handoff coverage, one native done marker and a separate Access acknowledgement command. Auth also reads its persisted consent due/completion marker.
- Bound: each probe is indexed `EXISTS`, no `COUNT(*)`; no single final step loops over every partition or all workflows. Final ack uses one account partition and the fixed version-1 participant list [ER]. Auth sleeps without a checked-out connection; wait adds no database work. `none` additionally requires initial inventory coverage for all roles and no pre-existing applicable records/copies; minimal erasure protocol markers do not turn an initially empty participant into `erased`, but their shared copies still require durable locator handoff. No wall-clock completion promise is invented from a per-page bound.
- Growth check: the two final named tests grow account-owned page count while holding each step budget, inject failure before/after every commit and port call, replay after DBOS history is removed, and assert outcomes immutable. Assert every store's account-specific personal rows absent, every retained skeleton's exact allowed fields, and unaffected survivors intact. Other participants may still be pending; do not assert global `complete` from just these two acknowledgements.
