# Library type identity keys

Research evidence and recommendation, inspected 2026-10-27. This report is not the Library contract. The question is how to preserve every accepted primary type while bounding indexed keys, filters, counts and continuation. A definition release is at most 4 MiB; that is not a per-identifier limit. The accepted identifier is exact ASCII CURIE text. Alphabetical facets are not required.

## Evidence

PostgreSQL [B-tree documentation](https://www.postgresql.org/docs/17/btree.html) limits an index entry to approximately one third of a page after any applicable compression. This includes the entire composite entry, not just its longest field; a compressible example passing is no guarantee for another valid identifier. [TOAST](https://www.postgresql.org/docs/17/storage-toast.html) can store a large table value out of line, but does not make an arbitrary full text B-tree key safe. An [expression index](https://www.postgresql.org/docs/17/indexes-expressional.html) changes what is indexed, not the entry size rule. PostgreSQL [hash indexes](https://www.postgresql.org/docs/17/hash-index.html) hold a 4-byte hash, are lossy and need heap rechecks, cannot enforce uniqueness, support only equality and one column, and can have overflow chains. They are not a bounded exact dictionary or ordered continuation. PostgreSQL documentation is under the [PostgreSQL licence](https://www.postgresql.org/about/licence/).

Two mature RDF stores demonstrate bounded identity mappings, with materially different collision policies. These are source observations, not claims that their APIs meet the private shelf's growth contract. Clones were read as untrusted text, never installed, built or run; no code was copied.

- **Apache Jena TDB2**, [Apache-2.0 licence](https://github.com/apache/jena/blob/2f3b8d05eaa83db911000e510007eeaab1b6e652/LICENSE), commit `2f3b8d05eaa83db911000e510007eeaab1b6e652`: [`NodeTableNative.java`](https://github.com/apache/jena/blob/2f3b8d05eaa83db911000e510007eeaab1b6e652/jena-tdb2/src/main/java/org/apache/jena/tdb2/store/nodetable/NodeTableNative.java) hashes a node to a fixed-size index key, maps it to a node ID, and synchronizes allocation. [`NodeTableTRDF.java`](https://github.com/apache/jena/blob/2f3b8d05eaa83db911000e510007eeaab1b6e652/jena-tdb2/src/main/java/org/apache/jena/tdb2/store/nodetable/NodeTableTRDF.java) stores the full serialized term in an append file and uses its position as ID; [`TripleTable.java`](https://github.com/apache/jena/blob/2f3b8d05eaa83db911000e510007eeaab1b6e652/jena-tdb2/src/main/java/org/apache/jena/tdb2/store/TripleTable.java) supports pattern lookup through IDs. The inspected hash hit returns its ID without comparing the full node, so the implementation assumes hash identity rather than resolving a collision. [TDB architecture](https://jena.apache.org/documentation/tdb/architecture.html) documents the hash-to-ID and reverse mappings. This is not proof of collision-safe identity.
- **Eclipse RDF4J NativeStore**, [BSD-3-Clause licence](https://github.com/eclipse-rdf4j/rdf4j/blob/f0adec73f408062e89fb008bd9f5d15d30f4db14/LICENSE), commit `f0adec73f408062e89fb008bd9f5d15d30f4db14`: [`DataStore.java`](https://github.com/eclipse-rdf4j/rdf4j/blob/f0adec73f408062e89fb008bd9f5d15d30f4db14/core/sail/nativerdf/src/main/java/org/eclipse/rdf4j/sail/nativerdf/datastore/DataStore.java) finds candidates by a fixed hash, reads each full stored byte value and compares it, then returns an integer ID. Synchronized insertion checks for an existing value before storing data and indexing its ID. [`ValueStore.java`](https://github.com/eclipse-rdf4j/rdf4j/blob/f0adec73f408062e89fb008bd9f5d15d30f4db14/core/sail/nativerdf/src/main/java/org/eclipse/rdf4j/sail/nativerdf/ValueStore.java) maps RDF values in both directions; [`NativeSailStore.java`](https://github.com/eclipse-rdf4j/rdf4j/blob/f0adec73f408062e89fb008bd9f5d15d30f4db14/core/sail/nativerdf/src/main/java/org/eclipse/rdf4j/sail/nativerdf/NativeSailStore.java) resolves pattern values into IDs and exposes statement iteration. It preserves distinct hash collisions through full comparisons, but candidate scanning is not bounded independently of colliding values.

Both designs separate large values from compact internal keys and translate query terms before index operations. Their query interfaces return RDF values and support patterns; SPARQL exposes `ORDER BY`, `LIMIT` and `OFFSET` ([W3C query standard](https://www.w3.org/TR/sparql11-query/#modResultLimit), [protocol](https://www.w3.org/TR/sparql11-protocol/)). Offset pagination is not evidence of bounded stable keyset paging. Neither source establishes the desired account-partitioned facet API or a worst-case constant collision bucket.

Local evidence: [Access write-rate identity](../../services/kernel/src/access/write-rate-identity.ts) and [schema](../../services/kernel/db/access/schema.sql) use an HMAC-derived fixed-size identity for bounded account/IP inputs and a rate counter, not exact arbitrary text equality. Semantic's [source candidate and external claim keys](../../services/kernel/db/semantic/schema.sql) include raw source/external text; [source-facet design](../../services/kernel/src/semantic/relation-facet-rebuilds-design.md) describes bounded 32/1024-byte source identities and digest-derived work identity. Those existing different contracts do not prove that an unbounded type is safe in a B-tree. The [shelf activity report](library-shelf-activity.md) establishes private account partition and activity ordering; it does not establish alphabetical types.

## Comparison and inference

| Approach | Exact identity and bound |
| --- | --- |
| Raw text or an expression returning raw text | Exact until an incompressible entry exceeds the B-tree limit; unsuitable even with TOAST or a release-size cap. |
| Digest plus full-value check | Index key is fixed and a comparison prevents false equality, but one digest can have arbitrarily many candidates. Full-value verification alone neither enforces uniqueness under concurrent inserts nor bounds collision scans. A unique digest rejects a legitimate distinct collision; trusting it silently aliases identities. Cryptographic improbability is not a proof and SHA-256 is not an adopted decision. |
| Surrogate dictionary ID | Fixed FK, sort and filter keys and long value in non-indexed storage. It still needs an exact, concurrency-safe full-value-to-ID mapping; the ID alone does not solve allocation. |
| Truncated prefix | Bounded key but different long values can share the entire prefix. Ignoring oversized values or treating a prefix as identity loses types; rechecking every prefix bucket makes work grow with unrelated types, as does scanning a digest collision bucket. |

An exact mapping with bounded keys and no collision assumption can use a **chunk trie**. Split exact ASCII bytes into fixed, e.g. 256-byte chunks; index each edge by `(partition, account, parent-node-id, chunk-bytes)` with a uniqueness constraint and keep a terminal marker/ID on the final node. The unique root is scoped to the owner partition; mark termination separately so a value and its strict extension remain different. Each index key has fixed overhead plus at most 256 bytes; use `bytea` equality, not locale-dependent text comparison. A full value is retained separately in an unindexed text column, or reconstructible from chunks. No identifier is truncated or limited by chunk size. Point lookups and `INSERT ... ON CONFLICT` per edge, with transactional terminal allocation and retry after conflicts, make same-identity creation converge, and different endings diverge. Lock/insert shared prefixes in root-to-leaf order; transaction rollback leaves no published half dictionary. A generated fixed-size random UUID can be the terminal `typeKey`; enforce scoped uniqueness and retry UUID allocation conflicts. A collision of random UUIDs must not alias values. The trie rather than a digest is the authority; an optional verified digest cache may accelerate a hit but cannot be the only path on collision or miss.

This is an inference and a recommendation, not a claim that either source uses a trie. Its cost is O(L/256) edge probes and upserts for L bytes, plus O(L) bytes for comparison/storage; page, write amplification, round trips, locking and worst-case release-sized inputs require measurement. Trie sharing can reduce space, not increase the required probes beyond the input's own chunks. Finite PostgreSQL value, transaction and resource limits still apply; do not invent a smaller API type cap. Allocation may be staged and resumed in bounded transactions if needed, but must not publish an incomplete identity. A product claiming constant work independent of L would be impossible while reading or returning L bytes.

## Proposed private shelf

Keep the dictionary and all identity resolution inside `(route, account_id)` with owner authorization and partition fencing. Store the full authoritative type exactly; `typeKey` is an opaque, stable, non-reused UUID scoped to the owner, not an authorization credential. Facet results return both `typeKey` and full type; entry list, summary and bulk filters accept the bounded key. A client obtains it from an authorized facet; unknown, foreign-account, malformed and stale keys must follow an agreed non-disclosing error/empty policy. A key must never resolve across accounts. If direct selection of a type not present in facets is needed, specify a separate authorized body-based resolution endpoint capable of receiving the full identifier; a URL or cursor with a 256-byte limit is not that endpoint.

Maintain private count rows keyed by account, typeKey and each supported status, plus an all-status count (or equivalent explicit aggregates). Maintain only positive rows in the *paged facet projection*, via an indexed predicate or separate table. Retain the dictionary/terminal even when every count is zero, so key identity is stable; otherwise a long history of zero-count types makes a page scan unbounded. For each supported status/all selector seek a positive-count index `(route, account, selector, typeKey)` after the last key, limit P+1, and join at most P+1 dictionary rows to return values. Counts update atomically with entry/status/type changes, nonnegative and exactly once under replay. Summary of a particular key is a point lookup; an overall summary should use maintained aggregates, not scan entries or all historic types. List indexes must separately support every admitted shape, e.g. account + activity order, account + status + activity order, account + typeKey + activity order and account + status + typeKey + activity order, with a unique bounded tie-breaker and the same privacy partition. A bulk operation must use the same scoped FK and a separately bounded batch/continuation, not expand all matching entries without a bound.

Order facets by immutable typeKey in a specified byte order, not by full text or mutable count. A bounded encoded UUID is the after-key. This provides deterministic keyset continuation, not alphabetical order or a cross-request snapshot: concurrent additions/deletions may appear or disappear around a cursor. Define the consistency and restart behavior explicitly; if a snapshot is required, retain/version a bounded seekable snapshot rather than claiming this live ordering provides one. The current shared cursor requires binding method/path, canonical owner viewer and **every effective predicate**, including status, typeKey, sort, page size, defaults and any visibility or selection mode, as canonical scalar values. Normalize equivalent inputs before both query and binding; use canonical bounded encoding for key sets with an explicit batch maximum compatible with the 2,048-byte query cap, or a server-side bounded handle with defined lifetime and authorization. Bind the full effective set, not a partial digest without a collision policy. Use the existing epoch/fence handling. After strings must fit 256 UTF-8 bytes and the whole token 4,096 characters; no raw identifier appears in position or associated query. Cursor expiry, rotation and authentication remain the shared helper's contract.

For page size P, SQL examines at most P+1 qualifying positive facet index rows plus bounded point joins, assuming the selected plan and no unbounded residual filter; index navigation is logarithmic in index size. The response bytes are O(P + sum of the returned identifier lengths), not O(P) bytes. It is incorrect to claim a fixed byte response just because P is fixed; ensure response/body and transport limits can carry full allowed values, or adopt explicit streaming/continuation for values without truncation. Entry pages similarly need P+1 qualifying ordered index rows and bounded joins; a type filter must be in the leading seek, not a residual scan. Status selectors should be a finite supported set, not an arbitrary unindexed predicate. Verify actual plans and concurrent contention, and distinguish qualifying row bounds from PostgreSQL MVCC/dead tuple and lock-wait costs.

On an entry type change, atomically remove its old status/type count and membership, add the new one, and maintain activity indexes. A subject merge must resolve the canonical subject and transfer or deduplicate each affected account entry with count deltas exactly once; a paged, idempotent reconciliation can spread work over affected accounts and entries, with ordering/fencing and replay revisions. Do not count both source and destination or delete a retained zero-count type key. If type projection changes asynchronously, document the visible staleness and use revisions/tombstones so stale messages cannot roll counts back. Bound merge work per continuation, not by total merge fanout.

## Decisions needed before implementation

The owning Library/shared API must adopt or change: (1) scoped opaque `typeKey` format, issuance, non-reuse, unknown/foreign behavior and any direct type-to-key resolution; (2) supported status selectors, count semantics, filter combinations and indexes, plus maximum bulk/key-set size compatible with the unchanged canonical-query cap; (3) stable UUID ordering, live-page consistency and epoch behavior across partition moves, mutations and key lifecycle; (4) response transport of complete long identifiers and any resumable response design; (5) exact trie chunk size, allocation transaction/retry and staging budget, storage/retention and operational limits without adding a type length cap; (6) atomic count maintenance, merge and type-projection freshness/replay semantics. SHA-256 is neither required nor presumed adopted. The shared cursor helper and caps remain unchanged.

## Adversarial verification recommended

- Use incompressible valid identifiers longer than a B-tree entry and 256 UTF-8 bytes; create, return, filter, count and continue across them. Include a near-release-sized value and verify full response bytes, not just row count.
- Use many values sharing a long prefix and distinct final chunks, a value that is a prefix of another, and (if a digest cache exists) forced equal digests. Confirm exact distinct keys and no bucket scan.
- Race creation of the same identity and of different identities with shared prefixes; verify one terminal per exact input, no aliases, no partially visible rows and correct retry/rollback.
- Accumulate many retained zero-count dictionary identities; positive facet pages and status counts must stay bounded and keys must survive removal/re-addition.
- Test all supported filter/index shapes, cursor binding changes, foreign-account keys, FK ownership, empty results and merge/type/status transitions with duplicate and reordered delivery. Exercise concurrent mutations between pages against the documented live semantics.
- Grow unrelated types, entries and historical zero-count types independently while holding P, the selected predicate and input lengths fixed. Capture plans and examined rows for facet, filtered list, counts and bulk continuation. Separately grow L and measure trie probes and response bytes; assert the stated linear cost rather than a false constant bound.
