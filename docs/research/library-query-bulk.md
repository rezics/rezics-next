# Query-scoped private shelf operations

Research date: 2026-10-27. This is evidence and a recommendation for adoption into the library contract, not a new API contract. Scope: status changes, Collection additions/removals and library removal, using either explicit selection or one server request for all matching items. Shelf layout is already covered by [the shelf study, sections 3.3–3.4](library-shelves.md) and [the UI contract](../../packages/ui/README.md#shelves).

## Recommendation

Accept a durable operation, discover its targets in bounded pages into a private persistent manifest, then execute that manifest with independently receipted commands. Finish discovery before this operation changes anything that could affect its query. Use an immutable admission key and a captured high-water mark, never the shelf's mutable sort or offsets. Persist each discovery checkpoint with its manifest inserts; persist each target effect with its receipt. DBOS drives recovery and scheduling; native operation and target records define membership, outcomes and idempotency.

Recommend **bounded discovery-time matching**, followed by a frozen manifest. This deliberately does not promise the exact set visible when the user clicked: new entries after admission are excluded, while concurrent changes to existing candidates can affect membership until their discovery page is read. A high-water mark alone cannot freeze mutable status, rating, tags, permissions or Collection membership. A strict acceptance-time snapshot would require additional historical/versioned query data or a bounded total selection limit; neither exists in the current library commands. This temporal choice needs adoption, not an undocumented snapshot guarantee.

### BookOrbit: real query-scoped request, eagerly materialized IDs

The payload-to-effect chain is [B1] → [B2] → [B3] → [B4] → [B5]. `HomeView.vue` records library, filter, text query and sort when all matching is selected. `useBookBulkActions.ts` sends `{query: ...}` instead of an ID array; its displayed total is not sent as an authoritative target count. The DTO accepts query or explicit IDs; the service rejects both together.

On `bulk-set-status`, the controller resolves selection on the server. `resolveSelectionToIds` obtains accessible libraries, applies user/content filters and query predicates, then `findIdsByWhere` selects **all** matching IDs with no limit. Sort is accepted in the query payload but is not used by this resolver. This freezes the in-memory ID list at that query's execution, not at selection in the UI. Status writes thereafter use those IDs, so their own filter mutations do not cause pagination skips. This is genuine server query selection, but memory and initial SQL result size grow with all matches. [B1], [B2], [B3], [B4]

`bulkSetManual` processes groups of 50 with `Promise.allSettled` when reading-attempt support is installed; a rejected target aborts subsequent groups after that group settles. Its fallback instead submits all ID writes with `Promise.all`. Successful earlier effects are not rolled back by this method. No durable bulk manifest, request-key deduplication or per-target replay receipt is present in this traced path. Repeating the HTTP request resolves the query anew and can change lifecycle-related state; setting a status is not evidence of exactly-once side effects. [B5]

Collection add/remove follows the same selection resolver, deduplicates IDs, then performs one insert of all values with conflict-ignore, or one delete by Collection and ID list. The Collection is checked writable before resolution. This path does not establish continuous grant checking during a durable job. Its set-like membership behavior cannot define REZICS duplicate-sensitive behavior. These status/Collection methods return after their work; they do not expose a durable operation handle, cancellation or paged target errors. BookOrbit also has streaming metadata work, but that does not supply these missing status/Collection guarantees. [B6]

### Ryot: useful asynchronous contrast, not the second query-bulk implementation

Following the adopted study's candidate through to execution changes the interpretation of its select-all UI. [R1] sets `take: Number.MAX_SAFE_INTEGER` on a matching list/Collection contents query, receives IDs into the browser and stores them in the selection atom. [R2] maps those entities into an explicit mutation array. Consequently this is **browser enumeration**, not one query-scoped mutation request. Its ID list is fixed by that list response, while authority and state can change before mutation execution.

The GraphQL resolver enqueues add/remove application jobs and returns a Boolean. The backend dispatcher calls sequential per-entity helpers. Add finds an existing entity membership and updates its information, otherwise inserts; remove deletes by Collection/entity identity. Earlier iterations can already have committed when a later one fails; the traced loop has neither a bulk transaction nor a stable per-target receipt. The UI's success notification follows job submission and cannot prove all targets completed. Cache expiry/event work is also performed, so repeat submissions are not proven effect-free. [R2], [R3], [R4]

Ryot supports learning the selection affordance and async execution separation, but cannot count toward two real server query-scoped implementations. BookOrbit and OpenSearch below satisfy that requirement. Do not transfer Ryot's set-membership semantics or optimistic completion message to REZICS.

### OpenSearch: query snapshot, bounded scroll/bulk, explicit partial effects

The request-to-execution chain is [O1] → [O2] → [O3] → [O4]. `POST /{index}/_update_by_query` parses the query/script into a server request. The REST base handler either waits or stores a task result and returns a task ID for `wait_for_completion=false`. Transport starts the bulk-by-scroll action, whose source issues an initial search and successive scroll requests. The request defaults to pages of 1,000; each scroll page builds a bulk request. This is the second inspected implementation with real server query-scoped mutation semantics.

The official [Update by Query contract](https://docs.opensearch.org/latest/api-reference/document-apis/update-by-query/) describes a start-of-operation snapshot, optimistic version conflicts, already-applied changes surviving later failure, task progress/cancellation and rejection retries. Source sharpens this: update requests carry each hit's sequence number and primary term; successful bulk items increment counters, conflicts are counted and either abort or continue, and cancellation is checked between work stages. The scroll advances independently of edited filter/order fields. Slicing creates multiple readers; it should not be inferred to provide a single cross-shard or cross-slice serializable business transaction. [O2], [O3], [O4], [O5]

The source retries rejected requests with backoff and distinguishes failures from successful bulk items. It does not establish a request-key guarantee that resubmitting a completed HTTP query cannot execute a script again. Task identity is progress identity, not permanent mutation deduplication. Scroll contexts also expire and are not a native PostgreSQL manifest that DBOS can reconstruct after arbitrary downtime. Follow the snapshot/traversal and per-item conflict patterns, not the storage mechanism or a claim of exactly-once arbitrary scripts. [O3], [O4], [O5]

### Primary API guidance

- [Google AIP-151](https://google.aip.dev/151): return an operation handle for long work, with progress/partial-failure metadata, a terminal result or error, and documented expiry. An initial validation error differs from failure after work begins. This supports an operation resource; it does not require REZICS to adopt Google's protobuf transport.
- [AIP-234](https://google.aip.dev/234): synchronous batch update must be atomic; asynchronous batches may support partial success. Partial failures identify individual request indices and should omit transient errors still being retried. [AIP-235](https://google.aip.dev/235) discourages filter-based deletion unless necessary and requires documented batch bounds. These are design guidance, not claims that REZICS's existing explicit partial-result API violates its own contract.
- [AIP-165](https://google.aip.dev/165): necessary criteria-based deletion is an asynchronous operation using the same filter meaning as listing; its non-forced form reports count/sample without deleting. This supports a meaningful removal confirmation, but a preview is not proof of the later target set. [AIP-155](https://google.aip.dev/155) motivates client request identity for safe resubmission after a lost response.
- [Shopify bulk mutation imports](https://shopify.dev/docs/apps/build/apis/graphql-admin/bulk-operations/imports): a job has an ID, status and incrementing `objectCount`, and result/partial-result data; JSONL line ordering is not execution ordering. Per-input mutation results must be examined rather than equating job completion with every row's success. This is an explicit-input job contract, not evidence for query-time snapshots. Its [2026-10 cancellation API](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/bulkOperationCancel) starts cancellation and explicitly allows a delay before cancellation completes.

## Patterns and limits shared by the evidence

Selection representation, discovery, target execution and user-visible completion are separate responsibilities. BookOrbit freezes IDs before mutations but pays unbounded materialization cost; OpenSearch bounds each transfer and protects snapshot hits with optimistic concurrency. Ryot demonstrates that async enqueue alone fixes neither selection growth nor truthful completion. Neither real query-bulk source proves permanent request/per-target deduplication. Standards and Shopify make partial completion and operation identity explicit. These observations support a bounded native manifest plus receipts; that mechanism is an inference for REZICS, not code claimed to exist in either application.

## Proposed mechanism for REZICS

### 1. One admission request

Submit exactly one of explicit identifiers or a normalized query, plus action arguments and a client idempotency key. Bind the account, optional source Collection/context, target Collection, query-language version and action version into an immutable digest. Reject unknown filters, invalid combinations, excessive predicate depth/bytes and unsupported actions before admission. Use the same private predicates as listing; no public search index may become private membership authority. Shelf layout/cursor/display sort does not define the target set.

Start with at most 1,000 explicit targets per request and 100 candidates per discovery/dispatch page; these are proposed limits, not measured throughput promises. Store explicit input as bounded operation input, then stage it through the same manifest path. Do not manufacture a browser ID list for query mode. Explicit subjects are deduplicated for status/library actions; explicit Collection removals identify member occurrences. Distinct subjects and member occurrences are different selection types.

In a short account-partition command, authorize, capture the immutable durable initiator/source binding, persist the operation and its admission bound, and emit enqueue intent with its receipt. Return `202` plus stable operation ID/location; this acknowledges acceptance only. Use the existing event relay to enqueue a deterministic DBOS workflow ID, closing the commit/enqueue crash gap. Same key/digest returns the same operation after live authorization; changed digest conflicts. Neither replay nor a second enqueue creates another operation.

### 2. Finite discovery with an immutable key

Add an indexed, immutable, per-account entry admission sequence and incarnation identity, assigned on creation. Capture high-water `H` through the same transactional account counter used by creation: a concurrent insertion either commits before the captured bound or gets a larger sequence afterward. A bare PostgreSQL sequence allocation, UUID timestamp, `created_at <= acceptance_time`, or maximum random subject ID does not prove this ordering because allocation and commit can differ. Existing rows require a migration/backfill before enabling this traversal; these fields are proposed storage, not current capabilities.

The candidate family depends on the source surface: an entry shelf scans account entries; a Collection-origin shelf scans member occurrences, including subjects without an account entry. Give member creation the same immutable admission/bound discipline. Persist a Collection-origin discovery submanifest and checkpoint together on its source partition, then idempotently acknowledge immutable pages to the account operation. Do not claim atomic checkpointing across two partitions. Deduplicate subjects for status/library actions while retaining occurrence IDs for member removal. A status target records the account entry's observed revision/incarnation or explicit absence; creating an absent entry must use insert-if-absent, never an unconditional upsert over intervening edits.

Scan raw account candidates in ascending admission sequence with `after < sequence <= H`, `LIMIT 100`. Evaluate the normalized predicate for that bounded candidate page, using bounded authoritative point reads for external subject/Collection attributes. Do not put an expensive arbitrary predicate before `LIMIT` and assume only 100 rows were examined. Use bounded `EXISTS`/probes rather than expanding Collection duplicates or reading an entire subject's history. An unsupported expensive predicate must be refused or served by an explicitly bounded index/projection, never silently approximated.

Commit the matched target records, observed incarnation/revision, and the last **examined candidate** key atomically in the operation's partition. Advance past nonmatches too. On crash, repeat the same interval safely using manifest uniqueness; never advance a checkpoint without its target records. Once the finite interval is exhausted, atomically mark discovery complete and freeze its total. Discovery retries may observe later concurrent state on an uncommitted page, which is part of the stated discovery-time semantics.

No effect belonging to this operation starts until all discovery, including any occurrence expansion for removals, completes. For a status-filtered shelf, changing all `planned` entries to `completed` then consumes manifest keys, not a shrinking `planned` query. Removing library entries, changing last activity, and removing the source Collection's membership likewise cannot shift traversal. Never use `OFFSET`, the current shelf cursor, ordinal keys that can respace, or `SKIP LOCKED` followed by checkpoint advancement over unvisited targets.

Concurrent external changes remain visible during discovery: an old entry can join or leave the query before its page, and a deleted/recreated entry receives a new incarnation above `H`. After discovery, membership is immutable; execution does not rerun the filter. Capture revisions/incarnations so an intervening edit becomes an explicit conflict rather than an implicit overwrite. This freezes identities, not authorization. A queue delay is also why UI count and final discovered count can differ.

### 3. Bounded execution and exact replay identity

Persist an immutable ordinal and target payload for each manifest item. Derive a target command key from operation ID, action version and target occurrence/incarnation, not from an attempt number, mutable cursor or a fresh random key. Keep its request digest, expected revision and arguments unchanged on every retry. Preserve resolved subject identity instead of repeating redirect resolution and changing the digest during replay; the current HTTP command wrappers' preflight reads are not themselves a durable bulk adapter. Fetch at most 100 pending items by indexed manifest ordinal. Initially execute commands serially per operation; existing queue concurrency bounds jobs, not an additional unbounded `Promise.all` over targets. Give each command the existing finite library deadline and each page a time budget that yields between commands as well as a target-count bound.

For account actions, use a command on the account partition that atomically performs CAS, existing follow behavior where applicable, events and the target receipt. Prefer also committing the target's terminal outcome/counter transition in that transaction when colocated. Collection effects receive the same atomic treatment on the Collection partition. A retry after commit replays the receipt, including the generated member ID, rather than creating another occurrence. A retry after rollback executes again with the same identity. This provides exactly one committed effect for a successfully applied logical target while its evidence is retained; it does **not** promise every selected target succeeds or exactly-once execution of arbitrary workflow code.

| Situation                                                  | Recommended outcome/recovery                                                                                                                                                                                     |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lost reply or crash after effect, before DBOS checkpoint   | Reauthorize and retry the identical command; receipt proves the earlier result. A native outcome transition updates progress once.                                                                               |
| Serialization failure, deadline, overload, partition fence | Use the shared command-step retry policy; leave target pending while retryable. Exhaustion becomes an operational interruption, not a claim of no effect. Resolve the exact receipt before final classification. |
| Revision/incarnation mismatch                              | Record `conflict` with no replacement write. Do not refresh revision under the same key or let a recreated revision-1 row pass an old revision-1 CAS. A newly requested action needs a new logical identity.     |
| Same state, already absent, missing member                 | Distinguish a deliberately receipted no-effect outcome from a precondition conflict; adopt the policy per action. Never infer this operation applied merely from current state.                                  |
| Grant/consent/account/delegation revoked                   | Deny executing and replaying commands under the live Access policy; stop further work for operation-wide authority loss. Preserve prior effects and report partial completion.                                   |
| Unknown transport outcome or evidence unavailable          | Keep `reconciling`/interrupted, not success or safe-to-repeat with a new key. No speculative duplicate addition.                                                                                                 |

Restore the durable initiator at every executing command attempt and before receipt disclosure, with the actual source and target anchors and original scope ceiling. A replayed DBOS step may simply return its already-recorded result; it must not confer authority for the next command. Do not use `trustedAccount` as a substitute for initiator restoration for user-requested bulk changes. Receipt-only reconciliation is allowed only through existing Access policy or a private internal accounting reader that verifies exact committed operation/target/receipt evidence, as in erasure. It may establish a prior outcome; it cannot authorize a new effect or disclose hidden target data to a revoked caller.

Record terminal non-effect outcomes durably too. Exceptions roll back a command receipt, so a caught CAS/validation failure needs a separate guarded native outcome transition. `runCommand` requires at least one event: an outcome command can emit a private operation event, while an event-free receipt would require a separately vetted module-private pattern such as semantic bulk's receipt-only resolution. Do not call the ordinary envelope with an empty event list. Accounting may continue under narrowly scoped service authority after revocation; personal writes may not. Transient attempts and replayed successes must not increment terminal counters again.

### 4. Collection source/target steps and duplicates

1. On the **source account partition**, discover private library targets and freeze subject/incarnation records. On a Collection surface, also preserve selected member IDs; membership reads require the source Collection's authority. Persist the source record/digest before dispatching anything elsewhere.
2. For **add**, derive one logical target per selected subject under the proposed append-one policy. On the **target Collection partition**, restore/check the original initiator, source binding, subject readability and current `collection:update` authority. Execute the existing member-add semantics, capacity check and ordering behavior with a stable receipt key; store its resulting member ID. Existing occurrences remain legal. One retried add cannot become a second occurrence; a separately admitted add may create one.
3. For **remove**, selecting a visible occurrence means removing that member ID only. A subject-scoped library selection instead needs an explicit policy: recommend removing all occurrences of the selected subjects that were recorded during a separate bounded target-Collection discovery phase. Freeze exact member IDs before deleting; add an immutable member admission key/incarnation with the same high-water rules as entries. Capture this target bound when expansion starts and report its time separately from the account admission bound. Current ordinal cursors are unsuitable if concurrent reordering/respacing is allowed. Scan the target Collection once in bounded raw pages, checking selected-subject membership through bounded source-manifest probes; do not scan it again for every selected subject. Commit each occurrence submanifest page and its checkpoint together on the Collection partition. Transfer/acknowledge those immutable pages to the source operation idempotently; begin effects only after the complete expansion is sealed. Concurrently added occurrences after the bound survive; no retry runs a fresh `DELETE WHERE subject_id = ...` that could erase them. Collection size is currently capped at 5,000, but do not turn that into one transaction or one unpaged workflow result.
4. Commit each effect and receipt in the target partition; only then acknowledge its outcome to the source operation with a unique target identity. A crash between these steps replays the target receipt before the source acknowledgement. Source progress can lag committed target effects and must say so. Do not hold a source transaction open while calling a target command or claim a two-partition atomic commit.

Source checks and target checks are execution-time observations through Access, not a distributed lock on the query. Binding a frozen source target prevents substitution; live authorization prevents an old manifest from acting as a permanent grant. Concurrent revocation follows existing command admission/linearization rules. Do not promise an atomic snapshot spanning account state, external subject attributes and Collection membership. Per-Collection ordering work remains subject to [placement/respacing](../../services/kernel/src/library/collection-placement.ts), and public Collection projection uses existing listing effects. Private source selection and target error details must stay private; do not publish the selecting account or query with a subject event.

### 5. Progress, failure, cancellation and retention

Expose a private operation resource with phase (`queued`, `discovering`, `applying`, `reconciling`, terminal), timestamps, selection/action summary, discovery checkpoint, scanned/discovered counts, terminal target counts and cancellation request. The UI can poll it with backoff; notifications are optional hints. Do not put an unbounded target list or error array on that resource: provide authorized keyset pages of outcomes, with member-level counts separately from subject counts.

During discovery, total is unknown; display discovered/scanned counts and label any preflight count as an estimate. After discovery, `selected = pending + applied + no_effect + conflict + failed + denied + cancelled` is a useful invariant for mutually exclusive target outcomes at one counting level. An expanded removal counts member targets separately; a subject with some removed and some failed occurrences is partially applied, not wholly successful. Retry attempts and receipt replays are separate diagnostics. Update counts from unique terminal transitions, never workflow-local increments or repeated whole-manifest `COUNT` queries. A receipt may prove application while the source counter still lags; reconcile before publishing a terminal summary. Report `completed_with_errors` separately from full success, and preserve target-level reasons when an operation fails globally.

Cancellation is a durable request checked before discovery pages and before dispatching the next target. An in-flight admitted command may finish; cancellation does not undo it. Drain/reconcile in-flight commands, then classify untouched targets as cancelled through bounded accounting pages. During interrupted discovery, say selection is incomplete rather than reporting undiscovered matches as failures. Do not silently compensate by restoring old statuses or readding deleted members: that could overwrite newer user work. New retries of conflicts/denials require explicit new intent; resuming a transient interruption uses the same immutable manifest and identities.

Keep native operation identity, target deduplication/outcome records, creation receipt and durable-initiator evidence at least through the supported execution/retry horizon. DBOS retention alone is insufficient. Recommend retaining a compact root tombstone keyed by principal/command-kind/client-key, with digest, operation ID and terminal state, for the account's lifetime. After detailed results expire, a same-key admission returns an authorized expired-operation result and never starts fresh work; changed input still conflicts. The admission body must consult that native tombstone even if its old command receipt has been collected. This trades permanent compact admission-key storage for unambiguous rejection of old retries; a bounded-retention alternative needs an explicitly time-bounded admission-key namespace. Do not silently recycle arbitrary client keys.

Never let an expired workflow ID reopen effects. Enqueue/recovery and every target dispatch must check native terminal state before issuing a command; an expired operation cannot execute. If receipt or initiator evidence disappears while work is pending, fail closed. Garbage collection itself uses bounded pages; target evidence may be collected only after the operation is permanently closed to execution. A new action following expiry requires new user intent and a new admission key.

## Work, counters and growth

Let `A` be admitted source candidates up to `H`, `N` the frozen targets, `D` the expanded member occurrences, `C=100` the proposed page bound, and `J` unrelated retained jobs/targets. A sparse predicate can still require `O(A)` discovery, even when `N` is tiny. With the proposed account/sequence and operation/ordinal indexes, each page examines at most `C` candidates plus bounded point probes, with B-tree seeks logarithmic in relation size. These are design bounds, not measured PostgreSQL plans. Existing schema does not prove them for the proposed fields or every shelf predicate.

Manifest storage is `O(N)` or `O(N+D)` for occurrence expansion; receipts, outbox and downstream effects grow with committed target commands, not one HTTP request. Overall work cannot be constant in the number of selected items. Peak worker payload/memory is `O(C)` plus bounded authorization evidence; no transaction spans `N`. Collection append can trigger `O(M)` respacing for `M <= 5,000`, so even a one-target command is not uniformly constant in Collection size. Public listing/projection work and contention on shared account/Collection counters add costs beyond selection.

Use indexed per-operation pending/terminal access and unique outcome transitions so a progress read is `O(1)` rows plus index seeks, not `O(N+J)` recounts. Bound active jobs per account and target Collection, dispatch concurrency, error-page size and predicate probes. Reserve/rate-charge work in bounded target chunks under an adopted policy; one query request must not buy unlimited uncharged writes. Do not reserve an exact match count before discovery or charge every retry as another logical success. Current write-rate rules cover explicit batches, not this future query job; quota/counter semantics need adoption.

DBOS history also grows with pages/steps. Use bounded continuation segments, for example at most 100 pages per workflow, persisting a continuation generation/checkpoint and enqueue intent natively. Each segment uses a deterministic workflow ID; target receipt keys stay stable across segments. Never attach the entire manifest to a DBOS input/result. This bounds live history per segment, not total retained storage. Operation/receipt/DBOS retention and deletion throughput need capacity planning against arrival rate and retry duration. Compact root tombstones under the recommended policy grow with lifetime admitted operations, even after target rows expire; they require an account/key index, not a history scan.

Before implementing claimed bounds, growth checks should vary source account size with sparse/no matches, unrelated accounts/receipts/jobs, huge histories behind a filter, duplicate memberships, Collection fullness/respacing, concurrent edits/reorders, retained manifests and revoked grants. Recovery cases include every commit/checkpoint/acknowledgement gap, repeated cancellation, workflow collection and delete/recreate ABA. These are future verification recommendations; no product tests or gates are changed by this report.

## Decisions still needed in the owning contract

1. Adopt discovery-time membership, or require an exact acceptance-time snapshot. The latter requires historical/versioned predicate inputs or a total selection cap; an immutable cursor and high-water alone cannot supply it. Decide whether the confirmation may accept count drift or must confirm a completed manifest before effects.
2. Adopt append-one-per-selected-subject for Collection add, versus ensure-at-least-one. Ordinary Collections permit duplicates, so a uniqueness constraint is not an acceptable accidental choice. For subject-scoped removal, adopt all captured occurrences versus one occurrence, and specify deterministic placement of additions relative to concurrent edits. Explicit occurrence removal already has a clear identity.
3. Define no-effect versus conflict for already-desired status, disappeared entry/member, and concurrent revision changes; recommend frozen revision/incarnation CAS with conflicts preserved. On a Collection surface containing subjects without entries, decide whether bulk status creates entries, as single-item `putEntry` can, or only updates saved entries. Decide whether target-specific denials continue other targets; recommend stopping on operation-wide authority loss. An empty manifest should complete as no work after authorization. No all-target success promise follows from admission.
4. Define library removal's destructive scope and confirmation wording. Current `deleteEntry` deletes the entry with CAS and leaves copies; it does not erase progress/history or Collection membership. The shelf study asks confirmation to name history removed. A bulk wrapper cannot invent history deletion or silently imply it exists; any adopted cascade must itself have bounded durable steps and replay identity.
5. Adopt explicit/query admission limits, per-account/Collection scheduling, cost/rate policy, retry/expiry horizon, outcome retention and cancelled-operation presentation. The proposed page and continuation sizes are starting bounds, not evidence of acceptable latency. Decide which shelf predicates have authoritative bounded implementations before enabling them in bulk.
