# Independent analysis of bounded current multi-leaf final evidence

Research date: 2026-10-28. This report is evidence for an owning-document decision, not a new native ABI,
admission rule, implementation, or acceptance waiver. Repository contracts determine semantics.

## Finding

**The inspected implementation does not establish the required universal final-proof bound.** Current Search
Scope and Semantic leaf execution are unavailable scaffolds. The real selected-slot machinery admits nine
independent material properties with 32 current selected statements each. Replaying their native forward
selection traversals can require at least 288 raw keys. Even granting an ideal directly reusable identity for
one matching fact leaves at least 257 keys, before candidate, alias, lookahead and extra final reads. Existing
coalesced relation-facet maintenance does not index these material slots and does not repair this example.

This verifies a counterexample to **fresh earlier-leaf replay using the existing specified access paths**.
It is not an impossibility proof for every conceivable algorithm or additive native access structure. There is
no implemented Scope evaluator to run and expose a measured 288-key violation. Neither a different traversal
order nor an unspecified useful hint is an implemented universal proof. Preserving all constraints requires a
new, explicitly justified source-owned evidence-access capability; this report does not approve one.

The failure exists in a fixed, finite, fully selected, readable state. Long-name cursor sizing, perpetual
writes, lack of test slots, and a single relation leaf's eventual last-survivor discovery are not its cause.

## What a final proof has to pay

Search alone interprets statement values, inclusive quantity/time ranges, units, same-statement item qualifiers,
and AND/OR/NOT. `compileCurrentFilter` deduplicates by complete normalized clause, including property and
qualifiers. Its actual planner accepts a complete aligned result vector. Unknown survives NOT; decisive true
OR and false AND can settle soundly. A true AND of independent leaves needs each positive. Engine
`matched_queries` can prioritize work but cannot supply native evidence or truth.

The producer returns selected facts, coverage and raw progress. The current contract permits a proven complete
possible-witness pair path for item values; otherwise it uses bounded current selected slots. Range and
qualifier predicates are explicitly not native SQL filters. A witness `revalidate` argument is a previously
discovered opaque native identity, not a property/value query, ordinal guess or supplied body.

The following accounting follows [Search's contract](../../services/kernel/src/search/README.md#scope-source)
and [Semantic's contract](../../services/kernel/src/semantic/README.md#current-leaf-evidence):

- All candidate, alias, internal driver, discarded, duplicate, lookahead and reread keys debit the same
  aggregate 256. Splitting calls or asking for fewer returned facts does not reset it.
- One native call has at most 101 keys, including its explicitly reserved lookahead, and at most 100 witnesses.
  Points, witnesses, rows, bytes and empty seeks have separately reserved/reported allowances. They cannot pay
  for raw keys. Empty indexed probes still cost points and empty seeks.
- Compact's 33-operation shape and expanded selection's 32-candidate shape bound a slot, not its cost at zero.
  A batch or JSON selection containing 32 identities does not turn their examination into one charged key.
- Preparation, continuation and final structural identity observations independently pay the specified two
  4096-home sweeps, 8192 metadata rows plus core observations. These are not candidate-key credits and cannot
  be omitted from a physical capture. All other native axes must also fit independently.
- Current source/original/terminal authority and earlier positive evidence must be freshly checked before
  disclosure. A digest is not a current observation of every foreign target or Content fence.

Legitimate request-local reuse matters: read one property's selected evidence once and use the same Search
matcher for several clauses against it, subject to the required current observation. Deduplicate a shared
foreign target read where the native observation permits it. The ledger still charges every actual read.
This saves repeated work for shared properties; it does not share distinct properties' candidate identities
and does not transport another request's truth or witness list.

## A concrete admitted selection

Use a valid custom release, not nine invented relation slots. Define `ex:Subject` with nine material quantity
facets `ex:p1` through `ex:p9`. Each is `multivalued: true`, units `['1']`, with the ordinary quantity value
schema and no `relation` declaration. Optionally admit the item qualifier `ex:key`, targeting `ex:Target`,
on each quantity property. The source type lists those properties; its facets list the nine quantities.

Choose native routed source `S = 00000000-0000-8000-8000-740000000001` and a readable target
`Q = 00000000-0000-8000-8000-750000000001` in a different home partition. Create one English source label.
For every property, create 32 normal statements in native sequence order, whose values are
`{ amount: '+1', unit: '1' }` through `{ amount: '+32', unit: '1' }`. In the qualified variant every statement
has `ex:key = Q`. No statement is hidden, retracted, deprecated, privately selected or fenced out. Release,
source, terminal, original, revision and target observations are ready and stable.

The filter is the AND of these nine clauses, one for each distinct `p`:

```json
{
  "statement": {
    "property": "ex:p1",
    "range": { "gte": 32, "lte": 32, "unit": "1" },
    "qualifiers": [{ "property": "ex:key", "in": ["00000000-0000-8000-8000-750000000001"] }]
  }
}
```

Omitting qualifiers gives the simpler nine-leaf case. Keeping them makes the foreign observation explicit:
the admitted expanded-leaf count is 18, while the shared current plan has nine distinct statement leaves.
Both are below 32; one qualifier and one value are below four qualifiers and 64 values. Adding an explicit
type anchor, if desired, uses one more admitted leaf. The quantities already provide a positive anchor.

## Explicit debit and progress argument

In the actual forward compact/selected-ordinal traversal, statements 1..31 do not satisfy the range and
statement 32 does. Let `H >= 0` denote all additional outer candidate/alias/lookahead/internal/final keys.
Use the most favorable debit of only one key per examined fact identity; ignore even the slot-head and
adoption observations. These are **lower bounds**, not invented exact SQL receipts from the stub:

| Final-request strategy                                                      | Mandatory fact-key subtotal | Consequence                                                         |
| --------------------------------------------------------------------------- | --------------------------: | ------------------------------------------------------------------- |
| Freshly replay nine independent selected traversals                         |              `9 × 32 = 288` | `288 + H > 256`.                                                    |
| Grant one ideal retained matching identity and exact one-key current reread |          `8 × 32 + 1 = 257` | `257 + H > 256`, even granting more than pending progress promises. |
| Replay nine, then separately reread nine positives                          |             `288 + 9 = 297` | Applies if those final reads cannot be fused with discovery.        |
| Ideal one-identity strategy, then separately reread nine positives          |             `257 + 9 = 266` | Same qualification; no mandatory double counting is assumed.        |

The first two rows already fail before positive final rereads. If fresh discovery is the final valid
observation, omit the extra rereads; it still fails. If selection-head, normalization/body, witness candidate,
provenance, or alias paths examine additional keys, charge those too. Returning one matched fact, zero rows,
or a small receipt does not erase preceding raw work. Splitting 288 into calls below 101 cannot fit one 256
ledger. Generous native point/row/byte allowances cannot change this arithmetic.

The scalar progress record carries one leaf/value/phase and one native sequence or consumed witness UUID.
It does not identify all nine matches. In particular a selected ordinal is not an opaque revalidation
identity, and a last-consumed witness cursor is not a vector of earlier positive witnesses. The ideal
second row intentionally grants one such direct identity anyway. `ownerBasisDigest`, the other encrypted
position fields, a prepared handle, or server-private state must not conceal the missing vector or bodies.

Every single leaf can finish a bounded traversal in finite steps. The trouble is assembling a fresh final
AND proof in one request. Keep this state quiescent, complete every existing maintenance job, and repeat the
procedure: there is no material hint changed by relation rebuild and no new path on the next request. Earlier
matches must be rediscovered and checked; partial results cannot be carried as truth. A cycle of scan,
restart, or fresh-cursor/readiness responses is not liveness in this fixed ready state.

This is deliberately a path-specific counterexample. A hypothetical reverse traversal happens to find `+32`
first, and a program hardcoded to probe ordinal 32 happens to win this instance. The actual traversal is
forward. For another predetermined order, place the sole match last in that order; values/ranks/selection
order can be written accordingly. This adversarial observation explains why a fixed ordering alone supplies
no universal bound, but does not prove all adaptive algorithms or future indexes impossible. The current
contracts provide neither a direct material matching-fact path nor a complete range/qualifier access proof.

Foreign changes reinforce freshness, rather than being necessary to the arithmetic. A current hide/denial
of Q, or a current Content source fence on a selected imported statement, can invalidate evidence while local
slot selection/adoption stays unchanged. The real `fences.ts:candidateSources/fencedIds` uses current
foreign-home fence observations; the native contract also requires referenced-target authority and public
consent. A single local selection generation cannot certify earlier positives globally. After a change,
Search must rematch current returned facts; unavailable/denied is unknown, including under NOT.

## What completed coalesced repair really supplies

The owner implementation at [the pinned commit](https://github.com/rezics/rezics-next/tree/4fc44443992ddf2a9c94a0c32de328375558e810/services/kernel/src/semantic)
is useful, but has a narrower invariant than universal leaf repair:

- `relation-facet-witnesses.ts:relationFacetProperties` includes declared facets with `property.relation`
  only. `insert-facts.sql` and `candidates-insert-candidate.sql` populate possible pair identities for relations,
  with UUID values. The nine quantity properties produce no such pair driver or useful hint.
- `visibleWitnesses` and `facet-witness-evidence.sql` check actual compact/expanded selection, current
  revision, moderation/retraction, source eligibility, fences and target visibility. They are not an AST
  interpreter. The private helper's hardcoded normal rank/normalization still needs the shared producer
  extraction described in Semantic's contract.
- `requestFacetRebuild` coalesces source-home generations/causes. `relationFacetRebuilds` scans durable
  finite pages, stages at most one visible `witness_id` for each `(property, value)` pair and publishes after
  completion. `facet-witness-stage.sql` uses conflict suppression for those pair entries. This is a real
  query-independent positive relation hint, not a saved proof of an arbitrary material leaf.
- `matchFacetProbes` tries the saved hint and at most 32 further possible witnesses through
  `facet-witness-range.sql`, requests repair on unresolved work, and returns true or `not_proven`.
  Its 256-probe input cap is not a 256-total-raw-key receipt. The old method has no caller ledger/continuation
  and cannot be silently substituted for `readScopeLeafEvidence`.

Under finite quiescence and eventual maintenance service, a surviving unqualified relation pair can obtain a
useful hint, which must still be currently point-validated. This helps a long 257/4096 witness history; the
maintenance pass itself costs work proportional to history in bounded pages. It does not imply a hint for
every material item/code/range/qualified leaf. Even for item relations, a 64-value leaf may require multiple
hint probes; no whole-filter cost bound follows from one hint per pair.

Nor does a completed pass guarantee definitive negatives for every supported leaf. The native contract's
`empty_pair` requires a truly empty complete possible-witness superset for every requested pair, including
bootstrap/write completeness. A historically nonempty pair whose witnesses are now unreadable remains
nonempty; deleting its visible hint supplies no such certificate. End-of-range, a repaired hint miss, or
old rejected witnesses are not current negative evidence. Complete selected-slot coverage can prove a
material nonmatch, but its raw reads are charged. The contract explicitly permits some nonempty historical
pairs to remain unknown after quiescence; that safety rule must not be rewritten as false or liveness.

## Consequences for UUID unions and ordered TypeLists

A UUID Scope/Zone union need not prove every alternative false once a true alternative settles membership.
Nevertheless a Zone containing only this Search scope, or other alternatives that do not settle true, needs
the nine-leaf proof for its essential candidate. Union OR is not a shortcut through the internal true AND.
Original-to-terminal resolution and readable aliases must also be real, current and charged.

The TypeList ordering reports correctly separate native ordering from UUID union membership: use the actual
native ordered candidate stream and apply current Zone membership and type residuals without sorting a
truncated UUID prefix. That does not make an essential Zone Search residual cheaper. A type leaf may be
simple, but the candidate's Zone membership can be exactly the filter above. The unresolved ordered tuple
cannot be passed as covered/exhausted. This issue survives even if every name has one byte and every cursor
fits. Aliases 257/4096 and last-readable originals add progress obligations; they provide no key credit.

A proposed universal seam must supply an actual worst-case derivation, not merely say “repair supplies hints.”
For one final request require, with actual driver debits and shared reads counted once only when really reused:

```text
K_final = K_candidates + K_aliases + K_lookahead + K_identity_driver
        + K_selected_discovery + K_exact_final_rereads + K_other_raw <= 256
```

State a per-shape bound across up to 32 admitted leaves and 64 values, plus independent points, witnesses,
rows, bytes and empty seeks. Show how the pending alias is resumed first, how earlier matches are rediscovered
in the same request, what completed maintenance guarantees, and a finite progress measure in a fixed ready
state. An illustrative allocation of four keys per leaf would consume 128 before outer work; nothing inspected
establishes four, or any equally sufficient constant, for every range/qualifier/negative case. Do not present
that arithmetic as a repair design. Readiness for an essential historical unknown also needs an explicit
contract distinction from a promised positive's finite final proof.

Recommend a source-owner design/proof follow-up for this universal seam before positive Scope/Zone adoption,
while allowing separately justified request-local reuse work. Keep Search's same pure matcher/planner as the
sole interpreter. Do not create a private query/holder/permission engine, a second truth interpreter, a
query-specific hidden proof cache, a ninth position field, or a browser/server pool snapshot/PIT across calls.
If no evidence-access design can meet the bound under the admitted semantics, escalate the explicit constraint
tradeoff; this report supplies no authority to raise 256 or reduce filters.

PostgreSQL's residual scan illustrates why few successful rows do not bound examined input. Its Memoize node
illustrates that avoiding repeated execution by retaining results uses actual state, memory and completeness
rules. That is a distinct capability, not something scalar continuation silently provides. REZICS can reuse
data within one request; it cannot import that cache across requests under the current contract.

PostgreSQL's [index-only scan documentation](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)
separates an index's data from visibility evidence; its
[transaction isolation documentation](https://www.postgresql.org/docs/18/transaction-iso.html) distinguishes
statement and transaction snapshots. Neither a local index hint nor one home's RR client establishes current
authority across later requests and foreign homes. These are analogies, not a replacement for native Access.

OpenSearch's implementation retains actual sort values for keyset position. Its official
[pagination documentation](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/)
distinguishes live `search_after` traversal from retained PIT contexts. A position and a stable snapshot are
different mechanisms. A native ordered TypeList tuple solves order continuation, not current multi-leaf proof.

The shared pattern is explicit separation of access path, residual interpretation, visibility, continuation
and retained state. The recommendation is to preserve those boundaries and require a native cost/progress
proof for the missing evidence access path. No external files or long passages should be copied.
