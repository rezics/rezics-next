# Zone TypeList ordering with a bounded union restriction

**Research date:** 2026-10-28

**Question:** Can a Zone restrict a composition `TypeList` to its current saved-scope / mounted-Collection union while preserving the list's declared Search order and making bounded, resumable progress?

## Finding

The smallest honest design is a native Search candidate stream in the exact `TypeList` sort, followed by current Zone-membership residual proofs over each candidate. For candidate `c`, membership remains `current subject Access(c) AND distinct union(admitted saved-scope membership(c), readable mounted-Collection membership(c))`; the membership proof does not replace Search's own current filter/source evaluation. The residual step must retain the stream's exact raw sort tuple. It must advance past a candidate only after the candidate is definitively eligible or ineligible; an essential `not_proven` result holds the boundary before that candidate and resumes the same candidate and owner proof. A true result from any current union source settles that union, subject to current source authorization and the final subject-Access recheck.

This is a viable composition pattern, but the current branch does not implement its required seams. The ordinary `Search.search` method returns a public filtered page and performs its own drop/refill; the Search scope adapter currently returns retryable readiness; Semantic's leaf producer is an explicit `not_ready` stub and the identity ports described by its README are not exported; Commerce's `collection-source.ts` does not exist. A Zone cannot produce the required result by calling public Search once, sorting one UUID page, or assuming a refill policy.

Two ordering contracts remain distinct:

1. The Zone `/subjects` union listing is in ascending canonical UUID order, as specified in [zone-membership](../zone-membership.md#ordered-settled-prefixes).
2. A composition `TypeList` keeps Search's native `name` or `collections` order. Search sorting one UUID prefix does not preserve either of those orders globally.

The recommendation is an additive internal ordered-candidate port owned by Search, consumed by Zone's residual union evaluator through a Zone-aware presentation dispatch. It should share Search compilation, engine hits and current evaluation, but must not call the public global Search endpoint as a black box. Keep the two orderings explicit and separate.

## Evidence from this branch

### Composition plans a global Search read

`platformRegistry` admits `TypeList.sort` as `name | collections`; its reader creates only `{filter:{type:{in:...}}, sort, limit}`. It carries no Zone scope or mount restriction ([`registry.ts`](../../packages/composition/src/registry.ts#L493-L511)). `planReads` canonicalizes and deduplicates equivalent descriptors, but does not change their meaning or execute them ([`reads.ts`](../../packages/composition/src/reads.ts#L49-L72)).

Kernel presentation validates the descriptor, rejects an incoming Search `cursor`, then dispatches it as a `POST /v1/subjects:search` with the original authorization and session headers. It preserves the subresponse status/body and merges returned session tokens ([`presentation/reads.ts`](../../services/kernel/src/presentation/reads.ts#L178-L184), [`presentation/reads.ts`](../../services/kernel/src/presentation/reads.ts#L224-L233), [`presentation/reads.ts`](../../services/kernel/src/presentation/reads.ts#L312-L356)). The existing `readPage` dispatch has no Zone restriction argument. A Zone page that uses it unchanged runs the global TypeList query, contrary to [`zones.md`](../zones.md#shared-page-response-and-no-leak-reads).

### Search owns a real ordered hit stream, but the public method is already a filtered page

The native query tuples are:

| TypeList sort | Search tuple | Meaning |
| --- | --- | --- |
| `name` | `[name_sort, id]` | normalized name ascending, then unique ID ascending |
| `collections` | `[public_collection_count DESC (missing = 0), name_sort, id]` | existing public Collection-count ranking, then name and unique ID |

These exact tuples are built by [`search/query.ts`](../../services/kernel/src/search/query.ts#L108-L141). The same Search engine returns each raw hit's `sort` values; `service.ts` passes the last consumed tuple back as `search_after` and encodes it into its continuation ([`search/service.ts`](../../services/kernel/src/search/service.ts#L323-L357), [`search/service.ts`](../../services/kernel/src/search/service.ts#L365-L375)).

The public service is not a raw candidate API. It calls `checkHits` against current Semantic source evidence, consumes rejected candidates, refills for at most three engine rounds, and returns projected public subjects. It may use lower-bound totals when current evidence makes the index total unsafe. Its continuation is its own public-page continuation, not an exposure of all examined candidates or an owner membership probe ([`search/service.ts`](../../services/kernel/src/search/service.ts#L323-L365)). General Search totals therefore cannot be reported as Zone-restricted totals.

Canonical Search hits need a further qualification. The Search README's adopted canonical-index-coverage protocol says a certificate proves that stored original IDs in one physical index incarnation are canonical under a real structural identity basis; it does not itself prove current visibility, matching facts or complete ordinary recall. That protocol is currently marked unavailable: `coverage.ts` exports `index_not_ready` stubs, and formatting/native test coverage is not runtime proof ([`README.md`](../../services/kernel/src/search/README.md#canonical-index-coverage-producer), [`coverage.ts`](../../services/kernel/src/search/coverage.ts#L64-L115)). A future candidate port must require actual ready coverage for its exact physical incarnation, and bracket enumeration (including a zero-hit page) with the real native identity and per-home checks the Search contract specifies. A hit ID or apparently unique engine `_id` alone cannot establish canonical deduplication or truthful exhaustion. Do not normalize or deduplicate after paging; a changed structural basis requires restart/readiness under the Search contract.

Search's current index representation also matters to the continuation. Name-sort keys preserve a complete normalized key only up to 512 UTF-16 code units; missing and oversized keys sort as native null/missing-last, with ID as the tie-breaker. They are not truncated or hashed. The bounded-key design and remaining native outcome requirements are recorded in [`search/README.md`](../../services/kernel/src/search/README.md#confidential-cursor-and-bounded-name-sort) and [`document.ts`](../../services/kernel/src/search/document.ts#L3-L20). The collection sort is the indexed public collection count, not a count recomputed inside the Zone.

`createSearchScopeSource` is deliberately labeled an admission scaffold. `prepare` admits and compiles the current filter, then reports `semantic_not_ready`; `prefix` and `evaluate` also report unavailable. Its present prefix type is explicitly sorted by canonical subject ID (`afterSubject`), with no `name`/`collections` tuple input ([`scope-source.ts`](../../services/kernel/src/search/scope-source.ts#L37-L69), [`scope-source.ts`](../../services/kernel/src/search/scope-source.ts#L89-L165)). That is suitable as a future Zone source prefix contract, but is not a TypeList native-order contract.

The current expected native test files describe real engine hits, matched queries, quota, truthful exhaustion, pinned generation and current rejections; their existence is not evidence that the scaffold has become production capability ([`scope-prefix.test.ts`](../../services/kernel/test/search/scope-prefix.test.ts#L182-L245), [`scope-evaluate.test.ts`](../../services/kernel/test/search/scope-evaluate.test.ts), [`service-scope.test.ts`](../../services/kernel/test/search/service-scope.test.ts#L52-L55)).

## Why native candidates followed by a residual proof preserves order

Let Search emit candidates `c₁, c₂, …` in its native total order, and let `M(c)` be the current Zone membership proof. Applying a definitive Boolean membership predicate to this stream preserves the relative native order of the included rows; no second sort or ranking calculation is needed. This is an order-preserving filter, not a claim that the existing Search API performs it.

The bounded consumer must treat outcomes as follows:

| Current proof for candidate | Stream action |
| --- | --- |
| At least one current source proves `true`, and required current subject/source checks pass | Emit once in the candidate's original Search position; advance after its exact Search tuple. |
| Every source is definitively `false` or denied under current disclosure | Emit nothing; advance after its exact Search tuple. |
| No source proves `true`, and any source needed to decide the union remains `not_proven` | Stop before this candidate. Return only an earlier settled prefix, or retryable readiness if there is no such prefix. Retain enough owner progress to resume this same candidate. |

The three-valued rule is the one already specified for Zone unions: an independent current `true` settles `OR`; `NOT not_proven` stays unknown. A public Search hit cannot convert an unknown Zone membership result to false, and Search's drop/refill behavior cannot be assumed to keep refilling after a second, external residual predicate. Every raw candidate, owner key, duplicate, lookahead, reread and final recheck remains charged against the one shared 256-key ledger. Point, witness, row, byte and empty-seek work—including the specified 8,192 home metadata rows plus core observations per identity-basis read—are separately reserved and measured as [`zone-membership`](../zone-membership.md#local-budget-derivation-and-separate-native-bounds) requires.

Do not call `post_filter` with a made-up Zone predicate. OpenSearch's query and post-filter clauses are engine query DSL predicates over indexed fields; they do not perform current Access checks across Semantic and Commerce owner partitions. Materializing a Zone-membership field or permission claim in the Search index would also break the current-source and revocation rules.

## Counterexamples the design must survive

1. **A UUID page cannot be sorted into a global name page.** Suppose a UUID-ordered prefix contains IDs `…001`, `…002`, while a later UUID `…fef` has the alphabetically first name. Sorting the first UUID page yields the wrong top row. It cannot be repaired without continuing the native name stream. The same counterexample applies to collection-count ranking.
2. **An unknown earlier candidate blocks a later candidate.** If candidate A precedes B by Search's tuple, A is `not_proven`, and B is currently a Zone member, emitting B can put B before A if A later proves true. Stop before A and resume A; never consume it as false. A source independently proving A true may settle A even if another source remains unknown.
3. **The readable alias can be the 257th raw member.** For a canonical subject with 257 stored aliases and only the last original readable, checking the first 256 and declaring no membership loses a valid Zone result. The cursor must preserve both the Search candidate boundary and the resumable alias/leaf source progress for that same candidate. Choosing one representative or a candidate-ID index alone is insufficient.
4. **Tie and missing-name semantics are part of the cursor.** Equal normalized names are ordered by ID. Missing and oversized normalized keys remain native null and sort last; do not replace null with a made-up sentinel or resume by the display label. For `collections`, retain the exact count/name/ID tuple. A name or count update during live traversal can move a row across the cursor; this branch and the Zone contract promise no snapshot under concurrent mutation. Fixed-basis/quiescent acceptance can prove order and termination, but must not claim a stable snapshot through a live re-sort. Any stronger restart guarantee needs a Search freshness witness that observes the mutation; current index generation alone is not a per-document snapshot.
5. **Source revocation invalidates an old positive.** A prior page or cursor is not an Access grant. Recheck current Zone, source, original and terminal subject authority at final use; a revoked mount must not disclose through cached membership in a cursor or the Search document.
6. **An overlong cursor key cannot be shortened.** A 250-CJK normalized name is roughly 750 UTF-8 bytes, already above the Zone default 256-byte key limit. The actual Search write bound allows an `s`-prefixed normalized sort key up to about 1,537 UTF-8 bytes. Truncating or hashing either key changes native order and can collide; a cursor that cannot encode the complete tuple must fail the selected profile rather than issue a lossy continuation.

## Comparison with established indexed ordering

OpenSearch documents `search_after` as a forward continuation that takes the previous hit's sort values. It requires a unique final sort key to avoid skipped/repeated tied rows, and its documentation warns that ordinary `search_after` is live rather than snapshot-stable; PIT is the documented option for a frozen view. OpenSearch sorting also supports an explicit multi-field priority and missing-last behavior. Its `post_filter` remains an engine filter used to refine hits, while preserving aggregations; it is not a remote owner proof. See the official [pagination](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/), [sort](https://docs.opensearch.org/latest/search-plugins/searching-data/sort/), [filter](https://docs.opensearch.org/latest/search-plugins/filter-search/), and [PIT](https://docs.opensearch.org/latest/search-plugins/searching-data/point-in-time/) documentation.

The pinned OpenSearch 3.9.0 source parses string, numeric and null `search_after` values and checks that their arity equals the active sort-field count in `server/src/main/java/org/opensearch/search/searchafter/SearchAfterBuilder.java` ([pinned source](https://github.com/opensearch-project/OpenSearch/blob/4ee42a94e87f66fbf1e62a9871b1b87f91e02472/server/src/main/java/org/opensearch/search/searchafter/SearchAfterBuilder.java#L124-L148)). `SearchService.java` applies those exact values to the native `FieldDoc` after validating the request shape ([pinned source](https://github.com/opensearch-project/OpenSearch/blob/4ee42a94e87f66fbf1e62a9871b1b87f91e02472/server/src/main/java/org/opensearch/search/SearchService.java#L1734-L1743)). The inspected clone is `/home/edge/projects/rezics/rezics-next/.reference/search-canonical-coverage/opensearch`, commit `4ee42a94e87f66fbf1e62a9871b1b87f91e02472`, Apache-2.0 (`LICENSE.txt`, `NOTICE.txt`). The official documentation source project is Apache-2.0 and its reused clone/commit is recorded in `.reference/INDEX.md`.

PostgreSQL documents the complementary B-tree pattern: an index can deliver rows in `ORDER BY` order without a separate sort, and an order-compatible index can return the first `n` rows for `ORDER BY … LIMIT n`. It also warns that pagination needs a predictable unique order. This supports letting the owner of the index preserve its ordering and cursor rather than trying to reconstruct a globally correct page from a truncated, differently ordered source. The PostgreSQL planner may choose another path when cost favors it, so the index is not a promise of constant work. See [Indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html) and [`LIMIT` and `OFFSET`](https://www.postgresql.org/docs/18/queries-limit.html). The inspected PostgreSQL source clone is `/home/edge/projects/rezics/rezics-next/.reference/search-canonical-coverage/postgres`, commit `227de22095c8101905ce41e1ebf425239feed079`, PostgreSQL License (`COPYRIGHT`); relevant implementation areas include `src/backend/optimizer/path/indxpath.c` and `src/backend/access/nbtree/nbtree.c`.

**Shared pattern:** the indexed-order owner defines the order and tie semantics; OpenSearch explicitly resumes with its exact sort tuple, while PostgreSQL's B-tree can stream matching `ORDER BY` rows directly for `LIMIT` when the planner selects that path. Applying a definitive independent residual predicate preserves the stream's remaining relative order by ordinary sequence reasoning. The requirement to stop before an unknown external membership proof is an inference for this Zone contract, not a behavior promised by either product's documentation. Neither OpenSearch nor PostgreSQL supplies current cross-partition Access, alias repair or union semantics for REZICS.

PIT is not recommended here. OpenSearch documents that PIT retains a search context and should be kept only as long as needed; the Zone contract explicitly declines a cross-request snapshot. Introducing long-lived engine contexts would be an additional product/storage decision and is unnecessary for fixed-basis ordering tests.

## Minimum additive contract and owner handoff

This is a proposal for the manager to adopt before runtime work; none of these methods is a live export today.

1. **Search candidate port — `services/kernel/src/search/query.ts`, `scope-source.ts`, `service-scope.ts` and `coverage.ts`.** Add a service-bound, internal method for a validated TypeList body that uses the existing compiler and Search template, pins the current physical index/generation and admitted query/profile basis, and enumerates raw `SearchHit`s in the exact `name` or `collections` tuple. Its continuation input is the exact typed `SearchHit.sort` tuple, not `afterSubject`; its result reports examined candidates, last *covered and consumed* tuple, reserved lookahead, and truthful exhaustion. Require the actual canonical-index coverage reader and per-home identity checks around each enumeration, including zero hits. Reject partial shards/timeouts. Keep the existing canonical-ID scope prefix contract intact for `/subjects` union listing. Do not mint public DTOs, totals, fake hits or an alternate filter language.
2. **Current candidate evaluation — Search and Semantic.** The candidate port must use the same Search current-source checks and the shared Boolean evaluator, with real Semantic leaf evidence and current identity/alias-group ports. `true | false | not_proven` must remain exact. A `matched_queries` hint can prioritize current work but cannot replace evidence. Revalidate the emitted positive before returning it.
3. **Collection residual port — `services/kernel/src/library/collection-source.ts`.** Complete the one owner ABI already declared by its fixture: current authorized `prepare`, canonical covered prefix, and bounded `containsSubject` over the same curated/built-in/frozen authority. Preserve `true | false | not_proven`, original and terminal Access, source basis, resumable progress and final positive revalidation. Never use notes, private fact copies, public reverse listings or occurrence order as current Zone membership.
4. **Zone orchestration — proposed `services/kernel/src/zones/reads.ts`.** For each Search candidate, evaluate the union over the at-most-16 admitted scopes and 16 mounts with one pre-reserved shared 256-key ledger. Count candidates, duplicates, internal fact drivers, lookahead, rereads, alias work and final checks against that same ledger; reserve points, witnesses, rows, bytes and empty seeks separately. Stop before an essential unknown. One current true source may settle the group. Recheck current source/subject Access at disclosure. Never cache membership or Access as a cursor allow claim.
5. **Presentation dispatch — `services/kernel/src/presentation/reads.ts`.** Add the smallest internal hook needed for a Zone page's planned Search descriptors to go through the restricted orchestration, preserving existing incoming credentials, language selection, response status/body and session-token merge. The normal page read continues to call the normal Search route. Do not add a public query language or silently intercept all Search reads.

## Cursor capacity and required cross-owner decision

The current Zone membership cursor has eight position keys and already assigns all eight:

`[basisDigest, settledCanonicalId, groupId, sourceOrdinal, aliasAfter, sourceAfter, ownerBasisDigest, formatVersion]`.

`sourceAfter` for Search leaf progress is one 18-byte record (24 base64url characters). That record does not encode a native Search sort tuple, alias-group boundary, current source ordinal or owner basis by itself. Adding a ninth position key or nesting source tokens is outside the contract.

**Capacity conclusion:** the default list-cursor profile cannot carry every legal TypeList name sort key because it caps each string key at 256 UTF-8 bytes. The existing `search` profile has 2,560 bytes per key, 3,072 aggregate string bytes, 3,584 plaintext bytes and 4,864 token characters. A *single packed, typed raw tuple* containing a maximum 512-UTF-16-unit normalized name plus the unique ID and (for collection sort) count can fit those byte ceilings together with the bounded alias/leaf fields, if an operation-specific layout replaces the otherwise-used settled UUID slot and a worst-case serializer proves the plaintext/token bounds. The native tuple's `null` name must have an explicit typed encoding; the `ListCursorPosition.after` API itself accepts strings/numbers, not `null`.

That is only a capacity observation, not an adopted wire design. The current Zone position layout has no free slot, has no agreed packed-tuple codec, and is for canonical-UUID union order. Reusing `settledCanonicalId` for a TypeList tuple is a cross-owner protocol change; it is valid only if the native tuple's final ID is enough to anchor the TypeList candidate and the pending alias group independently retains the original under evaluation. If a TypeList tuple is instead represented as two or three raw `after` entries, those entries plus the eight-field Zone layout do not fit the existing eight-key limit. No implementation may truncate or hash the name key, add a ninth key, concatenate arbitrary JSON to evade the bound, or claim the old layout already proves both orders.

There is a second incompatibility: the current `search` profile is a real API option in `list-cursor.ts`, but Search's current `service.ts` still uses `tokens/cursor.ts`; the Search README says the encrypted-profile migration remains outstanding. The list-cursor Search profile is authenticated separately and makes even anonymous tokens time-limited, whereas Zone's current contract promises deterministic, timeless anonymous cursors. Selecting it for a Zone TypeList continuation would change behavior. Before production, Search, Zone and token owners must choose whether this exact operation gets an explicitly authenticated larger profile and what its anonymous lifetime is, or keep the current Zone profile and decline full name continuation under that profile. No decision in this report changes Zone defaults, token TTL, codec or profile selection.

Any chosen profile/layout needs independent native acceptance for: maximum normalized key bytes and serialization; 250-CJK names; null/missing/oversized keys; equal-name ID ties; collection-count/name/ID ties; preserving exact string/number/null values; simultaneous raw tuple plus group/alias/18-byte leaf progress; exact eight-key, per-key, aggregate, plaintext and token ceilings; actor/Zone/body/basis binding; and cross-profile decode rejection. A cursor-size failure must be explicit, never a lossy fallback.

## Independent native acceptance before runtime

Add a Zone TypeList outcome test using real Search, Semantic, Commerce and Access state, without weakening the existing owner tests. It should assert:

- Native Search candidates with deliberately different UUID, name and Collection-count orders produce the full expected `name`/`collections` sequence across bounded windows; a UUID-page-then-sort implementation fails the fixture.
- The candidate continuation retains Search's exact multi-key tuple, `matched`/security revision evidence and stable ID tie-breaker. It does not emit rows outside the current Zone union, does not reorder accepted rows, and exposes no Zone-restricted total.
- Before treating candidate IDs or exhaustion as canonical, real Search coverage for the exact physical incarnation is ready and identity/per-home observations bracket the enumeration, including empty results; structural changes restart or return readiness. No post-page ID normalization establishes coverage.
- Missing/null/overlong names stay last and resume correctly across the null boundary; actual long Unicode keys round-trip without truncation. Equal names and equal Collection counts use the existing ID tie-breaker.
- A definitive rejection advances; an unknown earlier candidate prevents later output and resumes the same candidate; an independent current true source settles an otherwise unknown union candidate. A no-progress pending candidate returns readiness, not a repeated successful empty cursor.
- Zone membership is `current subject Access AND distinct union(saved scopes, readable Collection members)`; every emitted candidate satisfies both the current TypeList Search evaluation and current Zone membership. A related reference is not implicitly a member.
- A native 257-alias / only-last-readable case progresses through the same pending candidate and finds the positive with bounded work. Merge, unmerge and repoint invalidate unsafe continuation. Current source revocation or subject denial before final use suppresses the row.
- The one 256 raw-key reservation includes all Search candidates, duplicates, lookahead, Search/Semantic fact drivers, Commerce source drivers, alias windows, rereads and final rechecks. Separate native point/witness/row/byte/empty-seek capture includes identity basis sweeps and core observations; no owner gets a free 256 refill.
- Partial shard, timeout, unavailable leaf, missing identity basis and incomplete Collection prefix cannot become false membership or exhaustion. A fixed, finite, quiescent ready basis progresses through empty filtered windows and terminates. Live name/count changes are not asserted to behave as a snapshot; if an implementation promises restart on them, test its real freshness witness.
- Cursor profile tests prove the selected authenticated profile and bounds for the full tuple plus simultaneous pending owner progress. Actor, Zone, request shape and stable body binding are authenticated; dynamic source/index/identity bases are encrypted and compared before resume. Tokens contain no private facts, source IDs, totals or allow results.

Existing files `test/search/query.test.ts`, `collections-sort.test.ts`, `bounded-sort-keys.test.ts`, `bounded-name-cursor-outcomes.test.ts`, `scope-prefix.test.ts`, `scope-evaluate.test.ts`, `semantic/scope-leaf-evidence.test.ts`, `semantic/scope-leaf-identity-composition.test.ts`, and `library/canonical-source-store.test.ts` cover pieces of these owner contracts. They do not by themselves prove a Zone TypeList restriction. In this branch the Search scope, Semantic leaf/identity and Commerce source dependencies identified above are still scaffold or absent; treat the native tests as acceptance requirements, not passing production evidence.

## Decision for the manager

Adopt the native ordered-candidate plus bounded residual-proof pattern for TypeList. Preserve `name` and `collections` tuples exactly and keep Zone `/subjects` listing in canonical UUID order. Route only Zone-planned Search descriptors through a new internal Search candidate port and Zone's current-union evaluator. Before runtime, agree the operation-specific cursor layout/profile and its anonymous lifetime with Search and token owners; the existing default profile is too small for legal native name keys, while the larger Search profile changes the current anonymous lifetime. Require the independent native acceptance above before claiming TypeList restriction or finite Zone traversal is ready.

This is a proposal based on current code and cited public behavior, not an implemented adapter, measured production bound, or change to an owning contract.
