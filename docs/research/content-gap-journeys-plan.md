# Content audit journeys

The three audits identify eight Content API gap groups, with repeated rows on different pages. Their findings
must be read against the retained implementation and existing assignments. The premise that workers are idle is
false: watch delivery, classification recovery and publication of retained Content journeys already have running
or held assignments. Integrated assignments also cover substantial parts of the audits. Integration is a coverage
assignment, not a claim that native, rendered or growth acceptance passed.

Decision: retain existing journey owners; add only Subject reactions on Home and Home/Subject conversation-activity
assembly, which the existing reaction and activity producers explicitly leave outside their delivered scope.

The two continuations estimate 2,000–3,000 changed implementation lines each. That is the size of the complete
journey, not the length of its instructions or a padding requirement. Both include native composition, its existing
interface consumer, operation costs and growth acceptance. No product code is changed by this plan.

## Ready continuations and overlap

1. [Home Subject reactions](../../.temp/continuation/01-home-subject-reactions.md): 2,400 estimated changed lines,
   implementation. Native Subject counts/viewer state/action advice and the current Home reaction receiver only.
2. [Home and Subject conversation activity](../../.temp/continuation/02-home-subject-conversation-activity.md):
   2,500 estimated changed lines, implementation. Existing activity-source composition and current conversation cards.

Both use `goal: content`, `manager: content`, default acceptance placement and no model/effort override. Neither
has a code dependency on the other. They share feed contract/assembly files and the existing complete-input
publisher; that overlap is not an `after` dependency. Workers preserve each other's fields and use the supported
publication path. Watch, diary, Inbox, classification, discovery, source figures, Board and thread tasks retain their
existing outcomes and original growth obligations.

The current native Home reaction task restricts `FeedReactionTarget` to thread/post, and `targetFor` returns no
target for non-Content keys. The new Subject branch therefore does not repeat that delivered scope. Similarly,
`createConversationActivityBatch` is an installed producer, while its owner explicitly requires page consumers to
select, hydrate, confirm and reobserve disclosure. Continuation 02 implements those missing Home/Subject consumers,
not publication, invalidation or repair of the underlying aggregate.

## Sources and delivery boundary

Planning used the three reports, `bun tools/goal/src/cli.ts status`, `git log dev`, the named existing journey
contracts, the Content reaction/watch/Inbox/activity owner sections, the Rating counted-reader contract,
`docs/feeds.md` reaction/context contracts and the Feed action/producer handoff. Targeted source inspection covered
the feed contract and reaction projector, Subject-thread composition/consumer declarations, and native Subject
reaction routes/readers. The reference `INDEX.md` was consulted; these continuations reuse existing REZICS semantics
and introduce no external provider design or copied source.

The retained source already contains reaction receiving (`219a39a7e2`), Home context rendering (`512c7ab4e7`), Inbox
disclosure/seen state (`a774c634fd`, `3f4f2ce044`), current Review census (`14fa4d631e`), native Space witnesses
(`267525a182`) and the counted-reader protocol (`d258290882`). These `dev` changes support keeping existing
assignments instead of recreating their work. Their remaining native/rendered/growth acceptance is still theirs.

Acceptance is deferred to integration under the current launch policy. This documentation-only change creates no
test files or changed code workspace requiring a typecheck. The continuation workers own their missing outcome
tests, keep test lines below product lines, update any superseded non-frozen assertions and add only the named
page states. The mapping makes no green claim for a pending or failed product acceptance.
