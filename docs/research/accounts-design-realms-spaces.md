# Realms and Spaces: design and delivery status

Desk research, 31 October 2026 (Asia/Shanghai), against the worker's integrated checkout. This report is evidence for the owners to adopt; it changes no product contract. **Implemented** below means present in integrated source. **Proposed** means a recommendation or an open producer's intended delivery. **Outcome-proven** requires the owning delivery's recorded outcome evidence; tracing a route or reading a test here does not supply that evidence. No checks or native verification were run.

## Boundary and existing evidence

[Scope](../scope.md) places **Realms and Spaces In**, owned by **Content, with Accounts owning membership and Access**. A Space is a stable routed identity and address; its one carried Realm is a distinct resource on the same route. A Realm owns community metadata and membership history, not Semantic definitions. Zones, arbitrary nested communities, federation and a new invitation service are not additions authorized by this research.

The normative owners are [Accounts](../accounts.md), [Access](../../services/kernel/src/access/README.md), [Community](../../services/kernel/src/community/README.md), [Content](../../services/kernel/src/content/README.md), [Semantic](../../services/kernel/src/semantic/README.md) and [deletion](../deletion.md). There is no `docs/realms.md` or `docs/spaces.md` in this checkout; the module documents carry their converted contracts. General record deletion allows restoration for 30 days; final account deletion does not. Neither rule establishes a callable Realm deletion command or its resource-specific authority.

## Actual UI ↔ API ↔ storage journeys

The common Web path is the locale-prefixed route → TanStack server function → `@rezics/client` → kernel HTTP. Sources are [Realm/Space loading](../../apps/web/src/community/space.ts), [BFF actions](../../apps/web/src/community/space-actions.ts), [membership actions](../../apps/web/src/community/realm-membership-actions.ts), [session request](../../apps/web/src/session/request.ts) and [session storage](../../apps/web/src/session/store.ts). Server functions have framework-generated transport URLs; there is no hand-written public BFF membership endpoint to name. An opaque session cookie resolves through `SESSIONS`; unsafe cookie requests check Origin/CSRF. Credential refresh uses Auth's OIDC token endpoint; explicit bearer requests carry that bearer. Session tokens do not confer organization identity from request JSON.

At the kernel, the [HTTP composition](../../services/kernel/src/http/kernel.ts) supplies authentication, the mounted action catalogue, admission/rate limits and Access. Every command has one trusted kernel **T**, distinct from its wall-clock deadline. Access evaluates actor grants ∩ current client-consented scopes ∩ principal grants when delegated, with current membership/denials and the anonymous floor. Parent checks use released preparation before target checkout; writes stay within one partition per transaction. [Command execution](../../services/kernel/src/command/command.ts) couples effects with `core.receipt` and `core.outbox` ([schema](../../services/kernel/db/schema.sql)); receipt replay follows fresh authorization. A database row, inverse candidate or cached UI state is never substituted for that formula.

The actual [role catalogue](../../services/kernel/src/access/resource-roles.json) gives Realm owners read/manage/ban/publish/board-create/grant/takedown, moderators read/ban/publish/board-create/takedown, and members read/participate. Standing active-account authority supports participation/join where public eligibility permits it; public participation therefore need not imply membership. Organization-role grant subjects require current membership in that organization; they do not make the organization a token subject. The [native inverse admission](../../services/kernel/src/access/membership-inverse.ts) currently requires an active, unfenced actor with no operator and complete inverse coverage: neither an organization nor an automated actor is admitted as a Realm member through that path. Read/write problems also include unavailable/deadline 503; writes expose rate-limited 429 and idempotency-conflict 422. These must not become a positive membership result.

## Gaps and decisions for adoption

**Usability and operational convergence.** The [membership component](../../apps/web/src/community/realm-membership.tsx) maps an accepted write to local `pending`; its [query](../../apps/web/src/community/realm-membership-queries.ts) has no mutation-driven invalidation/polling or terminal work-result handling. Refocus/reload can refresh it, but neither is a guaranteed completion journey. The BFF drops the returned workflow ID and collapses most failures into “refused”; cap exhaustion and lost durable authority need distinguishable outcomes before claiming a complete admission UX. Existing member/participation reads can establish settled state without inventing a workflow API. A signed-out `viewer.state === none` rendering branch also has an inert Join button; preserve the normal sign-in link in that branch. Creation, edit/address management, direct add, ban history and role administration lack controls on the current pages.

**Privacy and authority.** Protected-ban veto is implemented in the current resource read path; do not undo it while removing a membership. The private own-Realm query's name disclosure during pending ban, viewer-derived `realmId` under an unchanged Space ETag, authenticated-versus-anonymous hydration, and non-ban participation denial labelled “banned” need explicit UI/cache/disclosure acceptance. A ban can affect current member-derived read without erasing membership history immediately. Follows, inverse candidates, public account preferences and search projections never supply authority. The closed `globalReach` set remains `moderation:takedown`, `moderation:read_reports`, `post:erase`, `media:erase`, `access:grant`; there is no widening to Realm management, banning or deletion.

**Restore and custody.** General record restore and final account erasure are different operations. Ban erasure already has target/actor locators and a documented time-limited reason exception; it does not establish member-history erasure or a complete owner ACK. Open native producers must close actual membership/archived revision/notice/rating and shared receipt/outbox/DBOS copies before claiming completion. Backups remain a separately documented operational obligation. A Realm delete plan must state whether restoring content can restore membership/grants/addresses and how to prevent reviving subsequently revoked authority; no such behavior is inferred here.

Root and the affected owners need to adopt these **product decisions** before the corresponding new interfaces are commissioned:

- Accounts + Content: whether existing direct manager-add remains the admission model, or invitations/request-to-join are needed. If needed, define recipient consent, discoverability, expiry, reject/cancel, replays and ban interactions first; none is an existing callable invitation contract.
- Accounts + Content: Realm succession and orphan handling, including organization-held grants, direct-role renunciation, creator deletion and genuine remaining holders. Recommend multiple explicit holders and a last-holder invariant, without selecting a primary-owner model or adding undeclared Global reach. Resolve whether direct ownership belongs in private/public “my Realms” discovery.
- Content + Accounts + Semantic: the Realm/Space delete/restore authority and obligations under existing deletion policy. Keep Content's boards/publications and Semantic's Context/definitions separate; do not erase another owner's resource by adjacency. Include pending membership work, historical roles/ban evidence, address reservations, retained public contributions, projections and exact shared-copy custody.
- Accounts + Web: a non-disclosing way to distinguish banned, insufficient client scope, pending, failed and settled admission. Recommend using a generic denied participation result with the existing responses until that distinction is adopted, without asserting a ban or inventing a workflow-status API.
