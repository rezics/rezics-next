## Concrete cut candidate and its limits

Call the following a **proposed durable local reservation protocol**, not an exported method.
It requires new owner producers. It cannot be assembled by calling current `current()` methods sequentially.

1. Seal complete capture and target expectations under the immutable operation. Retain exact full participant coverage, including homes with only negative, foreign, excluded or order dependencies. Reuse native indexed coverage producers; an unknown participant set refuses confirmation.
2. On each participant's home, in its admitted native transaction, take dependency-local writer serialization locks, validate the sealed baseline and sticky history, native target expectations, identity/custody and current lifecycle. Then commit an operation/capture/attempt-specific durable reservation and receipt. Release the connection before contacting another home.
3. Every relevant native writer, including one begun before enrollment, must encounter those same serialization points at its **final commit boundary**. It either committed before reservation and made validation stale, or cannot commit the relevant change while the reservation can still authorize a root cut. Rollback publishes no change; asynchronous invalidation after commit is too late.
4. Commerce commits its actual `preview-complete -> confirmed` transition and exact cut receipt only after all complete reservations are durably established and still incapable of unilateral withdrawal. Cancellation/expiry competes on that same native root decision. No target dispatch precedes known committed confirmation.
5. Release each reservation only against the exact durably resolved root decision. A confirmed release marks subsequent native changes as post-cut; an abort releases without dispatch. Cut release releases selection serialization, not native source custody or current authorization obligations.

The lock/index domain must be precise enough for unrelated work to proceed and writer lookup bounded by affected dependencies.
An account-wide/global mutex, a scan of every live preview, or holding all home connections would violate the contract.
Both reservation and writer must conflict on the same stable native domain row or a proved unique-key creation handshake; a snapshot SELECT of an arm table is insufficient.
In a writer whose SERIALIZABLE/RR snapshot predates enrollment, the final shared-row write/lock must force current serialization or a native retry, never accept that old snapshot's apparent absence of an arm.
Predicate-range/dependency registration, phantom/new-key handling, index-maintenance costs and committed enrollment of already-running writers are missing native producer work.
Per-home SERIALIZABLE reads without writer reservations do not satisfy step 3.

**Race closure, conditional on those invariants:** after Q validates/arms, P changes Q's relevant dependency before root confirmation.
If P committed first, Q's sticky baseline/history check rejects the reservation; if Q reserved first, P's final commit guard refuses/waits without committing that change.
Thus root confirmation cannot consume an unchanged Q receipt while that pre-cut change has committed.
The same proof applies when P changes a captured entry revision rather than membership.
In contrast, `check Q; commit P; CAS root` succeeds under independent validations, even if root is SERIALIZABLE: the root transaction has no native conflict edge to P.
Adding another digest read or per-target CAS preserves that gap; it merely detects some drift after forbidden dispatch.

The reservation protocol has three specific unresolved conflicts, not hidden implementation details:

- **Authority writes:** if an armed dependency can stall immediate privacy/account/consent/source revocation, independent live authority is violated. A local authority stop still blocks effects, but does not make an incorrectly confirmed pre-cut selection valid. The owner must supply an atomic revocation-vs-root ordering/abort path that does not defer effective revocation, or reject this reservation design for that participant.
- **Lost root decision:** if a participant expires/releases an arm while the root may commit an old acknowledgement, the original race returns. Retaining an arm until a root decision is known can instead outlive finite cleanup/retention and block writers during an outage. A wall-clock timeout alone cannot choose safely. No cross-home clock/failure-detector guarantee or bounded resolution primitive is currently supplied.
- **Admission and fanout:** dependency matching, participant enrollment and invalidation may exceed the original finite statement/point/byte allowance or retained-byte capacity. No active-preview count/population/version cap is authorized to hide that work. Exact indexes/bodies and finite byte admission must establish the bound before this candidate is available.

An alternative is a native **validation/commit ordering producer** jointly owned by Commerce and each authoritative home.
Minimum semantics: every relevant writer's authoritative commit is atomically ordered either before the exact root cut (invalidating it, including ABA) or after it; root confirmation cannot commit from withdrawn/stale evidence; authority loss takes effect immediately; unknown decisions have exact durable recovery and bounded custody.
It must cover OLD/NEW negative/phantom dependencies and captured target expectations, enroll old writers, and expose charged actual receipts on the supported clients/homes.
It cannot be an asynchronous cancel message, ordinary root CAS, selected-ID digest, or a new permission token.
The missing deliverable is the actual cross-owner placement/atomicity/recovery body, not a function signature named `seal` or `confirm`.
A bounded same-home transaction could implement a local subset, but cannot delete this cross-home requirement.

## End-to-end ownership and lifecycle

Admission retains exact intentions, filter/release/source/client provenance, durable initiator and absolute proposed 24h execution/48h result deadlines **from admission**, plus the shared proof expiry.
Replays restore the original native owner through `CommandAuthorization.prepare`; no cached actor or bearer is a durable permission.
Source/identity provenance includes actual owner/receiving epochs, incarnation/generation, native transaction/position/effect key, and publication generation where applicable.
Admission, owner restoration, dependencies and unsupported sources must fail before pretending to have complete coverage.

Capture proceeds in finite admitted raw steps; record result/negative coverage, repair frontiers and native source/identity custody before acknowledging progress.
For each consumer page, atomically compare exact ownership/page identity, insert immutable manifest rows, CAS its checkpoint and acknowledge the native continuation on the supported same client.
No durable native continuation/ACK bridge is present merely because prefixes can be paged.
Complete preview requires both complete subject capture and complete real-occurrence expansion for the chosen action, plus captured target expectations.
Empty preview still needs complete coverage/currentness and a cut; zero target rows are not proof of emptiness.

Confirmation participates in the chosen cross-home ordering body; only a known committed cut permits dispatch.
Afterward use ordinary native authorization before receipt lookup, original/terminal/foreign/source checks and exact immutable expectations.
Fresh profile validation follows authorized receipt replay, so a profile change cannot hide an already committed original receipt.
Each applied target's native mutation/events/receipt and `bulk_effect` belong in its one native transaction.
Core `noEffect` forbids domain writes/events/callbacks, so it cannot insert `bulk_effect`; use the authorized receipt-only path for an unchanged target.
Persist unique target transitions/counters; no duplicate progress credit from retries.
Unknown effects enter reconciliation using the original receipt key/input, never a replacement request or current-state guess.

[command.ts](../../services/kernel/src/command/command.ts) is an ordinary native command executor, not a cross-home coordinator.
[operational.ts](../../services/kernel/src/command/operational.ts) exposes live branded resources and exact account fences;
[work/client.ts](../../services/kernel/src/work/client.ts) enqueues on an actual caller transaction.
The ordinary Command-to-Work bridge, source continuation/dispatch ACK and late-effect/erasure copy locators still need native producers.
[bulk-outcome-page.ts](../../services/kernel/src/library/bulk-outcome-page.ts) is a bounded authorized result reader, not complete operation lifecycle.

Cancellation/expiry/revocation closes dispatch and drains unknown receipts without reopening selection or extending any deadline.
Owner restoration retakes native account/partition/episode authority; suspension/restoration never renews old proof or membership.
At erasure T, refuse reads/touches/new work immediately; drain indexed result, dependency, arm, manifest/effect and cleanup children, then their headers.
Record actual DBOS input/output/step/message copy locators atomically at creation and hand them to the existing shared-history minimizer.
Target/effect account indexes alone do not cover late writes or actual Work copies; an enqueue is not an erasure ACK.
Release/retirement must preserve still-live stopped custody and only retire an actually terminal native episode; do not purge someone else's destination or recreate a missing hold.
Shared proof expiry, execution expiry and result retention are distinct; none grants another Source frame or receipt-disclosure permission.

### Original allowance ledger, including the missing bodies

For each actual admitted invocation let `A0` be its original eight-axis remaining allowance and `D0` its original deadline.
For steps j in that invocation, retain **`Aj+1 = Aj - Vj` componentwise**, including failed/repeated/rollback/unknown attempts and child/control work; dispatch only a fully bounded body fitting Aj and D0.
Capture rows, dependency registration/journal/repair, target expectation reads, result/manifest inserts, page equality/checkpoint/ACK, cut preparation/root/release/receipt and cleanup all consume that same remainder when composed in the call.
