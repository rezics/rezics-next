# Performance cost audit

This is a static audit of the development tree at `cb7f4b3e99`. The completion rule does **not** hold: some implemented paths have no Cost table row, some citations measure another operation, and some bounds or descriptions are stale. No growth check was run for this audit.

## Scope and reading rules

The inventory starts at `services/kernel/src/http/{app,kernel}.ts`, every mounted route factory, `services/auth/src/service.ts` and its website/account-operation transports, then follows command bodies, `work/modules.ts`, registered workflows, scheduled ticks, event relays/projections, and Search source/query/indexing calls. It includes error/replay paths that perform I/O. The accompanying SQL and database schemas identify actual keys, range limits, changed rows and fanout; README headings did not determine inclusion. Importer uses SQLite and calls the audited Kernel over HTTP; its local storage is outside the PostgreSQL/search definition.

`K/` means `services/kernel/src/`, `KT/` means `services/kernel/test/`, `A/` means `services/auth/src/`, and `AT/` means `services/auth/test/`. Module READMEs are `K/<module>/README.md`; Auth uses `services/auth/README.md`. The shared Kernel core protocols and the two explicitly named Access integration costs use the existing `services/kernel/README.md` Cost table, identified as **Kernel service** in the table. That shared documentation is credited rather than requiring duplicate derivations in every caller's README. File/function notation includes methods returned by factories and private functions reached from their public entry points. Module and owner are repeated deliberately: the owner must close the gap even when its caller belongs to another module.

A row is an operation family: aliases with the same SQL path, or named phases of the same command/page, share a row. Shared command, authorization, partition, relay and durable-work costs are inventoried once and compose with each caller. A primitive's growth check is not credited as a complete wrapper check when the wrapper adds I/O. A cited test title is literal, including `${...}` for generated titles; a labelled `checkGrowth name` identifies a generated enclosing test whose name is not a string literal in the source. A README citation to the actual checkGrowth name is valid even when the enclosing test has a different title.

Concrete internal per-command/page/batch native ports are included even when their default HTTP/workflow composition is pending (notably shelf readers, metadata, preparation and coverage storage). This conservatively audits merged executable I/O without claiming those product features are live. Pure validators/codecs, interfaces and fail-closed stubs with no database/search I/O are excluded. `scope-source.prepare` is included because its default release lookup does perform SQL before failing closed.

Startup/schema migration, governance bootstrap, initial definition/profile bootstrap, one-time membership-inverse backfill and whole-index administrative rebuild/reconcile are excluded. The recurring generation-discovery/bootstrap recovery and retirement inside the runner are included. `profile-migration-page.pinLegacyFactsPage` is included as a resumable native batch port, not as its one-time deployment orchestrator. Future canonical Library source, shelf-maintenance orchestration, Semantic identity/leaf/publication/repair contracts and Search coverage coordinator/positive scope execution are excluded where production code is absent or returns not-ready without I/O. Tests implementing those contracts inside fixtures do not make a native production hot path exist. `/v1/subject-pages` itself currently throws before SQL; its implemented candidate-page helper is inventoried separately.

**Cost row:** `yes` requires an actual `| Operation | ... |` Cost table entry; `no` includes prose-only Cost sections; `stale` means an existing entry has obsolete scope, derivation or citation. Most kernel module Cost sections are prose, so a working check alone does not satisfy the literal table requirement. The table names the existing entry where one exists.

**Check matches row:** `Y` = current table entry and measured operation/declared bound agree; `P` = native operation/bound evidence exists, but there is no table row to match; `X` = partial, neighbouring, weaker-bound or stale-citation evidence, explained in the last column; `N` = no qualifying `checkGrowth` for the operation. Additional assertions outside the harness's `bounds` object count when they establish the derived cap. A file merely called `growth-*`, raw statement comparisons, `assertGrowth`, or fake-source request counts are not themselves a `checkGrowth` operation. `none` can therefore coexist with useful nonqualifying tests.

At a fixed admitted request/page/change neighbourhood, the usual bound is constant rows and statements with logarithmic indexed blocks as unrelated population/history grows. Input-linear work, actual affected fanout and fixed-home sweeps are identified separately. These are static coverage findings, not measured performance results or promises of constant engine postings/latency.
