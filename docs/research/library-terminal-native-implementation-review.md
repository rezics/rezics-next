# Library terminal cleanup: native implementation review

Research date: 28 October 2026. This is a read-only implementation review, not a new policy authority or an erasure guarantee.

## Finding

The adopted first-scope policy is implementable with the existing owner commands, event relay and DBOS runtime, but the current Library runtime does not implement terminal account cleanup. The Access deletion barrier is real and immediately blocks account commands; Library has no consumer for its tombstone event, no terminal checkpoint/dispatcher, and no complete indexed child-page graph. Existing row schemas and ordinary due indexes are useful locators, not proof of cleanup. Do not claim that all Library-linked private payload is physically erased until the Library namespaces and the shared evidence boundaries below have exact cleanup evidence.

This inspection is against worktree `HEAD` `cb7f4b3e9934db49cb817f6f7384ea5ab936cc1f`, on the requested worker branch. The local `main` ref is `f84a5db6327f748261596d841ccc8c0fdd81310b` and lacks later integrated Library migrations; it is not the implementation baseline here. The bounded account-fact page at `c7c49de1fc481aab28c7ba58b65518768443e78d` and retained-entry due DAO at `d80ebdbb7290ddb746f181475c888acaeeca071d` are readable branch evidence, not ancestors of this `HEAD`. Neither supplies a registered terminal worker or whole-graph proof.

## Policy used for this review

The current first-scope contract supersedes older hold language in general deletion material and research reports:

- Individual record undo lasts exactly 720 hours. At the exact deadline, undo is closed; eligible private payload is automatically purged through bounded durable work.
- Account deletion becomes terminal at fresh authentication plus typed confirmation time `T`. Private cleanup starts immediately through bounded work. There is no account restore, generation, 30-day account window, platform permission or consumer wait.
- At `T`, retain only active public contributions. For a dynamic public Collection, retain its last complete published generation A, never pending/private B or a query of private facts at `T`. Retain detached, explicitly published log snapshots. De-identify retained public material. Erase private, unlisted and already-deleted graphs.
- Legal hold support and a custody engine are deferred from first scope. Exact minimization of actual shared private payload remains required. Payment business state is outside this Library review.

The account becomes terminal at `T` without waiting for any consumer. Cleanup and shared-payload minimization start asynchronously at once; a replay-safety cutoff may govern removal of a particular shared artifact, but it cannot delay account deletion or be presented as an account restore window.

The relevant adopted evidence is [Library account retention](library-account-retention.md), [entry undo research](library-entry-undo-independent-current.md), and its [deep report](library-entry-undo-independent-deep.md). The frozen [deletion outcome spec](../../services/kernel/specs/library-deletion-outcomes.test.ts) still contains an earlier legal-hold outcome. This report follows the newer first-scope decision; the spec owner must reconcile that stale assertion before using it as first-scope product acceptance. No test or frozen file was changed here.

## Access barrier and current read behavior

`access/lifecycle-fence.sql` atomically sets `state='deleted'`, raises `authn_fenced` and the authentication floor, scrubs account profile fields, and records a lifecycle-fence receipt. `access/lifecycle.ts` emits `com.rezics.access.account-tombstoned.v1`. `library/command-support.ts:createLibraryCommandRunner().ownAccount` checks the authoritative Access row and denies non-active or fenced accounts before the command receipt; `trustedAccount` also requires an active account and cannot run terminal cleanup after `T`.

`library/work-module.ts` registers only `registerLibraryWork`. `library/work.ts` registers Collection member/listing synchronization effects and the `library.collectionListing` workflow. It does not consume `account-tombstoned.v1`. Thus the real Access barrier is not a Library producer/cleanup barrier. Existing account commands are denied after `T`, but the Library has no page worker that persists `T`, freezes public publication state, deletes private rows, or proves completion.

Current Collection point-read authorization checks the row’s active state and visibility. The Library read guard has no deleted-curator condition; an active unlisted Collection can still enter the known-ID path. Access hides the owner’s profile collection listing, but that does not prove all direct unlisted reads or stale derived projections are hidden at `T`. Public Collection retention has no terminal snapshot/cutover. Treat this as an at-`T` disclosure gap until a terminal fence is checked by those reads or a durable cleanup transaction removes the private graph. Do not expose private facts to compute what public data survives.

## Native command, crash and replay evidence

`command/command.ts:runCommand` runs a serializable owner command with authorization before keyed receipt read and atomically commits body effects, receipt, outbox and fence. That is strong per-command replay evidence. It does not yet wrap a Library terminal page sequence. `library/work.ts` caps its Collection listing sync page at 100 and uses deterministic DBOS workflow IDs for event-triggered listing; no such workflow handles account tombstones. `profile-migration-page.ts:pinLegacyFactsPage` validates a 1–100 limit and uses the account share lock, but only pins entry/session/copy profiles.

At `c7c49de`, `purgeAccountFactsPage` is useful branch-only evidence: it uses the actual Access `readAccount` row and requires deleted plus fenced state, a 5-second command deadline, raw page size at most 100 and command receipt. It deletes only live entry, copy and follow rows. It has no committed graph-phase checkpoint/dispatcher and omits archives, Collections, progress, labels, staged state, public retention and shared payload. Its branch test is not evidence that the code is integrated. The separate `d80ebdb` due DAO keysets by `(restore_until,route,account_id,deletion_id)` and checks the expected deadline, but has no command, Access guard, cursor receipt or scheduled worker.

The in-flight entry DELETE/restore/due command and workflow chain is a genuine ordinary-record lifecycle, separate from account terminal cleanup. Even when complete, its scope is retained entry episodes and their 720-hour expiry, not the rest of the Library graph.

The terminal page must use an explicit authorization against the actual deleted-and-fenced Access row (or its owned terminal proof) inside the page transaction. Do not impersonate a deleted account with `trustedAccount`; that API correctly rejects it. Page deletion, exact receipt and phase cursor must commit atomically. A lost enqueue after commit must resume from that cursor; a crash before commit must repeat the same raw keys safely. Parent completion is valid only after every child namespace and shared-evidence phase is exhausted. Account IDs and deletion generations must never be restored or reused.

## Concrete failure cases to prevent

1. An old due task keyed by account/subject can delete a replacement entry after clear, refill and another clear. The current live delete has no archive writer; the new archive must use immutable `deletion_id`, expected restore deadline and exact row CAS. Terminal account cleanup must also remove every retained archive immediately.
2. A terminal page commits deletion and receipt, then its enqueue is lost. Without a durable per-account phase/cursor, an event retry can repeat earlier pages or falsely report completion. Keep the exact page receipt and cursor atomic and resume through the registered workflow.
3. A stale listing/canonical rebuild publishes after private Collection erasure. Derived rows are not source authority; fence writers before removing them and prevent a stale generation from reinstalling them. Retained dynamic public data comes only from the last complete A pointer, never B or a query over private entries.
4. Deleting a Collection parent first either violates member/canonical foreign keys or tempts an unbounded cascade; deleting only the parent without manually clearing subject-side pairs leaves a readable stale graph.
5. A scan of receipts by deleted account principal misses another editor or subject-side principal. Searching JSON for an account/subject string is neither an exact locator nor a bounded cleanup proof.
6. `DBOS` age-based history GC can leave recent private inputs after `T`, while deleting an unfinished workflow early can destroy delivery/replay evidence. Neither age threshold nor workflow status alone proves both safe replay and payload erasure.

## Cross-source patterns and recommendation

No new upstream research or reference clone was needed; the adopted reports already contain primary-source comparisons. The open-source trash implementations share a separation between the active object and a recoverable deletion record with an explicit expiry. PostgreSQL’s unique-key, partial-index and row-comparison rules support the additional REZICS recommendation: restore by exact locator plus live-slot precondition, and purge through an indexed deadline selector with a final in-transaction CAS. These patterns support the repository’s native route/command design; none of the upstream implementation should be copied.
