# Native Zone Subject list: transport and preparation

## Recommendation and evidence boundary

Reuse the native membership/union producers for a UUID-ordered GET, with default-profile locators into bounded server preparation and the existing
safe Subject summary shape. Do not forward POST tokens or extract a partial common document.
Research choice: recommend explicit retained preparation for GET, subject to transport adoption; this report adopts no product contract and changes no owner document or exposure gate.
Both the supplied base and the inspected current `dev:services/kernel/src/zones/http.ts` mount metadata, configuration, owned lists and POST
readPage, but no Subject GET. This finding is code inspection, not an executed native/browser pass.
Authority remains [Zones](../zones.md#routes-and-native-declarations), [membership](../zone-membership.md), and [filtered
lists](../filtered-lists.md). Collection metadata GET is a separate mounted-source outcome, outside this design.
Confidence is high in the call graph and codec constraints; finite sparse completion and compliant complete-observation safety require owner implementation and measured native evidence below.

## Current native call graph

Paths below are relative to `services/kernel/src/` unless otherwise qualified; named symbols are existing exports, not proposed interfaces.

1. `http/app.ts:createApp` derives the request deadline, authenticates an actual bearer with `actorOf` through reserved admission, and derives account/anonymous session scope. Invalid credentials propagate; they never become anonymous.
2. `zones/http.ts:zoneRoutes` uses `admission.run('normal', job, ...)`, the injected real Search service, Access, clock, routing key and Accounts key ring. POST records the selected Zone component and every returned source component.
3. `zones/resource-reads.ts:createZoneReads().page(actor,id,null,deadline)` supplies an internal descriptor from the authorized head and authoritative time: withholding-filtered `scopes`, `mounts`, immutable `releaseDigest`, and `revision: lifecycleRevision` commitment, plus Zone partition component.
4. Its native Access preparation and repeatable-read check require a readable active Zone, active owner and current `zone:read`; `zones/eligibility.ts:zoneReadEligibility`, `zoneReadable`, `zoneWithheld` retain public floor/lifecycle semantics. Unknown, unreadable, deleted or wholly withheld Zone is concealed 404.
5. `zones/page-runtime.ts:readZonePage` selects that head before `access/gates/admission.ts:admitGroup('zone_sources')`. Static source-free documents bypass the group; a Subject GET always depends on sources. Exposure admission grants neither Collection nor Subject rights.
6. `zones/membership.ts:createZoneMembership` prepares each saved scope using `search/service-scope.ts:createSearchScopeForService`, reader context/native T and the saved release digest. It uses the service's registered constructor runtime, never a replacement adapter.
7. Every mount first calls `library/collection-source.ts:createCollectionSource().prepare`. Only native `not_found` omits a mount; readiness/dependency failures propagate. Structural UUID mounts use `readCanonicalSourceState` and `seekCanonicalSourceGroup`, then actual `containsSubject` with `CollectionAliasProgress`.
8. Filtered/ordered mounts instead obtain `library/collection-source-native.ts:readNativeCollectionScopeIdentity`, then use native Search Scope preparation. A Collection UUID is not a Source identity. GET needs neither this extra filter nor name/count ordering.
9. `zones/union.ts:advanceZoneUnion`, `initialUnionPosition`, `revalidateZoneUnion` retain complete discovery and current OR membership. Native `semantic/summaries.ts:readSubjectSummaries` supplies current summaries; `readSubjectSummaryObservation` additionally supplies source components and `current()`.
10. POST `zones/page-work.ts:zonePageWork` stores bounded locators, and `zones/page-continuation.ts` declares Search-profile query/202 schemas. Both hardcode Search transport. Neither is a ready-made default-profile GET endpoint.

## Field-by-field default cursor proposal

Use `tokens/list-cursor.ts:encodeListCursor` and `decodeListCursor` with omitted/default profile. The following is a proposed binding layout for adoption, not an implemented GET ABI.

| Field            | Proposed value and purpose                                                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `binding.route`  | Stable `GET /v1/zones/:id/subjects`; distinct method/operation from POST and all other lists.                                                                                                           |
| `binding.viewer` | Actual lowercase account UUID or null. Current bearer/account/scope checks still run on every use.                                                                                                      |
| `binding.query`  | `{zone: id, limit: normalizedP}`; no cursor itself, hidden mount IDs, mutable revision, or arbitrary client operation name. Fixed UUID order is part of this route's meaning.                           |
| `position.epoch` | Internal positive layout version, e.g. 1, not a claim that native identity or authorization is current.                                                                                                 |
| `after[0]`       | 64-byte digest committing current Zone/source configuration+lifecycle revision, release pins, union producer bases and complete identity/meaning observation. A hash cannot supply missing observation. |
| `after[1]`       | Existing server generation UUID: retained-state locator only.                                                                                                                                           |
| `after[2]`       | Decimal retained CAS revision: exact coordinate, not source truth.                                                                                                                                      |
| Additional keys  | None. Page start/floor, pending group and discovery locators stay server-side. No owner token vector, permissions, facts or summary payload.                                                            |

Three keys use `64 + 36 + d` ASCII bytes, where d is the database bigint revision's decimal length, at most 19: 119 bytes. Each fits 256 bytes,
versus eight keys/2,048 aggregate key bytes; route ≤256 and canonical query ≤2,048 bytes also remain independently enforced.
The default token limit is 4,096 unpadded base64url characters: ≤3,072 envelope bytes, 34 bytes envelope overhead and ≤3,038 plaintext capacity. The
encoder enforces resulting token length; retain all independent string/batch/schema limits.
Anonymous encoding is deterministic for an identical binding/position/key and timeless: synthetic salt, no issued-at field. Account encoding uses
random salt and issued time, 15-minute lifetime and 60-second future allowance. Do not add Zone expiry, anonymous time, random per-encode salt or Search's 4,864-character allowance.
Determinism does not make state immortal: generations change on actual replacement and coordinates change on progress. An unchanged anonymous coordinate encodes identically; an evicted coordinate conveys no authority.
Recommend 400 for cryptographically invalid/rebound tokens and 409 stale_cursor for expired or valid-but-incompatible/evicted coordinates, consistent
with GET witnesses in Zones. Exact expired/eviction mapping needs adoption; the codec exposes `invalid` versus `expired` and does not choose HTTP status.

## Bounded retained preparation and repair

The existing migration `services/kernel/db/zones/migrations/20261031010001_page_preparation.sql` allows 32 slots per Zone/viewer, one JSON position
≤1,048,576 bytes per row, keyed by route/Zone/viewer digest/slot. Thus position payload ≤32 MiB per Zone/viewer, not a global/per-account storage quota.
`zonePageWork` hashes normalized request body to a slot, checks request/basis/generation/revision, and CAS-writes a new revision only for changed
position. Its SQL checks an active configured Zone; the FK cascades purge and Zone configuration/lifecycle/owner/release/withholding updates delete retained rows transactionally.
Use an operation-tagged normalized GET descriptor for the slot hash; include operation and P to prevent POST/GET request confusion. Hash collisions
may evict other requests, never borrow their state. The token's AAD remains the independent operation boundary.
Existing storage supports a disposable bounded page frontier, not an unbounded complete result table, autonomous retry queue, per-viewer global quota
or retained authority. Search/Commerce retain their own prepared results and durable maintenance. Do not add a second scheduler or Zone membership engine.
Retain one `ZoneUnionPosition`: basis, settled `after`, ≤P selected row locators, at most one unfinished group, and optional discovery
`{next,rows,covered,exhausted}`. Discovery rows are ≤min(100,2×remainingSlots+1); source ordinal ≤32. Stored row source is a preferred lookup hint only.
The union queries every source through a common covered watermark before settling that interval. Partial discovery retains the next source ordinal
and common minimum coverage; it does not retain 32 owner cursors. Canonical `[id]` comparison is bytewise; duplicate IDs must have the same key.
When one source is unfinished, independent current true may settle OR **only inside the completely discovered interval**. Unknown is never negative
or EOF. Floor stays before the unresolved group; actual Collection alias/source progress or Search leaf progress survives.
Definitive false advances floor; true appends a locator once. A full page can retain an undisclosed discovery suffix. After final publication, clear
emitted rows in the following coordinate while preserving floor, suffix and pending progress; never replay the previous page's final leaves as the next page.
POST already models this clearing in `page-runtime.ts` before `preparation.progress(following)`. GET must preserve that separation of preparation
coordinate and successor coordinate; no partial 200 window, private seen set or UUID post-sort.
Final revalidation reruns actual current OR, preferring the located witness. A definitive negative removes that row and resumes filling after the
settled floor; unknown preserves its actual progress and gives preparation only after change. Do not drop a row merely because its summary is missing.
If membership stays true but native summary cannot be disclosed/current, return readiness and let the native owner repair/reject the locator.
Otherwise a withheld summary could falsely prove exhaustion. Final summary observation also protects representative editions, covers and foreign source tuples.
Basis changes cannot reinterpret an old floor under new canonical meaning. Reauthorize Zone and source gate first, then reject stale GET coordinates
and require an explicit new traversal; do not silently restart at zero on every request. Under stable basis, resume retained intervals without resetting.
Pending identity within the actual complete Source dependencies yields readiness; disjoint identity work must not create a universal gate. Changed
source/configuration, release/meaning or identity invalidates old membership and absence, including already successful cursor coordinates.
Existing CAS is finite but one-slot latest-revision storage is not replay history: a lost response after save makes the old token unusable. Recommend
retaining one predecessor transition beside the successor in the same JSON row, still ≤1 MiB total, rather than restarting a healthy traversal after each lost response.
For preparation replay, the predecessor locates the committed successor and returns its continuation; for a lost 200, retain the emitted page's locators and start/floor so the same page is rebuilt under fresh native checks before returning its successor. Store no DTO or verdict. Commit both coordinates atomically before responding; conflicting/older coordinates are explicitly stale. This is a proposed bounded store extension, not existing helper behavior or a public ABI.
The two positions may hold ≤2P selected locators and ≤200 discovery locators; enforce the existing byte ceiling before CAS. Replay always spends fresh authorization/final-use budget. Owner checkpoints resume actual input work with at most one uncommitted step reread; they do not certify old leaves. First-page retries can reuse the keyed initial preparation until completion; a deliberate no-cursor traversal still means First.

## Actual readiness, privacy and missing evidence

`createSearchScopeForService` rejects an unregistered service with index_not_ready. Scope `prepare` parses/admitFilter against the exact immutable release, refuses unsupported admitted plans, checks physical generation/UUID, captures Source/identity preparation and returns `readiness:'ready'` only after current observation revalidation.
Scope `prefix` executes a real count-free indexed UUID search with quota+lookahead and current checks before/after; `sourcePrefix` uses the native Collection Source order. `evaluate` uses native leaf evidence and can return not_proven/progress; it is not a public Search-page surrogate.
`scope-source.ts:current` revalidates scoped observations, optional public observation, Collection observation, native work definition where applicable, and physical index UUID. `scope-preparation.ts:createScopePreparation` retains definitions/frontiers and uses the existing Search work infrastructure; no helper registration implies readiness.
The Zone README's statement that all ordered preparation/prefix bodies are unavailable is too broad for current code: `scope-source.ts` now contains ordered preparation/native execution. This UUID GET does not rely on those bodies or relax their refusals.
Collection ordinary `prepare` supports native curated and private_builtin authorities with ready canonical state and matching Source fence. Activated/frozen public-output ordinary captures are explicitly dependency_unavailable in `ready`; work-context paths have separate native admission and are not GET shortcuts.
`containsSubject` reauthorizes Source, reads the canonical group, probes current original support, resolves original AND terminal disclosure, and reprobes the witness. An exhausted complete group can prove false; incomplete group/native evidence returns not_proven with progress only after actual keyset work.
Ready native cases therefore include an admitted empty union, ready curated canonical Sources with current eligible support, and ready saved catalogue scopes with installed Search, immutable release, complete prepared observation and native leaf support. These are callable readiness cases, not proof that every public case satisfies the future privacy boundary.
Missing metadata, pending canonical repair, incomplete source registration, absent indexed generation/release, unavailable native evidence and unready published output remain explicit refusals. A request cannot turn them into omitted sources, empty membership or successful low-cost samples.
The complete query-level privacy boundary remains with Semantic/Search/Commerce: Semantic records reductions in the authoritative transaction; Search observes required filter/order keys and returned subjects, ACKs only refresh-visible local AND dependent foreign repair, and revalidates the original covered cut plus retained execution start.
Current `semantic/public-filter-source.ts` has real per-home reduction log production. Neither the inspected Zone composition nor `Scope.current` establishes the complete indexed behind/changed observation, physical no-resurrection custody and final cut required by [current disclosure and query privacy](../filtered-lists.md#current-disclosure-and-query-privacy).
Candidate/summary Access cannot reconstruct excluded NOT inputs, missing intervals, ordering or hidden mounts, nor detect relevant reduce→repair→ACK between start and final. Index UUID, identity observation and generation equality do not certify those facts. This report selects no cross-home mechanism or new evidence ABI.
The guard is priced at the public GET cursor ingress: reject stale/unsafe membership AND exclusion, not just unsafe returned fields. Zone reads observe current Zone/owner/withholding; admitGroup observes exposure; Collection Source observes mount rights/support; Search owns complete indexed predicates/readiness/freshness; Semantic owns identity and reductions; native summaries own current fields/foreign fences.
Each authority must run on continuation and final use from the same admitted budget. Exposure never reveals a mount or releases source consent/fences. A stale successful page can reveal both inclusion and absence after revocation or canonical repair.
Healthy finite sparse completion additionally needs actual source/index readiness, eventually successful fair durable owner repair, affordable current full-page revalidation, and complete scoped identity bindings. All-unavailable routing is not completion. Ordinary 60-second searchable freshness, >5-minute lag readiness and next-read owner writes remain owner obligations.

## Work derivation: structural cap and owner ceilings

One GET has P≤100, at most S=16 saved scopes and M=16 mounts, N=S+M≤32. Use structural `zoneWork(deadline)`; do not request ordered slots to enlarge its cap. `ZoneWork` shares 256 aggregate structural candidate keys across preparation, prefix/lookahead, aliases, duplicates, rejects, rereads and final use.
Its current compatibility root is exactly: 65,536 charged native rows, 16,384 identity metadata rows, 256 empty seeks, 4,096 native points, 8,192 witness keys, 8,192 statements and 4,194,304 bytes. These are implementation ceilings, not the stricter useful-page cost proof.
Scope UUID prefix quota≤100 in the producer (Zone requests ≤99), quota+1≤budget≤256; Collection discovery seeks one canonical group, canonical raw allowance≤100, and ordinary group membership uses ≤min(groupLimit, floor(remainingKeys/4)). Receipts include internal driver/alias/duplicate/lookahead keys.
The union has ≤3 rounds, ≤N prefixes per round, hence ≤96 prefix calls. Per round it retains ≤100 discovery rows and attempts ≤100 settlements; ≤300 `contains` attempts plus ≤P final attempts, each considering ≤N streams. At most 32 initial Source prepares and 16 extra mounted canonical-state reads precede this. These conservative call bounds are not free I/O allowances.
Actual dispatched work must also fit the shrinking 256 key/root reservation; preferred positive witnesses reduce calls but grant no extra allowance. Source preparation and zero-result control work consume independent dimensions even when no candidate is returned. `LIMIT 1` cannot price a native probe or index iterator.
`zonePageWork` charges one exact read: 1 statement/point/row and 1,049,600 bytes; progress adds 1 statement, 2 points, 3 rows and 1,049,600 bytes; finish deletion adds 1 statement/point/row when usable. A read+save alone reserves 2,099,200 bytes, leaving 2,095,104 of the structural root for producers.
Positive ordinary Collection membership currently reserves `resolveSubject` at 8,192 rows, 128 points, 128 statements and 1 MiB, plus surrounding native probes. Rechecking 100 such witnesses alone exceeds the root (819,200 rows, 12,800 points/statements, 100 MiB). Retained locators cannot amortize away current authorization.
Consequently current helper ceilings do not establish an admitted P=100 implementation or finite final replay for every ready mount. Owners must supply measured bounded native current proof/batching and preparation/readback paths within existing budgets; increasing keys or caching final true is not a solution.

For admission/capture use the owning [filtered-list cost tables](../filtered-lists.md#cost) in addition to the structural cap. For one direct read let c≤min(256,600,6P+3), charged across every Source; for a ready-result read c≤min(256,2P+2). No per-source multiplication of the allowance is permitted.

| Unit                     | One admitted GET page / preparation request                                                                                                                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Output / candidates      | ≤P≤100 output; structural aggregate≤256 including all rereads; direct/ready plan candidate ceiling additionally applies.                                                                                                      |
| Source/index calls       | Direct catalogue≤6 engine searches / owner≤3 seeks, ≤3 refill rounds; ready result≤2 index reads. Excess union fanout is preparation, not 32 independent budgets.                                                             |
| Points / rows / blocks   | ≤16+8c points; ≤64+16c examined including removed rows; blocks≤6×budgeted examined rows. At c=256: 2,064 points, 4,160 rows, 24,960 blocks.                                                                                   |
| Statements / connections | One-read page≤12 statements per PostgreSQL backend, one connection per backend. Zone/source/safety/summaries/control are included, not added outside the page.                                                                |
| Bytes                    | Response PostgreSQL+engine≤16 KiB+4 KiB×c; request≤64 KiB+1 KiB×c. At c=256: 1,064,960 response and 327,680 request bytes. Public encoded response needs measured schema-width accounting too.                                |
| Durable preparation      | ≤1,000 input keys and result writes, one frontier write, 8 points/input, 64+16×input rows, 16 statements/backend, 4 engine searches, one connection/backend and 4 MiB response. GET still retains its 256 structural-key cap. |
| Privacy subset           | Shared ≤2 statements, ≤64+2×(behind homes+changed homes) rows, included in whole-page totals; no two 4,096-head sweeps or active-XID/history scan hidden in a digest.                                                         |
| State / cursor           | ≤1 MiB/slot, 32 slots/Zone/viewer; default token≤4,096 chars, eight keys, 256 bytes/key, 2,048 aggregate key bytes; summary batch≤256 IDs.                                                                                    |

For default P=20 the direct c ceiling is 123 (1,000 points, 2,032 rows); P=100 still caps structural c at256, not ordered600. These are ceilings requiring a feasible native plan, not claimed measured producer costs. A direct candidate limit does not bound OpenSearch iterator work.
Native summaries may address representative editions/media and independently routed fences; count those rows, statements, bytes and source components too. Existing root receipts do not instrument all summary/gate/Zone work; a new GET must include actual shared captures, not report those omissions as zero.
Prepared owner quota (32 live/owner, 24-hour idle expiry) and public one-current/one-building generations belong to their owners. Zone's 32 hashed slots are a different bound. Admission/eviction must compose both; a finite sparse build reads relevant input once, replaying at most one step.

## Adoption questions and complete implementation journey

Resolve together before publishing: GET retained-preparation status/body (recommend 202 `{next}` with default token), exact stale/expired/evicted-coordinate recovery, and the bounded predecessor replay policy above. None is implemented merely by choosing the codec above.
Owner dependencies are complete query safety/ACK and physical retained-copy custody, complete scoped Source/identity bindings, actual prepared output readiness, affordable current Source/summary proofs and inclusive cost capture. Build against those documented boundaries; do not fabricate a new certificate or weaken checks to claim availability.
The following is one complete implementation brief for adoption, not permission to publish this transport:

> Implement GET /v1/zones/{id}/subjects from request admission through a full current-summary page, preserving default cursor profile and 200 {subjects,next}. Adopt the GET preparation/recovery schema in the owning transport documents first; keep POST and collection metadata GET independent.
> Reuse createZoneReads().page, current zone_sources admission, real createZoneMembership and complete advanceZoneUnion/revalidateZoneUnion. Use native safe summary observations, native session components and current final field/source/Zone/exposure checks; conceal Zone before gate detail and never downgrade invalid credentials.
> Factor the bounded preparation store's transport policy to use default encodeListCursor/decodeListCursor and operation-tagged request binding. Retain complete common coverage, unresolved group progress and undisclosed suffix; clear published rows only into the successor coordinate. Bind every mutable meaning without exposing hidden mounts or reusable truth.
> Deliver finite sparse preparation, crash/response-loss replay and current final-use proof together. Close owner readiness/cost dependencies through their documented native contracts; do not mount an all-unavailable substitute, create a new Search adapter, cache permission, or increase the structural aggregate256 cap.
> Generate and install @rezics/client declarations with `bun run --cwd services/kernel client`; extend `services/kernel/test/client.test.ts` and a real installed-package consumer so default GET success, preparation, Problem and stale recovery are received through the generated API. No handwritten declaration or mock success counts.
> Extend native `test/zones/membership-contract.test.ts`, `static-page-runtime.test.ts`, `public-slice-exposure.test.ts`, `test/search/scope-source-contract.test.ts` and `test/library/canonical-source-store.test.ts` using their actual resource fixtures and Search runtime. > Prove P=1/20/100 and invalid limits; full pages/final EOF; overlap across 16 scopes+16 mounts; duplicate originals/occurrences; canonical first/deep order and last eligible original in a 4,096-original group; unknown intervals, pending identity, source removal/restoration and withheld summaries. Run changed test files with the Kernel landing command and affected workspace typing; integration owns the full native/browser/root checks. Research inspection itself is no executed acceptance.
