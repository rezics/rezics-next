# Merge queue throughput

Research date: 2026-10-27. This is evidence and a recommendation for the manager, not a change to the train's contract.

## What matters here

The current train rebases and formats each worker on dev, checks scope, and validates the candidate. An advancing dev invalidates an in-flight attempt. In `tools/goal/src/merge-train.ts`, integration checks are already selected by changed path, and the result is already stored as a candidate baseline under the candidate commit and the serialized **set** of selected commands. On failure the same command set is looked up or run on the base, and normalized error lines are compared. This is a baseline-tolerant gate, not a guarantee that every dev commit is green. Promotion has a separate 40–60 minute remote stabilize gate; changing dev throughput does not speed that gate.

Given 23 landings/hour, 78 s median, 221 s mean and a 33-item queue, the 33 represent about 86 minutes of work at observed throughput if arrivals stopped. The timing distribution, concurrency, failures and measurement window are unknown. In particular 3600/221 = 16.3/hour is not directly comparable to the observed 23/hour: landing elapsed time can include overlapping work or waiting. Do not use the median as the service time or promise a speedup from it.

## Evidence from existing queues

- **GitHub merge queue.** [Official documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) describes cumulative merge-group candidates and build concurrency of 1–100, and configurable minimum and maximum group size. A failed required check normally removes its PR and rebuilds following groups. An option permits failed intermediate PR checks if the final group passes, explicitly trading per-PR evidence for tolerance of intermittent failures. There is no documented general automatic bisection in the cited documentation. Required checks are supplied by CI; path-based selection and caching are CI design choices, not a queue guarantee. No measured landings/hour is stated in this source.
- **GitLab merge trains.** [Official documentation](https://docs.gitlab.com/ci/pipelines/merge_trains/) describes parallel cumulative merged-result pipelines A, A+B, A+B+C. A failure removes its MR and cancels and recreates downstream pipelines; a dropped pipeline cannot simply be retried because its result is stale. CI jobs can be selected by [`rules:changes`](https://docs.gitlab.com/ci/yaml/#ruleschanges), but pipeline source and comparison base matter; merged-result commits can alter which files are considered. Retry of a job can address transient failure while its candidate remains valid; this is not an automatic flake classifier. The source snapshot has train behavior in `app/services/merge_trains/` and `app/models/merge_trains/`, and explanation in `doc/ci/pipelines/merge_trains.md` (GitLab MIT for applicable code, CC BY-SA 4.0 for docs; see its LICENSE for exceptions). No measured rate is stated in the cited train documentation.
- **bors-ng.** Its [README](https://github.com/bors-ng/bors-ng) describes batching approved PRs, fast-forwarding a passing staging commit, splitting a failing batch, and rejecting a failing singleton. Source `lib/worker/batcher/divider.ex` actually splits patches; conflict handling is separate. [Commands](https://bors.tech/documentation/) include `bors retry` and `max_batch_size`; manual retry is not automatic flake diagnosis. A batch pass checks its final tree, not every intermediate PR state. The README's O(E log N) description is a simplifying claim, not a general bound with interactions, retries or changing bases. Check selection and caches belong to CI; no measured rate was found in these sources. Source licence: Apache-2.0.
- **Zuul.** [Project gating](https://zuul-ci.org/docs/zuul/latest/gating.html) and [dependent pipelines](https://zuul-ci.org/docs/zuul/latest/config/pipeline.html) use speculative cumulative candidates; a failed earlier change removes that change and invalidates dependent results. Source `zuul/manager/dependent.py` and `zuul/manager/__init__.py` implement the pipeline managers. [Job file matchers and attempts](https://zuul-ci.org/docs/zuul/latest/config/job.html) select jobs using files and allow retry of execution/infrastructure errors; normal test failure is not automatically reclassified as flaky. There is no general bisection or baseline cache guarantee in those sources. No measured rate is stated there. Source licence: Apache-2.0.
- **Mergify.** [Batching and failure handling](https://docs.mergify.com/merge-queue/batches/) splits a failing batch, tests parts against appropriate preceding parts, merges passing prefixes and requeues invalidated later work. [Performance](https://docs.mergify.com/merge-queue/performance/) describes cumulative speculative batches and CI path scoping. Optional `skip_intermediate_results` permits a later pass to cover an earlier failure, with an explicit warning that checks comparing only the later batch's own diff do not cover earlier changes. This reduces flake disruption but can mask real intermediate failures. The documented 6 PRs in 10 minutes with two parallel batches of three is an illustrative ideal, not measured production throughput. Baseline caching is not established by these sources.
- **Aviator.** [Batching](https://docs.aviator.co/mergequeue/concepts/batching) combines cumulative speculative pipelines with batch splitting after failure; updates or removals reset affected downstream candidates. [Optimistic validation](https://docs.aviator.co/mergequeue/concepts/managing-flaky-tests-in-mergequeue) can wait for a later passing cumulative candidate when an earlier candidate fails, with bounded lookahead. It can delay rejection of a real failure and does not prove every intermediate state passed. Its example of six PRs in two pipelines rather than two is illustrative, not a measured rate. Path selection and baseline caching are not established by these cited queue documents.
- **Uber SubmitQueue.** The authors' [2019 EuroSys paper](https://doi.org/10.1145/3302424.3303970) reports production scale of thousands of daily commits and describes conflict analysis and speculative alternative outcomes, not just a single optimistic prefix. The authors' [2025 paper](https://arxiv.org/abs/2501.03440) reports approximately 53% less CI resource use, 44% less CPU and 37% lower P95 wait after scheduling improvements across major monorepos; these are measured relative changes, not a transferable landings/hour prediction. [Uber's account](https://www.uber.com/rs/en/blog/slashing-ci-costs-at-uber/) describes hundreds of changes/hour across monorepos. The open-source implementation's `doc/rfc/submitqueue/speculation.md` and `submitqueue/orchestrator/controller/speculate/` describe bounded path selection, invalidation and merge after dependencies resolve; `doc/rfc/submitqueue/workflow.md` describes the controllers. Source licence: Apache-2.0. The papers use build dependency analysis to identify affected work and conflicts, which is stronger than a simple path heuristic. The cited sources do not establish an equivalent baseline cache or a universal flake retry policy; do not assume one. The open-source implementation is a current design, not necessarily identical to the historical paper's production system.

Source snapshots are in `.reference/merge-queues/` in the main checkout; `.reference/INDEX.md` records URLs, exact commits, licences and date. GitHub, Mergify and Aviator are cited through their official public documentation rather than assumed open-source queue implementations. The snapshots were read as data, not executed.

## Shared patterns and correctness boundaries

The common optimization is to validate a **specific predicted future tree** while earlier work is unresolved, or to amortize a validation over a group. Parallel speculation consumes more simultaneous CI resources and wastes work on an invalidated suffix. Batching saves runs on passing groups but makes fault attribution slower and can hide a broken intermediate commit. Bisection identifies a failure relative to the current passing prefix; interacting changes, flaky tests, and a pre-existing red base can make a single culprit impossible to identify. Do not silently drop or blame an innocent worker. A retry must retain the same candidate, environment and check identity; a timeout or infrastructure failure is not evidence of a code regression.

Path filtering is safe only with a conservative dependency map, including shared configs, lockfiles, generated outputs, deletions and renames. Unknown paths or map changes should trigger the full relevant suite. A check comparing a diff must cover the entire cumulative candidate against its actual starting base, not only the last worker. Cache a result only for the exact tree or commit, command, toolchain, dependencies, environment and relevant configuration; mutable services and nondeterministic tests require expiry or no reuse. A cached known failure is evidence of a baseline, not evidence of a pass. Flake retries should be bounded and recorded, and persistent infrastructure failures should stop the affected gate rather than become success.

## Recommendation, in benefit per effort

1. **Measure and improve existing per-check baseline reuse.** Record per-stage duration, base/candidate identities, individual command results, cache hits, invalidations, failure fingerprints and queue time. Split the existing combined baseline key into independently keyed check results, preserving output and comparison semantics. Include toolchain, lockfile, check version and environment in the key; invalidate on changes. Never cache a timeout as a stable baseline. This helps only failure paths or changed combinations, so expected throughput is **23–25/hour**, a planning estimate, not a measured forecast. Risk: false equivalence, stale red baselines and nondeterminism. First verify the observed baseline miss rate.
2. **Run independent integration commands concurrently, with resource limits.** They currently run sequentially; preserve all results and the per-command baseline comparison, and isolate commands that mutate shared files or generated outputs. Measure CPU, memory and elapsed time before increasing concurrency. If gate time is 30–50% of landing time and its parallelizable part shrinks by half, the simple service-time model predicts roughly **27–31/hour** from 23/hour; actual values could be unchanged under host contention. Risk: cross-check interference and resource contention. Do not parallelize the recorded-response generator with commands that read its outputs without isolation.
3. **Speculate a small ordered window, initially depth 2–3.** Construct immutable cumulative candidates in isolated worktrees: dev+A, dev+A+B, dev+A+B+C, including each worker's rebase, formatting, scope and selected checks. Persist queue order, input revisions, expected base, exact resulting tree and gate evidence. Only land in order with a compare-and-swap on the expected dev head; reuse the next result only if the actual preceding landed tree and all check inputs match. A failed, edited, cancelled or conflicting predecessor invalidates and cancels its dependent suffix; rebuild it from the new base. Crash recovery must recheck fences and never publish stale results. Keep per-worker gates and cumulative diff coverage. At depth 2–3, if CI capacity is available and 70–85% of work survives invalidation, a rough saturated-queue target is **32–50/hour**; this is an illustrative 23 × 2–3 × 0.70–0.85, not a prediction or additive to earlier estimates. Measure actual hit rate and CPU saturation, and roll back if reliability or tail latency worsens.
4. **Only then test batches of 2–3 under backlog.** Run per-worker scope and formatting before grouping. Check the combined tree; publish it atomically only when the checked tree is exactly what will land. Bisect a failing group against the last accepted base, rerunning the other part after the base changes. Bound retries and splits; report interaction or indeterminate failure rather than assuming singleton guilt. Avoid waiting to fill a batch when the queue is short. Ideal batch size 2–3 could raise the 23/hour baseline to **46–69/hour** under sustained backlog and unchanged gate duration; failure, setup cost and batching delay reduce this, and this is not additive to speculation's estimate. This changes the guarantee: intermediate worker commits may not have independently passed. Adopt only if dev consumers accept that policy and atomic publication preserves the existing record of individual outcomes.
5. **Refine path selection conservatively after collecting evidence.** The train already has path-configured checks, including the kernel client/web check. Extend only with an audited dependency map and a full-suite fallback; periodically shadow skipped checks to estimate misses. Expected gain is **unquantified** until per-check duration and affected-path frequencies are measured. Shared changes can break unrelated checks; stabilize is a separate backstop, not permission to weaken dev silently.

Do not adopt later-pass-overrides-earlier-failure or ML conflict prediction initially. The former weakens per-worker evidence and interacts badly with diff-scoped checks and red-base comparisons; the latter needs substantially more telemetry and complexity than this queue currently justifies. For known transient failures, retry the same check once with a recorded reason and limit; quarantine only through an explicit gate policy, never by automatically treating failures as passes.

Success criteria for a pilot: compare a similar backlog and host capacity before/after; report completed landings/hour, queue and gate P50/P95, CI CPU-minutes per landing, suffix invalidation rate, baseline cache hit/miss, retries, and regressions reaching dev and stabilize. Keep one-at-a-time mode as a fallback. These estimates are alternative scenario targets, not guaranteed results; measure before choosing depth and batch size.
