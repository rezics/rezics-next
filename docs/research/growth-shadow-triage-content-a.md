# Content growth shadow triage

Inspected on 2026-10-28. Paths in the table are relative to `services/kernel`.
Each entry assigns one disposition to the rejection and names the change needed
before enabling the series gate. These are recommendations; no implementation,
test, bound or calibration is changed here.

The declarations are the [Content Cost derivations][content-cost], including
their [Access contribution][access-cost]. Index names and keys were checked in
the [Content schema][content-schema]. `N` is the check's scale, `P` a growing
stored relation, and `h(P)` its integer index height. An exact B-tree probe has
constant examined rows but `O(log(2+P))` blocks. Shared, route-leading indexes
grow with the whole relation, even when the selected partition stays fixed.
`A` and `C` retain the README meanings of Access and the command envelope.

The harness counts scan output **and filtered candidates**, not only returned
objects. Consequently a small-table sequential scan can have _more_ measured
rows than the later exact-key index plan. This is a test-range problem when a
check claiming representative indexed work starts with only tens or hundreds of
rows. It is not evidence that a primary-key lookup traverses the growing history.
Every check below has one warm-up per scale; repetitions in the table exclude it.
The harness vacuums/analyzes after growth, before the warm-up, and does not reset
application relations between repetitions.

The calibrated intervals used here are `E_rows = 22`,
`E_blocks = max(9, 0.03 × median_blocks)`, and exact statements. This follows
`shadowVerdict`'s absolute/relative **maximum**, rather than adding the two
allowances. The checked-in uncertainty defaults are different; a fresh profile
must be classified again with these calibrated values. With a constant family,
the intervals can overlap across a row-count range of 44, not merely 22.

An additional distinction matters for the block entries: `classifySeries`
requires a two-sided fit to `a+b log(N/N0)` (or an allowed simpler family),
with nonnegative parameters. It does not accept every function in `O(log N)`.
Integer height changes and batches of point probes need an explicit model
allowance, as [the classification report already requires][classification].
Those are **B** dispositions below when the operational curve is tighter than
the SQL derivation; they are not attributed to vacuum or hint-bit noise without
evidence. **T** takes precedence where the check itself confounds the scale with
plan selection or accumulated write history.

Counts: **R 0, B 4, N 0, T 18** (22 metric entries, 21 distinct
file/check pairs). No static SQL derivation here requires an unbounded scan of
the seeded history for the named fixed-key operation. T is a finding about the
check's ability to establish that derivation, not permission to dismiss its
observed rejection or skip its repair.

The repeated pattern is an undersized first population followed by a cheaper
indexed plan. Since all fitted slopes are nonnegative, a substantial downward
row step is incompatible even though the operation improves. A row floor
calibrated from repeated executions of an unchanged plan does not describe that
plan transition. Fix the representative range rather than inflate the 22-row
allowance to cover table scans. The media fixture intentionally holds the
admitted actor inverse at 1,000
entries: `permission-inverse.sql` reads that fixed account anchor, so the later
1,000-plus-row plateaus are consistent with A, not growth in uploader history.
`permission-candidates.sql`/`permission-check.sql` probe grown grant relations
for bounded admitted keys; a small-relation scan can multiply filtered work
across those keys. The aggregate profile cannot assign the entire initial
826,441-row reservation sample to one such subplan. The write checks also need
an explicit choice
between fresh state and a seeded repeat-update history; one measured repetition
cannot establish a within-scale noise distribution.

The B entries expose a different issue: a smooth finite-range curve is stricter
than a logarithmic index-cost derivation, and a batch whose count and index size
both grow has a composed cost. Retain those terms in the model. None of these
static facts justifies a universal increase to 9 blocks/3%, and no entry is
assigned N merely because it writes. In particular, obsolete tuples/HOT pruning
can change blocks, but dead tuple chains are not extra logical scan rows in
`growth-cost.ts`; that explanation cannot substitute for a row-plan derivation.

Verification ran the normal kernel check path with `GROWTH_PROFILE`, limited to
`growth-media.test.ts`, `growth-sitemap.test.ts` and `cover-metadata.test.ts` once
each. All **19 tests passed**. Reclassifying the profile through `classifySeries`
with the calibrated intervals above reproduced all **12 assigned metric
rejections** in those files, without editing the checked-in uncertainty module.
The table records the medians in scale order and the smallest allowed-family
uncertainty multiplier `t`; compatibility requires `t<=1`. All other entries
are static audits;
their original coverage medians and per-statement plans were not supplied. The
new aggregate profile also does not retain per-statement plans. Small-relation
plan selection is inferred from the SQL, seed sizes and, where measured, the
large downward row steps; this report does not claim a particular scan node or
vacuum/hint-bit event was captured. For the reused-state entries, the concrete
fixture defect must be repaired before attributing a residual to storage noise.
